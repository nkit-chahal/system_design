Expert Parallelism for MoE Training

Introduction

In standard transformer training, every parameter in the neural network participates in the computation of every single token. As models scale from 8 billion to 70 billion and 405 billion parameters, the floating-point operations (FLOPs) required per token scale linearly with parameter count. This coupling creates a harsh computational ceiling: training a dense 405B model requires tens of thousands of GPUs running for months, consuming tens of millions of dollars of electricity and compute (see Lesson 7, Training FLOPs, Time and MFU).

Mixture-of-Experts (MoE) breaks this linear coupling by replacing dense feed-forward networks (MLPs) with a set of E independent "experts", coordinated by a lightweight parametric router [1]. For each incoming token, the router evaluates the token's hidden state and dynamically activates only the top-k most relevant experts (typically k=1 or k=2 out of E=8 or E=16). The remaining E−k experts sit completely idle for that token. This architectural sparsity enables a model to expand its total parameter capacity by 4× to 10× while holding the compute FLOPs per token strictly constant.

In Inference Lesson 35, Mixture-of-Experts Serving, we examined how MoE models are served in production, focusing on KV cache sizing, weight offloading, and batched decode throughput. Training an MoE model, however, introduces fundamentally different systems and algorithmic challenges that do not exist in inference.

During training, the system cannot treat idle experts as free. In mixed-precision Adam, every parameter across all E experts requires 16 bytes of memory for weights, gradients, master weights, and optimizer moments, regardless of how rarely that expert is selected (see Lesson 3, Training Memory). Furthermore, the router's gating parameters must learn via backpropagation, creating severe optimization pathologies such as router collapse where a few popular experts monopolize all tokens. Distributing experts across devices via Expert Parallelism (EP) requires four high-volume All-to-All communication collectives on every training step [7], [8]. In this lesson, we examine the mechanics of training MoE models, analyze load-balancing objectives and dropless execution, derive the All-to-All network traffic, explore DeepSeek-V3's auxiliary-loss-free balancing, and determine how to train an MoE version of our running model.

Clarifying the Problem

In machine learning infrastructure interviews, Mixture-of-Experts questions focus on routing differentiability, load balancing losses, All-to-All interconnect scaling, and the asymmetry between compute FLOPs and memory footprint. Here is how a discussion between a candidate and an interviewer typically unfolds:

Candidate: How should we distribute the experts across GPUs, and what communication pattern will that create?
Interviewer: We want to use Expert Parallelism (EP). How do the tokens move between GPUs during the forward and backward passes, what is the network traffic volume per step, and can our interconnect support it?

Interviewer: We need to evaluate the classic Switch Transformer auxiliary loss, the ST-MoE router z-loss, dropless token routing via MegaBlocks, and the auxiliary-loss-free dynamic bias strategy introduced by DeepSeek-V3. The real question underneath is: How do we train a sparse MoE model where compute scales with active parameters but memory scales with total parameters, prevent routing collapse without corrupting the loss gradient, and orchestrate All-to-All communication over physical network fabrics? To answer it, we begin by analyzing the router's gradients and load balancing.

Router Gradients, Collapse, and Load Balancing

How router gradients flow

In a standard top-k MoE layer, let x∈ℝh represent a token's input hidden state, and let E be the total number of experts. The router computes a raw affinity logit H(x)∈ℝE using a linear projection with weight matrix Wg∈ℝE×h [1]:

H(x)=Wgx

The router selects the indices of the k highest logits using the TopK operator:

𝒯=TopK(H(x),k)

The gating weights G(x)∈ℝE assigned to the selected experts are computed by applying a softmax function exclusively over the top-k logits (setting the gating values for all unselected experts to zero):

Gi(x)={exp(Hi(x))∑j∈𝒯exp(Hj(x))if i∈𝒯0otherwise

The final output of the MoE layer y is the linear combination of the selected expert outputs weighted by their gating coefficients:

y=∑i∈𝒯Gi(x)·Experti(x)

A central theoretical subtlety arises during backpropagation: the TopK selection operator is a discrete step function with zero derivative almost everywhere. The router cannot learn which experts to select via direct gradient descent on the discrete selection decision. Instead, gradients backpropagate through the continuous softmax gating coefficients Gi(x) [1], [2]:

∂ℒ∂Wg=∑i∈𝒯(∂ℒ∂y·Experti(x))∂Gi(x)∂H(x)x⊤

If expert i produces an output that reduces the overall loss, the gradient pushes the router logit Hi(x) upward for similar tokens, making expert i more likely to be selected in future forward passes.

The pathology of router collapse

Because the router learns through this gradient feedback loop, unconstrained top-k routing suffers from severe positive feedback instability, known as router collapse (or representation collapse) [1], [2].

At the start of pretraining, weights are initialized randomly. By chance, expert 0 might receive slightly better initial weights than expert 1 for common grammatical tokens. The router routes more tokens to expert 0. As a consequence, expert 0 receives more gradient updates and improves faster than other experts. The router observes lower loss from expert 0 and increases its routing probabilities further. Within a few thousand training steps, the router collapses onto a small subset of experts (e.g., 2 out of 8), dispatching 95%+ of all tokens to those experts while the remaining experts receive zero tokens.

Router collapse is catastrophic for two reasons:

  1. Hardware underutilization: In distributed training, each expert is hosted on a different GPU. If 95% of tokens route to GPU 0, GPU 0 runs out of memory or compute capacity while the other 7 GPUs sit completely idle, collapsing cluster throughput.
  2. Capacity loss: The parameters in the starved experts are never trained, reducing a 22B-parameter MoE model to the effective representational capacity of an 8B model while still paying the memory overhead of all 22B parameters.

The Switch Transformer auxiliary load-balancing loss

To prevent router collapse, Fedus et al. introduced the canonical auxiliary load-balancing loss in Switch Transformers (JMLR 2022) [2]. The auxiliary loss adds a penalty to the training objective that punishes non-uniform token distributions across experts.

For a batch ℬ containing T total tokens across all data-parallel ranks, define two vectors across the E experts:

  1. Dispatch fraction vector (f∈ℝE): The actual fraction of tokens assigned to expert i by the discrete TopK selection: fi=1k·T∑x∈ℬ1{i∈TopK(H(x),k)} Because of the indicator function 1, fi is discrete and non-differentiable.
  2. Probability fraction vector (P∈ℝE): The average router softmax probability assigned to expert i across all tokens in the batch: Pi=1T∑x∈ℬSoftmax(H(x))i Because it averages continuous softmax outputs before top-k truncation, Pi is smooth and differentiable.

The Switch Transformer auxiliary loss is the scaled dot product of these two vectors [2]:

ℒaux=α·E∑i=1Efi·Pi

Where α is an auxiliary loss hyperparameter, typically set to α=0.01 or 0.001. The scaling factor E ensures that under perfect uniform balance (where every fi=1/E and every Pi=1/E), the loss evaluates to a constant:

ℒauxuniform=α·E∑i=1E(1E·1E)=α·E·E·1E2=α

If the router begins routing disproportionately to expert i, both fi and Pi become large, causing their product fi·Pi to spike quadratically. Because Pi is differentiable, taking the derivative with respect to the router weights ∂ℒaux/∂Wg provides strong, continuous gradient feedback that pushes probabilities away from overloaded experts and toward underutilized experts, enforcing balanced routing across the cluster.

Router z-loss in ST-MoE

In 16-bit mixed-precision training (BF16 or FP16), router projections introduce a subtle numerical instability. As training progresses, the logits H(x)=Wgx can drift to large absolute magnitudes (e.g., +50 or −80). While softmax is mathematically invariant to constant shifts, in floating-point arithmetic computing exp(Hi(x)) with large positive logits causes numerical overflow (inf), while large negative logits produce subnormal underflow. This leads to NaN gradients that corrupt router weights.

To eliminate this instability, Zoph et al. introduced the router z-loss in ST-MoE (2022) [3]. The z-loss penalizes large values in the log-normalizer (log-sum-exp) of the router logits:

ℒz=czT∑j=1T(log∑i=1Eexp(Hj,i))2

Where cz is a small weighting coefficient (typically cz=10−4 or 10−3). The z-loss penalizes logits that drift far from zero without altering their relative ranking. ST-MoE demonstrated that adding the router z-loss eliminates loss spikes and allows stable long-duration pretraining without requiring manual gradient clipping or FP32 router casts [3].

Capacity factor, token dropping, and MegaBlocks

Even with an auxiliary load-balancing loss, token assignments fluctuate dynamically across micro-batches. On some batches, an expert might receive 12% of the tokens; on others, 18%. In early MoE implementations (such as Mesh-TensorFlow and Tutel), GPUs required rigid, static tensor dimensions to execute fast cuBLAS GEMM kernels [8].

To enforce static tensor dimensions, systems established a fixed expert capacity (C):

C=Capacity Factor×(k·B·sE)

Where the Capacity Factor (CF) is a slack hyperparameter (typically 1.0 to 1.5). This rigid capacity created a punishing dilemma:

  • Token dropping: If an expert received more tokens than its capacity C, the excess tokens were dropped—passed around the expert layer via residual connection without MLP processing. Dropping tokens degraded model reasoning and factual recall.
  • Padding waste: If an expert received fewer tokens than C, its input tensor was padded with zeros. A capacity factor of 1.5 wasted up to 33% of GPU memory and compute on dummy padding tokens.

To solve this dilemma, Gale et al. developed MegaBlocks (MLSys 2023) [4]. MegaBlocks reformulates MoE computation as a block-sparse matrix multiplication (dMoE). Instead of padding ragged token counts into uniform dense tensors, MegaBlocks implements custom GPU kernels that execute directly on variable-length token assignments. Every expert computes on exactly the number of tokens routed to it. Token dropping is completely eliminated (CF=∞), zero compute is wasted on padding, and end-to-end training throughput improves by up to 40%. Modern frontier MoE models (Mixtral 8x7B, DeepSeek-V3) universally operate dropless using block-sparse execution.

DeepSeek-V3's auxiliary-loss-free balancing

While the Switch Transformer auxiliary loss successfully prevents router collapse, it introduces an unavoidable quality penalty: the gradients of the auxiliary loss directly conflict with the gradients of the primary language modeling loss [6]. The auxiliary loss forces the router to dispatch tokens evenly across experts, even when a specific expert is genuinely superior for a given token. This trade-off forces practitioners to tune α delicately: if α is too small, the router collapses; if α is too large, model perplexity degrades significantly.

To eliminate this fundamental trade-off, DeepSeek-AI introduced an auxiliary-loss-free load balancing strategy in the DeepSeek-V3 Technical Report (December 2024) [6]. Instead of adding penalty terms to the loss function, DeepSeek-V3 decouples load balancing entirely from backpropagation by introducing dynamic, expert-specific bias terms.

The mechanism operates in three steps:

  1.   2. Dynamic step-by-step bias updates (zero loss gradients): At the conclusion of each training step, the system measures the actual token count Li dispatched to expert i across the batch. DeepSeek-V3 demonstrated near-perfect load balance across 256 fine-grained routed experts with zero degradation in pretraining loss [6].

Expert Parallelism (EP) and All-to-All Communication

Sharding experts across devices

When training an MoE model, the E experts within each layer are sharded across Ep GPUs, where Ep is the Expert Parallel (EP) degree. In a typical configuration with E=8 experts, Ep=8, placing exactly one expert per GPU inside an 8-GPU node [7], [8].

Because each GPU hosts a different expert, tokens must be physically routed across GPUs based on the router's top-k decisions. This routing is executed via collective All-to-All (A2A) communication.

The Four All-to-All collectives per training step

In standard dense training, a layer requires communication only during the backward pass (for data-parallel gradient synchronization) or within the layer (for tensor-parallel All-Reduces). In Expert Parallelism, communication occurs in both forward and backward passes, totaling four All-to-All collectives per MoE layer on every training step:

  1. Forward Dispatch (All-to-All #1): Each GPU routes its local tokens. If token t selects expert e located on GPU j, the hidden state vector of token t (shape [h]) is transmitted from GPU i to GPU j. Every GPU sends and receives slices of tokens to and from all other GPUs in the EP group.
  2. Forward Combine (All-to-All #2): After each GPU executes its local expert MLP on its gathered tokens, the resulting output activation vectors (shape [h]) must be sent back to the tokens' originating GPUs. Originating GPUs receive the outputs, multiply them by their gating coefficients Gi(x), and accumulate them into the residual stream.
  3. Backward Dispatch (All-to-All #3): During backpropagation, the gradients of the loss with respect to the expert outputs (∂ℒ/∂y) are generated on the originating GPUs. These activation gradient vectors must be dispatched back to the GPUs hosting the respective experts so that local expert backward passes can compute weight gradients ∂ℒ/∂We.
  4. Backward Combine (All-to-All #4): After local expert backward execution, the gradients with respect to the expert inputs (∂ℒ/∂x) are gathered back to the originating GPUs to propagate gradients through the attention block and earlier layers.

Worked traffic arithmetic: Mixtral 8x7B

To quantify the network bandwidth demanded by Expert Parallelism, we evaluate the exact data volume transferred across the four All-to-All collectives. Consider a model with the architecture of Mixtral 8x7B [5]:

  • Layers: L=32
  • Hidden dimension: h=4,096
  • Experts per layer: E=8, top-2 routing (k=2)
  • Expert Parallel degree: Ep=8 (1 expert per GPU across 8 GPUs)
  • Micro-batch size: b=1, sequence length: s=8,192 tokens
  • Precision: BF16 (2 bytes per element)

For one micro-batch on one GPU, the number of input tokens is b×s=8,192 tokens. Because each token selects k=2 experts, the GPU must dispatch 2×8,192=16,384 token vectors. Each token vector contains h=4,096 elements×2 bytes=8,192 bytes (8 KiB).

    PyTorch MoE Layer
    Megatron-LM MoE config
    import torch
import torch.nn as nn
import torch.nn.functional as F

class Top2MoELayer(nn.Module):
    def __init__(self, hidden_dim: int = 4096, ffn_dim: int = 7168, num_experts: int = 8,
                 aux_loss_coeff: float = 0.01, z_loss_coeff: float = 1e-4):
        super().__init__()
        self.num_experts = num_experts
        self.aux_loss_coeff = aux_loss_coeff
        self.z_loss_coeff = z_loss_coeff

        # Gating router: projects hidden_dim to num_experts logits
        self.router = nn.Linear(hidden_dim, num_experts, bias=False)

        # Independent expert MLP blocks (SwiGLU)
        self.experts = nn.ModuleList([
            nn.Sequential(
                nn.Linear(hidden_dim, ffn_dim, bias=False),
                nn.SiLU(),
                nn.Linear(ffn_dim, hidden_dim, bias=False),
            )
            for _ in range(num_experts)
        ])

    def forward(self, x: torch.Tensor):
        # x shape: [batch_size, seq_len, hidden_dim]
        orig_shape = x.shape
        x_flat = x.view(-1, orig_shape[-1])  # [num_tokens, hidden_dim]
        num_tokens = x_flat.size(0)

        # 1. Compute router logits
        logits = self.router(x_flat)  # [num_tokens, num_experts]

        # 2. Router z-loss (ST-MoE: penalize large logits to prevent overflow)
        logsumexp_logits = torch.logsumexp(logits, dim=-1)
        z_loss = self.z_loss_coeff * torch.mean(logsumexp_logits ** 2)

        # 3. Softmax probabilities across all experts (for aux loss and gating)
        probs = F.softmax(logits, dim=-1)  # [num_tokens, num_experts]

        # 4. Top-2 Expert Selection
        top2_weights, top2_indices = torch.topk(probs, k=2, dim=-1)
        # Normalize top-2 weights so they sum to 1
        top2_weights = top2_weights / (top2_weights.sum(dim=-1, keepdim=True) + 1e-9)

        # 5. Switch Transformer Auxiliary Load Balancing Loss
        # f_i: fraction of tokens routed to expert i
        mask = F.one_hot(top2_indices, num_classes=self.num_experts).sum(dim=1)  # [tokens, experts]
        dispatch_fraction = mask.float().mean(dim=0)  # [num_experts]
        prob_fraction = probs.mean(dim=0)             # [num_experts]
        aux_loss = self.aux_loss_coeff * self.num_experts * torch.sum(dispatch_fraction * prob_fraction)

        # 6. Dispatch and combine token computations
        out = torch.zeros_like(x_flat)
        for expert_idx, expert in enumerate(self.experts):
            # Mask tokens routed to this expert (in position 0 or position 1)
            selected_pos0 = (top2_indices[:, 0] == expert_idx)
            selected_pos1 = (top2_indices[:, 1] == expert_idx)

            if selected_pos0.any():
                tokens0 = x_flat[selected_pos0]
                weights0 = top2_weights[selected_pos0, 0:1]
                out[selected_pos0] += weights0 * expert(tokens0)

            if selected_pos1.any():
                tokens1 = x_flat[selected_pos1]
                weights1 = top2_weights[selected_pos1, 1:2]
                out[selected_pos1] += weights1 * expert(tokens1)

        total_aux_loss = aux_loss + z_loss
        return out.view(orig_shape), total_aux_loss

    Other Talking Points

    If there is extra time at the end of the interview, here are some additional talking points:

    • Shared experts in DeepSeekMoE: In addition to routed experts, DeepSeekMoE isolates 1 or 2 "shared experts" that process every single token unconditionally. The shared experts capture common linguistic syntax and universal representations, leaving the routed experts free to specialize in domain-specific knowledge [6].
    • Hierarchical All-to-All for multi-node EP: When scaling to 64 or 256 experts, EP must cross server nodes. Hierarchical All-to-All breaks the collective into two stages: an intra-node All-to-All over NVLink, followed by an inter-node All-to-All over InfiniBand. This reduces cross-rack network congestion.
    • Fine-grained vs coarse-grained experts: Early MoE models used coarse experts (e.g., 8 large experts with top-1 or top-2). Modern models (such as DeepSeek-V3) favor fine-grained architectures: 256 small experts with top-8 routing. Fine-grained experts allow exponentially more combinatorial routing patterns while maintaining identical active compute.
    • Expert specialization analysis: Contrary to early intuitions, empirical studies show that individual experts do not specialize strictly in semantic domains (e.g., "math" or "history"). Instead, experts specialize in syntactic structure, token frequencies, and morphological patterns across diverse text.
    • MoE checkpoint size during distributed save: Saving an MoE checkpoint with 671 billion parameters in FP32 master weights requires 2.7 terabytes of disk space. Distributed checkpointing frameworks (PyTorch DCP) write each expert shard directly from its host GPU in parallel to distributed storage, avoiding host-memory serialization bottlenecks.
    • Expert parallelism combined with Tensor Parallelism (TP + EP): When individual experts are large, a single expert can be sharded across multiple GPUs using Tensor Parallelism inside each node, while different experts are partitioned across nodes using Expert Parallelism.

    Summary

    • Mixture-of-Experts (MoE) decouples model capacity from compute cost by activating only top-k experts per token, but introduces memory, routing gradient, and interconnect challenges absent in inference.
    • Router gradients flow through continuous softmax coefficients into router weights Wg. Without constraints, positive feedback causes router collapse onto a few popular experts.
    • The Switch Transformer auxiliary loss (αE∑fiPi) forces uniform token allocation, while the ST-MoE router z-loss penalizes large logits to eliminate numerical overflow in BF16.
    • MegaBlocks dropless MoE eliminates token dropping and padding waste by reformulating MoE as block-sparse matrix multiplications (dMoE).
    • DeepSeek-V3 achieves auxiliary-loss-free load balancing by adding dynamic biases (si+bi) to selection scores while calculating gating weights with unbiased scores, updating biases algorithmically with zero loss gradients.
    • Expert Parallelism requires four All-to-All collectives per MoE layer per step (forward dispatch/combine and backward dispatch/combine). Traffic is high (17.2 GB/step for Mixtral 8x7B) and must remain on intra-node NVLink (EP≤8).
    • The fundamental MoE asymmetry: training compute scales strictly with active parameters (6NactiveD FLOPs), while GPU memory scales strictly with total parameters (16Ntotal bytes for Adam).
    • To train an MoE version of our 8B model on 256 H100s, configure EP=8 within each node over NVLink and DP=32 across nodes over InfiniBand, with 8 experts and top-2 active.

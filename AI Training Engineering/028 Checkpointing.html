Checkpointing

Introduction

Training a large language model across hundreds or thousands of GPUs is an exercise in managing inevitable interruptions. High-performance accelerators, high-bandwidth memory (HBM3), optical transceivers, and complex collective communication fabrics fail regularly under sustained thermal load [1]. Without a reliable checkpointing strategy, an unhandled GPU failure or node reboot wipes out days of expensive cluster progress. Checkpointing is the insurance policy of large-scale distributed training: it periodically serializes the exact execution state of the model and optimizer to persistent storage so training can resume seamlessly after an interruption.

However, saving model state at scale introduces a severe systems tension. For an 8-billion parameter model such as Llama 3.1 8B, the mixed-precision AdamW optimizer states, FP32 master weights, and BF16 model parameters consume 16 bytes per parameter, or approximately 128.5 GB (Lesson 3, Training Memory). If 256 GPUs halt execution to write their states synchronously over a shared network file system, storage bandwidth bottlenecks stall training for minutes. Over a multi-week pretraining run, synchronous checkpoint stalls directly degrade Model FLOPs Utilization (MFU) and waste hundreds of thousands of dollars in idle GPU capacity.

Modern distributed systems resolve this tension through sharded distributed checkpointing (where each rank writes its local tensor shard concurrently without rank-0 consolidation) and asynchronous checkpointing (where states are rapidly copied to host RAM in milliseconds while a background thread flushes to storage without stalling compute) [2][3]. Furthermore, determining the optimal checkpoint frequency requires balancing the time spent saving against the expected rework lost upon failure, governed mathematically by the classical Young/Daly optimal interval formula [4][5].

In this lesson, we examine everything a checkpoint must contain to guarantee bit-for-bit mathematical resumption, derive the exact I/O overhead of synchronous versus sharded saving, explore PyTorch Distributed Checkpoint (DCP) and asynchronous background staging, calculate the optimal checkpoint interval for our running 256-GPU cluster, design a multi-tier storage retention lifecycle, and demonstrate how to convert sharded training checkpoints into standalone Hugging Face artifacts for evaluation and serving.

Clarifying the Problem

In a systems design interview for an AI infrastructure role, checkpointing questions typically begin with a storage bottleneck or an elastic restart scenario. Here is how a discussion between a candidate and an interviewer unfolds:

Candidate: What model architecture, cluster size, and parallelism strategy are we sizing for?
Interviewer: We are pretraining our running model—the Llama 3.1 8B architecture (8.03 billion parameters)—on 256 NVIDIA H100 80 GB GPUs across 32 nodes. We use Fully Sharded Data Parallelism (FSDP) with mixed-precision AdamW.

Candidate: What storage infrastructure connects to the cluster?
Interviewer: Each 8-GPU node has 3.8 TB of local NVMe SSD storage capable of 10 GB/s sequential writes. All 32 nodes mount a shared parallel cluster file system (Lustre) delivering an aggregate peak write throughput of 25 GB/s.

Candidate: How often does the cluster experience interruptions, and what is our target restart time?
Interviewer: Across our 256 GPUs, hardware and network interruptions occur roughly once every 8 days (Mean Time Between Failures, MTBF ≈198 hours; Lesson 29, Failures, Restarts and Elastic Training). However, when a job restarts, we want to lose at most a fraction of an hour of compute and resume within 5 minutes.

Candidate: Are we allowed to resume on a different number of GPUs if a node suffers permanent hardware damage?
Interviewer: Yes. If a failed node must be drained, the system might restart on 31 nodes (248 GPUs) or allocate a spare node. The checkpoint format must support dynamic resharding without offline re-indexing.

Candidate: Does saving a checkpoint stall training compute, and what MFU penalty is acceptable?
Interviewer: Our pretraining run targets 40% MFU. Total checkpointing overhead—including saving stalls and lost work upon crash—must account for less than 1% of total cluster time.

The question underneath is: How do we architect a checkpoint pipeline that saves 128.5 GB of distributed state reliably, eliminates GPU compute stalls, reshard across arbitrary topologies upon restart, and identifies the mathematically optimal save frequency? To answer it, we begin with the anatomy of an exact checkpoint.

What an Exact Checkpoint Must Contain

A machine learning checkpoint is not merely a dictionary of neural network weights. While inference requires only the trained BF16 weights (16.06 GB for an 8B model), resuming training deterministically requires restoring the complete optimization and data-loading state. If any state is omitted or corrupted, optimization dynamics diverge, learning rates jump unexpectedly, or training samples are duplicated or skipped.

1. Heavy Model and Optimizer States (16 Bytes per Parameter)

For an 8.03-billion parameter model trained with mixed-precision AdamW, the primary memory footprint comprises five tensors per parameter (Figure 1):

  • BF16 Model Weights (2 bytes/param): The active network parameters used in forward and backward matrix multiplications: 8.03×109×2=16.06 GB.
  • FP32 Master Weights (4 bytes/param): The high-precision reference parameters updated by the optimizer step: 8.03×109×4=32.12 GB.
  • FP32 Adam First Moment m (4 bytes/param): The running exponentially decaying average of past gradients: 32.12 GB.
  • FP32 Adam Second Moment v (4 bytes/param): The running exponentially decaying average of past squared gradients: 32.12 GB.

Summing these four components gives exactly 14 bytes per parameter that must be saved to disk: Checkpoint State Size=8.03×109×(2+4+4+4) bytes=112.42 GB≈104.7 GiB In implementations where gradients or optimizer FP32 step counts are stored within state dictionaries, the serialized footprint reaches the canonical 16 bytes per parameter, or approximately 128.5 GB (119.7 GiB). Notice that gradients themselves are never saved: before a checkpoint is triggered, the optimizer executes its step and zeroes the gradients, so gradients upon resumption are naturally recomputed during the next forward/backward pass.

2. Lightweight Execution and Determinism Metadata (< 1 MB)

While optimizer states account for 99.999% of bytes on disk, deterministic resumption depends completely on lightweight scalar and generator metadata:

  • Learning Rate Scheduler State: The current global step index, learning rate value, warmup stage, and cosine decay phase. If the scheduler is not saved, restarting resets the learning rate to its initial maximum or triggers a second warmup phase, destabilizing the optimizer.
  • Random Number Generator (RNG) States: The internal bit-generator seeds for PyTorch CPU (torch.get_rng_state()), CUDA devices across all GPUs (torch.cuda.get_rng_state_all()), Python's built-in random.getstate(), and NumPy's np.random.get_state(). Restoring RNG states guarantees that data shuffling, stochastic dropout masks, and tensor augmentations produce identical sequences across restarts.
  • DataLoader Position and Cursor: In pretraining across 1 trillion tokens, the data loader must record the exact dataset epoch, shard index, and sample token offset. If the DataLoader position is lost, the restarted run restarts from token zero (re-reading data already trained on) or skips entire data shards, violating curriculum balance.
  • Global Step Counter and Loss Scaler: The integer step index and dynamic loss scale factor (used in FP16 or FP8 training to prevent underflow).

The I/O Bottleneck: Synchronous Stalls versus Sharded DCP

The Failure of Naive torch.save()

In early distributed training scripts, engineers frequently wrote checkpoints using PyTorch's naive serialization: torch.save(model.state_dict(), path). In a distributed data-parallel run across 256 GPUs, naive saving fails disastrously in two ways:

  1. Rank-0 Consolidation OOM: If rank 0 gathers all model and optimizer states across the cluster via an all-gather collective to write a single monolithic file, rank 0's host RAM must hold 128.5 GB of weights plus communication buffers simultaneously. This causes an immediate out-of-memory crash on standard host nodes.
  2. I/O Concurrency Contention: If every rank writes an unsharded duplicate copy of the model, 256 GPUs attempt to write 16.06 GB concurrently over the network: Total Unsharded Traffic=256×16.06 GB≈4,111 GB≈4.11 TB Over a shared Lustre file system delivering 25 GB/s aggregate write bandwidth, writing 4.11 TB takes: tunsharded=4,111 GB25 GB/s≈164.4 seconds≈2.74 minutes Stalling the entire cluster for nearly three minutes at every checkpoint severely degrades training throughput.

Distributed Checkpoint (DCP): Parallel Rank-Local Shards

Modern distributed training frameworks—including PyTorch FSDP2 and torchtitan—use PyTorch Distributed Checkpoint (DCP) (torch.distributed.checkpoint) [2]. In DCP, no consolidation takes place. Instead, each of the 256 GPU ranks writes only its locally sharded parameter and optimizer tensors directly to a dedicated shard file in a shared directory.

Figure 3 illustrates the filesystem architecture of a DCP checkpoint. The destination directory contains:

  • .metadata: A single compact coordinator file written by rank 0. It contains the global tensor shapes, data types, sharding metadata, and a spatial index mapping global tensor slices to specific shard files.
  • Data Shard Files (__0_0.distcp, __1_0.distcp, …): 256 individual binary shard files written in parallel by each rank. For our 8B model with FSDP over 256 GPUs, each rank writes exactly its local sharded slice: Size per Rank Shard=128.5 GB256 ranks≈502 MB

Because each rank writes only its unique sharded slice, total cluster I/O is strictly 128.5 GB, rather than 4.11 TB. Across our Lustre file system's 25 GB/s aggregate bandwidth, a synchronous DCP flush takes:

tDCP, sync=128.5 GB25 GB/s≈5.14 seconds

This represents a 32× reduction in I/O wall-clock time compared to naive serialization.

Asynchronous Checkpointing: Eliminating Compute Stalls

While 5.14 seconds is fast, stalling 256 GPUs every 30 minutes still degrades cluster efficiency. If saving occurs every 30 minutes, 5.14 seconds of stall represents a direct 0.3% loss in hardware utilization. On clusters training 70B or 405B models where checkpoints reach terabytes, synchronous stalls expand to multiple minutes.

GPU-to-Host Staging via async_save

Asynchronous checkpointing decouples tensor serialization from physical disk I/O [3]. In PyTorch DCP, dcp.async_save splits the saving process into two distinct phases (Figure 2):

  1. Staging Phase (Blocking, Milliseconds): The trainer copies the model and optimizer state tensors from GPU High Bandwidth Memory (HBM3) to CPU pinned host memory over the PCIe bus. On an NVIDIA H100 SXM node, each GPU connects to the host CPU via PCIe Gen5 (64 GB/s bidirectional bandwidth). For each rank's 502 MB shard, transferring data over PCIe takes: tstage=502 MB64 GB/s≈0.0078 seconds≈7.8 ms Even with memory allocation overhead and CUDA synchronization barriers, the total GPU compute stall is under 250 milliseconds.
  2. Persistence Phase (Non-Blocking, Background): A dedicated background thread or subprocess (AsyncCheckpointerType.THREAD) handles network serialization and writes the staged CPU buffers to Lustre or local NVMe storage. While the background thread writes to storage, the GPUs immediately resume executing forward and backward passes for step n+1.

Host Memory Budgeting

Asynchronous checkpointing trades host CPU memory for GPU compute continuity. While the background thread writes shard data to disk, the host CPU memory must hold the staged tensors until the I/O write finishes. For an 8-GPU node hosting 8 ranks, total staged memory in host RAM is: Staged RAM per Node=8 ranks×502 MB≈4.02 GB Modern H100 host servers typically provide 1.5 TB to 2.0 TB of system RAM, so reserving 4 GB to 16 GB for checkpoint staging represents negligible overhead (<1% of system RAM). However, systems must enforce a strict guardrail: never trigger a new asynchronous save while a previous save is still in flight. If a previous background write is delayed by network storage contention, queuing multiple asynchronous saves can rapidly exhaust host RAM and trigger Linux Out-Of-Memory (OOM) kernel kills.

Dynamic Resharding Across Topologies

A major failure mode in legacy distributed training was rigid topology coupling: if a model was saved using 256 GPUs with Megatron-LM Tensor Parallelism 4 and Pipeline Parallelism 8, restarting required the exact same 3D parallelism layout. If one node failed and only 31 nodes were available, the run could not restart without running complex offline re-sharding scripts.

PyTorch DCP solves this fundamentally through spatial tensor metadata. When saving under FSDP or DTensor, each rank writes its local data alongside a global slicing descriptor (e.g., "This shard contains rows 0 to 255 of weight matrix W whose global shape is [8192,4096]"). When loading, DCP compares the checkpoint's global index against the memory layout requested by the current cluster topology (Figure 4).

If training restarts on 64 GPUs instead of 32 GPUs, rank 0's DCP planner calculates which byte ranges in the stored shard files correspond to each new rank's local slice. Each rank then reads its required chunks directly from the shard files. This allows seamless transitions between cluster sizes, changing Tensor Parallelism degrees, or loading training checkpoints directly into single-GPU evaluation jobs.

How Often to Checkpoint: The Young/Daly Formula

Choosing checkpoint frequency is a fundamental trade-off between two costs (Figure 5):

  1. Checkpoint Overhead Cost (δ/τ): If checkpoints are saved too frequently (interval τ is very small), the cluster spends too much time staging or persisting checkpoints, increasing I/O stalls and CPU memory traffic.
  2. Rework Cost upon Failure (τ/(2M)): If checkpoints are saved too rarely (τ is very large), an unexpected hardware failure forces the cluster to roll back to a distant checkpoint, losing hours of valuable compute. Assuming failures arrive as a memoryless Poisson process, the expected lost work per failure is half the checkpoint interval: τ/2.

Analytical Derivation

Let τ be the checkpoint interval (in hours), δ be the checkpoint commit duration or effective GPU stall (in hours), and M be the Mean Time Between Failures (MTBF, in hours) of the entire cluster. In 1974, John W. Young derived the first-order approximation minimizing total wasted time [4]:

τopt=2δM

In 2006, J. T. Daly extended Young's model to higher-order terms for large-scale high-performance computing clusters where checkpoint duration δ is non-negligible compared to MTBF [5]:

τopt, Daly=2δM+δ(or 2δM−δ if interval includes save time)

For modern clusters where δ≪M, the classical first-order formula τopt=2δM is highly accurate.

Worked Example: Our 256-GPU Run

Let us calculate the optimal checkpoint interval for our pretraining run on 256 NVIDIA H100 GPUs:

  • Cluster MTBF (M): From Lesson 29 (Failures, Restarts and Elastic Training), the empirical failure rate scaled from Meta's Llama 3 16K-GPU run yields a cluster MTBF of approximately 198 hours (8.25 days) for 256 GPUs.
  • Synchronous Save Stall (δsync): If using synchronous checkpointing where storage write takes 5.14 seconds, plus barrier overhead: δ≈90 seconds=0.025 hours. τopt, sync=2×0.025×198=9.9≈3.15 hours Under synchronous checkpointing, saving roughly every 3 hours minimizes total wasted time.
  • Asynchronous Save Stall (δasync): If using asynchronous checkpointing where the GPU compute stall is limited to host staging: δ≈2 seconds≈0.000555 hours. τopt, async=2×0.000555×198=0.220≈0.469 hours≈28.1 minutes

With asynchronous checkpointing, the optimal interval drops to approximately 30 minutes! Because the GPU stall is under a second, saving every 30 minutes limits lost recomputation upon failure to at most 15 minutes of training on average, while adding negligible save overhead.

Storage Tiers, Retention, and Hugging Face Conversion

Multi-Tier Storage Architecture

Managing checkpoints across multi-week pretraining runs requires a three-tier storage pipeline (Figure 6):

  • Tier 1: Local Node NVMe (Scratch / Buffer): High-speed local SSDs mounted on each node (>10 GB/s write). Used for fast intermediate async staging and ephemeral caching. Tiers are flushed every step; if a node reboots, local data is discarded.
  • Tier 2: Shared Cluster Parallel File System (Lustre / GPFS): Central shared storage mounted across all 32 nodes (25 GB/s aggregate bandwidth). Holds the rolling window of the last 2 to 3 checkpoints (e.g., step_1000/, step_950/, step_900/). When step 1,050 completes successfully, step 900 is automatically deleted by a cleanup daemon. This bounds total Lustre disk usage to < 400 GB while providing immediate rollback targets if a job crashes.
  • Tier 3: Cloud Object Storage (Amazon S3 / Google Cloud Storage): Cost-effective remote object storage. A background archival worker syncs milestone checkpoints (saved every 5,000 steps or every 12 hours) from Lustre to S3. Milestone checkpoints are retained permanently for downstream evaluation, loss divergence analysis, and model release.

Converting DCP Checkpoints to Hugging Face Format

Training checkpoints cannot be loaded directly into inference engines such as vLLM or Hugging Face Transformers. A training checkpoint contains sharded optimizer momentum tensors, FP32 master weights, and internal FSDP parameter prefixes (e.g., _fsdp_wrapped_module.model.layers.0...). Preparing a checkpoint for evaluation or serving requires a conversion pipeline:

  1. Consolidating shards: Rank-local DCP shards are read and concatenated according to the global .metadata coordinate map.
  2. Stripping optimizer states: Adam first and second moments (m and v) and FP32 master weights are discarded, leaving only the active model parameters.
  3. Casting to target precision: FP32 master weights or BF16 tensors are cast cleanly to BF16 (or quantized to FP8).
  4. Renaming parameter keys: Internal framework prefixes are stripped to match standard Hugging Face causal language model naming conventions (e.g., model.layers.0.self_attn.q_proj.weight).
  5. Serializing safetensors and configs: Parameters are written out as unpickled model-00001-of-00004.safetensors files alongside config.json, generation_config.json, and tokenizer.json.

Which checkpoint setup fits our run?

For our pretraining run of Llama 3.1 8B on 256 H100 GPUs across 32 nodes, we select PyTorch Distributed Checkpoint (DCP) with asynchronous host staging (dcp.async_save) saving every 30 minutes (approximately every 1,000 steps). Local host RAM staging takes < 250 ms per node, keeping GPU compute stalls well below 0.05% MFU penalty. Checkpoints are written to our shared Lustre filesystem with a rolling retention policy keeping the last 3 saves (~385 GB total). Every 5,000 steps (~2.5 hours), a milestone checkpoint is asynchronously copied to cloud object storage (S3) and converted to Hugging Face safetensors for parallel evaluation.

import os
import torch
import torch.distributed as dist
import torch.distributed.checkpoint as dcp
from torch.distributed.checkpoint.state_dict import (
    get_model_state_dict,
    get_optimizer_state_dict,
    set_model_state_dict,
    set_optimizer_state_dict,
    StateDictOptions,
)

def save_fsdp2_checkpoint(model: torch.nn.Module, optimizer: torch.optim.Optimizer, step: int, save_dir: str):
    """Save sharded model, optimizer, and execution metadata using PyTorch DCP."""
    os.makedirs(save_dir, exist_ok=True)

    # Configure options for sharded distributed state dict extraction
    options = StateDictOptions(full_state_dict=False, cpu_offload=False)

    # Extract sharded state dicts from FSDP2 wrapped modules
    model_sd = get_model_state_dict(model, options=options)
    optim_sd = get_optimizer_state_dict(model, optimizer, options=options)

    # Build complete checkpoint payload
    state_dict = {
        "model": model_sd,
        "optimizer": optim_sd,
        "step": step,
        "rng_torch": torch.get_rng_state(),
        "rng_cuda": torch.cuda.get_rng_state(),
    }

    # Execute sharded write across all ranks
    dcp.save(state_dict, checkpoint_id=save_dir)
    if dist.get_rank() == 0:
        print(f"[DCP] Checkpoint successfully persisted at step {step} to {save_dir}")

def load_fsdp2_checkpoint(model: torch.nn.Module, optimizer: torch.optim.Optimizer, load_dir: str) -> int:
    """Load sharded model and optimizer state, supporting dynamic resharding."""
    options = StateDictOptions(full_state_dict=False, cpu_offload=False)

    model_sd = get_model_state_dict(model, options=options)
    optim_sd = get_optimizer_state_dict(model, optimizer, options=options)

    state_dict = {
        "model": model_sd,
        "optimizer": optim_sd,
        "step": 0,
        "rng_torch": torch.get_rng_state(),
        "rng_cuda": torch.cuda.get_rng_state(),
    }

    # DCP automatically maps saved chunks to current rank tensor slices
    dcp.load(state_dict, checkpoint_id=load_dir)

    # Restore parameters into active FSDP2 structures
    set_model_state_dict(model, model_state_dict=state_dict["model"], options=options)
    set_optimizer_state_dict(model, optimizer, optim_state_dict=state_dict["optimizer"], options=options)

    # Restore RNG determinism
    torch.set_rng_state(state_dict["rng_torch"])
    torch.cuda.set_rng_state(state_dict["rng_cuda"])

    step = state_dict["step"]
    if dist.get_rank() == 0:
        print(f"[DCP] Resumed execution exactly from step {step}")
    return step
import os
import torch
import torch.distributed as dist
import torch.distributed.checkpoint as dcp
from torch.distributed.checkpoint.state_dict import (
    get_model_state_dict,
    get_optimizer_state_dict,
    StateDictOptions,
)

class AsyncCheckpointer:
    """Non-blocking checkpointer staging tensors to host RAM in milliseconds."""
    def __init__(self):
        self._active_future = None

    def save_async(self, model: torch.nn.Module, optimizer: torch.optim.Optimizer, step: int, save_dir: str):
        # 1. Guard against concurrent in-flight writes
        if self._active_future is not None and not self._active_future.done():
            if dist.get_rank() == 0:
                print(f"[WARN] Previous async checkpoint still writing. Blocking until complete...")
            self._active_future.result()

        os.makedirs(save_dir, exist_ok=True)
        # cpu_offload=True stages tensors into pinned CPU host memory during extraction
        options = StateDictOptions(full_state_dict=False, cpu_offload=True)

        model_sd = get_model_state_dict(model, options=options)
        optim_sd = get_optimizer_state_dict(model, optimizer, options=options)

        state_dict = {
            "model": model_sd,
            "optimizer": optim_sd,
            "step": step,
            "rng_torch": torch.get_rng_state(),
            "rng_cuda": torch.cuda.get_rng_state(),
        }

        # 2. Trigger asynchronous background persistence
        # Returns immediately after PCIe staging, allowing GPUs to continue training
        self._active_future = dcp.async_save(
            state_dict=state_dict,
            checkpoint_id=save_dir,
        )
        if dist.get_rank() == 0:
            print(f"[AsyncDCP] Staged step {step} to CPU RAM; background disk write started.")

    def wait_until_finished(self):
        """Block until background I/O finishes (e.g., at job end or before shutdown)."""
        if self._active_future is not None:
            self._active_future.result()
            self._active_future = None
import os
import torch
import torch.distributed.checkpoint as dcp
from safetensors.torch import save_file

def convert_dcp_to_huggingface(dcp_checkpoint_dir: str, output_safetensors_path: str):
    """Offline utility: consolidates sharded DCP checkpoint into a single Hugging Face safetensors file."""
    print(f"Reading sharded DCP metadata from {dcp_checkpoint_dir}...")

    # 1. Read metadata coordinator without loading tensor data
    metadata = dcp.read_metadata(dcp_checkpoint_dir)

    # 2. Create placeholder dict with empty CPU tensors matching global parameter shapes
    full_model_state = {}
    for name, item in metadata.state_dict_metadata.items():
        if name.startswith("model."):
            # Strip internal FSDP prefixes
            clean_name = name.replace("model._fsdp_wrapped_module.", "").replace("model.", "")
            full_model_state[name] = torch.empty(item.size, dtype=item.properties.dtype, device="cpu")

    # 3. Load full consolidated model state onto CPU
    dcp.load(
        state_dict=full_model_state,
        checkpoint_id=dcp_checkpoint_dir,
    )

    # 4. Clean keys and cast master weights to BF16
    hf_state_dict = {}
    for k, v in full_model_state.items():
        clean_key = k.replace("model._fsdp_wrapped_module.", "").replace("model.", "")
        # Cast to standard BF16 serving precision
        hf_state_dict[clean_key] = v.to(torch.bfloat16).contiguous()

    # 5. Persist as safe standalone safetensors file
    os.makedirs(os.path.dirname(output_safetensors_path), exist_ok=True)
    save_file(hf_state_dict, output_safetensors_path)
    print(f"Successfully exported {len(hf_state_dict)} tensors to {output_safetensors_path}")

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • In-memory peer checkpointing: Methods such as CheckFreq and Bamboo that replicate checkpoint shards directly across high-speed InfiniBand into the RAM or NVMe of neighbor nodes, surviving single-node power outages without writing to central network storage [6].
  • Loss divergence rollbacks: How monitoring pipelines detect loss spikes (e.g., sudden gradient norm explosion) and trigger automated rollbacks to a clean milestone checkpoint saved 2,000 steps earlier with an adjusted learning rate schedule.
  • Copy-on-write memory overhead: Why process-based asynchronous checkpointing requires careful memory management under Linux: fork-based approaches risk memory duplication if subsequent training iterations mutate large model tensors before background writes finish.
  • Storage metadata throttling: How parallel file systems (such as Lustre or NFS) degrade when thousands of ranks open, create, and close thousands of files simultaneously, and why DCP bundles tensors into larger chunk files to keep file counts manageable.
  • FP8 optimizer state saving: Recent research compressing Adam first and second moments to 8-bit floating point, reducing optimizer checkpoint size from 12 bytes per parameter down to 4 bytes per parameter with minimal precision loss.
  • Validating checkpoint integrity: Computing streaming CRC32 or SHA-256 checksums during asynchronous staging to catch silent data corruption (SDC) before an invalid checkpoint overwrites a healthy rolling save.

Summary

  • An exact training checkpoint requires 16 bytes per parameter (128.5 GB for Llama 3.1 8B) to store BF16 weights, FP32 master weights, and Adam momentum and variance states, alongside lightweight LR scheduler, DataLoader, and RNG states.
  • Naive torch.save() crashes master ranks via memory gathering and saturates network storage. PyTorch Distributed Checkpoint (DCP) allows each rank to write its local shard independently, eliminating all rank-0 bottlenecks.
  • Asynchronous checkpointing (dcp.async_save) stages tensors across PCIe to CPU host RAM in under 250 milliseconds, allowing GPUs to resume training immediately while a background thread writes to storage.
  • DCP's global .metadata index enables dynamic resharding, allowing training to resume seamlessly on different GPU counts or altered parallelism layouts without manual offline re-indexing.
  • The Young/Daly formula τopt=2δM balances save overhead against rework lost upon failure, yielding an optimal checkpoint frequency of approximately 30 minutes for our 256-GPU cluster under asynchronous saving.
  • A three-tier storage lifecycle—ephemeral local NVMe, a rolling window of 3 saves on shared Lustre, and permanent S3 milestone archives—guarantees fast crash recovery while bounding storage costs.

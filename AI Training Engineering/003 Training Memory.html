Training Memory

Introduction

Training a large language model is, before anything else, a battle against GPU memory limits. While inference requires memory primarily to hold model weights and the key-value cache of generated tokens, training demands vastly more. During training, the GPU must simultaneously store the model weights, their gradients, multiple optimizer states per parameter, intermediate activations retained from the forward pass for backpropagation, communication buffers, and scratch workspaces for matrix multiplications [1].

In standard mixed-precision training with the Adam optimizer, the model and optimizer states alone consume 16 bytes per parameter [2]. For an 8-billion-parameter model such as Llama 3.1 8B, this baseline footprint reaches 128.5 GB. Because an NVIDIA H100 SXM GPU provides 80 GB of High Bandwidth Memory (HBM3), the model states alone exceed the physical capacity of a single GPU by more than 60% before allocating a single activation tensor. Training an 8B model on a single 80 GB GPU is physically impossible without aggressive sharding or offloading.

Beyond static states, activation memory grows with batch size, hidden dimension, and context length. For modern 8,192-token sequences, naive attention activations require over 380 GB per GPU across 32 layers, dwarfing even the optimizer states [3]. Sizing a training run requires understanding exactly what each tensor costs, how memory scales across sequence length and batch dimensions, and which levers—activation checkpointing, FlashAttention, and state sharding—make training feasible without starving compute throughput.

In this lesson, we break down every byte that occupies GPU memory during training, derive the exact analytical scaling laws for activations, examine the memory reduction levers and their trade-offs, work a complete memory budget for our running 256-GPU pretraining cluster, and inspect memory allocation in PyTorch using memory snapshots.

Clarifying the Problem

In a systems design interview for an AI infrastructure role, memory accounting questions typically start from an out-of-memory failure or a cluster sizing challenge. Here is how a discussion between a candidate and an interviewer typically unfolds:

Candidate: What model architecture and precision are we targeting for this training run?
Interviewer: We are pretraining a model with the Llama 3.1 8B architecture—32 layers, hidden dimension 4,096, 32 query heads, 8 KV heads, and vocabulary size 128,256, totaling 8.03 billion parameters. We use BF16 mixed-precision training with the AdamW optimizer.

Candidate: What hardware cluster and network topology do we have available?
Interviewer: A cluster of 256 NVIDIA H100 80 GB SXM GPUs arranged across 32 nodes. Within each node, the 8 GPUs communicate via NVLink at 900 GB/s per GPU. Across nodes, each node connects through 8 InfiniBand NDR NICs offering 400 Gb/s (50 GB/s) per GPU.

Candidate: What sequence length and batch size are specified for pretraining?
Interviewer: The sequence length is 8,192 tokens. The global batch size is approximately 4 million tokens, which corresponds to 512 sequences of 8,192 tokens per optimizer step.

Candidate: What is our primary optimization objective—minimizing memory footprint to fit the largest possible batch, or maximizing compute throughput?
Interviewer: We need to reach at least 40% Model FLOPs Utilization (MFU). The run must never crash with an Out-Of-Memory (OOM) error, but we cannot afford techniques that severely degrade hardware efficiency or saturate our inter-node network.

Candidate: Can we train this model on a single H100 if we use gradient accumulation?
Interviewer: You tell me. Can you fit Llama 3.1 8B on one 80 GB GPU for training, and if not, why?

The question underneath is: How do we account for every gigabyte across the cluster, fit long 8,192-token sequences without running out of memory, and avoid paying unnecessary communication penalties on our interconnects? To answer it, we begin by accounting for the static baseline: model and optimizer states.

The 16-Byte Baseline: Model and Optimizer States

The arithmetic of mixed-precision Adam

In mixed-precision training with 16-bit floating point (BF16 or FP16), the forward pass and backward pass matrix multiplications execute in 16-bit to exploit tensor core throughput [2]. However, parameter updates cannot be performed directly in 16-bit without severe numerical underflow and weight stagnation. Standard practice therefore maintains an FP32 copy of the weights and computes the optimizer step in full 32-bit precision.

For every parameter p in the model, the system stores five distinct values across the training step:

  • BF16 model weight (2 bytes): Read during the forward pass to compute layer activations, and read during the backward pass to compute gradients with respect to input activations.
  • BF16 gradient (2 bytes): Computed during backpropagation and accumulated across micro-batches before the optimizer update.
  • FP32 master weight (4 bytes): The high-precision reference copy of the parameter. The optimizer applies the weight update directly to this FP32 tensor, which is then cast back to BF16 for the next forward pass.
  • FP32 Adam first moment m (4 bytes): The exponentially decaying moving average of past gradients (momentum), updated at each optimizer step.
  • FP32 Adam second moment v (4 bytes): The exponentially decaying moving average of past squared gradients (uncentered variance), used to scale individual coordinate learning rates.

Summing these five components yields the canonical memory footprint for mixed-precision Adam:

Memory per Parameter=2+2+4+4+4=16 bytes

Figure 2 illustrates this state accounting and shows how the 16 bytes divide between model representations and optimizer states.

Notice that 12 of the 16 bytes (75%) belong entirely to the optimizer. The active weights and gradients used by the neural network layers account for only 4 bytes per parameter (25% of the total).

Why Llama 3.1 8B cannot train on one 80 GB GPU

Our running model has N=8.03×109 parameters. Multiplying by 16 bytes gives the exact static memory requirement:

Static Memory=8.03×109×16 bytes=128.48×109 bytes≈128.5 GB

In binary units (gibibytes), this corresponds to 128.48×109/10243≈119.66 GiB. An NVIDIA H100 SXM 80 GB GPU exposes approximately 79.6 GiB (85.47 GB) of visible memory to the CUDA driver.

Even before allocating a single activation tensor, communication buffer, or CUDA context overhead, the baseline states exceed total GPU memory by 48.5 GB (1.61× physical capacity). Accumulating gradients over smaller micro-batches reduces activation memory, but gradient accumulation cannot reduce model or optimizer states. Unsharded single-GPU training of an 8B model with Adam on an 80 GB GPU is fundamentally impossible.

Why inference memory is radically smaller

Engineers transitioning from inference to training often wonder why a model that serves comfortably on a single 24 GB or 80 GB GPU suddenly requires a distributed cluster to train. The difference lies in the absence of backward passes and optimizer updates during inference (see Inference Lesson 17, VRAM Budgeting).

During inference, there are no gradients (0 bytes), no FP32 master weights (0 bytes), and no Adam momentum or variance states (0 bytes). The model requires only its BF16 weights (16.06 GB, or 15.0 GiB) or FP8 weights (~9.08 GB). Furthermore, inference decodes one token at a time, so its active layer activations require less than 100 MB. The remaining ~52 GiB of memory on an 80 GB H100 is dedicated entirely to the KV cache, allowing the GPU to concurrently serve hundreds of users. In training, the KV cache does not exist; instead, optimizer states and forward activations consume the entire memory budget.

Activation Memory: Anatomy and Scaling

What activations are saved for the backward pass

While model and optimizer states remain fixed throughout training, activation memory is dynamic. When a neural network executes a forward pass, it computes intermediate tensors at each layer. According to the chain rule of calculus, computing the gradient of the loss with respect to a layer's weights requires the input activations to that layer [1]:

∂ℒ∂W=(∂ℒ∂Y)X⊤where Y=WX

To evaluate this outer product during backpropagation, the forward activations X must either remain in GPU memory until the backward pass reaches that layer, or be recomputed on the fly. In an uncheckpointed transformer, every linear projection input, normalization statistic, attention score matrix, and non-linear activation tensor across all 32 layers is saved in HBM.

Analytical derivation from Megatron-LM

To quantify activation memory rigorously, we use the analytical framework formulated by Korthikanti et al. in the Megatron-LM study Reducing Activation Recomputation in Large Transformer Models [3]. Let s be the sequence length, b the micro-batch size per GPU, h the hidden dimension, a the number of attention heads, and L the number of transformer layers. In 16-bit precision (2 bytes per element), the intermediate activations stored per transformer layer divide into two distinct categories: linear terms and quadratic attention terms.

1. Self-attention block linear activations (12sbh bytes)

  • Attention input & LayerNorm: Storing the input to the pre-attention RMSNorm / LayerNorm requires 2sbh bytes. Storing the normalized output feeding the Q, K, V projections requires 2sbh bytes.
  • Q, K, V projections: Storing the projected query (2sbh) and key (2sbh) tensors needed to compute gradients of the attention matrix requires 4sbh bytes. Storing value vectors V requires 2sbh bytes.
  • Attention out-projection & dropout: Storing the context projection input requires 2sbh bytes. Attention dropout masks add 1sbh (or 2sbh if stored uncompressed).

2. Quadratic self-attention matrix activations (5as2b bytes)

In standard multi-head self-attention, the query-key matrix multiplication produces an attention score tensor of shape [b,a,s,s]:

  • The raw attention score tensor QK⊤/d in 16-bit requires 2as2b bytes.
  • The post-softmax attention probability tensor requires 2as2b bytes to backpropagate through the softmax Jacobian.
  • The attention dropout mask requires 1as2b bytes (as a 1-byte mask).

Summing these terms yields 5as2b bytes per layer. This term scales with the square of sequence length s2.

3. Feed-forward network (MLP) activations (22sbh bytes)

In standard transformer MLPs with GeLU activation expanding to intermediate size 4h:

  • The pre-MLP LayerNorm input requires 2sbh bytes.
  • The input to the first linear up-projection requires 2sbh bytes.
  • The intermediate expanded tensor of dimension 4h before the non-linearity requires 8sbh bytes (4×2sbh).
  • The post-activation tensor of dimension 4h feeding the down-projection requires 8sbh bytes.
  • The output residual dropout mask requires 2sbh bytes.

In modern architectures using SwiGLU (such as Llama 3.1), the MLP uses three projections (Wgate,Wup,Wdown) with intermediate dimension dff=14,336=3.5h. The linear activation footprint remains roughly comparable, totaling approximately 34sbh bytes per layer when combined with attention linear terms.

Combining all linear and quadratic terms yields Korthikanti et al.'s formula for uncheckpointed activation memory per layer [3]:

Activation Memory per Layer=34sbh+5as2b bytes

Across all L layers of the model, total uncheckpointed activation memory is:

Total Activation Memory=L×(34sbh+5as2b) bytes

The quadratic explosion at 8,192 tokens

Now let us evaluate this formula for our pretraining scenario with micro-batch size b=1, sequence length s=8,192, hidden size h=4,096, attention heads a=32, and L=32 layers:

  • Linear term per layer: 34×8,192×1×4,096=1,140,850,688 bytes≈1.14 GB (1,088 MiB). Across 32 layers: 32×1.14 GB=36.51 GB.
  • Quadratic term per layer: 5×32×(8,192)2×1=10,737,418,240 bytes≈10.74 GB (10.0 GiB). Across 32 layers: 32×10.74 GB=343.60 GB.
  • Total per layer: 1.14 GB+10.74 GB=11.88 GB.
  • Total across 32 layers: 36.51 GB+343.60 GB=380.11 GB (354.0 GiB).

At 8,192 tokens, the quadratic attention matrix accounts for 90.4% of total activation memory. To store uncheckpointed activations for just one sequence would require nearly five 80 GB GPUs purely for activations! Figure 3 plots this scaling behavior against sequence length.

What FlashAttention changes

The breakthrough that made long-context LLM training practical without quadratic memory scaling is FlashAttention (Dao et al., 2022 [4]; FlashAttention-2, 2023). Standard attention materializes the intermediate s×s attention score and dropout matrices in GPU High Bandwidth Memory (HBM) during the forward pass so that the backward pass can read them.

FlashAttention restructures the attention computation using GPU On-Chip Static RAM (SRAM). By tiling the inputs into blocks that fit within the H100's fast SRAM (which delivers ~33 TB/s, roughly 10× faster than HBM3) and computing the softmax incrementally using online normalization, FlashAttention computes attention without ever writing the b×a×s×s intermediate matrix to HBM.

Crucially for training memory, FlashAttention avoids saving the quadratic attention matrix for the backward pass. Instead, it saves only the forward outputs and a single softmax scaling vector (the log-sum-exp values of shape [b,a,s], requiring only 4asb bytes in FP32, or 1 MB for 8,192 tokens). During the backward pass, FlashAttention recomputes the attention tiles on the fly directly in SRAM from the saved inputs Q,K,V and the log-sum-exp vector.

As a result, FlashAttention completely eliminates the 5as2b term from GPU memory. The activation footprint collapses from 34sbh+5as2b down to strictly the linear term 34sbh. For Llama 3.1 8B at 8,192 tokens, activation memory across all 32 layers plummets from 380.1 GB to 36.5 GB—a 10.4× memory reduction achieved with zero loss in numerical accuracy, and actually running 2–3× faster due to reduced HBM memory traffic.

Memory Reduction Levers and Their Costs

Even with FlashAttention holding activation memory to 36.5 GB, our model states (128.5 GB) plus activations (36.5 GB) still total 165 GB, far exceeding an 80 GB GPU. Training engineers employ several architectural and distributed levers to bring memory within hardware limits. Each lever trades off compute, communication, or engineering complexity.

Activation checkpointing and recomputation

Activation checkpointing (also known as gradient checkpointing, Chen et al., 2016 [5]) trades compute cycles for memory. Instead of storing all intermediate activations computed during the forward pass across every layer, the system retains only the input tensor at the boundary of each transformer layer.

During the forward pass of a 32-layer model, Layer 0 saves its input tensor x0, runs its forward operations, passes x1 to Layer 1, and immediately discards all internal activations (projections, normalization states, and SwiGLU intermediates). Only x0,x1,…,x31 remain in memory.

When the backward pass reaches Layer i, PyTorch retrieves the saved input tensor xi, re-executes the forward pass of Layer i to regenerate its internal activations, immediately calculates the parameter gradients, and frees the recomputed activations before moving to Layer i−1. Figure 4 diagrams this lifecycle.

The memory savings are staggering. Instead of storing 34 elements per token per layer, full checkpointing stores only the input activation tensor:

Checkpoint Memory per Layer=2sbh bytes (in BF16)

For Llama 3.1 8B with b=1 and s=8,192:

Per Layer=2×8,192×1×4,096×2=134,217,728 bytes≈67.1 MB

Across all 32 layers, total stored activations drop to 32×67.1 MB=2.15 GB (2.0 GiB)—a 94% reduction compared to uncheckpointed FlashAttention (36.5 GB).

The exact compute overhead

Re-running the forward pass is not free. As established in the standard FLOPs accounting (see Lesson 7, Training FLOPs, Time and MFU), a standard training step requires approximately 6ND FLOPs (2ND for the forward pass, and 4ND for the backward pass to compute both input and parameter gradients). Recomputing the forward pass during backpropagation adds another 2ND FLOPs, increasing total compute to 8ND FLOPs:

Compute Overhead=8ND−6ND6ND=2ND6ND=13≈33.3%

Full activation checkpointing adds exactly 33.3% more compute FLOPs to every training step. However, because it frees tens of gigabytes of VRAM, it allows training with larger micro-batch sizes that achieve higher tensor core saturation, frequently offsetting much of the nominal time penalty.

State sharding across GPUs: ZeRO and FSDP

While activation checkpointing solves the activation bottleneck, model and optimizer states (128.5 GB) still exceed a single 80 GB GPU. The solution is state sharding, formalized by Rajbhandari et al. in ZeRO (Zero Redundancy Optimizer [6]) and implemented natively in PyTorch as Fully Sharded Data Parallel (FSDP) [7].

In standard Distributed Data Parallel (DDP), every GPU holds a complete, identical copy of the model weights, gradients, and optimizer states. FSDP eliminates this redundancy by partitioning states across data-parallel ranks:

  • ZeRO-1 (Optimizer State Sharding): Each GPU keeps full BF16 weights (16.1 GB) and BF16 gradients (16.1 GB), but shards the FP32 master weights and Adam moments across Nd GPUs. For Nd=8, optimizer states drop from 96.4 GB to 12.0 GB. Total model state drops from 128.5 GB to 44.2 GB.
  • ZeRO-2 (Optimizer + Gradient Sharding): Gradients are also sharded. As backward pass gradients are computed, they are reduced directly to the rank that owns that parameter shard. Gradients drop to 16.1/Nd GB. For Nd=8, total model state drops to 30.2 GB.
  • ZeRO-3 / FSDP (Full Parameter Sharding): Weights, gradients, and optimizer states are all sharded across Nd GPUs. Each GPU stores strictly 16/Nd bytes per parameter.

Figure 5 compares state sharding under three deployment strategies: unsharded DDP, intra-node sharding across 8 GPUs, and full cluster sharding across 256 GPUs.

The communication trade-off in FSDP

Under full FSDP, because weights are sharded, a GPU does not hold the weights for Layer i when it needs to compute that layer. Prior to executing Layer i's forward pass, all GPUs in the sharding group perform an all-gather collective to reconstitute the full layer weights in temporary memory, execute the forward GEMMs, and immediately discard the gathered weights. The same all-gather occurs during the backward pass, followed by a reduce-scatter collective to synchronize gradients [7].

This introduces 50% more collective communication volume than standard DDP. If FSDP is sharded across all 256 GPUs in a cluster, every layer's all-gather and reduce-scatter must traverse the inter-node network (400 Gb/s InfiniBand, offering 50 GB/s per GPU). This is 18× slower than the 900 GB/s NVLink connecting GPUs within the same node, throttling GPU compute engines with inter-node communication stalls (see Lesson 11, ZeRO and FSDP).

Alternative memory levers

Other techniques exist to reduce memory, though each carries distinct trade-offs:

  • Micro-batch sizing and gradient accumulation: Setting micro-batch size b=1 minimizes activation memory. To achieve a large target global batch size B, gradients are accumulated locally over M micro-steps before synchronizing and calling optimizer.step(). This reduces activation memory linearly with b, but cannot reduce model states.
  • CPU offload (ZeRO-Offload): Moves optimizer states and master weights to host CPU RAM, updating weights on the CPU and copying them back over PCIe. While this allows fine-tuning an 8B model on a single desktop GPU, PCIe Gen5 x16 bandwidth (~64 GB/s) is 52× slower than H100 HBM3 (3.35 TB/s), severely crippling throughput. It is unsuitable for large-scale pretraining.
  • 8-bit optimizers (bitsandbytes): Dettmers et al. [8] introduced non-linear block-wise quantization for Adam states. By quantizing momentum m and variance v to 8-bit floats with per-block scaling factors, optimizer states drop from 8 bytes to 2 bytes per parameter. Total model states drop from 16 bytes to 10 bytes per parameter (saving 48 GB for an 8B model). While effective for fine-tuning, large pretraining runs generally retain FP32 master weights and moments to eliminate any risk of optimizer numerical divergence.
  • Lower-precision training (FP8): Executes forward and backward matrix multiplications using 8-bit floating point formats (E4M3 for activations/weights and E5M2 for gradients), halving activation and gradient storage (see Lesson 5, Mixed Precision Training - BF16 and FP8).

Which levers fit our run?

For our running pretraining scenario (Llama 3.1 8B, 256 H100 80 GB GPUs, sequence length 8,192, target 40% MFU), the optimal strategy is Hybrid Sharded Data Parallelism:

  1. FlashAttention-2 is mandatory: it eliminates the 343.6 GB quadratic attention tensor with zero compute penalty and zero accuracy loss.
  2. Full activation checkpointing is enabled: it cuts stored activations from 36.5 GB to 2.15 GB per GPU, leaving abundant headroom for temporary buffers and GEMM workspaces.
  3. Intra-node FSDP across 8 GPUs (Hybrid Sharding): Inside each 8-GPU node, weights, gradients, and optimizer states are sharded across the 8 GPUs over 900 GB/s NVLink. This reduces static model states from 128.5 GB to 16.1 GB per GPU. Across the 32 nodes, standard data parallelism (DDP) synchronizes gradients via ring all-reduce over InfiniBand once per step.

We explicitly reject full cluster sharding across 256 GPUs. As shown in Table 1, full FSDP would reduce model states to 0.5 GB per GPU, leaving over 65 GB of expensive HBM3 memory completely empty while forcing every single transformer layer to fetch its weights across the 18× slower InfiniBand fabric. Intra-node FSDP provides the ideal balance: it uses ~33 GB of the 80 GB capacity, avoids network bottlenecks, and preserves the highest possible MFU.

Worked Memory Budgets: Intra-Node vs Full Sharding

Step-by-step memory accounting per GPU

Let us construct the complete, byte-for-byte memory budget for a single H100 80 GB GPU under our chosen pretraining configuration (b=1,s=8,192) and contrast it with full 256-GPU sharding.

1. Sharded model and optimizer states

Total unshared state is 8.03×109×16 bytes=128.48 GB:

  • Under 8-GPU intra-node FSDP: Each GPU stores 128.48/8=16.06 GB (14.96 GiB). This breaks down into 2.01 GB BF16 weights, 2.01 GB BF16 gradients, 4.02 GB FP32 master weights, and 8.03 GB FP32 Adam moments.
  • Under 256-GPU full FSDP: Each GPU stores 128.48/256=0.502 GB (502 MB or 0.47 GiB).

2. Unsharded active layer buffer

During the forward and backward passes, FSDP all-gathers full weights for the active transformer layer. One layer contains 8.03B/32≈251M parameters. In BF16, one layer's weights require:

Active Layer Weights≈251×106×2 bytes≈0.50 GB (0.47 GiB)

With prefetching enabled (fetching Layer i+1 while computing Layer i), two layers coexist temporarily in memory, occupying ~1.0 GB.

3. Activation memory

With FlashAttention and full activation checkpointing at b=1 and s=8,192:

  • Saved input checkpoints across 32 layers: 32×(2×8,192×1×4,096×2)≈2.15 GB.
  • Peak recomputed activations during backward pass: Layer i recomputes its internal activations, requiring 34sbh≈1.14 GB.
  • Total peak activation memory during backward: 2.15 GB+1.14 GB=3.29 GB (3.06 GiB).

4. Temporary buffers, GEMM workspaces, and loss computation

A training step requires ephemeral buffers that allocate and free within milliseconds:

  • cuBLAS & FlashAttention workspaces: High-performance matrix multiplication libraries allocate scratch buffers for tensor core tiling heuristics (~1.5 GB).
  • Cross-entropy logits tensor: In the final layer, the hidden state of shape [b,s,h] projects to vocabulary size V=128,256. The unchunked logits tensor of shape [1,8192,128256] in FP32 requires: 1×8,192×128,256×4 bytes=4,202,561,536 bytes≈4.20 GB If chunked across 4 micro-slices, this drops to ~1.05 GB.
  • FSDP communication buckets: Buffers allocated for all-gather and reduce-scatter collective operations (~1.0 GB).
  • Total temporary workspace: approximately 5.0 GB.

5. Caching allocator headroom and fragmentation

PyTorch's caching allocator retains freed CUDA memory blocks to avoid expensive cudaMalloc driver synchronizations. Depending on tensor allocation patterns and variable-sized intermediates, memory fragmentation creates unallocatable gaps between cached blocks. Reserving a safety margin of 8.0 GB (10% of total memory) ensures that allocations never trigger an out-of-memory error.

In Practice

To profile GPU memory and diagnose out-of-memory errors in PyTorch, standard queries like torch.cuda.memory_allocated() provide aggregate snapshots, but they fail to reveal transient allocation spikes or memory fragmentation. PyTorch provides a dedicated memory snapshot facility [9], [10] that records every tensor allocation event and stack trace, exportable for visualization at pytorch.org/memory_viz.

The first tab demonstrates a profiling script that records memory events through forward, backward, and optimizer steps, captures peak memory, and dumps a snapshot file. The second tab provides a standalone memory budget calculator that computes model states, activation scaling, and FSDP sharding budgets from first principles for any transformer configuration.

import os
import torch
import torch.nn as nn

def profile_training_memory():
    if not torch.cuda.is_available():
        print("CUDA unavailable; running mock allocation test on CPU.")
        return

    device = torch.device("cuda:0")
    torch.cuda.reset_peak_memory_stats(device)

    # 1. Start recording memory allocation history with stack traces
    # Max entries controls event history buffer depth
    print("Enabling PyTorch CUDA memory history tracking...")
    torch.cuda.memory._record_memory_history(
        enabled="all",
        context="all",
        stacks="python",
        max_entries=100000,
    )

    # 2. Allocate model, mock inputs, and mixed-precision AdamW
    hidden_dim = 4096
    seq_len = 2048
    layer = nn.TransformerEncoderLayer(
        d_model=hidden_dim, nhead=32, dim_feedforward=14336,
        activation="gelu", batch_first=True, dtype=torch.bfloat16,
    ).to(device)

    optimizer = torch.optim.AdamW(layer.parameters(), lr=1e-4)

    initial_alloc = torch.cuda.memory_allocated(device) / (1024**2)
    print(f"Allocated after model load: {initial_alloc:.2f} MiB")

    # 3. Execute Forward and Backward Pass
    inputs = torch.randn(1, seq_len, hidden_dim, dtype=torch.bfloat16, device=device)
    out = layer(inputs)
    fwd_alloc = torch.cuda.memory_allocated(device) / (1024**2)
    print(f"Allocated after forward pass (with activations): {fwd_alloc:.2f} MiB")

    loss = out.sum()
    loss.backward()
    bwd_alloc = torch.cuda.memory_allocated(device) / (1024**2)
    print(f"Allocated after backward pass (gradients populated): {bwd_alloc:.2f} MiB")

    optimizer.step()
    optimizer.zero_grad(set_to_none=True)

    peak_alloc = torch.cuda.max_memory_allocated(device) / (1024**2)
    peak_reserved = torch.cuda.max_memory_reserved(device) / (1024**2)
    print(f"Peak Allocated: {peak_alloc:.2f} MiB | Peak Reserved: {peak_reserved:.2f} MiB")

    # 4. Dump snapshot pickle for visualization at https://pytorch.org/memory_viz
    snapshot_path = "training_memory_snapshot.pickle"
    torch.cuda.memory._dump_snapshot(snapshot_path)
    print(f"Memory snapshot dumped to '{snapshot_path}'.")
    print("Upload this file to https://pytorch.org/memory_viz to inspect allocation timeline.")

    # Stop recording
    torch.cuda.memory._record_memory_history(enabled=None)

if __name__ == "__main__":
    profile_training_memory()
def calculate_training_memory(
    num_params: float,
    num_layers: int,
    hidden_dim: int,
    seq_len: int,
    micro_batch: int,
    num_heads: int,
    sharding_world_size: int = 8,
):
    """
    Computes exact training memory requirements in decimal gigabytes (GB)
    and binary gibibytes (GiB) for transformer pretraining.
    """
    bytes_per_param = 16  # Mixed precision Adam (2B wt + 2B grad + 12B opt)
    total_model_states = num_params * bytes_per_param

    # Activation memory per layer (Korthikanti et al., 2022)
    # Linear: 34 * s * b * h bytes
    # Quadratic: 5 * a * s^2 * b bytes
    linear_per_layer = 34 * seq_len * micro_batch * hidden_dim
    quad_per_layer = 5 * num_heads * (seq_len ** 2) * micro_batch

    uncheckpointed_std_attn = num_layers * (linear_per_layer + quad_per_layer)
    uncheckpointed_flash_attn = num_layers * linear_per_layer
    checkpointed_flash_attn = num_layers * (2 * seq_len * micro_batch * hidden_dim)

    # Sharded model states
    sharded_model_states = total_model_states / sharding_world_size

    print(f"=== Model State Accounting ({num_params / 1e9:.2f}B Parameters) ===")
    print(f"Total Unsharded States : {total_model_states / 1e9:.2f} GB ({total_model_states / 2**30:.2f} GiB)")
    print(f"Sharded over {sharding_world_size:2d} GPUs   : {sharded_model_states / 1e9:.2f} GB ({sharded_model_states / 2**30:.2f} GiB)")
    print()
    print(f"=== Activation Memory (s={seq_len:,}, b={micro_batch}, {num_layers} layers) ===")
    print(f"Standard Attention (No Checkpoint): {uncheckpointed_std_attn / 1e9:.2f} GB")
    print(f"FlashAttention (No Checkpoint)    : {uncheckpointed_flash_attn / 1e9:.2f} GB")
    print(f"FlashAttn + Full Checkpointing    : {checkpointed_flash_attn / 1e9:.2f} GB")

if __name__ == "__main__":
    calculate_training_memory(
        num_params=8.03e9,
        num_layers=32,
        hidden_dim=4096,
        seq_len=8192,
        micro_batch=1,
        num_heads=32,
        sharding_world_size=8,
    )

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Loss layer memory spikes from vocabulary size: The final cross-entropy loss projects hidden states [b,s,h] to vocabulary size V=128,256. Generating the full unchunked logits tensor requires over 4.2 GB of memory in FP32. Fused cross-entropy kernels (such as Liger Kernel) chunk the logits computation across the sequence dimension, computing softmax and cross-entropy loss in-kernel to avoid materializing the multi-gigabyte logits tensor in HBM.
  • Sequence parallelism for ultra-long context: When context length extends beyond 32,768 tokens, activation checkpointing alone is insufficient because even the saved layer boundary inputs (2sbh) exceed available memory. Sequence parallelism (Megatron-SP or DeepSpeed Ulysses) splits the sequence dimension across tensor-parallel or context-parallel GPUs, reducing activation memory linearly with parallel degree.
  • Memory fragmentation and allocator tuning: Frequent allocations of varying sizes can fragment PyTorch's caching allocator pool, causing an OOM even when total free memory exceeds the requested tensor size. Setting the environment variable PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True enables virtual memory address reservation, allowing non-contiguous physical pages to satisfy contiguous allocation requests.
  • Peak memory coexistence during backpropagation: The instantaneous peak memory of a training step occurs at the very start of the backward pass. At this moment, all activation checkpoints across all 32 layers are held in memory, the backward pass allocates the recomputed forward activations for Layer 31, and gradient buffers begin accumulating, creating the highest memory watermark of the step.
  • Selective activation recomputation: Instead of recomputing entire transformer layers, selective activation recomputation (Korthikanti et al., 2022 [3]) recomputes only the memory-intensive attention score matrices while saving linear MLP projections. When FlashAttention is active, selective recomputation is effectively built into the attention kernel.
  • Memory overhead of PyTorch compilation: Using torch.compile with Inductor fuses element-wise kernels and reduces activation memory, but requires additional temporary memory during compilation to capture CUDA graphs and build optimized kernel workspaces.
  • Why gradient accumulation does not save optimizer memory: Accumulating gradients across micro-batches allows simulating large global batches with smaller micro-batch activations, but it does not reduce model, gradient, or optimizer state tensors by a single byte.

Summary

  • GPU training memory comprises four distinct components: static model states, dynamic backward activations, temporary GEMM and communication buffers, and allocator fragmentation headroom.
  • Mixed-precision Adam consumes exactly 16 bytes per parameter (2B weight, 2B gradient, 4B master weight, 8B moments m and v). 75% of static memory belongs to the optimizer.
  • For Llama 3.1 8B, static states require 128.5 GB (119.7 GiB), exceeding the physical capacity of an 80 GB H100 by 48.5 GB before allocating a single activation tensor.
  • Uncheckpointed activations scale as 34sbh+5as2b per layer. At 8,192 tokens, standard attention activations explode to 380.1 GB across 32 layers, dominated by the quadratic 5as2b term.
  • FlashAttention removes the quadratic term entirely, cutting activations to 36.5 GB. Full activation checkpointing drops activations to 2.15 GB (saving 94%) in exchange for a 33.3% compute penalty (6ND→8ND FLOPs).
  • For pretraining on 256 H100s, intra-node FSDP over 8 GPUs is optimal: it reduces model states to 16.1 GB per GPU and keeps heavy sharding all-gathers on 900 GB/s NVLink, avoiding the 18× communication penalty of inter-node InfiniBand sharding.
  • Inference requires only 15 GiB for weights (0 optimizer states, 0 gradients), dedicating ~52 GiB of free memory to the KV cache for concurrent requests.

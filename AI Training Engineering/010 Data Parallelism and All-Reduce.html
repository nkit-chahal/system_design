Data Parallelism and All-Reduce

Introduction

Distributed deep learning began with a straightforward idea: when a dataset is too vast for a single machine to process in a reasonable time, distribute the data across multiple workers. In data parallelism (DP), every GPU in a cluster holds an identical copy of the model parameters. Each worker ingests a unique slice of the global training batch, computes a forward pass to determine the loss, and evaluates backpropagation to calculate local parameter gradients. Before any parameter can be updated, the workers execute a distributed collective operation called all-reduce to compute the arithmetic average of their gradients across all devices. Once synchronized, every GPU applies an identical optimizer update, guaranteeing that the model replicas remain bit-for-bit identical at the start of the next training step [1].

While conceptually elegant, scaling data parallelism to hundreds or thousands of GPUs reveals severe systems challenges. As cluster size grows, the volume of gradient data transmitted across network links threatens to overwhelm inter-node interconnects. Modern training systems overcome this communication barrier through bandwidth-optimal ring collectives, hierarchical network routing, and aggressive communication-computation overlap, where gradient synchronization for completed layers runs concurrently with backpropagation of earlier layers [1], [2].

However, pure data parallelism faces an unyielding physical constraint. Because every worker must maintain a complete copy of the model weights, gradients, and optimizer states, data parallelism does not reduce the per-GPU memory footprint by a single byte [5]. For modern large language models, the static memory required by standard mixed-precision optimizers exceeds the physical capacity of modern accelerators before allocating even one activation tensor. Understanding how data parallelism functions, where its network communication scales, and where its memory wall hits is the essential foundation for all advanced distributed training architectures.

In this lesson, we examine the mechanics of data parallelism, derive the exact communication volume of ring and tree all-reduce algorithms, analyze how PyTorch DDP overlaps gradient communication with backward computation, evaluate worked cluster timings for our 256-GPU cluster, examine the mathematical limits of batch size scaling, and discover why plain data parallelism must ultimately yield to state sharding.

Clarifying the Problem

In systems design interviews for distributed training infrastructure, discussions around data parallelism typically begin with cluster sizing and scaling efficiency. Here is how a discussion between a candidate and an interviewer unfolds:

Candidate: What model architecture, precision, and optimizer are we targeting for this pretraining cluster?
Interviewer: We are training a model with the Llama 3.1 8B architecture—8.03 billion parameters across 32 transformer layers. We use BF16 mixed-precision training with the AdamW optimizer.

Candidate: What cluster hardware and network topology are available?
Interviewer: We have 256 NVIDIA H100 80 GB SXM GPUs arranged across 32 nodes (8 GPUs per node). Within each node, the 8 GPUs communicate over NVLink at 900 GB/s bidirectional bandwidth per GPU. Across nodes, each node connects through 8 dedicated 400 Gb/s InfiniBand NDR NICs, providing 50 GB/s line rate per GPU.

Candidate: What are the sequence length and global batch size targets?
Interviewer: The sequence length is 8,192 tokens. The target global batch size is approximately 4 million tokens per optimizer step, which equals 512 sequences.

Candidate: Can we train this run using plain PyTorch DistributedDataParallel (DDP) across all 256 GPUs?
Interviewer: That is the core question. Can you train Llama 3.1 8B using pure data parallelism on this cluster, how long does the gradient all-reduce take, and does network communication hide behind compute?

The question underneath is: How does data-parallel communication scale across an InfiniBand network fabric, can asynchronous gradient bucketing completely mask collective latency behind tensor core computation, and why does memory capacity force us beyond plain replication?

The Mechanics of Data Parallelism and All-Reduce

Micro-batch partitioning and synchronization

Let N be the number of data-parallel workers (GPUs) and let B be the global batch size measured in sequences. In standard data parallelism, each GPU receives a disjoint micro-batch of size b=B/N sequences. Worker i evaluates the loss ℒi(W) over its local micro-batch using local model weights W. During the backward pass, automatic differentiation evaluates local parameter gradients:

gi=∇Wℒi(W)

Because the objective function across the global batch is the arithmetic mean of the local losses, the true global gradient g¯ is the average of the local gradient vectors across all N workers [1]:

g¯=1N∑i=0N−1gi

The collective operation that sums tensors across all ranks and delivers the resulting sum to every rank is all-reduce. Once all-reduce completes, each worker scales the sum by 1/N to produce g¯ and invokes its local optimizer (such as AdamW) to update W. Because all replicas begin with identical initial weights and apply identical averaged gradients, their updated weights remain synchronized without requiring parameter broadcasts.

The Ring All-Reduce algorithm

A naive implementation of all-reduce might designate a master node, gather all gradients to that node, sum them, and broadcast the result back. For N=256 workers, the master node's network interface would saturate immediately, creating an intractable bottleneck. Modern distributed systems execute all-reduce using decentralized algorithms, most notably ring all-reduce [2].

In ring all-reduce, the N GPUs are logically arranged in a unidirectional ring: rank i transmits data only to rank (i+1)modN and receives data only from rank (i−1)modN. The gradient buffer of size S bytes is partitioned into N equal chunks of size S/N. The algorithm executes in two distinct phases of N−1 steps each [2]:

Phase 1: Reduce-Scatter (N−1 steps)

At each step k∈[0,N−2], each worker i sends chunk (i−k)modN to rank i+1 while simultaneously receiving chunk (i−k−1)modN from rank i−1. Upon receiving a chunk, the worker performs an element-wise vector sum with its local corresponding chunk. After N−1 steps, each worker holds the fully accumulated sum for exactly one of the N chunks. The total volume of data sent by each GPU during this phase is:

Data Sentreduce-scatter=(N−1)×(SN)=N−1NS bytes

Phase 2: All-Gather (N−1 steps)

In the second phase, the fully reduced chunks are circulated around the ring so that every worker receives the complete gradient tensor. At each step, worker i sends its newly acquired fully reduced chunk to rank i+1 and receives another reduced chunk from rank i−1. After N−1 steps, all N chunks have visited every GPU. The total data sent by each GPU during all-gather is identical to Phase 1:

Data Sentall-gather=(N−1)×(SN)=N−1NS bytes

Total traffic and bandwidth optimality

Summing both phases yields the total network traffic transmitted (and received) by each GPU during ring all-reduce [2]:

Total Data Sent per GPU=2×N−1NS bytes

This formula demonstrates a profound mathematical property: as the number of GPUs N grows large, the fraction (N−1)/N→1. Consequently:

limN→∞Total Data Sent per GPU=2S bytes

The communication volume per GPU is asymptotically independent of the number of GPUs. Doubling the cluster size from 128 to 256 GPUs does not double the data transmitted per worker; each worker always transfers approximately 2S bytes. If the interconnect provides bidirectional bandwidth B, the transfer time is governed by:

Tring=2N−1NSB+2(N−1)α

where α represents the network latency per transfer step. For large models where S is measured in gigabytes, the bandwidth term 2S/B completely dominates the latency term 2Nα, achieving near 100% link utilization [2].

Collective Topologies in NCCL: Ring versus Tree

The NVIDIA Collective Communications Library (NCCL) implements the communication primitives underpinning PyTorch DDP. While the ring algorithm maximizes bandwidth utilization for large messages, its latency scales linearly with N (2(N−1)α steps). On large clusters with hundreds or thousands of nodes, this linear hop count introduces measurable overhead for small tensors [6].

To eliminate this latency bottleneck, NCCL incorporates the Double Binary Tree algorithm [6]. GPUs are arranged into two complementary binary trees where internal nodes in one tree act as leaves in the other. In a tree topology, the reduction flows up to the root in log2N steps, followed by a broadcast down the tree in log2N steps, yielding a total latency of 2log2N×α [6]. However, because root and internal nodes must service multiple child edges, link utilization is lower than in a balanced ring.

NCCL selects the optimal algorithm dynamically at runtime using an internal analytical cost model (the auto algorithm mode). For small buffers (typically below 256 KiB to 4 MiB), NCCL deploys Tree all-reduce to minimize latency hops. For large gradient tensors, it routes traffic through Ring all-reduce (or NVLS hardware-accelerated multicast trees within Hopper NVSwitches) to saturate line-rate bandwidth [6].

Overlapping Communication with Computation

Why naive synchronization stalls training

A naive data-parallel implementation would compute the full forward pass, compute the full backward pass across all layers, and then initiate an all-reduce across all model parameters. Under this blocking model, GPU tensor cores sit completely idle throughout the all-reduce phase, waiting for network transfers to conclude. Conversely, the high-speed network interfaces sit completely idle throughout the forward and backward passes. This serialization wastes substantial hardware capacity [1].

PyTorch DDP: Autograd hooks and gradient bucketing

PyTorch DistributedDataParallel (DDP) avoids serialization by overlapping communication directly with the backward pass [1]. This overlap relies on a fundamental architectural reality: backpropagation traverses neural network layers in reverse topological order. Gradients for the final transformer layer (Layer 32) are fully evaluated milliseconds after the backward pass begins, while gradients for Layer 1 will not be computed until the backward pass reaches completion.

Instead of dispatching an all-reduce operation for each individual parameter—which would flood the CUDA stream and NCCL with thousands of tiny, high-overhead kernel launches—DDP aggregates parameter gradients into contiguous memory buffers called buckets [1]:

  1. Initialization: When DistributedDataParallel(model) is constructed, DDP inspects the model parameters and packs them into buckets in roughly reverse order of model.parameters(). The maximum size of each bucket is governed by the configuration parameter bucket_cap_mb (defaulting to 25 MiB) [1], [7].
  2. Hook Registration: DDP registers a post-accumulate gradient autograd hook (register_post_accumulate_grad_hook) on every parameter tensor [1].
  3. Bucket Readiness: As loss.backward() executes, whenever a parameter's gradient computation concludes, its autograd hook fires and marks that parameter ready within its assigned bucket.
  4. Asynchronous Launch: The instant the final parameter in a bucket is marked ready, DDP immediately dispatches an asynchronous non-blocking all-reduce (via torch.distributed.all_reduce) for that entire bucket on a dedicated CUDA communication stream [1].
  5. Concurrent Execution: While the network interface transfers and reduces Bucket 0 across the cluster, the GPU compute stream is actively evaluating gradients for Bucket 1. By the time the backward pass reaches the initial model layers, nearly all upper-layer gradient buckets have already completed their network transfers [1].

Gradient accumulation and synchronization control

When training large models, the micro-batch size that fits in memory may be smaller than the desired batch size per GPU. Engineers use gradient accumulation: running multiple local forward and backward passes, accumulating gradients into param.grad, and executing the optimizer update only once every K micro-steps.

Under standard DDP, every call to loss.backward() triggers gradient all-reduce across all buckets. Launching communication on intermediate accumulation steps is entirely redundant, as only the final accumulated gradient needs to be synchronized. PyTorch DDP provides the model.no_sync() context manager to disable gradient synchronization during intermediate micro-batches [1], [7]:

Accumulation Loop
# Accumulate gradients over K micro-batches without network sync
optimizer.zero_grad()
for step in range(accumulation_steps):
    is_last_microbatch = (step == accumulation_steps - 1)

    # Disable all-reduce during intermediate micro-steps
    if not is_last_microbatch:
        with model.no_sync():
            outputs = model(inputs[step])
            loss = criterion(outputs, targets[step]) / accumulation_steps
            loss.backward()
    else:
        # Final micro-step: DDP hooks fire and all-reduce runs
        outputs = model(inputs[step])
        loss = criterion(outputs, targets[step]) / accumulation_steps
        loss.backward()

optimizer.step()

By wrapping the first K−1 backward passes in model.no_sync(), the cluster eliminates K−1 network communication rounds, preserving interconnect bandwidth exclusively for the final synchronization step [1].

Worked Cluster Numbers: Bandwidth, Latency, and Compute Overlap

Sizing gradient communication for Llama 3.1 8B

Let us apply these formulas to our pretraining scenario. The model has Nparams=8.03×109 parameters. In BF16 mixed-precision training, each gradient element requires 2 bytes. The uncompressed gradient tensor size is:

S=8.03×109×2 bytes=16.06×109 bytes≈16.06 GB(14.96 GiB)

We evaluate all-reduce communication performance across two physical network fabrics:

1. Intra-node NVLink (8 GPUs)

Inside a single 8-GPU H100 SXM node, GPUs connect through NVSwitches providing 900 GB/s bidirectional NVLink bandwidth per GPU (450 GB/s transmit and 450 GB/s receive). For N=8 ranks:

Traffic Factor=2×8−18=2×78=1.75 Data Transferred per GPU=1.75×16.06 GB=28.105 GB

At 900 GB/s effective bus bandwidth, the time required to all-reduce the entire 8B gradient tensor across the node is:

TNVLink=28.105 GB900 GB/s≈0.0312 s=31.2 ms

Even accounting for 80% practical bus efficiency (~720 GB/s), the all-reduce completes in under 39 ms.

2. Inter-node InfiniBand (256 GPUs across 32 nodes)

Across the full 256-GPU cluster, each node contains 8 InfiniBand NDR NICs operating at 400 Gb/s, providing 50 GB/s dedicated bidirectional line rate per GPU. For N=256 ranks:

Traffic Factor=2×256−1256=2×255256≈1.9922 Data Transferred per GPU=1.9922×16.06 GB=31.995 GB≈32.00 GB

At 50 GB/s line rate, the theoretical minimum all-reduce time across the 256-GPU cluster is:

TIB=31.995 GB50 GB/s≈0.640 s=640 ms

Assuming 90% network efficiency after packet headers and congestion (~45 GB/s), the actual transfer requires approximately 711 ms.

Step compute time versus communication latency

To determine whether the 640 ms InfiniBand all-reduce introduces pipeline stalls, we must compare it against the computation time of one training step. The global batch size is 512 sequences of 8,192 tokens (approximately 4.19 million tokens). Across 256 GPUs, each GPU processes:

Sequences per GPU=512256=2 sequences=16,384 tokens per step

With micro-batch size b=1, each GPU executes 2 gradient accumulation steps. When using full activation checkpointing (recomputation), training requires approximately 8×Nparams floating-point operations per token [3] (see Lesson 7, Training FLOPs, Time and MFU). The compute workload per GPU per step is:

FLOPs per step=8×8.03×109×16,384≈1.053×1015 FLOPs=1,053 TFLOPs</textblock><p>AnNVIDIAH100SXMGPUdelivers989denseBF16TFLOPSpeak.Atourtarget40<texblock>Sustained Throughput=989 TFLOPS×0.40=395.6 TFLOPS</textblock><p>Dividingworkloadbythroughputyieldsthetotalstepcomputeduration:</p><texblock>Tcompute=1,053 TFLOPs395.6 TFLOPS≈2.662 seconds

In standard backpropagation with activation recomputation, the forward pass consumes approximately one quarter of the computation (~0.665 s), while the backward pass consumes three quarters (≈1.997 s).

Here is the critical observation: the 640 ms InfiniBand all-reduce is vastly shorter than the 1,997 ms backward compute pass (640 ms/1,997 ms≈32%). Because DDP streams gradient buckets asynchronously as layers complete, the entire 16 GB gradient transfer finishes long before the backward pass evaluates the final input embeddings. The communication overhead is 100% hidden, allowing the cluster to scale with near-linear compute efficiency.

The vulnerability of shrinking batch size

What happens if the team reduces the global batch size to 256 sequences (1 sequence per GPU, with no gradient accumulation)?

With only 8,192 tokens per GPU, the compute workload halves to 526 TFLOPs, cutting total step compute to 1.33 s and backward pass duration to approximately 0.998 s (998 ms). While the 640 ms all-reduce still fits within 998 ms, the communication margin narrows dramatically: communication now occupies 64% of the backward window. Any transient packet loss, route congestion on the spine switches, or straggler GPU delay will immediately exceed the remaining 358 ms buffer, stalling the compute engines and degrading cluster MFU.

Global Batch Size, Gradient Accumulation, and Optimization Limits

The Critical Batch Size and Gradient Noise Scale

Given that larger batch sizes provide longer backward passes that easily conceal communication latency, why not scale the global batch size to 10 million or 50 million tokens? The constraint lies not in networking, but in optimization mathematics.

In their seminal empirical study, McCandlish et al. established that every neural network training run exhibits a Critical Batch Size, denoted Bcrit [4]. The critical batch size is governed by the gradient noise scale ℬ*, which measures the ratio of the trace of the gradient covariance matrix to the squared norm of the true gradient vector [4]:

ℬ*=Tr(Σ)|G|2=𝔼[|gi−G|2]|G|2

where G=𝔼[gi] is the true gradient and Σ is the covariance of individual sample gradients.

The gradient noise scale defines two distinct operating regimes [4]:

  • Linear Scaling Regime (B≪Bcrit): When the batch size is small, individual gradients are noisy. Increasing the batch size averages out the noise, providing a higher-fidelity gradient estimate. In this regime, doubling the batch size halves the number of optimizer steps required to reach a target validation loss. Step throughput scales with near-perfect linear speedup.
  • Diminishing Returns Regime (B≫Bcrit): Once the batch size surpasses Bcrit, gradient variance is effectively eliminated; additional samples yield virtually identical gradient averages. Further increasing batch size does not reduce the required optimization steps, meaning extra compute is wasted on redundant data. Total sample efficiency collapses.

For modern 7B–8B parameter autoregressive language models, empirical measurements show that Bcrit starts around 1 million to 2 million tokens in early training and expands to approximately 4M to 8M tokens as the loss stabilizes [4]. Our target pretraining batch size of ~4M tokens (512 sequences of 8,192 tokens) sits precisely at this sweet spot, maximizing cluster parallelism without crossing into the regime of wasteful diminishing returns.

Learning rate scaling rules

When changing the global batch size, the learning rate must be adjusted to maintain stable convergence. Two primary conventions exist:

  1. Linear Scaling Rule: Formulated by Goyal et al. for SGD [3], setting ηnew=ηbase×(Bnew/Bbase). To prevent early instability when applying large learning rates, training must include a linear warmup schedule, gradually ramping the learning rate from near zero over the first several thousand steps [3].
  2. Square-Root Scaling Rule: For adaptive moment optimizers such as AdamW, the second moment normalizer scales with the root of squared gradients. Many pretraining recipes scale the learning rate with the square root of the batch size ratio: ηnew=ηbase×Bnew/Bbase, which maintains better numerical stability across large batch transitions.

The Memory Wall: Why Plain DDP Fails for 8B Models

We have demonstrated that over our 256-GPU InfiniBand network, data-parallel communication takes only 640 ms and hides entirely behind the 1,997 ms backward pass. Why, then, can we not simply deploy standard PyTorch DDP to pretrain Llama 3.1 8B?

The answer is the 16-byte memory wall analyzed in Lesson 3, Training Memory. In pure DDP, every worker GPU maintains a standalone, complete model replica. For mixed-precision training with AdamW, each parameter requires 16 bytes of static memory [5]:

  • BF16 model parameters: 2 bytes (8.03×109×2=16.06 GB)
  • BF16 gradients: 2 bytes (8.03×109×2=16.06 GB)
  • FP32 master parameters: 4 bytes (8.03×109×4=32.12 GB)
  • FP32 Adam momentum (m): 4 bytes (8.03×109×4=32.12 GB)
  • FP32 Adam variance (v): 4 bytes (8.03×109×4=32.12 GB)

Summing these components yields:

Static Memory per GPU=16 bytes×8.03×109=128.48 GB(119.66 GiB)

An NVIDIA H100 80 GB SXM GPU exposes 79.6 GiB of usable High Bandwidth Memory. Replicating the model states under plain DDP requires 119.66 GiB, exceeding physical memory capacity by 48.5 GB per GPU before allocating a single activation tensor, communication buffer, or CUDA context overhead!

Gradient accumulation reduces activation memory by shrinking the micro-batch size, but gradient accumulation does nothing to shrink static model or optimizer states. Plain PyTorch DDP cannot train Llama 3.1 8B on an 80 GB GPU. To make pretraining physically possible, the redundant 16 bytes per parameter must be partitioned across devices. How much data parallelism for our run?

For our 256-GPU pretraining run targeting Llama 3.1 8B with global batch size 512 sequences, we require a total data-parallel degree of 256 (DP=256). However, because plain DDP runs out of memory, we cannot replicate all states. Instead, we must employ sharded data parallelism (Fully Sharded Data Parallelism / ZeRO), which we explore thoroughly in Lesson 11, ZeRO and FSDP. By sharding optimizer states, gradients, and model parameters across GPUs, the static memory per GPU drops from 128.5 GB to under 16 GB, fitting comfortably within our 80 GB H100 budget while preserving the overlap characteristics of all-reduce.

In Practice

The code below demonstrates a minimal, correct PyTorch DistributedDataParallel implementation configured for multi-node execution. The script configures the process group using NCCL, tunes gradient bucketing via bucket_cap_mb, demonstrates gradient accumulation with model.no_sync(), and is launched using torchrun.

train_ddp.py
torchrun launch
import os
import torch
import torch.nn as nn
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader, Dataset
from torch.utils.data.distributed import DistributedSampler

class SyntheticDataset(Dataset):
    def __init__(self, size: int = 1024, seq_len: int = 2048, hidden: int = 4096):
        self.size = size
        self.seq_len = seq_len
        self.hidden = hidden

    def __len__(self):
        return self.size

    def __getitem__(self, idx):
        # Micro-batch synthetic token representations
        x = torch.randn(self.seq_len, self.hidden)
        y = torch.randn(self.seq_len, self.hidden)
        return x, y

def setup_distributed():
    # torchrun populates RANK, WORLD_SIZE, LOCAL_RANK, MASTER_ADDR, MASTER_PORT
    dist.init_process_group(backend="nccl")
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)
    return local_rank

def cleanup_distributed():
    dist.destroy_process_group()

def main():
    local_rank = setup_distributed()
    device = torch.device(f"cuda:{local_rank}")

    # Simple model replica
    model = nn.Sequential(
        nn.Linear(4096, 4096, bias=False),
        nn.GELU(),
        nn.Linear(4096, 4096, bias=False)
    ).to(device)

    # Wrap in DDP with custom bucket_cap_mb (default 25 MB)
    # Tuning bucket_cap_mb balances overlap frequency against collective launch overhead
    model = DDP(
        model,
        device_ids=[local_rank],
        output_device=local_rank,
        bucket_cap_mb=25,
        find_unused_parameters=False
    )

    optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4)
    criterion = nn.MSELoss()

    dataset = SyntheticDataset()
    sampler = DistributedSampler(dataset, shuffle=True)
    loader = DataLoader(dataset, batch_size=1, sampler=sampler)

    accumulation_steps = 2
    model.train()

    optimizer.zero_grad()
    for step, (inputs, targets) in enumerate(loader):
        inputs = inputs.to(device)
        targets = targets.to(device)
        is_accumulation_boundary = ((step + 1) % accumulation_steps == 0)

        # Disable all-reduce gradient synchronization during intermediate micro-steps
        if not is_accumulation_boundary:
            with model.no_sync():
                outputs = model(inputs)
                loss = criterion(outputs, targets) / accumulation_steps
                loss.backward()
        else:
            # Final micro-step: triggers asynchronous bucketed all-reduce
            outputs = model(inputs)
            loss = criterion(outputs, targets) / accumulation_steps
            loss.backward()
            optimizer.step()
            optimizer.zero_grad()

    cleanup_distributed()

if __name__ == "__main__":
    main()
# Launch script for 32 nodes with 8 H100 GPUs per node (256 GPUs total)
# Run on Rank 0 node:
torchrun \
  --nnodes=32 \
  --nproc_per_node=8 \
  --node_rank=0 \
  --master_addr="10.0.0.1" \
  --master_port=29500 \
  train_ddp.py

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • GPUDirect RDMA: How modern NICs bypass host memory and transfer gradient buffers directly between GPU HBM across PCI switches or NVLink, cutting latency and freeing CPU cores [6].
  • Gradient Compression: Techniques such as FP8 gradient all-reduce, 1-bit Adam, and PowerSGD that compress the 16 GB gradient payload to 8 GB or 2 GB on bandwidth-constrained Ethernet clusters.
  • Straggler Mitigation: How a single throttled GPU or thermal event on one of 256 workers stalls the synchronous ring all-reduce, degrading cluster-wide MFU, and how watchdogs monitor rank completion times.
  • NCCL Channels: How NCCL establishes multiple concurrent rings and trees (typically 8 to 32 channels) mapped to distinct SMs and PCIe lanes to fully saturate bidirectional interconnects [6].
  • Dynamic Batch Sizing: Gradually expanding the global batch size from 1M to 4M tokens across the pretraining curriculum to match the evolving gradient noise scale ℬ* [4].
  • Fault Recovery: Why data-parallel checkpoints require coordinated distributed saving (such as PyTorch Distributed Checkpointing), where each rank saves its local data slice without gathering to rank 0.

Summary

  • Data parallelism replicates the full model across all GPUs and partitions the global batch into distinct micro-batches. Local gradients are averaged via collective all-reduce before the optimizer step.
  • Ring all-reduce executes in two phases—Reduce-Scatter and All-Gather—transferring 2(N−1)/N×S bytes per GPU. Communication volume asymptotically approaches 2S, remaining independent of GPU count.
  • NCCL dynamically switches between Double Binary Tree (low latency, 2log2N steps) for small payloads and Ring (high bandwidth, 2N steps) for large gradient buffers.
  • PyTorch DDP overlaps communication with computation by grouping parameters into buckets (governed by bucket_cap_mb) and launching asynchronous all-reduces as reverse-topological backpropagation completes each bucket.
  • For Llama 3.1 8B (16.06 GB BF16 gradients), all-reduce takes 31.2 ms over intra-node NVLink and 640 ms across 256 GPUs over 400 Gb/s InfiniBand. This 640 ms is easily hidden within the 1,997 ms backward pass.
  • Plain DDP cannot train Llama 3.1 8B because replicating weights, gradients, and Adam states requires 128.5 GB per GPU, exceeding an 80 GB H100 by 48.5 GB. Sharded data parallelism (ZeRO and FSDP) is mandatory.

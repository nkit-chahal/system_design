Pretraining Data Pipelines

Introduction

Modern large language models are fundamentally shaped by the data on which they train. While model architectures, optimizer settings, and parallel communication schemes dictate how efficiently compute converts into parameters, the training data sets the ceiling on reasoning ability, factual recall, and downstream performance. Feeding petabytes of uncurated internet text directly into a distributed cluster yields models plagued by toxic repetition, hallucination, and degraded benchmark accuracy [1].

Transforming raw, noisy internet crawls into a high-octane pretraining corpus requires an industrial-scale pretraining data pipeline. This multi-stage pipeline ingests hundreds of terabytes of compressed web archives, extracts clean body prose while stripping navigation boilerplates and ads, filters non-target languages, purges repetitive gibberish, removes personally identifiable information (PII), deduplicates mirror documents, tokenizes text into discrete integer IDs, and packs documents into fixed-length sequence shards [2].

At our pretraining scale of 1 trillion tokens, data pipelines handle astronomical volumes: roughly 20 to 40 terabytes of raw crawl text must be decanted into 4 terabytes of pristine, packed token arrays. Furthermore, during distributed training on 256 NVIDIA H100 GPUs, the data loader must stream sequences at over 2 million tokens per second without a single worker stalling, because a 400-millisecond I/O pause on one rank stalls the entire 256-GPU cluster at the next collective synchronization barrier.

In this lesson, we examine where pretraining data originates across major open datasets, trace the eight stages of a modern pipeline, calculate the storage and CPU compute budgets required to process 1 trillion tokens, analyze the mechanics of fixed-length sequence packing, and design a streaming data loader that guarantees deterministic resumption after cluster failures.

Clarifying the Problem

In a systems design interview for an AI infrastructure or training role, data engineering questions often begin with dataset sizing, pipeline throughput, or data-loader starvation. Here is how a discussion between a candidate and an interviewer typically unfolds:

Candidate: What model architecture, context window, and token budget are we targeting for this pretraining run?
Interviewer: We are pretraining a model with the Llama 3.1 8B architecture—32 layers, hidden dimension 4,096, vocabulary size 128,256, and a sequence length of 8,192 tokens. The pretraining budget is 1 trillion tokens.

Candidate: What compute cluster are we feeding, and what hardware efficiency do we expect?
Interviewer: We have 256 NVIDIA H100 80 GB SXM GPUs arranged across 32 nodes (8 GPUs per node) connected by 400 Gb/s InfiniBand NDR. We target 40% Model FLOPs Utilization (MFU).

Candidate: What raw data sources do we have access to, and are we building the dataset from raw Common Crawl archives or curating existing open pretraining corpora?
Interviewer: We want to understand both paths. We have access to Common Crawl dumps, public GitHub code, arXiv papers, and existing open datasets like FineWeb and Dolma. We need to decide how to build our 1-trillion-token mix.

Candidate: Are there strict data-loading constraints during training, especially regarding recovery from hardware restarts?
Interviewer: Yes. The cluster experiences occasional node failures. The data loader must resume deterministically from the exact sequence offset where the checkpoint was saved, without re-shuffling or re-reading past shards.

Candidate: Can we allow padding tokens within our 8,192-token context windows?
Interviewer: Absolutely not. At 40% MFU, wasting 20% or 40% of sequence slots on padding tokens would burn tens of thousands of dollars in wasted H100 compute. Every sequence must be fully packed.

The question underneath is: How do we process petabytes of raw web text into 1 trillion high-quality packed tokens, store them in high-throughput binary container formats, and feed a 256-GPU cluster at 2.1 million tokens per second without I/O stalls? To answer it, we begin by examining where pretraining data comes from.

Pretraining Text Sources: Web, Code, and Curated Data

Where pretraining text originates

Pretraining corpora for modern foundation models do not come from a single monolithic repository. Instead, they combine diverse domain slices to balance linguistic breadth, multi-step logical reasoning, factual knowledge, and structural syntax [3]. The primary sources include:

  • Web crawls (Common Crawl): Common Crawl is an open repository of web crawl data that has archived billions of web pages since 2008. Each monthly crawl produces roughly 200 to 300 TB of compressed web archives. It provides unmatched linguistic diversity and real-world knowledge, but over 80% of its volume consists of navigation menus, spam, machine-generated SEO text, boilerplate footers, and link farms [2].
  • Source code: Repositories from GitHub (such as The Stack v1 and v2 [4]) provide code in hundreds of programming languages, documentation, and commit histories. Training on code significantly improves symbolic reasoning, algorithmic problem-solving, and instruction adherence in natural language tasks [3].
  • Academic papers: Preprints and peer-reviewed papers from arXiv, PubMed Central, and S2ORC/peS2o provide dense, formal discourse, technical terminology, and mathematical equations formatted in LaTeX [3].
  • Books and literature: Corpora such as PG-19 (Project Gutenberg) and Smashwords provide long-form narrative arcs, literary prose, and extended character dialog, teaching the model long-range discourse structure across thousands of tokens [1].
  • Curated encyclopedic and Q&A domains: Wikipedia, StackExchange, and Wikihow contribute high-density factual explanations, multi-turn community reviews, and structured problem resolutions.

Open pretraining corpora: FineWeb, Dolma, and RedPajama

In recent years, open-science initiatives have transparently published both multi-trillion-token pretraining datasets and the exact software tools used to curate them:

  • FineWeb (Hugging Face, 2024): A 15-trillion-token English web dataset derived from 96 Common Crawl snapshots spanning 2013 to 2024 [2]. Stored as 44 TB of uncompressed Parquet files, FineWeb demonstrated that thorough heuristic filtering, Trafilatura text extraction, and MinHash deduplication produce open models that outperform models trained on older open web corpora such as C4 or RefinedWeb. The specialized FineWeb-Edu subset contains 1.3 trillion tokens filtered using an educational quality classifier, achieving superior scores on reasoning benchmarks such as MMLU and ARC [2].
  • Dolma (Allen Institute for AI, 2024): A 3-trillion-token English corpus created to train the open-weights OLMo model family [3]. Dolma compiles 68% web crawl, 14% scientific papers (peS2o), 9% source code (The Stack), and 9% books, Wikipedia, and social discussion. The Dolma toolkit open-sourced high-throughput Rust and Python filtering components that process petabytes of text using modular Bloom filters and heuristic rules.
  • RedPajama (Together AI, 2023): RedPajama-1T reproduced the original 1.2-trillion-token LLaMA pretraining mixture across seven distinct domains (Common Crawl, C4, GitHub, arXiv, Wikipedia, Books, and StackExchange) [5]. RedPajama-Data-v2 scaled this effort to over 30 trillion raw tokens across five languages, providing pre-computed quality annotations (such as Gopher and C4 heuristic metrics) for every document.

Scale arithmetic: Sizing 1 trillion tokens

To plan storage and compute infrastructure, we must translate tokens into physical storage units. In modern Byte-Level Byte-Pair Encoding (BPE) tokenizers (such as Llama 3's 128k tokenizer), one token corresponds to approximately 4.0 bytes of clean UTF-8 text (roughly 0.75 words per token) [2].

  • Tokens per GB of clean text: 109 bytes/4.0 bytes/token≈250×106 tokens (250 million tokens per decimal GB).
  • Raw text storage for 1T tokens: 1012 tokens×4.0 bytes/token=4.0×1012 bytes=4.0 TB of uncompressed clean text (3.64 TiB).
  • Tokenized integer array storage: Llama 3.1 8B uses a vocabulary size of V=128,256. Because 128,256>216−1=65,535, token IDs cannot fit into 16-bit unsigned integers (uint16). They require 32-bit unsigned integers (uint32), consuming 4 bytes per token. Thus, 1 trillion token IDs stored as raw binary arrays require exactly 1012×4 bytes=4.0 TB.
  • Crawl volume required: Raw web crawls yield only 10% to 20% clean, usable text after discarding non-target languages, HTML markup, navigation boilerplate, low-quality spam, and near-duplicate pages [2]. Sourcing 4 TB of clean text therefore requires ingesting between 20 TB and 40 TB of uncompressed crawl text, corresponding to 5 to 10 monthly Common Crawl dumps (hundreds of terabytes of compressed WARC files).
  • CPU processing budget: Parsing 30 TB of raw HTML with high-quality extractors like Trafilatura (which process ~15 to 25 MB/s per modern CPU core) requires approximately 30×106 MB/20 MB/s=1.5×106 core-seconds≈417 core-hours. Adding language identification, heuristic filtering, and MinHash deduplication brings the total processing budget to approximately 3,000 to 5,000 CPU core-hours. On a 128-core compute node, the entire data ingestion and filtering pipeline completes in under 40 hours.

Pipeline Stages: From Raw Web Archive to Clean Text

Step 1: HTML text extraction (WARC vs WET)

Common Crawl distributes web archives in three formats: WARC (Web ARChive, containing raw HTTP response headers and full HTML markup), WAT (extracted metadata), and WET (text extracted by Common Crawl's internal pipeline). Early NLP datasets such as C4 used WET files directly. However, Common Crawl's WET extractor naively dumps DOM text nodes, preserving navigation menus, cookie consent banners, sidebar teasers, and copyright footers while stripping structural markdown headings [2].

Modern pretraining pipelines (such as FineWeb and RefinedWeb) bypass WET files and extract text directly from raw WARC archives using specialized content extractors such as Trafilatura [6] or Resiliparse. Trafilatura analyzes the DOM tree structure, evaluates paragraph-to-boilerplate text density, identifies the primary <article> container, and strips navigational chrome, advertisements, and legal disclaimers while preserving document headings, lists, and paragraph boundaries. Figure 3 illustrates this contrast.

Step 2: Language identification

The extracted text contains hundreds of distinct languages. To isolate target languages (or enforce balanced multilingual ratios), pipelines evaluate every document with a fast linear classifier, predominantly fastText using the pretrained lid.176.bin model [7]. FastText evaluates character n-grams, classifying documents at rates exceeding 100 MB/s per CPU core.

Standard practice enforces a probability threshold (e.g., fastText English confidence score P(en)≥0.65). Documents falling below the threshold are either discarded or routed to secondary multilingual language queues. Extremely short documents (< 50 words) frequently trigger false positives or low confidence scores and are purged during heuristic filtering.

Step 3: Heuristic quality filtering

Rule-based heuristic filters eliminate documents that are technically valid text but semantically worthless for language modeling. The industry standard heuristics originate from DeepMind's Gopher quality filters [1] and Google's C4 heuristics [8]:

  • Word count boundaries: Documents must contain between 50 and 100,000 words. Shorter texts lack sufficient context; longer texts are frequently machine-generated logs or concatenated dictionaries [1].
  • Mean word length: The average word length must fall between 3 and 10 characters. A mean length below 3 indicates abbreviation lists or symbol soup; a mean above 10 indicates unspaced code, chemical formulas, or obfuscated spam.
  • Symbol-to-word ratio: The ratio of symbols (such as #, $, %, ...) to total words must remain below 0.1 (10%).
  • Repetition thresholds: Web pages often get stuck in repetitive loops (e.g., "click here click here"). Documents are rejected if the most frequent 2-gram accounts for more than 20% of total 2-grams, or if the top 3-gram exceeds 18%, or top 4-gram exceeds 16% [1].
  • Stopword presence: Coherent natural language documents contain common grammatical stopwords (e.g., "the", "and", "is", "of"). A document must contain at least 2 unique stopwords; documents lacking stopwords are typically keyword-stuffed SEO listings or table headers.
  • Line-start and ellipsis filters: Documents where more than 90% of lines begin with bullet points, or where more than 30% of lines end with ellipses (...), are purged to remove product catalogs and truncated RSS feeds [1].

Step 4: Deduplication and quality filtering

Even after heuristic cleaning, web text contains massive redundancy: syndicated news articles, boilerplate privacy policies, mirror websites, and near-identical blog reposts appear tens of thousands of times. Unchecked duplicates cause catastrophic memorization, waste cluster compute, and contaminate evaluation benchmarks. Deduplication algorithms (exact hash matching, MinHash with Locality-Sensitive Hashing, and suffix-array substring removal) and model-based quality scoring (such as FineWeb-Edu's classifier) form the intellectual core of modern curation; we study them exhaustively in Lesson 18, Deduplication and Quality Filtering.

Step 5: PII removal and safety filtering

Before tokenization, text must be scrubbed of personally identifiable information (PII) to protect privacy and comply with regulatory standards [3]. High-speed regular expressions and lightweight Named Entity Recognition (NER) models scan for sensitive patterns:

  • IPv4 and IPv6 addresses are replaced with <IP_ADDRESS> tokens.
  • Email addresses are replaced with <EMAIL> tokens.
  • US Social Security Numbers and national identity numbers are replaced with <ID_NUM>.
  • Phone numbers matching international E.164 formats are masked.

Safety filters apply domain blocklists (such as the LDNOOBW list of adult and illegal domains) and toxic text classifiers to remove hate speech, explicit content, and malicious instructions [1, 2].

How do we build 1T tokens for our run?

For our 256-H100 pretraining run targeting Llama 3.1 8B, building a web crawler from scratch to collect 30 TB of raw WARC archives is an expensive, unnecessary operational distraction. The most rigorous engineering strategy combines verified open pretraining corpora with high-value domain data:

  • Core web backbone (70% · 700B tokens): Ingest a verified slice of FineWeb and FineWeb-Edu. FineWeb has already undergone state-of-the-art Trafilatura extraction, fastText language filtering, and MinHash deduplication, validated across hundreds of ablation models [2].
  • Code reasoning (15% · 150B tokens): Ingest permissive source code from The Stack v2 [4] across Python, C++, Rust, Go, JavaScript, and SQL, formatted with repository metadata.
  • Academic and technical (10% · 100B tokens): Ingest scientific preprints from arXiv and peS2o (Dolma's cleaned S2ORC corpus [3]), providing formal mathematics, algorithms, and technical reasoning.
  • Encyclopedic and reference (5% · 50B tokens): Ingest recent dumps of Wikipedia, StackExchange, and curated documentation.

This 70/15/10/5 mixture guarantees strong natural language generation, robust code syntax, and deep factual recall while avoiding the multi-week engineering overhead of raw WARC scraping.

Tokenization, Packing, and Binary Storage

Step 6: Tokenization

Once text is cleaned, filtered, and scrubbed, it must be converted from raw UTF-8 strings into discrete token IDs. We apply a Byte-Level Byte-Pair Encoding (BPE) tokenizer with a 128,256 vocabulary (matching Llama 3.1). We examine tokenizer algorithms, vocabulary sizing trade-offs, and parameter costs in detail in Lesson 19, Tokenizers.

Step 7: Sequence packing

Transformer architectures process batches of fixed sequence length (in our scenario, s=8,192 tokens). However, real-world documents vary wildly in length: a short news brief may contain 250 tokens, while an academic paper contains 12,000 tokens.

Naive data loaders pad each document to 8,192 tokens using a special <pad> token. As shown in Figure 4, if the average document length is 1,600 tokens, padding wastes over 80% of the sequence. Because self-attention and feed-forward networks execute compute on every token regardless of whether it is a real token or padding, naive padding wastes up to 80% of cluster FLOPs!

To eliminate this waste, pretraining pipelines employ sequence packing (also called sequence concatenation). Multiple documents are concatenated head-to-tail, separated by an End-Of-Sequence delimiter (<|endoftext|> or <|eot_id|>), until the sequence reaches exactly 8,192 tokens. Documents longer than 8,192 tokens are simply split across sequence boundaries.

Cross-document attention leakage

Concatenating independent documents into one 8,192-token sequence introduces a subtle theoretical challenge: tokens from Document B attend to tokens from Document A via causal attention. In practice, because pretraining tasks focus on next-token prediction, pretraining models tolerate cross-document attention with negligible degradation if separated by clear EOS delimiters. However, for strict isolation, two techniques eliminate leakage:

  • Block-diagonal attention masks: The attention mask is set to zero for all query-key pairs where the key belongs to an earlier document in the same packed sequence.
  • FlashAttention varlen (cu_seqlens): Modern attention kernels such as FlashAttention provide a variable-length API (flash_attn_varlen_func) [9]. The caller passes a flat tensor of concatenated tokens along with a cumulative_sequence_lengths tensor (cu_seqlens). The CUDA kernel computes attention independently within each document boundary, completely preventing cross-document attention without any padding overhead.

Step 8: Sharding into binary container formats

A fatal mistake in pretraining infrastructure is storing trillions of tokens as billions of loose text or JSONL files. An ext4 or Lustre filesystem collapses when managing hundreds of millions of small files due to inode exhaustion and metadata server locking. Furthermore, parsing text or JSON during training saturates CPU cores and introduces severe latency jitter.

Instead, pretraining data is serialized into sharded binary container files. Each shard is sized between 100 MB and 2 GB (containing roughly 25 million to 500 million tokens) [10]:

  • Megatron-LM binary format (.bin and .idx): Megatron-LM stores tokens as contiguous arrays of binary integers in a single .bin file, accompanied by an .idx index file containing 64-bit integer pointers to document byte offsets and document lengths. Workers access documents via direct memory mapping (mmap), allowing instantaneous random access with zero Python deserialization overhead.
  • MosaicML StreamingDataset (MDS format): MosaicML's open-source streaming library packages data into compressed binary chunks with index metadata, purpose-built for elastic streaming from cloud object storage (S3/GCS) [10].
  • Apache Arrow / Parquet: Columnar binary storage with built-in compression (Snappy or ZSTD) and schema validation, supported natively by Hugging Face Datasets and DataTrove [2].

Because Llama 3.1's vocabulary is 128,256, each token ID must be stored as a uint32 (4 bytes). Storing 1 trillion tokens in uint32 format yields exactly 4.0 TB of sharded binary files (e.g., 4,000 shards of 1 GB each).

Data Loading During Training: Avoiding Distributed Stalls

Worked consumption throughput for 256 H100 GPUs

How fast must the data loader feed our cluster? Let us calculate the exact consumption rate from our running scenario facts:

  • Cluster size: 256 NVIDIA H100 SXM 80 GB GPUs.
  • Dense BF16 compute per H100: 989 TFLOPS=989×1012 FLOPS.
  • Target MFU: 40%⟹0.40×989 TFLOPS=395.6 TFLOPS per GPU.
  • Total effective cluster compute: 256×395.6 TFLOPS=101,273.6 TFLOPS≈1.013×1017 FLOPS.
  • Model size: N=8.03×109 parameters.
  • Training FLOPs per token: In standard training without full activation recomputation, each token requires 6N FLOPs (2N forward, 4N backward): 6×8.03×109=48.18×109 FLOPs/token (If full activation checkpointing is active, this increases to 8N≈64.24 GFLOPs/token).

Data engineering tools: DataTrove, Ray, and Spark

Building and executing pipelines at the terabyte scale requires distributed processing frameworks:

  • Hugging Face DataTrove: A dedicated library for large-scale pretraining data curation [2]. DataTrove organizes pipelines into composable, chainable blocks (WarcReader, Trafilatura, GopherQualityFilter, LanguageFilter, MinhashDedup, TokensCounter). It provides executors for running locally on multi-core workstations or scaling across thousands of Slurm or Ray cluster tasks without modifying pipeline logic.
  • Ray Data: A general-purpose distributed computing framework that executes streaming data transformations across heterogeneous CPU and GPU clusters with dynamic memory management.
  • Apache Spark: The enterprise standard for distributed map-reduce data processing, widely used for heavy global shuffle operations such as massive URL deduplication and graph clustering.

import re
import trafilatura

def extract_and_filter(html_content: str) -> dict | None:
    """
    Extracts main article text from raw HTML using Trafilatura and applies
    standard Gopher quality heuristics (word counts, mean word length, symbol ratios).
    """
    # 1. Extract clean text, stripping navigation, ads, and footers
    text = trafilatura.extract(
        html_content,
        include_comments=False,
        include_tables=True,
        no_fallback=False,
    )
    if not text:
        return None

    # 2. Tokenize into words for heuristic checks
    words = re.findall(r"\b\w+\b", text)
    word_count = len(words)

    # Heuristic 1: Word count bounds (50 <= count <= 100,000)
    if not (50 <= word_count <= 100_000):
        return None

    # Heuristic 2: Mean word length (3.0 <= mean <= 10.0 chars)
    mean_word_len = sum(len(w) for w in words) / word_count
    if not (3.0 <= mean_word_len <= 10.0):
        return None

    # Heuristic 3: Symbol-to-word ratio (< 0.1)
    symbols = re.findall(r"[#\$%\^&\*\(\)_=\+\[\]\{\}\|\\<>/]", text)
    if len(symbols) / word_count > 0.10:
        return None

    # Heuristic 4: Common stopword presence (minimum 2 unique stopwords)
    common_stopwords = {"the", "be", "to", "of", "and", "a", "in", "that", "have", "it"}
    found_stopwords = {w.lower() for w in words if w.lower() in common_stopwords}
    if len(found_stopwords) < 2:
        return None

    return {"text": text, "word_count": word_count, "mean_word_len": mean_word_len}
import numpy as np

def pack_and_shard_tokens(
    tokenized_docs: list[list[int]],
    seq_len: int = 8192,
    eos_token_id: int = 128001,
) -> tuple[np.ndarray, list[list[int]]]:
    """
    Packs arbitrary document token streams into fixed-length sequences of shape [N, seq_len]
    using uint32 integers, tracking document boundaries (cu_seqlens) for FlashAttention varlen.
    """
    packed_sequences = []
    document_boundaries = []

    current_buffer = []
    current_boundaries = [0]

    for doc in tokenized_docs:
        # Append document tokens followed by EOS delimiter
        tokens = doc + [eos_token_id]
        doc_len = len(tokens)
        offset = 0

        while offset < doc_len:
            remaining_space = seq_len - len(current_buffer)
            slice_len = min(remaining_space, doc_len - offset)
            current_buffer.extend(tokens[offset : offset + slice_len])
            current_boundaries.append(len(current_buffer))
            offset += slice_len

            # When buffer reaches exact sequence length, flush to packed array
            if len(current_buffer) == seq_len:
                packed_sequences.append(current_buffer)
                document_boundaries.append(current_boundaries)
                current_buffer = []
                current_boundaries = [0]

    # Convert packed list to contiguous uint32 binary numpy array
    packed_array = np.array(packed_sequences, dtype=np.uint32)
    return packed_array, document_boundaries
import os
import numpy as np

class ShardedStreamReader:
    """
    Memory-mapped binary shard reader supporting deterministic resumption
    after training restarts without re-reading past shards.
    """
    def __init__(self, shard_paths: list[str], seq_len: int = 8192):
        self.shard_paths = shard_paths
        self.seq_len = seq_len
        self.current_shard_idx = 0
        self.current_seq_offset = 0
        self._mmap_current_shard()

    def _mmap_current_shard(self):
        path = self.shard_paths[self.current_shard_idx]
        file_bytes = os.path.getsize(path)
        num_tokens = file_bytes // 4  # 4 bytes per uint32 token
        self.num_sequences = num_tokens // self.seq_len
        # Memory-map the binary array directly from local NVMe storage
        self.data = np.memmap(path, dtype=np.uint32, mode="r", shape=(self.num_sequences, self.seq_len))

    def get_state(self) -> dict:
        """Returns exact resumption state to persist in training checkpoint."""
        return {
            "shard_idx": self.current_shard_idx,
            "seq_offset": self.current_seq_offset,
        }

    def load_state(self, state: dict):
        """Restores exact shard and sequence position after cluster restart."""
        self.current_shard_idx = state["shard_idx"]
        self.current_seq_offset = state["seq_offset"]
        self._mmap_current_shard()

    def next_sequence(self) -> np.ndarray:
        """Yields the next 8,192-token sequence without I/O stalls."""
        if self.current_seq_offset >= self.num_sequences:
            self.current_shard_idx = (self.current_shard_idx + 1) % len(self.shard_paths)
            self.current_seq_offset = 0
            self._mmap_current_shard()

        seq = self.data[self.current_seq_offset]
        self.current_seq_offset += 1
        return seq

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Loss masking across packed document boundaries: When concatenating documents, many teams mask the loss on the very first token of each document. The model cannot predict the opening token of an unrelated document from previous context, so computing loss on that transition penalizes the model unjustly.
  • WARC vs WET vs WAT in Common Crawl: While WET files provide pre-extracted plain text, they lose HTML layout signals (headers, lists, tables). In contrast, WAT files provide structural JSON metadata (links, server headers), and WARC preserves raw HTTP payloads, enabling custom, high-accuracy DOM extraction.
  • Synthetic data integration in pretraining: Frontier models (such as Llama 3.1 and Gemma 2) increasingly supplement web crawls with synthetic textbook explanations, rewritten web prose, and multi-turn QA generated by larger teacher models to increase token density.
  • Multi-epoch training on high-quality subsets: While training for more than 4 epochs on duplicate data causes severe memorization, repeating pristine subsets (such as Wikipedia or high-scoring FineWeb-Edu text) for 2 to 4 epochs improves downstream knowledge without degrading perplexity.
  • FastText vs transformer language identification: While lightweight transformer models (such as GlotLID) achieve higher accuracy on rare languages and dialect classification, fastText processes hundreds of megabytes per second per core, making it the only cost-effective choice for multi-terabyte web scale.
  • Double buffering and pinned memory in PyTorch: Passing pin_memory=True and non_blocking=True in PyTorch DataLoaders enables asynchronous host-to-device CUDA DMA copies over PCIe, completely hiding host tensor transfer time behind GPU tensor core computation.
  • Storage encryption and compliance scrubbing: Large-scale enterprise pipelines incorporate automated compliance filters that scrub copyrighted lyrics, medical records (HIPAA), and known vulnerability exploits before saving binary shards to permanent storage.

Summary

  • Pretraining datasets combine web crawls (Common Crawl), source code (The Stack), academic papers (arXiv, peS2o), books, and encyclopedias to build broad reasoning, coding, and factual recall.
  • Raw Common Crawl text requires eight sequential processing stages: HTML extraction via Trafilatura, fastText language ID, Gopher heuristic rules, deduplication, PII masking, tokenization, sequence packing, and binary sharding.
  • At 1 trillion tokens, clean UTF-8 text requires 4.0 TB of storage (~250M tokens per GB); sourcing this volume requires filtering 20 TB to 40 TB of raw crawl text, taking 3,000 to 5,000 CPU core-hours.
  • Because Llama 3.1's vocabulary is 128,256, token IDs exceed 16 bits and must be stored as uint32 arrays (4 bytes per token), totaling 4.0 TB of sharded binary files.
  • Sequence packing concatenates documents into fixed 8,192-token windows with EOS delimiters, eliminating up to 80% compute waste compared to naive document padding.
  • On 256 H100 GPUs at 40% MFU, the cluster consumes 2.10 million tokens per second (8,211 tokens/s per GPU). Local node NVMe prefetching prevents unbuffered remote I/O stalls that otherwise cascade across collective all-reduce barriers.
  • Saving (epoch, shard_idx, sequence_offset, worker_seed) in checkpoints enables deterministic data resumption without re-reading past shards after cluster restarts.

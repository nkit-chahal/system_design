Introduction

Llama 3.1 70B does not fit on one H100. Its BF16 weights take 131.4 GiB, and even its FP8 weights leave no room for a KV cache on an 80 GB card (Lesson 17, VRAM Budgeting). And even if a GPU were big enough, it would have to read all 141 GB of weights on every decode step, which caps a single stream at about 24 tokens per second.

Tensor parallelism (TP) solves both problems at once. It splits every weight matrix of every layer across several GPUs, so each GPU stores and reads only its share, and all of them work on the same token at the same time. The price is communication: after each half of every layer, the GPUs must add up their partial results over the interconnect. Figure 1 shows the idea.

On the left, one 80 GB H100 would need to hold all 80 layers, 141 GB of weights, and cannot. On the right, four GPUs each hold a quarter of every layer, about 35 GB each, and are joined by NVLink, over which two all-reduces per layer combine their partial results so every GPU works on the same token.

In this lesson, we see how Megatron-style tensor parallelism splits the attention and MLP blocks, count the bytes its all-reduces move, and work out why it lowers per-token latency with diminishing returns. We then cover the constraints on the TP size, compare TP with pipeline, data, and expert parallelism, and choose a layout for Llama 3.1 70B on an eight-GPU node.

Clarifying the Problem

Tensor parallelism comes up in interviews as a layout question. Here is a typical exchange between a candidate and an interviewer:

Candidate: Which model, and at what precision?
Interviewer: Llama 3.1 70B Instruct in BF16. The team is evaluating an FP8 checkpoint, but it is not approved yet.

Candidate: What hardware do we have?
Interviewer: One server with eight H100 SXM GPUs connected by NVLink. We may get a second server later, and procurement keeps offering cheaper servers whose GPUs talk only over PCIe.

Candidate: What does the traffic look like?
Interviewer: The same chat traffic as our 8B service: about 2,000 prompt tokens and 500 output tokens per request, 1,000 requests per minute on average and about 33 per second at the daily peak. We want as many concurrent users per server as possible.

Candidate: What latency do users need?
Interviewer: The same targets too: p95 time to first token of at most 500 ms, and p95 time per output token of at most 25 ms, which is at least 40 tokens per second per stream.

Candidate: Can we run several copies of the model behind a router?
Interviewer: Yes, the router can spread traffic across replicas (Lesson 25, Request Routing).

The question underneath is: how should we split one 70B model across eight GPUs: one replica with TP = 8, two with TP = 4, or four with TP = 2, and what does the communication cost? To answer it, we need to know exactly what TP splits and what it sends.

Why One GPU Is Not Enough

There are two separate reasons, and they lead to different fixes.

Memory. The weights of Llama 3.1 70B take 141.1 GB in BF16, or 131.4 GiB, more than the 79.6 GiB an H100 offers. In FP8 they take 67.7 GiB, which fits, but weights plus runtime memory exceed the engine's budget and leave nothing for the KV cache. Any layout that spreads the weights over several GPUs fixes this, including pipeline parallelism, which gives each GPU a block of whole layers.

Latency. A decode step must read every weight once, so its time is bounded below by the bytes read divided by memory bandwidth (Lesson 2, Prefill vs Decode) [1]. Suppose a single GPU had enough memory: reading 141 GB at 3.35 TB/s takes 42 ms per step, at most 24 tokens per second, far above our 25 ms per-token target before a single cached token is read. Only a split inside each layer fixes this, because a token passes through the layers one after another. If each of N GPUs holds 1/N of every layer, all of them read their shares at the same time, and a step at TP = 8 needs only 17.6 GB per GPU, about 5.3 ms. That is what tensor parallelism does.

How Tensor Parallelism Splits a Layer

Column-parallel and row-parallel matrix multiplies

The scheme used by every major serving engine comes from Megatron-LM [2]. It rests on two ways of splitting a matrix multiply. If a weight matrix A is split by columns across two GPUs, each GPU computes its own columns of the output from the same input, with no communication:

X A = X \begin{bmatrix} A_1 & A_2 \end{bmatrix} = \begin{bmatrix} X A_1 & X A_2 \end{bmatrix}

If the next matrix B is split by rows, each GPU multiplies its slice of the input by its rows of B and gets a full-size partial result. The true output is the sum of the partials, so the GPUs exchange them in an all-reduce, a collective operation that leaves the sum on every GPU:

Y B = \begin{bmatrix} Y_1 & Y_2 \end{bmatrix} \begin{bmatrix} B_1 \\ B_2 \end{bmatrix} = Y_1 B_1 + Y_2 B_2

The trick is to pair them. A column-parallel multiply produces exactly the column slice that the following row-parallel multiply needs, so the pair costs a single all-reduce at the end. Any element-wise operation between them runs locally, because each GPU holds complete columns.

The MLP

Llama's MLP computes \text{down}(\text{SiLU}(x W_{\text{gate}}) \odot x W_{\text{up}}), with an intermediate width of 28,672 for the 70B model [3]. The gate and up projections are split by columns, so with TP = 2 each GPU holds 14,336 of the 28,672 columns. SiLU and the element-wise product act on each GPU's own columns. The down projection is split by rows to match, which leaves each GPU with a partial output of full width, and one all-reduce adds them up. Figure 2 shows the pattern.

Two GPU lanes. Each receives the same input X. GPU 0 holds the left half of the gate and up columns and the top half of the down rows; GPU 1 holds the other halves. Each computes SiLU of gate times up on its own 14,336 columns, multiplies by its half of the down rows to get a partial result, and an all-reduce adds the two partials into Z.

Attention heads across GPUs

Attention splits even more naturally, because its heads are independent. The query, key, and value projections are column-parallel by head: with TP = 4, each GPU gets 16 of the 64 query heads and 2 of the 8 KV heads. Because Llama groups 8 query heads around each KV head, a GPU's 16 query heads need exactly its own 2 KV heads, so each GPU computes attention for its heads without talking to the others. The output projection is row-parallel: each GPU holds the 2,048 rows that match its heads (16 × 128) and produces a partial result, and a second all-reduce sums them (Figure 3).

Four GPU lanes receive the same input x. Each multiplies it by its slice of the QKV weights to get 16 query heads and 2 KV heads, runs attention against its own slice of the KV cache (heads 0–1, 2–3, 4–5, 6–7), and multiplies the result by its 2,048 rows of the output projection to get a partial output. An all-reduce sums the four partials into y, which every GPU receives.

The KV cache is split the same way. Each GPU stores and reads only its own KV heads, which is why Lesson 17 divided the per-token cache cost by the TP size: 320 KiB per token for the whole model becomes 80 KiB per GPU at TP = 4. The embedding and output layers are split across the vocabulary and add one more collective per forward pass, which is small next to the per-layer ones.

Two all-reduces per layer, and what they cost

Every transformer layer therefore runs two all-reduces in the forward pass, one after attention and one after the MLP [2]. They are synchronization points: no GPU can start the MLP until every GPU has finished attention and the sum has arrived, so the slowest GPU sets the pace (Figure 4).

A timeline with four GPU lanes. Each lane computes attention for its own heads, waits briefly for the slowest GPU, joins all-reduce 1, computes its MLP columns, waits again, joins all-reduce 2, and moves on to the next layer. A box notes that each all-reduce adds up 16 KiB per token, that a ring all-reduce makes every GPU send and receive 2(N − 1)/N of that, and that 80 layers mean 160 all-reduces per forward pass.

Each all-reduce sums a tensor of T \times h values, where T is the number of tokens in the step and h the hidden size. In the common ring algorithm, every GPU sends and receives 2(N-1)/N times that tensor [4]. With L layers and b bytes per value, the traffic per GPU per forward pass is:

\text{bytes per GPU} = 2L \times \frac{2(N-1)}{N} \times T \times h \times b

For Llama 3.1 70B, h = 8{,}192 and activations are BF16, so each all-reduce carries 16 KiB per token, and 80 layers mean 160 all-reduces per forward pass. To turn bytes into time we need the link speed and a fixed cost per operation:

t_{\text{comm}} \approx 2L \times \left( \alpha + \frac{2(N-1)}{N} \cdot \frac{T h b}{B_{\text{link}}} \right)

An H100 SXM has 900 GB/s of NVLink bandwidth, which counts both directions, so B_{\text{link}} is 450 GB/s each way. A PCIe Gen5 x16 slot offers 128 GB/s in total, 64 GB/s each way [5]. For the fixed cost \alpha, we assume 10 µs per all-reduce on NVLink; it depends on the GPUs, the NCCL version, and the engine's all-reduce kernels, so measure it before relying on it. Two regimes appear. A decode step for a few requests moves very little data, so its cost is almost entirely the fixed 1.6 ms. Large batches and prefills move gigabytes, so their cost is bandwidth, and that is where NVLink and PCIe part ways.

Why TP Lowers Latency, With Diminishing Returns

Decode

Putting the pieces together, the lower bound on a decode step at TP = N is the time to read this GPU's share of the weights and cache, plus the all-reduces:

t_{\text{step}}(N) \approx \frac{W + \text{KV}}{N \times \text{HBM bandwidth}} + t_{\text{comm}}(N)

The first term shrinks as 1/N; the communication term does not. For a single request in BF16, the weight read takes 21.1 ms at TP = 2, 10.5 ms at TP = 4, and 5.3 ms at TP = 8, while communication stays near 1.6 ms. Figure 5 shows the result: 44, 82, and 145 tokens per second. Quadrupling the GPUs from two to eight buys 3.3 times the speed, and communication grows from 7% to 23% of the step.

A stacked bar chart. At TP = 2 the step is 21.1 ms of weight reading plus 1.6 ms of all-reduces, 22.7 ms or 44 tokens per second. At TP = 4 it is 10.5 plus 1.6, 12.1 ms or 82 tokens per second. At TP = 8 it is 5.3 plus 1.6, 6.9 ms or 145 tokens per second. Communication is 7, 13, and 23 percent of the step. The values are arithmetic lower bounds.

Real scaling is worse than this bound for two more reasons. Each GPU's matrix multiplies get thinner as N grows (at TP = 8, the QKV slice is 8,192 × 1,280), and thin multiplies use the GPU less efficiently. And fixed costs per step, such as sampling, scheduling, and kernel launches, do not shrink with N at all (Lesson 19, GPU Utilization). Quantization makes the effect stronger: FP8 halves the weight bytes but not the all-reduce traffic, because activations stay in BF16, so at TP = 8 communication grows to about 37% of a single-request step.

Under load, the bandwidth term grows too. With 526 requests in the batch, the all-reduces move 2.25 GiB per GPU per step (Table 1), about 5.4 ms on NVLink on top of the 1.6 ms fixed cost.

Prefill and the interconnect

Prefill processes the whole prompt at once, so its all-reduces carry thousands of tokens. For a 2,000-token prompt, Figure 6 compares the transfer time with the compute time at the H100's peak of 989 dense BF16 TFLOPS. The prompt needs 2 \times 70.55 \times 10^9 \times 2{,}000 \approx 282 TFLOP, about 36 ms per GPU at TP = 8 even at peak.

Grouped horizontal bars for TP = 2, 4, and 8. Compute at peak takes 143, 71, and 36 ms. The all-reduces take 11.7, 17.5, and 20.4 ms over NVLink, but 82, 123, and 143 ms over PCIe Gen5. Over PCIe, communication exceeds compute at TP = 4 and TP = 8.

Over NVLink, the all-reduces cost a fraction of the compute, and engines can hide part of them behind it. Over PCIe they take 82 to 143 ms, longer than the compute itself at TP = 4 and 8: the GPUs spend more time exchanging partial sums than doing math. This is why tensor parallelism belongs on NVLink-connected GPUs, and why vLLM's documentation suggests pipeline parallelism instead when GPUs lack NVLink [6].

Beyond one node

TP = 16 across two servers would halve the weight read again, from 5.3 to 2.6 ms. But each of the 160 all-reduces would then cross the network. A 400 Gb/s network adapter per GPU, common in H100 clusters, moves 50 GB/s each way, a ninth of NVLink, with a higher fixed cost per message, so communication would grow by more than the 2.6 ms saved. TP above 8 also stops shrinking the KV cache, as the next section shows. The rule is to keep the TP group inside one NVLink domain. That domain is eight GPUs in an H100 server; rack-scale systems such as the GB200 NVL72 extend it to 72 GPUs [7].

Constraints on the TP Size

Because TP splits heads, the head counts decide which sizes are legal. Figure 7 shows where Llama 3.1 70B's KV heads end up.

At TP = 4, each GPU holds 2 KV heads, 80 KiB of cache per token per GPU. At TP = 8, each holds 1, 40 KiB per GPU. At TP = 16, spread over two nodes, each GPU still holds one KV head, so every head is copied to two GPUs and the replica stores 640 KiB per token in all. At TP = 3, the 64 query heads cannot be split evenly and vLLM refuses to start.
  • Query heads must divide evenly. vLLM checks that the number of attention heads is divisible by the TP size and stops with "Total number of attention heads (64) must be divisible by tensor parallel size (3)" otherwise [8]. For Llama 3.1 70B, that allows 1, 2, 4, 8, 16, 32, or 64.
  • KV heads split up to TP = 8, then replicate. Up to the number of KV heads, each GPU gets 8 ÷ TP of them. Beyond it, vLLM gives each GPU one KV head and copies each head to TP ÷ 8 GPUs, which requires TP to be a multiple of 8 [9]; SGLang does the same [10]. Replication means the cache per GPU stops shrinking at 40 KiB per token, and at TP = 16 the replica stores every token's cache twice.
  • The other dimensions must divide too. The MLP width of 28,672 splits cleanly up to 16 ways (1,792 columns each). Engines pad the vocabulary, so it rarely matters.
  • The NVLink domain sets a practical ceiling. With eight GPUs per H100 server, TP = 8 is the largest group that stays on NVLink.
When asked "why not TP = 16?", give three reasons: every all-reduce leaves NVLink, the KV heads start to replicate, and a replica now fails when either server fails. Then propose a second TP = 8 replica instead.

Tensor, Pipeline, Data, and Expert Parallelism

Tensor parallelism is one of four ways to spread a model over GPUs, and production layouts often combine them. Figure 8 shows the four side by side.

Four panels of four GPUs each. Tensor parallel: every layer bar spans all four GPUs, split four ways, with two all-reduces per layer. Pipeline parallel: each GPU holds a block of 20 consecutive layers and hands its output to the next. Data parallel: each GPU holds a full copy of all layers and nothing is exchanged. Expert parallel: each GPU holds its own attention and two of eight experts, and tokens travel all-to-all between GPUs.
  • Pipeline parallelism (PP) splits the model into stages of consecutive layers [11]. Between stages it sends one hidden-state tensor, 16 KiB per token, instead of 160 all-reduces, so it tolerates slow links and uneven GPU counts. But a token still passes through every stage in order, so a step reads all the weights in sequence: with PP = 2 in BF16, about 42 ms, no faster than one hypothetical big GPU. Throughput comes from keeping every stage busy with a different batch [12].
  • Data parallelism runs independent replicas. There is no communication between them, so capacity and throughput scale linearly, but every replica needs the whole model and has its own KV cache, which makes routing matter for prefix-cache hits (Lesson 25, Request Routing). vLLM can run replicas behind one endpoint with --data-parallel-size; note that --max-num-seqs then applies to each replica [13].
  • Expert parallelism (EP) is for mixture-of-experts models. Each GPU holds a subset of the experts, and every MoE layer sends each token to the GPUs holding its chosen experts and back, two all-to-all exchanges per layer [14]. In vLLM, --enable-expert-parallel forms an expert group of size TP × DP [15]. Lesson 35, Mixture-of-Experts Serving, covers it in depth.
  • Context parallelism splits one very long sequence across GPUs and is covered in Lesson 36, Long-Context Serving.

The full-cache column holds a surprise: every layout lands near 21 ms per step before communication. A full GPU reads about its whole memory on every step (Lesson 17), however the model is split, so the layouts differ only in communication: about 7 ms per step for TP = 8 with 526 requests in the batch, 3 ms for TP = 4 with 177. What larger TP buys at full load is capacity: one TP = 8 replica stores the weights once, while two TP = 4 replicas store them twice, and those 131 GiB go to the KV cache instead.

The last column matters because real steps are slower than these bounds. Lesson 19 puts an H100 serving the 8B model at about 21 ms per step with 53 concurrent streams, while the bandwidth bound for that load is about 10 ms, so real steps took roughly twice the bound. If the 70B model behaves the same way, meeting a 25 ms p95 needs a bound near 12.5 ms. That is where the layouts separate: a TP = 4 replica in BF16 spends 10.5 ms reading its weights and 1.6 ms on all-reduces before it reads any cache, so it has room for almost no users, while TP = 8 still carries about 138.

Which TP size fits our deployment?

Our targets are a p95 time per output token of 25 ms, a p95 time to first token of 500 ms, and as many users per server as possible, in BF16 for now. Four TP = 2 replicas are out: in BF16 they leave no room for a cache. Of the other two, TP = 8 wins on every count. It holds the most chats in memory (526 against 354), keeps the most under the 25 ms bound (444 against 354), and is the only BF16 layout that still serves a useful number of users if real steps take twice the bound (138 against 10). Its first token is fast too: a 2,000-token prefill needs about 36 ms of compute at peak plus 22 ms of all-reduces, well inside 500 ms even after some queueing (Lesson 4, Time to First Token).

We choose one TP = 8 replica in BF16 and set --max-num-seqs from measurement rather than from memory: Lesson 21's lab measures inter-token latency under load, and we cap concurrency where p95 reaches 25 ms, somewhere between the 138 and 444 bounds above. When the FP8 checkpoint passes our evaluation set, we keep TP = 8, which then carries the most users under the target (200 at the 12.5 ms bound, against 156 for two TP = 4 replicas). Failure isolation comes from the fleet rather than from splitting one server: at the daily peak of 33 requests per second, each lasting about 13 s (0.5 s to the first token plus 500 tokens at 25 ms), about 430 streams run at once (Little's law), so we will run several servers anyway, and losing one costs only part of the capacity (Lesson 40, Reliability and Rollouts). Lesson 20, Cost per Million Tokens, and Lesson 21's lab turn these numbers into a fleet size. New servers become more TP = 8 replicas, never halves of a TP = 16 group.

Multi-node considerations

Some models do not fit in one server even with TP = 8. Llama 3.1 405B, for example, needs about 810 GB in BF16, more than eight 80 GB GPUs hold. The usual layout is then TP inside each server and PP across servers: vLLM's documentation recommends setting the TP size to the GPUs per node and the PP size to the number of nodes [6], because the stage boundary sends only one hidden-state tensor per step across the slower network. A few practical points follow:

  • Every node needs an identical environment and the model at the same path; containers make that easy [6].
  • Use a fast fabric such as InfiniBand with GPUDirect RDMA, and check that NCCL actually uses it, for example with NCCL_IB_HCA set as the vLLM docs describe [6].
  • vLLM can launch across nodes with Ray, or with its own multiprocessing backend using --nnodes, --node-rank, --master-addr, and --headless on the workers [6]. SGLang uses --nnodes, --node-rank, and --dist-init-addr [16].
  • A multi-node replica fails when any node fails and loads more slowly, so prefer single-node replicas whenever the model fits.

Llama 3.1 405B's size comes from its 405 billion parameters at 2 bytes each [3]. In FP8 it is about 405 GB, which fits in one eight-GPU H100 server (640 GB) with room left for the cache, another case where quantization changes the layout rather than just the budget.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Sequence parallelism replaces each all-reduce with a reduce-scatter and an all-gather and splits the layer norms along the sequence, moving the same bytes while storing less activation memory per GPU [18].
  • Engines can hide part of the all-reduce time by splitting a batch in two and computing one half while the other half communicates.
  • vLLM ships its own all-reduce kernel for small messages inside a node, where the fixed cost dominates; --disable-custom-all-reduce falls back to NCCL [19].
  • Low-bit weights shrink the weight reads but not the BF16 activations that the all-reduces carry, so quantized models spend a larger share of each step communicating.
  • Disaggregated serving can give prefill and decode different parallel layouts, for example a larger TP for prefill to cut time to first token (Lesson 34, Disaggregated Prefill and Decode).
  • Rack-scale NVLink domains such as GB200 NVL72 make TP and expert parallelism beyond eight GPUs practical, which changes the "keep TP inside one server" rule [7].

Summary

Mind map summarizing the tensor parallelism lesson: why one GPU is not enough, how layers are split, the cost of the all-reduces, the constraints on TP size, and how to choose a layout.
  • Tensor parallelism splits every weight matrix across GPUs, so each GPU stores and reads only its share and per-token latency falls. It is the only split that speeds up a single stream.
  • Megatron-style TP pairs a column-parallel multiply with a row-parallel one: QKV by heads then the output projection, and gate and up by columns then down by rows. That costs two all-reduces per layer, 160 per forward pass for Llama 3.1 70B.
  • Each all-reduce carries 16 KiB per token for the 70B model, and a ring makes every GPU send 2(N − 1)/N of it. A 2,000-token prefill at TP = 8 moves about 8.5 GiB per GPU: 20 ms over NVLink, 143 ms over PCIe.
  • For one request in BF16, a decode step drops from 22.7 ms at TP = 2 to 6.9 ms at TP = 8: four times the GPUs give 3.3 times the speed, because the fixed communication cost does not shrink.
  • The TP size must divide the 64 query heads; above 8 the KV heads replicate, and beyond one server every all-reduce crosses the network. Keep TP inside the NVLink domain.
  • Pipeline parallelism suits slow links and spanning servers, replicas add throughput once the model fits, and expert parallelism serves MoE models.
  • For Llama 3.1 70B on eight H100s under a 25 ms per-token target, one TP = 8 replica is the best layout in BF16 and in FP8: it fits the most chats in memory and keeps the most of them under the latency target.

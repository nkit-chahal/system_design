Introduction

"Which serving engine is faster?" is one of the most common questions in inference engineering, and one of the easiest to answer badly. Two engines serving the "same" model can differ in precision, cache size, prefix caching, sampling defaults, and the prompts the benchmark tool happens to generate. Any one of these can move the result by more than the engines themselves do. A fair benchmark is mostly a list of things held equal.

In this lab we compare vLLM and SGLang, the engines of Lesson 9, vLLM, and Lesson 10, SGLang, serving Llama 3.1 8B Instruct to 50 concurrent users, meaning 50 requests in flight at every moment. TensorRT-LLM (Lesson 11, TensorRT-LLM) is an optional third engine. We use each engine's own load generator, check that each can drive the other engine's server, and repeat every run so that we can tell a real difference from noise. Figure 1 shows the setup.

Two load generators, vllm bench serve as the primary and sglang.bench_serving as a cross-check, send 50 concurrent requests over localhost to either vLLM on port 8000 or SGLang on port 30000. Both engines read one local copy of the model, with the same weights, tokenizer and chat template, and only one of them runs on the H100 at a time. Results land as JSON files, and summarize.py turns them into a table of median and range over three runs per engine.

In this lab, we write a fairness checklist, launch each engine with matching settings, run a fixed workload three times per engine, cross-check with a second load generator, and turn the results into a table. Then we discuss how to read differences, when they are noise, and which workloads would favor which engine.

Step 1: Write the Fairness Checklist

Write the checklist before launching anything, and keep it next to the results; a benchmark without its settings cannot be reproduced or trusted. Figure 2 groups the items into four layers.

Four rows. Model: same weight files from one local copy, same dtype BF16, same tokenizer and chat template, same 8,192-token max context. Engine settings: the same explicit memory fraction of 0.90 with KV capacity checked in both logs, prefix caching off on both, batch limits above 50, same GPU with nothing else running. Workload: same prompts from a fixed seed, exactly 2,000 tokens in and 500 out, temperature 0 and ignore_eos, an untimed warmup run first. Measurement: same load generator and version, same network path over localhost, 50 requests in flight, three or more runs per engine, versions recorded.

Two rows deserve more attention, because the flag names suggest an equivalence that does not exist. The first is memory. vLLM's --gpu-memory-utilization is the fraction of the whole GPU that the engine may use for everything: weights, activations, CUDA graphs, and KV cache [2]. SGLang's --mem-fraction-static is the fraction used for "static allocation (model weights and KV cache memory pool)", with the rest left for activations and graphs [5]. We set both explicitly to 0.90, the value Lesson 3, KV Cache, uses, because the defaults differ: recent vLLM releases default to 0.92, and SGLang computes its own value from the GPU's memory. Even at the same number, SGLang's cache comes out somewhat larger, because its fraction leaves activations out. Figure 3 shows the approximate split.

Two bars of the same 79.6 GiB GPU. vLLM at 0.90: 15 GiB of weights, about 4.6 GiB of activations and graphs, about 52 GiB of KV cache, and 10% unused, for a total budget of about 71.6 GiB. SGLang at 0.90: 15 GiB of weights and a KV pool of about 56.7 GiB, together about 71.6 GiB of static memory, with about 8 GiB left for activations and graphs. A note says to compare the KV capacity each engine reports, not just the flag values.

The second is the length of the generated prompts, which we return to in Step 5. Notice also what the checklist leaves alone: scheduler settings such as chunked-prefill size and batch limits stay at each engine's defaults. They are part of what we are comparing, and the write-up should say so.

Step 3: Launch Each Engine and Read Its Capacity

Run one engine at a time on the GPU. Each tab is run from that engine's own environment; SGLang's installation guide recommends uv with --prerelease=allow [10]. Stop one server before starting the next. Both servers answer to the model name llama31-8b, so the load generator's command line is identical except for the URL.

uv venv venv-vllm --python 3.12 --seed && source venv-vllm/bin/activate uv pip install vllm --torch-backend=auto python -c "import vllm; print(vllm.__version__)" # record it vllm serve /models/llama31-8b \ --served-model-name llama31-8b \ --dtype bfloat16 \ --max-model-len 8192 \ --gpu-memory-utilization 0.90 \ --no-enable-prefix-caching \ --port 8000 2>&1 | tee vllm.log # Second terminal: grep -E "Model loading took|KV cache size" vllm.log curl -s http://localhost:8000/health && echo ready uv venv venv-sglang --python 3.12 && source venv-sglang/bin/activate uv pip install --prerelease=allow sglang python -c "import sglang; print(sglang.__version__)" # record it python -m sglang.launch_server \ --model-path /models/llama31-8b \ --served-model-name llama31-8b \ --dtype bfloat16 \ --context-length 8192 \ --mem-fraction-static 0.90 \ --disable-radix-cache \ --port 30000 2>&1 | tee sglang.log # Second terminal: grep -E "Load weight end|KV Cache is allocated" sglang.log curl -s http://localhost:30000/health && echo ready # From a TensorRT-LLM environment; see its installation guide for the container or wheel. trtllm-serve /models/llama31-8b \ --host 127.0.0.1 --port 8001 \ --max_seq_len 8192 \ --kv_cache_free_gpu_memory_fraction 0.80 # Second terminal: find the model id it serves, then pass it to the benchmark. curl -s http://localhost:8001/v1/models

What you should see. vLLM logs Model loading took … GiB memory and GPU KV cache size: … tokens; SGLang logs Load weight end. … mem usage=… GB and KV Cache is allocated. … #tokens: …. Both weight figures should be about 15 GiB. Write down both token capacities. Expect about 426,000 tokens for vLLM (Lesson 3, KV Cache) and about 464,000 for SGLang (56.7 GiB ÷ 128 KiB), roughly 9% more. Both are far above what this workload needs, 50 × 2,500 = 125,000 tokens, so neither engine will preempt and the difference does not touch the result. If your workload does fill the cache, at higher concurrency or with long contexts, lower SGLang's fraction until the logged capacities match and say so in the write-up; otherwise part of what you measure is preemption, not the engine. The TensorRT-LLM flag is a third convention again: it is a fraction of the memory left free after weights and buffers are allocated [6].

SGLang's own entry point, sglang serve, is equivalent to python -m sglang.launch_server in recent releases; either works.

Step 4: Run the Benchmark at 50 Concurrent Users

The primary load generator is vllm bench serve [3]. It talks to any OpenAI-compatible completions endpoint, so it drives SGLang and TensorRT-LLM as easily as vLLM: --backend vllm selects the request format (a streaming /v1/completions call), and --base-url selects the server. The script below runs one untimed warmup of 100 prompts and then three timed runs of 500 prompts, each with exactly 50 requests in flight. Run it from venv A while the engine under test is serving.

#!/usr/bin/env bash # bench_engine.sh ENGINE URL [FIRST_RUN]: one untimed warmup, then three timed runs # against whichever engine is serving at URL. Run it from the vLLM environment. # ./bench_engine.sh vllm http://localhost:8000 # ./bench_engine.sh sglang http://localhost:30000 # ./bench_engine.sh vllm http://localhost:8000 4 # session 2: runs 4-6 set -euo pipefail ENGINE=$1 URL=$2 FIRST=${3:-1} MODEL_DIR=/models/llama31-8b # tokenizer used to build the prompts SERVED=${SERVED:-llama31-8b} # model name the server answers to mkdir -p results COMMON=(--backend vllm --base-url "$URL" --model "$MODEL_DIR" --served-model-name "$SERVED" --dataset-name random --random-input-len 2000 --random-output-len 500 --max-concurrency 50 --seed 0 --temperature 0 --ignore-eos) # Untimed warmup: first-request compilation, allocator growth, cold caches. vllm bench serve "${COMMON[@]}" --num-prompts 100 for i in $(seq "$FIRST" $((FIRST + 2))); do vllm bench serve "${COMMON[@]}" --num-prompts 500 \ --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,95,99 \ --save-result --result-dir results --result-filename "${ENGINE}-run${i}.json" \ --metadata engine="$ENGINE" run="$i" sleep 15 done chmod +x bench_engine.sh ./bench_engine.sh vllm http://localhost:8000 # while vLLM is serving # stop vLLM, start SGLang, then: ./bench_engine.sh sglang http://localhost:30000 # optional, with TensorRT-LLM serving: SERVED="" ./bench_engine.sh trtllm http://localhost:8001

What you should see. For each timed run, a Serving Benchmark Result block with Successful requests: 500, Failed requests: 0, Maximum request concurrency: 50, request and output token throughput, and mean, median, P50, P95, and P99 lines for TTFT, TPOT, ITL, and E2EL. Three JSON files per engine appear in results/. A run cannot be faster than the bandwidth floor: with 50 users and an average context of 2,250 tokens, each decode step reads 16.06 GB of weights plus 14.75 GB of cache, at least 9.2 ms on an H100, so 500 output tokens take at least 4.6 s and ten waves of 50 requests at least 46 s. Expect a minute or two per run.

Every request carries a 2,000-token prompt and generates exactly 500 tokens, because of how the random dataset is defined. In vllm bench serve, --random-range-ratio defaults to 0, which gives every request exactly the requested lengths, and the tool switches on ignore_eos by itself for this dataset. We pass --ignore-eos and --temperature 0 anyway, so that the command documents its own assumptions; recent versions no longer default to greedy sampling.

Step 5: Cross-Check with SGLang's Load Generator

A load generator can favor the engine it was written for, if only through defaults. Repeating the comparison with SGLang's tool [4] tells us whether the ranking depends on the client. python -m sglang.bench_serving also accepts --backend vllm, which in this tool means the same OpenAI completions request format; its sglang-oai backend sends identical requests. Run this from venv B against each engine in turn.

ENGINE=vllm; URL=http://localhost:8000 # then: ENGINE=sglang; URL=http://localhost:30000 python -m sglang.bench_serving \ --backend vllm --base-url "$URL" \ --model /models/llama31-8b --served-model-name llama31-8b \ --dataset-name random \ --random-input-len 2000 --random-output-len 500 --random-range-ratio 1 \ --num-prompts 500 --max-concurrency 50 \ --warmup-requests 10 --seed 1 \ --output-file "results/sgbench-${ENGINE}.jsonl"

What you should see. A Serving Benchmark Result block with Backend, Successful requests, Output token throughput (tok/s), a Concurrency line close to 50, and mean, median, P90, P95, and P99 lines for E2E latency, TTFT, TPOT, and ITL. Each run appends one JSON line to the output file. Recent releases also print a warning that the module has moved to sglang.benchmark.serving; the old name still works.

Note --random-range-ratio 1. The two tools share the flag name but not its meaning. vLLM's tool draws each length from [n × (1 − r), n × (1 + r)], so 0 means "exactly n". SGLang's tool draws from [max(n × r, 1), n], so its default of 0 means "uniform between 1 and n", and only 1 means "exactly n" (Figure 4). With both defaults, SGLang's tool sends about half the work of vLLM's for what looks like the same command, and any comparison across the two tools would be meaningless.

Three small histograms of input length from 0 to 2,000 tokens. vllm bench serve with --random-range-ratio 0, the default, puts every prompt at 2,000 tokens. sglang.bench_serving with the same default spreads prompts uniformly from 1 to 2,000, with a mean of about 1,000. sglang.bench_serving with --random-range-ratio 1 puts every prompt at 2,000 tokens.

Even with matching lengths, the two tools generate different text: vLLM's random dataset builds prompts from synthetic token sequences, while SGLang's (for the random dataset) cuts and repeats ShareGPT conversations, which it downloads on first use. SGLang's tool also sets temperature 0 and ignore_eos on every request by default. Compare engines within one tool's results, never a vLLM-tool number against an SGLang-tool number.

Reading the Results

Is the difference real?

Every number in Table 3 is a sample. Run the same command three times on the same engine and you will get three slightly different throughputs, because of GPU clock and temperature changes, the order in which requests happen to finish, background processes, and timing-dependent scheduling decisions inside the engine. The question is never "which median is bigger" but "is the gap bigger than the run-to-run spread", a point the scientific benchmarking literature makes at length [8]. Figure 5 shows the two cases.

Two illustrative bar charts for Engine A and Engine B, each bar the median of three runs with a whisker from minimum to maximum and dots for individual runs. Left, output tokens per second: B's median is 3% higher but the ranges overlap, so the result is a tie. Right, p99 TTFT: the gap is far larger than the spread and the ranges are separated, so the difference is real. A note says to confirm separated results in a second session with the order reversed.

Use three rules. First, a difference counts only when the ranges do not overlap, which is what summarize.py checks. Second, it must survive a second session with the engine order reversed, as in Figure 6, so that slow drift cannot always favor the engine that ran first. Third, tail metrics need more data than medians: the p99 TTFT of a 500-request run is set by its five slowest requests, so it moves far more between runs than p50 does. If p99 is the metric you care about, run more prompts or more repetitions. p99 ITL is steadier, because it pools roughly 250,000 token gaps per run.

Two sessions on a timeline. Session 1 starts vLLM, runs an untimed warmup, runs 1 to 3, stops, then does the same for SGLang. Session 2 reverses the order: SGLang first with runs 4 to 6, then vLLM with runs 4 to 6. A legend marks start and stop, the 100-prompt warmup, and the 500-prompt timed runs.

Then ask whether a real difference changes a decision. A 3% throughput gap changes a 100-GPU fleet by about three GPUs. A latency gap can matter far more, because 50 users is close to the edge: Lesson 19, GPU Utilization, estimates that one H100 carries about 53 concurrent streams of this model at the course's targets of p95 TTFT ≤ 500 ms and p95 TPOT ≤ 25 ms. At this load, an engine that keeps p95 TPOT at 22 ms and one that reaches 27 ms are on opposite sides of the target, and that decides how many GPUs the fleet needs (Lesson 21, Lab - GPUs for 1,000 Requests per Minute Under a 2s SLA).

Why the engines differ

Both engines implement continuous batching [9] over a paged KV cache [1] (Lesson 7, Continuous Batching; Lesson 8, PagedAttention), so the differences come from scheduling policy and kernels rather than from the basic design. The metrics often split. One engine may admit new prompts more eagerly, giving lower TTFT but more prefill work mixed into each decode step and so a higher p99 ITL; the other may protect streaming smoothness at the cost of waiting time. Neither is simply faster. Which one wins depends on your latency targets, which is why a single "tokens per second" headline is not a benchmark result. Differences in attention kernels, CUDA graph coverage, and CPU-side scheduling overhead also show up most at moderate batch sizes like 50, where the GPU is busy but not saturated (Lesson 33, GPU Architecture and Attention Kernels).

Which engine fits our workload?

This lab's workload is deliberately plain: random prompts with no shared prefix, no constrained output, fixed lengths, one model. It measures continuous batching and kernel efficiency and nothing else. Real workloads add features that each engine was designed around, so before choosing, rerun the comparison with the features your traffic actually has. The common ones are:

  • Long shared prefixes (system prompts, multi-turn chat, agents). Turn prefix caching back on in both engines and use a shared-prefix dataset. SGLang's RadixAttention was built around this pattern [7], and vLLM's automatic prefix caching is on by default (Lesson 10, SGLang; Lesson 24, Prefix Caching).
  • Constrained output (JSON schemas, regular expressions, tool calls). Measure throughput and latency with a schema attached; the SGLang paper introduced a compressed finite-state machine for faster constrained decoding [7] (Lesson 38, Structured Output and Tool Calling).
  • Many fine-tuned variants of one base model. Test multi-LoRA serving with your adapter count and traffic mix (Lesson 37, Multi-LoRA and Multi-Tenant Serving).
  • An NVIDIA-only fleet chasing peak throughput. Add TensorRT-LLM as a third engine, with FP8 weights on all three (Lesson 11, TensorRT-LLM; Lesson 13, Quantization - FP8, INT8 and 4-bit).
  • Mixed hardware or the newest open models. Check model and hardware support before speed; vLLM supports NVIDIA, AMD, Intel, and TPU backends (Lesson 9, vLLM).
  • Long documents of 32K tokens and more. Rerun with long prompts, where cache capacity and prefill scheduling start to dominate (Lesson 36, Long-Context Serving).
When asked to compare engines, list what you would hold equal before naming a winner: weights and precision, KV cache capacity, prefix caching, sampling and output lengths, the client, and repeated runs. Then say which workload features of the actual product would change the answer.

Common Pitfalls

  • Relying on defaults, or on flag names. The memory defaults differ between engines, so set the fraction explicitly on both. Even then, --gpu-memory-utilization 0.90 and --mem-fraction-static 0.90 give different cache sizes; compare the token capacities in the logs.
  • Prefix caching on one side only. Both engines enable it by default. Leaving it on is fine, but on both, and with a workload where it matters.
  • Different prompt lengths. SGLang's tool with default flags sends prompts that average half the requested length. Check total input tokens in each result before comparing.
  • Sampling defaults. vLLM's server applies the model's generation_config.json by default, and recent vllm bench serve versions no longer force greedy sampling. Pass temperature 0 explicitly so both engines decode the same way.
  • Measuring compilation. The first requests after a start include kernel compilation and graph capture. Always warm up, and never count the warmup run.
  • Two engines on one GPU. A second engine idling on the same GPU holds memory and can steal cycles. Check nvidia-smi shows one process before each session.
  • A noisy host. Shared cloud instances vary. Note the instance type, keep the client on the same machine, and use the reversed second session to catch drift.
  • Stale conclusions. Both projects release often. A result is a snapshot of two versions on one GPU; record them and rerun before relying on an old number.

Stretch Goals

  • Sweep concurrency (1, 8, 16, 32, 50, 64, 128) instead of fixing it at 50, and plot p99 TTFT against output throughput for both engines; the curve is more informative than one point.
  • Replace the closed loop with Poisson arrivals at fixed request rates (--request-rate in both tools) and report goodput at a TTFT and TPOT target with --goodput in vllm bench serve.
  • Re-enable caching and use SGLang's generated-shared-prefix dataset or vLLM's prefix_repetition dataset to measure prefix reuse (Lesson 24, Prefix Caching).
  • Repeat with FP8 weights on both engines, using the checkpoint you build in Lesson 16, Lab - Halve Model Memory Without Losing Quality.
  • Add TensorRT-LLM through trtllm-serve and extend the tables to three engines.

Summary

Mind map of the lab: the fairness checklist, the launch settings, the two load generators, the results table, and how to tell a real difference from noise.
  • A fair engine comparison holds the model, engine settings, workload, and measurement equal; most of the work is the checklist, not the run.
  • Serve both engines from one local copy of the weights in BF16 with an 8,192-token context, prefix caching off on both, and the same model name.
  • Set the memory fraction explicitly to the same value (0.90) on both engines, then read the logged KV capacities: vLLM's fraction covers the whole engine and SGLang's covers weights plus the KV pool, so SGLang gets about 9% more cache. Both far exceed the 125,000 tokens that 50 users need.
  • vllm bench serve and python -m sglang.bench_serving can each drive the other engine through the OpenAI completions API, but their --random-range-ratio flags mean opposite things.
  • Run a warmup and at least three timed runs per engine; call a difference real only when the run ranges do not overlap and it survives a reversed second session.
  • This workload measures batching and kernels only; shared prefixes, structured output, LoRA, or long contexts can change the ranking.

Introduction

Engine metrics tell us what the serving software is doing: how many requests wait, how full the KV cache is, how fast tokens come out (Lesson 29, Queue Depth). GPU metrics tell us what the hardware is doing underneath: whether its streaming multiprocessors have work, whether its memory bandwidth is saturated, whether it is running at full clock speed, and whether it is healthy. When a replica is slow, the GPU metrics decide which of very different fixes applies: add capacity, fix a software bottleneck, or replace a failing card.

The catch is that the two GPU numbers everyone knows are nearly useless for inference. GPU utilization from nvidia-smi reads close to 100% whenever any kernel is running, even a tiny one, and memory used reads about 90% from the moment a serving engine starts, because the engine reserves its KV cache up front. The useful signals come from NVIDIA's Data Center GPU Manager (DCGM), which reads the GPU's hardware performance counters and exports them to Prometheus.

On each GPU node, the DCGM host engine reads counters from the H100s, and dcgm-exporter publishes the fields listed in its CSV file on port 9400 with pod, namespace and container labels taken from the kubelet pod-resources socket. The vLLM pods publish engine metrics on their own metrics endpoint. Prometheus scrapes both every 15 to 30 seconds and feeds Grafana dashboards and Alertmanager, which notifies the on-call engineer or triggers automation such as draining a node.

In this lesson, we build the metrics pipeline, go through the GPU metrics that matter for inference and what a bad value means, explain why high memory use is normal, read GPU and engine metrics together to tell compute-bound, memory-bound, idle, starved, and throttled replicas apart, cover the caveats of MIG and shared GPUs, and choose which GPU metrics deserve an alert.

Clarifying the Problem

GPU monitoring questions in interviews usually start from a confusing dashboard. Here is a typical exchange between a candidate and an interviewer:

Candidate: What does the serving fleet look like?
Interviewer: H100 SXM GPUs on Kubernetes, one vLLM replica of Llama 3.1 8B Instruct per GPU, five replicas at average load and nine at the daily peak, because the autoscaler keeps each replica at 75% of its 53-stream capacity (Lesson 22, Autoscaling). Prometheus already scrapes the vLLM metrics.

Candidate: Which GPU metrics do we collect today?
Interviewer: Only utilization and memory used from nvidia-smi. Utilization reads near 100% and memory near 90% around the clock, so nobody looks at them anymore.

Candidate: What should the GPU metrics help us decide?
Interviewer: Three things. When a replica is slow, is it overloaded, starved by something else, or impaired? Is a GPU failing before it crashes or returns garbage? And are we using the hardware we pay for?

Candidate: Do we share GPUs between workloads?
Interviewer: A separate pool runs small embedding and classification models on MIG slices of H100s.

Candidate: What are the rules for paging?
Interviewer: Page only for things that need a human right now. Everything else goes to tickets or dashboards.

The question underneath is: which GPU metrics should we collect, how do we read them together with the engine's metrics to diagnose a slow replica, and which of them deserve an alert? We start with how the numbers are collected, because the collection method limits what they can mean.

Collecting GPU Metrics

NVML, DCGM, and dcgm-exporter

Three layers sit between the hardware and a dashboard. NVML, the NVIDIA Management Library, ships with the driver and powers nvidia-smi: it reports device-level counters such as utilization, memory, power, temperature, and clocks. DCGM builds on it with health checks, error tracking, and profiling metrics read from the GPU's hardware performance counters, available on datacenter GPUs from Volta onward [1]. dcgm-exporter wraps DCGM and serves the fields listed in a CSV file as Prometheus metrics on port 9400 at /metrics [3].

The CSV file matters more than it looks. The exporter's default list includes GPU utilization, memory, power, temperatures, clocks, PCIe, XID errors, row remapping, and three profiling fields (graphics engine, tensor pipe, and DRAM activity). It leaves out SM activity, SM occupancy, the power limit, ECC error counts, throttling counters, and per-direction NVLink traffic [4]. For inference, several of those are exactly the metrics we need, so we ship our own CSV.

Two caveats apply to profiling fields. Some can only be collected in separate hardware passes, so DCGM multiplexes them by sampling, and very high collection frequencies can return zeros [1]. And the newest DCGM field reference renames many fields while keeping their IDs: field 1002 is listed as DCGM_FI_PROF_SM_UTIL_RATIO, and DCGM_FI_DEV_GPU_UTIL is deprecated in favor of DCGM_FI_DEV_GPU_UTIL_RATIO [2]. Lesson 19, GPU Utilization, explains the renaming. This lesson uses the names that dcgm-exporter exposes, because the exporter names each Prometheus metric after the field name in its CSV, and those are the names you query.

Deploying on Kubernetes

On Kubernetes, dcgm-exporter runs as a DaemonSet, one pod per GPU node. The NVIDIA GPU Operator deploys it by default; without the Operator, NVIDIA publishes a Helm chart [5][11]. Three details of the chart are worth knowing:

  • Pod attribution: with Kubernetes mapping enabled, the exporter reads the kubelet pod-resources socket and adds pod, namespace, and container labels to each GPU's metrics [5]. This is what lets us join GPU metrics with the engine metrics of the vLLM pod on that GPU.
  • Privileges: profiling fields (DCGM_FI_PROF_*) need the SYS_ADMIN capability, which the chart grants by default [5].
  • Scraping: the chart creates a Prometheus Operator ServiceMonitor with a 30-second interval, and a custom field list can replace the default CSV through the chart's customMetrics value. It replaces the list rather than adding to it, so the custom list must be complete [5].

The Metrics That Matter for Inference

What each metric measures

Each metric watches one part of the GPU. Figure 2 maps them onto an H100: the 132 streaming multiprocessors (SMs) with their tensor cores, the 80 GB of HBM3 memory, the PCIe link to the host, the NVLink links to other GPUs, and the power and thermal controls [12]. Lesson 33, GPU Architecture and Attention Kernels, explains what these parts do; here we only need to know which counter watches which part.

A block diagram of an H100 SXM. The 132 streaming multiprocessors, each with tensor cores, are watched by GPU utilization, graphics engine activity, SM activity, SM occupancy and tensor pipe activity. The 80 GB of HBM3 is watched by DRAM activity, framebuffer used and free, memory temperature, ECC errors and row remapping. The PCIe link to the host CPU is watched by PCIe transmit and receive bytes and PCIe replays. NVLink to peer GPUs is watched by NVLink bytes. Power and thermal control is watched by power draw and limit, GPU temperature, SM clock and throttling counters. XID errors come from the driver.

Utilization is not work

GPU utilization is defined as the share of time in which one or more kernels was running [7]. It does not ask how much of the GPU each kernel used. A decode step at batch size 1 launches a long sequence of small kernels, each of which keeps only a fraction of the 132 SMs busy, yet the GPU always has some kernel running, so utilization reads 100%. SM activity averages over all SMs and tells the two cases apart, as Figure 3 shows.

Two panels, each showing one second of a GPU with its 132 SMs drawn as twelve groups. In the first, small decode kernels run back to back but occupy only three of the twelve groups at a time: GPU utilization reads 100 percent and SM activity about 0.25. In the second, a large batch keeps eleven of the twelve groups busy: GPU utilization still reads 100 percent and SM activity about 0.9.

NVIDIA's guidance for SM activity is that 0.8 or more is necessary, but not sufficient, for effective use of the GPU, and that values below 0.5 likely indicate ineffective use [1]. Even SM activity cannot say whether the active warps do useful arithmetic or wait on memory; that needs the tensor and DRAM counters, or the model-level MFU and MBU of Lesson 19, GPU Utilization.

Why high memory use is normal

Lesson 3 showed how vLLM budgets an H100: with --gpu-memory-utilization 0.90, set explicitly since recent vLLM versions default to 0.92, it takes 90% of the card's memory at startup, loads 15 GiB of weights, reserves about 4.6 GiB for activations and CUDA graphs, and turns the remaining ~52 GiB into KV cache blocks. All of that is allocated whether one request is running or two hundred. The frame buffer therefore reads about 72 GiB used (0.90 × 79.6 GiB) from the first second and stays there, as Figure 4 shows.

A 24-hour chart for one replica in a fixed pool of nine H100s. Frame buffer used jumps to about 72 GiB, 90 percent of the H100, when the server starts and stays flat all day. The engine's KV cache usage follows the daily traffic cycle, from about 5 percent at night to about 21 percent at the afternoon peak.

Load lives in the engine's own metric, vllm:kv_cache_usage_perc (Lesson 29). Frame buffer metrics are still worth watching for two other reasons. If used memory rises above the engine's budget, something else is on the GPU, such as a stray notebook or a second process. And because vLLM's memory fraction is a per-instance limit, two engines placed on the same GPU each try to take their full fraction; the vLLM documentation suggests 0.5 each for two instances on one GPU [13].

Reading GPU and Engine Metrics Together

What our replica should look like

Before diagnosing anything, we work out what healthy readings look like. Lesson 19 modeled our replica at its capacity of about 5 requests per second: about 53 streams decode together, each step takes about 21 ms, and prefill takes about 31% of the GPU's time. Two lines of arithmetic turn that into expected counter levels:

  • Compute: 5 requests per second bring 12,500 prompt and output tokens per second. At about 2 × 8.03 billion FLOPs per token, that is about 200 TFLOPS, or 20% of the H100's 989 dense BF16 TFLOPS. Tensor activity should sit well below 0.5.
  • Bandwidth: each decode step reads 16 GB of weights plus the cache of 53 requests at about 2,250 tokens each, 53 × 2,250 × 128 KiB ≈ 15.6 GB, for 31.7 GB per step. Over a 21 ms step that averages 1.5 TB/s, about 45% of 3.35 TB/s; during the decode part of the step it is about 65%, Lesson 19's MBU. DRAM activity should read roughly 0.45 to 0.5.
  • GPU utilization: close to 100%, as it is at one request per second.

These numbers set expectations. A replica at capacity that shows DRAM activity of 0.2 is spending its step time on something other than reading memory, such as CPU overhead between kernels, and that is worth investigating. A replica at 0.75 is near the practical ceiling of about 0.8 and has no bandwidth left for more streams.

Before reading a GPU dashboard, estimate what it should say: tokens per second times 2 × parameters for compute, and bytes per step divided by step time for bandwidth. A reading far from the estimate is more informative than any threshold.

Telling the states apart

A slow or underperforming replica is usually in one of five states. Each has a different signature across GPU and engine metrics and needs a different response, as Figure 5 shows.

A decision table with five rows. Compute-bound: SM activity and tensor activity high, DRAM moderate, many prompt tokens per second and TTFT rising with prompt length; this is normal for prefill-heavy load, so add capacity or use FP8. Memory-bound: DRAM activity near 0.8, tensor activity low to moderate, many running requests with high KV usage and rising time per output token; normal for decode, so use FP8 KV cache, speculative decoding or more replicas. Idle: all activity low, nothing running or waiting; scale down. Starved: GPU activity low while requests wait; the bottleneck is outside the GPU, so check CPU, tokenizer, network or a hung worker. Throttled: activity normal but SM clock below peers, power at its limit or high temperature, violation counters growing, and lower throughput than peer replicas at the same load; fix cooling or power and drain the node if it persists.
  • Compute-bound: SM and tensor activity are high and DRAM activity moderate, while the engine shows many prompt tokens per second and TTFT that grows with prompt length. This is normal for prefill-heavy traffic. The fixes are more GPUs, FP8 compute (Lesson 13), or a cap on prefill tokens per step to protect decode latency.
  • Memory-bound: DRAM activity is near 0.8 and tensor activity low to moderate, while running requests and KV usage are high and the time per output token grows with the batch. This is the normal state of a busy decode replica. The fixes reduce bytes per token: an FP8 KV cache (Lesson 3), quantized weights (Lesson 13), speculative decoding (Lesson 15), or more replicas.
  • Idle: everything is low and the engine has nothing running or waiting. The fleet is over-provisioned at this hour; the autoscaler should remove replicas (Lesson 22).
  • Starved: GPU activity is low or bursty while the engine has requests waiting. The bottleneck is outside the GPU: a CPU-bound tokenizer or scheduler, kernel launch overhead that CUDA graphs would remove (Lesson 19), slow network input, or a hung worker. GPU utilization alone often hides this state, because short kernels still keep it high.
  • Throttled: activity looks normal, but the SM clock is below that of peer GPUs, power sits at its limit or temperature is high, and the violation counters grow. The engine shows lower throughput than its peers at the same load. The fix is physical: cooling, power configuration, or draining the node.

Comparing a replica with its peers is often the fastest test. Identical GPUs serving the same traffic mix through the same router should show nearly identical clocks, temperatures, and time per output token; the odd one out is the one to drain. Figure 6 shows an illustrative cooling failure: one GPU's temperature climbs from about 62 °C to 88 °C, its SM clock falls to about 80% of the fleet median once thermal slowdown begins, and its replica's time per output token rises from 21 ms to 23 ms while its peers stay flat.

Three aligned panels over 60 minutes for five GPUs. Four peers stay flat. One GPU's temperature climbs from about 62 to 88 degrees Celsius between minutes 20 and 35. From minute 32, its SM clock falls to about 80 percent of the fleet median, and its replica's time per output token rises from 21 to 23 milliseconds.

MIG and shared GPUs

Multi-Instance GPU (MIG) splits one H100 into up to seven isolated GPU instances, each with its own SMs and memory; on the H100 80 GB, profiles range from 1g.10gb (one seventh of the SMs, one eighth of the memory) to 7g.80gb [9]. MIG changes how metrics read:

  • No utilization per instance: NVML, and therefore nvidia-smi and DCGM_FI_DEV_GPU_UTIL, cannot attribute utilization to MIG devices and reports it as not available [8]. Use DCGM's profiling fields, such as DCGM_FI_PROF_GR_ENGINE_ACTIVE, which DCGM reports per GPU instance.
  • Instance-relative values: an instance's activity is relative to its own SMs. The whole GPU's activity is the average weighted by each instance's share of compute, which DCGM's documentation illustrates with a worked example [1].
  • Labels: dcgm-exporter adds GPU_I_PROFILE and GPU_I_ID labels to per-instance series, so dashboards must group by them [3].
An H100 split into a 3g.40gb instance at 0.90 graphics engine activity, a 2g.20gb instance at 0.50, a 1g.10gb instance at 0.20, and an idle 1g.10gb instance at 0. GPU utilization reads not available. Weighting each instance by its sevenths of the compute gives 3 times 0.9 plus 2 times 0.5 plus 1 times 0.2 plus 0, divided by 7, which is about 0.56 for the whole GPU.

Figure 7 shows why per-instance reading matters: the busiest instance is at 0.90 and would benefit from more capacity, while the whole GPU reads 0.56 and looks comfortable. Without MIG, GPUs can also be shared by time-slicing or by running several processes on one card. Then every GPU metric describes the whole card, and pod labels can attribute the same GPU to several pods, so per-workload numbers have to come from the engines themselves.

Alerting on GPU Metrics

Three kinds of GPU signal

Brendan Gregg's USE method asks three questions of every resource: how utilized it is, how saturated it is, and whether it has errors [14]. For a GPU serving LLMs, the answers come from different places. Utilization comes from the profiling fields. Saturation is best read from the engine, as queue depth and KV cache usage (Lesson 29). Errors come from XID codes, ECC counters, row remapping, and PCIe replays. Only errors and throttling describe a problem with the GPU itself; the rest describe load, and load is already covered by the engine and latency alerts.

Which metrics to alert on for our deployment?

For our H100 fleet behind a TTFT objective, we page on only three GPU conditions: a fatal XID code, a row remap failure, and a GPU that stops reporting. Each of them means the hardware can no longer be trusted, and automation should drain the node at the same moment the page goes out, since a fleet of five replicas at average load has little spare capacity. Lesson 40, Reliability and Rollouts, covers draining, replacing, and returning failed GPUs. Throttling and growing memory error counts open tickets, because they degrade a GPU slowly and can wait for business hours. The "starved GPU" condition is a warning that usually explains a TTFT page rather than replacing it.

We deliberately put no alert on GPU utilization, SM activity, tensor or DRAM activity, or memory used. High values are normal for a busy inference server, and low values are already caught as idle capacity by the autoscaler or as starvation by the combined rule. These metrics earn their place on the dashboard next to the engine panels, where they answer "why" once a symptom alert has fired.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Model FLOPs utilization and model bandwidth utilization, which convert tokens per second into the share of peak compute and bandwidth that the model actually uses (Lesson 19, GPU Utilization).
  • Energy per token: dcgm-exporter's default list includes a total energy counter, which divided by tokens served gives joules per token, a useful efficiency metric next to cost per million tokens (Lesson 20).
  • DCGM health checks and diagnostics (dcgmi diag) run before a node joins the serving pool, so a weak GPU is caught before it serves traffic [1] (Lesson 40, Reliability and Rollouts).
  • Fabric and NVLink health on multi-GPU servers, where one bad link slows every tensor-parallel replica that uses it (Lesson 18).
  • Recent dcgm-exporter versions offer opt-in metrics that count XID errors and clock events per code over a time window, which are easier to alert on than the last-XID gauge [6].
  • Sampling rate: profiling metrics are averages over the collection interval, so a one-second spike disappears in a 30-second scrape; use a shorter interval only on nodes under investigation [1].

Summary

Mind map summarizing the GPU metrics lesson: the DCGM pipeline, the key metrics, why memory looks full, reading GPU and engine metrics together, MIG caveats, and what to alert on.
  • dcgm-exporter publishes DCGM fields to Prometheus on port 9400; its default CSV omits SM activity, occupancy, the power limit, throttling, and ECC counters, so inference fleets should ship their own list.
  • GPU utilization only says that some kernel was running; SM activity, tensor activity, and DRAM activity say how much of the GPU was working, with about 0.8 as the practical DRAM ceiling.
  • Inference engines pre-allocate memory, so about 72 GiB (90%) used on an H100 is normal at any load; read load from the engine's KV cache usage instead.
  • At its capacity of about 5 requests per second, our replica should use about 20% of peak compute and 45% of peak bandwidth; readings far from these estimates are worth investigating.
  • GPU and engine metrics together separate compute-bound, memory-bound, idle, starved, and throttled replicas, each with a different fix.
  • With MIG, per-instance profiling fields replace GPU utilization. Page only on GPU health (fatal XIDs, row remap failures, missing GPUs), and keep load metrics on dashboards.

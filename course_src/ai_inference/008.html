Introduction

Every request in an LLM server owns a KV cache that grows by one token per decode step, and nobody knows in advance how large it will get. Early serving systems handled this the simplest way: when a request arrived, they reserved one contiguous chunk of GPU memory big enough for the longest sequence the request could ever reach. Most of that chunk was never used, and the server ran out of memory long before it ran out of compute.

PagedAttention, introduced with the vLLM serving engine in 2023, fixes this by borrowing the oldest trick in operating systems: paging [1]. Each request's KV cache is split into small fixed-size blocks that are handed out from a shared pool only when needed. A per-request block table records where each block lives, and the attention kernel follows that table to read keys and values that are scattered across memory.

Two requests, A and B, each have a row of logical blocks holding their tokens in order. Each request's block table maps logical block numbers to physical block numbers: A maps 0, 1, 2 to physical blocks 7, 1 and 4; B maps 0, 1 to physical blocks 2 and 6. The physical pool of nine blocks shows the blocks of A and B interleaved, with four blocks still free. Blocks hold 4 tokens in the drawing; vLLM's default is 16.

In this lesson, we look at why contiguous allocation wastes so much memory, how the operating-system analogy maps onto the KV cache, how block tables and the attention kernel work together, how to choose a block size, and how blocks make memory sharing between sequences almost free.

Clarifying the Problem

PagedAttention questions usually start from a server that runs out of memory too early. Here is a typical exchange between a candidate and an interviewer:

Candidate: Which model, hardware, and context limit are we working with?
Interviewer: Llama 3.1 8B Instruct in BF16 on one H100 80 GB, with a 32K-token context limit because some customers send long documents.

Candidate: What do typical requests look like?
Interviewer: Mostly chat: about 2,000 prompt tokens and 500 output tokens. A "suggest replies" feature also asks for four different answers to the same prompt.

Candidate: How does the current server manage KV cache memory?
Interviewer: It is a home-grown server. When a request arrives, it reserves a contiguous KV buffer for the full 32K context. It tops out at 13 concurrent requests, even though almost no request goes past 3,000 tokens.

Candidate: Can we lower the context limit?
Interviewer: No. The 32K limit is part of the product.

Candidate: Is the memory layout of the cache up to us, as long as accuracy is unchanged?
Interviewer: Yes. Recommend a design and justify any settings you choose.

The question underneath is: how do we make each request pay only for the cache it actually uses, without slowing attention down? To answer it, we first need to see exactly where the memory goes.

The Memory-Management Problem

Why the KV cache is hard to allocate

Most tensors in a neural network have shapes known before the forward pass runs, so frameworks store each one in a single contiguous buffer. The KV cache breaks that pattern. It grows by one token per decode step, its final length depends on when the model happens to emit an end-of-sequence token, and its lifetime ends whenever the request finishes. A server that insists on contiguous storage must decide a request's buffer size at admission time, before it knows any of this.

Three kinds of waste

The PagedAttention paper names three ways a contiguous allocator wastes cache memory [1]:

  • Reserved slots: space for tokens the request will generate later. It is used eventually, but it sits idle for most of the request's life, blocking other requests.
  • Internal fragmentation: space reserved for the maximum length that the request never reaches because it stops early. It is pure waste.
  • External fragmentation: gaps between reserved chunks of different sizes that are too small to hold a new request's chunk.
A memory strip holds two contiguous reservations. Request A has filled 9 slots of a 32-slot reservation: 9 slots hold tokens, 3 are reserved for tokens it will still generate, and 20 will never be used because A stops early. Request B fills 5 of 16 slots, with 2 reserved and 9 never used. A 6-slot gap between them is external fragmentation that no new 16-slot request can use.

Figure 2 shows all three in one memory strip. The paper measured how bad this is: in its reimplementations of Orca [2], a state-of-the-art system that reserved memory per request, only 20.4% to 38.2% of the KV cache memory held actual token states [1]. In other words, these systems wasted roughly 60% to 80% of their cache. vLLM, with paging, used 96.3% of it for token states.

Worked example: contiguous reservation on our H100

Lesson 3, KV Cache, found that Llama 3.1 8B needs 128 KiB per token and that about 52 GiB of an H100 is left for the cache with --gpu-memory-utilization set explicitly to 0.90 (recent vLLM releases default to 0.92). Reserving the full 32K context per request costs 32,768 × 128 KiB = 4 GiB, so only 52 ÷ 4 = 13 requests fit, which is exactly where the interviewer's server tops out.

A chat request, however, ends at about 2,500 tokens. It uses 2,500 ÷ 32,768 ≈ 7.6% of its reservation, and the other 92% sits idle for the request's whole life. Reserving less does not solve the problem either: any fixed reservation must either be large enough for the rare long request, which wastes memory on every short one, or too small, which forces the server to reject or restart requests that run long.

Borrowing from the Operating System

Virtual memory in one paragraph

Operating systems solved the same problem for processes decades ago. A process sees a contiguous range of virtual addresses, but the OS divides that range into fixed-size pages and maps each one to any free physical frame in RAM through a page table. A frame is assigned only when the process first touches the page, so a program that reserves a large buffer but uses a little of it consumes only what it uses. Because every frame has the same size, any free frame fits any page, and external fragmentation disappears.

The mapping

PagedAttention applies the same design to the KV cache. In the paper's words, one can think of "blocks as pages, tokens as bytes, and requests as processes" [1]. Table 1 lists the full correspondence, and Figure 3 draws it.

Block tables

Each sequence keeps a block table: an array whose entry i holds the physical block ID of the sequence's logical block i. With block size B, the token at position p lives in logical block \lfloor p / B \rfloor at offset p \bmod B. For a 2,500-token chat request with 16-token blocks, token 2,499 sits in logical block 156 at offset 3, and the table needs 157 entries.

The table is tiny next to the data it maps. A full 32K-token sequence needs 2,048 entries, about 8 KiB as 32-bit integers, to describe 4 GiB of cache. Allocation is just as cheap: when a sequence's last block fills, the engine pops a free block ID from a list and appends it to the table; when the sequence finishes, all its IDs go back to the list. Waste is limited to the unfilled part of each sequence's last block.

For a model like Llama, where every layer uses full attention, one block ID in vLLM covers the same token positions in every layer, so a block's size is summed across layers. For Llama 3.1 8B, one layer stores 16 tokens × 8 KV heads × 128 dimensions × 2 bytes = 32 KiB of keys and the same for values, and 32 layers bring the block to 2 MiB. vLLM sizes the pool by dividing the memory left for the cache by the bytes per block [3].

Worked example: the block pool on our H100

The 52 GiB KV budget is divided into 26,624 blocks of 2 MiB. Each block holds 16 tokens across all 32 layers, at 64 KiB per layer. A 2,500-token chat request uses 157 blocks, the last one holding only 4 of its 16 tokens, so 169 such requests fit in the pool, against 13 with contiguous 32K reservations.
  • Block size in bytes: 16 tokens × 128 KiB = 2 MiB.
  • Blocks in the pool: 52 GiB ÷ 2 MiB = 26,624 blocks, or 26,624 × 16 = 425,984 tokens, the same capacity Lesson 3 computed.
  • One chat request: 2,500 tokens ÷ 16 = 156.25, so 157 blocks. The last block holds 4 tokens and wastes 12 slots, 1.5 MiB, about 0.5% of the request's 314 MiB.
  • Concurrency: 26,624 ÷ 157 ≈ 169 chat requests at their full length, against 13 with contiguous 32K reservations, about 13× more.

Paging does not shrink the cache per token; Lesson 3's techniques do that. It removes the gap between what a request reserves and what it uses, which for this workload is the difference between 13 and 169 users on the same GPU.

State the block math in one breath: "16 tokens at 128 KiB is a 2 MiB block, 52 GiB is 26,624 blocks, a 2,500-token chat needs 157 of them, so about 169 requests fit, and the only waste is the tail of each last block."

How Attention Reads a Paged Cache

Gathering non-contiguous blocks

A standard attention kernel expects each sequence's keys and values in one contiguous tensor. A paged kernel instead receives, for every sequence in the batch, its query, its block table, and its context length. It then walks the block table: for logical block j it looks up the physical ID, computes that block's address inside each layer's cache tensor, loads the block's keys, computes attention scores against the query, and later loads the matching values. Within one layer's tensor, in a block-major layout, the address of a token's keys is:

\text{addr}(p) = \text{base} + \text{table}\left[\lfloor p / B \rfloor\right] \cdot S_{\text{block}} + (p \bmod B) \cdot S_{\text{token}}

where S_{\text{block}} and S_{\text{token}} are the bytes of one block and one token in that layer. The softmax still has to run over all positions, so the kernel either keeps a running maximum and sum as it moves from block to block, or computes partial results per block and merges them at the end. The paper writes attention exactly this way, as a sum over blocks [1]. Figure 5 traces one decode step.

A query vector for request A and A's block table, which lists physical blocks 7, 1 and 4. The kernel walks the table, loads key and value blocks 7, 1 and 4 from scattered places in the pool, computes partial attention for each block, and merges the partial results with a running softmax into one output vector.

Indirection is not free. The original vLLM kernel assigned one GPU warp to each block so that loads stay coalesced, and still measured 20% to 26% higher attention-kernel latency than FasterTransformer's contiguous kernel, from the extra table lookups, branches, and variable lengths [1][4]. Attention is only one part of each step, though, and fitting 2× to 4× more requests into memory outweighs the slower kernel by a wide margin. Today's attention libraries treat paged caches as a first-class layout; FlashInfer, for example, handles paged and other KV storage formats through a block-sparse representation [5]. Lesson 33, GPU Architecture and Attention Kernels, looks inside these kernels.

Choosing a block size

The block size sets a trade-off between memory waste and kernel efficiency:

  • Small blocks waste less: on average about half a block per sequence is empty. They also let sequences share memory at a finer grain, since sharing happens in whole blocks. But each block is a smaller memory transaction, the kernel does more table lookups, and swapping many small blocks to CPU memory uses PCIe bandwidth poorly [1].
  • Large blocks give the kernel bigger contiguous loads and shorter tables, but waste grows linearly with block size and sharing gets coarser.
A bar chart of the average memory wasted in last blocks across 170 concurrent sequences for block sizes of 1, 16, 64, 128, 256 and 512 tokens: 0, 0.16, 0.65, 1.32, 2.65 and 5.30 GiB, which is 0, 0.3, 1.3, 2.5, 5.1 and 10.2 percent of the 52 GiB cache.

Figure 6 puts numbers on the waste side for our deployment, assuming sequence lengths fall evenly across block boundaries. At 16 tokens, 170 sequences lose about 0.16 GiB, 0.3% of the cache. At 512 tokens they lose about 5.3 GiB, 10% of the cache, or about 17 chat requests' worth. The paper measured the other side: on ShareGPT traces, block sizes from 16 to 128 performed best, while on the shorter Alpaca traces only 16 and 32 did well, so vLLM chose 16 as its default [1]. vLLM 0.32 still defaults to 16 tokens [6]. When an attention backend needs a different size, vLLM picks one the backend supports and logs the change, unless you set --block-size yourself [7][8]. Other engines chose differently: SGLang defaults to a page size of 1 token [9], and TensorRT-LLM's XQA kernel supports 8 to 128 tokens per block [10].

Sharing Blocks Between Sequences

Reference counts and copy-on-write

Once a cache is a list of block IDs, two sequences can point at the same physical block. Each physical block carries a reference count: the number of block tables that contain it. A block returns to the free pool only when its count drops to zero.

Parallel sampling is the simplest case. The "suggest replies" feature asks for four answers to one prompt, so the four samples start with identical prompt caches. With paging, the prompt is prefilled once, and all four block tables point at the same physical blocks, each with a reference count of 4. When a sample is about to write into a block that others still share, the engine applies copy-on-write: it allocates a fresh block, copies the shared block's contents into it, points the writing sample's table at the copy, and decrements the original's count [1]. Only the partly filled last block of the prompt is ever copied; full blocks are never written again.

The prompt's 125 full blocks are shared by four samples with a reference count of 4. Its last block holds 4 tokens and is also shared. When samples 1, 2 and 3 write their first token, each copies that block into a new one and the shared block's count drops from 4 to 1; sample 4 then writes in place. Each sample's 500 new tokens go into its own blocks.

Take a 2,004-token prompt, which fills 125 blocks plus 4 tokens of a 126th, and four 500-token answers. Without sharing, each sample needs ⌈2,504 ÷ 16⌉ = 157 blocks, 628 blocks or 1,256 MiB in total. With sharing, the 125 full prompt blocks exist once, and each sample owns 32 blocks (its copy of the partial block plus 31 new ones): 125 + 4 × 32 = 253 blocks, or 506 MiB. Sharing saves 60% of the memory, and three block copies are the only cost.

Beam search shares even more. Beams branch from common ancestors, so they share not only the prompt but long stretches of generated text, and the sharing pattern changes as weak beams are dropped and their blocks freed. On OPT-13B with Alpaca traces, the paper measured memory savings of 6.1% to 9.8% for parallel sampling and 37.6% to 55.2% for beam search; on ShareGPT traces, with longer prompts, the savings were 16.2% to 30.5% and 44.3% to 66.3% [1].

vLLM's current engine implements a request with n > 1 by splitting it into n child requests [11]. Sharing between the children then comes from prefix caching, which is on by default [6] and reuses full blocks once they have been computed [12], rather than from a separate copy-on-write path. A partly filled last block is never shared.

Prefix sharing builds on the same blocks

The same mechanism works across unrelated requests. Many requests begin with the same system prompt or the same few-shot examples, and a block's keys and values depend only on the tokens up to and including that block. vLLM therefore identifies each full block by a hash of its parent block's hash, its own tokens, and extra keys such as a LoRA adapter ID [12]. A new request whose prompt starts with already-cached blocks maps its first logical blocks to the existing physical blocks, increments their reference counts, and skips their prefill. Blocks whose count drops to zero stay in the pool as a cache until they are evicted for new allocations. Lesson 24, Prefix Caching, covers hit rates, eviction, and routing for cache reuse.

What paging bought

By filling memory with real tokens instead of reservations, vLLM could batch far more requests, and throughput followed. Table 2 collects the main numbers from the paper and the launch blog post. The gains are largest exactly where memory is tightest: long sequences, large models, and decoding methods that create several sequences per request. When memory is plentiful and sequences are short, as with OPT-175B on eight GPUs serving the short Alpaca prompts, the baselines can also batch many requests and the advantage shrinks [1].

Alternatives: virtual contiguity and token-level pages

PagedAttention moves address translation into software, which means every attention kernel must understand block tables. vAttention takes the opposite route [14]. It keeps each request's KV cache contiguous in virtual memory and uses CUDA's virtual memory management APIs to back it with physical memory only as the cache grows. Attention kernels see an ordinary contiguous tensor and need no changes, while physical memory is still allocated on demand. The authors report up to 1.23× higher serving throughput than the paged kernels of FlashAttention and FlashInfer, and add LLM-specific optimizations to work around the limits of CUDA's virtual memory support. The paper appeared at ASPLOS 2025.

Two stacks. In PagedAttention, the attention kernel reads a block table and gathers scattered physical blocks itself. In vAttention, the kernel reads one contiguous virtual buffer per request, and the GPU's memory-mapping hardware translates virtual pages to physical pages that the serving system maps on demand through CUDA's virtual memory APIs.

At the other extreme, SGLang manages its cache in pages of a single token by default and organizes cached prefixes for reuse through RadixAttention [15][9]. With one-token pages, the last-block waste disappears entirely, and sharing can happen at any token boundary, at the cost of one index entry per token.

Which block size fits our deployment?

We keep vLLM's paged cache with its default 16-token blocks. At 16 tokens the last-block waste is about 0.3% of the cache for 170 sequences, so smaller blocks or one-token pages could win back at most 0.16 GiB, less than one chat request. Larger blocks would cost real capacity, about 1.3% at 64 tokens and 10% at 512, and would make prefix sharing coarser, which matters because our chat traffic shares system prompts. The paper's measurements show 16 is already large enough for efficient kernels on typical chat traffic. We set --block-size only if the attention backend demands a different value.

For the "suggest replies" feature, we keep prefix caching on, which is the default, so the four samples can share their prompt blocks. With the paged cache, our H100 moves from 13 concurrent requests to about 169 at full chat length, and a four-answer request whose samples share the prompt needs about 506 MiB instead of 1,256 MiB.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Preemption works at sequence granularity: the paper evicts all of a sequence's blocks or none, since attention needs every block, and found that recomputation never cost more than 20% of swapping's latency in its tests [1]. Lesson 7, Continuous Batching, covers how the scheduler decides whom to preempt.
  • With tensor parallelism, every GPU shard uses the same block IDs and stores only its own attention heads in each block, so one block manager serves all GPUs [1] (Lesson 18, Tensor Parallelism).
  • Paging makes it cheap to move cache blocks between machines or memory tiers, which disaggregated prefill and decode (Lesson 34, Disaggregated Prefill and Decode) and KV offloading to CPU memory (Lesson 36, Long-Context Serving) both build on.
  • Models that mix full attention with sliding-window or linear-attention layers need different block policies per layer type, since window layers can free old blocks while the sequence is still running.
  • Why compaction does not help: moving gigabytes of cache to close gaps costs too much bandwidth on the serving path, and it still would not allow sharing between sequences [1].
  • The vllm:kv_cache_usage_perc gauge reports the fraction of blocks in use, which makes it the first metric to check when preemptions rise [16].

Summary

Mind map summarizing the PagedAttention lesson: the memory-management problem, the operating-system analogy, block tables and the attention kernel, block size, sharing, and results.
  • Contiguous per-request reservations waste KV cache memory through reserved slots, internal fragmentation, and external fragmentation; the PagedAttention paper measured 60% to 80% waste.
  • PagedAttention treats blocks as pages, tokens as bytes, and sequences as processes: fixed-size blocks come from a shared pool on demand, and a block table maps each sequence's logical blocks to physical ones.
  • For Llama 3.1 8B on one H100, 16-token blocks are 2 MiB each; 52 GiB holds 26,624 of them, so about 169 chat requests fit instead of 13 with 32K reservations.
  • The attention kernel follows the block table to gather scattered blocks; the original kernel was 20% to 26% slower than a contiguous one, but end-to-end throughput rose 2× to 4×.
  • Block size trades last-block waste against kernel efficiency; 16 tokens wastes about 0.3% of our cache and remains vLLM's default.
  • Reference counts and copy-on-write let samples and beams share blocks; four answers to a 2,004-token prompt need 253 blocks instead of 628.
  • vAttention keeps caches virtually contiguous with CUDA virtual memory instead, and SGLang uses one-token pages by default.

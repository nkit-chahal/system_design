Introduction

A large language model generates text one token at a time. To pick the next token, every attention layer compares the newest token against all the tokens that came before it. Without help, this means the model reprocesses the entire conversation at every step: generating the 1,000th token would repeat the work already done for the first 999.

The KV cache removes that repetition. The first time the model processes a token, it saves that token's attention keys and values in GPU memory. Every later step reads them back instead of recomputing them. This trade, spending memory to save compute, is what makes LLM generation fast enough to use. It also creates the central constraint of LLM serving: the KV cache, not the model weights, decides how many users a GPU can serve at once.

Two grids of five steps by five tokens. Without a cache, every step recomputes keys and values for every previous token, forming a triangle of 15 computations. With a cache, each step computes keys and values only for the newest token and reads the rest from the cache.

In this lesson, we look at what the cache stores, how to calculate its size for any model, why a full cache also makes generation slower, and the techniques that serving teams use to shrink and manage it.

Clarifying the Problem

KV cache questions in interviews usually start from a capacity problem. Here is a typical exchange between a candidate and an interviewer:

Candidate: Which model are we serving, and at what precision?
Interviewer: Llama 3.1 8B Instruct, with weights in BF16.

Candidate: What hardware do we have?
Interviewer: A single NVIDIA H100 with 80 GB of memory.

Candidate: What do typical requests look like?
Interviewer: Most are chat requests with about 2,000 prompt tokens and 500 output tokens. A few customers upload documents that fill a 32K-token context.

Candidate: Is there a latency target?
Interviewer: Users should see steady streaming output. We want as many concurrent users per GPU as possible without hurting that.

Candidate: Are we allowed to trade a little accuracy for memory, for example by storing the cache in lower precision?
Interviewer: Only if our evaluation set shows no meaningful quality drop.

The question underneath is: how many requests fit on this GPU at the same time, and what can we do to fit more? To answer it, we need to know exactly what the cache holds.

How Attention Uses Keys and Values

Self-attention in one equation

Each attention layer projects every token's hidden state x into three vectors: a query q = W_q x, a key k = W_k x, and a value v = W_v x. A token's output is a weighted average of the values of all the tokens it can see, where the weights come from comparing its query with their keys [1]:

\text{Attention}(q, K, V) = \text{softmax}\left(\frac{q K^\top}{\sqrt{d}}\right) V

Here K and V stack the keys and values of every visible token, and d is the size of one attention head.

Why past keys and values never change

Decoder-only LLMs use causal masking: a token can attend only to itself and to earlier tokens. Appending a new token therefore never changes the hidden states of earlier tokens, so their keys and values never change either. Anything that never changes can be computed once and stored.

At each decode step, the model computes q, k, and v for the single new token, appends the new k and v to the cache, and attends over the whole cache. Figure 2 shows one step for one layer.

The new token "on" is projected into q, k and v. The new k and v rows are appended to the K and V caches, which already hold rows for "The", "cat" and "sat". The query is compared with all cached keys to produce scores, softmax turns them into weights, and the weights average the cached values into the output that flows to the next layer.

The cost shifts from compute to memory. Without a cache, producing n tokens repeats work that grows with n^2. With a cache, each step does a fixed amount of new compute, but it must read every cached key and value. Generation becomes a memory-bandwidth problem, which is why decode is called memory-bound [2] (we explore this in Lesson 2, Prefill vs Decode).

What exactly gets stored

For every token in a sequence, the cache stores one key vector and one value vector per KV head, in every layer. Figure 3 shows the layout for Llama 3.1 8B, which has 32 layers, 8 KV heads, and a head size of 128.

One cached token fans out into 32 layers. Each layer stores a K block and a V block of 8 KV heads by 128 dimensions. The total is 2 times 32 times 8 times 128 times 2 bytes, which is 131,072 bytes or 128 KiB per token.

Sizing the KV Cache

Multiply out the dimensions to get the size of one token's cache:

\text{KV bytes per token} = 2 \times L \times H_{\text{kv}} \times d_{\text{head}} \times b

The 2 counts keys and values, L is the number of layers, H_{\text{kv}} the number of KV heads, d_{\text{head}} the head dimension, and b the bytes per number (2 for BF16 or FP16, 1 for FP8). The size of one request is this number multiplied by its total tokens, prompt plus output:

\text{KV bytes per request} = \text{KV bytes per token} \times (\text{prompt tokens} + \text{output tokens})

All four values sit in the model's config.json as num_hidden_layers, num_key_value_heads, head_dim (or hidden_size / num_attention_heads), and the weight dtype. Table 1 applies the formula to well-known models.

Two models of similar size can differ by almost 10× in cache cost. Llama 2 7B and Qwen2.5 7B have nearly the same number of weights, but Qwen's cache is about nine times smaller because it keeps only 4 KV heads and 28 layers. When you choose a model for serving, its cache footprint matters as much as its parameter count.

Worked example: one H100 serving Llama 3.1 8B

Now we can answer the interviewer. A serving engine such as vLLM loads the weights, reserves working memory for activations and CUDA graphs, and gives everything that remains to the KV cache. We set --gpu-memory-utilization 0.90, so vLLM uses 90% of GPU memory and leaves the rest free (recent vLLM versions default to 0.92).

A horizontal bar splits the H100's memory into 15 GiB of weights, about 4.6 GiB of activations and CUDA graphs, about 52 GiB of KV cache and 8 GiB held back. 52 GiB divided by 128 KiB per token gives about 426,000 tokens, which serves about 170 chat requests of 2,500 tokens or 13 document requests of 32,768 tokens.
  • Weights: 8 billion parameters × 2 bytes ≈ 15 GiB.
  • KV cache budget: roughly 52 GiB remains after weights and runtime overhead.
  • Tokens that fit: 1 GiB ÷ 128 KiB = 8,192 tokens, so 52 GiB holds about 52 × 8,192 ≈ 426,000 tokens.
  • Chat traffic: at 2,500 tokens per request, about 170 requests fit at once.
  • Long documents: at 32,768 tokens per request, only 13 fit.

The weights take less than a quarter of the GPU, yet the cache caps concurrency. Long-context traffic is roughly 13 times more expensive than chat traffic on the same hardware, which is why many providers price long contexts differently.

Say the numbers out loud: "128 KiB per token, about 8,000 tokens per GiB, so 52 GiB of free memory holds roughly 426K tokens." Interviewers care that you can size the cache from first principles more than that you recall a benchmark.

Why a full cache also makes decode slow

The cache costs time as well as space. At every decode step, attention reads the keys and values of every token of every request in the batch. Once the cache is full, one step on our H100 must read about 56 GB of cache plus 16 GB of weights. At the H100's 3.35 TB/s of memory bandwidth, that is about 21 ms per step even with perfect efficiency, which caps each stream near 46 tokens per second. Packing more requests into the cache raises total throughput but slows every individual stream. We return to this trade-off in Lesson 5, Tokens per Second.

Shrinking the KV Cache

Since the cache limits both capacity and speed, a whole family of techniques tries to make it smaller. They differ in where they act: some change the model architecture, some change the number format, and some change which tokens are kept.

Fewer KV heads: MQA, GQA, and MLA

In the original multi-head attention (MHA), every query head has its own key and value head. Multi-query attention (MQA) shares a single KV head across all query heads [3]. Grouped-query attention (GQA) is the middle ground: query heads are split into groups and each group shares one KV head [4]. Llama 3.1 8B uses 32 query heads and 8 KV heads, so its cache is a quarter of the MHA size.

Three panels with eight query heads each. MHA connects each query head to its own KV head, so the cache is 100%. GQA connects groups of four query heads to two KV heads, so the cache is 25%. MQA connects all eight query heads to one KV head, so the cache is 12.5%.

Multi-head latent attention (MLA), introduced in DeepSeek-V2 [5], goes further: it caches one small compressed latent vector per token per layer and reconstructs keys and values from it. This is why DeepSeek-V3, a 671B-parameter model, needs less cache per token than Llama 3.1 8B. All three techniques are fixed when the model is trained, so as a serving engineer you get them by choosing the model, not by flipping a flag.

Lower precision: FP8 and INT4 caches

The cache can be stored in fewer bits than the weights. An FP8 cache halves the memory per token, from 128 KiB to 64 KiB for Llama 3.1 8B, which doubles the tokens that fit. vLLM enables it with --kv-cache-dtype fp8 and supports the fp8_e4m3 and fp8_e5m2 formats [7]. Research methods such as KIVI push keys and values down to 2 bits [8]. The risk is accuracy, especially on long contexts and reasoning tasks, so measure it on your own evaluation set before shipping.

Bounded attention: sliding windows and local layers

If a layer only attends to the last w tokens, its cache never grows beyond w tokens. Mistral 7B used a 4,096-token sliding window in every layer [11]. Newer models such as Gemma 2 and Gemma 3 mix cheap local-window layers with a few full-attention layers, so most layers have a small, fixed cache. Like GQA, this is an architectural choice.

Token eviction and compression

Another family keeps the architecture but drops tokens that matter little. StreamingLLM keeps a few initial "attention sink" tokens plus a recent window [9]. H2O keeps the "heavy hitter" tokens that receive the most attention [10]. SnapKV compresses a long prompt by selecting the positions that the final prompt tokens attend to [14]. These methods can cut memory dramatically but may lose details the model needs later, such as a fact buried in the middle of a document.

Offloading to CPU memory and SSD

Instead of throwing tokens away, the cache can move to cheaper, slower memory. Tools such as LMCache store caches in CPU memory or on local and remote disks so they can be reused across requests, for example for a long shared document [13]. Offloading saves recomputation but adds transfer time, so it pays off when the same prefix is reused often.

Which technique fits our deployment?

For Llama 3.1 8B on one H100, the model choice is fixed, and it already uses GQA. The most practical lever is an FP8 KV cache: it requires no retraining, roughly doubles capacity to about 850,000 tokens, and usually costs little accuracy. We enable it, then confirm on the evaluation set that quality holds, as the interviewer required. Eviction methods are riskier for document question answering, where any token might matter, so we leave them out. If the team later chooses a new model, cache size per token becomes part of the comparison.

Managing the Cache inside a Serving Engine

Contiguous versus paged allocation

Early serving systems reserved one contiguous chunk of memory per request, sized for the longest sequence it might reach. Because no one knows in advance how long a response will be, most of that reservation sits empty. The PagedAttention paper measured that such systems wasted 60–80% of their KV cache memory [6].

In the contiguous layout, three requests each reserve 16 slots but use 5, 2 and 9 of them, so two thirds of the memory is idle. In the paged layout, the same 16 blocks of data are allocated from a shared pool on demand, leaving free blocks for new requests.

Paged allocation borrows the idea of virtual memory from operating systems. The cache is split into fixed-size blocks (16 tokens per block by default in vLLM), handed out as tokens arrive. A per-request block table maps logical positions to physical blocks, so a request's cache does not need to be contiguous. Waste drops to at most one partly filled block per request. We study this in detail in Lesson 8, PagedAttention.

When the cache runs out: preemption

Requests grow as they generate, so a full cache must still find room for the next token. The scheduler then preempts a request: it frees that request's blocks and later rebuilds its cache by recomputing the prompt and the tokens generated so far. vLLM's current engine preempts by recomputation by default. Frequent preemption is a warning sign that the server is admitting more requests than its cache can hold, and it shows up as latency spikes for the preempted users.

Sharing the cache across requests

Many requests start with the same text, such as a system prompt, few-shot examples, or a document that several users ask about. Because the cache for a given prefix is always the same, an engine can compute it once and let many requests point to the same blocks. This is prefix caching, and it can remove most of the prefill work for chat applications with long system prompts. Lesson 24 covers it in depth.

In Practice

The first tab computes the cache size of any Hugging Face model from its config. The second starts vLLM with an FP8 cache; its startup log reports the cache capacity directly. The third shows the speed difference the cache makes, using a small model that runs on a laptop; the Transformers cache guide covers the other cache classes [12].

from transformers import AutoConfig def kv_bytes_per_token(model_id: str, bytes_per_value: int = 2) -> int: cfg = AutoConfig.from_pretrained(model_id) cfg = getattr(cfg, "text_config", cfg) # multimodal models nest the LLM config head_dim = getattr(cfg, "head_dim", None) or cfg.hidden_size // cfg.num_attention_heads kv_heads = getattr(cfg, "num_key_value_heads", None) or cfg.num_attention_heads return 2 * cfg.num_hidden_layers * kv_heads * head_dim * bytes_per_value per_token = kv_bytes_per_token("Qwen/Qwen2.5-7B-Instruct") print(f"{per_token / 1024:.0f} KiB per token") # 56 KiB print(f"{per_token * 32_768 / 2**30:.2f} GiB per 32K request") # 1.75 GiB free_gib = 52 # what remains after weights and runtime overhead print(f"{free_gib * 2**30 // per_token:,} tokens fit in {free_gib} GiB") # Serve with an FP8 KV cache (half the memory per token). vllm serve meta-llama/Llama-3.1-8B-Instruct \ --max-model-len 32768 \ --gpu-memory-utilization 0.90 \ --kv-cache-dtype fp8 # The startup log reports cache capacity. Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Cross-layer attention, which lets adjacent layers share one KV cache to shrink it further [15].
  • Disaggregated serving, where prefill and decode run on different GPUs and the KV cache is transferred between them over fast interconnects.
  • How attention kernels such as FlashAttention and FlashInfer read a paged cache efficiently.
  • Why the cache makes beam search and parallel sampling cheaper: candidates share the prompt's blocks and copy a block only when they diverge.
  • Why per-token cache cost, not parameter count, should drive pricing for long-context requests.
  • Choosing --max-model-len: a lower limit does not shrink each token's cost, but it lets the scheduler admit requests with confidence that they can finish.

Summary

Mind map summarizing the KV cache lesson: what is cached, how to size it, how to shrink it, and how serving engines manage it.
  • The KV cache stores each token's attention keys and values so that decoding does not recompute them. It turns generation from a compute problem into a memory problem.
  • Size per token is 2 × layers × KV heads × head dim × bytes: 128 KiB for Llama 3.1 8B in BF16, or about 8,000 tokens per GiB.
  • On one H100, Llama 3.1 8B fits about 426,000 cached tokens: about 170 chat requests or 13 requests at 32K context.
  • A full cache also slows every decode step, because each step reads the whole cache from memory.
  • Architecture (GQA, MLA, sliding windows) sets the baseline cost. FP8 caches halve it without retraining. Eviction and offloading trade accuracy or latency for more room.
  • Serving engines allocate the cache in pages, preempt requests when it fills, and share it across requests with common prefixes.

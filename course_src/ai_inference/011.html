Introduction

TensorRT-LLM is NVIDIA's open-source library for running large language models on NVIDIA GPUs, released under the Apache 2.0 license [1]. NVIDIA first released it in October 2023 as a compiler: you converted a checkpoint, built a TensorRT engine tuned for one GPU type and one set of limits, and served that engine. Its purpose has always been the same: the highest throughput and lowest latency NVIDIA's own engineers can get from their hardware, with custom kernels for attention, matrix multiplies, and mixture-of-experts layers [1].

The library has since changed shape. Version 1.0, in September 2025, made a PyTorch-based runtime the default, and the 1.4 release candidates of October 2026 removed the old engine-building path entirely [2][3]. Today TensorRT-LLM (its documentation now writes "TensorRT LLM") loads Hugging Face checkpoints directly, runs them with NVIDIA's kernels inside a PyTorch runtime, and serves them through an OpenAI-compatible server. Figure 1 shows the path of one request.

A client sends a request to the trtllm-serve process, which runs the OpenAI-compatible HTTP server and the LLM API that tokenizes the prompt. An executor proxy sends the request over IPC to worker processes, one per GPU rank, launched with MPI. In each worker the PyExecutor loop takes requests from a queue, runs the capacity and micro-batch schedulers, prepares KV cache blocks with the KV cache manager, runs the model engine with NVIDIA kernels and CUDA graphs, and samples tokens. Results return to the proxy and stream to the client. Numbered circles 1 to 5 mark the order.

In this lesson, we see how TensorRT-LLM's runtime implements in-flight batching and the paged KV cache, what its kernels and quantization formats buy on Hopper and Blackwell GPUs, and how to deploy it with trtllm-serve, Triton Inference Server, or NVIDIA Dynamo. We then compare vLLM, SGLang, and TensorRT-LLM side by side and choose an engine for our running example. Version-specific details are as of late 2026: the latest stable release is v1.2.1 and the documentation tracks the 1.4 release candidates.

Clarifying the Problem

TensorRT-LLM questions usually come with a cost angle. Here is a typical exchange:

Candidate: Which model and GPUs?
Interviewer: Llama 3.1 8B Instruct in BF16 on H100 80 GB GPUs. Next year we may add B200s.

Candidate: What traffic and latency targets?
Interviewer: The same chat traffic as before: about 2,000 prompt tokens and 500 output tokens per request, 1,000 requests per minute on average and about twice that at the daily peak, a p95 time to first token of at most 500 ms, and a p95 time per output token of at most 25 ms.

Candidate: What matters most to the business?
Interviewer: Cost per token. At about 5 requests per second per H100 we need four GPUs on average and seven at the peak, and finance asked whether a faster engine could let us run fewer.

Candidate: Are we committed to NVIDIA hardware?
Interviewer: For the next two years, yes. We would like to keep the option to test other accelerators later.

Candidate: Who will operate the engine?
Interviewer: A platform team of two engineers, using Kubernetes and Prometheus.

The question underneath is: does the extra speed TensorRT-LLM can deliver on NVIDIA GPUs pay for the extra setup and lock-in, at our scale? To answer it we need to know what the runtime does differently, and then compare all three engines.

From Compiled Engines to a PyTorch Runtime

In the original workflow, a model went through three steps: a per-model script converted the checkpoint, trtllm-build compiled it into an engine, and the runtime served the engine. The build fixed limits such as the maximum batch size, sequence length, and tokens per step, and an engine built for an H100 did not run on an A100. Builds took minutes to hours, and every change of limits, GPU type, or parallelism meant a rebuild. The reward was performance that, for a long time, other engines could not match on NVIDIA hardware.

The upper row shows the removed path: a Hugging Face checkpoint goes through convert_checkpoint.py, then trtllm-build produces an engine fixed to one GPU type and one set of limits, which the runtime serves. The lower row shows the current path: the checkpoint, optionally quantized with NVIDIA Model Optimizer, is loaded directly by the LLM API or trtllm-serve, which runs PyTorch models with NVIDIA kernels and CUDA graphs. Limits become runtime settings.

The PyTorch runtime keeps the kernels and drops the compile step, as Figure 2 shows. Models are written as ordinary PyTorch modules that call NVIDIA's custom operators; CUDA graphs are captured for decode batches by default, and torch.compile with piecewise CUDA graphs is an opt-in feature [4]. Batch size and token limits become runtime settings. The migration guide lists what disappeared in the 1.4 release candidates: trtllm-build, the per-model conversion scripts, and the tensorrt backend option [3]. If you find an older tutorial that starts with trtllm-build, it describes the removed path; the stable v1.2 line still ships it, marked as legacy.

Inside the PyExecutor

Processes and the executor loop

The trtllm-serve process runs the HTTP server and the LLM API, which tokenizes prompts and detokenizes outputs. For a model on several GPUs, an executor proxy starts one worker process per GPU rank, through MPI by default or through Ray, and talks to them over ZMQ-based IPC. Each worker runs a PyExecutor, whose loop matches what we saw in vLLM: fetch new requests, schedule, run the forward pass, sample, and return tokens [5]. Its components have NVIDIA names: a CapacityScheduler decides which requests may hold resources, a MicroBatchScheduler picks the requests for the next forward pass, a KVCacheManager owns the paged cache, and a PyTorchModelEngine runs the model.

In-flight batching

In-flight batching is NVIDIA's name for continuous batching (Lesson 7, Continuous Batching): requests join and leave the batch at every step, and prompt tokens of new requests run in the same forward pass as decode tokens of running ones. TensorRT-LLM packs all tokens without padding and places context (prefill) tokens before generation tokens in the input [6]. Two limits bound a step: max_batch_size, the number of requests (default 2,048), and max_num_tokens, the number of tokens (default 8,192) [7]. Chunked prefill, called chunked context, is off by default in trtllm-serve (as of late 2026) and is enabled with --enable_chunked_prefill. The latency math from Lesson 9 applies unchanged: an 8,192-token step of an 8B model needs at least 133 ms of compute, and stalls every decoding user for that long, so we lower max_num_tokens to 2,048, which caps the stall near 33 ms, and turn chunking on.

Like the other engines, the runtime overlaps CPU and GPU work. The overlap scheduler launches the forward pass for step n+1 before the CPU has finished checking stop conditions for step n. It is on by default; the documentation notes the cost, one extra decoding step per request, and cites SGLang's zero-overhead scheduler as related work [8].

The capacity scheduler: reserve or overcommit

TensorRT-LLM's default admission policy differs from vLLM and SGLang. With GUARANTEED_NO_EVICT, the capacity scheduler admits a request only if enough KV blocks remain for it to finish: its prompt plus its full max_tokens. A started request is then never paused. The alternative, MAX_UTILIZATION, packs in as many requests as fit now, at the risk of pausing some if the cache fills [9][10]. Figure 3 puts numbers on the difference.

Three bars over a pool of 13,824 blocks of 32 tokens. With guaranteed no evict and max_tokens of 500, each request reserves 79 blocks and 174 requests fit. With guaranteed no evict and clients sending max_tokens of 4,096, each request reserves 191 blocks and only 72 fit, though each uses about 79. With max utilization, requests take blocks as they grow, so about 174 fit at these lengths, but requests can be paused if many run long.

The arithmetic starts from the cache size, which we compute below: 13,824 blocks of 32 tokens. A chat request of 2,000 prompt tokens with max_tokens 500 reserves \lceil 2500 / 32 \rceil = 79 blocks, so 174 requests fit. If the application sends max_tokens 4,096 "to be safe," each request reserves \lceil 6096 / 32 \rceil = 191 blocks and only 72 fit, even though each still uses about 79. The lesson for TensorRT-LLM deployments: set max_tokens realistically in clients, or switch the policy. With 50 users per replica we are well inside either limit.

The paged KV cache and block reuse

The KV cache is paged, in blocks of 32 tokens by default (tokens_per_block). Its size comes from --kv_cache_free_gpu_memory_fraction, default 0.9, which is a share of the memory that is still free after the weights and runtime buffers are allocated [7]. That is a different quantity from vLLM's --gpu-memory-utilization, which is a share of total memory (we set it to 0.90 explicitly; recent vLLM releases default to 0.92). Figure 4 compares the two on our H100.

Two horizontal bars of 79.6 GiB. In the vLLM bar, 0.90 of total memory is the budget: 15 GiB of weights, about 4.6 GiB of activations and CUDA graphs, and about 52 GiB of KV cache, with 8 GiB held back. In the TensorRT-LLM bar, weights and about 4.6 GiB of buffers are allocated first, leaving 60 GiB free; 0.9 of that, 54 GiB, becomes the KV cache, and 6 GiB is left. 54 GiB holds about 442,000 tokens in 13,824 blocks of 32 tokens.

Assume the same 15 GiB of weights and about 4.6 GiB of runtime buffers as in Lesson 3, KV Cache. About 79.6 − 15 − 4.6 = 60 GiB is free, and 0.9 of it is 54 GiB. At 128 KiB per token that is 54 × 8,192 = 442,368 tokens, or 13,824 blocks of 4 MiB (32 tokens × 128 KiB). The actual buffer size depends on the model and settings, so read the cache size from the startup log rather than trusting the estimate.

Prefix reuse is on by default (enable_block_reuse). Blocks of earlier requests stay in a radix search tree, and only leaf blocks are evicted. Eviction is prioritized LRU: every block has a priority from 0 to 100, default 35, all blocks of the lowest priority go before any of the next, and ties go to the least recently used. A per-request retention policy can raise the priority of, say, a system prompt so that it survives bursts of one-off traffic. Evicted blocks can be offloaded to host memory (host_cache_size, default 0) and stay reusable there [11]. An FP8 KV cache is a one-line setting (kv_cache_config: {dtype: fp8}), and Blackwell GPUs add an NVFP4 KV cache [12].

Kernels and Quantization

TensorRT-LLM's main asset is its kernels. NVIDIA writes attention, GEMM, and mixture-of-experts kernels for each new GPU generation, using CUTLASS and hand-tuned code; the XQA kernel, for example, speeds up decode attention for multi-query and grouped-query models [1][13]. Lesson 33, GPU Architecture and Attention Kernels, explains what these kernels optimize. Other engines reuse some of this work: vLLM lists TRTLLM-GEN attention and GEMM kernels among its backends [14], so the engines share more kernels than their names suggest.

Quantization is the other lever, and it depends on the GPU generation (Figure 5). FP8 runs natively on Hopper and Ada Lovelace GPUs in several scaling variants. NVFP4, a 4-bit format that stores one FP8 scale for every 16 values, runs natively on Blackwell [12][15]. Pre-quantized checkpoints come from NVIDIA Model Optimizer and load directly.

A grid with GPU generations as rows (Ada Lovelace, Hopper, Blackwell B200 and B300) and formats as columns (FP8 weights and activations, FP8 KV cache, NVFP4 or MXFP4 weights, NVFP4 KV cache, INT4 AWQ or GPTQ weights). Ada and Hopper support FP8 weights, FP8 KV cache, and INT4 weights but not NVFP4. Blackwell supports all of them. A note gives Llama 3.1 8B weight sizes: 16.1 GB in BF16, 8.0 GB in FP8, about 4.5 GB in NVFP4.

For our model, the weights take 8.03B × 2 bytes ≈ 16.1 GB in BF16, 8.0 GB in FP8, and about 8.03B × 4.5 bits ÷ 8 ≈ 4.5 GB in NVFP4, a 3.5× reduction that matches NVIDIA's own figure [15]. Real checkpoints are somewhat larger because embeddings and a few sensitive layers usually stay in higher precision: the published FP8 checkpoint is about 9.08 GB. On our H100s, FP8 is the format to evaluate first; NVFP4 becomes an option with the B200s. Lesson 13, Quantization - FP8, INT8 and 4-bit, covers accuracy, and Lesson 16 shows how to check it.

Deploying TensorRT-LLM

trtllm-serve

trtllm-serve <model> starts an OpenAI-compatible server on port 8000 with /v1/models, /v1/completions, and /v1/chat/completions, plus /health and /metrics [7]. NVIDIA recommends running it in the release container from NGC. A few dedicated flags cover parallelism and limits, and everything else goes in a YAML file passed with --config, whose keys map to the LLM API's arguments. Explicit flags override the file. Structured output is off until you name a backend: XGrammar or LLGuidance, set in the YAML file [16]. That differs from vLLM and SGLang, where it works out of the box. Lesson 38, Structured Output and Tool Calling, compares the backends.

Observing TensorRT-LLM

Monitoring takes more setup than in the other two engines. The documented /metrics endpoint, in beta, returns JSON iteration statistics such as GPU memory, KV cache blocks in use, and cache hit rate, but only when enable_iter_perf_stats: true is set. Each statistic is handed out once and then removed from a queue, so a single client must poll it [7]. For Prometheus, setting return_perf_metrics: true mounts a second endpoint at /prometheus/metrics with trtllm_-prefixed series, including trtllm_time_to_first_token_seconds, trtllm_e2e_request_latency_seconds, trtllm_request_queue_time_seconds, trtllm_num_requests_waiting, and trtllm_kv_cache_utilization. This endpoint appears in the source code rather than in the serving guide, and the queue and cache gauges are newer than the latency histograms, so check your version [17].

Benchmarking

trtllm-bench measures the runtime without an HTTP server. Its prepare-dataset command writes synthetic requests with chosen input and output lengths, and its throughput and latency commands run them in-process, optionally capped at a concurrency and with streaming to report TTFT and inter-token latency [18]. It is the fastest way to tune max_batch_size and max_num_tokens. To compare engines fairly, though, benchmark the HTTP servers with the same client, for example vllm bench serve or TensorRT-LLM's own benchmark_serving script, as Lesson 12 does.

Triton Inference Server and NVIDIA Dynamo

Two NVIDIA projects sit above the engine, as Figure 6 shows. Triton Inference Server is NVIDIA's general model server. Its TensorRT-LLM backend now has an LLM API path that serves Hugging Face models directly, configured by a model.yaml whose keys map to the LLM API's arguments, and the backend's source has moved into the TensorRT-LLM repository [19]. Teams that already run Triton for other models can add LLMs to the same fleet.

Three stacks side by side. On the left, clients call trtllm-serve directly, which runs one TensorRT-LLM engine. In the middle, clients call Triton Inference Server, whose TensorRT-LLM backend hosts the engine next to other models. On the right, clients call the NVIDIA Dynamo frontend and its KV-aware router, which sends work to separate prefill and decode worker pools running TensorRT-LLM, vLLM, or SGLang, with a planner that scales the pools and a KV block manager that offloads cache to CPU and storage.

NVIDIA Dynamo is an open-source, Apache 2.0 orchestration layer for data-center-scale serving. It does not replace an engine; it runs TensorRT-LLM, vLLM, or SGLang workers and adds disaggregated prefill and decode pools, routing based on worker load and KV cache overlap, a KV block manager that offloads cache from GPU to CPU, SSD, and remote storage, and a planner that resizes the pools against latency targets [20]. Lesson 34, Disaggregated Prefill and Decode, covers it. For a two-GPU deployment like ours, trtllm-serve behind a Kubernetes service is enough.

Strengths and weaknesses

TensorRT-LLM's strength is peak performance on NVIDIA GPUs, especially new ones. NVIDIA tunes its kernels and FP8 and NVFP4 paths for each generation, often supports popular models on release day, and publishes record results for large models on Blackwell [2]. Its admission policy gives predictable latency, since a started request is never paused, and Dynamo and Triton integrate with it closely.

The costs are real. It runs only on NVIDIA GPUs, and its official hardware list runs from the A100 (Ampere) through Ada Lovelace and Hopper to Blackwell parts such as the B200 and DGX Spark [21]. More settings live in YAML files, structured output and Prometheus metrics must be switched on, and the runtime has gone through two architectures in three years, so older guides mislead. Model coverage is narrower than vLLM's, and for a small dense model like ours, the gap in throughput between a well-configured TensorRT-LLM and a well-configured vLLM or SGLang may be modest; only a benchmark on your workload can tell.

Notice how much the engines have converged. All three batch continuously, page the KV cache, reuse prefixes, chunk long prompts, overlap CPU and GPU work, use XGrammar for structured output, and speak the OpenAI API. They differ in defaults, in which workload they were designed around, and in hardware reach.

Which engine fits our deployment?

Figure 7 turns the comparison into a decision. For our deployment, four to seven H100 replicas of Llama 3.1 8B serving chat with a shared system prompt, we choose vLLM. At 50 users per replica we are far from the roughly 170-request memory limit, so latency control matters more than peak throughput, and all three engines give us the same latency tool: a 2,048-token step with chunked prefill. vLLM adds Prometheus metrics with no extra setup, which a two-person team will value, the widest choice of models for the next upgrade, and the option to test non-NVIDIA accelerators later.

A decision flow. First question: must it run on non-NVIDIA hardware? Yes leads to vLLM or SGLang. No leads to the second question: is most prompt volume shared prefix, such as multi-turn chat, agents, or shared documents? Yes leads to SGLang. No leads to the third question: is the fleet large and fixed, and does a benchmark on our workload show at least 20% more throughput at the same p95 latency? Yes leads to TensorRT-LLM. No leads to vLLM.

Two results would change the choice. If the support agent grows until shared prefixes dominate traffic, SGLang's radix cache and cache-aware gateway become worth adopting. And TensorRT-LLM pays off only when its gain buys back whole GPUs. Assume $3.00 per H100-hour. A 20% throughput gain would raise capacity from about 5 to 6 requests per second per H100. The daily peak of 33 requests per second would then need 6 GPUs instead of 7 (33 ÷ 6 = 5.5), and the average of 16.7 would need 3 instead of 4. That saves about one GPU around the clock, 8,760 hours × $3 ≈ $26,000 a year, which must pay for the extra engineering and the lock-in. A fleet ten times larger would save about ten GPUs, roughly $263,000 a year, and easily would. Lesson 12 benchmarks two engines on exactly this workload, and Lesson 20, Cost per Million Tokens, turns throughput into cost.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Why reserve-to-completion admission trades capacity for predictable latency, and how inflated max_tokens values hurt it.
  • KV cache retention priorities: keeping a system prompt's blocks at priority 100 while one-off requests use the default 35 [11].
  • Wide expert parallelism and disaggregated serving for large mixture-of-experts models on Blackwell (Lesson 35, Mixture-of-Experts Serving, and Lesson 34, Disaggregated Prefill and Decode) [1].
  • How NVFP4's two-level scaling (an FP8 scale per 16 values and an FP32 scale per tensor) keeps 4-bit accuracy close to FP8 [15].
  • Why trtllm-bench numbers are higher than HTTP benchmark numbers: no tokenization, networking, or streaming overhead.
  • The trade-off of vendor lock-in: the best kernels for NVIDIA hardware, at the cost of a harder move to other accelerators.

Summary

Mind map summarizing the TensorRT-LLM lesson: the move to a PyTorch runtime, the PyExecutor, admission policies, KV cache sizing, quantization, deployment options, and the three-engine comparison.
  • TensorRT-LLM is NVIDIA's Apache 2.0 library for LLM inference on NVIDIA GPUs. Since v1.0 it runs a PyTorch runtime by default, and the 1.4 release candidates removed the old trtllm-build engine path.
  • Its PyExecutor does in-flight batching with limits of 2,048 requests and 8,192 tokens per step by default; chunked prefill is opt-in, and an overlap scheduler hides CPU work.
  • The default GUARANTEED_NO_EVICT policy reserves blocks for prompt plus max_tokens: 174 chat requests fit on one H100 with max_tokens 500, but only 72 with 4,096.
  • kv_cache_free_gpu_memory_fraction 0.9 is a share of memory left after weights: about 54 GiB, 442,000 tokens, or 13,824 blocks of 32 tokens on our H100. Block reuse uses prioritized LRU.
  • FP8 runs on Hopper and Ada; NVFP4 (4.5 bits per value, about 4.5 GB for Llama 3.1 8B) runs on Blackwell.
  • Deploy with trtllm-serve and a YAML --config, or under Triton or NVIDIA Dynamo; metrics and structured output must be enabled.
  • For our chat deployment of four to seven H100s we choose vLLM; a 20% faster engine would save only about one GPU ($26,000 a year at $3.00 per hour); SGLang wins if shared prefixes dominate, and TensorRT-LLM when a measured gain buys back whole GPUs in a large fleet.

Introduction

A chat answer is read by a person, who forgives a stray sentence or a missing comma. Much LLM output is read by a program instead: a ticket router that expects a JSON object, an extraction job that loads fields into a database, an agent that must name a function and its arguments. To a parser, "almost JSON" is an error. Prompting a model to "reply only with JSON" works most of the time, and most of the time is not good enough for a pipeline that handles millions of requests.

Structured output moves the guarantee from the prompt into the serving engine. At every decode step, the engine knows which tokens could still lead to a valid output and forbids all others. The model can still choose badly among the allowed tokens, but it can no longer break the format. Figure 1 shows the difference for a ticket-classification request.

On the left, unconstrained generation produces a friendly sentence, then JSON with an invented category "payments", a priority written as the word "high", and a trailing comma; the parser fails. On the right, the same request with a JSON schema passes through a grammar mask at every step and produces a valid object with category "billing", priority 2, and a summary; the parser succeeds.

Tool calling builds on the same machinery. The model emits a structured request to run a function, the application runs it, and the result goes back to the model for another turn. Each turn is a new request with its own prefill and decode, so tool use changes the latency of a conversation as much as its capabilities.

In this lesson, we look at how constrained decoding masks tokens, why tokenizers make it harder than it looks, how engines keep the per-token cost near zero, what strict constraints do to quality, and how tool calls flow through an OpenAI-compatible server, with the latency each round trip adds.

Clarifying the Problem

Structured output questions usually start from a pipeline that breaks. Here is a typical exchange:

Candidate: What must the output look like, and who reads it?
Interviewer: Every support ticket gets a JSON object with a category from six fixed values, a priority from 1 to 4, and a one-line summary. A downstream service parses it; a parse failure drops the ticket into a manual queue.

Candidate: How often does that happen today?
Interviewer: About 2% of replies fail to parse: extra prose around the JSON, trailing commas, or categories the model made up.

Candidate: Does the assistant also call tools?
Interviewer: Yes, the chat assistant can look up an order and issue a refund through two functions.

Candidate: Which model, engine, and targets?
Interviewer: Llama 3.1 8B Instruct on vLLM, H100s, and the usual targets: p95 TTFT under 500 ms and p95 TPOT under 25 ms.

The question underneath is: how do we guarantee that every reply parses, without slowing decode or hurting answer quality, and what does each tool call cost the user in latency?

Constrained Decoding

Masking logits one token at a time

At each decode step, the model produces a logit for every token in its vocabulary, 128,256 tokens for Llama 3.1. Constrained decoding adds one step before sampling: it builds a token mask that marks which tokens keep the output a valid prefix of the target format, sets the logits of all other tokens to minus infinity, and samples from what remains [1]. After sampling, the constraint advances its state by the chosen token. Figure 2 works one step.

The output so far is {"category": "billing", "priority": followed by a space. The schema says priority is one of the integers 1 to 4. Six candidate tokens have logits: a quote character 2.1, the digit 3 at 1.8, the word high at 1.5, the digit 2 at 1.2, the digit 5 at 0.9, and null at 0.4. The mask keeps only 3 and 2 and sets the others to minus infinity. Softmax over the two survivors gives 3 a probability of about 0.65 and 2 about 0.35, and the sampler picks 3. The grammar state then moves to expect a comma or closing brace.

Two details matter. The mask only removes options; among the allowed tokens the model's own preferences still decide, which is why the prompt should still describe the format. And the mask is a bitmask of one bit per vocabulary entry, 128,256 bits or about 16 KB per sequence per step, which the engine copies to the GPU and applies to the logits in one cheap kernel.

Automata: finite-state machines and pushdown automata

The constraint's state comes from an automaton compiled from the format. A regular expression, an enum, or a JSON schema without recursion compiles to a finite-state machine (FSM): each state lists the characters that may come next. Outlines made this practical by precomputing, for every FSM state, which vocabulary tokens lead to a valid next state, so that each decode step becomes a table lookup [1]. Figure 3 shows an FSM for our category field next to a case that needs more.

On the left, an FSM for the category field: from the start state an opening quote leads to a state with six branches, one per allowed category such as billing, shipping, or refund, each leading to a closing quote and an accepting state. On the right, a JSON value that nests objects inside arrays inside objects; a pushdown automaton keeps a stack of open brackets, here an object, an array, and an object, and may only close the innermost one. A note says a finite-state machine cannot count arbitrary nesting depth.

Recursive formats, such as JSON with nested arrays of objects, arbitrary JSON, or the grammar of a programming language, are context-free grammars. They need a pushdown automaton (PDA), an automaton with a stack that remembers which brackets are open. The stack is what makes CFG masks expensive: whether a token is legal can depend on the whole stack, not just the current state, so it cannot always be looked up in a table built ahead of time.

The tokenizer alignment problem

Grammars are written in characters, but models emit tokens, and the two do not line up. A single token can span a grammar boundary, as Figure 4 shows. Llama 3.1's tokenizer splits {"category": "billing" into six tokens, {", category, ":, ", billing, and ", and three of them cover pieces of two grammar elements. Longer objects add tokens such as ", and "}. The mask must therefore ask, for each token, whether its whole character string keeps the output valid from the current state, which is much harder than checking one character.

The string {"category": "billing" is shown twice. The top row splits it into grammar elements: open brace, quote, the key category, quote, colon, space, quote, the value billing, quote. The bottom row shows Llama 3.1's actual tokens: {", category, ":, space-quote, billing, quote. Three tokens span two grammar elements: {" covers the brace and the opening quote, ": covers the closing quote and the colon, and space-quote covers the whitespace and the opening quote. A note warns that forcing the grammar's boundaries, for example emitting the quote and the colon as separate tokens, produces token sequences the model rarely saw in training.

Getting this wrong has two costs. If the mask is too strict and allows only tokens that end exactly on grammar boundaries, the model is pushed into unusual tokenizations it rarely saw in training, and accuracy drops. The DOMINO paper measured this effect and showed that a subword-aligned constraint avoids it [4]. If the mask is too loose, invalid output gets through. Modern libraries handle alignment by matching each token's full byte string against the automaton, usually with a prefix tree over the vocabulary so that tokens sharing a prefix are checked together.

In vLLM, --structured-outputs-config.backend defaults to auto, which the documentation describes as an opinionated choice based on the request that may change between releases [5]. In the current source, auto tries XGrammar first and falls back to LLGuidance, or in a few cases Outlines, when XGrammar rejects the schema [6]. SGLang uses XGrammar unless --grammar-backend names Outlines or LLGuidance [7]. TensorRT-LLM supports XGrammar and LLGuidance through its guided_decoding_backend setting, which is off by default (Lesson 11, TensorRT-LLM) [8]. The LLGuidance repository reports that it powers OpenAI's Structured Outputs for JSON Schema [3].

Hiding the per-token cost

Masks cost CPU time, and CPU time spent between decode steps adds directly to TPOT. Take LLGuidance's figure of about 50 µs per sequence per token. A replica decoding 53 streams, one GPU's share of our traffic at the latency targets (Lesson 19, GPU Utilization), needs about 53 × 50 µs ≈ 2.7 ms of mask work per step. If that work ran on one core after the forward pass, it would stretch a 21 ms step by 13%. Engines avoid paying it with four techniques, shown in Figure 5:

Two timelines of three decode steps. In the serialized timeline, each 21 ms forward pass is followed by 2.7 ms of mask computation on the CPU before sampling, so each step takes about 23.7 ms. In the overlapped timeline, the CPU fills the masks for the next step on several threads while the GPU runs the forward pass, and the mask is ready when the logits are, so each step stays at about 21 ms. A separate note shows a first request with a new schema paying a one-time compile before prefill, while later requests with the same schema hit the compiled-grammar cache.
  • Precompile. XGrammar checks the context-independent tokens of every grammar state once, at compile time, and stores the results; at runtime only the small set of context-dependent tokens needs the stack [2].
  • Cache compiled grammars. Most applications send the same few schemas again and again. vLLM keeps compiled XGrammar grammars in a cache sized by VLLM_XGRAMMAR_CACHE_MB and compiles new ones asynchronously in a thread pool, so a request with a new schema waits for its compile without blocking the rest of the batch [6].
  • Parallelize. vLLM fills the bitmasks for large batches on a pool of threads rather than one [6].
  • Overlap with the GPU. A sequence's mask for the next step depends only on the tokens it has already produced, so the CPU can compute it while the GPU runs the forward pass. XGrammar was designed with this overlap in mind and reports near-zero end-to-end overhead for structured generation [2].

The first request with a new schema still pays the compile in its TTFT, so measure first-use and cached latency separately. The vLLM team's introduction to structured decoding explains the V1 design goal of computing masks once, at the scheduler level, instead of in every GPU worker, so that one request's grammar does not block the rest of the batch [9].

Jump-forward decoding

Constraints sometimes leave exactly one option: after {"category": in a schema with fixed key order, the next key's name is fully determined. SGLang's jump-forward decoding exploits this: it compresses chains of forced transitions in the automaton and appends the whole forced string in one prefill step instead of decoding it token by token, re-tokenizing the text to avoid unnatural token boundaries [10][11]. LMSYS reported up to 2× lower latency and 2.5× higher throughput on JSON workloads when it was introduced in 2024 [10]. XGrammar exposes the same capability as find_jump_forward_string, and SGLang's grammar backends still implement a jump-forward interface, but neither SGLang's nor vLLM's current documentation presents it as a feature you can switch on, so do not count on it when sizing; speculative decoding gives a similar benefit for forced tokens, because they are easy to predict (Lesson 15, Speculative Decoding).

Quality: strict formats and good prompts

A constraint guarantees syntax, not sense. A study titled "Let Me Speak Freely?" found that format restrictions lowered LLM reasoning accuracy, more so for stricter formats [12]. A response from the Outlines team argued that the comparison used inconsistent prompts and that structured generation matches or beats free generation when both conditions get the same, well-designed prompt [13]. Both points lead to the same practice:

  • Describe the format in the prompt too. The mask stops the model from leaving the format, but a model that expects the format puts high probability on good tokens to begin with.
  • Put reasoning before answers. If a task needs thought, add a reasoning string field before the category field, so the model writes its explanation before committing to a label.
  • Prefer enums to free text for anything a program branches on, and avoid tight length limits that force the model to stop mid-sentence.
  • Know your library's coverage. Engines support different subsets of JSON Schema; JSONSchemaBench tested six frameworks on 10,000 real-world schemas and found that coverage and speed differ [16]. Test your actual schemas.

Tool Calling

The round trip

The client sends the tool definitions, as JSON schemas, with the conversation. The chat template inserts them into the prompt, where they count as prompt tokens on every turn. The model may answer in text, or emit a tool call: a function name and JSON arguments in the model's own format. The server parses that output into the OpenAI tool_calls field and finishes the response with finish_reason: "tool_calls". The client runs the function and sends the result back as a message with role: "tool" and the call's tool_call_id, and the model continues [17]. Figure 6 follows one order lookup.

A timeline with three phases. Request 1: a 2,000-token prefill of about 65 ms, then about 30 tokens of tool call decoded in about 0.75 s at 25 ms per token. Then the client runs lookup_order for an assumed 300 ms. Request 2: a prefill of 2,530 tokens, about 82 ms without prefix caching or about 17 ms for the 530 new tokens with it, followed by the streamed answer. The user's first visible token arrives after about 1.2 s, against a 500 ms TTFT target. A note says the same round trip at 32K tokens of context would re-prefill about 1.06 s without prefix caching.

Put numbers on it with Lesson 1's prefill estimate of about 32 µs per token for Llama 3.1 8B on an H100 (2 × 8.03 billion FLOPs per token at 50% of 989 TFLOPS):

  • Turn 1: prefill 2,000 tokens, about 65 ms, then decode a 30-token tool call at the 25 ms TPOT target, about 0.75 s.
  • Tool: the client runs lookup_order; assume 300 ms.
  • Turn 2: prefill the whole conversation again, now 2,530 tokens with the call and a 500-token result, about 82 ms. With prefix caching, only the 530 new tokens are computed, about 17 ms (Lesson 24, Prefix Caching).

The first word the user sees arrives after about 65 + 750 + 300 + 82 ≈ 1.2 s, well past the 500 ms TTFT target, even though every individual request met it. At this context length, prefix caching saves only about 65 ms; the tool-call decode and the tool itself dominate. In a 32K-token conversation the re-prefill grows to about 1.06 s per round trip, and the cache, together with routing that returns the conversation to the replica holding it (Lesson 25, Request Routing), becomes essential. Each round trip also re-enters the queue, so under load the queueing delay of Lesson 4, Time to First Token, is paid once per turn.

Measure agent latency per conversation, not per request: count the turns, and add each turn's queueing, prefill, tool-call decode, and tool time. An agent that makes three tool calls pays four TTFTs.

Server side: parsers and strictness

vLLM turns tool calling on with --enable-auto-tool-choice, picks the parser for the model's tool-call format with --tool-call-parser (llama3_json for Llama 3.1, hermes for Hermes and Qwen models, among many), and usually needs a matching --chat-template that handles tool-role messages [14]. How reliable the call is depends on tool_choice:

  • A named function or "required": vLLM constrains the output with the structured outputs backend, so the call always parses, though the documentation is careful to say "validly-parsable", not high-quality [14].
  • "auto": the model decides whether to call a tool, and by default vLLM extracts calls from the raw text, so arguments can occasionally be malformed. Setting strict: true on a tool, or raising the server-wide floor with --tool-strict-level function or parameter, makes vLLM constrain the call's structure in auto mode too [14].
  • "none": no tool calls, text only.

Model limits still apply: vLLM's documentation notes that Llama 3 models do not support parallel tool calls and that smaller Llama models often fail to emit tool calls correctly [14]. SGLang offers the same flow with --tool-call-parser llama3 [7]. Whatever the engine, validate arguments before running a function; the OpenAI SDK's own documentation warns that a model may produce invalid JSON or hallucinate parameters [17].

Which approach fits our deployment?

For ticket classification, we use response_format with a JSON schema whose category is an enum of the six values and whose priority is one of the integers 1 to 4, and we leave vLLM's backend on auto. The 2% parse failures go to zero by construction, provided max_tokens leaves room for the whole object, since a reply cut off by the length limit is still invalid. The schema never changes, so after the first request it is always compiled and cached, and the mask work hides behind the forward pass; we confirm with the measurement script below that p95 TPOT stays under 25 ms at production concurrency. We keep the format description in the system prompt and check classification accuracy on a labeled set before and after, since the constraint fixes syntax, not judgment.

For the assistant, we enable --enable-auto-tool-choice --tool-call-parser llama3_json and mark both tools strict: true, so auto-mode calls are constrained too. Because a lookup adds roughly 1.2 s before the user sees a word, the client streams a short status message while the tool runs, and we keep tool results compact, since every result token is prefilled on the next turn and stays in the context for the rest of the conversation. A refund is a side effect, so the client asks the user to confirm before executing it, no matter how well-formed the call is.

In Practice

The first tab starts vLLM with tool calling and the default structured outputs backend, plus the SGLang equivalent. The second sends a schema-constrained classification and then runs a full tool round trip with the OpenAI client. The third measures the latency cost of a schema: it compares TTFT and TPOT with and without response_format and reports the first, uncached request separately.

Please fix it today."}, ], response_format={"type": "json_schema", "json_schema": {"name": "ticket", "schema": ticket_schema}}, ) print(json.loads(reply.choices[0].message.content)) # 2) Tool calling: the model asks, the client executes, the result goes back. tools = [{ "type": "function", "function": { "name": "lookup_order", "description": "Get the status and charges of an order.", "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"], "additionalProperties": False}, "strict": True, }, }] def lookup_order(order_id: str) -> dict: return {"order_id": order_id, "status": "delivered", "charges": [49.0, 49.0]} # stub messages = [{"role": "user", "content": "Why was I charged twice for order 8812?"}] first = client.chat.completions.create(model=MODEL, messages=messages, tools=tools, tool_choice="auto") msg = first.choices[0].message messages.append(msg.model_dump(exclude_none=True)) for call in msg.tool_calls or []: if call.function.name != "lookup_order": raise ValueError(f"unexpected tool {call.function.name}") args = json.loads(call.function.arguments) # Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Reasoning models: vLLM applies the constraint only after the reasoning section ends when a --reasoning-parser is set, so the model can think freely and answer in format [5].
  • Structured output with speculative decoding: the grammar must check and roll back draft tokens, which vLLM's XGrammar backend supports [6].
  • Structural tags, which constrain only the tool-call section of an otherwise free-text answer; vLLM uses them for strict tool calls in auto mode [14].
  • Security: tool results are untrusted input that can contain instructions; never let a model's tool call trigger a side effect without authorization checks in the application.
  • Token accounting: tool definitions and results add prompt tokens on every turn, and a tool_calls finish reason marks a request that will be followed by another (Lesson 31, Per-Request Token Accounting).

Summary

Mind map summarizing the lesson: constrained decoding with token masks, automata and tokenizer alignment, the libraries and how engines hide their cost, quality practices, and the tool-calling round trip and its latency.
  • Constrained decoding masks, at every step, the logits of tokens that would break the format; the model still chooses among the allowed tokens.
  • Regexes, enums, and flat schemas compile to finite-state machines; nested formats need a pushdown automaton with a stack. Tokens span grammar boundaries, so each token's full string must be checked.
  • XGrammar (SGLang's default and vLLM's first choice), LLGuidance (vLLM's fallback, about 50 µs per token), and Outlines do the work; precompiling, caching, threading, and overlap with the GPU keep the cost near zero.
  • Unhidden, 53 streams at about 50 µs each would add about 2.7 ms, 13%, to a 21 ms step; a new schema also pays a one-time compile in TTFT.
  • Constraints guarantee syntax, not quality: describe the format in the prompt, put reasoning fields first, and evaluate on labeled data.
  • A tool call is a round trip: decode the call, run the tool, re-prefill the conversation. One lookup pushes the first visible token to about 1.2 s; prefix caching matters most for long contexts.

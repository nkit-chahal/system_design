Introduction

A model that serves well on a good day is half the job. GPUs fail, engines hang, nodes disappear, and every few weeks someone ships new weights, a new engine version, or a changed setting. Reliability is the discipline of keeping the service within its objectives through all of that, and rollouts are how we change the service without breaking it.

LLM serving makes both harder than for a typical web service. Each replica holds a GPU that costs dollars per hour, so spare capacity is expensive. A request lives for seconds and streams its answer, so a failure cuts users off mid-sentence. Replicas are packed onto 8-GPU servers, so one hardware fault can remove several of them at once. And a release can be "healthy" by every infrastructure measure while producing worse answers. Figure 1 shows the nested failure domains we must plan for, each with its own defense.

Nested dashed boxes: a GPU inside an 8-GPU node, inside an availability zone, inside a region, with a release shown as a domain that cuts across all of them. A GPU fault removes one replica and is handled by health checks and N+1 capacity. A node failure removes every replica on the node and needs spreading across nodes. A zone outage needs replicas in several zones. A regional outage needs a second region or a fallback model or API. A bad release can hit every replica at once and needs canaries and automated rollback.

In this lesson, we catalog how GPU inference fails, look at what health checks really prove, drain and retry streaming requests safely, roll out models and engines with canary, blue/green, and shadow traffic, size capacity for failure, and tie it all to SLOs and error budgets. We finish by choosing a reliability design for the running example.

Clarifying the Problem

Reliability questions usually start after the first outage. Here is a typical exchange:

Candidate: What are we running, and where?
Interviewer: Llama 3.1 8B Instruct on vLLM, one replica per H100, on Kubernetes in one cloud region with three availability zones. The GPU nodes are 8-GPU H100 servers.

Candidate: How much traffic, and what can one replica carry?
Interviewer: About 16.7 requests per second on average and 33 at the daily peak. Load tests say about 5 requests per second per H100 within our latency targets.

Candidate: What are the objectives?
Interviewer: p95 time to first token under 500 ms, p95 time per output token under 25 ms, and 99.9% of requests succeeding over 30 days.

Candidate: What went wrong recently?
Interviewer: A GPU node failed during the afternoon peak and took four replicas with it. A week later, a model update changed the chat template, and answers degraded for two hours before anyone noticed.

Candidate: How often do we release, and what can we spend?
Interviewer: New weights or engine versions about every two weeks. We can add GPUs, but we want to know what each one buys. We have a hosted API contract we could use as a fallback.

The question underneath is: how many replicas, placed where, with which checks and release process, keep us within a 99.9% objective through hardware faults and bad releases, and what does that cost?

Hardware faults are routine at scale

GPUs fail far more often than CPUs in ordinary servers. Meta reported that during a 54-day snapshot of Llama 3 pre-training on up to 16K H100s, there were 419 unexpected interruptions, about 78% of them attributed to confirmed or suspected hardware; faulty GPUs (148) and GPU HBM3 memory (72) were the two largest causes [1]. That is roughly one GPU or HBM fault per 4,000 GPU-days. Training is harsher than inference, so treat the number as an order of magnitude, but even a 24-GPU serving fleet should expect a few GPU faults a year, and a large fleet sees them weekly.

The driver reports faults as XID error codes, which the NVIDIA XID catalog describes: 48 is a double-bit ECC error, 79 means the GPU has fallen off the bus, 74 is an NVLink error, and 94 and 95 are contained and uncontained memory errors [2]. Lesson 30, GPU Metrics, shows how to export and alert on them. The serving lesson is simpler: a fatal XID means the node cannot be trusted, so automation drains it at once, and capacity planning assumes that it will happen at the worst moment.

Software that stops making progress

The most dangerous failures are the quiet ones. In a replica that spans several GPUs with tensor parallelism (Lesson 18), every step ends with collective operations across the GPUs. If one GPU or link stalls, the others wait inside the collective, and the replica stops producing tokens while its process, its port, and often its health endpoint all look fine. Runaway requests are a milder version: a model that never emits an end token keeps generating until the length limit, holding KV cache that other users need. A server whose process is alive is not necessarily a server that is doing work.

Detecting and Containing Failures

What a health check really proves

Kubernetes offers three probes with different consequences [3]. A startup probe gives a slow-loading container time before the other probes start (Lesson 23, Cold Starts). A liveness probe restarts the container when it fails. A readiness probe removes the pod from Service endpoints when it fails, without restarting it. Getting them wrong is a classic outage: a liveness probe that times out under heavy load restarts healthy replicas exactly when they are needed, and their cold starts turn a slowdown into an outage.

vLLM's /health endpoint calls the engine's check_health(); it returns 200 if that succeeds and 503 if the engine core has died [4]. It does not run the model. A GPU that faults while the process stays up can keep returning 200, and a proposal to add a readiness check that runs a one-token forward pass was closed without being merged [5]. Figure 2 shows what each layer of checking proves.

A ladder of five rungs. The process is running: the container is alive. /health returns 200: the engine core has not died. Readiness passes: the pod receives traffic. A synthetic canary prompt returns the expected answer within a TTFT budget: the GPU computes correct tokens now. Real-traffic SLIs such as error rate, TTFT, tokens per second and output quality: users are being served well. Each rung costs more and proves more.

We use each rung for what it can carry. /health drives liveness and readiness because it is cheap and cannot flap under load. A synthetic canary prompt runs outside the probes: every 30 seconds, a prober sends each replica directly a fixed prompt with a known answer, such as "What is 17 + 25? Answer with the number only.", with temperature 0 and max_tokens 8, and checks the answer and its TTFT. Two consecutive failures mark the replica for draining through automation, with a limit on how many replicas it may drain at once so that a prober bug cannot empty the fleet. A progress watchdog alerts when a replica has running requests but has produced no tokens for two minutes, which catches the collective hang above.

A liveness probe that generates tokens competes with real traffic, times out on a busy replica, and restarts it at the worst moment. Keep liveness cheap; prove generation with a separate prober that acts through rate-limited automation.

Draining and shutting down

Planned removals (scale-down, rollouts, node maintenance) should never cut a stream. When a pod is deleted, Kubernetes marks its endpoints as terminating and not ready, so load balancers stop sending it new requests, runs the preStop hook, then sends SIGTERM, and kills the container when terminationGracePeriodSeconds (30 seconds by default) runs out [6]. Lesson 22, Autoscaling, built the drain hook and the 300-second grace period that our longest generations need. Two additions matter for reliability. First, a replica found unhealthy by the prober should flip its readiness before anything else, so that it stops receiving traffic while its streams finish. Second, unplanned failures allow no drain at all: when a node dies, its streams are simply gone, and only retries can help.

Retries and idempotency for streamed responses

Lesson 25, Request Routing, set the core rule: retry on another replica only before the first token reaches the client, within a retry budget. After the first token, a blind retry would send the user a second, different beginning. Three practices cover the rest:

  • Resume rather than restart. A client that kept the partial answer can send it back as the final assistant message and ask the model to continue. vLLM supports this with continue_final_message, which formats the chat so that the last message is open-ended [7]. The continuation is coherent but not identical to what the failed replica would have written.
  • Idempotency keys for side effects. When a response triggers actions, such as a tool call that sends an email (Lesson 38, Structured Output and Tool Calling), the gateway stores a client-supplied request ID and returns the stored result for duplicates instead of generating again. Batch jobs get the same property from per-request IDs (Lesson 39, Batch and Offline Inference).
  • Fail fast and visibly. A stream that stops should end with an explicit error event, not a silent close, so the client knows to resume or to show an error.

Rolling Out Models and Engines

A release is a bundle

Our second incident, a changed chat template, was a release problem, not a hardware one. An LLM's behavior depends on more than its weights: the tokenizer and chat template, the default sampling settings in generation_config.json, the engine version and its kernels, the engine flags, and the driver underneath. vLLM loads generation defaults from the model by default (--generation-config auto), so a model repository update can silently change the default temperature [8]. Figure 3 shows the bundle we version together.

A release ID such as chat-2026-10-20 groups six pinned parts: the engine image by digest, the model weights by Hugging Face commit with --revision, the tokenizer and chat template with --tokenizer-revision, generation defaults with --generation-config, engine flags such as --max-model-len and --max-num-seqs, and the node pool's driver version. A rollback restores all six at once.

We pin each part: the container image by digest, the weights with --revision set to a commit hash, the tokenizer with --tokenizer-revision [8], and the flags in the same manifest. Better still, we copy the pinned weights into our own storage, which also speeds cold starts (Lesson 23). A release then has one ID, every replica reports it as a label on its metrics, and rolling back means restoring one manifest rather than remembering which of six things changed.

Canary, blue/green, and shadow traffic

Three strategies trade GPU cost against risk, as Figure 4 and Table 2 show.

Canary: the router sends 12.5% of traffic to one new replica and 87.5% to seven old replicas, needing one extra GPU at most. Blue/green: a full second fleet of seven new replicas is started, then the router switches all traffic at once, needing twice the GPUs during the switch. Shadow: live requests go to the old fleet and a copy goes to a new replica whose responses are discarded, needing extra GPUs for the copies and carrying no user risk.
  • Canary: a small share of live traffic goes to the new release while the rest stays on the old one, and the share grows only if the canary's metrics hold. With the Gateway API, an HTTPRoute splits traffic by weight between two backends [9], and controllers such as Argo Rollouts automate the steps, the analysis, and the rollback [10].
  • Blue/green: a complete second fleet runs the new release, and the router switches all traffic at once, with an instant switch back. It is simple and fast to roll back, but needs twice the GPUs during the switch, which is often impossible at peak. Running it at night, when the fleet is 3 replicas instead of 12, costs 3 extra GPUs for an hour.
  • Shadow (mirrored) traffic: the gateway copies live requests to the new release and discards its responses. The Gateway API's RequestMirror filter does this, and the gateway must ignore the mirror's responses [11]. Users see no risk, so shadowing is the safe way to test a new engine version's latency and stability on real prompts. It cannot measure how users react, and mirrored requests must never trigger tool calls with side effects.

One detail is specific to GPUs: the canary must carry a normal load. A replica that receives 1% of traffic runs tiny batches and looks faster than it will at full load (Lesson 19, GPU Utilization). We give the canary one replica's fair share, 1 of 8 replicas or 12.5%, so that its TTFT and TPOT can be compared with the old replicas at equal load.

Gates on quality, latency, and cost

A canary is only as good as the gates that judge it. Figure 5 shows the pipeline we use, with a gate before every increase in exposure.

A new release passes an offline evaluation gate (task accuracy, safety, format checks), then a shadow stage on mirrored traffic (errors, latency), then a canary at 12.5% for 30 minutes, then 50%, then 100%. Each canary step checks quality signals (refusal rate, output length, thumbs-down rate, judge score on samples) and latency and cost signals (p95 TTFT, p95 TPOT, error rate, tokens per request). Any failed check triggers an automated rollback to the pinned previous release.
  • Offline evaluations first. Before any user sees the release, it runs the regression suite: task accuracy on a labeled set, safety prompts, and format checks such as valid JSON for tool calls. This is a batch job on the critical path (Lesson 39). The chat-template bug in our incident would have failed here.
  • Online quality signals. Some regressions only show up on real traffic. Cheap proxies compared between canary and baseline catch many of them: refusal rate, mean and p95 output length, the share of answers that hit max_tokens, user thumbs-down rate, and an LLM judge scoring a sample of paired responses.
  • Latency and cost. p95 TTFT and TPOT within the SLO and close to the baseline, error rate, and tokens per request, because a model that answers at twice the length doubles the cost per request (Lesson 31, Per-Request Token Accounting).

The value of the gate is easy to quantify with the error budget. A 99.9% objective over 30 days of our traffic, about 43.3 million requests, allows about 43,300 failed requests. A bad release that reaches all traffic for 30 minutes at the average rate affects 16.7 × 1,800 ≈ 30,000 requests, 69% of the month's budget. On a 12.5% canary with a 30-minute window, it affects about 3,800 (8.7%); with automated rollback after 10 minutes, about 1,250 (2.9%). Counting only hard failures understates the benefit, since degraded answers do not show up as errors at all.

Capacity for Failure

N+1 is per failure domain

Lesson 21 added one spare replica so that the fleet survives the loss of any one GPU: N+1 redundancy. With one replica per GPU and 8 GPUs per node, the failure we actually saw removes several replicas at once, so the spare must be counted in the unit that fails. At peak we need N = \lceil 33 \div 5 \rceil = 7 replicas. If the replicas are spread evenly over k nodes and any one node may fail, the other k - 1 nodes must hold all N:

\text{replicas per node} = \left\lceil \frac{N}{k-1} \right\rceil, \qquad \text{total replicas} = k \times \left\lceil \frac{N}{k-1} \right\rceil Bars show capacity left after the worst single-node failure for five layouts, against a dashed line at the 33 requests per second peak. Eight replicas on one node: 0 left. Eight replicas as 4 plus 4 on two nodes: 20 requests per second left, short of the peak. Fourteen replicas as 7 plus 7 on two nodes: 35 left. Twelve replicas as 4 plus 4 plus 4 on three nodes in three zones: 40 left. Ten replicas as 2 per node on five nodes: 40 left.

Figure 6 applies the formula. Lesson 21's N+1 rule, 7 + 1 = 8 replicas, packed on one node survives a GPU fault but not a node failure, which leaves nothing; split 4 + 4 over two nodes, it leaves 20 requests per second, 61% of the peak, which is what happened in our incident. Two nodes need 7 each (14 replicas), three nodes need 4 each (12), and five nodes need 2 each (10). Spreading over more nodes lowers the total, but only pays if the rest of each node's GPUs do useful work.

Zones, regions, and the GPU capacity reality

The same arithmetic applies one level up. Placing one node in each of three zones turns the three-node layout into one that also survives a zone outage, at no extra cost: losing any zone leaves 8 replicas, 40 requests per second. Kubernetes topology spread constraints keep replicas balanced across zones, and a PodDisruptionBudget keeps voluntary disruptions from taking several at once.

Regions are different, because GPUs are scarce. A failover plan that assumes the second region can start 7 H100s on demand during an outage is a hope, not a plan: when a region fails, many customers fail over at once and compete for the same GPUs. There are three honest options. Reserved standby capacity in a second region costs about 7 × 730 × $3.00 ≈ $15,300 a month at our assumed price. Active-active serving splits traffic across two regions, each sized to carry the whole peak, which doubles the fleet. Degraded fallback keeps the product up with less: a smaller or quantized model on whatever GPUs remain (Lesson 13, Lesson 14), or a hosted API. At the assumed API price of $0.0007 per request from Lesson 20, a four-hour regional outage at peak costs 33 × 3,600 × 4 ≈ 475,000 requests, or about $330.

When asked about multi-region failover for GPU serving, say that spare GPUs in the other region are not guaranteed during a regional event. Then compare reserved standby, active-active, and a fallback model or API, with a cost for each.

Incident response and error budgets

Detection and response tie back to the SLOs of Lesson 28, p50, p95 and p99 Latency. With a 99.9% objective, the Google SRE workbook recommends paging when the error budget burns 14.4 times faster than sustainable over both a 1-hour and a 5-minute window, which spends 2% of a 30-day budget in an hour, and opening a ticket at a burn rate of 1 over 3 days [12]. For us, a 14.4× burn is a 1.44% error rate, about 870 failed requests in an hour at average traffic.

When the page fires, the order of work is fixed: mitigate first, diagnose later. If a release is in progress, roll it back; if one replica or node is the outlier, drain it; if the fleet is short of capacity, shed low-priority traffic (Lesson 26, Rate Limiting) or overflow to the fallback. Then find the cause and write a blameless postmortem. The error budget also governs the release cadence: an example policy in the SRE workbook halts all changes other than P0 issues and security fixes once the budget for the preceding four weeks is spent [13]. For a service that changes its model every two weeks, that policy is what keeps reliability and velocity in balance.

A bad release on a 12.5% canary rolled back after 10 minutes spends about 1,250 requests, 2.9%. The same canary noticed after 30 minutes spends about 3,760, 8.7%. A bad release at 100% for 30 minutes spends about 30,060, 69%. A marker at 2% shows what a 14.4 times burn spends in one hour, the threshold for paging.

Figure 7 puts the two incidents from the interview on the same scale. A node failure with the right spare capacity costs at most the streams that were in flight: 4 replicas × 53 streams = 212 requests, 0.5% of the budget. The unguarded release cost far more, which is the usual pattern: once hardware failures are handled by spreading and spares, changes become the main source of lost budget.

Which reliability design fits our deployment?

We choose three GPU nodes, one per zone, with up to 4 chat replicas each: 12 H100s for chat at peak, which leave 40 requests per second after losing any node or zone. Off-peak, the autoscaler keeps at least half of current demand in each zone, so the night load of 8 requests per second runs on 3 replicas instead of 2. The other GPUs on each node run batch work at a low PriorityClass (Lesson 39), so a replacement replica can start there in about 3 minutes by preempting batch work (Lesson 22). The extra 4 H100s at peak cost about $12 an hour at our assumed price.

Around that capacity: /health for liveness and readiness, a synthetic canary prober and a progress watchdog that drain bad replicas automatically, a preStop drain with a 300-second grace period, and retries only before the first token. Releases are pinned bundles that pass offline evaluations, a shadow stage for engine upgrades, and a 12.5% canary gated on quality, latency, and cost with automated rollback. For a regional outage, we fall back to the hosted API, about $330 for a four-hour peak outage instead of $15,300 a month of standby GPUs, after confirming that its quality passes our evaluation set and that the contract allows our data. Lesson 39's 7-GPU fleet, by contrast, would survive no node failure at peak.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Larger replicas widen the blast radius: a Llama 3.1 70B replica with tensor parallelism of 4 loses all four GPUs when one fails, so N+1 costs a whole replica (Lesson 21).
  • Chaos testing: deliberately killing a replica, a node, or a zone during a load test confirms that the spare capacity and retries work as planned.
  • Release-aware metrics: labeling every metric with the release ID makes canary comparisons and post-incident analysis straightforward (Lesson 32's dashboard).
  • Silent data corruption: some faulty GPUs produce wrong numbers without any error code, which only output checks such as the synthetic prober can catch.
  • Graceful degradation inside the product, such as shorter max_tokens or disabling expensive features during an incident, buys capacity without an outage (Lesson 26).
  • Prefix-cache-aware routing changes failure behavior: when a replica dies, its cached prefixes move to other replicas and their prefill load rises for a while (Lesson 24, Lesson 25).

Summary

Mind map summarizing the reliability lesson: failure modes, health checks, draining and retries, rollout strategies, capacity for failure, and error budgets.
  • GPU inference fails through hardware faults (XID and ECC errors), hangs that leave the process alive, runaway requests, driver mismatches, bad releases, and missing capacity. Hardware faults are routine at scale, about one per 4,000 GPU-days in Meta's training fleet.
  • vLLM's /health proves the engine core is alive, not that it computes correct tokens. Add a synthetic canary prompt and a progress watchdog, and keep generation out of liveness probes.
  • Drain planned removals with readiness, a preStop hook and a long grace period; retry only before the first token, resume with the partial answer, and use idempotency keys for side effects.
  • A release pins the image, weights, tokenizer, generation defaults, flags and driver together. Canary at one replica's share, gate on quality, latency and cost, and roll back automatically.
  • N+1 must be counted per failure domain: at 7 replicas needed for the 33 requests per second peak, three nodes in three zones with 4 replicas each survive a node or zone loss with 40 requests per second left.
  • Spare GPUs in another region are not guaranteed; compare reserved standby (about $15,300 a month) with a fallback API (about $330 for a four-hour peak outage).
  • Under a 99.9% objective, a 30-minute bad release at full traffic spends 69% of the monthly budget; a canary with 10-minute automated rollback spends about 3%.

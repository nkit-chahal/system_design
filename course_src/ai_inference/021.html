Introduction

Capacity questions often arrive as one sentence: "How many GPUs do we need to serve 1,000 requests per minute under a 2-second latency SLA?" The sentence hides three unknowns: what the 2 seconds measure, how long the responses are, and how much work one GPU can do while keeping the promise. A guess can be off by a factor of three in either direction.

This lab turns the sentence into a number that traces back to stated assumptions, then checks the number with a load test. Figure 1 shows the flow.

Five boxes in a row: pin down the SLA (p95 end-to-end at most 2 s, which leaves 10 ms per token), traffic (1,000 requests per minute is 16.7 per second), one GPU's capacity (at most 4.12 requests per second within 10 ms per token), GPU count (ceiling of 16.7 divided by 3.30, plus one spare, is 7 H100s), and a load test with vllm bench serve that compares p95 latency to 2 s. A feedback arrow runs from the load test back to the GPU capacity box: measured latency recalibrates the efficiency assumptions.

In this lab, we fix the meaning of "2 seconds" in a Candidate/Interviewer exchange, apply Little's law, find the largest batch that meets the per-token budget using the decode model of Lesson 3, KV Cache, and Lesson 5, Tokens per Second, count GPUs with an N+1 spare, repeat the exercise for Llama 3.1 70B with tensor parallelism, write a small calculator, and validate it with vllm bench serve at a fixed request rate.

Step 1: Pin Down the SLA

Every number later in the lab depends on what the 2 seconds measure, so we settle it first. Here is a typical exchange:

Candidate: Which model and hardware are we planning for?
Interviewer: Llama 3.1 8B Instruct in BF16 on H100 SXM 80 GB GPUs, served with vLLM.

Candidate: What does the traffic look like?
Interviewer: 1,000 requests per minute on average. Over a day it swings between about 8 and 33 requests per second, but size for the average first. Each prompt is about 2,000 tokens: instructions plus a customer's support ticket.

Candidate: Does "2 seconds" mean the time until the first token appears, or the time until the whole answer is back?
Interviewer: The whole answer. Our agent tool receives a JSON object with a draft reply and shows it all at once. Nothing is streamed.

Candidate: Then the output length decides almost everything. How long are the answers?
Interviewer: About 100 tokens on average. We set max_tokens to 150.

Candidate: Is 2 seconds a limit for every request, or a percentile?
Interviewer: The 95th percentile, measured at our API gateway over any five-minute window.

Candidate: What failures must we survive without breaking the SLA?
Interviewer: The loss of any one GPU.

The question underneath is: how many requests per second can one H100 complete in under 2 seconds when an answer can be 150 tokens long, and how many H100s does that make once we add room for bursts and one failure?

Two readings of "2 seconds"

A request's end-to-end latency is the time to the first token plus one decode step for each further token (Lesson 4, Time to First Token). The first token comes from prefill, so strictly there are n_{\text{out}} - 1 decode steps; at 150 tokens the difference is under 1%, and we ignore it:

T_{\text{e2e}} \approx \text{TTFT} + n_{\text{out}} \times \text{TPOT}

Under an end-to-end SLA, this caps the output length for any given speed, or the speed for any given output length:

n_{\text{out}} \le \frac{2\,\text{s} - \text{TTFT}}{\text{TPOT}}

We give TTFT a p95 allowance of 0.5 s, which covers the 65 ms prefill (Step 3) plus queueing, tokenization, and the network. That leaves 1.5 s for 150 tokens: a per-token budget of 10 ms. Figure 2 compares it with the streamed reading, where the SLA covers only the first token.

Two timelines. In the end-to-end reading, a 0.5 s TTFT allowance is followed by 150 tokens at 10 ms each, and the whole answer arrives by 2.0 s. In the streamed reading, the first token must arrive within 2 s, after which 500 tokens stream at no more than 25 ms each, so the stream ends after about 14.5 s.

The streamed reading needs a second target, since a stream that starts on time and then crawls is still a bad experience. We borrow the course's running-example target: p95 TPOT of at most 25 ms, at least 40 tokens per second. We carry both readings through the lab.

The output length matters enormously

Every decode step reads all 16.06 GB of weights, which takes 4.8 ms at 3.35 TB/s even for a batch of one (Lesson 2, Prefill vs Decode). A 500-token answer therefore needs at least 2.4 s, so a 2 s end-to-end SLA for the running example's chat answers is impossible at any fleet size: more GPUs add streams, not speed.

Before doing any capacity math, ask what the latency target measures and how long the outputs are. Then say the per-token budget out loud: "1.5 s for 150 tokens is 10 ms per token, and reading the weights alone takes 4.8 ms, so we have very little room to batch."

Step 2: Turn Requests per Minute into Concurrency

The arrival rate is \lambda = 1,000 ÷ 60 ≈ 16.7 requests per second. A GPU, however, does not see a rate. It sees the requests that are inside it at the same moment. Little's law connects the two: the average number of requests in a system equals the arrival rate times the average time each request spends in it [1]:

L = \lambda W

The law holds for any arrival pattern and scheduling policy. Figure 3 applies it to both readings.

Two rows. Short answers: 16.7 requests per second times 1.1 s each gives about 18 requests in flight, holding about 4.6 GiB of KV cache, 9% of one H100's cache. Streamed chat: 16.7 requests per second times 12.6 s each gives about 210 requests in flight, holding about 58 GiB of KV cache, 1.1 H100s' worth.
  • Short answers: about 0.1 s to the first token (65 ms of prefill plus queueing) and 100 tokens at up to 10 ms gives W ≈ 1.1 s and L ≈ 18 requests in flight across the fleet. At 2,050 tokens each on average, their KV cache is about 4.6 GiB.
  • Streamed chat: 0.1 s plus 500 tokens at up to 25 ms gives W ≈ 12.6 s and L ≈ 210. At 2,250 tokens each, their cache is about 58 GiB, more than the 52 GiB one H100 holds (Lesson 3).

Same arrival rate, 11 times the concurrency: concurrency, not the request rate, fills the KV cache. Both durations are taken at the SLA limit, so they are upper bounds. And 16.7 is an average; with independent arrivals, the count in any one second varies by about √16.7 ≈ 4 requests. We need headroom for that.

Step 3: Estimate One GPU's Capacity

Where a GPU's time goes

We reuse the bandwidth-bound decode model of Lesson 5 [2]: a decode step reads the weights once for the whole batch, and reads each request's KV cache once. Prefill is compute-bound. Three quantities describe one H100 serving this workload:

  • Weight reads per decode step, shared by every request in the batch: t_w = 16.06 GB ÷ 2.35 TB/s = 6.85 ms. The spec sheet's 3.35 TB/s is a peak; we assume decode reaches 70% of it. This is the floor of the time per output token.
  • KV reads per request per step: t_{\text{kv}} = 2,050 tokens × 128 KiB ÷ 2.35 TB/s = 0.115 ms. A short-answer request holds 2,000 prompt tokens plus, on average, half of its 100 output tokens.
  • Prefill per request: t_{\text{pre}} = 2 × 8.03B parameters × 2,000 tokens ÷ (50% × 989 TFLOPS) = 65 ms. We assume prefill reaches 50% of peak compute.

From time per request to maximum request rate

Split the GPU's work into two kinds. Some work belongs to a single request: its prefill, plus reading its KV cache once for each of its output tokens. Call that w, the GPU time each request consumes:

w = t_{\text{pre}} + n_{\text{out}} \, t_{\text{kv}} = 65.0 + 100 \times 0.115 = 76.4\ \text{ms}

The other work is the weight read, once per decode step, shared by the whole batch. Figure 4 shows both budgets for the two readings of the SLA.

Two stacked bars. A short-answer request costs 65.0 ms of prefill plus 11.5 ms of KV reads, 76.4 ms in total, so one H100 saturates at 13.1 requests per second. A streamed-chat request costs 65.0 ms of prefill plus 62.9 ms of KV reads, 127.8 ms in total, so the GPU saturates at 7.8 requests per second. A separate box notes that every decode step also reads 16 GB of weights in 6.85 ms, shared by the batch, which sets the floor of the time per token.

If a GPU receives r requests per second, it spends r \times w of every second on per-request work. Whatever time remains is spent on weight reads, one per decode step, and every request in the batch gains one token per step. Fewer spare seconds means fewer steps per second, and slower tokens for everyone:

\text{TPOT}(r) = \frac{t_w}{1 - r / r_{\text{sat}}}, \qquad r_{\text{sat}} = \frac{1}{w}

The GPU saturates at r_{\text{sat}} = 1 ÷ 76.4 ms = 13.1 requests per second. Setting TPOT equal to the budget gives the largest rate that meets it:

r_{\max} = r_{\text{sat}} \left(1 - \frac{t_w}{\text{TPOT}_{\text{budget}}}\right) = 13.1 \times \left(1 - \frac{6.85}{10}\right) = 4.12\ \text{req/s}

Little's law, applied to the decode phase alone, gives the batch at that rate: B = r \times n_{\text{out}} \times \text{TPOT} = 4.12 × 100 × 10 ms ≈ 4.1 requests. That is the largest batch that still meets the per-token budget. Its KV cache, about 4.1 × 2,150 ≈ 8,900 tokens, fills 2% of the 426,000-token cache. For this SLA, latency binds and memory sits idle.

The model is deliberately conservative: it assumes prefill and decode never overlap, while chunked prefill (Lesson 7, Continuous Batching) lets decode tokens ride along in steps that carry a prefill chunk [3]. Step 7 tells us how conservative it is.

The streamed reading and the KV check

For streamed chat, the average context is 2,250 tokens, so t_{\text{kv}} = 0.126 ms, w = 65.0 + 500 × 0.126 = 127.8 ms, and the GPU saturates at 7.8 requests per second. The 25 ms budget allows r_{\max} = 7.82 × (1 − 6.85 ÷ 25) = 5.68 requests per second, a batch of 5.68 × 500 × 25 ms ≈ 71 whose cache fills at most 42% of capacity. At a 50 ms budget the limit would be 6.75 requests per second with a batch of 169, and memory would bind at the same point: the "170 chat requests" of Lesson 3. Figure 5 plots TPOT against load for both readings.

This matches Lesson 19, GPU Utilization, which puts one H100 at about 5 requests per second at the course's running-example targets (about 53 streams at about 21 ms per step); at 5 requests per second our model predicts 19 ms per token and about 47 streams. The end-to-end reading gets fewer, 4.12, despite answers one fifth as long, because a 10 ms budget allows a batch of only four.

Which reading fits our deployment?

The interviewer's tool shows the whole answer at once, so we plan with the end-to-end reading: 4.12 requests per second per H100. Step 4: Count GPUs with Headroom

The bare minimum is 16.7 ÷ 4.12 = 4.05, so five GPUs would run each one at its limit, with no margin at all. We add two kinds of headroom:

  1. Load headroom. We plan each GPU at 80% of r_{\max}, or 3.30 requests per second. The model predicts means, while the SLA is a p95, arrivals are bursty, and tail latency reacts to load far more sharply than the mean does [10].
  2. Failure headroom. We add one spare replica, so the SLA survives the loss of any one GPU. This is N+1 redundancy.
\text{GPUs} = \left\lceil \frac{\lambda}{0.8 \, r_{\max}} \right\rceil + 1 = \left\lceil \frac{16.7}{3.30} \right\rceil + 1 = 6 + 1 = 7

Check the result with the TPOT formula. With all seven GPUs serving, each receives 2.38 requests per second and the model predicts 8.4 ms per token. With one GPU down, the other six receive 2.78 requests per second each and the model predicts 8.7 ms per token. Both are inside the 10 ms budget.

The streamed reading needs ⌈16.7 ÷ (0.8 × 5.68)⌉ + 1 = ⌈3.67⌉ + 1 = 5 GPUs. Assuming $3.00 per H100-hour, the comparison is stark:

  • Short answers, 2 s end-to-end: 7 GPUs, $21 per hour. The fleet produces 60,000 requests × 100 tokens = 6.0M output tokens per hour, or $3.50 per million output tokens.
  • Streamed chat, 2 s TTFT and 25 ms per token: 5 GPUs, $15 per hour for 30M output tokens per hour, or $0.50 per million output tokens.

The strict SLA makes each output token seven times more expensive, because it forbids the large batches that make GPUs efficient (Lesson 20, Cost per Million Tokens). Figure 6 summarizes the counts.

Traffic also swings between about 8 and 33 requests per second over the day. The daily peak needs ⌈33.3 ÷ 3.30⌉ + 1 = 12 GPUs for short answers (9 for streamed chat) and the overnight low needs 4 (3). A fleet fixed at 7 misses the SLA every afternoon; Lesson 22, Autoscaling, lets the fleet follow the cycle.

Step 5: Repeat for Llama 3.1 70B with Tensor Parallelism

Now suppose the team wants Llama 3.1 70B. Its 141 GB of BF16 weights do not fit on one 80 GB GPU, so each replica splits the model with tensor parallelism (TP), as in Lesson 18, Tensor Parallelism [5]. A replica of k GPUs reads its weights with k times the bandwidth, but every layer ends with an all-reduce; we assume these add 2 ms per decode step. Memory rules out TP = 2: 65.7 GiB of weights per GPU leaves about 1.3 GiB for cache, three chat requests per replica. TP = 4 leaves about 137 GiB per replica (448,000 tokens at 320 KiB each) and TP = 8 about 405 GiB (1.3M tokens).

The end-to-end reading is out of reach: the TPOT floor is 35.3 GB ÷ 2.35 TB/s + 2 ms = 17.1 ms at TP = 4, above the 10 ms budget, and 9.5 ms at TP = 8, which would need 272 GPUs. Serving 70B under that SLA needs FP8 weights (Lesson 13, Quantization - FP8, INT8 and 4-bit), speculative decoding (Lesson 15), or a looser SLA.

The streamed reading works, but the 25 ms per-token target is tight for a model this size. For TP = 4, prefill takes 2 × 70.6B × 2,000 ÷ (4 × 50% × 989 TFLOPS) = 143 ms, KV reads add 500 × 0.079 ms = 39 ms, and the 17.1 ms floor leaves only 8 ms of the 25 ms for batching: 1.75 requests per second per replica. Which TP degree fits our deployment?

We choose TP = 8. Under a 25 ms target, the weight-read floor decides: at TP = 4 it eats 17.1 ms of every 25 ms token, at TP = 8 only 9.5 ms, so each GPU serves 0.85 requests per second instead of 0.44, and the fleet needs 40 GPUs instead of 52. The answer depends on the budget, though. At a looser 50 ms per token, TP = 4 serves 3.62 requests per second per replica and needs 28 GPUs, while TP = 8 needs 32, because N+1 costs one replica and a TP = 8 replica is 8 GPUs. Rerun the comparison whenever the latency target changes.

Step 6: Put It in a Calculator

A spreadsheet works, but a short script is easier to review and rerun. The first tab keeps every assumption from Table 2 as a named constant, computes one replica's capacity with the formulas from Step 3, and counts GPUs as in Step 4. The second tab is what it prints; the numbers follow from the arithmetic above.

"""gpu_calculator.py: GPUs needed for a request rate under a latency SLA (Lesson 21).""" import math from dataclasses import dataclass GiB = 2**30 @dataclass class Model: name: str params: float # number of parameters bytes_per_param: float # 2 for BF16, 1 for FP8 kv_bytes_per_token: int # Lesson 3: 2 x layers x KV heads x head dim x bytes @dataclass class GPU: name: str mem_gib: float # visible memory bandwidth: float # bytes per second (spec sheet) flops: float # dense BF16 FLOP/s (spec sheet) @dataclass class Workload: rate: float # requests per second at the busy hour prompt: int # prompt tokens out_mean: int # mean output tokens tpot_budget: float # seconds per output token the SLA allows # Assumptions: replace them with values measured in Step 7. BW_EFF = 0.70 # fraction of peak bandwidth that decode achieves MFU = 0.50 # fraction of peak FLOPS that prefill achieves MEM_UTIL = 0.90 # vLLM --gpu-memory-utilization OVERHEAD_GIB = 4.6 # activations and CUDA graphs per GPU (Lesson 3) PLAN_LOAD = 0.80 # run each replica at 80% of its SLA limit SPARES = 1 # N+1: survive the loss of one replica def replica_capacity(m: Model, g: GPU, w: Workload, tp: int = 1, comm_s: float = 0.0) -> dict: bw = g.bandwidth * BW_EFF * tp # a replica reads with all its GPUs t_w = m.params * m.bytes_per_param / bw + comm_s # per decode step, shared by the batch ctx = w.prompt + w.out_mean / 2 # average context while decoding t_kv = ctx * m.kv_bytes_per_token / bw # one request's KV read in one step t_pre = 2 * m.params * w.prompt / (g.flops * tp * MFU) work = t_pre + w.out_mean * t_kv # GPU-seconds each request consumes r_sat = 1 / work # requests/s at which the replica saturates r_max = r_sat * (1 - t_w / w.tpot_budget) # requests/s at which TPOT hits the budget batch = r_max * w.out_mean * w.tpot_budget # Little's law for the decode phase weights_gib = m.params * m.bytes_per_param / tp / GiB kv_gib = tp * (g.mem_gib * MEM_UTIL - weights_gib - OVERHEAD_GIB) kv_tokens = max(kv_gib, 0) * GiB / m.kv_bytes_per_token kv_fits = batch * (w.prompt + w.out_mean) <= kv_tokens return dict(t_w_ms=t_w * 1e3, t_kv_ms=t_kv * 1e3, t_pre_ms=t_pre * 1e3, r_sat=r_sat, r_max=max(r_max, 0.0), batch=max(batch, 0.0), kv_tokens=kv_tokens, kv_fits=kv_fits) def tpot_at(rate: float, cap: dict) -> float: """Predicted seconds per output token when one replica receives `rate` requests/s.""" load = rate / cap["r_sat"] return float("inf") if load >= 1 else cap["t_w_ms"] / 1e3 / (1 - load) def gpus_needed(w: Workload, cap: dict, tp: int = 1) -> tuple[int, int]: if cap["r_max"] <= 0 or not cap["kv_fits"]: return 0, 0 # this configuration cannot meet the SLA replicas = math.ceil(w.rate / (cap["r_max"] * PLAN_LOAD)) + SPARES return replicas, replicas * tp if __name__ == "__main__": h100 = GPU("H100 SXM", mem_gib=79.6, bandwidth=3.35e12, flops=989e12) llama8b = Model("Llama 3.1 8B", 8.03e9, 2, 131_072) llama70b = Model("Llama 3.1 70B", 70.6e9, 2, 327_680) rate = 1000 / 60 short = Workload(rate, prompt=2000, out_mean=100, tpot_budget=(2.0 - 0.5) / 150) chat = Workload(rate, prompt=2000, out_mean=500, tpot_budget=0.025) cases = [("8B, 2 s end-to-end", llama8b, short, 1, 0.0), ("8B, streamed chat", llama8b, chat, 1, 0.0), ("70B TP=4, streamed chat", llama70b, chat, 4, 0.002), ("70B TP=8, streamed chat", llama70b, chat, 8, 0.002)] for label, m, w, tp, comm in cases: cap = replica_capacity(m, h100, w, tp, comm) replicas, gpus = gpus_needed(w, cap, tp) print(f"{label:26s} TPOT floor {cap['t_w_ms']:5.2f} ms | max {cap['r_max']:5.2f} req/s " f"per replica, batch {cap['batch']:5.1f} | {replicas} replicas = {gpus} GPUs") 8B, 2 s end-to-end TPOT floor 6.85 ms | max 4.12 req/s per replica, batch 4.1 | 7 replicas = 7 GPUs 8B, streamed chat TPOT floor 6.85 ms | max 5.68 req/s per replica, batch 71.0 | 5 replicas = 5 GPUs 70B TP=4, streamed chat TPOT floor 17.05 ms | max 1.75 req/s per replica, batch 21.8 | 13 replicas = 52 GPUs 70B TP=8, streamed chat TPOT floor 9.53 ms | max 6.80 req/s per replica, batch 85.0 | 5 replicas = 40 GPUs

Step 7: Validate with a Load Test

Serve one replica

Replicas run independently, so we validate one H100 and scale by the replica count. Recent vLLM releases default --gpu-memory-utilization to 0.92; we set 0.90 explicitly to match Lesson 3's budget [7].

Drive it at a fixed request rate

vllm bench serve generates an open-loop load: --request-rate sets the average number of requests per second, and arrival times follow a Poisson process unless you change --burstiness (values above 1 make arrivals more evenly spaced) [6]. Do not set --max-concurrency: it makes the test a closed loop that slows down with the server and hides queueing. A range ratio of 0.5 on the output spreads lengths over 50 to 150 tokens, --ignore-eos makes the model produce exactly those lengths, and --goodput e2el:2000 counts requests that finish within 2 s, the goodput idea from DistServe [4]. The key rate is 2.78 requests per second, each replica's share after one of seven fails; the sweep around it locates the knee, and the third tab compares the results with the calculator.

Reading the Results

Start at the lowest rate. At 1 request per second the batch is tiny, so TPOT is almost pure weight reading. If you measure 7.0 ms where the model predicts 7.4 ms, decode is reading weights faster than assumed: the implied weight read is 7.0 × (1 − 1 ÷ 13.1) ≈ 6.5 ms, so bandwidth efficiency is about 4.8 ÷ 6.5 ≈ 74% rather than 70%. Update BW_EFF. Then compare TTFT at low load with the 65 ms prefill estimate to adjust MFU, rerun the calculator, and see whether the GPU count changes.

Then look at the shape. Figure 8 shows the typical result of a sweep next to the model's prediction; the points are illustrative. Latency stays nearly flat, bends, then climbs steeply near saturation, when requests start waiting for a place in the batch and TTFT grows along with TPOT.

  • Measured latency below the model at low load is expected. The model charges the full 0.5 s TTFT allowance, while real TTFT at low load is closer to the 65 ms prefill.
  • The knee earlier than predicted means the efficiency assumptions were optimistic, or the benchmark prompts are harder than the production ones. Recalibrate and recount.
  • p95 above 2 s at 2.78 requests per second fails the SLA. Look at which part grew. A large p95 TTFT points to queueing behind prefill; a large TPOT points to decode. Both can be bought back with FP8 weights or a smaller max_tokens, and Table 3 tells you how much each buys.
  • The streamed reading needs no new tools: run the same sweep with --random-output-len 500 and a range ratio of 0, check p95 TTFT against 2 s and p95 TPOT against 25 ms, and use --goodput ttft:2000 tpot:25.

Common Pitfalls

  • Planning with the mean output length. The p95 latency belongs to the long answers. Use the cap or the p95 output length for the per-token budget, and the mean for the load.
  • Spec-sheet bandwidth as achievable bandwidth. Planning at 100% of 3.35 TB/s would put the TPOT floor at 4.8 ms instead of 6.85 ms and overstate capacity by about half.
  • Synthetic prompts that don't match production. Random prompts get no prefix cache hits, while production traffic with a shared system prompt may skip much of its prefill (Lesson 24, Prefix Caching). Without --ignore-eos, outputs may also end early. Validate on a sample of real prompts before cutting GPUs.
  • Measuring from the wrong place. The SLA is measured at the gateway. A benchmark client on the same host as vLLM misses network time, TLS, and authentication; one on another continent adds too much.
  • Rounding too early, or forgetting the daily cycle. Keep fractions until the final ceiling, then add the spare, and size the peak of the day separately from the average.

Stretch Goals

  • Rerun the calculator with FP8 weights and an FP8 KV cache (Lesson 13). Set bytes_per_param=1, use 65,536 bytes per token, and see how the short-answer GPU count moves. Then validate it, including an accuracy check.
  • Add a TTFT model: treat prefill as a queue with arrival rate r and service time t_{\text{pre}}, and check the 0.5 s allowance at p95.
  • Measure the all-reduce cost at TP = 4 and TP = 8 as in Lesson 18, and see whether TP = 8 still wins per GPU.
  • Size a disaggregated deployment (Lesson 34, Disaggregated Prefill and Decode): a prefill pool sized from t_{\text{pre}} alone, and a decode pool sized with the TPOT formula and t_{\text{pre}} = 0. Compare its GPU count with Step 4.

Summary

Mind map summarizing the lab: pinning down the SLA, Little's law, one GPU's capacity, GPU count with headroom, tensor parallelism for 70B, and validation with a load test.
  • Pin down the SLA before doing math. Under a 2 s end-to-end SLA, the output length sets the per-token budget: (2 s − 0.5 s) ÷ 150 tokens = 10 ms.
  • 1,000 requests per minute is 16.7 per second. Little's law turns it into about 18 requests in flight for short answers, or about 210 for streamed 500-token chat.
  • One H100 serving Llama 3.1 8B reads its weights in 6.85 ms per step at 70% efficiency. TPOT grows as t_w / (1 - r/r_{\text{sat}}), which allows 4.12 requests per second within 10 ms per token, or 5.68 within 25 ms, in line with Lesson 19's estimate of about 5.
  • At 80% planned load plus an N+1 spare, short answers need 7 H100s ($3.50 per million output tokens at $3.00 per GPU-hour); streamed chat needs 5 ($0.50).
  • Llama 3.1 70B cannot meet the end-to-end SLA in BF16. For streamed chat at 25 ms per token it needs 40 GPUs as five TP=8 replicas, against 52 at TP=4; at 50 ms per token the order flips.
  • Validate with open-loop load from vllm bench serve --request-rate: check p95 at each replica's post-failure share, then recalibrate the efficiency assumptions from what you measure.

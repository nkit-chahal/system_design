Introduction

Every token an LLM produces is paid for in GPU time. A self-hosted model has no price list: we rent or buy GPUs by the hour, and the cost of a token is whatever fraction of a GPU-hour it consumes. Turning "$3 per GPU-hour" into "$X per million tokens" is the arithmetic that decides whether a product is profitable, which model and hardware to choose, and whether to run our own GPUs at all.

The arithmetic itself is one line. The hard part is choosing the right numbers to put into it: which throughput, which tokens, and how many of the GPU-hours we pay for actually serve traffic. Figure 1 shows the basic conversion for our running example.

A flow from an assumed GPU price of $3.00 per H100-hour, divided by 3,600 seconds, to $0.000833 per GPU-second. Dividing by 2,500 output tokens per second gives $0.33 per million output tokens; by 12,500 input plus output tokens per second, $0.067 per million tokens; by 5 requests per second, $0.17 per thousand requests.

In this lesson, we derive the cost formula, split the cost between input and output tokens, account for idle GPUs with a utilization factor, compute cost per request and per user, compare self-hosting with a per-token API at assumed prices, and rank the levers that bring the cost down.

Clarifying the Problem

Cost questions usually come from finance or product, and the first job is to pin down every number that feeds the formula. Here is a typical exchange:

Candidate: Which model and hardware are we costing?
Interviewer: Llama 3.1 8B Instruct in BF16 on H100 SXM GPUs, served with vLLM, one model copy per GPU.

Candidate: What do we pay for a GPU?
Interviewer: We rent on-demand cloud capacity. For this exercise, assume $3.00 per H100-hour.

Candidate: What does the traffic look like over a day?
Interviewer: Chat requests of about 2,000 prompt tokens and 500 output tokens. Traffic averages 1,000 requests per minute, about 16.7 per second, on a daily cycle from about 8 per second at night to about 33 at the afternoon peak.

Candidate: How much can one GPU serve within our latency targets?
Interviewer: Our load test says 5 requests per second per H100 while p95 TTFT stays under 500 ms and p95 time per output token under 25 ms.

Candidate: What decision does this feed?
Interviewer: Finance wants a cost per million tokens and a comparison with a hosted API for a model of similar quality. Assume it charges $0.20 per million input tokens and $0.60 per million output tokens.

The question underneath is: what does one token really cost us, which tokens cost the most, and at what volume does running our own GPUs beat paying per token? All prices here are assumptions for the exercise; the method is what carries over.

The Basic Formula

From GPU-hours to tokens

A GPU costs the same per hour whether it is busy or idle. If it produces a steady number of tokens per second, the cost of one token is the cost of one GPU-second divided by the tokens produced in that second. Scaling to a million tokens gives the cost per million tokens:

\$\text{ per 1M tokens} = \frac{\text{GPU }\$\text{ per hour}}{\text{tokens per second} \;\times\; \text{3,600}} \times \text{1,000,000}

For a fleet, use the total hourly price of all GPUs and the total tokens per second they produce. For a model that spans several GPUs, the GPU price is the price of the whole group.

Worked example: one H100 at full load

At 5 requests per second, one H100 processes 5 × 2,000 = 10,000 input tokens and generates 5 × 500 = 2,500 output tokens every second.

  • Cost per GPU-second: $3.00 ÷ 3,600 ≈ $0.000833.
  • Per million output tokens: $3.00 ÷ (2,500 × 3,600) × 1,000,000 ≈ $0.33.
  • Per million tokens, input and output together: $3.00 ÷ (12,500 × 3,600) × 1,000,000 ≈ $0.067.
  • Per request: $0.000833 ÷ 5 ≈ $0.000167, or $0.17 per 1,000 requests.

The first two numbers differ by 5×, and neither is wrong. "Per million output tokens" loads the whole GPU cost onto generated tokens; the blended figure spreads it over every token processed. Always say which one you mean, and never compare one against an API's price for the other.

Which tokens per second?

The formula is only as good as the throughput we plug in, and the same GPU can produce very different numbers. Using the example measurements from Lesson 19, GPU Utilization:

  • A single stream at 140 output tokens per second gives $3.00 ÷ (140 × 3,600) × 10⁶ ≈ $5.95 per million output tokens.
  • Pure decode at batch 64, 4,000 tokens per second, gives ≈ $0.21 per million output tokens, but it ignores prompt processing.
  • The load test at our latency targets, 2,500 output tokens per second with prompts included, gives $0.33.

The honest number is the last one: throughput measured on the real request mix, at the batch size the latency targets allow. A vendor benchmark at maximum batch with short prompts will quote a far lower cost than you can achieve. Lesson 21, Lab - GPUs for 1,000 Requests per Minute Under a 2s SLA, shows how to measure it.

Input Tokens versus Output Tokens

Why they cost different amounts

Input and output tokens use the GPU in very different ways (Lesson 2, Prefill vs Decode). Prefill processes all prompt tokens of a request in parallel, so the weights are read once for thousands of tokens and the work is compute-bound. Decode produces one token per request per step, and each step must read every weight and every cached key and value, so the work is memory-bound. A GPU therefore turns out input tokens many times faster than output tokens.

Per-token APIs reflect this by usually pricing output tokens higher than input tokens, often several times higher. Our assumed API charges 3× more for output. To compare fairly, we need our own split.

Splitting cost by GPU time

The fairest split charges each phase for the GPU time it uses. Lesson 19's example prefill benchmark puts our H100 at 32,000 prompt tokens per second (52% MFU), an assumption until you measure your own. At 5 requests per second, the 10,000 input tokens arriving each second need 10,000 ÷ 32,000 ≈ 0.31 seconds of GPU time, and decode uses the remaining 0.69 seconds to produce 2,500 output tokens. Figure 2 turns these shares into prices.

A bar for one second of H100 time: 0.31 seconds of prefill for 10,000 input tokens and 0.69 seconds of decode for 2,500 output tokens. Prefill's share of a $3.00 hour is $0.94 over 36 million input tokens, or $0.026 per million. Decode's share is $2.06 over 9 million output tokens, or $0.23 per million. An output token uses about 275 microseconds of GPU time and an input token about 31.
  • Input: 31% of $3.00 is about $0.94 per hour, spread over 36 million input tokens: $0.026 per million.
  • Output: 69% is about $2.06 per hour over 9 million output tokens: $0.23 per million.
  • Ratio: an output token costs about 9× an input token (275 µs versus 31 µs of GPU time).

For one request, the 2,000 input tokens cost about $0.000052 and the 500 output tokens about $0.000115. Output tokens are 20% of the tokens but about 69% of the cost. The ratio depends on the workload: longer prompts shift cost toward input, and longer contexts make every decode step read more KV cache, which makes output tokens dearer still (Lesson 3, KV Cache).

If asked "what does a token cost?", answer with two numbers: "about $0.03 per million input tokens and $0.23 per million output tokens at full load, because decode is memory-bound and prefill is not." It shows you know where the money goes.

Cached input tokens

With prefix caching, a request whose prompt starts with text the server has already processed, such as a long system prompt, reuses the stored KV cache instead of recomputing it (Lesson 24, Prefix Caching) [1]. Cached input tokens cost almost no GPU time. Hosted APIs pass part of this saving on: Anthropic, for example, bills cache reads at 0.1× the base input price for most models [2].

For our deployment, suppose 1,500 of each request's 2,000 prompt tokens are a shared system prompt. Prefill per request drops from 62.5 ms to about 15.6 ms of GPU time, while decode stays at about 137.5 ms. Total GPU time per request falls from 200 ms to about 153 ms, roughly 23% less, so one GPU can carry about 30% more requests before decode becomes the limit again.

Average Load versus Peak: The Utilization Factor

Paying for idle GPUs

The worked example assumed the GPU is fully loaded every second of the day. Real traffic rises and falls, but we must provision for the peak, plus headroom, or latency explodes when traffic is highest. Every GPU-hour that is provisioned but not serving is still paid for. We capture this with the utilization factor U, the average load served divided by the capacity provisioned:

\text{effective cost per token} = \frac{\text{cost per token at full load}}{U}

Note that U is a fleet-level ratio of request rates, not the GPU-Util or MFU of Lesson 19. A GPU at the efficient operating point all day has U = 1; a fleet that is half idle on average has U = 0.5 and pays double per token.

Worked example: a daily traffic cycle

Our traffic averages 16.7 requests per second but swings from about 8 at 2 a.m. to about 33 at 2 p.m., with a narrow afternoon peak: 1.44 million requests and 720 million output tokens a day. Figure 3 compares two ways to provision for it.

A 24-hour chart. Traffic follows a smooth curve from about 8 requests per second at 2 a.m. to about 33 at 2 p.m., averaging 16.7. A dashed line shows 8 GPUs, or 40 requests per second of capacity, all day; the hatched area between it and the traffic is idle capacity that is still paid for. A green step line shows autoscaled capacity, between 2 and 8 GPUs, following the curve with 20% headroom. Static uses 192 GPU-hours a day at 42% utilization; autoscaled uses 112 at 71%.
  • Static peak provisioning: 33 requests per second plus 20% headroom is 39.6, which needs 8 GPUs at 5 requests per second each. That is 192 GPU-hours, or $576 per day, and U = 16.7 ÷ 40 ≈ 42%. Cost: $576 ÷ 1.44 million = $0.40 per 1,000 requests, or $0.80 per million output tokens, 2.4× the full-load figure.
  • Autoscaling (Lesson 22, Autoscaling) with the same 20% headroom, adjusted every hour and never below 2 GPUs, averages 4.7 GPUs: 112 GPU-hours, or $336 per day, and U ≈ 71%. Cost: $0.23 per 1,000 requests, or $0.47 per million output tokens.

Autoscaling cut the bill by about 40% without touching a single kernel; the narrower the peak, the more it saves. In practice the gain is smaller: new replicas take minutes to start (Lesson 23, Cold Starts), so the autoscaler must act early and keep more headroom. The other way to raise U is to fill the quiet hours with work that can wait, such as offline evaluation or batch summarization, at nearly zero marginal cost (Lesson 39, Batch and Offline Inference).

Cost per request and per user

Product teams think in requests and users, not tokens. With the numbers above:

  • Per request: $0.00017 at full load, $0.00023 autoscaled, $0.00040 with static provisioning.
  • Per user: a user who sends 20 chat requests a day makes about 600 a month, so they cost about $0.14 a month autoscaled, or $0.24 with static provisioning.
  • Heavy users: a request with a 32,768-token document costs far more than its share of tokens suggests, because its KV cache displaces about 13 chat requests from the GPU (Lesson 3, KV Cache). Per-request accounting (Lesson 31, Per-Request Token Accounting) makes these users visible.

Self-Hosting versus a Per-Token API

Break-even utilization

At the assumed API prices, one of our requests costs 2,000 × $0.20 + 500 × $0.60 per million tokens = $0.0004 + $0.0003 = $0.0007, or $0.70 per 1,000 requests. Self-hosting costs $0.167 per 1,000 requests at full load and $0.167 ÷ U in general. The two are equal when:

U^{*} = \frac{\text{self-hosted cost at full load}}{\text{API cost}} = \frac{0.167}{0.70} \approx 24\% A curve of self-hosted GPU cost per 1,000 requests, $0.167 divided by utilization, falls from about $1.19 at 14% utilization to $0.17 at 100%. A dashed horizontal line marks the API at $0.70 per 1,000 requests. They cross at about 24% utilization; below it the API is cheaper. Points mark static provisioning at 42% ($0.40), autoscaling at 71% ($0.23), and full load ($0.17).

Figure 4 shows the result. If our fleet averages less than about 24% utilization, the API is cheaper even before we count anyone's salary. Above it, self-hosting wins on GPU cost, by about 1.75× at 42% and 3× at 71%.

Break-even volume

GPU cost is not the whole story. Self-hosting has fixed costs that an API does not: engineers to run the serving stack, an on-call rotation, and a minimum footprint, since we want at least two GPUs for redundancy even at 3 a.m. Assume $10,000 per month of engineering and operations time and a floor of 2 GPUs (2 × 730 hours × $3.00 ≈ $4,380 per month), with our autoscaled 71% utilization above the floor ($0.000233 per request):

\text{self-hosted} = \$\text{10,000} + \max(\$\text{4,380},\; \$\text{0.000233} \times R), \qquad \text{API} = \$\text{0.0007} \times R

Here R is requests per month. Setting them equal gives R = $10,000 ÷ ($0.0007 − $0.000233) ≈ 21 million requests per month, about 8 requests per second on average, or 700,000 a day. With static provisioning ($0.0004 per request), break-even rises to about 33 million.

Monthly cost against requests per month from 0 to 60 million. The API line rises from zero to $42,000. Two self-hosted lines start at a $14,400 floor for two GPUs plus operations. The autoscaled line, at 71% utilization, crosses the API at about 21 million requests and $15,000; the static line, at 42%, crosses at about 33 million and $23,000. A vertical marker at our 43.8 million requests shows the API at about $30,700, static self-hosting at about $27,500, and autoscaled self-hosting at about $20,200.

Figure 5 shows why fixed costs and utilization both matter. Counting GPUs alone, self-hosting would win above about 6 million requests per month; the operations budget pushes break-even to 21 million with autoscaling and 33 million without. Our traffic, 1,000 requests per minute, is about 43.8 million requests per month. At that volume the API would cost about $30,700 per month; self-hosting costs about $27,500 with static provisioning or $20,200 with autoscaling, including the $10,000 of operations.

Which option fits our deployment?

At about 44 million requests per month, roughly twice the autoscaled break-even volume, self-hosting with autoscaling is the better fit: about $20,200 per month against about $30,700 for the API at the assumed prices, a saving of about a third. Autoscaling is not optional here. With static peak provisioning the saving shrinks to about $3,100 a month, too thin to justify running our own stack. The autoscaled margin survives moderate errors: operations would have to cost about twice our assumption, over $20,000 a month, to erase it. We keep the API as an overflow path: when a launch spike of up to 10× the average outruns the autoscaler, sending the excess to the API is cheaper than holding idle GPUs for rare peaks (Lesson 27, Lab - Surviving a 10x Traffic Spike).

The decision would flip for a smaller product. Below about 8 requests per second on average, or if the fleet could not hold utilization above about 24%, the API is cheaper and frees the team to work on the product. The decision also assumes the API model matches our quality on the evaluation set; if it does not, the comparison is moot.

Levers That Lower Cost per Token

Adding utilization to the basic formula shows that every lever works through one of three terms: the GPU's hourly price, the tokens per second it produces, or the fraction of paid hours that serve traffic. Figure 6 maps the common levers to their terms.

The equation dollars per million tokens equals GPU dollars per hour divided by tokens per second times utilization times 3,600, times one million, with arrows to three boxes. Lower GPU dollars per hour: reserved or committed capacity, spot capacity, right-sizing the GPU type. Raise tokens per second: bigger batches up to the SLO, FP8 weights and KV cache, a smaller or distilled model, prefix caching, speculative decoding. Raise utilization: autoscaling, batch jobs in quiet hours, sharing GPUs across small models.

Throughput levers

Bigger batches are the largest lever, because a decode step costs nearly the same for 1 request as for 64. Going from a single stream to batch 64 cut the decode cost from $5.95 to $0.21 per million output tokens in Lesson 19's example, and PagedAttention's authors reported 2–4× throughput at the same latency over earlier systems, largely by fitting bigger batches [3]. The limit is the latency target. Quantization (Lesson 13, Quantization - FP8, INT8 and 4-bit) roughly halves the bytes per decode step with FP8 weights and KV cache, which can approach 2× decode throughput and doubles KV capacity, subject to a quality check. A smaller or distilled model (Lesson 14, Distillation) is the biggest single step if quality allows: Llama 3.1 70B has about 8.8× the parameters of the 8B model, and so roughly 8.8× the weight bytes and FLOPs per token. Speculative decoding (Lesson 15, Speculative Decoding) reported 2–3× faster generation in the original paper [4], mostly at small batch, where compute is idle.

Price levers

Reserved or committed capacity lowers the hourly price in exchange for paying whether we use it or not, so it suits the always-on base of the fleet. Spot capacity is cheaper still; AWS advertises up to 90% off on-demand prices [5], but it can be reclaimed with a two-minute warning [6], so it suits batch work and stateless replicas behind a router that tolerates losing them (Lesson 40, Reliability and Rollouts). Right-sizing the GPU matches hardware to the bottleneck: decode cost follows memory bandwidth per dollar, and prefill cost follows FLOPS per dollar. An L4 has 300 GB/s against the H100's 3.35 TB/s, so even at its best it needs an hourly price below about 9% of an H100's to match it on decode, and its 24 GB leaves far less room for KV cache. An H200's 4.8 TB/s and 141 GB pay off when its price is less than about 1.4× an H100's.

Utilization levers

Autoscaling raised U from 42% to 71% in our example, a 1.7× saving, and filling quiet hours raises it further. Serving several small or fine-tuned models on shared GPUs helps when each alone would leave its GPU mostly idle (Lesson 37, Multi-LoRA and Multi-Tenant Serving).

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Splitting prefill and decode onto different machines, each tuned for its own bottleneck: Splitwise reports 1.4× throughput at 20% lower cost [9] (Lesson 34, Disaggregated Prefill and Decode).
  • Goodput, the request rate served within both TTFT and TPOT targets, as the right denominator for cost, because throughput that breaks the SLO has no value [10].
  • Long-context pricing: KV cache, not token count, limits concurrency, so a 32K-token request occupies the room of about 13 chat requests (Lesson 36, Long-Context Serving).
  • Reasoning models that generate thousands of output tokens per request shift almost all cost to decode, which raises the value of FP8, speculative decoding and larger batches.
  • Owning GPUs instead of renting them turns the hourly price into depreciation, power, cooling and data-center space, and makes utilization even more important because the cost is sunk.
  • Mixture-of-experts models need memory for every expert but compute only for the active ones, so their cost per token depends strongly on batch size (Lesson 35, Mixture-of-Experts Serving).

Summary

Mind map summarizing the cost lesson: the basic formula, input versus output cost, the utilization factor, cost per request and user, self-hosting versus an API, and the cost levers.
  • $ per 1M tokens = GPU $ per hour ÷ (tokens per second × 3,600) × 1,000,000. At an assumed $3.00 per H100-hour and 5 requests per second, that is $0.33 per million output tokens, or $0.17 per 1,000 requests.
  • Use throughput measured on the real request mix at the latency targets; a single stream or a maximum-batch benchmark gives costs that are 18× too high or misleadingly low.
  • Splitting GPU time by phase, an output token costs about 9× an input token: $0.23 versus $0.026 per million. Cached input tokens cost almost nothing.
  • Paid idle time divides into every token: effective cost = full-load cost ÷ utilization. For 1,000 requests per minute, static peak provisioning (8 GPUs) gave 42% utilization; autoscaling gave 71% and cut cost by about 40%.
  • At assumed API prices of $0.20 and $0.60 per million input and output tokens, self-hosting wins above about 24% utilization on GPU cost. With $10,000 of monthly operations it needs about 21 million requests per month with autoscaling (33 million without); our 44 million qualifies.
  • Levers act on price (reserved, spot, right-sized GPUs), throughput (batching, quantization, smaller models, prefix caching, speculative decoding), or utilization (autoscaling, filling quiet hours).

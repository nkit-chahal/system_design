Introduction

vLLM is the most widely deployed open-source engine for serving large language models. It began in 2023 in the Sky Computing Lab at UC Berkeley as the reference implementation of PagedAttention [1], and it has since grown into a community project with more than 2,000 contributors that runs on NVIDIA, AMD, and Intel GPUs, on CPUs, and on other accelerators through plugins [2]. When a team says "we serve open models," vLLM is usually the first engine they try.

An engine is more than its famous idea. Between an HTTP request and a GPU kernel, vLLM tokenizes text, decides which requests run in the next step, allocates and shares KV cache blocks, replays pre-recorded CUDA graphs, samples tokens, and streams them back. Knowing where each of these happens tells you which flags change capacity, which change latency, and which metric to read when something goes wrong. Figure 1 shows the path one request takes through vLLM's current engine, called V1.

A client on the left sends a request through three dashed process groups. The API server process receives the HTTP request and tokenizes it, then sends it over ZMQ to the engine core process, where the scheduler picks tokens for the next step and the KV cache manager hands out blocks. The step is broadcast over a shared-memory queue to one GPU worker process per GPU, which run the forward pass and sampling and talk to each other over NCCL. Sampled token IDs return to the engine core, which updates requests and sends outputs over ZMQ back to the API server, which detokenizes and streams text to the client. Numbered circles 1 to 6 mark the order.

In this lesson, we walk through the V1 architecture, see how continuous batching (Lesson 7, Continuous Batching) and PagedAttention (Lesson 8, PagedAttention) appear in its scheduler and KV cache manager, cover the features that change capacity and latency, and then deploy and monitor vLLM for our running example. Flags, defaults, and metric names are as of late 2026 (vLLM v0.32); check them against the documentation of the version you run.

Clarifying the Problem

Engine questions in interviews usually start from a concrete deployment. Here is a typical exchange:

Candidate: Which model are we serving, and on what hardware?
Interviewer: Llama 3.1 8B Instruct in BF16, one NVIDIA H100 80 GB per replica.

Candidate: What does the traffic look like?
Interviewer: Chat requests with about 2,000 prompt tokens and 500 output tokens. The first 1,000 tokens of every prompt are the same system prompt. The fleet receives about 1,000 requests per minute on average, or 16.7 per second, and about twice that at the daily peak. We plan for about 50 concurrent users per H100.

Candidate: What latency do users need?
Interviewer: A p95 time to first token of at most 500 ms and a p95 time per output token of at most 25 ms.

Candidate: How do clients call the model?
Interviewer: The application uses the OpenAI Python SDK. Some calls must return JSON that matches a schema.

Candidate: Where will it run, and how do we monitor it?
Interviewer: Containers on Kubernetes. Prometheus scrapes every service.

The question underneath is: what does vLLM do with each request at each step, and which few settings decide whether one H100 can carry about 50 of those users within the latency targets? Lesson 19, GPU Utilization, estimates about 53 concurrent streams, or about 5 requests per second, per H100 at these targets, so the plan is realistic. We start with the processes that make up the engine.

Inside the V1 Engine

Three kinds of processes

V1 splits the work across separate operating-system processes so that CPU work never stalls the GPU [3][4]:

  • The API server process runs the HTTP server and the OpenAI-compatible API. It renders chat templates, tokenizes prompts, loads images, and on the way back detokenizes output tokens and streams them to the client.
  • The engine core process runs the scheduler and the KV cache manager in a busy loop. It talks to the API server over ZMQ sockets. There is one engine core per data-parallel rank.
  • The GPU worker processes, one per GPU, load the weights and run the forward pass through a model runner. The engine core broadcasts each step's work to them over a shared-memory queue, and tensor-parallel workers exchange activations over NCCL.

When data parallelism is on, a small DP coordinator process balances load across engine cores. The documentation gives the process count as A + DP + N, plus one coordinator if DP > 1, where A is the number of API servers (default DP) and N the number of GPUs [4]. Our single-H100 replica therefore runs 1 + 1 + 1 = 3 processes. Each one wants a physical CPU core, and the engine core's busy loop is especially sensitive to CPU starvation, so the pod needs at least 3 physical cores, or 6 vCPUs with hyperthreading [5]. A CPU-starved pod shows up as high time to first token while the GPU sits idle.

The separation pays off. The V1 announcement reported up to 1.7× higher throughput than the previous engine, largely because tokenization and detokenization now overlap with model execution instead of running between steps [3].

One engine step

The engine core repeats the same three phases, as Figure 2 shows. Schedule: the scheduler decides how many tokens each request processes in this step and makes sure the KV cache has room for them. Execute: the workers run one forward pass over all scheduled tokens and sample the next token for every request that finished its prompt. Update: the scheduler appends the new tokens, checks stop conditions, frees the blocks of finished requests, and sends outputs to the API server.

Two timelines with a CPU row and a GPU row. Without async scheduling, the GPU waits while the CPU schedules step n plus one and updates step n, leaving gaps between forward passes. With async scheduling, the CPU prepares step n plus one while the GPU is still running step n, so forward passes run back to back. Durations are illustrative.

In a naive loop the GPU waits while the CPU schedules and updates. vLLM now enables asynchronous scheduling by default when the configuration supports it: the scheduler prepares step n+1 while the GPU is still running step n, which removes those gaps [6]. SGLang and TensorRT-LLM implement the same idea under the name "overlap scheduler" (Lesson 10, SGLang). The catch is that the scheduler commits to step n+1 before it has seen step n's tokens, so it reserves placeholder slots for them and reconciles once they arrive.

The scheduler: one token budget for prefill and decode

The V1 scheduler treats prompt tokens and output tokens the same way. Its decision for a step is a mapping from request ID to the number of tokens that request processes, for example {A: 1, B: 1, C: 1008} [3]. A decoding request needs 1 token; a new request needs its whole prompt, or a chunk of it. Two limits bound each step: --max-num-seqs caps the number of requests, and --max-num-batched-tokens caps the total tokens.

The scheduler fills the budget in a fixed order. It schedules every running (decoding) request first, then spends the rest on waiting requests, splitting any prompt that does not fit into chunks. This chunked prefill is on by default [5][17]. For vllm serve on a GPU with at least 70 GiB, such as the H100, the defaults are 8,192 batched tokens and 1,024 sequences per step; smaller GPUs get 2,048 and 256 [6]. Lesson 7, Continuous Batching, explains why mixing prefill and decode in one step keeps the GPU busy.

Figure 3 applies the budget to our traffic. With 50 users decoding, each step spends 50 tokens on decode and has 8,142 left for prompts. If a new request's first 992 tokens are already in the prefix cache (we will see why 992 and not 1,000 shortly), it needs 1,008 tokens of prefill, so 8 new requests fit in one step (8 × 1,008 = 8,064). A 32,768-token document with nothing cached needs 5 steps of up to 8,142 tokens each.

Two horizontal bars represent one step. With the default budget of 8,192 tokens, 50 decode tokens are followed by eight prefill chunks of 1,008 tokens and 78 unused tokens; the step needs at least 133 ms of compute. With a budget of 2,048 tokens, 50 decode tokens are followed by one 1,008-token prefill and a 990-token chunk of the next prompt; the step needs at least 33 ms.

The budget also sets the longest gap between tokens, because every decoding user waits for the whole step. A pure decode step for about 50 users takes roughly 14 ms in Lesson 19's model, and about 21 ms once that lesson's prompt chunks are mixed in, inside our 25 ms target. A forward pass costs about 2 \times \text{params} FLOPs per token, so even at the H100's full 989 TFLOPS, a step that also carries 8,192 tokens needs at least

\frac{2 \times 8.03 \times 10^{9} \times 8192}{989 \times 10^{12}\ \text{FLOP/s}} \approx 133\ \text{ms}

Every decoding user sees such a step as a stall of 133 ms or more. Time per output token averages over a whole 500-token answer, so a few stalls barely move it, but they show up in p99 inter-token latency and as visible hiccups in the stream. A budget of 2,048 tokens caps the stall near 33 ms, at the cost of spreading long prompts over more steps. The documentation describes the same trade-off: smaller values give better inter-token latency, larger values give better time to first token and throughput [5].

What does move time per output token is the total amount of prefill, whatever the budget. At 5 requests per second, each with 1,008 uncached prompt tokens, the GPU spends at least 5 × 1,008 × 16.2 µs ≈ 82 ms of every second on prompts, where 16.2 µs = 2 × 8.03 × 109 ÷ (989 × 1012) seconds is the compute floor per prompt token. If none of that work overlapped with decoding, the 14 ms decode step would stretch to about 14 ÷ (1 − 0.082) ≈ 15 ms per token. Real prefill runs nearer half of peak (Lesson 19 assumes 32,000 prompt tokens per second, 52% MFU), which doubles the share to about 16% and gives about 17 ms. Without the prefix cache, prompts are twice as long, the share doubles again to about 31%, and the estimate reaches about 20 ms, close to Lesson 19's 21 ms for 53 streams: still inside the target, with little room to spare.

When a running request needs a new block and none is free, the scheduler preempts the request at the back of the running queue (the most recently admitted one under the default first-come-first-served policy), frees its blocks, and later recomputes its tokens, as Lesson 3, KV Cache, described. The engine logs a warning and counts each event in a metric, which we will watch in production.

PagedAttention as implemented: the KV cache manager

At startup, vLLM loads the weights, runs a dummy forward pass to measure peak activation memory, and accounts for CUDA graph memory. Everything that remains under --gpu-memory-utilization becomes a pool of fixed-size blocks of 16 tokens each [6]. For Llama 3.1 8B one block holds 16 × 128 KiB = 2 MiB, so the 52 GiB from Lesson 3 becomes 26,624 blocks, or 425,984 tokens. The startup log reports this number as the GPU KV cache size.

The default for --gpu-memory-utilization is 0.92 in current releases (as of late 2026) [6]; earlier releases used 0.90. This course passes 0.90 explicitly so the numbers match Lesson 3. The extra 0.02 × 79.6 GiB ≈ 1.6 GiB would hold about 13,000 more tokens. To pin the cache size instead of deriving it, --kv-cache-memory-bytes sets it directly and skips the profiling run.

Each request keeps a block table that maps its logical token positions to physical blocks, which is the PagedAttention idea from Lesson 8. The manager tracks a reference count on every block and keeps free blocks in a doubly linked free queue, so it can move a block to the head or tail in constant time [7].

Automatic prefix caching

Prefix caching is on by default in V1. vLLM identifies each full block by a hash of three things: the hash of the block before it, the token IDs in the block, and extra keys such as a LoRA adapter ID, image hashes, or a per-request cache_salt [7]. Because each hash includes its parent, equal hashes mean equal prefixes. When a request arrives, the manager hashes its prompt block by block and reuses cached blocks until the first miss. Figure 4 shows two requests that share our system prompt.

Request A and Request B each have a block table. Their first 62 blocks have the same chained hashes, h1 through h62, so both tables point to the same 62 physical blocks, which carry a reference count of 2. Block 63 holds the last 8 system prompt tokens plus different user tokens, so it gets a different hash for each request and is not shared. Below, a free queue holds evictable cached blocks with the least recently used one at the head.

Only full blocks are shared. Our 1,000-token system prompt fills 62 blocks (992 tokens); its last 8 tokens share a block with user text, so that block differs per request and is recomputed. That is why each new request needs 2,000 − 992 = 1,008 tokens of prefill instead of 2,000, which roughly halves prefill work. With 50 users, the other 49 requests point at the same 62 blocks instead of holding copies, which saves 49 × 62 × 2 MiB ≈ 5.9 GiB of cache.

When a request finishes, its blocks return to the free queue but keep their hashes, so a later request can still hit them. New allocations take blocks from the head of the queue, which makes eviction least recently used. A request's blocks are returned in reverse order, so its last blocks, which are the least likely to be shared, are evicted first [7]. The V1 design makes prefix caching nearly free even when nothing hits, which is why it is on by default [3]. In multi-tenant systems, cache_salt limits sharing to requests that use the same salt, which closes a timing side channel. Lesson 24, Prefix Caching, covers cache-aware design in depth.

CUDA graphs and torch.compile

For a small model, launching hundreds of kernels from Python each step can cost as much as running them. vLLM attacks this overhead in two ways. First, torch.compile is on by default: at startup vLLM compiles the model into fused kernels and stores the result in a cache under ~/.cache/vllm/torch_compile_cache, and all compilation finishes before the server accepts a request [8]. Second, vLLM records CUDA graphs for a set of batch sizes and replays a whole step with one launch. The default mode, FULL_AND_PIECEWISE, captures a full graph for pure decode batches and a piecewise graph, with attention left outside, for mixed prefill and decode batches [9]. Lesson 33, GPU Architecture and Attention Kernels, explains why launch overhead and kernel fusion matter.

Six boxes in a row: load weights, profile memory, allocate KV blocks, torch.compile (cached), capture CUDA graphs, and ready, where the health endpoint returns 200. Arrows run left to right. Notes under the boxes say that the compile cache can be copied into the container image and that --enforce-eager skips compilation and graph capture.

Both cost startup time and some memory, as Figure 5 shows. The -O optimization levels (-O0 to -O3, default -O2) trade startup time for speed, and --enforce-eager skips compilation and graph capture entirely for the fastest start and the slowest decode [5]. This matters for autoscaling: Lesson 23, Cold Starts, shows how shipping the compile cache inside the container image shortens the time before a new replica can take traffic.

Quantization

vLLM loads quantized checkpoints in many formats, including FP8, NVFP4, INT8, INT4 GPTQ and AWQ, GGUF, and compressed-tensors checkpoints made with LLM Compressor or NVIDIA Model Optimizer [10]. It can also quantize a BF16 checkpoint to FP8 while loading it: in late-2026 releases the documented online schemes are --quantization fp8_per_tensor and fp8_per_block [10]. An FP8 checkpoint of our model needs about 9.1 GB of weights instead of 16 GB (embeddings and the output layer stay in BF16), which frees about 6.5 GiB for the KV cache and cuts the bytes read in every decode step. Lesson 13 compares the formats and Lesson 16 shows how to check that quality holds.

Parallelism

vLLM supports tensor, pipeline, data, expert, and context parallelism; Lesson 35, Mixture-of-Experts Serving, and Lesson 36, Long-Context Serving, cover the last two. On one node it uses Python multiprocessing; across nodes it uses Ray or its own multi-node launcher (--nnodes, --node-rank, --master-addr) [11]. Figure 6 shows three ways to use an 8-GPU node and the processes each one starts.

Three panels of eight GPU squares. With -tp 8, one engine core drives all eight GPUs as one model copy: 1 API server, 1 engine core and 8 workers make 10 processes. With -tp 2 -dp 4, four engine cores each drive a pair of GPUs: 4 API servers, 4 engine cores, 8 workers and 1 coordinator make 17 processes. With -dp 8, eight engine cores each drive one GPU: 8 plus 8 plus 8 plus 1 make 25 processes.

For an 8B model that fits on one GPU, tensor parallelism mostly adds communication. More replicas, either with -dp or as separate pods behind a router (Lesson 25, Request Routing), give more throughput. Tensor parallelism earns its cost for models that do not fit on one GPU, such as Llama 3.1 70B, whose 141 GB of BF16 weights need at least two H100s (Lesson 18, Tensor Parallelism).

Speculative decoding, LoRA, and structured outputs

Speculative decoding is configured with one JSON flag, for example --speculative-config '{"method": "eagle3", "model": "...", "num_speculative_tokens": 2}'. Supported methods include n-gram matching, suffix decoding, EAGLE and EAGLE-3 draft heads [20], multi-token prediction, and separate draft models [12]. The documentation recommends it for memory-bound traffic at low to medium load; Lesson 15 explains why the gain shrinks as batches grow.

Multi-LoRA serving loads small adapter weights next to one base model. --max-loras (default 1) caps the adapters in one batch and --max-lora-rank (default 16) sets the largest rank, which sizes the reserved memory [6][13]. A request selects an adapter by passing its name as the model field. Lesson 37, Multi-LoRA and Multi-Tenant Serving, covers adapter scheduling in depth.

Structured outputs constrain sampling so the output always matches a JSON schema, regular expression, choice list, or grammar. vLLM uses XGrammar [19] or LLGuidance as the backend and picks one automatically by default [14]. Clients pass a standard response_format with a JSON schema, or vLLM's own structured_outputs field through extra_body. The older guided_json style fields were removed in v0.12.0 [14]. Lesson 38, Structured Output and Tool Calling, goes deeper.

Deploying and Observing vLLM

Launching the server

One command starts the API server, the engine core, and the workers: vllm serve <model> [flags]. The server listens on port 8000 and exposes /v1/chat/completions, /v1/completions, /v1/models, and /v1/responses, plus /health for readiness probes and /metrics for Prometheus. Any OpenAI client works by pointing its base URL at the server. A handful of flags decide most of the capacity and latency:

  • --max-model-len: the longest prompt plus output the server accepts. Llama 3.1 defaults to its 131,072-token context; our requests need 2,500, so we cap it at 8,192 to reject runaway requests early.
  • --gpu-memory-utilization: the share of GPU memory vLLM may use for weights, activations, and KV cache.
  • --max-num-batched-tokens and --max-num-seqs: the per-step budget from Figure 3.
  • --kv-cache-dtype: fp8 doubles cache capacity once evaluations allow it.
  • -tp, -dp: parallelism, as in Figure 6.

Which settings fit our deployment?

For Llama 3.1 8B on one H100 with 50 users, we keep the defaults that already help us (chunked prefill, prefix caching, asynchronous scheduling, CUDA graphs) and change three things. We set --max-model-len 8192, since no request needs more and a smaller limit lets the scheduler admit requests confidently. We pass --gpu-memory-utilization 0.90 explicitly to match our capacity math: about 426,000 tokens, or 170 requests of 2,500 tokens, far above 50 users. Most importantly, we lower --max-num-batched-tokens to 2,048, because the default 8,192-token step can stall every decoding user for at least 133 ms whenever a burst of prompts arrives. With 50 decoders, 1,998 tokens per step remain for prompts, enough for one cached-prefix request per step plus most of the next one. At 5 new requests per second, a new prompt waits only a few steps of roughly 33 ms or more, far inside the 500 ms time-to-first-token target. We do not enable the FP8 KV cache yet; with 50 users the cache is not the bottleneck, so we would take the quality risk for no gain. Lesson 12 benchmarks this configuration at 50 concurrent users.

Observing vLLM: the /metrics endpoint

The API server publishes Prometheus metrics at /metrics on the same port [15]. Counters gain a _total suffix when exported, so the counter vllm:num_preemptions appears as vllm:num_preemptions_total. Figure 7 places the most useful series on a request's timeline.

A request timeline runs from arrival through queued, prefill, and decode to finished. Histograms span the phases: request_queue_time_seconds over the queued phase, time_to_first_token_seconds from arrival to the first token, inter_token_latency_seconds between decode tokens, and e2e_request_latency_seconds over the whole request. Below, gauges describe the engine at any moment: num_requests_waiting, num_requests_running, and kv_cache_usage_perc. Counters for preemptions, prompt and generation tokens, and prefix cache queries and hits sit at the bottom.

Read them in pairs. Rising vllm:num_requests_waiting with vllm:kv_cache_usage_perc near 1 means the cache is full and requests are queuing for memory; a non-zero rate of vllm:num_preemptions_total confirms it. Rising waiting requests with a half-empty cache points at the per-step limits or at CPU starvation instead. The ratio of vllm:prefix_cache_hits_total to vllm:prefix_cache_queries_total is the prefix hit rate; for our traffic it should sit near 992 ÷ 2,000 ≈ 50%. Lessons 28 to 32 build dashboards from these series.

For load testing, vllm bench serve drives any OpenAI-compatible server and reports the mean, median, and chosen percentiles of TTFT, time per output token, and inter-token latency, measured at the client [16]. Two cautions from its documentation: repeated runs against the same server reuse the prefix cache and inflate results, and for production benchmarks the vLLM team recommends GuideLLM.

Strengths and weaknesses

vLLM's strengths are breadth and defaults. It supports more than 200 model architectures and usually runs new open models on release day. It runs on the widest range of hardware of the three engines in this stage, and its V1 goal of "zero configs" means chunked prefill, prefix caching, CUDA graphs, and compilation are already on. It also has the largest community, so problems are often already reported and fixed.

The weaknesses come from the same pace. Defaults change between releases, as the move from 0.90 to 0.92 memory utilization shows, so pin the version and re-read the release notes before upgrading. Startup includes compilation and graph capture, which lengthens cold starts unless you ship the caches. Its prefix cache works in full 16-token blocks and reuses only exact prefixes, while SGLang's radix tree matches at token granularity and is built around multi-call programs. On NVIDIA GPUs, a carefully tuned TensorRT-LLM deployment can reach higher peak throughput for some models, at a higher setup cost (Lesson 11, TensorRT-LLM).

How vLLM differs from SGLang and TensorRT-LLM

  • Prefix cache: vLLM hashes full 16-token blocks; SGLang keeps a token-level radix tree; TensorRT-LLM keeps a radix tree of 32-token blocks with priority-based eviction.
  • Memory knob: vLLM's --gpu-memory-utilization is a share of total GPU memory for everything. SGLang's --mem-fraction-static covers only weights plus the KV pool. TensorRT-LLM's kv_cache_free_gpu_memory_fraction is a share of the memory left after weights and buffers.
  • Admission: vLLM allocates blocks as tokens arrive and preempts when it runs out. TensorRT-LLM by default reserves blocks for a request's maximum length before admitting it. SGLang admits against an estimate of future tokens and retracts requests when the pool fills.

Lesson 11 puts the three engines side by side in one table.

When to choose vLLM

Choose vLLM as the default when you need broad model and hardware support, an OpenAI-compatible server with little tuning, and a large community, which describes most teams serving open models. Look at SGLang when traffic is dominated by long shared prefixes, multi-turn agents, or multi-call programs, and at TensorRT-LLM when you run a fixed model on NVIDIA GPUs at a scale where a few percent of throughput pays for extra engineering.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • The priority scheduling policy (--scheduling-policy priority) for running batch jobs next to interactive traffic (Lesson 39, Batch and Offline Inference) [6].
  • Why V1 schedules decodes before prefills, and how Sarathi-Serve's stall-free batching motivated chunked prefill [17].
  • Iteration-level scheduling from Orca, the idea underneath every continuous-batching engine [18].
  • Disaggregated prefill and decode in vLLM, where KV blocks move between instances through connectors such as NIXL or LMCache (Lesson 34, Disaggregated Prefill and Decode).
  • Using cache_salt to stop one tenant from inferring another tenant's prompts through prefix-cache timing.
  • Why the --prefix-caching-hash-algo default is SHA-256, and when a faster non-cryptographic hash is acceptable [6][7].
  • Sizing CPU for a pod: at least 2 + N physical cores for N GPUs, more with data parallelism [5].
  • Sleep mode and pre-built compile caches for fast scale-up, and their effect on cold-start time (Lesson 23).

  • vLLM V1 runs an API server process, an engine core process with the scheduler and KV cache manager, and one GPU worker process per GPU; a single-GPU replica is 3 processes and needs at least 3 physical CPU cores.
  • The scheduler spends a per-step token budget on decodes first and prompt chunks second. On an H100 the default is 8,192 tokens, which can stall every decoding user of an 8B model for at least 133 ms; 2,048 tokens caps the stall near 33 ms.
  • The KV cache is a pool of 16-token blocks: 2 MiB each for Llama 3.1 8B, or 26,624 blocks in 52 GiB.
  • Automatic prefix caching hashes full blocks with their parent's hash and evicts least recently used blocks; our 1,000-token system prompt shares 62 blocks, halving prefill and saving about 5.9 GiB across 50 users.
  • torch.compile and CUDA graphs are on by default; they speed up decode but lengthen startup, which matters for cold starts.
  • Deploy with vllm serve and a few flags (--max-model-len, --gpu-memory-utilization, --max-num-batched-tokens); watch vllm:num_requests_waiting, vllm:kv_cache_usage_perc, preemptions, and the latency histograms on /metrics.

Introduction

Open a terminal on almost any inference server, run nvidia-smi, and the GPU-Util column will probably read close to 100%. It is tempting to conclude that the GPU is full and to order more hardware. That conclusion is often wrong. GPU-Util measures how much of the time some kernel was running, not how much of the chip that kernel used. A tiny kernel that keeps a handful of the H100's 132 streaming multiprocessors busy reports the same 100% as a matrix multiply that saturates all of them.

GPUs are the largest line item in an inference budget (Lesson 20, Cost per Million Tokens), so misjudging how full they are means buying hardware we do not need or leaving throughput on the table. Figure 1 shows two workloads that nvidia-smi ranks in the wrong order.

Two grids of streaming multiprocessors over one sample period. In workload A, one small kernel keeps a quarter of the SMs busy for the whole period, so nvidia-smi reports 100% while SM activity is 25%. In workload B, full-GPU kernels run 60% of the time with idle gaps, so GPU-Util and SM activity both read 60%. B does 2.4 times more work.

In this lesson, we pin down what GPU-Util reports, replace it with counters that look inside the chip, and introduce model FLOPs utilization (MFU) and model bandwidth utilization (MBU), which say how close we are to the hardware's limits. We work both for Llama 3.1 8B on an H100, list what drags utilization down, weigh the levers that raise it against their latency cost, and show how to profile a serving engine.

Clarifying the Problem

Utilization questions usually arrive disguised as a capacity argument. Here is a typical exchange:

Candidate: Which model, hardware, and serving engine are we talking about?
Interviewer: Llama 3.1 8B Instruct in BF16, one copy per H100 SXM GPU, served with vLLM.

Candidate: What does the traffic look like?
Interviewer: Chat requests with about 2,000 prompt tokens and 500 output tokens. At the daily peak, each GPU handles about 5 requests per second.

Candidate: What are the latency targets?
Interviewer: p95 time to first token under 500 ms, and at least 40 tokens per second for every user, so p95 time per output token under 25 ms.

Candidate: What do the dashboards show today?
Interviewer: nvidia-smi reports GPU-Util between 95% and 100% all day. The team says the GPUs are maxed out and wants to buy more before next month's launch.

Candidate: What tools can we use to dig in?
Interviewer: The DCGM exporter and vLLM's Prometheus metrics in production, and a staging machine where we can run profilers.

The question underneath is: how much of this GPU's capacity are we really using, and can it serve more traffic without breaking the latency targets? To answer it, we need a better definition of utilization than nvidia-smi's.

What "GPU Utilization" Really Measures

The nvidia-smi definition

NVIDIA defines the GPU-Util figure precisely: it is the "percent of time over the past sample period during which one or more kernels was executing on the GPU", with a sample period between 1/6 of a second and 1 second depending on the product [1]. DCGM reports the same quantity as DCGM_FI_DEV_GPU_UTIL (field 203), and it is the default "GPU utilization" panel on most dashboards.

The test is yes-or-no over time: any running kernel makes that instant busy, however little of the GPU it occupies. A memory copy, a single-block reduction, or a communication kernel waiting for its peers counts the same as a full-chip matrix multiply. The "memory utilization" column has the same weakness: it is the fraction of time memory was read or written, not the share of bandwidth used [1].

What is inside the GPU

An H100 has 132 streaming multiprocessors (SMs), each holding up to 64 resident warps of 32 threads [2], with tensor cores for matrix math and CUDA cores for everything else. All SMs share 80 GB of HBM3 at 3.35 TB/s. The hardware spreads a kernel's thread blocks across the SMs, so a kernel with fewer blocks than SMs leaves part of the chip dark for as long as it runs. Lesson 33, GPU Architecture and Attention Kernels, covers the hardware in depth.

"Is the GPU busy?" therefore splits into several questions: are kernels running (time), how many SMs do they cover (space), how many warps sit on each SM (depth), are the tensor cores and memory doing work, and how much of that work becomes tokens? Figure 2 lines up the metrics that answer each one.

A five-row table of metrics. GPU-Util asks whether any kernel was running and is fooled by one tiny kernel. SM activity asks what share of SMs had work, but stalled warps still count. SM occupancy asks how many warps sit on each SM, but higher is not always faster. Tensor and DRAM activity ask whether the math pipes or memory were busy, but busy cycles are not useful work. MFU and MBU ask how much model work was done against the peak and need a FLOP and byte model.

Hardware counters that look inside

NVIDIA's Data Center GPU Manager (DCGM) reads the GPU's hardware performance counters and exposes them as profiling metrics [3]. Five matter for inference:

  • Graphics engine activity (DCGM_FI_PROF_GR_ENGINE_ACTIVE, field 1001): time the compute engine was active, with GPU-Util's blind spot.
  • SM activity (DCGM_FI_PROF_SM_ACTIVE, field 1002): the fraction of time at least one warp was active on an SM, averaged over all SMs. A kernel that uses a fifth of the SMs for the whole interval scores 0.2. NVIDIA's guidance is that 0.8 or more is necessary, but not sufficient, for effective use, and that below 0.5 likely indicates ineffective use [3].
  • SM occupancy (DCGM_FI_PROF_SM_OCCUPANCY, field 1003): resident warps as a fraction of the SM's maximum. More warps help hide memory latency, but higher is not automatically faster [3].
  • Tensor pipe activity (DCGM_FI_PROF_PIPE_TENSOR_ACTIVE, field 1004): the fraction of cycles the tensor-core pipe was active, the closest hardware signal to "doing matrix math".
  • DRAM activity (DCGM_FI_PROF_DRAM_ACTIVE, field 1005): the fraction of cycles the memory interface was sending or receiving data. NVIDIA notes that about 0.8 is the practical peak [3].

These counters still measure activity, not useful work: tensor cores can be busy multiplying padding, and memory can be busy re-reading data a better kernel would have kept on chip. To learn how much of the GPU turns into tokens, we need ratios defined by the model itself.

MFU and MBU: Utilization in Model Terms

Model FLOPs utilization

Model FLOPs utilization (MFU) was introduced in the PaLM paper as an implementation-independent measure of efficiency: the observed throughput divided by the throughput the hardware could reach at peak FLOPS, counting only the operations the model requires [5]. For inference it becomes:

\text{MFU} = \frac{\text{tokens per second} \;\times\; \text{FLOPs per token}}{\text{peak FLOPS}}

A dense transformer with N parameters needs about 2N FLOPs per token in the forward pass, one multiply and one add per weight. For Llama 3.1 8B that is 2 × 8.03 billion ≈ 16.06 GFLOPs per token. Attention over the context adds a little more: for a 2,000-token prompt, about 0.5 GFLOPs per token on average, or 3%, so we leave it out of quick estimates.

Because MFU counts only the FLOPs needed for the tokens users receive, it excludes wasted work such as padding, recomputation after preemption, or redundant math, which makes it more honest than any hardware counter.

Model bandwidth utilization

Decode is limited by memory bandwidth, not by FLOPs (Lesson 2, Prefill vs Decode). Each decode step must stream every weight and every cached key and value through the memory system once. Model bandwidth utilization (MBU), defined by the Databricks inference team, measures how close a step comes to that limit [6]:

\text{MBU} = \frac{(\text{weight bytes} + \text{KV cache bytes}) \div \text{TPOT}}{\text{peak memory bandwidth}}

TPOT, the time per output token, equals one decode step for a batch of requests. The numerator is the bandwidth the model needs, so MBU is the decode lower bound from Lesson 3, KV Cache, turned into a ratio: a step that took exactly as long as reading its bytes at full speed would score 100%.

Which ratio applies: the roofline

The two ratios are the two sides of the roofline model [7]. A workload's arithmetic intensity is the number of FLOPs it performs per byte it moves. Below the GPU's ridge point, a workload is limited by bandwidth; above it, by compute. For an H100 in BF16, the ridge sits at 989 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOPs per byte.

  • Prefill pushes thousands of prompt tokens through each read of the weights. A 2,000-token prompt does 2,000 × 16.06 GFLOPs ≈ 32 TFLOPs of work for about 16.3 GB of weight and KV traffic, roughly 2,000 FLOPs per byte, far above the ridge. MFU is the right lens.
  • Decode at batch size B does B \times 2N FLOPs per step while reading the weights once plus every request's KV cache. With 2,250 tokens of context per request, that is about 1 FLOP per byte at batch 1 and about 29 at batch 64. Both sit far left of the ridge, so MBU is the right lens.
A log-log roofline chart for an H100 in BF16. A slanted memory roof at 3.35 terabytes per second meets a flat compute roof at 989 TFLOPS at about 295 FLOPs per byte. Decode at batch 1 sits at about 1 FLOP per byte and 2.2 TFLOPS, just under the memory roof (MBU 68%). Decode at batch 64 sits at about 29 FLOPs per byte and 64 TFLOPS (MBU 65%). Prefill sits near 2,000 FLOPs per byte and 514 TFLOPS, under the compute roof (MFU 52%).

Figure 3 places our three examples on the roofline. The slanted roof caps decode: at batch 1, the best possible is 3.35 TB/s × 0.98 FLOPs per byte ≈ 3.3 TFLOPS, or 0.33% of peak. No kernel tuning lifts decode MFU above that; only higher arithmetic intensity does, through bigger batches or fewer bytes per token.

Worked example: prefill MFU

Suppose a prefill-only benchmark on our H100 (2,000-token prompts, one output token each, many prompts in flight) measures 32,000 prompt tokens per second. This is an example measurement for the arithmetic; Lesson 6, Lab - Measure TTFT and Throughput, shows how to take your own.

  • FLOPs per token: 2 × 8.03 billion = 16.06 GFLOPs.
  • Achieved compute: 32,000 × 16.06 GFLOPs ≈ 514 TFLOPS.
  • MFU: 514 ÷ 989 ≈ 52%.

For comparison, Pope et al. reached 76% MFU processing input tokens at large batch for PaLM 540B [8]. An 8B model has smaller matrices and proportionally more time in attention and normalization, so half of peak is reasonable, with room left.

Worked example: decode at batch 1

Now run a single request: a 2,000-token prompt that generates 500 tokens. Suppose we measure 140 tokens per second, a TPOT of 7.14 ms. The context grows from 2,000 to 2,500 tokens during decode, so it averages about 2,250 tokens.

  • Weight bytes per step: 8.03 billion × 2 bytes = 16.06 GB.
  • KV bytes per step: 2,250 tokens × 128 KiB ≈ 0.29 GB.
  • Bandwidth needed: 16.35 GB × 140 steps per second ≈ 2.29 TB/s.
  • MBU: 2.29 ÷ 3.35 ≈ 68%.
  • MFU: 140 × 16.06 GFLOPs ≈ 2.25 TFLOPS, or 0.23% of 989 TFLOPS.

The same GPU is at 68% of its memory limit and 0.23% of its compute limit, while nvidia-smi reads close to 100%. All three are correct answers to different questions; only MBU says how close decode is to its real limit. The Lesson 3 lower bound agrees: 16.35 GB ÷ 3.35 TB/s ≈ 4.9 ms per step, at most about 205 tokens per second, against the 140 we measured.

Worked example: decode at batch 64

Now 64 requests decode together, and we measure a TPOT of 16 ms. Each user sees 62.5 tokens per second, and the GPU produces 4,000 tokens per second in total.

  • Bytes per step: 16.06 GB of weights + 64 × 0.29 GB of KV cache ≈ 34.9 GB.
  • Bandwidth needed: 34.9 GB ÷ 16 ms ≈ 2.18 TB/s, so MBU ≈ 65%.
  • MFU: 4,000 × 16.06 GFLOPs ≈ 64 TFLOPS, or 6.5%. The roof allows at most about 10% at this intensity.
A bar chart with three groups. Prefill at 32,000 prompt tokens per second: GPU-Util about 100%, MFU 52%. Decode at batch 1, 140 tokens per second: GPU-Util about 100%, MFU 0.23%, MBU 68%. Decode at batch 64, 4,000 tokens per second: GPU-Util about 100%, MFU 6.5%, MBU 65%. GPU-Util is illustrative.

Figure 4 puts the three cases side by side. Batching multiplied decode throughput, and with it MFU, by about 28× (0.23% to 6.5%), while MBU barely moved: the weights are read once per step whether 1 or 64 requests share them. This is the whole economic case for batching, and it is invisible in GPU-Util, which reads near 100% in all three cases.

This explains a common puzzle: small-batch decode shows high GPU-Util and tiny MFU at once. The GPU is genuinely busy streaming 16 GB of weights to produce one token, while its tensor cores, which supply almost all of its FLOPS, wait for data.

When someone says "the GPU is at 100%", ask "100% of what?" Then compute MBU for decode and MFU for prefill from tokens per second. Two lines of arithmetic usually settle the argument.

What Lowers Utilization

Utilization is lost in two ways. Either the GPU sits idle between kernels, leaving gaps on the timeline, or kernels run but do little useful work per byte or per FLOP. Figure 5 shows the first kind for a small-batch decode loop.

Three CPU and GPU timelines over 15 milliseconds. In eager mode, the CPU schedules, launches about 300 kernels one by one, and samples, and the GPU shows many small gaps plus long idle periods, for about 7.5 ms per step. With CUDA graphs, one launch replaces the many, the GPU runs one dense block, and idle periods remain only while the CPU schedules and samples, for about 6.2 ms per step. With CUDA graphs and asynchronous scheduling, the CPU prepares the next step while the GPU runs the current one, leaving only tiny gaps, for about 4.1 ms per step.

Small batches

As the worked examples showed, a decode step costs almost the same at batch 1 and at batch 64, so small batches waste most of each weight read. Batches stay small when traffic is light, when --max-num-seqs caps the number of running requests too low, or when the KV cache is too small to admit more requests (Lesson 3, KV Cache).

CPU and Python overhead

Every step, the scheduler picks requests and builds input tensors; after the forward pass, the engine samples, detokenizes, checks stop conditions and streams text. If this CPU work runs between GPU steps, the GPU waits, and the smaller the model and batch, the larger the share of time lost.

Kernel launch gaps and missing CUDA graphs

One decode step of an 8B model runs hundreds of small kernels (normalization, projections, attention, activations, residual adds) across 32 layers, and each launch costs CPU time. NVIDIA's CUDA Graphs article measured a 2.9 µs kernel costing 9.6 µs per kernel when launched one at a time with synchronization, and 3.4 µs when the same kernels were captured into a graph [9]. When kernels are this short, launch overhead rather than the GPU sets the pace. CUDA graphs record a whole step once and replay it with a single launch. vLLM captures graphs by default, and --enforce-eager disables them [10]: handy for debugging, costly in production. Lesson 33 also covers kernel fusion, which removes launches altogether.

Communication in tensor parallelism

With Megatron-style tensor parallelism, each layer ends its attention and MLP blocks with an all-reduce across GPUs [11], so a 70B model's 80 layers mean 160 all-reduces per decode step. The messages are small, so fixed latency dominates; a GPU waiting for its peers does no math while its communication kernels keep GPU-Util high. vLLM's tuning guide warns that a larger tensor-parallel size may cause excessive synchronization overhead [12]; Lesson 18, Tensor Parallelism, covers when the trade pays.

Padding

Engines that batch fixed-shape tensors pad short sequences up to the longest one. A batch holding a 200-token prompt and a 2,000-token prompt pads the short one with 1,800 tokens, and the GPU computes all of them. Tensor activity looks excellent, but MFU, which counts only real tokens, exposes the waste. Continuous batching with packed, variable-length batches avoids almost all padding (Lesson 7, Continuous Batching).

Preemption

When the KV cache fills up, vLLM preempts requests and later recomputes them when space frees up [12]. Recomputation keeps every hardware counter busy while producing no new tokens. Frequent preemption shows up as busy GPUs, falling throughput, a rising vllm:num_preemptions_total counter, and latency spikes for the preempted users.

Idle time between requests

Finally, the GPU may simply have nothing to do: overnight, a GPU sized for the daytime peak runs small batches or none. Here GPU-Util is honest, and the fix lies in the fleet: scale replicas with load (Lesson 22, Autoscaling) or fill quiet hours with batch work (Lesson 39, Batch and Offline Inference). Lesson 20 turns this idle time into cost.

Raising Utilization, and What It Costs

Most ways of raising utilization trade per-request latency for throughput, but a few are free, so we start there.

Free wins: remove the gaps

Keep CUDA graphs on and keep the CPU off the critical path. Recent vLLM versions enable asynchronous scheduling (--async-scheduling) unless an incompatible option is set: the scheduler prepares step n+1 while the GPU runs step n, which the documentation says "helps to avoid gaps in GPU utilization" [10]. The third timeline in Figure 5 shows the effect. Both shorten every step, improving latency and throughput together.

Bigger batches

Raising the number of requests that decode together is the most powerful lever, and it is not free. Each extra request adds its KV cache to every step's reads, so every user's TPOT grows. Figure 6 uses the decode lower bound at a fixed 65% MBU to show the trade for our model. Going from batch 1 to batch 64 raises throughput from about 130 to about 4,000 tokens per second, while TPOT grows from 7.5 ms to 16 ms. Somewhere past batch 128, TPOT crosses our 25 ms target even before any prompt work is added.

Two stacked charts against batch size from 1 to 160. Top: output tokens per second rise steeply and then flatten, from about 130 at batch 1 to about 4,000 at batch 64 and 5,500 at batch 160, with decode MFU at 0.2%, 6.5% and 9.0%. Bottom: time per output token for pure decode rises linearly from 7.5 ms to 29 ms and crosses a 25 ms target near batch 128. A marker at about 53 requests shows steps stretched to about 21 ms once prompt chunks are mixed in at 5 requests per second.

Mixing prefill into decode steps

Chunked prefill splits long prompts into chunks and runs them in the same step as ongoing decodes, so prompt processing uses the compute that memory-bound decode steps leave idle [13]. vLLM enables it by default where possible. Its main knob, --max-num-batched-tokens, caps the tokens per step. vLLM's tuning guide notes that smaller values such as 2,048 give better inter-token latency, larger values give better TTFT, and values above 8,192 favor throughput, especially for small models on large GPUs [12].

In our deployment, 5 requests per second bring 10,000 prompt tokens per second. At 32,000 prompt tokens per second, they take 31% of GPU time. Spread over the decode steps, that stretches each step from about 14.5 ms of pure decode to about 21 ms, with about 53 requests decoding at once (the purple marker in Figure 6). The same model also shows how sharp the edge is: at 5.5 requests per second, the average step grows to about 26 ms, already over target.

Fewer bytes per token, more work per byte

Lower-precision weights and KV cache (Lesson 13, Quantization - FP8, INT8 and 4-bit) cut the bytes each decode step must read. With FP8 weights and an FP8 KV cache, a batch-64 step reads about 9.1 GB + 9.4 GB ≈ 18.5 GB instead of 34.9 GB (the FP8 checkpoint keeps embeddings and the output layer in BF16), so at the same MBU it takes about half as long. Throughput rises and latency falls together, at the cost of a quality check.

Speculative decoding (Lesson 15, Speculative Decoding) attacks the other side: a draft model proposes several tokens and the large model verifies them in one pass, so each weight read yields more than one token. The original paper reports 2–3× faster generation on T5-XXL [14]. It helps most at small batch, where compute sits idle.

Which utilization target fits our deployment?

Back to the interviewer's GPUs. A GPU-Util of 95–100% told us nothing. Suppose staging confirms the example measurements: about 52% MFU in prefill and 65% MBU in decode, with CUDA graphs and asynchronous scheduling on and no long CPU gaps on the Nsight timeline. Then the GPUs are busy where it matters, on memory bandwidth during decode, and low decode MFU is the roofline at work, not a defect.

So we do not optimize for a utilization number. We optimize for goodput: the most requests per second each GPU serves while p95 TTFT and TPOT stay within target. MFU and MBU are diagnostics; the latency targets decide where to stop batching. At 5 requests per second our steps take about 21 ms against a 25 ms target, and half a request per second more breaks it. The team is right, for the wrong reason: at this target, the GPUs are nearly full.

Before buying more GPUs, we change the bytes rather than the batch: enable FP8 weights and an FP8 KV cache, confirm quality on the evaluation set, and re-measure. In the simple model of Figure 6, halving the bytes lets the same GPU carry about 8 requests per second at a similar step time; real gains are usually smaller, so we measure before counting on it. Prefix caching (Lesson 24, Prefix Caching) can also shrink the 31% of GPU time spent on prefill.

Profiling: Finding Where the Time Goes

When MFU or MBU is lower than expected, profile from coarse to fine, as Figure 7 shows. Each step is more expensive to run than the last, so go deeper only when the step before points there.

Four boxes in a row with arrows: 1, fleet view with DCGM metrics, asking whether the GPU is idle or busy; 2, model ratios, MFU for prefill and MBU for decode, asking how far from the roof; 3, an Nsight Systems timeline, asking where the holes are; 4, kernels with the PyTorch profiler or Nsight Compute, asking which kernel dominates. A fifth box, fix one thing, loops back to step 1.

Fleet view and model ratios

DCGM metrics sampled every second tell us whether a GPU is idle, busy but shallow (high GPU-Util, low SM activity), or genuinely working (high DRAM or tensor activity). Next, compute MFU and MBU from the engine's token counters, such as rate(vllm:generation_tokens_total[1m]). Recent vLLM versions started with --enable-mfu-metrics also export their own FLOP and byte estimates as counters [15]; dividing their rates by the GPU's peaks gives MFU and an MBU-style ratio over time.

Nsight Systems: the timeline

Nsight Systems (nsys) records CPU threads, CUDA API calls, kernels, memory copies and NCCL communication on a single timeline [16]. Gaps between kernels, long CPU sections before each step, and NCCL kernels waiting for peers are visible at a glance. vLLM's profiling guide recommends --trace-fork-before-exec=true so that worker processes are traced, --cuda-graph-trace=node so that kernels inside CUDA graphs appear individually, and --capture-range=cudaProfilerApi so that a running server is captured only while a benchmark has profiling switched on [17].

PyTorch profiler: which operators and which code

The PyTorch profiler records CPU and CUDA time per operator, summarizes it in a table, and exports a trace that opens in Perfetto or chrome://tracing [18]. It answers "which operations dominate GPU time, and how much CPU time surrounds them?" vLLM can run it inside the server through --profiler-config and the /start_profile and /stop_profile endpoints [17], as the In Practice section shows. For a single kernel's memory throughput and tensor-core use, Nsight Compute goes one level deeper.

Traces grow fast; vLLM's guide advises sending only a few requests while profiling [17]. Profilers also slow the engine down, so take throughput and latency numbers from a separate, unprofiled run.

PARAMS = 8.03e9 # parameters WEIGHT_BYTES = PARAMS * 2 # BF16 weights KV_BYTES_PER_TOKEN = 131_072 # 128 KiB per token (Lesson 3, KV Cache) PEAK_FLOPS = 989e12 # dense BF16 PEAK_BW = 3.35e12 # HBM3 bytes per second def mfu(tokens_per_s: float) -> float: """Useful model FLOPs per second as a share of peak (2 FLOPs per parameter per token).""" return tokens_per_s * 2 * PARAMS / PEAK_FLOPS def mbu(tpot_s: float, batch: int, avg_context_tokens: int) -> float: """Bytes one decode step must read, divided by the step time, as a share of peak bandwidth.""" step_bytes = WEIGHT_BYTES + batch * avg_context_tokens * KV_BYTES_PER_TOKEN return step_bytes / tpot_s / PEAK_BW # Example measurements from this lesson; replace them with your own. print(f"prefill MFU {mfu(32_000):.1%}") # 52.0% print(f"decode@1 MBU {mbu(1 / 140, 1, 2_250):.1%} MFU {mfu(140):.2%}") # 68.3% 0.23% print(f"decode@64 MBU {mbu(0.016, 64, 2_250):.1%} MFU {mfu(64 / 0.016):.1%}") # 65.2% 6.5% # The memory roof caps decode MFU at (FLOPs per byte x bandwidth) / peak FLOPS. for batch in (1, 64): step_bytes = WEIGHT_BYTES + batch * 2_250 * KV_BYTES_PER_TOKEN intensity = batch * 2 * PARAMS / step_bytes print(f"batch {batch:>2}: {intensity:5.1f} FLOPs/byte, " f"MFU ceiling {intensity * PEAK_BW / PEAK_FLOPS:.2%}") # 0.33%, 9.97% # 1. Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Hardware FLOPs utilization (HFU) versus MFU: HFU also counts recomputed work, which is why the PaLM authors preferred MFU as the consistent measure [5].
  • Goodput, the rate a GPU can serve within both TTFT and TPOT constraints, as the target DistServe optimizes by running prefill and decode on separate GPUs [19] (Lesson 34, Disaggregated Prefill and Decode).
  • Why MBU rarely approaches 100%: DCGM itself treats about 0.8 as the practical peak of DRAM activity [3], so a decode at 65–70% MBU has little kernel-level headroom left.
  • Clocks and power: a GPU held below its boost clock by power or thermal limits cannot reach the datasheet peak, so its MFU looks lower. DCGM reports SM clock and power draw too.
  • Mixture-of-experts models: MFU should count only the active parameters per token, and MBU depends on how many experts a batch touches (Lesson 35, Mixture-of-Experts Serving).
  • Sharing one GPU among several low-traffic models or adapters, which raises fleet utilization without changing any kernel (Lesson 37, Multi-LoRA and Multi-Tenant Serving).

Summary

Mind map summarizing the GPU utilization lesson: why GPU-Util misleads, the DCGM counters, MFU and MBU with worked numbers, causes of lost utilization, levers and their latency cost, and the profiling workflow.
  • nvidia-smi's GPU-Util is the fraction of time any kernel was running. A kernel that uses a few SMs reads 100%, so it can only tell you whether a GPU is idle.
  • DCGM's SM activity, SM occupancy, tensor activity and DRAM activity (fields 1002–1005) look inside the chip, but they measure activity, not useful work.
  • MFU = tokens/s × 2N ÷ peak FLOPS judges compute-bound prefill; MBU = (weight + KV bytes) ÷ TPOT ÷ peak bandwidth judges memory-bound decode.
  • For Llama 3.1 8B on an H100: prefill at 32,000 tokens/s is 52% MFU; decode at batch 1 (140 tokens/s) is 68% MBU but 0.23% MFU; decode at batch 64 (4,000 tokens/s) is 65% MBU and 6.5% MFU.
  • Utilization leaks through small batches, CPU and Python overhead, kernel launch gaps without CUDA graphs, tensor-parallel communication, padding, preemption and idle time.
  • CUDA graphs and asynchronous scheduling are free; bigger batches and larger prefill chunks cost TPOT; FP8 and speculative decoding change the bytes or work per token.
  • Optimize for goodput under the latency targets, use MFU and MBU as diagnostics, and profile coarse to fine: DCGM, model ratios, Nsight Systems, then kernels.

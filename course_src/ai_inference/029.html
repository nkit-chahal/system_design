Introduction

Every request to an LLM service waits somewhere before the model starts working on it. It may sit in a load balancer, in an API gateway, or, most often, in the serving engine's own scheduler queue while the GPU finishes other work. The number of requests waiting at one of these points is its queue depth.

Queue depth matters because waiting time is part of the user's latency. Time to first token is queueing plus prefill (Lesson 4, Time to First Token), and prefill rarely changes much from minute to minute. When TTFT suddenly jumps from 0.3 seconds to 8 seconds, the extra time is almost always spent in a queue. A queue also grows before latency metrics react, because a waiting request has not produced a latency sample yet. That makes queue depth one of the most useful early-warning signals in LLM serving.

Requests flow from clients through a load balancer, an API gateway, and an engine API server into the engine's waiting queue, then into the running batch on the GPU. The load balancer and gateway hold short queues of in-flight connections. The engine's waiting queue is where most waiting happens. The running batch is limited by KV cache blocks and the maximum number of sequences, and preemption sends requests from the running batch back to the waiting queue.

In this lesson, we look at where queues form in a serving stack, use Little's law to turn queue depth into seconds of waiting, explain why latency explodes as a server approaches full utilization, read the queue signals that vLLM and SGLang export, and design autoscaling triggers, load shedding, and alerts around them.

Clarifying the Problem

Queue questions in interviews usually start from an incident. Here is a typical exchange between a candidate and an interviewer:

Candidate: What are we serving, and on what hardware?
Interviewer: Llama 3.1 8B Instruct in BF16 with vLLM, one replica per H100, behind a load balancer, an API gateway, and a router. The autoscaler runs five replicas at average load (Lesson 22, Autoscaling).

Candidate: What does the traffic look like?
Interviewer: About 1,000 chat requests per minute on average, from about 8 to 33 requests per second over the day, each with roughly 2,000 prompt tokens and 500 output tokens. Product launches bring spikes of up to ten times the average.

Candidate: What latency do we promise?
Interviewer: A p95 time to first token under 500 ms and a p95 time per output token under 25 ms. A typical request sees about 0.3 seconds to the first token. One replica meets both targets up to about 5 requests per second, about 53 concurrent streams at about 21 ms per decode step (Lesson 19, GPU Utilization), and we run vLLM with --max-num-seqs 53, the capacity limit from Lesson 22.

Candidate: What do we monitor today?
Interviewer: GPU utilization and p95 latency. Last week TTFT was bad for ten minutes before anyone noticed. GPU utilization read 100% before, during, and after the incident.

Candidate: Are we allowed to delay or reject some requests?
Interviewer: Free-tier traffic can be delayed or rejected under load. Paid traffic should not be.

The question underneath is: which queue signals tell us that TTFT is about to break, what thresholds should we use, and what should the system do automatically when they fire? To answer it, we first need to know where requests actually wait.

Where Requests Wait

The queues in a serving stack

Figure 1 shows the path of a request. Each box can hold requests that are not yet being worked on:

  • Load balancer: holds connections while it picks a backend. With healthy backends this wait is microseconds to milliseconds.
  • API gateway: authenticates, applies rate limits (Lesson 26, Rate Limiting), and may cap in-flight requests per tenant. It sees how many requests are in flight, but not whether they are waiting or running inside the engine.
  • Engine API server: accepts the HTTP request, applies the chat template, tokenizes, and hands the request to the engine core. It accepts almost everything immediately, so its own queue is short.
  • Engine waiting queue: the scheduler's list of requests that have not started prefill. This is where nearly all LLM queueing happens.
  • Running batch: the requests that the scheduler has admitted into the continuous batch (Lesson 7, Continuous Batching). Its size is limited by free KV cache blocks (Lesson 3, KV Cache, and Lesson 8, PagedAttention) and by the engine's maximum number of sequences (--max-num-seqs in vLLM).

The engine queue is special because by default it is unbounded. vLLM and SGLang accept every request over HTTP and park it in the waiting queue until there is room in the batch. Upstream components therefore see a healthy, fast-responding server that is quietly accumulating a backlog. This is why queue signals must come from the engine itself.

Two ways to be full

An LLM engine can be full in two different senses. It is slot-full when the KV cache has no free blocks: the scheduler cannot admit another request, so new arrivals wait. It is step-full when every extra request in the batch makes each decode step slower: the running batch is itself a kind of queue, because every running request shares the same GPU steps. More running requests mean more tokens per second in total, but a slower stream for each user (Lesson 5, Tokens per Second). For our replica the step limit binds first: Lesson 19 found about 53 streams decoding at about 21 ms per step at 5 requests per second, and steps passing the 25 ms target at 5.5 requests per second, while the KV cache would not fill until about 170 requests (Lesson 3).

Slot-fullness shows up as a growing waiting queue and a longer TTFT. Step-fullness shows up as a longer time per output token, and by default it produces no queue at all, because the engine keeps admitting requests until the cache is full. That is why Lesson 22 sets --max-num-seqs to the capacity of 53: the engine then turns step-fullness into slot-fullness, and excess load becomes visible as waiting requests. Little's Law and Queueing Intuition

Little's law

Little's law connects three averages for any stable system: the average number of items inside it, L, equals the average arrival rate, \lambda, times the average time each item spends inside, W [1]:

L = \lambda W

It holds whatever the arrival pattern or service order, as long as we look at long-run averages and the system is not growing without bound. It applies to any boundary we draw: the whole fleet, one replica, or just the waiting queue.

Apply it to our fleet. The arrival rate is 1,000 requests per minute, or about 16.7 per second. A request spends about 0.3 s reaching its first token and then 499 more tokens at about 21 ms each (Lesson 19), so W = 0.3 + 0.021 \times 499 \approx 10.8 s. Figure 2 shows the result.

Requests arrive at 16.7 per second, spend 10.8 seconds in the system, and so about 180 requests are in flight across the fleet. Split across five replicas, each replica sees 3.3 requests per second and holds about 36 requests, which is 68 percent of its limit of 53 and about a fifth of the 170 chat requests that its KV cache could hold.
  • Fleet: L = 16.7 \times 10.8 \approx 180 requests in flight at any moment.
  • Per replica: about 36 requests, with 3.3 arriving per second.
  • Headroom: each replica runs at about 68% of its limit of 53 in flight, and at about a fifth of the 170 chat requests its KV cache could hold (Lesson 3).

Reading queue depth as time

Apply the same law to the waiting queue alone. If L_q requests are waiting and requests leave the queue at rate \lambda, each one waits on average W_q = L_q / \lambda. This turns a count into seconds, which is what users feel.

Our TTFT target is 0.5 s and a typical request needs 0.3 s without queueing, so the queue may add at most about 0.2 s. At 3.3 requests per second per replica, L_q = 0.2 \times 3.3 \approx 0.7. On a normal minute, even one waiting request per replica, sustained, uses up the whole latency budget. The same count means different things at different rates: four waiting requests cost about 1.2 s of wait at 3.3 requests per second, but 0.8 s when the replica is draining 5 requests per second. Thresholds on raw queue depth are therefore fragile. It is better to divide by the current rate and alert on the estimated wait.

During overload the rate that matters is the rate at which requests leave the queue, not the rate at which they arrive. When the batch is full, a new request can start only when another finishes, so the useful estimate is:

\text{estimated wait} \approx \frac{\text{waiting requests}}{\text{completions per second}}

In steady state completions equal arrivals, so this is Little's law. During a spike it predicts the wait of a request that arrives now, which is exactly the TTFT problem we want to see coming.

The ceiling of one replica

Little's law also turns a concurrency limit into a throughput limit. With --max-num-seqs 53 and requests that last about 10.8 s at about 21 ms per step, a full replica completes about 53 / 10.8 \approx 4.9, or about 5 requests per second, the same capacity Lesson 19 found and Lesson 20, Cost per Million Tokens, prices. Without the cap, the replica would keep admitting requests until its KV cache held about 170, completing more requests per second but with every stream slower than the target.

On an average minute each replica runs at \rho = 3.3 / 5 \approx 0.67 of that ceiling. A tenfold spike changes the picture completely: each of the five replicas receives 33.3 requests per second but can start only 5, so its queue grows by about 28 requests every second. After 10 seconds, about 283 requests are waiting, and a newcomer can expect to wait 283 / 5 \approx 57 s for its first token. No autoscaler can react within those 10 seconds, which is why Stage 5 pairs autoscaling with admission control.

Convert every queue number into seconds before judging it. "Ten requests waiting" sounds small; "ten requests waiting at 4 requests per second is 2.5 seconds of added TTFT" shows you understand what the user will feel.

Why latency explodes near full utilization

Queueing theory explains why a server that looks fine at 70% busy can be unusable at 95%. The simplest model, the M/M/1 queue, has one server, random (Poisson) arrivals, and random (exponential) service times with mean S. At utilization \rho, the average time in the system is:

W = \frac{S}{1 - \rho}

At 50% utilization a request takes twice its service time; at 80%, five times; at 90%, ten times; at 95%, twenty times. The curve is flat for most of its range and then turns almost vertical, as Figure 3 shows.

Two curves of time in system, as a multiple of service time, against utilization from 0 to 1. The M/M/1 curve rises from 1 to 2 at 50 percent, 5 at 80 percent, 10 at 90 percent and 20 at 95 percent. The M/M/8 curve, eight parallel servers, stays near 1 until about 80 percent, reaches 1.9 at 90 percent and 3.1 at 95 percent, then also turns vertical. A note says these are queueing models, not measurements of an LLM engine.

An LLM engine is not an M/M/1 queue. It runs many requests in parallel, and its service time depends on the batch size. A model with many parallel servers, such as M/M/8 in Figure 3, is closer: it stays flat longer and then turns more sharply. That matches what operators see. An engine at 80% of its slot capacity looks perfectly healthy, while one at 95% is a few seconds of bad luck away from a large backlog.

Variability makes things worse. Kingman's approximation for a single-server queue says the average wait grows with the squared coefficients of variation of inter-arrival and service times [2]. LLM traffic has both kinds of variability in abundance: bursty arrivals, prompts from 50 to 30,000 tokens, and outputs from one token to thousands. The practical rule is to run well below a replica's measured ceiling; Lesson 22's autoscaler targets 75% of it, 40 of 53 requests in flight.

Engine-Level Queue Signals

The four signals

The engine knows exactly how many requests are waiting, how many are running, and how full its cache is. Both vLLM and SGLang export these as Prometheus metrics on their /metrics endpoint (SGLang needs --enable-metrics) [3][5]. Figure 4 places each signal on the engine's internal state machine.

Arriving requests enter the waiting queue, measured by waiting requests and queue time. The scheduler admits them into the running batch when KV cache blocks are free; the running batch is measured by running requests and KV cache usage. When the cache runs out, the scheduler preempts a running request back to the waiting queue, counted by the preemption counter. Finished requests leave and are counted by the request success counter.
  • Waiting requests: requests the scheduler has not started, including preempted ones that must start again. A nonzero value that persists means the engine is slot-full.
  • Running requests: requests in the current batch. Compare it with the replica's limit (53 for us) to see how close the replica is to full before anyone waits.
  • KV cache usage: the fraction of KV blocks in use, from 0 to 1. It rises with both the number of running requests and their lengths. Our 53 chat requests fill less than a third of the cache, so for us it matters when long documents arrive: 13 requests at 32K tokens fill it completely (Lesson 3).
  • Preemptions: a counter of requests evicted from the batch to make room. The PagedAttention paper describes two ways to preempt, swapping the cache out and recomputing it later [7]; vLLM's current engine recomputes (Lesson 3). Each preemption throws away work, so a rising rate means the engine admits more than its cache can hold, and the preempted users see latency spikes.

Recent vLLM versions also split the waiting count by reason, vllm:num_requests_waiting_by_reason, with reason="capacity" for requests waiting for room in the batch and reason="deferred" for requests held back by temporary constraints such as a LoRA adapter budget or a KV transfer [3].

Reading the signals together

No single signal tells the whole story, but a few combinations cover most incidents:

  • Waiting near 0, running below the limit: healthy, with headroom.
  • Waiting growing, running pinned at --max-num-seqs, KV usage moderate: the replica is at its load-tested capacity. With the limit set as in Lesson 22, this is the intended overload signal: add replicas or shed load.
  • Waiting growing, KV usage near 100%, running below the limit: memory binds first, usually because long prompts arrived and each request holds more cache than the capacity plan assumed.
  • Preemptions rising with KV usage above 95%: the cache is thrashing. Long requests are being evicted and recomputed, wasting GPU time exactly when it is scarce.
  • Waiting growing, running low, GPU mostly idle: the engine is stuck or starved by something other than the GPU, such as a hung worker or a CPU-bound tokenizer. Lesson 30, GPU Metrics, shows how to confirm this.

Leading versus lagging indicators

A leading indicator moves before users are hurt; a lagging indicator confirms the damage afterwards. Queue signals lead and latency percentiles lag, for three reasons:

  • When the sample is recorded: the queue gauge counts a request the moment it arrives. Its TTFT is recorded only when its first token appears, after the wait is over, and its end-to-end latency only when the response finishes, about 11 seconds later in our example. A request that is still waiting produces no latency sample at all. If the engine hangs completely, latency histograms simply stop receiving samples while the queue climbs.
  • How the number is computed: latency percentiles come from histograms over a window, typically the last five minutes (Lesson 28, p50, p95 and p99 Latency). New slow requests are mixed with older fast ones, which damps the signal.
  • What it predicts: a growing queue tells you how bad the wait will be for the next arrival. A percentile tells you how bad it was for requests that already finished.

Figure 5 shows a simulated ramp in which traffic to one replica climbs steadily from 3.3 to 6 requests per second over seven minutes, past its capacity of about 5 (53 streams ÷ 10.8 s ≈ 4.9).

Four aligned panels over eight minutes. Arrival rate rises from 3.3 to 6 requests per second and crosses the replica's capacity of about 4.9 at about 5.2 minutes. In-flight requests rise from 36, cross the autoscaling target of 40 at 2.25 minutes and pass the running cap of 53 at 5.5 minutes. The waiting queue stays at zero until 5.5 minutes, then grows to about 94 requests. The p95 TTFT over a five-minute window stays at 0.3 seconds until 5.75 minutes, then rises to about 14 seconds, always below the TTFT that the queue estimate predicts for a new arrival.

The order is the point. In-flight requests cross the autoscaling target at 2.25 minutes, more than three minutes before any request waits. The waiting queue appears at 5.5 minutes. The p95 TTFT crosses the 0.5 s target one 15-second scrape later, at 5.75 minutes, and from then on it trails the queue-based estimate: at 7 minutes the estimate says a new request will wait about 8 s, while the p95 TTFT still reports 5.8 s. This is a smooth, idealized model; in real traffic, randomness makes queues appear before the replica is completely full, which gives the queue signals even more lead. The lesson for alerting is that in-flight counts buy minutes, the waiting queue buys seconds and states the size of the problem, and latency percentiles confirm it afterwards.

Acting on Queue Depth

Autoscaling on queue signals

Lesson 22, Autoscaling, covers the mechanics; here the question is which signal to scale on. GPU utilization is a poor choice because it reads close to 100% whenever any kernel runs, even at low load (Lesson 19, GPU Utilization). The waiting queue alone is also a poor choice: it stays at zero until the replica is already slot-full, and a new replica takes minutes to start (Lesson 23, Cold Starts). KV cache usage is better but stops at 100% and cannot say how far beyond capacity the fleet is.

The signal that works across the whole range is in-flight requests per replica, running plus waiting, which is also Lesson 22's choice. Below saturation, Little's law ties it directly to arrival rate; above saturation, the waiting part keeps growing and shows how far behind the fleet is. With KEDA's default AverageValue metric type, a target of 40 in-flight requests per replica means the autoscaler asks for \lceil \text{total in flight} / 40 \rceil replicas [12]. On an average minute, 180 in flight asks for 5 replicas; at the daily peak of 33 requests per second, about 356 in flight asks for 9. A target of 40 is 75% of a replica's limit of 53, which leaves room for growth while new replicas start (Lesson 23, Cold Starts). That headroom is why the peak gets 9 replicas rather than the 7 it needs at full load (33 ÷ 5 = 6.6) or the 8 of Lesson 20's static fleet with 20% headroom.

Admission control and load shedding

Autoscaling cannot absorb a tenfold spike that arrives in seconds, so the system must also decide what to do with requests it cannot serve in time. An unbounded queue is the worst answer: every request is accepted, every request waits close to a minute, and many clients time out and retry, which adds more load. Google's SRE guidance recommends small queues relative to a server's capacity, so that it rejects early instead of building latency it cannot pay back [8].

Lesson 26, Rate Limiting, covers the policies. The queue signals tell those policies when to act:

  • At the router: Lesson 26 bounds the router's fleet-wide queue at 250 ms of wait, half the TTFT budget, and sheds the lowest priority first, free and batch traffic before paid traffic, with HTTP 503 and a Retry-After header.
  • In the engine: recent vLLM versions add --max-num-queued-reqs, a cap on in-flight requests (waiting plus running) beyond which new requests get HTTP 503, and --max-num-queued-tokens, a cap on prompt tokens in the prefill backlog. The vLLM documentation suggests sizing the token cap as the TTFT target times the prefill throughput [6]. For our replica, a cap of about 58, the 53 running requests plus about one second of queue at 5 requests per second, is a backstop that keeps the worst wait inside the engine near one second.
  • By priority: vLLM's --scheduling-policy priority serves requests with a lower priority value first, which lets paid traffic overtake free traffic inside the engine queue [6]. Lesson 39, Batch and Offline Inference, uses the same mechanism to run batch work beside interactive traffic.

Figure 6 puts these actions on one ladder, so that each step up is a stronger response to a longer queue.

Requests waiting in one engine: that replica is at its limit of 53, so the router steers new requests to others. Estimated wait above 0.2 seconds for 2 minutes: warn the team channel and confirm the autoscaler is adding replicas. Router queue wait above 250 milliseconds: shed free-tier and batch traffic first with 503 and Retry-After. Engine cap of about 58 in flight: the engine itself rejects with 503. A side note says paging is reserved for the TTFT SLO burn rate.

Designing queue alerts

An alert has three parts: a condition, a duration, and an action. Each choice trades speed against noise:

  • Threshold on the level, for example "estimated wait above 0.2 s". It is easy to read but fires on every short burst if used alone.
  • Duration: Prometheus's for clause keeps an alert pending until its condition has held on every evaluation for the given time, and keep_firing_for keeps it firing for a while after the condition clears, which stops flapping [10]. A duration removes bursts but delays every alert by the same amount.
  • Threshold on the rate of change, for example "the queue has grown for five minutes". PromQL's deriv() fits a line to a gauge over a window and returns its slope per second [11]. A rate rule catches a slow climb before the level crosses its threshold, and predict_linear() can ask "will the KV cache reach 100% within ten minutes?".
A trace of waiting requests over 30 minutes has two short bursts, at minute 4 and minute 9, and then a slow climb of one request per minute starting at minute 14. A plain threshold of more than 5 waiting fires on both bursts, then twice more as the climb wobbles across 5 at minutes 19 and 20. The same threshold held for 3 minutes ignores the bursts and fires at minute 23. A growth rule, slope above 0.01 requests per second with more than 2 waiting, held for 2 minutes, fires at minute 19.25.

Figure 7 compares the three rules on a simulated trace. The plain threshold fires twice for bursts that cleared by themselves, then flaps as the climb wobbles around the threshold. Adding a three-minute duration removes the false alarms but fires last, at minute 23. The growth rule fires at minute 19.25, nearly four minutes earlier, because it reacts to the direction of the queue rather than its size. In practice we combine a level rule with a duration for sudden steps and a growth rule for slow climbs.

The other choice is who gets alerted. Google's SRE book lists saturation among the four golden signals and notes that many systems degrade before they reach 100% utilization [9]. Saturation signals are causes, though, and paging people on causes produces noise. A common split is to page on user-facing symptoms, here the burn rate of the TTFT objective (Lesson 28, and the SRE workbook's guide to alerting on SLOs [13]), and to send queue alerts to a chat channel or to automation that scales or sheds load. The queue panels then sit next to the TTFT panels on the same dashboard, so the person who is paged sees the cause immediately.

Which signals and thresholds fit our deployment?

For our fleet of H100 replicas, five at average load, we choose:

  • Autoscale on in-flight requests per replica (running plus waiting), target 40, with --max-num-seqs 53 so that waiting requests mean "over capacity" (Lesson 22). In-flight counts move minutes before any request waits, and Little's law lets us reason about them.
  • Warn when the estimated wait exceeds 0.2 s for 2 minutes, our whole queueing budget, or when the queue has grown for 3 minutes. These go to the team channel, not a pager.
  • Shed free-tier and batch traffic at the router beyond 250 ms of queue wait (Lesson 26), and cap each engine at about 58 in-flight requests as a backstop, so that a spike produces fast rejections and retries elsewhere instead of minute-long waits.
  • Open a capacity ticket when preemptions are sustained with KV usage above 95%: the traffic mix has shifted toward longer requests than the capacity plan assumed.
  • Page only on the TTFT SLO burn rate, with the queue panels on the same dashboard to explain it.

We prefer the estimated wait to a raw count because its threshold, 0.2 s, comes straight from the latency budget and stays correct when the traffic rate changes. GPU utilization, which caused last week's missed incident, stays on the dashboard but drives no alert at all.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Kingman's approximation: at the same utilization, more variable arrivals and service times produce longer waits, which is why traffic with mixed prompt lengths needs more headroom than uniform traffic [2].
  • Queue order under overload: first-in-first-out serves requests whose clients may already have given up, while LIFO or CoDel-style policies drop stale work first; deadlines propagated from the client make this safe [8].
  • Counting the queue in tokens rather than requests: one 32K-token prompt costs as much prefill as sixteen 2K-token prompts, which is why vLLM also offers a cap on queued prompt tokens [6].
  • Load-aware routing: sending each request to the replica with the shortest queue or the most free KV cache keeps queues even across the fleet (Lesson 25, Request Routing).
  • Per-tenant queues: fair queuing gives each tenant its own queue, so that one tenant's burst delays mostly itself (Lesson 26, and Lesson 37, Multi-LoRA and Multi-Tenant Serving).
  • Disaggregated prefill and decode create separate queues for each phase and for the KV transfer between them; recent SGLang versions export a separate gauge for each of these queues (Lesson 34, Disaggregated Prefill and Decode).
  • Coordinated omission in load tests: closed-loop benchmark clients wait for a response before sending the next request, which hides queueing that open-loop production traffic would create (Lesson 12).
  • Retry storms: clients that retry on timeout without backoff turn a short overload into a sustained one, so rejections should carry Retry-After and clients should add jitter.

Summary

Mind map summarizing the queue depth lesson: where queues form, Little's law, utilization, engine signals, and how to act on them.
  • Most LLM queueing happens in the engine's waiting queue, which is unbounded by default; the running batch is limited by KV cache blocks and the maximum number of sequences.
  • Little's law, L = \lambda W, turns counts into time: our fleet holds about 180 requests in flight, about 36 per replica, and an estimated wait is waiting requests divided by completions per second.
  • With a 0.5 s TTFT target and 0.3 s of unavoidable work, the queue budget is 0.2 s, less than one waiting request per replica at normal load. A replica capped at 53 in flight completes about 5 requests per second.
  • Latency rises slowly and then explodes as utilization approaches 1 (5× service time at 80% and 20× at 95% in an M/M/1 model), so run replicas well below their ceiling; our autoscaler targets 40 of 53 in flight.
  • vLLM exports waiting and running requests, KV cache usage, and preemptions; SGLang exports the same ideas under different names. Queue and saturation signals lead TTFT, while latency percentiles lag.
  • Autoscale on in-flight requests per replica, shed load by priority when queues pass their bounds, cap engine queues as a backstop, and page on the TTFT SLO with queue panels alongside to explain the cause.

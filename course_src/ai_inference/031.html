Introduction

Dashboards built from Prometheus counters answer fleet questions: how many tokens per second, how full the cache is, how long the queue is (Lesson 29, Queue Depth). They cannot answer questions about a single request or a single customer. Which tenant used 40% of yesterday's GPU time? Why did request req-7f3a take 30 seconds? Is one API key sending 30,000-token prompts in a loop? Answering these needs per-request token accounting: one record for every request, with who sent it, how many tokens it used, and how long it took.

Tokens are the unit of cost in LLM serving. Lesson 20, Cost per Million Tokens, turned GPU-hours into a price per input and output token; per-request records turn those prices into a bill per tenant, a cost per feature, and a forecast for next quarter. They are also the raw material for rate limiting (Lesson 26, Rate Limiting), abuse detection, and debugging.

A client calls the API gateway, which assigns a request ID and a tenant, forwards the request through the router to a vLLM replica with an X-Request-Id header, and receives the streamed answer with a final usage chunk. The gateway writes one usage event per request to an event log, which loads a warehouse table used for billing, capacity planning and investigations. The gateway also increments Prometheus counters labeled only by tenant, model and token kind. A daily reconciliation job compares warehouse totals with the engines' own token counters.

In this lesson, we decide what goes into a usage record, get token counts from the OpenAI-compatible API including streamed responses, compare counting tokens ourselves with trusting the server, turn tokens into cost, store and aggregate the records without overloading Prometheus, handle privacy and retention, and reconcile the gateway's numbers with the engine's.

Clarifying the Problem

Accounting questions in interviews usually start from finance or from an angry customer. Here is a typical exchange between a candidate and an interviewer:

Candidate: Who calls the service, and how do we know who they are?
Interviewer: About 200 customers on free, standard and enterprise plans call one API gateway with API keys. Behind it, vLLM serves Llama 3.1 8B Instruct on an autoscaled H100 fleet, plus a few LoRA adapters fine-tuned for large customers.

Candidate: How much traffic?
Interviewer: About 1,000 requests per minute on average, mostly streamed chat with about 2,000 prompt tokens and 500 output tokens. Most of each prompt is a shared system prompt and chat history.

Candidate: What must the records support?
Interviewer: Monthly invoices per tenant, a cost report per product feature, capacity planning, and support tickets of the form "my request was slow at 14:02".

Candidate: Are there constraints on what we store?
Interviewer: Enterprise contracts forbid storing prompt or response text unless the customer opts in. Billing records must be kept for audits.

Candidate: What does a token cost us?
Interviewer: Use Lesson 20's numbers: at an assumed $3.00 per H100-hour and full load, about $0.026 per million input tokens and $0.23 per million output tokens.

The question underneath is: what record do we keep for each request, where do its numbers come from, and how do we store and aggregate 1.44 million records a day so that billing is exact, dashboards are cheap, and nothing private leaks?

What Goes into a Usage Record

Why one record per request

Aggregates hide the cases that matter. A fleet-wide counter says the service produced 0.72 billion output tokens yesterday; it cannot say that one tenant produced a third of them, that requests from one adapter always hit the output limit, or that the slow request in a support ticket waited 9 seconds in a queue. A per-request record supports four jobs:

  • Cost attribution: invoices per tenant, and internal cost per product feature or adapter (Lesson 37, Multi-LoRA and Multi-Tenant Serving).
  • Capacity planning: the real distribution of prompt and output lengths, which drives KV cache needs (Lesson 3) and GPU counts (Lesson 21).
  • Abuse detection: a key that suddenly sends long prompts at a steady rate, or requests that always run to the output limit.
  • Debugging: given a request ID from a customer, find its replica, its queue time, its time to first token, and why it stopped.

The timing fields come from different clocks, and Figure 2 shows how they fit together. The gateway measures what the user experiences, from the moment the request arrives to the last byte sent. The engine knows how long the request waited in its own queue, which the gateway cannot see.

A timeline for one streamed request. The gateway receives it at time zero and forwards it; the engine places it in its waiting queue and schedules it 0.04 seconds later, which is the queue time measured by the engine. The first content token reaches the gateway at 0.31 seconds, which is the time to first token. Tokens stream until the last content token, then a final chunk carries the usage, and the stream ends at 10.8 seconds, which is the end-to-end latency. The gateway then writes the usage record.

Two fields deserve a note. vLLM uses an incoming X-Request-Id header as its internal request ID, and with --enable-request-id-headers it echoes the header on the response, so one ID connects the gateway's record with the engine's logs and traces [3][4]. The engine's queue time is not part of the API response; it is available per request from vLLM's OpenTelemetry tracing (--otlp-traces-endpoint), whose spans carry the request ID, the time in queue, the time to first token, and token counts [6]. Tracing every request is expensive, so many teams sample traces and keep queue time only for sampled or slow requests.

Getting Token Counts

Usage in the OpenAI-compatible API

Every non-streamed chat completion in the OpenAI API returns a usage object with prompt_tokens, completion_tokens, and total_tokens, plus optional details: prompt_tokens_details.cached_tokens for prompt tokens served from a cache, and completion_tokens_details.reasoning_tokens for hidden reasoning tokens, which are billed as output [1][2]. vLLM returns the same object. It fills in prompt_tokens_details only when started with --enable-prompt-tokens-details [4].

Usage in streamed responses

Streamed responses are the common case for chat, and by default they carry no usage at all. A client must set stream_options={"include_usage": true}. The server then sends one extra chunk before the final data: [DONE] message; its choices array is empty and its usage field holds the totals for the whole request, while every earlier chunk carries usage: null [1][2]. Figure 3 shows the stream.

Left: the chunks of a normal stream. The first chunk carries the role, the following chunks carry content deltas with usage set to null, the last content chunk carries finish reason stop, then a usage chunk with an empty choices array reports 2,000 prompt tokens, 1,500 of them cached, and 500 completion tokens, and the stream ends with DONE. Right: a stream interrupted after 120 tokens never receives the usage chunk, so the gateway records the request with usage missing and must estimate it or fetch it from the engine.

Two details trip people up. First, code that reads chunk.choices[0] on every chunk crashes on the usage chunk, whose choices list is empty. Second, the OpenAI reference warns that an interrupted or cancelled stream may never deliver the usage chunk [2]. A client that gives up after 120 tokens has still consumed 2,000 prompt tokens of prefill and 120 tokens of decode, but nobody received a usage chunk to say so.

vLLM adds two options for this. The continuous_usage_stats stream option puts running usage on every chunk, so the last chunk a disconnecting client received still reports how far it got. And --enable-force-include-usage makes the server include usage on every request, even when the client did not ask for it [4]. The second matters most for a gateway: it should not depend on every customer's client setting stream_options correctly.

Counting tokens yourself versus trusting the server

It is tempting to count tokens at the gateway with a tokenizer library and skip the server's numbers. That fails in three ways:

  • Different tokenizers: each model family has its own vocabulary. Llama 3 uses a 128K-token vocabulary, and on a sample of English text its tokenizer needs 3.94 characters per token where Llama 2's needed 3.17 [8]. The same 10,000 characters are about 3,155 Llama 2 tokens but about 2,538 Llama 3 tokens, roughly 20% fewer. A count from the wrong tokenizer is off by tens of percent.
  • The chat template: the server turns a list of messages into one prompt with role headers and special tokens before counting. A gateway that counts only the message text undercounts every request.
  • Hidden work: cached prompt tokens, reasoning tokens, and tool definitions are only known to the server.
Two bars for the same 10,000 characters of English. The Llama 2 tokenizer, at 3.17 characters per token, produces about 3,155 tokens. The Llama 3 tokenizer, at 3.94 characters per token, produces about 2,538 tokens, about 20 percent fewer. A note says the chat template adds role headers and special tokens on top of the message text.

The rule is therefore: bill from the server's usage, and count yourself only for estimates. A gateway does need an estimate before a request runs, for example to charge a token bucket on admission (Lesson 26); it should use the served model's own tokenizer and chat template, then settle the difference when the real usage arrives. Self-counting is also the fallback for the rare request whose usage never arrives.

From Tokens to Cost

Three prices, not one

Lesson 20 split the cost of a fully loaded H100, at an assumed $3.00 per hour, by the GPU time each phase uses: about $0.026 per million input tokens and $0.23 per million output tokens. Cached input tokens skip prefill and cost almost no GPU time. For an internal rate card we price them at 10% of the input rate, $0.0026 per million, the same ratio Lesson 20 cites for one hosted API's cache reads. The cost of one request is then:

\text{cost} = (p - c) \times r_{\text{in}} + c \times r_{\text{cached}} + o \times r_{\text{out}}

where p is prompt tokens, c cached prompt tokens, o output tokens, and the r are the three rates. For our typical chat request with 1,500 of its 2,000 prompt tokens cached and 500 output tokens:

  • Uncached input: 500 × $0.026 per million ≈ $0.000013.
  • Cached input: 1,500 × $0.0026 per million ≈ $0.0000039.
  • Output: 500 × $0.23 per million ≈ $0.000115.
  • Total: about $0.00013 per request, or $0.13 per 1,000 requests, against $0.17 per 1,000 if nothing were cached (Lesson 20).
Two stacked bars for a chat request. By tokens it is 1,500 cached input, 500 uncached input and 500 output tokens. By cost it is 3.9, 13 and 115 millionths of a dollar, so output is about 87 percent of the cost although it is 20 percent of the tokens. A second request, a 30,000-token uncached document with 300 output tokens, costs about 849 millionths of a dollar, about 6.4 times the chat request.

Output tokens are 20% of the chat request's tokens but about 87% of its cost, which is why a record that stores only total_tokens is useless for billing. A tenant that uploads 30,000-token documents and asks for 300 tokens back costs about 30,000 × $0.026 + 300 × $0.23 per million ≈ $0.00085 per request, about 6.4 times a chat request. Even that understates long prompts, because each one also holds far more KV cache while it runs (Lesson 3); providers that serve long contexts often price them separately.

These are full-load rates. A fleet that averages 75% of its provisioned capacity pays for the idle quarter too, so Lesson 20 divides by the utilization factor. For invoices, the simplest fair rule is to bill the rate card and let the margin absorb idle time; for internal cost reports, scale every tenant's cost by the same factor so that the reports add up to the GPU bill.

Storing and Aggregating Records

Events to a warehouse, counters to Prometheus

The records go to two places with different jobs. The full record goes into an append-only event log, such as a Kafka topic, and from there into a warehouse table partitioned by day. At 1,000 requests per minute that is 1.44 million rows a day; at an assumed 500 bytes per record, about 720 MB a day before compression, or about 65 GB for 90 days. Any analytical database handles this easily, and the warehouse answers the per-tenant, per-request, and per-feature questions.

Prometheus gets only aggregates: counters of tokens by tenant, model, and token kind, which feed real-time dashboards and alerts. The engines already export their own aggregates, such as vllm:prompt_tokens_total, vllm:generation_tokens_total, and, in recent versions, vllm:prompt_tokens_cached_total [5].

Why request IDs must not become Prometheus labels

Every unique combination of label values is a separate time series in Prometheus, and its documentation warns against labels with high cardinality, such as user IDs or other unbounded sets of values [7]. A counter labeled with request_id would create a new series for every request: 1.44 million new series a day, each with a single sample, which no Prometheus server is designed to hold. Figure 6 compares the two designs.

Left: a token counter labeled by 200 tenants, 2 models and 3 token kinds has at most 1,200 time series, no matter how much traffic arrives. Right: the same counter labeled by request ID gains one new series per request, 1.44 million per day at 1,000 requests per minute. The per-request detail belongs in the warehouse, where 1.44 million rows a day is ordinary.

The rule is simple: labels must come from small, bounded sets. Tenant is acceptable at our 200 customers; an end-user ID on a consumer product with millions of users is not, and neither are request IDs, prompts, or adapter names that customers can create without limit.

Privacy and retention

A usage record needs counts and times, not content. We therefore do not log prompt or response text by default:

  • Keep the gateway's access log free of request bodies, and leave vLLM's --enable-log-requests off in production; when enabled at DEBUG level it logs prompt inputs [4].
  • Store end-user identifiers only as salted hashes, if at all; the tenant ID is enough for billing.
  • Follow the same split as OpenTelemetry's GenAI conventions, where token counts such as gen_ai.usage.input_tokens are ordinary attributes but input and output messages are opt-in [9].

Retention differs by purpose. Billing records stay as long as invoices can be disputed and audited, which the finance and legal teams decide. Detailed debugging data, such as traces, stays for days or weeks. Any content captured for an opted-in customer gets its own short, documented retention and access controls.

Reconciliation

The gateway's records and the engines' counters measure the same traffic from two sides, so their totals should agree. A daily job compares them per model, as Figure 7 shows, and the differences have known causes:

  • Retries: a request retried on another replica runs twice on the engines but is one billable request at the gateway.
  • Rejections and aborts: requests rejected with 429 or 503 never reach an engine; streams aborted by the client may lack a usage chunk.
  • Internal traffic: health checks, warm-up requests (Lesson 23), and evaluation jobs reach the engines but not the gateway.
  • Counting differences: a gateway that self-counts any requests disagrees with the engine by the tokenizer and template effects above.
Two columns of daily output-token totals for one model. Engine counters report 721 million tokens. Gateway records report 715 million billed tokens. The 6 million difference is explained by retried requests, aborted streams without usage, and internal warm-up and health-check traffic, leaving an unexplained remainder of 0.1 percent, inside a 1 percent tolerance.

An unexplained gap above a small tolerance, say 1%, means records are being lost: a crashed gateway pod that never flushed its events, a dropped Kafka partition, or a client path that bypasses the gateway. Reconciliation is how we learn that before a customer's invoice is wrong.

Which design fits our deployment?

Three designs are common. Client-side accounting records usage in each product's code; it is easy to start but misses any caller that forgets, and customers' clients cannot be trusted for billing. Engine-side accounting builds records from engine logs or traces; it sees every request but does not know tenants, plans, or client disconnects. Gateway-side accounting records every request where tenant, timing, and status are all known.

For our multi-tenant API we choose the gateway as the system of record. vLLM runs with --enable-force-include-usage and --enable-prompt-tokens-details, so every response carries complete usage whatever the client asked for, and with --enable-request-id-headers, so the gateway's request ID appears in engine logs and traces. The gateway writes one event per request to Kafka for the warehouse and increments bounded Prometheus counters by tenant, model, and token kind. Queue time comes from sampled engine traces joined on the request ID. A daily job reconciles warehouse totals with vllm:prompt_tokens_total and vllm:generation_tokens_total. Prompt text is never stored unless a customer opts in.

In Practice

The first tab streams a chat completion through the OpenAI Python client, measures time to first token and end-to-end latency, reads the usage chunk, writes one JSON line per request without any prompt text, and increments bounded Prometheus counters [2][7]. It is written as a client, but the same logic belongs in a gateway. The second tab starts vLLM with the flags that make usage complete and request IDs traceable [4][6]. The third tab holds PromQL for token dashboards and for the engine side of the daily reconciliation [5].

"""Stream a chat completion and record one usage event per request.""" import json import time import uuid from openai import OpenAI from prometheus_client import Counter client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY") MODEL = "meta-llama/Llama-3.1-8B-Instruct" # Aggregates only: bounded labels (tenant, model, kind), never request IDs. TOKENS = Counter("llm_gateway_tokens", "Tokens served", ["tenant", "model", "kind"]) # Rate card in dollars per million tokens (Lesson 20, full load; cached = 10% of input). RATES = {"input": 0.026, "cached_input": 0.0026, "output": 0.23} def cost_usd(prompt: int, cached: int, output: int) -> float: return ((prompt - cached) * RATES["input"] + cached * RATES["cached_input"] + output * RATES["output"]) / 1e6 def chat(messages: list[dict], tenant: str, log_path: str = "usage.jsonl") -> str: request_id = f"req-{uuid.uuid4()}" start = time.time() first_token_at = None finish_reason = None usage = None status = "ok" parts: list[str] = [] try: stream = client.chat.completions.create( model=MODEL, messages=messages, max_tokens=1024, stream=True, stream_options={"include_usage": True}, extra_headers={"X-Request-Id": request_id}, ) for chunk in stream: if chunk.choices: # the usage chunk has an empty choices list choice = chunk.choices[0] if choice.delta.content: if first_token_at is None: first_token_at = time.time() parts.append(choice.delta.content) if choice.finish_reason: finish_reason = choice.finish_reason if chunk.usage is not None: usage = chunk.usage except Exception as exc: # disconnects, timeouts, HTTP errors status = type(exc).__name__ raise finally: end = time.time() details = usage.prompt_tokens_details if usage else None cached = (details.cached_tokens or 0) if details else 0 record = { "request_id": request_id, "tenant": tenant, "model": MODEL, "prompt_tokens": usage.prompt_tokens if usage else None, "cached_prompt_tokens": cached if usage else None, "output_tokens": usage.completion_tokens if usage else None, "finish_reason": finish_reason, "status": status, "ttft_s": round(first_token_at - start, 3) if first_token_at else None, "e2e_s": round(end - start, 3), "usage_missing": usage is None, "started_at": start, } if usage: record["cost_usd"] = cost_usd(usage.prompt_tokens, cached, usage.completion_tokens) TOKENS.labels(tenant, MODEL, "input").inc(usage.prompt_tokens - cached) TOKENS.labels(tenant, MODEL, "cached_input").inc(cached) TOKENS.labels(tenant, MODEL, "output").inc(usage.completion_tokens) with open(log_path, "a", encoding="utf-8") as f: f.write(json.dumps(record) + "\n") # counts and times only, no text return "".join(parts) if __name__ == "__main__": answer = chat([{"role": "user", "content": "Explain the KV cache in two sentences."}], tenant="acme") print(answer) # --enable-prompt-tokens-details: report usage.prompt_tokens_details.cached_tokens # --enable-force-include-usage: include usage even if the client omits stream_options # --enable-request-id-headers: echo the X-Request-Id header on responses # --otlp-traces-endpoint: per-request spans with queue time and token counts # --enable-log-requests stays off: at DEBUG level it would log prompt inputs. export OTEL_SERVICE_NAME="vllm-llama-8b" vllm serve meta-llama/Llama-3.1-8B-Instruct \ --enable-prompt-tokens-details \ --enable-force-include-usage \ --enable-request-id-headers \ --otlp-traces-endpoint "grpc://otel-collector:4317" # Tokens per second by tenant and kind, from the gateway's bounded counters sum by (tenant, kind) (rate(llm_gateway_tokens_total[5m])) # Dollars per hour by tenant at the Lesson 20 rate card sum by (tenant) ( rate(llm_gateway_tokens_total{kind="input"}[1h]) * 0.026 + ignoring(kind) rate(llm_gateway_tokens_total{kind="cached_input"}[1h]) * 0.0026 + ignoring(kind) rate(llm_gateway_tokens_total{kind="output"}[1h]) * 0.23 ) * 3600 / 1e6 # Engine side of the daily reconciliation, per model sum by (model_name) (increase(vllm:prompt_tokens_total[1d])) sum by (model_name) (increase(vllm:generation_tokens_total[1d])) # Prefix cache hit rate in tokens sum(rate(vllm:prefix_cache_hits_total[5m])) / sum(rate(vllm:prefix_cache_queries_total[5m]))

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Settling rate-limit reservations: the gateway reserves tokens on admission from an estimate and refunds the difference when the usage record arrives (Lesson 26).
  • Reasoning tokens: models that think before answering produce billed output tokens the user never sees, reported in completion_tokens_details.reasoning_tokens [2].
  • Structured output and tool calls add tokens for schemas and tool definitions, and a tool_calls finish reason marks a request that will be followed by another (Lesson 38, Structured Output and Tool Calling).
  • Batch traffic can be billed at a lower rate because it runs in otherwise idle capacity (Lesson 39, Batch and Offline Inference).
  • Exactly-once billing: event logs deliver at least once, so the warehouse deduplicates on request_id.
  • OpenTelemetry's GenAI semantic conventions define standard attribute names for token usage, which lets traces from different gateways and SDKs share one schema [9].
  • Per-request energy: dividing a GPU's energy counter over the tokens it served gives joules per token, which can be attributed to tenants like cost (Lesson 30, GPU Metrics).

Summary

Mind map summarizing the per-request token accounting lesson: the record's fields, getting usage from the API, counting tokens, cost, storage, and privacy.
  • Keep one record per request with request ID, tenant, model and adapter, prompt, cached and output tokens, finish reason, status, queue time, TTFT, end-to-end latency, and replica.
  • Streamed responses carry usage only with stream_options={"include_usage": true}, in a final chunk with empty choices; interrupted streams may lose it, so make vLLM force usage on every request.
  • Bill from the server's usage: tokenizers differ by model (Llama 3 needs about 20% fewer tokens than Llama 2 for English) and chat templates add tokens the client never sees.
  • Price input, cached input and output separately: our chat request costs about $0.00013, and its output is 20% of the tokens but about 87% of the cost.
  • Send full records to an event log and warehouse (1.44 million rows a day) and only bounded aggregates to Prometheus; a request-ID label would add 1.44 million series a day.
  • Do not store prompt text by default, and reconcile gateway totals with engine counters daily to catch lost records.

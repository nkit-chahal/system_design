Introduction

Time to first token (TTFT) is the time from the moment a user sends a request to the moment the first token of the answer reaches them. Until then, the user sees a blank reply or a spinner. Once text starts streaming, attention shifts to how fast it flows (Lesson 5, Tokens per Second), but the wait before the first word is what makes an assistant feel responsive or broken.

TTFT is not one thing. It is the sum of several stages: the network, preparing the prompt, waiting in a queue, the prefill pass that reads the prompt, and streaming the token back. Figure 1 lays them out. On an idle server, prefill usually dominates. On a busy server, the queue can be a hundred times larger than everything else combined.

Seven boxes from left to right: network from client to server, prepare (template and tokenize), queue (wait for a slot), prefill plus sampling token 1, stream out (detokenize and send as a server-sent event), network back to the client, and token 1 on screen. Illustrative values under each box are 1 to 50 ms, about 3 ms, 0 to seconds, about 65 ms, under 1 ms, and 1 to 50 ms. A bracket marks the first six boxes as time to first token; a smaller bracket marks queue plus prefill as the part vLLM's server-side metric covers.

In this lesson, we break TTFT into its parts, calculate how it grows with prompt length, show why it spikes under load, compare the levers that bring it down, and explain how to measure it correctly from a client and from server metrics.

Clarifying the Problem

TTFT questions usually start from a latency complaint. Here is a typical exchange between a candidate and an interviewer:

Candidate: What are we serving, and on what hardware?
Interviewer: Llama 3.1 8B Instruct in BF16 on eight H100 GPUs, one vLLM replica per GPU, behind a load balancer.

Candidate: What do requests look like?
Interviewer: Chat requests with about 2,000 prompt tokens and 500 output tokens. About 1,500 of the prompt tokens are our system prompt and tool definitions. Traffic averages 1,000 requests per minute, about 16.7 per second, and follows a daily cycle from about 8 requests per second at night to 33 at the evening peak.

Candidate: Is the system prompt identical for every request?
Interviewer: Nearly. It starts with the current date and time and the user's name, then the fixed instructions.

Candidate: What do the dashboards show?
Interviewer: p50 TTFT is about 150 ms all day. At the evening peak, p95 climbs to about 0.9 seconds and p99 to about 3 seconds, and support tickets say the assistant "hangs" before answering.

Candidate: What is the target, and does anything else run on these GPUs?
Interviewer: p95 TTFT of at most 500 ms, as users see it, at every hour of the day. A nightly summarization job also shares the fleet, and it sometimes overlaps the evening peak.

The question underneath is: which part of TTFT grows at peak, and which lever brings p95 under 500 ms without simply buying more GPUs? To answer it, we need to know what each part costs.

What TTFT Is Made Of

The breakdown

For a streaming request, TTFT is the sum of the stages in Figure 1:

\text{TTFT} = t_{\text{network}} + t_{\text{prepare}} + t_{\text{queue}} + t_{\text{prefill}} + t_{\text{stream}}
  • Network (both directions): the request travels to the server and the first chunk travels back. Within one cloud region this is a millisecond or two; across a continent it can be tens of milliseconds each way. A new connection also pays for TCP and TLS handshakes, which is why clients should reuse connections.
  • Prepare: the server parses the request, applies the model's chat template, and tokenizes the result. In our test, templating and tokenizing a 2,000-token prompt with the Llama 3.1 tokenizer took about 3 ms on a desktop CPU. Images or audio need preprocessing that can cost far more.
  • Queue: the request waits until the scheduler admits it. Admission needs free KV cache blocks (Lesson 3, KV Cache), a free sequence slot, and room in the step's token budget. On an idle server this is zero.
  • Prefill: one forward pass over the prompt (Lesson 2, Prefill vs Decode). The first output token is sampled from the logits of the prompt's last position, so there is no separate decode step before it. vLLM counts the first token as produced by prefill and excludes it from its time-per-output-token metric for this reason.
  • Stream: the token is turned back into text, wrapped in a server-sent event (SSE), and flushed to the client. This takes well under a millisecond unless something in the path buffers the response.

Figure 2 adds these up for one chat request on an idle server and on a busy one. The busy case is the tenth request of a burst, which we analyze below.

Two stacked horizontal bars on a 0 to 700 ms axis. The idle-server bar has 20 ms of network, 3 ms of preparation, 67 ms of prefill, under 1 ms of streaming, and 20 ms of network back, for 111 ms. The busy-server bar adds a 585 ms queue segment, labeled waiting behind 9 earlier prompts, for 696 ms in total.

Only one segment changes by an order of magnitude between the two bars. That observation is the core of most TTFT investigations: when TTFT spikes, look at the queue before anything else.

How TTFT grows with prompt length

Prefill is compute-bound, so its time is the FLOPs it needs divided by the FLOPs the GPU actually delivers. With about two FLOPs per parameter per token (Lesson 2):

t_{\text{prefill}} \approx \frac{2 \times N \times n_{\text{prompt}}}{\text{peak FLOPS} \times \text{MFU}}

Here N is the parameter count, n_{\text{prompt}} the number of prompt tokens, and MFU the fraction of peak the kernels achieve. For Llama 3.1 8B on an H100 (989 TFLOPS dense BF16) at an assumed 50% MFU, the denominator is about 495 TFLOPS, so the GPU ingests about 31,000 prompt tokens per second. Attention adds work that grows with the square of the prompt length. Table 1 gives both estimates.

Two lessons follow from Figure 3. For our 2,000-token chat prompts, prefill uses about an eighth of the 500 ms target, so a 3-second p99 cannot be explained by prefill. And a full 32K-token document cannot meet the target on one H100 at all, no matter how idle the server is. Long-context traffic needs its own target, more GPUs per request (Lesson 18, Tensor Parallelism), or cached prefixes; Lesson 36, Long-Context Serving, covers the options. Short prompts also run below 50% MFU in practice, because small matrix multiplies and fixed per-step overheads use the GPU less efficiently, so measure your own curve before relying on these numbers.

Quote the prefill rate, not just the formula: "At 50% MFU an H100 prefills Llama 3.1 8B at about 31,000 tokens per second, so a 2,000-token prompt costs about 65 ms." It lets you sanity-check any TTFT number in seconds.

Why TTFT Spikes Under Load

Queueing grows faster than load

A request waits whenever the server is busy with work that arrived before it. Queueing theory gives the shape of that wait. In the simplest model, an M/M/1 queue with random arrivals and one server, the average time spent waiting is [2]:

W_q = \frac{\rho}{1 - \rho} \times S

Here \rho is the utilization, the fraction of time the server is busy, and S the average service time. Figure 4 plots the multiplier. At 50% utilization a request waits, on average, one service time. At 80% it waits four, at 90% nine, and at 95% nineteen. With a 65 ms prefill as the service time, that is 65 ms, 260 ms, 585 ms, and 1.2 s of average waiting. The tail is much longer than the average.

A curve of average wait divided by service time against utilization from 0 to 100%. It stays near zero up to about 50%, then bends sharply upward: 1 times at 50%, 4 times at 80%, 9 times at 90% and 19 times at 95%. With a 65 ms service time these are 65 ms, 260 ms, 585 ms and 1.2 s.

A serving engine with continuous batching is not an M/M/1 queue, but it shares the property that matters: a finite service rate and random arrivals. The curve explains the interviewer's dashboard. Lesson 19 estimates that one H100 serves about 5 of these chat requests per second within our latency targets, so eight GPUs can absorb about 40 per second. At night the fleet sees 8 requests per second, a fifth of that. At the evening peak it sees 33, more than 80%, right where the curve turns upward. p50 TTFT barely moves because most requests still find a free slot, while p95 and p99 explode. Launch-day spikes of up to 10 times the average would push far past the knee (Lesson 27, Lab - Surviving a 10x Traffic Spike).

Bursts

Arrivals are not smooth. Even when the average load is moderate, requests arrive in clumps: a page that many users open at once, a retry storm after an error, or a batch job that starts on the hour. Figure 5 shows what happens when ten 2,000-token chat requests reach an idle H100 at the same moment.

Ten bars, one per request in order of service. Each has a 65 ms orange segment for its own prefill on top of a purple segment for time spent waiting for earlier prefills. TTFT rises from 65 ms for the first request to 650 ms for the tenth. Markers on the right show the idle TTFT of 65 ms, the median of about 360 ms and the slowest at 650 ms.

The burst holds 20,000 prompt tokens. At about 31,000 tokens per second, clearing it takes about 650 ms, and the requests finish one after another: the first at 65 ms, the median at about 360 ms, the last at 650 ms. Nothing is wrong with the server. It is simply doing the work in order. Requests already decoding make it worse, because they take a share of every step, and so does a full KV cache, which blocks admission until running requests finish (about 170 chat requests fit on one H100, as Lesson 3 showed).

Telling queueing from slow prefill

vLLM splits the server-side part of TTFT into two histograms: vllm:request_queue_time_seconds, the time a request spends waiting before it is first scheduled, and vllm:request_prefill_time_seconds, the time from first scheduling to the first token [4]. The gauge vllm:num_requests_waiting counts requests in the queue right now. If p95 queue time tracks the TTFT spike and the waiting gauge is above zero, the problem is capacity or scheduling. If prefill time is the part that grew, look at prompt lengths, prefix cache hit rates, and interference from long prompts. Lesson 29, Queue Depth, builds alerts on these signals.

Prefix caching deserves a closer look. vLLM enables it by default and identifies each cached block by a hash that includes the hash of the block before it [13]. Because each block's identity therefore depends on every token before it, a single different token near the start invalidates everything after it. Putting the date, time, and user name at the top of the system prompt therefore defeats the cache for all 1,500 tokens behind them. Moving those fields after the fixed instructions lets every request reuse the cached instructions and prefill only its last 500 or so tokens: about 16 ms of weight math plus about 1 ms of attention over the cached context, instead of about 67 ms.

Priority scheduling is a single flag in vLLM: with --scheduling-policy priority, each request may carry a priority value, and lower values are handled first, with arrival time breaking ties [5]. Admission control is the safety valve. vLLM's --max-num-queued-tokens rejects new requests with HTTP 503 once the prompt tokens waiting for prefill exceed a limit; its documentation suggests setting the limit to the TTFT target multiplied by the prefill throughput [5], which for one of our replicas is about 0.5 s × 31,000 tokens per second ≈ 15,500 tokens.

Which lever fits our deployment?

Start with the cheapest fix that removes work. The prefix cache hit rate (vllm:prefix_cache_hits_total divided by vllm:prefix_cache_queries_total) will be near zero because of the timestamp at the top of the prompt. Reordering the system prompt cuts prefill work per request by about three quarters, which lowers peak utilization and moves the fleet back from the steep part of Figure 4. Next, mark the nightly summarization job as low priority, or move it to hours without chat traffic, so it never sits ahead of an interactive user (Lesson 39, Batch and Offline Inference). Then confirm with the queue-time histogram that the peak has moved off the steep part of the curve, and with client-side measurements that p95 TTFT at peak is under 500 ms. Only if it is not do we add replicas or autoscaling, and we keep admission control as a guard for the next burst. Disaggregation and a smaller model are not needed: our prompts are short, and the model already prefills them in a fraction of the budget.

Measuring TTFT Correctly

From a streaming client

Client-side TTFT is the number users feel, so it is the one to put in a service-level objective. Measure it with a streaming request: start a high-resolution timer just before sending and stop it when the first chunk with non-empty content arrives. With OpenAI-compatible servers, the first streamed chunk often carries only the assistant role and no text, so stopping on the first chunk of any kind underestimates TTFT. A non-streaming request cannot measure TTFT at all; its latency is the full end-to-end time.

Synthetic tests have three common traps. First, warm the connection before timing, or the first request includes connection setup. Second, give each test prompt a unique beginning; otherwise the prefix cache serves repeated prompts and hides the prefill cost you meant to measure. Third, drive load at a fixed arrival rate rather than a fixed number of concurrent clients. A closed loop of N clients never sends more than N requests at once, so it can never build the queue that real traffic builds. vllm bench serve --request-rate generates Poisson arrivals for exactly this reason [6]. NVIDIA's benchmarking guide notes that tools also differ in how they define these metrics, so record which tool and settings produced a number [1].

From server metrics

vLLM exports TTFT as the histogram vllm:time_to_first_token_seconds on its /metrics endpoint [4]. Its clock starts when the request enters the engine's front end inside the server process, so it excludes network time, proxies, and HTTP handling; depending on the endpoint and version, it may also exclude chat templating and tokenization. Figure 6 shows what each measurement point covers.

A chain of four boxes: client, load balancer or API gateway, vLLM API server, and engine core. A bracket over the whole chain marks client-side TTFT, from request sent to the first non-empty content chunk. A shorter bracket starting at the load balancer marks gateway TTFT. Below, a bracket over the end of the API server and the engine core marks vllm:time_to_first_token_seconds, split into queue time and prefill time. A red note warns that nginx buffers proxied responses by default, so server TTFT can look fine while users wait.

The gap between client-side and server-side TTFT is network plus everything in between. One classic cause of a large gap is a proxy that buffers responses. nginx, for example, buffers proxied responses by default (proxy_buffering on); for streaming endpoints, turn buffering off in the proxy configuration or have the upstream send the X-Accel-Buffering: no header [7]. Track both numbers, and alert on the client-side one.

When computing percentiles from Prometheus histograms, sum the bucket rates across replicas by le before calling histogram_quantile, and never average per-replica percentiles, which yields statistically meaningless values [8]. Remember that the result is interpolated within a bucket, so its precision is limited by the bucket boundaries.

p50 versus the tail

The median (p50) describes a typical request. The 95th percentile (p95) describes the slowest one in twenty, and the 99th (p99) the slowest one in a hundred. Figure 7 shows an illustrative TTFT distribution at an evening peak with the shape the interviewer described.

A histogram of time to first token on a log axis from 30 ms to 10 s. Most requests form a peak between about 80 and 300 ms, with p50 at about 147 ms. A long tail stretches past 1 s, colored red beyond the 500 ms target. Dashed lines mark p95 at about 0.9 s and p99 at about 2.9 s. The data is illustrative.

In this data the mean is about 270 ms, a value that describes neither the typical request nor the slow ones, which is why latency targets use percentiles. The tail also matters more than "one in twenty" suggests. A user who sends 20 messages in a session has a 1 − 0.95²⁰ ≈ 64% chance of hitting at least one response at or beyond the p95, and a 1 − 0.99²⁰ ≈ 18% chance of hitting one at or beyond the p99. Lesson 28, p50, p95 and p99 Latency, covers percentile math in depth.

Typical targets

A useful anchor comes from usability research: about 0.1 s feels instantaneous, about 1 s keeps the user's flow of thought, and about 10 s is the limit for keeping attention on the task [9]. Industry benchmarks set explicit numbers too. MLPerf Inference's Llama 3.1 8B benchmark requires a TTFT of 2,000 ms and a time per output token of 100 ms in its conversational category, and 500 ms and 30 ms in its interactive category, measured at the 99th percentile [10]. In Practice

The first tab measures client-side TTFT for several prompt lengths with the OpenAI Python client against a running vLLM server; the unique prefix keeps the prefix cache from hiding prefill. The second holds PromQL queries that split server-side TTFT into queueing and prefill. The third runs vllm bench serve at a fixed Poisson arrival rate and reports TTFT percentiles; repeat it at increasing rates to find where p95 turns upward [6].

import time import uuid from openai import OpenAI client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY") MODEL = "meta-llama/Llama-3.1-8B-Instruct" def measure_ttft(prompt: str, max_tokens: int = 32) -> tuple[float | None, int]: """Seconds from sending the request to the first chunk that carries text.""" start = time.perf_counter() stream = client.chat.completions.create( model=MODEL, messages=[{"role": "user", "content": prompt}], max_tokens=max_tokens, stream=True, stream_options={"include_usage": True}, ) ttft, prompt_tokens = None, 0 for chunk in stream: # The first chunk usually carries only the role, so wait for real text. if ttft is None and chunk.choices and chunk.choices[0].delta.content: ttft = time.perf_counter() - start if chunk.usage: # included in the final chunk prompt_tokens = chunk.usage.prompt_tokens return ttft, prompt_tokens measure_ttft("Say hi.") # warm-up: pays for connection setup outside the timing sentence = "The quick brown fox jumps over the lazy dog. " for repeats in (40, 180, 720): # A unique prefix defeats prefix caching, which would hide the prefill cost. prompt = f"[run {uuid.uuid4()}] Summarize this text.\n" + sentence * repeats ttft, n = measure_ttft(prompt) print(f"{n:>6,} prompt tokens: TTFT {ttft * 1000:7.1f} ms") # p50 and p95 server-side TTFT over 5 minutes, across all replicas histogram_quantile(0.50, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m]))) histogram_quantile(0.95, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m]))) # Is the spike queueing? p95 time waiting before first being scheduled histogram_quantile(0.95, sum by (le) (rate(vllm:request_queue_time_seconds_bucket[5m]))) # ...or prefill? p95 time from first scheduling to the first token histogram_quantile(0.95, sum by (le) (rate(vllm:request_prefill_time_seconds_bucket[5m]))) # Requests waiting for a slot, per replica sum by (instance) (vllm:num_requests_waiting) # Prefix cache hit rate: share of queried prompt tokens found in the cache sum(rate(vllm:prefix_cache_hits_total[5m])) / sum(rate(vllm:prefix_cache_queries_total[5m])) # Open-loop load test: Poisson arrivals at 4 requests/s with 2,000-token # prompts and 500-token answers, reporting TTFT and end-to-end percentiles. vllm bench serve \ --model meta-llama/Llama-3.1-8B-Instruct \ --dataset-name random --random-input-len 2000 --random-output-len 500 \ --ignore-eos --num-prompts 600 --request-rate 4 \ --percentile-metrics ttft,e2el --metric-percentiles 50,95,99 # Repeat with --request-rate 6, 8, 10 and plot P95 TTFT against the rate. # It stays nearly flat, then turns sharply upward as the server saturates.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Reasoning models: the first visible answer token may follow hundreds of hidden thinking tokens, so "time to first answer token" can differ greatly from TTFT.
  • Cold starts: the first requests after a scale-up wait for weights to load and CUDA graphs to be captured, which can add seconds or minutes (Lesson 23, Cold Starts).
  • Cache-aware routing: sending requests that share a prefix to the replica that already holds it turns prefix caching from a per-replica win into a fleet-wide one (Lesson 25, Request Routing).
  • Long-context requests deserve their own SLO class and possibly their own pool, since their prefill alone can exceed a chat TTFT target (Lesson 36, Long-Context Serving).
  • DistServe defines goodput as the request rate a system can serve while meeting both TTFT and time-per-output-token targets, which makes TTFT part of capacity planning rather than an afterthought [11].
  • Chunked prefill trades TTFT against the smoothness of other users' streams; Sarathi-Serve studies this trade-off [12].

Summary

Mind map summarizing the lesson: what TTFT is made of, how it grows with prompt length, why it spikes under load, the levers that reduce it, and how to measure it.
  • TTFT is network + preparation + queue + prefill + streaming. The first token comes out of the prefill pass itself.
  • Prefill time ≈ 2 × parameters × prompt tokens ÷ (peak FLOPS × MFU): about 65 ms for 2,000 tokens of Llama 3.1 8B on an H100 at 50% MFU, and about 1.6 s for 32K tokens once attention is counted.
  • Queueing causes most TTFT spikes. In an M/M/1 queue the average wait is ρ ÷ (1 − ρ) service times: 4 at 80% utilization, 9 at 90%.
  • A burst of ten 2,000-token prompts turns a 65 ms TTFT into a staircase up to 650 ms on an idle H100.
  • The cheapest levers remove work or reorder it: a stable prompt prefix for prefix caching, priority for interactive traffic, then capacity and admission control. Our target is p95 TTFT ≤ 500 ms at the client.
  • Measure TTFT at the client with streaming, stopping at the first non-empty chunk; split server-side TTFT into queue and prefill time; set targets on p95 or p99, not the mean.

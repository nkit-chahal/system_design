Introduction

Most companies that serve open models do not serve just one model. A support platform fine-tunes the base model for each enterprise customer on that customer's tickets. A developer tools company keeps one variant for SQL, one for code review, and one for commit messages. A marketplace lets every seller upload a tone-of-voice tune. The result is dozens, hundreds, or thousands of fine-tuned variants of the same base model, most of them used only occasionally.

Serving each variant as its own deployment is simple and very wasteful. Every deployment holds a full copy of the weights, 16 GB for Llama 3.1 8B, on a GPU that mostly sits idle waiting for that variant's few requests. If the variants were trained with LoRA, almost all of those 16 GB are identical across variants: the fine-tune lives in a small set of extra matrices, tens of megabytes each. Multi-LoRA serving keeps one copy of the base model on the GPU and swaps or mixes the small adapters per request, so one GPU can serve hundreds of variants.

On the left, three fine-tuned variants each run on their own GPU with a full 15 GiB copy of the weights; each GPU is mostly idle. On the right, a single GPU holds one 15 GiB copy of the base model plus many 80 MiB adapters, and requests for different customers are batched together. A note says 500 variants would need 500 GPUs on the left and a handful on the right.

Sharing a GPU among customers also makes the deployment multi-tenant: requests from different customers, using different adapters, run in the same batch. That raises questions a single-model deployment never faces: who may use which adapter, how one customer's burst affects another's latency, and how to bill each customer for the GPU time it used.

In this lesson, we recap LoRA from a serving point of view and compute adapter sizes for Llama 3.1 8B, compare merged and unmerged adapters, look at the kernels and memory managers that batch many adapters in one forward pass, map the engine flags, and then design a multi-tenant deployment for 500 customer adapters with worked memory numbers.

Clarifying the Problem

Multi-LoRA questions usually start from a platform with many customers. Here is a typical exchange:

Candidate: How many fine-tuned variants do we serve, and what do they share?
Interviewer: 500 enterprise customers, each with its own LoRA adapter trained on Llama 3.1 8B Instruct from its support tickets. A few new adapters arrive every week.

Candidate: What rank and target modules does the training pipeline use?
Interviewer: Rank 16 on all linear layers by default. A handful of customers paid for rank 64.

Candidate: How is traffic spread across customers?
Interviewer: Together they send our usual volume, about 1,000 requests per minute (16.7 per second) with a daily cycle of 8 to 33 per second. It is skewed: the top 50 customers send most of it, and many customers send only a few requests a day.

Candidate: Do the usual latency targets apply to every customer, including rarely used adapters?
Interviewer: Yes. p95 TTFT under 500 ms and p95 TPOT under 25 ms, for everyone.

Candidate: What are the isolation requirements?
Interviewer: A customer must never reach another customer's adapter or see any trace of another customer's data. Contracts also require a monthly usage report per customer.

This lesson deliberately changes the running example: the same model and the same total traffic, but split across 500 customer adapters. The question underneath is: how do we serve 500 adapters at the course's latency targets on a few GPUs instead of 500, and keep the customers isolated, fairly treated, and correctly billed?

LoRA from a Serving Point of View

Frozen weights plus a low-rank update

Full fine-tuning changes every weight of the model. LoRA (low-rank adaptation) freezes the pretrained weights and learns a small correction for selected weight matrices [1]. For a frozen matrix W of shape d_{\text{out}} \times d_{\text{in}}, LoRA learns two thin matrices, A of shape r \times d_{\text{in}} and B of shape d_{\text{out}} \times r, where the rank r is small, typically 8 to 64. The layer's output becomes:

h = W x + \frac{\alpha}{r} B A x

The scaling factor \alpha is a training hyperparameter stored in the adapter's config. B starts at zero, so training begins from the base model's behavior. Figure 2 shows the shapes for the query projection of Llama 3.1 8B.

The input x of 4,096 numbers flows through two paths. The frozen base weight W, 4,096 by 4,096, holds 16.8 million parameters. The LoRA path first multiplies by A, 16 by 4,096, shrinking x to 16 numbers, then by B, 4,096 by 16, expanding back to 4,096. The two paths are added. A and B together hold 131,072 parameters, 0.8% of W.

Two properties matter for serving. First, the adapter is tiny compared with the base model, so many adapters fit where one extra model copy would not. Second, the base path W x is the same for every adapter, so requests for different adapters can share it, as long as the engine computes each request's own BAx term.

How big is an adapter?

Each adapted matrix adds r \times (d_{\text{in}} + d_{\text{out}}) parameters. Llama 3.1 8B has a hidden size of 4,096, a feed-forward size of 14,336, 32 query heads and 8 KV heads of dimension 128, and 32 layers [2]. Its seven linear projections per layer have these shapes:

  • Attention: q_proj and o_proj are 4,096 × 4,096, so each adds r \times 8{,}192. k_proj and v_proj map 4,096 to 8 × 128 = 1,024, so each adds r \times 5{,}120. Together: r \times 26{,}624 per layer.
  • MLP: gate_proj, up_proj, and down_proj connect 4,096 and 14,336, so each adds r \times 18{,}432. Together: r \times 55{,}296 per layer.
  • All seven: r \times 81{,}920 per layer, or r \times 2{,}621{,}440 over 32 layers.

At rank 16 on all linear layers, that is 16 × 2,621,440 = 41,943,040 parameters, which at 2 bytes each in BF16 is 83,886,080 bytes, exactly 80 MiB. Table 1 repeats the calculation for common choices.

Our default adapter, 80 MiB, is 0.52% of the 8.03B-parameter base model, so 500 of them total 500 × 80 MiB ≈ 39 GiB, less than three copies of the base weights. The rank-64 adapters are four times larger, 320 MiB each. Size scales linearly with rank and with the number of adapted modules, which is why the serving team should have a say in the training defaults.

Merged versus unmerged adapters

Because W x + \frac{\alpha}{r} BAx = (W + \frac{\alpha}{r} BA)x, an adapter can be merged into the base weights once, producing an ordinary model with exactly the base model's speed. The LoRA paper highlights this: a merged adapter adds no inference latency [1]. The price is flexibility. A merged model serves one adapter only, and switching adapters means rewriting 16 GB of weights.

An unmerged adapter stays separate, and the engine computes the extra BAx term at every adapted layer for every token. The extra arithmetic is small: 2 FLOPs per adapter parameter per token, or about 84 MFLOPs against 16 GFLOPs for the base model, about 0.5%. The real cost is that these thin matrix products run poorly on GPUs and add kernel launches and memory reads. In exchange, one copy of the base model serves every adapter, and requests for different adapters can share a batch. Figure 3 compares the two.

On the left, merged: each adapter is folded into its own copy of the weights, W plus BA for customer A and W plus BA for customer B, each on its own GPU. There is no extra latency, but one copy per adapter and no batching across adapters. On the right, unmerged: one shared W computes Wx for a mixed batch, and small per-request BAx terms are added from an adapter store. One copy serves all adapters, at the cost of some extra latency per step.

Neither choice is always right. A single high-traffic variant that fills its own GPUs should be merged and served like any other model. A long tail of low-traffic variants should stay unmerged and share GPUs. dLoRA switches between the two at runtime, merging when one adapter dominates a replica's traffic and unmerging when traffic is mixed [3].

Batching Many Adapters in One Forward Pass

Why the naive approach fails

The simplest multi-adapter engine keeps several adapters in GPU memory but runs one adapter at a time: it batches the requests for adapter A, runs a step, then those for adapter B. Continuous batching (Lesson 7, Continuous Batching) gets its throughput from putting many requests in each step, and splitting the batch by adapter destroys that. With 500 adapters and 53 concurrent streams per GPU, most batches would contain only one or two requests.

The fix is to run the shared base computation W x as one large matrix multiply over the whole batch, then add each request's own BAx. The hard part is the second step: each row of the batch needs a different pair of small matrices.

Punica and the SGMV kernel

Punica introduced a CUDA kernel for exactly this, called Segmented Gather Matrix-Vector multiplication (SGMV) [4]. The batch is sorted so that requests using the same adapter sit next to each other, forming segments. For each segment, the kernel gathers that adapter's A and B and applies them only to that segment's rows. It runs in two steps: a shrink that multiplies by A and reduces each row from 4,096 numbers to r, and an expand that multiplies by B and brings it back to 4,096, where it is added to the base output. Figure 4 shows one layer for a batch of six tokens from three customers.

A batch of six token rows is sorted into segments: two rows for customer A, one for B, three for C. All six rows go through one batched multiply with the shared base weight W. In parallel, the SGMV shrink step multiplies each segment by its own adapter's A, producing rank-16 rows, and the expand step multiplies by its own B. The LoRA outputs are added to the base outputs. A note says the base weights are read once for the whole batch.

Punica reports 12× higher throughput than state-of-the-art serving systems when serving multiple LoRA models, while adding about 2 ms of latency per token [4]. Its scheduler also consolidates work: it sends new requests to a small set of busy GPUs and migrates requests to free others. Today's engines descend from this design. vLLM's LoRA layers call Triton lora_shrink and lora_expand kernels through a wrapper still named after Punica [16], and SGLang's default LoRA backend is a chunked SGMV kernel, csgmv [8].

S-LoRA and unified paging

Punica solved the compute side. S-LoRA tackled memory: how to keep thousands of adapters available without fragmenting GPU memory [5]. It stores all adapters in host memory and copies the ones the current batch needs to the GPU, predicting the next batch's adapters from the waiting queue so that copies overlap with computation.

Its key idea is unified paging: one memory pool holds both the KV cache and the adapter weights, in pages that are each a vector of the model's hidden size. A KV cache for S tokens takes S pages and a rank-R adapter takes R pages, interleaved and non-contiguous, as the top of Figure 5 shows. Adapters of different ranks and sequences of different lengths draw from the same free list, so memory is not split into fixed adapter slots that sit half empty, as they do in the bottom of Figure 5. This is the same idea as PagedAttention (Lesson 8, PagedAttention), extended to adapter weights.

A row of 24 pages, each one hidden-size vector, is shared. KV cache pages for two requests (5 and 4 pages) and adapter pages for a rank-4 adapter X and a rank-2 adapter Y are interleaved, and 9 pages are free for any use. For contrast, fixed adapter slots sized for rank 8 leave half of X's slot and three quarters of Y's slot reserved but unused, and the KV cache cannot borrow that space.

S-LoRA served 2,000 adapters at once on a single A100 80 GB, with up to 4× the throughput of a vLLM baseline that merged adapters into separate model copies, and up to 30× that of Hugging Face PEFT [5]. Its custom kernels, MBGMM for prefill and MBGMV for decode, extend Punica's kernels to non-contiguous memory and mixed ranks.

What adapters cost at decode time

Lesson 3's decode lower bound, step time ≥ bytes read ÷ memory bandwidth, extends naturally to adapters. Each decode step must read the weights of every distinct adapter in the batch, in addition to the base weights and the KV cache. Suppose 53 concurrent streams on one H100 (Lesson 19's capacity at our latency targets) all use different rank-16, all-linear adapters:

  • Extra bytes per step: 53 × 80 MiB ≈ 4.4 GB.
  • Extra time per step: 4.4 GB ÷ 3.35 TB/s ≈ 1.3 ms, about 6% of a 21 ms step.
  • With rank-64 adapters: four times as much, about 5.3 ms, or 25% of the step.

The bound explains two practical rules. Batches that share adapters are cheaper, because each distinct adapter is read once per step however many rows use it. And rank is a serving cost, not just a training choice: a fleet of rank-64 adapters costs four times the adapter bandwidth of rank 16.

Adapter caching tiers

An adapter can live in four places, and the engine moves it toward the GPU on demand, as Figure 6 shows. The latencies below are rough estimates for one 80 MiB adapter under stated assumptions, not measurements; measure your own storage path.

Four tiers stacked from fastest to slowest. GPU slots, sized by the maximum adapters per batch: already resident, no delay. CPU memory cache, sized by the CPU adapter limit: about 3.4 ms over PCIe at an assumed 25 GB/s. Local NVMe disk: about 42 ms at an assumed 2 GB/s including parsing. Remote object store or model hub: about 0.4 s or more at an assumed 200 MB/s plus request overhead. Arrows show adapters being promoted up and evicted down in least-recently-used order. Figures are labeled as rough assumptions.
  • GPU slots: adapters ready for the current batch. In vLLM, --max-loras sets how many distinct adapters one batch may use, and the engine reserves GPU memory for that many adapters at --max-lora-rank [7].
  • CPU memory: an LRU cache of recently used adapters (--max-cpu-loras in vLLM). Promotion is a host-to-device copy. PCIe Gen5 x16 peaks at about 64 GB/s each way; at an assumed effective 25 GB/s, 80 MiB takes about 3.4 ms, short enough to hide inside one request's prefill.
  • Local disk: adapters downloaded earlier. At an assumed 2 GB/s for reading and parsing, about 42 ms, which a cold request feels in its TTFT.
  • Remote storage: an object store or model hub. At an assumed 200 MB/s plus connection setup, about 0.4 s or more, a visible TTFT spike. Pre-download adapters to local disk when they are published instead of on first request.

When a batch already uses --max-loras distinct adapters, a request for one more waits even if memory is free. vLLM counts these as waiting for a "deferred" reason in vllm:num_requests_waiting_by_reason (Lesson 29, Queue Depth), which is the signal that the slot count is too low for the traffic mix.

Multi-Tenant Serving

Routing requests to replicas that hold the adapter

With several replicas, the router decides which adapters each replica must hold. Spraying requests for all 500 adapters across all replicas makes every replica load every adapter, and its GPU slots and CPU cache churn constantly. Lesson 25, Request Routing, gives each adapter a home group of two or three replicas and balances load within the group. The Kubernetes Gateway API Inference Extension implements this as LoRA affinity: its endpoint picker prefers pods that already have the requested adapter loaded, reading vLLM's vllm:lora_requests_info gauge, whose labels list the running and waiting adapters and the max_lora setting [10][11].

Home groups also shrink the per-replica working set. With 8 replicas and home groups of 2, each replica is home to 500 × 2 ÷ 8 = 125 adapters instead of 500. Skew helps further: the top customers' adapters stay resident, and the long tail shares the remaining slots.

Isolation of data and adapters

A customer's adapter was trained on that customer's data and can reproduce parts of it, so it is customer data and needs the same protection. Figure 7 shows where the controls sit.

Tenant requests with API keys reach a gateway. The gateway authenticates the key, maps the tenant to its allowed adapter, rewrites the model field, applies per-tenant token buckets and concurrency caps, and records usage per tenant and adapter. The router sends the request to a replica in the adapter's home group. Inside the replica, the engine keeps one base model, adapter slots, and a KV cache whose prefix blocks are keyed by adapter and cache salt. The adapter admin endpoints are reachable only from an internal control plane, not from tenants.
  • Bind tenants to adapters at the gateway. The engine trusts the model field, so a client that names another customer's adapter would get it. The gateway must map each API key to the adapters that tenant may use and overwrite the field, never pass it through.
  • Keep adapter management private. Runtime loading endpoints accept arbitrary paths. Expose them only to an internal control plane that loads adapters from a vetted registry, and do not enable resolver plugins that download unknown names on request.
  • Keep the prefix cache per tenant. vLLM includes the adapter ID in each block's hash, so different adapters never share cached blocks; requests on the bare base model can use cache_salt to stop one tenant from probing another's prompts through cache-hit timing (Lesson 9, vLLM).
  • Keep data out of shared logs. Prompts and outputs from all tenants pass through the same process; log metadata, not text, unless the tenant agreed.

Sharing a batch does not mix data between rows: each row's attention reads only its own KV cache, and each row's LoRA term uses only its own adapter. The risks are in the control plane and the caches, not in the matrix multiplies.

Quotas, fairness, and noisy neighbors

On a shared replica, one tenant's traffic changes everyone's latency. Three noisy-neighbor patterns are specific to multi-LoRA serving:

  • KV cache hogging: a tenant sending 30,000-token documents fills the cache and pushes others into the queue or preemption. Per-tenant token buckets and concurrency caps at the gateway bound this (Lesson 26, Rate Limiting).
  • Adapter thrash: a tenant rotating through many rarely used adapters, or a burst of cold adapters, keeps evicting other tenants' warm adapters and fills the GPU slots, so requests for warm adapters wait as "deferred". Cap distinct adapters per tenant, and pin the adapters of tenants with latency guarantees.
  • Expensive adapters: a high-rank adapter in the batch adds its bytes to every decode step for every row. Serve rank-64 adapters on their own pool, or price them accordingly.

Inside the replica, first-come-first-served lets a flooding tenant delay everyone. The Virtual Token Counter scheduler keeps a running count of the input and output tokens served to each client and always serves the waiting client with the lowest count, which bounds the service gap between backlogged clients [12]. Most production stacks approximate this with weighted fair queues per tenant at the router, as Lesson 26 describes.

Per-tenant cost attribution

Engines report fleet-level metrics, but the bill is per tenant. vLLM's model_name metric label carries the served base model, not the adapter [13], so per-tenant token counts must come from request-level records: the gateway logs each request's tenant, adapter, prompt tokens, cached prompt tokens, and output tokens from the response's usage field, as Lesson 31, Per-Request Token Accounting, describes. To turn tokens into dollars, split the fleet's cost by each tenant's share of weighted tokens. If 8 H100s cost 8 × $3.00 = $24.00 per hour (assuming $3.00 per H100-hour) and a tenant used 2% of the weighted tokens, it is charged $0.48 for that hour. Weight output tokens more heavily than input tokens, rank-64 adapters more than rank-16, and add a fixed fee for tenants whose adapters are pinned in GPU memory, since they occupy capacity even when idle.

Which layout fits our 500 customer adapters?

We compare three layouts for 500 rank-16 adapters at a peak of 33 requests per second.

  • One merged deployment per customer: 500 copies of 16 GB on at least 500 GPUs, costing 500 × $3.00 = $1,500 per hour, while the whole fleet's peak traffic needs about 33 ÷ 5 ≈ 7 H100s at our latency targets. Each GPU would carry on average 16.7 ÷ 500 ≈ 0.03 requests per second, under 1% of the roughly 5 per second it can serve. Rejected, except for a single customer large enough to fill its own GPUs.
  • All 500 adapters resident on every GPU: 500 × 80 MiB ≈ 39 GiB of GPU memory per replica, leaving about 13 GiB of the 52 GiB KV budget (Lesson 3, with --gpu-memory-utilization 0.90 set explicitly), or about 106,000 tokens and 42 chat requests, fewer than the 53 streams we need. Rejected: most of those adapters are idle at any moment.
  • A small set of GPU slots, a CPU cache, and home-group routing: chosen. Figure 8 shows the memory budget of one replica.
A horizontal bar for the H100: 15 GiB of weights, about 4.6 GiB of activations and CUDA graphs, 5 GiB for 64 adapter slots at rank 16, about 47 GiB of KV cache, and 8 GiB held back. 47 GiB divided by 128 KiB per token gives about 385,000 tokens, or about 154 chat requests, well above the 53 streams needed. Below, host memory holds a CPU cache of 128 adapters, 10 GiB, covering the replica's 125 home adapters; the other adapters stay on local disk.

Each replica's 53 concurrent streams draw from its 125 home adapters. If every adapter were equally popular, a batch of 53 would contain about 125 × (1 − (1 − 1/125)53) ≈ 43 distinct adapters; with real skew it contains fewer. So we set --max-loras 64, which reserves 64 × 80 MiB = 5 GiB and leaves about 47 GiB of KV cache, about 385,000 tokens or 154 chat requests, nearly three times the 53 streams we need. --max-cpu-loras 128 keeps every home adapter in host memory for 10 GiB per replica, so a cold adapter costs a few milliseconds of PCIe copy rather than a disk read. Decode pays at most about 1.3 ms per step for adapter reads, and we verify on a load test that p95 TPOT stays under 25 ms. Eight replicas cover the 33 requests per second peak with room for the LoRA overhead, and the autoscaler (Lesson 22, Autoscaling) removes replicas at night. The fleet costs about $24 per hour at peak instead of $1,500.

Two rules keep the plan valid as the platform grows. Keep training at rank 16 unless a customer pays for more, and serve rank-64 adapters on a separate pool, because a single --max-lora-rank 64 would make all 64 slots four times larger, 20 GiB. And when a customer's traffic grows large enough to keep its own GPUs busy, merge its adapter and move it to a dedicated deployment.

Size the adapter from the model dimensions before anything else: "rank 16 on all seven projections is 2.6 million parameters per rank, so 42 million parameters, 80 MiB; 500 of them are 39 GiB." It shows you can reason about slots, caches, and bandwidth with real numbers.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • QLoRA trains adapters against a 4-bit quantized base model [14]; serving such an adapter on a BF16 or FP8 base changes the numbers it was trained with, so evaluate on the serving precision (Lesson 13, Quantization - FP8, INT8 and 4-bit).
  • LoRA with tensor parallelism: S-LoRA aligns the adapter's partitioning with the base model's so that one all-reduce covers both [5], and vLLM shards only part of the LoRA computation unless --fully-sharded-loras is set [6].
  • Updating an adapter in place: vLLM's load endpoint accepts load_inplace to replace an adapter under the same name [6], but in-flight requests and cached prefixes should not mix versions, so version adapter names instead.
  • Open-source multi-LoRA servers such as LoRAX popularized dynamic adapter loading and heterogeneous batching; its repository was archived in October 2026, and similar features are now built into the main engines [15].
  • Adapter thrash looks like a cache problem in metrics: watch adapter load counts, "deferred" waiting requests, and TTFT for cold adapters separately from warm ones.
  • Other adapter types, such as prefix tuning or (IA)³, change the serving math; LoRA dominates in practice because its batched kernels are mature in every engine.

Summary

Mind map summarizing the lesson: LoRA adapter sizes, merged versus unmerged, batched kernels, caching tiers, engine flags, and multi-tenant isolation, fairness, and billing.
  • A LoRA adapter adds rank × (d_in + d_out) parameters per adapted matrix. For Llama 3.1 8B at rank 16 on all linear layers that is 42 million parameters, 80 MiB, 0.52% of the base model.
  • Merged adapters cost nothing at inference but need a model copy each; unmerged adapters share one base model and one batch, at a small per-step cost.
  • Punica's SGMV kernel batches requests for different adapters in one forward pass; S-LoRA pages adapter weights and KV cache from one pool and served 2,000 adapters on one A100.
  • Each decode step reads every distinct adapter in the batch: 53 rank-16 adapters add about 1.3 ms to a 21 ms step on an H100, four times that at rank 64.
  • Adapters move between GPU slots (--max-loras), a CPU cache (--max-cpu-loras), local disk, and remote storage; a cold load costs milliseconds from CPU memory and up to seconds from remote storage.
  • For 500 customer adapters: 64 GPU slots (5 GiB), a 128-adapter CPU cache, and home-group routing serve the peak on about 8 H100s instead of 500.
  • Multi-tenancy needs a gateway that binds tenants to adapters, per-tenant quotas and fair queues, private adapter management, and per-request token records for billing.

Introduction

Many of the strongest open models are no longer dense. DeepSeek-V3, Qwen3-235B-A22B, Mixtral, and OpenAI's gpt-oss replace each transformer's feed-forward block with a set of smaller feed-forward networks called experts, and a small router picks a few of them for every token. A model can then hold hundreds of billions of parameters while each token uses only a few tens of billions. This is a mixture-of-experts (MoE) model [1][2].

For training, the attraction is quality per FLOP. For serving, MoE creates a split that dense models do not have: memory follows the total parameters, but per-token compute follows the active parameters. DeepSeek-V3 must keep 671 GB of FP8 weights in GPU memory, yet a token's forward pass costs about as much arithmetic as a 37B dense model [3]. How many of those 671 GB each decode step actually reads depends on the batch, and how the experts are spread across GPUs decides how much data travels between them. Figure 1 shows one MoE layer.

A token's hidden state enters a router, which scores all routed experts and keeps the top k, here 8 of 256 as in DeepSeek-V3. The token is processed by those 8 experts and by one shared expert that every token uses. The expert outputs are multiplied by their gate weights and summed into the layer output. The other 248 experts do no work for this token but still sit in GPU memory.

In this lesson, we look at how routing works, compare total and active parameters for well-known models, work out what an MoE model costs to prefill and decode, compare tensor and expert parallelism, examine the all-to-all communication and load imbalance that expert parallelism brings, study the large deployments that combine wide expert parallelism with disaggregated prefill and decode, and choose a layout for DeepSeek-V3.

Clarifying the Problem

MoE questions usually start when a team wants a frontier-class open model and discovers that it does not fit the hardware it has. Here is a typical exchange between a candidate and an interviewer:

Candidate: Which model, and at what precision?
Interviewer: DeepSeek-V3, using its released FP8 weights. This is a separate service from our Llama 3.1 8B chat assistant.

Candidate: What do requests look like?
Interviewer: The same shape as our chat traffic: about 2,000 prompt tokens and 500 output tokens. At peak we expect about 800 requests generating at the same time.

Candidate: What latency do users need?
Interviewer: It is an internal assistant for long answers, so p95 time to first token under 1 second and p95 time per output token under 50 ms, which is 20 tokens per second.

Candidate: What hardware can we use?
Interviewer: We own servers with eight H100 80 GB GPUs, connected by NVLink inside each server and by a 400 Gb/s adapter per GPU between servers. We can also rent servers with eight H200 GPUs.

Candidate: Which engines are allowed?
Interviewer: vLLM or SGLang.

The question underneath is: how much memory and bandwidth does this model really need, how should its experts be spread across GPUs, and which hardware serves 800 streams at 20 tokens per second? This lesson uses this MoE scenario, not the course's running example, wherever DeepSeek-V3 appears.

How Mixture-of-Experts Models Work

Routing tokens to experts

In a dense transformer, every token passes through the same feed-forward network (FFN) in every layer. An MoE layer keeps the attention block as it is and replaces the FFN with E expert FFNs plus a router. The router is a single linear layer that scores every expert for the token's hidden state x, keeps the k highest scores, and turns them into gate weights. The layer's output is the gated sum of the chosen experts [1][2]:

y = \sum_{i \in \text{TopK}(r(x),\,k)} g_i(x)\, \text{FFN}_i(x) \;+\; \text{FFN}_{\text{shared}}(x)

The choice is made per token and per layer, so two tokens of the same sentence can use different experts, and one token can use different experts in each layer. Switch Transformer routed each token to a single expert [4]; Mixtral uses 2 of 8 [5]; DeepSeek-V3 and Qwen3 use 8 of 128 or 256.

Two refinements are common. Fine-grained experts split each large expert into several smaller ones, so a token combines more specialists. Shared experts are always active for every token and capture common knowledge, so the routed experts can specialize. Both come from DeepSeekMoE [6], and DeepSeek-V3 uses 256 small routed experts plus one shared expert per MoE layer [3]. Not every model keeps shared experts: the Qwen3 report states that its MoE design excludes them [7].

Training must keep the router from sending most tokens to a few favorite experts. Earlier models added an auxiliary loss that penalizes imbalance [2][4]. DeepSeek-V3 instead adds a per-expert bias to the scores used for selection and adjusts it after each step, lowering it for overloaded experts and raising it for idle ones [3]. Training-time balance helps serving, but it is measured over training batches, not over a production traffic mix, so serving systems still need their own balancing, as we see later.

Memory Follows Total, Compute Follows Active

Memory: every expert must be resident

Any token may pick any expert, so every expert must sit in GPU memory, or the step stalls while weights are fetched. The weight budget is the total parameter count times the bytes per parameter (Lesson 17, VRAM Budgeting). For DeepSeek-V3, the config gives the split [12]: each expert is three 7,168 × 2,048 matrices, about 44 million parameters, and 256 of them in each of 58 MoE layers come to about 654 billion parameters. The attention blocks, the shared experts, the 3 dense layers at the bottom, and the embeddings make up the remaining 17 billion. In FP8 that is about 671 GB, or 625 GiB, before any KV cache.

The cache itself is small for this model. Its multi-head latent attention stores one 576-value latent per token per layer, about 68.6 KiB per token in BF16 (Lesson 3, KV Cache), roughly half of Llama 3.1 8B's 128 KiB. A 2,500-token conversation needs about 168 MiB. For MoE models, the weights are the memory problem.

Prefill: compute follows the active parameters

A forward pass costs about 2 FLOPs per active parameter per token (Lesson 2, Prefill vs Decode). For DeepSeek-V3, that is 2 × 37B ≈ 75 GFLOPs per token, so a 2,000-token prompt needs about 150 TFLOPs plus attention, the same as a 37B dense model and about 18 times less than a dense 671B model would need. At 50% of one H100's 1,979 dense FP8 TFLOPS, that is about 150 ms of compute, and less when the prompt's work is spread over several GPUs. A prompt's tokens route to almost every expert, so prefill reads all the weights, but with thousands of tokens per step it stays compute-bound. Prefill is where MoE delivers its promise directly.

Decode: the batch decides how many experts are read

Decode is memory-bound (Lesson 2), so its cost is the bytes each step reads. Here the batch matters in a way it does not for dense models. A single token reads the non-expert weights plus 8 experts in each MoE layer, about 37 GB in all. A batch of tokens reads every expert that any of them picks. If routing were uniform and independent, the expected fraction of experts touched by a batch of B tokens would be:

f(B) = 1 - \left(1 - \frac{k}{E}\right)^{B}

For DeepSeek-V3, k/E = 8/256 = 1/32. One token touches 3.1% of the experts, 16 tokens about 40%, 64 tokens about 87%, and 128 tokens about 98%. Figure 3 plots the curve for three expert layouts. Real routing is skewed, so hot experts are hit sooner and rare ones later, but the shape holds.

How large is "very large"? An expert's matrix multiply becomes compute-bound when it sees enough tokens per weight byte. With FP8 weights, each token adds 2 FLOPs per byte, and the H100's ridge point is 1,979 TFLOPS ÷ 3.35 TB/s ≈ 590 FLOPs per byte, so an expert needs about 295 tokens per step (Lesson 2 derives the same 295 for BF16). Each token visits 8 of 256 experts, so an expert sees B/32 tokens on average, and the batch must reach about 32 × 295 ≈ 9,500 tokens per step. At chat lengths that is over 23 million cached tokens across the deployment, far more than one server can hold. This one number explains why the largest MoE deployments spread experts over dozens of GPUs.

Spreading Experts Across GPUs

A 671 GB model needs at least eight large GPUs, so the next question is how to split it. Lesson 18, Tensor Parallelism, introduced the options; MoE adds one of its own. Figure 5 compares the two main layouts on four GPUs.

Left panel, tensor parallel: each of four GPUs holds a quarter of every expert and a quarter of the attention heads, and all four work on every token, joined by an all-reduce after each block. Right panel, expert parallel with data-parallel attention: each GPU runs attention for its own requests and holds 2 of the 8 whole experts; tokens are sent all-to-all to the GPUs that hold their chosen experts and sent back.

Tensor parallelism within experts

The simplest layout treats each expert like a dense FFN and splits its matrices across the GPUs of a tensor-parallel group, exactly as Lesson 18 splits Llama's MLP. Every GPU holds a slice of every expert and works on every token, so load is perfectly even and communication is the familiar two all-reduces per layer. In vLLM this is the default for MoE layers when expert parallelism is not enabled [13].

Two problems appear at scale. The expert matrices are small: DeepSeek-V3's 2,048-wide experts become 256-wide slices at TP = 8, and such thin multiplies run inefficiently. And attention suffers for models with latent attention. MLA caches one latent vector per token with no head dimension to split, so under tensor parallelism every GPU stores and reads the same latent for every request. Eight GPUs then hold one GPU's worth of distinct cache.

Expert parallelism

Expert parallelism (EP) places whole experts on different GPUs: with 256 experts on 8 GPUs, each GPU holds 32 complete experts of every MoE layer [2]. Attention is usually run data-parallel alongside it: each GPU keeps a full copy of the attention weights and serves its own subset of requests, so each request's cache lives on exactly one GPU and nothing is duplicated. The LMSYS team describes this "DP attention" as removing KV cache duplication for DeepSeek models [14]. In vLLM, --enable-expert-parallel forms an EP group of size TP × DP, and with --tensor-parallel-size 1 --data-parallel-size 8 attention is replicated across the eight data-parallel ranks [13]. In SGLang, --ep sets the expert-parallel size and --attn-dp-size the number of data-parallel attention groups [15][16].

Each MoE layer then needs two collective exchanges, shown in Figure 6. In dispatch, every GPU sends each of its tokens' hidden states to the GPUs that hold the chosen experts. Those GPUs run their experts on whatever tokens arrived. In combine, the results travel back to each token's home GPU, where they are weighted and summed. Both are all-to-all operations: every GPU sends a different amount to every other GPU.

Four GPUs, each with its own tokens after attention. In the dispatch step, arrows send each token's hidden state to the GPUs that hold its chosen experts; GPU 2 receives the most tokens because it holds a popular expert. Each GPU runs its experts on the tokens it received. In the combine step, the outputs flow back to the tokens' home GPUs, which add them with their gate weights and continue to the next layer's attention. A note gives the volume for DeepSeek-V3: 56 KiB per token for an FP8 dispatch and 112 KiB for a BF16 combine, per layer.

What the all-to-all costs

Each token is sent to 8 experts in each of 58 MoE layers. DeepSeek-V3 quantizes the hidden state to FP8 before dispatch and keeps the combine in BF16 [3], so one token costs 8 × 7,168 bytes = 56 KiB to dispatch and 8 × 14,336 bytes = 112 KiB to combine, 168 KiB per layer, or about 9.5 MiB per token per forward pass. This is an upper bound: some chosen experts are on the token's own GPU, and DeepSeek's kernels send a token across the network at most once per destination node.

For a decode step with 128 tokens per GPU, that is about 1.28 GB per GPU per step. Over NVLink at 450 GB/s each way, it takes about 2.8 ms. Over a 400 Gb/s adapter at 50 GB/s, it takes about 25.5 ms, which by itself would exceed a 25 ms TPOT target. Large deployments use four techniques to live with it:

  • Keep the exchange on NVLink when possible. An EP group inside one 8-GPU server, or inside a rack-scale NVLink domain, never touches the network.
  • Limit how far a token travels. DeepSeek-V3 routes each token to experts on at most 4 nodes, and sends it over InfiniBand once per node before forwarding it over NVLink to the GPUs there [3].
  • Use specialized kernels. DeepEP, DeepSeek's open-source communication library, provides all-to-all kernels for MoE dispatch and combine, including FP8 dispatch [17]. vLLM exposes it through --all2all-backend with deepep_high_throughput for prefill and deepep_low_latency for decode [13]; SGLang uses --moe-a2a-backend deepep with --deepep-mode auto, which switches between a high-throughput mode for prefill and a low-latency, CUDA-graph-compatible mode for decode [15].
  • Overlap communication with computation. Splitting each batch into two micro-batches lets one compute while the other communicates. DeepSeek does this in both phases [18], and SGLang enables it with --enable-two-batch-overlap [15].

Load imbalance across experts

Under expert parallelism, a step finishes only when the busiest GPU finishes. If routing sends 1.6 times the average number of tokens to one GPU's experts, every GPU waits for it, and the effective expert throughput drops by that factor. Popularity depends on the content: a coding workload favors different experts than a chat workload, and the mix changes during the day.

Training-era systems bounded the problem with a capacity factor: each expert accepts at most the average number of tokens times a factor such as 1.25, and tokens beyond that are dropped and pass through the residual connection unchanged [4]. Dropping tokens changes the model's output, so serving engines generally process every routed token and absorb imbalance as time instead. The serving fix is to change where experts live:

  • Redundant experts. Duplicate the hottest experts on extra GPUs and split their tokens between the copies. DeepSeek-V3's prefill deployment adds 32 redundant experts, chosen from online statistics and adjusted periodically, for example every 10 minutes [3].
  • An expert-parallel load balancer. DeepSeek's open-source EPLB takes estimated expert loads, such as a moving average of recent counts, and computes which experts to replicate and where to place every copy. Its hierarchical policy, used when the number of nodes divides the number of expert groups, packs groups onto nodes and suits prefill with a smaller EP size; its global policy suits decode with a larger EP size [19].
  • Engine support. vLLM enables EPLB with --enable-eplb and tunes it through --eplb-config, with keys such as window_size, step_interval, and num_redundant_experts; its documentation estimates about 2.4 GB of memory per redundant expert per EP rank for DeepSeek-V3, so redundancy competes with the KV cache [13]. SGLang offers --enable-eplb, --ep-num-redundant-experts, and --eplb-rebalance-num-iterations [16].
Two bar charts of tokens received by each of eight GPUs. Before rebalancing, GPU 3 receives 1.6 times the average because it holds two popular experts, and every GPU waits for it. After EPLB places a copy of each hot expert on the least-loaded GPUs, the bars are within about 10% of the average and the step is set by a much lower maximum.

The 2.4 GB figure matches the arithmetic: one expert in each of 58 layers is 58 × 44 million ≈ 2.55 billion FP8 parameters, about 2.4 GiB. On a memory-tight layout, a few redundant experts per GPU can cost as much cache as hundreds of concurrent requests.

Wide Expert Parallelism in Production

The 9,500-token batch from the previous section points to the design DeepSeek published for serving V3 and R1: spread the experts so wide that each GPU holds only a few, which leaves room on every GPU for a large share of the batch's cache, and run prefill and decode separately because they want different widths and different communication modes [18]:

  • Prefill: each unit spans 4 nodes, with routed experts at EP32 and attention and shared experts data-parallel over the same 32 GPUs. With 32 redundant experts, each GPU holds 9 routed experts and the shared expert.
  • Decode: each unit spans 18 nodes, with EP144 and 144-way data-parallel attention. Each GPU holds 2 routed experts and the shared expert.
  • Overlap and balance: two micro-batches overlap communication with computation, and separate balancers even out attention work and tokens in prefill, cache usage and requests in decode, and expert load across GPUs.

Over a reported 24-hour window, each H800 node delivered about 73.7k input tokens per second during prefill (including cache hits) and about 14.8k output tokens per second during decode, with an average output speed of 20 to 22 tokens per second per user [18]. The SGLang team reproduced the approach on 12 nodes of 8 H100s, with prefill-decode disaggregation and large-scale EP, and reported 52.3k input and 22.3k output tokens per second per node for 2,000-token inputs, up to 5 times the output throughput of vanilla tensor parallelism on the same hardware [14]. They also explain why the two techniques travel together: without disaggregation, DeepEP's prefill-oriented and decode-oriented dispatch modes cannot both be used within one communication group under DP attention.

A Memory Budget for DeepSeek-V3

Which GPUs, and how many?

Now we can size the interviewer's deployment. We assume vLLM's memory limit is set explicitly to --gpu-memory-utilization 0.90, about 5 GiB per GPU for activations and CUDA graphs, and, conservatively, 141 × 10⁹ bytes ≈ 131 GiB for an H200, whose HBM3e runs at 4.8 TB/s [21]. The H100 exposes about 79.6 GiB. Figure 7 shows the per-GPU budget for four layouts.

Four stacked bars against a scale of GPU memory. 8 × H100 with TP = 8: 78.1 GiB of weights against 71.6 GiB usable, so it does not fit. 8 × H200 with TP = 8: 78.1 GiB of weights, 35 GiB of cache per GPU, but the latent cache is copied on all eight GPUs, so the server holds about 0.54 million distinct tokens. 8 × H200 with DP attention and EP = 8: 92 GiB of weights, 21 GiB of cache per GPU, each GPU holding its own requests, about 2.6 million tokens in total. 16 × H100 across two servers with DP attention and EP = 16: 54 GiB of weights, 13 GiB of cache per GPU, about 3.1 million tokens.
  • 8 × H100, TP = 8: 625 GiB ÷ 8 = 78.1 GiB of weights per GPU, but only 0.90 × 79.6 ≈ 71.6 GiB is usable. Even at 100% it would leave 1.5 GiB per GPU, no room for a cache. It does not fit. vLLM's documentation likewise suggests a multi-node setup for H100s [13].
  • 8 × H100, DP attention + EP = 8: replicating the 17 GB of attention and other non-expert weights on each GPU raises the load to 92 GiB per GPU. It fits even less.
  • 8 × H200, TP = 8: 78.1 GiB of weights leaves about 35 GiB of cache per GPU. Because every GPU holds the same latents, the server stores about 35 GiB ÷ 68.6 KiB ≈ 535,000 distinct tokens, or about 214 conversations of 2,500 tokens.
  • 8 × H200, DP attention + EP = 8: 92 GiB of weights leaves only about 21 GiB of cache per GPU, but each GPU's cache belongs to its own requests. The server stores about 2.6 million tokens, about 1,040 conversations, nearly five times as many.
  • 16 × H100 in two servers, DP attention + EP = 16: 54 GiB of weights per GPU and about 13 GiB of cache, 3.1 million tokens in all. It uses hardware the team owns, but half of every all-to-all crosses the 400 Gb/s network.

How many streams within 50 ms?

Memory sets an upper bound on concurrency; the TPOT target sets the real one. We plan a 40 ms step to leave room under the 50 ms target, assume decode reaches 65% of peak bandwidth (as in Lesson 19), and model each GPU's step as its weight bytes (scaled by f(B) for the experts) plus its requests' cache, plus the all-to-all time. At about 950 streams, every expert is touched every step, and each sees about 950 × 8 ÷ 256 ≈ 30 tokens, a tenth of the 295 needed to be compute-bound. The H200 server is still reading weights most of the time, which is why the wide deployments in the previous section go further. A tighter target changes the picture: even a full 25 ms step allows only about 40 to 55 streams on either H200 layout, because nearly all of the step goes to reading experts. MoE models are cheapest per token at relaxed latency targets and large batches.

How should we serve this MoE model?

We choose one 8 × H200 server per replica, with data-parallel attention and EP = 8. It is the only single-server layout that fits with a useful cache, its all-to-all stays on NVLink (about 2.3 ms per step in our model), and at about 950 streams it covers the 800-stream peak with about 15% to spare. Because one replica is one server, we run two for redundancy (Lesson 40, Reliability and Rollouts). We start without redundant experts, since each costs 2.4 GiB per GPU of an already small cache, and turn on EPLB only if the logged balancedness shows a persistent hot GPU. The 16 × H100 option is the fallback if H200s are unavailable: it fits and reaches a similar stream count in our model, but its step depends on the network all-to-all, so we would add DeepEP's low-latency kernels and two-batch overlap and verify the p95 TPOT under load before committing. Prefill-decode disaggregation and wider EP become worth their complexity only if traffic grows to several servers' worth.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Low-bit expert weights: gpt-oss ships its MoE weights in MXFP4, which is why the 117B-parameter model fits on one 80 GB GPU [9] (Lesson 13, Quantization - FP8, INT8 and 4-bit).
  • Speculative decoding for MoE models: DeepSeek-V3's multi-token prediction module can serve as a draft, raising the tokens produced per expert read [3][14] (Lesson 15, Speculative Decoding).
  • Why MFU for an MoE model should count active, not total, parameters, while bandwidth utilization depends on how many experts each batch touches (Lesson 19, GPU Utilization).
  • Rack-scale NVLink systems such as the GB200 NVL72, which keep a 72-GPU expert-parallel group off the network entirely (Lesson 34, Disaggregated Prefill and Decode).
  • Fault tolerance for wide EP: losing one GPU removes some experts, so the engine must reroute or reload them; SGLang's elastic EP addresses partial failures [20].
  • Pricing: because decode reads most experts at moderate batch, the cost per token of an MoE model depends strongly on batch size and latency target, more than for a dense model (Lesson 20, Cost per Million Tokens).

Summary

Mind map summarizing the lesson: routing and experts, total versus active parameters, prefill and decode cost, tensor versus expert parallelism, all-to-all and load balancing, wide EP deployments, and the memory budget for DeepSeek-V3.
  • An MoE layer routes each token to its top-k experts, plus any shared experts. DeepSeek-V3 picks 8 of 256 routed experts and has 671B parameters, of which 37B are active per token.
  • Memory follows total parameters: all 671 GB of FP8 weights must be resident. Prefill compute follows active parameters: about 75 GFLOPs per token.
  • Decode reads every expert the batch touches, 1 − (1 − k/E)B of them: 3% at batch 1, 87% at batch 64. At batch 64, DeepSeek-V3 reads 9.1 GB per token, close to a dense 671B model.
  • Expert parallelism places whole experts on GPUs and uses data-parallel attention, avoiding duplicated MLA cache; each MoE layer needs a dispatch and a combine all-to-all, about 9.5 MiB per token for DeepSeek-V3.
  • Load imbalance makes every GPU wait for the busiest one; redundant hot experts placed by EPLB fix it at about 2.4 GB per extra expert per GPU.
  • DeepSeek-V3 does not fit on 8 H100s. One 8 × H200 server with DP attention and EP = 8 holds about 2.6M tokens of cache and about 950 streams at a 40 ms step; wide EP with disaggregated prefill and decode serves the largest fleets.

Introduction

Traffic to an LLM product is never flat. It is low at night, climbs when the business day starts, and jumps when a feature launches or a customer runs a batch job. A fleet sized for the daily peak wastes GPUs for most of the day; a fleet sized for the average falls over every afternoon. Autoscaling adds and removes model replicas automatically so that capacity follows demand.

Ordinary web services autoscale on CPU utilization. LLM servers break that recipe three ways. The usual utilization metrics barely move with load, a new replica takes minutes rather than seconds to start, and removing a replica can cut off answers that are still streaming. Figure 1 shows the control loop we need to get right.

Requests flow through a load balancer to N vLLM replicas; Prometheus scrapes their metrics, an autoscaler (HPA or KEDA) sets N, and a node autoscaler adds a GPU node when a new pod cannot find a free GPU.

In this lesson, we look at why utilization-based scaling fails for LLM servers, which metrics track load instead, how to wire them into Kubernetes, how much spare capacity the startup delay forces us to keep, and how to scale down without hurting users.

Clarifying the Problem

Autoscaling questions usually begin once a team has a working deployment and a cloud bill. Here is a typical exchange between a candidate and an interviewer:

Candidate: What are we serving, and on what?
Interviewer: Llama 3.1 8B Instruct on vLLM. Each replica is one pod with one H100, running on Kubernetes in a public cloud.

Candidate: What does traffic look like over a day?
Interviewer: About 8 requests per second overnight (480 a minute). It jumps to about 1,600 a minute within ten minutes when the business day starts at 9:00 and peaks near 33 per second (2,000 a minute) in the afternoon, for an average of 1,000 a minute. Surges can double traffic within five minutes, and a product launch can bring a 10× spike. Requests are chat turns of about 2,000 prompt tokens and 500 output tokens.

Candidate: What are the latency targets?
Interviewer: p95 time to first token of at most 500 ms, and p95 time per output token of at most 25 ms, so text streams faster than people read.

Candidate: How much load can one replica take while meeting them?
Interviewer: About 5 requests per second, which is about 53 concurrent streams at roughly 21 ms per decode step (Lesson 19, GPU Utilization). Beyond that, latency climbs quickly.

Candidate: How long does a new replica take to start serving?
Interviewer: About 8 minutes if it needs a new GPU node, and about 3 minutes if a running node has a free GPU.

Candidate: Today the HPA scales on CPU utilization, I assume?
Interviewer: Yes, and it never scales. During spikes, users wait several seconds for the first token while CPU sits at 15%.

The question underneath is: which signal tells us how many replicas we need right now, and how much spare capacity must we hold, given that new capacity takes minutes to arrive?

Why Utilization Metrics Fail for LLM Servers

Classic autoscaling assumes that a resource's utilization rises in proportion to load and reaches 100% near the point where the service saturates. For an LLM server, none of the three obvious resources behaves that way. Figure 2 sketches what each one reports as offered load rises on a single replica.

Left: as load on one replica rises, GPU utilization jumps to about 98% at once, GPU memory stays at about 90%, CPU creeps from 3% to 22%, and only in-flight requests divided by 53 rises in proportion. Right: p95 TTFT crosses the 500 ms SLO at 300 requests per minute (53 in flight) and climbs steeply toward the point where the KV cache is full.

CPU utilization measures the wrong machine

The work happens on the GPU. The CPU runs the HTTP server, tokenization, and the scheduler loop, which cost roughly the same whether the batch holds 5 or 50 requests, so CPU sits at 15% while users wait seconds for a first token.

GPU utilization saturates at low load

The number most dashboards call GPU utilization is defined by nvidia-smi as the percent of time over the past sample period during which one or more kernels was executing on the GPU [1]. A serving engine runs a decode step, then another, for as long as any request is in flight. One request keeps a kernel running almost all the time, so the metric reads close to 100% at 5 concurrent requests and at 150. It tells us the GPU is busy, not how much more work it can take. Lesson 19, GPU Utilization, and Lesson 30, GPU Metrics, cover finer measures such as SM activity, but none of them maps cleanly to remaining serving capacity.

GPU memory is reserved up front

Recent vLLM versions claim 92% of GPU memory at startup by default (--gpu-memory-utilization 0.92; we set 0.90 explicitly to match Lesson 3, KV Cache) and hand everything beyond the weights to the KV cache. Memory in use is therefore a constant, not a load signal.

Scaling on GPU utilization usually produces the opposite of the intended behavior: the fleet scales to its maximum as soon as each replica has a single request, then never scales down, because a replica that is serving anything reads near 100%.

Signals That Track Load

The signals that work come from the serving engine itself, which knows how many requests it holds and how much memory they use. Figure 3 shows where each one sits on the path of a request through a vLLM replica, and the Prometheus metric that exposes it [2].

A request passes a waiting queue, a running batch capped by --max-num-seqs, KV cache blocks, and streamed tokens, each labeled with its vLLM metric. The roles are: waiting requests as a fast overload alarm, running requests as the primary signal, KV cache usage for long contexts, and TTFT as a lagging SLO guardrail.

In-flight requests versus capacity

The number of requests a replica holds, running plus waiting, follows directly from traffic. Little's law says the average number of requests in a system equals their arrival rate times the time each one spends inside:

L = \lambda \times W

A chat request in our scenario takes about 10.6 s: about 0.1 s to the first token, then 500 tokens at about 21 ms each. At 1,000 requests per minute, L = 16.7 \times 10.6 \approx 177 requests are in flight across the fleet. Dividing by the capacity of 53 per replica gives a utilization that rises linearly with traffic, which is exactly what a proportional autoscaler needs. If we target 40 in-flight requests per replica (75% of capacity), 1,000 requests per minute needs \lceil 177 \div 40 \rceil = 5 replicas, the afternoon peak of 33 requests per second needs \lceil 350 \div 40 \rceil = 9, and 8 per second at night needs 3.

vLLM exposes the two halves as the gauges vllm:num_requests_running and vllm:num_requests_waiting, labeled with model_name [2]. We scale on their sum, because once the batch is full, extra load shows up only in the queue.

Queue depth (waiting requests)

A request waits when the scheduler cannot start it yet, either because the running batch has reached --max-num-seqs or because the KV cache has no free blocks for its prompt. Recent vLLM versions default to a large batch limit (1,024 sequences on an H100 at the time of writing), so for our chat traffic the KV cache is the real limit: requests start waiting only when about 170 are running (Lesson 3, with --gpu-memory-utilization set to 0.90), long after latency has broken at 53. By default, a non-zero queue is a late signal.

We fix that by setting --max-num-seqs 53, the capacity at our latency targets. The replica then never runs more than it can serve well, and any excess becomes visible as waiting requests. A queue that stays above zero means this replica is over capacity right now, which makes it the fastest overload alarm we have. It also lets the router steer new requests to less loaded replicas (Lesson 25, Request Routing). Lesson 29, Queue Depth, treats this metric in depth.

KV cache usage

vllm:kv_cache_usage_perc reports the fraction of KV cache blocks held by running requests, from 0 to 1 (older releases named it vllm:gpu_cache_usage_perc). Cached blocks that no running request holds count as free. This signal counts tokens rather than requests, which matters when prompt lengths vary. At 40 chat requests per replica, the cache is only about 21% full (40 × about 2,250 tokens ≈ 90K of the ≈ 426K tokens Lesson 3 found with --gpu-memory-utilization 0.90). But 13 requests at 32K tokens fill it completely, and once it is full the engine starts preempting requests and recomputing them (Lesson 3). For a mixed workload with long documents, KV cache usage is a useful second trigger with a threshold around 0.7.

Latency SLO burn

It is tempting to scale on what we actually care about, p95 TTFT, computed from the vllm:time_to_first_token_seconds histogram, or on the SLO burn rate, which is how fast, relative to the SLO, the service consumes its error budget [3]. Latency makes a poor primary scaling signal for three reasons. It lags, because a percentile over a window reacts only after many slow requests. It is nonlinear: in Figure 2 it is flat until 53 in flight and then climbs steeply, so it says "too slow" without saying how many replicas to add. And it rises for reasons more replicas cannot fix, such as a burst of very long prompts or a bad deployment. Use it to alert, and to check that the capacity of 53 per replica is still right, not to drive the replica count.

Wiring the Signals into Kubernetes

Kubernetes offers three common ways to scale on engine metrics. Figure 4 shows how the metrics flow in each.

Three panels: the HPA reading Prometheus data through the Prometheus Adapter; KEDA turning a ScaledObject with Prometheus and cron triggers into an HPA; and Knative scaling Revision pods on in-flight requests counted by a queue-proxy, with an activator that holds requests at zero.

HPA with custom or external metrics

The HorizontalPodAutoscaler is a control loop that runs every 15 seconds by default. It computes

\text{desiredReplicas} = \left\lceil \text{currentReplicas} \times \frac{\text{currentMetricValue}}{\text{desiredMetricValue}} \right\rceil

and ignores changes within a 10% tolerance [4]. Out of the box, it reads CPU and memory from the metrics server. For anything else, it queries the custom.metrics.k8s.io or external.metrics.k8s.io APIs, which an adapter must serve. The usual choice for Prometheus data is the Prometheus Adapter, whose rules map a PromQL series to a pods or external metric [5]. The adapter's rule syntax is awkward, and every new metric needs a rule.

KEDA ScaledObject

KEDA wraps the same mechanism in a friendlier resource. A ScaledObject names the Deployment, the replica bounds, and one or more triggers; KEDA creates and feeds an HPA for it [6]. Its Prometheus trigger takes a serverAddress, a PromQL query that returns a single value, and a threshold [7]. With the default AverageValue metric type, the HPA divides the query result by the threshold, so a query that sums in-flight requests across the fleet with a threshold of 40 yields "one replica per 40 in-flight requests". KEDA also scales between zero and one replica itself, and its cron trigger raises the replica count during a time window [8]. The defaults to know: minReplicaCount is 0, pollingInterval is 30 seconds, and cooldownPeriod (300 seconds) applies only to scaling down to zero [6].

Knative concurrency-based scaling

Knative's autoscaler counts in-flight HTTP requests per pod through a queue-proxy sidecar. A streaming chat request counts for as long as its response is open, so concurrency matches "requests in flight" naturally. The target is a soft limit set with autoscaling.knative.dev/target (100 by default), applied at 70% utilization, and containerConcurrency is an optional hard limit [9]. The autoscaler averages over a 60-second stable window and switches to a 6-second panic window when demand reaches twice what the current pods can handle [10]. Its strength is scale to zero: at zero pods, the activator holds incoming requests and asks for capacity [11][12]. But its windows assume pods that start in seconds; with an 8-minute cold start, a 6-second panic decision still delivers capacity 8 minutes later (Lesson 23, Cold Starts).

Scale-Up Lag and Headroom

The timeline of a scale-up

Even with a perfect signal, new capacity arrives late. The delay has two parts. Detection covers the Prometheus scrape interval, the autoscaler's polling, and the HPA loop: typically 30 to 60 seconds. Startup covers everything a new replica must do before it serves: get a GPU node, pull a multi-gigabyte image, download and load 16 GB of weights, and initialize the engine. Lesson 23, Cold Starts, breaks this down; in our scenario it takes about 8 minutes from a new node.

Figure 5 shows what happens when traffic doubles over 5 minutes while the fleet runs at a 75% target: 5 replicas holding 177 requests, with room for 265. The autoscaler reacts within half a minute, but demand overtakes capacity 2.5 minutes into the spike, and the first new replica arrives 8 minutes after it was requested. For almost 8 minutes, requests pile up in queues and TTFT climbs far past the SLO.

Demand rises from 177 to 354 requests in flight between minutes 2 and 7, while capacity stays at 265 (5 replicas × 53) until new replicas arrive from minute 11.2. Demand exceeds capacity for about 7.8 minutes.

How much headroom do we need?

Spare capacity has to carry the growth that happens while new replicas start. Suppose traffic rises by a factor s over T_{\text{rise}} minutes, and new capacity arrives T_{\text{lag}} minutes after the rise begins. During the lag, load grows by (s-1) \times \min(1, T_{\text{lag}} / T_{\text{rise}}) of its starting value, and the replicas already running must hold it. The highest target utilization that survives is

u_{\max} = \frac{1}{1 + (s-1)\,\min\left(1, \dfrac{T_{\text{lag}}}{T_{\text{rise}}}\right)}

Figure 6 plots this for spikes of 1.5×, 2×, and 3×. For the interviewer's 2× surge (s = 2, T_{\text{rise}} = 5 minutes), the answer depends on the lag:

  • New GPU node, 8 minutes: the lag exceeds the rise, so u_{\max} = 1/2 = 50\%. The target is about 26 in-flight requests per replica (26.5), and 1,000 requests per minute needs \lceil 177 \div 26.5 \rceil = 7 replicas.
  • Free GPU on a running node, 3 minutes: u_{\max} = 1/(1 + 0.6) = 62.5\%, a target of about 33, and 6 replicas.
  • Warm pool, 1.5 minutes: u_{\max} = 1/(1 + 0.3) \approx 77\%, a target of about 41, and 5 replicas.
Curves for 1.5×, 2× and 3× spikes fall from 100% as lag grows relative to rise time and flatten at 67%, 50% and 33%. On the 2× curve, a warm pool (1.5 min) allows 77%, a free GPU on a running node (3 min) 62.5%, and a new GPU node (8 min) 50%.

The difference between 7 and 5 replicas, two H100s around the clock, is the price of a slow cold start, which is why the next lesson matters for cost as well as latency. The formula is slightly conservative, since replicas can briefly run above 53 at degraded latency, and slightly optimistic, since it assumes the rise is detected at once.

State the headroom rule as a sentence: "Spare capacity must cover the traffic growth that happens during one cold start." Then plug in numbers. Interviewers want to see that you connect startup time to the size of the fleet.

Minimum replicas

The same reasoning sets the floor. At night, 8 requests per second means about 85 requests in flight. If a 2× surge arrives and no new replica can start in time, the existing replicas must hold 170, which takes \lceil 170 \div 53 \rceil = 4 replicas. Four replicas also leave room to lose one to a node failure at normal night load (3 × 53 = 159 ≥ 85). So the minimum is 4, even though the night's average load fits on 2.

Scaling Down Safely

Stabilization windows and rate limits

Removing a replica is cheap to do and expensive to undo: if traffic returns, the replacement costs another cold start. The HPA's defaults already scale down more cautiously than up. Scale-down uses a 300-second stabilization window, meaning it acts on the highest recommendation of the last five minutes, while scale-up has no window and may add 4 pods or 100% of current pods every 15 seconds, whichever is larger [4]. For GPU replicas we go further: a 10-minute scale-down window and at most one replica removed every 2 minutes, so a brief lull does not trigger a wave of removals followed by a wave of cold starts. On scale-up, we cap additions at 4 pods per minute so that a metrics glitch cannot request 20 GPU nodes at once.

Draining in-flight streams

When the autoscaler removes a pod, Kubernetes marks it Terminating, removes it from the Service's EndpointSlices so it receives no new requests, runs its preStop hook, then sends SIGTERM. If the pod is still running when terminationGracePeriodSeconds expires (30 seconds by default), it is killed [13]. A chat answer that has been streaming for 10 seconds would be cut off mid-sentence. Figure 7 shows the sequence we want instead.

After the replica count is lowered, the pod is marked Terminating and removed from EndpointSlices, a preStop hook waits for in-flight streams to finish, and only then does SIGTERM stop vLLM, all within a 300-second grace period that ends in KILL.

The hook waits a few seconds for endpoint removal to reach the load balancer, then polls the engine's metrics until no requests are running or waiting. The grace period must exceed the longest generation we allow: with max_tokens of 4,096 at 25 ms per token, that is about 100 seconds, so 300 seconds leaves margin. Recent vLLM versions also have a --shutdown-timeout option (0 aborts, a positive value waits) [14]; check how your version treats in-flight requests before relying on it alone. The same drain applies whenever a pod goes away, during deploys and node maintenance too; Lesson 40, Reliability and Rollouts, covers those cases.

Two smaller controls help. The controller.kubernetes.io/pod-deletion-cost annotation suggests which pods a ReplicaSet should remove first, such as the least busy; it is best effort [15]. And a PodDisruptionBudget stops node consolidation from evicting serving pods faster than the fleet can absorb.

Predictive and Scheduled Scaling

Reactive scaling always lags by one cold start. When the shape of traffic is known in advance, we can start replicas before the traffic arrives. Our 9:00 ramp from 480 to 1,600 requests per minute takes ten minutes, faster than the 8-minute startup can follow. Figure 8 compares reactive scaling alone with a scheduled floor.

Demand rises from 85 to 283 requests in flight between 8:55 and 9:05. Reactive capacity, starting from the minimum of 4 replicas, reaches 8 only by 9:13, leaving demand above capacity from about 9:01 to 9:09, while a scheduled floor of 8 replicas from 8:30 stays above demand throughout.

KEDA's cron trigger sets a replica count for a time window, and because the HPA takes the largest recommendation across triggers, it acts as a dynamic minimum: metric triggers can still scale above it [8]. A floor of 8 replicas from 8:30 on weekdays covers the morning ramp, at the cost of 4 extra replicas from 8:30 until the reactive fleet would have caught up: about 2.7 GPU-hours, or $8 a day at $3.00 per H100-hour, far cheaper than 8 minutes of broken latency for everyone who logs in at 9:00.

Predictive scaling generalizes the idea: forecast arrivals from history (for example, the same hour last week, adjusted by this week's trend) and set the floor one cold start ahead of the forecast. A forecast job can publish that floor as a metric for KEDA to read. Known events such as a product launch should simply be pre-scaled the day before. Sudden 10× spikes are beyond what any autoscaler can absorb in time; Lesson 26, Rate Limiting, and Lesson 27, the 10× spike lab, combine autoscaling with load shedding.

Which signal and policy fits our deployment?

We scale on in-flight requests per replica (running plus waiting) with KEDA, because it grows linearly with traffic, reacts immediately, and maps directly to the capacity of 53 at our latency targets. We set --max-num-seqs 53 so that overload shows up as waiting requests, and add a second trigger on KV cache usage at 0.7 for the occasional burst of long documents. The target is 40 per replica (75%), which the headroom formula allows only if new replicas start in about 1.5 minutes. Today they take 3 to 8, so we pair this policy with Lesson 23's fixes: images and weights cached on the nodes and a couple of free GPUs kept in the cluster. Until those land, a target of 26 to 33 is the honest setting. On top, a minimum of 4 replicas, a weekday floor of 8 from 8:30, a 10-minute scale-down window that removes one replica at a time, and a preStop drain with a 300-second grace period. Latency SLO burn drives alerts, not scaling. Knative-style scale to zero stays reserved for internal models that can tolerate a cold start.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • LLM-specific autoscalers, such as those in the AIBrix stack, that scale on engine metrics and integrate with prefix-aware routing [16].
  • Live migration of running requests between replicas, as in Llumnix, which lets the scheduler rebalance load and empty a replica before removing it instead of waiting for streams to finish [17].
  • Faster scale-up by loading weights over the GPU network from running replicas and serving layer by layer before the new replica is fully loaded, as in BlitzScale [18].
  • Scaling on token throughput (prompt plus generated tokens per second) instead of requests, which matters when request sizes vary widely.
  • Scaling prefill and decode pools separately in disaggregated serving, since they saturate on different resources (Lesson 34, Disaggregated Prefill and Decode).
  • Filling the night's spare capacity with low-priority batch work instead of scaling all the way down (Lesson 39, Batch and Offline Inference).
  • Using spot or preemptible GPUs for burst capacity, and what happens to in-flight requests when the cloud reclaims them.
  • Fleets with many models, where autoscaling turns into bin packing GPUs across models and scale to zero for the long tail (Lesson 23, Cold Starts, and Lesson 37, Multi-LoRA and Multi-Tenant Serving).

Summary

Mind map summarizing the autoscaling lesson: misleading signals, better signals, Kubernetes options, headroom math, safe scale-down, and scheduled scaling.
  • CPU utilization, GPU utilization, and GPU memory do not track LLM load: the first barely moves, the second reads near 100% with one request, and the third is reserved at startup.
  • In-flight requests per replica (running plus waiting) grow linearly with traffic by Little's law and make the best primary signal; 1,000 requests per minute at 10.6 s each is about 177 in flight.
  • Set --max-num-seqs to the SLO capacity so waiting requests become an overload alarm; add KV cache usage as a trigger when long prompts are common; use latency burn for alerts.
  • KEDA's Prometheus and cron triggers fit most GPU fleets; the HPA with a Prometheus Adapter works too; Knative's concurrency scaling suits scale to zero for rarely used models.
  • Headroom must cover traffic growth during one cold start: for a 2× spike over 5 minutes, the safe target is 50% with an 8-minute start and about 77% with a 1.5-minute start, 7 versus 5 replicas.
  • Scale down slowly (10-minute window, one replica at a time) and drain streams with a preStop hook and a grace period longer than the longest generation.
  • Schedule a floor ahead of known ramps and pre-scale for launches; reactive scaling is always one cold start late.

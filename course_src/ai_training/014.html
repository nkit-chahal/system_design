Introduction

No single parallelization strategy can scale large language model pretraining across thousands of GPUs. In previous lessons, we examined the primary distributed primitives in isolation: Data Parallelism and FSDP replicate or shard parameters across data streams (see Lesson 10, Data Parallelism and All-Reduce, and Lesson 11, ZeRO and FSDP); Tensor Parallelism shards weight matrices inside individual transformer layers (see Lesson 12, Tensor, Sequence and Context Parallelism); and Pipeline Parallelism partitions layers vertically across sequential stages (see Lesson 13, Pipeline Parallelism). Each technique solves a specific bottleneck, but each also introduces a distinct failure mode when pushed beyond its natural boundary.

Tensor Parallelism requires two collective All-Reduce communications inside every transformer block, generating hundreds of high-frequency synchronizations per step. Pushing TP across high-latency inter-node networks stalls tensor cores. Pipeline Parallelism avoids high-frequency communication by transferring point-to-point activations only at stage boundaries, but it introduces an idle pipeline bubble that wastes compute unless the micro-batch count is large. Fully Sharded Data Parallelism (FSDP) scales compute linearly, but sharding parameters across thousands of nodes floods the cluster spine with all-gather communication traffic. Context Parallelism (CP) shards the sequence length via ring attention, but adds communication overhead unnecessary for short contexts [6].

To train frontier models efficiently, engineers combine these dimensions into a unified multi-dimensional device mesh: 3D Parallelism (composing TP, PP, and DP) and 4D Parallelism (adding CP for ultra-long context windows) [3], [7].

Hierarchical mapping of parallelism strategies to physical interconnect tiers. Tensor Parallelism is confined strictly to intra-node NVLink (900 GB/s, < 1 µs latency). Pipeline and Context Parallelism span inter-node leaf switches (400 Gb/s InfiniBand). Data Parallelism (FSDP) forms the outermost dimension across the cluster spine.

The central art of large-scale distributed systems design lies in mapping each mathematical dimension of parallelism to the physical interconnect tier that can support its communication pattern. When orchestrated correctly, a 4D mesh allows training models with hundreds of billions of parameters across tens of thousands of GPUs while maintaining a Model FLOPs Utilization (MFU) between 38% and 43% [7]. In this lesson, we examine how the four dimensions compose, derive the global batch arithmetic governing the cluster, analyze worked configurations for 8B, 70B, and 405B models, examine PyTorch's DeviceMesh API, and determine the optimal layout for our pretraining cluster.

Clarifying the Problem

In distributed training systems interviews, multi-dimensional parallelism questions focus on topology mapping, dimension sizing, memory budgets, and MFU trade-offs. Here is how a discussion between a candidate and an interviewer typically unfolds:

Candidate: What model scale and context length are we targeting for this training layout, and what cluster hardware do we have?
Interviewer: We have two primary targets. First, our baseline pretraining run: an 8-billion parameter model (Llama 3.1 8B, 32 layers, hidden dimension 4,096) on 256 NVIDIA H100 80 GB GPUs across 32 nodes, with sequence length 8,192 and global batch size 4 million tokens. Second, we want to know how our parallel layout strategy changes if we scale to a 70B model or a 405B flagship model.

Candidate: What interconnects connect the GPUs within each node and across nodes?
Interviewer: Within each 8-GPU node, GPUs connect via NVLink 4 delivering 900 GB/s per GPU in each direction with sub-microsecond latency. Across nodes, each node connects through 8 InfiniBand NDR NICs offering 400 Gb/s (50 GB/s) per GPU across a non-blocking fat-tree network.

Candidate: What is our primary optimization objective—minimizing memory footprint to allow larger batches, or maximizing throughput and MFU?
Interviewer: We need to achieve at least 40% Model FLOPs Utilization (MFU) on our 8B pretraining run. The layout must eliminate communication bottlenecks and avoid pipeline bubbles that waste expensive GPU-hours.

Candidate: Should we use a 3D layout (TP + PP + DP) for the 8B model?
Interviewer: You tell me. Does an 8B model on 256 GPUs benefit from Tensor or Pipeline Parallelism, or does adding dimensions degrade efficiency?

The fundamental question underneath is: How do we compose TP, PP, CP, and DP into a coherent device mesh that respects physical bandwidth limits, satisfies global batch constraints, and maximizes hardware compute utilization? To answer it, we begin by mapping the four dimensions to cluster topology.

The Four Dimensions and Hardware Topology

The Golden Rules of Distributed Parallelism

Every distributed training run maps four mathematical dimensions of parallelism to a physical cluster of N_{\text{gpus}} devices. The total GPU count is the product of the individual degrees:

N_{\text{gpus}} = \text{TP} \times \text{CP} \times \text{PP} \times \text{DP}

Each dimension imposes distinct communication volumes, synchronization frequencies, and latency sensitivities. Successful cluster design adheres to four foundational engineering rules:

  1. Tensor Parallelism (TP) must stay inside a single node (\text{TP} \le 8): Because TP splits matrix multiplications within attention and MLP blocks, it requires two All-Reduce collectives in every single transformer layer. Over a 32-layer model, that represents 64 barrier synchronizations per micro-batch. Only intra-node NVLink (900 GB/s per GPU, sub-microsecond latency) can execute these collectives without stalling GPU tensor cores. Crossing nodes with TP degrades MFU precipitously [1], [3].
  2. Pipeline Parallelism (PP) crosses nodes across layer depth (\text{PP} \ge 1): When a model exceeds the memory capacity of a single 8-GPU node (such as 70B or 405B models), layers must be partitioned across nodes. Pipeline parallelism transmits point-to-point activations only at stage boundaries (e.g., 3 boundaries for p = 4), generating minimal network traffic (67–134 MB per micro-batch) that transfers in 1.3–2.7 ms over 400 Gb/s InfiniBand. This transfer time easily hides behind the 30–50 ms forward compute of an entire stage [2].
  3. Context Parallelism (CP) scales sequence length beyond memory limits (\text{CP} \ge 1): Standard self-attention memory scales quadratically with sequence length (\mathcal{O}(s^2)). When context length expands from 8,192 to 65,536 or 131,072 tokens, key and value tensors exceed GPU memory even with FlashAttention (see Inference Lesson 33, GPU Architecture and Attention Kernels). Context Parallelism shards tokens along the sequence dimension using Ring Attention, passing key-value chunks in a circular peer-to-peer ring that overlaps with local attention compute [6].
  4. Data Parallelism / FSDP forms the outermost dimension across the cluster: Once model states and activations fit within the combined memory of a (\text{TP} \times \text{PP} \times \text{CP}) model replica, the remaining cluster scale is dedicated to Data Parallelism. Data-parallel replicas process distinct batches concurrently. FSDP all-gathers model weights on demand during the forward pass and reduce-scatters gradients during the backward pass. Because all-gathers can be prefetched asynchronously via CUDA streams, DP communication tolerates multi-hop cluster network latency better than any other dimension [4], [5].

The PyTorch DeviceMesh abstraction

Historically, configuring multi-dimensional parallelism required manually allocating nested NCCL process groups using torch.distributed.new_group(), tracking multi-dimensional rank strides by hand, and managing communication barriers. PyTorch 2.x standardizes multi-dimensional communication through the DeviceMesh abstraction (torch.distributed.device_mesh) [8].

A 16-GPU cluster organized into a 3D DeviceMesh of shape (dp=2, pp=2, tp=4). Each GPU receives a unique coordinate tuple (dp, pp, tp). Slicing along named dimensions automatically creates orthogonal process groups: rows form TP communicators, columns form PP communicators, and depth slices form DP communicators.

A DeviceMesh organizes the flat list of cluster ranks into an n-dimensional Cartesian coordinate tensor with named dimensions. For example, a 3D mesh of 16 GPUs with 2 data-parallel replicas, 2 pipeline stages, and 4-way tensor parallelism is initialized with:

\text{mesh\_shape} = (2, 2, 4), \quad \text{mesh\_dim\_names} = (\text{"dp"}, \text{"pp"}, \text{"tp"})

Each GPU rank is assigned an (i, j, k) coordinate. PyTorch automatically instantiates orthogonal communication submeshes along each axis:

  • mesh["tp"]: Isolates GPUs sharing the same (\text{dp}, \text{pp}) coordinates (e.g., ranks [0, 1, 2, 3]), binding them to an intra-node NCCL communicator for high-speed tensor parallel All-Reduce operations.
  • mesh["pp"]: Isolates GPUs sharing the same (\text{dp}, \text{tp}) coordinates across pipeline stages (e.g., ranks 0 and 4), managing peer-to-peer point-to-point activation transfers.
  • mesh["dp"]: Isolates corresponding GPUs across data-parallel replicas (e.g., ranks 0 and 8), handling FSDP all-gather and gradient reduce-scatter operations.

By decoupling parallel layout from model definition, modern frameworks such as torchtitan allow engineers to alter parallel topologies simply by changing configuration parameters without rewriting layer forward functions [9].

Global Batch Arithmetic and Scaling Constraints

The four-factor batch size equation

In distributed training, the global batch size in tokens (B_{\text{tokens}}) represents the total volume of data consumed across all devices to perform a single parameter update. It is governed by four multiplicative factors:

B_{\text{tokens}} = \text{DP} \times m \times b \times s

Where:

  • \text{DP} is the number of independent data-parallel model replicas (\text{DP} = N_{\text{gpus}} / (\text{TP} \times \text{PP} \times \text{CP})).
  • m is the number of gradient accumulation steps (or micro-batches per pipeline step).
  • b is the micro-batch size in sequences processed locally by a GPU during one forward/backward cycle.
  • s is the sequence length in tokens (e.g., 8,192).
The four components of global batch size: DP replicas, accumulation steps m, micro-batch size b, and sequence length s. Increasing DP to scale the cluster forces accumulation steps m to shrink under a fixed global batch, causing the pipeline bubble fraction (p − 1)/(m + p − 1) to explode.

The DP-PP scaling tension: Why PP caps cluster growth

The global batch equation exposes a critical structural tension between Data Parallelism and Pipeline Parallelism. Machine learning theory establishes that for any model and dataset, there exists a critical batch size beyond which increasing batch size yields diminishing returns in sample efficiency, slowing convergence and wasting compute [7]. For 8B to 70B models, the critical batch size during early pretraining is typically between 2 million and 4 million tokens (256 to 512 sequences of 8,192 tokens).

Suppose our target global batch size is fixed at B_{\text{tokens}} = 4,194,304\text{ tokens} (512 sequences of s = 8,192), and we fix micro-batch size b = 1 to minimize activation memory. Rearranging the batch equation yields:

m = \frac{B_{\text{seq}}}{\text{DP} \times b} = \frac{512}{\text{DP}}

As the cluster expands and we increase the Data Parallel degree \text{DP}, the number of micro-batches m that each replica can process per step must decrease proportionally. However, as derived in Lesson 13, Pipeline Parallelism, the pipeline bubble fraction is:

\text{Bubble Fraction} \approx \frac{p - 1}{m + p - 1}

Consider what happens to a pipeline of depth p = 8 across different cluster sizes:

  • Small cluster (\text{DP} = 16, 128 GPUs total): m = \frac{512}{16} = 32 \implies \text{Bubble Fraction} = \frac{8 - 1}{32 + 8 - 1} = \frac{7}{39} \approx 17.9\% A 17.9% bubble is acceptable.
  • Large cluster (\text{DP} = 128, 1,024 GPUs total): m = \frac{512}{128} = 4 \implies \text{Bubble Fraction} = \frac{8 - 1}{4 + 8 - 1} = \frac{7}{11} \approx 63.6\% Over 63% of total cluster compute is lost to pipeline idle time!

This dynamic illustrates why pipeline parallelism must be configured with the minimal viable depth p. Every increase in pipeline depth p forces a higher micro-batch count m \ge 4p to avoid devastating bubble overhead, which in turn consumes precious batch capacity that could otherwise be used to scale Data Parallelism across more GPUs.

Worked Parallel Configurations: 8B, 70B, and 405B

To understand how engineering teams navigate these trade-offs in production, we analyze three concrete model scales on NVIDIA H100 clusters.

Configuration 1: Our pretraining run (Llama 3.1 8B on 256 H100s)

Our running scenario specifies pretraining a model with the Llama 3.1 8B architecture (8.03B parameters, 32 layers, hidden dimension 4,096) on 256 H100 GPUs across 32 nodes, with sequence length 8,192 and global batch size 4 million tokens.

  • Static memory accounting: 8.03 billion parameters in mixed-precision Adam require 16 bytes per parameter, totaling 128.5\text{ GB} (119.7 GiB). Across the 8 GPUs of an H100 node, FSDP shards this footprint to 128.5 / 8 \approx 16.06\text{ GB} per GPU. Visible memory on an 80 GB H100 is 79.6 GiB (85.5 GB), leaving approximately 64 GB free for activations and workspaces.
  • Optimal parallel layout: Hybrid Sharded Data Parallel (HSDP): \text{TP} = 1, \quad \text{PP} = 1, \quad \text{CP} = 1, \quad \text{FSDP}_{\text{intra}} = 8, \quad \text{DP}_{\text{inter}} = 32 Total GPUs: 1 \times 1 \times 1 \times 8 \times 32 = 256\text{ GPUs}.
  • Why HSDP wins:
    1. \text{TP} = 1: Eliminates all layer-level All-Reduce operations, avoiding tensor core stalls and preserving 100% of single-GPU kernel efficiency.
    2. \text{PP} = 1: Eliminates pipeline bubbles entirely (\text{Bubble Fraction} = 0\%). Every GPU computes 100% of the time.
    3. \text{CP} = 1: At sequence length 8,192, FlashAttention-3 fits activations comfortably in GPU memory without sequence sharding.
    4. \text{FSDP}_{\text{intra}} = 8: Shards parameters and optimizer states strictly across the 8 GPUs inside each node over 900 GB/s NVLink. All-gathers occur over ultra-fast NVLink rather than the inter-node network.
    5. \text{DP}_{\text{inter}} = 32: Across the 32 server nodes, gradients are synchronized using standard Data Parallel All-Reduce across InfiniBand. For a global batch of 512 sequences, each of the 32 DP replicas processes 512 / 32 = 16\text{ sequences} per step (m = 16, b = 1).

By choosing pure HSDP, our 8B pretraining run eliminates both TP communication overhead and PP bubble losses, directly achieving our target 40%+ MFU.

Configuration 2: Mid-scale pretraining (Llama 3.1 70B on 512 H100s)

Scaling to Llama 3.1 70B (70.6B parameters, 80 layers, hidden dimension 8,192) across 64 nodes (512 H100 GPUs) requires a fundamental shift. Static states in 16-byte Adam require 70.6\text{B} \times 16\text{ bytes} \approx 1,130\text{ GB}.

  • Why pure FSDP struggles: Sharding 1,130 GB across an 8-GPU node leaves 1,130 / 8 \approx 141\text{ GB} per GPU, which exceeds an 80 GB GPU by 76%. Sharding across all 512 GPUs via pure FSDP requires all-gathering 141 GB of weights across inter-node InfiniBand every step, consuming 15–20% of step time in unoverlapped network transfers.
  • Optimal parallel layout: 3D Parallelism (TP + PP + DP): \text{TP} = 8, \quad \text{PP} = 4, \quad \text{CP} = 1, \quad \text{DP} = 16 Total GPUs: 8 \times 4 \times 1 \times 16 = 512\text{ GPUs}.
  • Memory and batch accounting:
    • Each model replica spans 4 nodes (8 \times 4 = 32\text{ GPUs}). Static states per GPU drop to 1,130 / 32 \approx 35.3\text{ GB}, fitting comfortably within 80 GB HBM.
    • \text{TP} = 8 stays strictly inside each 8-GPU node over 900 GB/s NVLink.
    • \text{PP} = 4 partitions the 80 layers into 20 layers per node stage over InfiniBand. Point-to-point transfer volume is 1 \times 8,192 \times 8,192 \times 2 = 134.2\text{ MB}, transferring in 2.68 ms over 400 Gb/s InfiniBand and overlapping behind ~40 ms of stage compute.
    • With \text{DP} = 16 and global batch 512 sequences, each replica processes m = 512 / 16 = 32\text{ micro-batches}.
    • The pipeline bubble fraction is (4 - 1) / (32 + 4 - 1) = 3 / 35 \approx 8.6\%, maintaining high MFU.

Configuration 3: Flagship pretraining (Llama 3 405B on 16,384 H100s)

The pretraining of Meta's Llama 3 405B represents the frontier of multi-dimensional parallelism engineering. In The Llama 3 Herd of Models (arXiv:2407.21783), Meta published the exact 4D scaling configurations and MFU metrics used to train 405B across 16,384 H100 GPUs (2,048 nodes) [7].

Notice the architectural insights embedded in Meta's configuration:

  1. Rigid hierarchy: \text{TP} = 8 is held constant across all configurations, never exceeding the 8-GPU node boundary. \text{PP} = 16 partitions the 126 transformer layers across 16 server nodes (~8 layers per node), creating a unified 128-GPU model replica (8 \times 16 = 128\text{ GPUs}).
  2. Impact of DP scaling: Scaling from 8K GPUs to 16K GPUs on 8K context doubled \text{DP} from 64 to 128. Under a fixed global batch size of 16M tokens, the per-replica batch size was halved from 32 sequences to 16 sequences (m = 16). This reduced micro-batch accumulation, increasing the pipeline bubble fraction from 15 / (32 + 15) \approx 31.9\% to 15 / (16 + 15) \approx 48.4\% (mitigated by interleaved 1F1B scheduling), causing MFU to drop slightly from 43% to 41%.
  3. Transition to 128K context: To train on 131,072-token sequences, Meta engaged Context Parallelism at \text{CP} = 16, trading off Data Parallelism (\text{DP} reduced from 128 to 8). Ring attention communications across CP ranks reduced MFU by only 3 percentage points (from 41% to 38%), demonstrating the effectiveness of pipelining ring exchanges behind FlashAttention compute.

Parallelism Choices and Model FLOPs Utilization (MFU)

The efficiency waterfall

In Lesson 7, Training FLOPs, Time and MFU, we defined Model FLOPs Utilization as the ratio between actual floating-point operations executed per second and the theoretical peak throughput of the hardware:

\text{MFU} = \frac{\text{Actual Training FLOPS}}{N_{\text{gpus}} \times \text{Peak Hardware FLOPS}}

An NVIDIA H100 SXM GPU provides a theoretical peak of 989 TFLOPS in dense BF16 tensor operations. Why does a world-class 4D training cluster operate at 38% to 43% MFU rather than 100%? Figure 5 traces where theoretical throughput is consumed.

Tracing the loss of theoretical throughput from 100% peak (989 TFLOPS) down to 38%–43% MFU on 16K GPUs. Single-GPU kernel rooflines consume ~35%; TP All-Reduce collectives consume ~9%; PP bubbles consume ~10%; and FSDP/CP communications consume ~5%.

The loss of theoretical throughput divides into four primary stages:

  1. Single-GPU kernel rooflines (Loss: ~35%): Matrix multiplications (GEMMs) in attention and MLP layers achieve 70–80% of peak tensor core efficiency due to memory bandwidth limits and tile quantization. Furthermore, non-GEMM operations—RMSNorm, rotary position embeddings (RoPE), SwiGLU activations, and softmax—are memory-bandwidth-bound and achieve negligible FLOP rates. On a single GPU, the achievable upper bound is approximately 65% MFU.
  2. Tensor Parallelism collectives (Loss: ~8–10%): Two All-Reduce operations per layer force GPU tensor cores to synchronize across NVLink. Memory bandwidth contention between communication buffers and kernel execution reduces efficiency by 8–10%.
  3. Pipeline Parallelism bubbles (Loss: ~10–12%): Warmup and cooldown idle periods, along with stage execution imbalance (embedding and LM head overhead), introduce a bubble fraction of 8–15% even with 1F1B scheduling.
  4. FSDP all-gather and CP ring overhead (Loss: ~4–6%): While asynchronous CUDA streams prefetch weights and exchange key-value tokens concurrently with computation, communication jitter and brief synchronization barriers consume the final 4–6%.

When an infrastructure team optimizes a 4D layout, every percentage point of MFU gained delivers massive economic savings. On our 256-GPU H100 cluster running a 1-trillion token pretraining job, increasing MFU from 35% to 40% reduces total run time from 6.3 days to 5.5 days, saving approximately 4,900 GPU-hours (\approx \$14,700 at $3.00/hour).

What layout for our run?

For our running pretraining scenario—Llama 3.1 8B on 256 H100 GPUs (32 nodes × 8 GPUs, 400 Gb/s InfiniBand, sequence length 8,192, global batch 4 million tokens)—we select Hybrid Sharded Data Parallel (HSDP) with:

\text{TP} = 1, \quad \text{PP} = 1, \quad \text{CP} = 1, \quad \text{FSDP}_{\text{intra}} = 8, \quad \text{DP}_{\text{inter}} = 32

We reject Tensor Parallelism because the 8B model's layers fit comfortably in memory without intra-layer splitting, avoiding 64 All-Reduce synchronizations per step. We reject Pipeline Parallelism because the model fits in an 8-GPU node under FSDP, avoiding the 10–20% bubble loss that PP would introduce. We reject Context Parallelism because sequence length 8,192 fits in memory with FlashAttention-3 without sequence sharding. Sharding weights across the 8 GPUs of each node over NVLink reduces state footprint to 16 GB per GPU, while replicating across 32 nodes allows 16 accumulation steps (m = 16, b = 1) to hit our exact 4M token batch with zero bubble overhead and an expected MFU above 42%.

In Practice

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Hybrid Sharded Data Parallel (HSDP) vs full FSDP: Full FSDP shards parameters across all GPUs in a cluster, which causes heavy inter-node communication traffic. HSDP limits full sharding to GPUs within the same NVLink domain (node), replicating the sharded model across nodes using standard data-parallel All-Reduce. This strikes an optimal balance between memory reduction and inter-node network bandwidth [5].
  • Sequence Parallelism (SP) paired with TP: Standard TP shards matrix multiplications in attention and MLP, but leaves LayerNorm and Dropout duplicated. Megatron Sequence Parallelism splits the sequence dimension across the TP group during LayerNorm and Dropout, reducing activation memory by an additional 5\times with zero extra communication [3].
  • Ring Attention vs DeepSpeed Ulysses for Context Parallelism: Ulysses uses All-to-All collectives to gather sequences and shard attention heads across CP ranks, requiring H \ge \text{CP}. Ring Attention avoids head count constraints by passing KV blocks in a circular ring, enabling context scaling to millions of tokens [6].
  • Network rail alignment: In modern multi-node clusters with 8 NICs per node, NIC k on every node connects to the same InfiniBand leaf switch (rail). Aligning DP or PP process groups along physical network rails eliminates spine switch hops, doubling effective collective throughput [7].
  • Automated mesh search (Alpa / Galvatron): Manually tuning 4D parallelism configurations requires extensive trial and error. Compilers such as Alpa and Galvatron use integer linear programming and execution cost models to automatically discover the Pareto-optimal combination of TP, PP, DP, and CP for any given model and cluster architecture.
  • Checkpointing multi-dimensional meshes: Distributed checkpoints saved under a specific 3D layout (e.g., TP=8, PP=4) historically could not be resumed on a cluster with a different layout (e.g., TP=4, PP=8). Modern PyTorch Distributed Checkpoint (DCP) saves state dictionaries as sharded coordinate tensors, enabling seamless resharding across different mesh dimensions upon restart.

Summary

Mind map summarizing 3D and 4D parallelism: hardware hierarchy mapping, global batch arithmetic, Llama 3 405B case study, and layout decisions.
  • Multi-dimensional parallelism composes Tensor (TP), Pipeline (PP), Context (CP), and Data (FSDP/DP) parallelism into an n-dimensional device mesh: N_{\text{gpus}} = \text{TP} \times \text{PP} \times \text{CP} \times \text{DP}.
  • Golden rules of topology: Confine TP strictly to intra-node NVLink (\le 8 GPUs); use PP across nodes to shard depth; use CP for ultra-long contexts; wrap the outer cluster in FSDP / DP.
  • Global batch arithmetic governs the cluster: B_{\text{tokens}} = \text{DP} \times m \times b \times s. Scaling DP under a fixed global batch forces accumulation steps m to shrink, which inflates the pipeline bubble fraction (p - 1) / (m + p - 1).
  • Meta trained Llama 3 405B across 16,384 H100 GPUs using a 4D configuration: \text{TP} = 8, \text{PP} = 16 (128 GPUs per replica), \text{DP} = 128, and \text{CP} = 16 for 128K context, achieving 38% to 41% MFU.
  • PyTorch DeviceMesh standardizes multi-dimensional communication by organizing ranks into coordinate grids with orthogonal submeshes (mesh["tp"], mesh["pp"], mesh["dp"]).
  • For our 256-GPU H100 pretraining run on Llama 3.1 8B, pure HSDP (\text{TP}=1, \text{PP}=1, \text{CP}=1, \text{FSDP}=8, \text{DP}=32) is optimal, eliminating TP communication overhead and PP bubble losses.

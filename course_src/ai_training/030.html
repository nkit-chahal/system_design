Introduction

Training a large language model across hundreds or thousands of GPUs is fundamentally a distributed systems challenge. While raw compute throughput is determined by GPU tensor cores, the speed of the entire cluster is dictated by how fast GPUs can exchange weights, gradients, and activations. A cluster of 256 state-of-the-art GPUs can spend more than half its time idling if the underlying network cannot feed its collective communication loops.

Modern AI training infrastructure exhibits an extreme bandwidth hierarchy. Inside an 8-GPU server node, NVIDIA H100 SXM GPUs communicate over an NVLink 4 crossbar delivering 900 GB/s bidirectional bandwidth per GPU. Across nodes, communication leaves the server chassis to traverse an InfiniBand NDR or RoCEv2 network, where eight 400 Gb/s network interface cards (NICs) yield 50 GB/s per GPU [1]. Intra-node communication is 18 times faster than inter-node communication. If distributed training algorithms treat every GPU link equally, inter-node network bottlenecks will quickly collapse cluster compute utilization.

An architectural diagram contrasting communication inside an 8-GPU H100 node with communication across nodes. Inside the chassis, 8 GPUs connect to four NVSwitch chips providing 900 GB/s bidirectional NVLink bandwidth per GPU. Across nodes, 8 ConnectX-7 NICs connect via PCIe Gen 5 to an external Quantum-2 InfiniBand fabric providing 50 GB/s (400 Gb/s) per GPU, with GPUDirect RDMA bypassing host CPU memory.

To orchestrate data exchange at hardware limits, deep learning frameworks rely on the NVIDIA Collective Communications Library (NCCL). Understanding how NCCL maps collective operations—All-Reduce, All-Gather, Reduce-Scatter, and All-to-All—onto physical cluster topologies is essential for designing high-throughput training runs. In this lesson, we analyze the cluster networking hierarchy, derive NCCL bandwidth metrics from first principles, evaluate ring versus tree collective algorithms, calculate exact communication overheads for our running 256-GPU pretraining cluster, and determine the optimal parallelism layout to avoid network starvation.

Clarifying the Problem

In a systems design interview for an AI infrastructure or training platform role, cluster networking questions typically begin with a collective communication bottleneck or cluster sizing scenario. Here is how a discussion between a candidate and an interviewer typically unfolds:

Candidate: What model architecture, precision, and cluster scale are we sizing the network for?
Interviewer: We are pretraining a model with the Llama 3.1 8B architecture—8.03 billion parameters across 32 transformer layers. We use BF16 mixed-precision training across 256 NVIDIA H100 80 GB SXM GPUs housed in 32 nodes.

Candidate: What interconnects are deployed inside and between the server nodes?
Interviewer: Each node contains 8 H100 SXM GPUs interconnected via NVSwitch with 900 GB/s bidirectional NVLink. Each node is equipped with 8 ConnectX-7 NICs running 400 Gb/s InfiniBand NDR (50 GB/s raw bandwidth per NIC), configured in a non-blocking rail-optimized fat-tree network with GPUDirect RDMA enabled.

Candidate: What parallelism strategy are we using, and what is our target efficiency?
Interviewer: Our baseline proposal is Fully Sharded Data Parallelism (FSDP / ZeRO-3) across all 256 GPUs. Our target is at least 40% Model FLOPs Utilization (MFU), which corresponds to a step time of roughly 470 milliseconds. Can flat FSDP across all 256 GPUs hit that target, or will the network starve the run?

Candidate: Are we allowed to adapt the parallelism topology, for example by using Hybrid Sharding or Tensor Parallelism, if inter-node communication is the bottleneck?
Interviewer: Yes. Your task is to analyze whether the physical network can sustain flat FSDP, calculate the exact collective transfer times, and pick the layout that achieves our 40% MFU target.

The question underneath is: How do we match the communication patterns of distributed training to the physical bandwidth boundaries of our cluster, and how do we measure whether our network is operating at peak physical capacity? To answer it, we begin by examining the physical network fabric.

Cluster Interconnects: NVLink vs InfiniBand

Intra-node fabric: NVSwitch and NVLink

Within a modern 8-GPU server chassis (such as an NVIDIA HGX H100), GPUs do not communicate across the PCIe bus. Instead, each H100 SXM GPU exposes 18 fourth-generation NVLink connections [1]. Each connection provides 50 GB/s of bidirectional bandwidth (25 GB/s in each direction), totaling 900 GB/s bidirectional bandwidth per GPU (450 GB/s unidirectional). Four on-board NVSwitch 3 chips interconnect the 8 GPUs into a non-blocking, full-bisection crossbar. Any GPU can access the High Bandwidth Memory (HBM3) of any other GPU in the node with sub-microsecond latency.

This massive intra-node bandwidth enables fine-grained parallelism such as Tensor Parallelism (Lesson 12, Tensor, Sequence and Context Parallelism), which requires multiple All-Reduce collectives at every transformer layer. Attempting Tensor Parallelism across slower links immediately stalls compute engines.

Inter-node fabric: InfiniBand, RoCEv2, and GPUDirect RDMA

When communication spans multiple nodes, data must pass through Network Interface Cards (NICs) connected to the host PCIe complex. In modern AI clusters, each server node contains eight NICs—one dedicated NIC per GPU. In our cluster, these are ConnectX-7 400 Gb/s (NDR) InfiniBand adapters.

A single 400 Gb/s NIC provides a theoretical maximum unidirectional bandwidth of 50 GB/s:

\text{Bandwidth per NIC} = \frac{400 \times 10^9\text{ bits/s}}{8\text{ bits/byte}} = 50 \times 10^9\text{ bytes/s} = 50\text{ GB/s}

With 8 NICs per node, the entire chassis provides 400 GB/s (3.2 Tb/s) of bi-directional network injection bandwidth. However, compared to NVLink's 450 GB/s unidirectional bandwidth per GPU, the network link provides only 50 GB/s—an 9× bandwidth gap in each direction (and an 18× gap when comparing 900 GB/s bidirectional NVLink to single-direction 50 GB/s NIC injection).

To maximize efficiency, distributed training requires GPUDirect RDMA (Remote Direct Memory Access) [2]. Without GPUDirect RDMA, an inter-node transfer requires copying data through host CPU memory via PCIe and passing through the host OS network stack. GPUDirect RDMA bypasses host CPUs and system memory completely: the ConnectX-7 NIC reads directly from source GPU HBM across the PCIe switch and writes directly into target GPU HBM across the network, cutting latency from over 30 microseconds to roughly 2 to 5 microseconds.

Rail-optimized fat-tree topology

Connecting 256 GPUs across 32 nodes requires a multi-tier network fabric. In a standard non-blocking two-tier fat-tree network, leaf switches connect to server NICs, and spine switches interconnect the leaf switches. However, because each server houses 8 independent NICs, naive cabling can lead to severe switch port contention and non-uniform latency.

Modern AI supercomputers deploy a rail-optimized fat-tree topology [3, 4]. In an 8-GPU node, GPU k (where k \in [0, 7]) is paired via its local PCIe switch directly with NIC k. In a rail-optimized network, all NIC 0s across all 32 nodes connect to a dedicated set of leaf switches designated as Rail 0. All NIC 1s connect to Rail 1 leaf switches, through to NIC 7 connecting to Rail 7. Figure 2 illustrates this architecture.

Rail-optimized cabling across 32 nodes. GPU k on each node pairs with NIC k. NIC k from every node connects to an independent leaf switch fabric (Rail k). In distributed data parallelism, communication between homologous ranks stays entirely within a single rail leaf switch, avoiding spine crossings and eliminating inter-rail network congestion.

Rail optimization is designed specifically for deep learning communication patterns. When training with pure Data Parallelism or Megatron-style parallel groups, rank k on Node A primarily exchanges gradients with rank k on Node B. Because both ranks communicate through their local NIC k, all traffic remains strictly contained inside the Rail k leaf switch domain. The traffic never traverses the spine switch layer. Spine switches are utilized only when cross-rail traffic is needed, such as in all-to-all shuffles across differing rank offsets.

NCCL Collectives and Parallelism Mappings

The primitives

NCCL provides five fundamental collective communication primitives that form the backbone of all distributed training frameworks [2]:

  • All-Reduce: Takes an input tensor of size S on each of N ranks, applies an associative reduction operator (typically summation), and delivers the identical reduced result tensor of size S to all N ranks.
  • All-Gather: Takes a chunk of size S/N (or size S) from each rank and concatenates them in rank order, so that all N ranks receive the full tensor of size S (or N \times S).
  • Reduce-Scatter: Takes an input tensor of size S on each rank, performs an element-wise reduction across all ranks, and splits the reduced result into N equal chunks, delivering chunk i of size S/N to rank i.
  • All-to-All: An N \times N personalized transpose. Each rank starts with N distinct buffers of size S/N and sends buffer j to rank j. Each rank receives buffer i from rank j.
  • Broadcast: Copies a tensor of size S from a single designated root rank to all other N - 1 ranks.

Ring vs tree collective algorithms

NCCL implements collectives using two primary algorithmic topologies: Ring and Tree [2, 5].

In a Ring All-Reduce, the N participating ranks form a logical circular ring. The input buffer of size S is partitioned into N equal chunks of size S/N. The algorithm proceeds in two sequential phases of N - 1 steps each, as shown in Figure 4:

  1. Scatter-Reduce phase (N - 1 steps): In step k, each rank sends one chunk to its right neighbor and receives a chunk from its left neighbor, summing the received chunk into its local buffer. After N - 1 steps, each rank holds the complete, fully reduced sum for one chunk of size S/N. This phase is functionally identical to a Reduce-Scatter.
  2. All-Gather phase (N - 1 steps): Each rank sends its fully reduced chunk around the ring. After N - 1 steps, all ranks hold all N reduced chunks.
Execution flow of a ring All-Reduce across four ranks. In the first three steps (Scatter-Reduce), chunks rotate and accumulate until each rank holds a reduced 1/4th slice. In the final three steps (All-Gather), the reduced slices circulate until every rank has the entire reduced tensor. Total data sent per rank is 2(N-1)/N times S.

In each step, each GPU sends exactly S/N bytes. Across all 2(N - 1) steps, the total volume of data transmitted by each GPU is:

\text{Data Transmitted per GPU} = 2(N - 1) \times \frac{S}{N} = \frac{2(N - 1)}{N} S

Notice the critical property of the ring algorithm: as the number of GPUs N grows large, the communication volume per GPU approaches 2S, independent of N [3]. However, the latency of a ring scales linearly with 2(N - 1) communication hops. For small tensors, ring latency dominates.

To eliminate linear latency scaling for small buffers, NCCL uses a Double Binary Tree algorithm [2]. In a tree collective, data is aggregated up a binomial or binary tree to a root and broadcast back down. Tree collectives reduce the step latency to \mathcal{O}(\log N) hops, making them significantly faster for small buffers (under 1 to 4 MB). However, tree algorithms cannot fully saturate all bi-directional physical links simultaneously. NCCL automatically chooses between Ring and Tree implementations at runtime based on the buffer size, rank count, and detected interconnect topology.

Measuring Network Performance: nccl-tests and Bandwidth Formulas

Algorithm bandwidth vs bus bandwidth

When benchmarking distributed networks using the official nccl-tests suite (such as all_reduce_perf or all_gather_perf) [4], output tables report two distinct bandwidth figures: Algorithm Bandwidth (algbw) and Bus Bandwidth (busbw). Understanding the mathematical relationship between them is essential to avoid misinterpreting cluster health.

Algorithm Bandwidth is the raw user-perceived data throughput. It measures how fast the input payload S is processed relative to the wall-clock time t:

\text{algbw} = \frac{S}{t}

Because collective algorithms divide data into chunks and circulate them over multiple hops, \text{algbw} changes with rank count N. It does not reflect whether the physical network links are saturated.

Bus Bandwidth normalizes the algorithm bandwidth by the theoretical minimum traffic factor of the collective algorithm, representing the effective throughput sustained across each GPU's physical network bus [4]:

\text{busbw} = \text{algbw} \times \text{Factor}

The scaling factor depends on the collective operation and the number of participating ranks N:

  • All-Reduce: In a ring All-Reduce, each rank transmits 2(N - 1)/N \times S bytes. Therefore: \text{busbw}_{\text{All-Reduce}} = \text{algbw} \times \frac{2(N - 1)}{N} For an 8-GPU node (N = 8), the factor is 2(7)/8 = 1.75. For our 256-GPU cluster (N = 256), the factor is 2(255)/256 \approx 1.992.
  • All-Gather and Reduce-Scatter: Each rank transmits (N - 1)/N \times S bytes. Therefore: \text{busbw}_{\text{All-Gather}} = \text{algbw} \times \frac{N - 1}{N} For N = 8, the factor is 7/8 = 0.875. For N = 256, the factor is 255/256 \approx 0.996.
  • All-to-All: Each rank transfers personalized slices to N - 1 peers: \text{busbw}_{\text{All-to-All}} = \text{algbw} \times \frac{N - 1}{N}
  • Broadcast: The root transmits S bytes: \text{Factor} = 1.0.

Below 1 MB, bus bandwidth is negligible (under 20 GB/s) because the fixed latency of kernel launches, CUDA stream synchronization, and network handshakes (~10–15 µs) dominates the transfer. As message size exceeds 32 MB, the pipeline fills and bus bandwidth approaches physical link limits. On an 8-GPU H100 SXM node, healthy NVLink bus bandwidth reaches 380 to 400 GB/s (roughly 85–89% of theoretical 450 GB/s unidir bandwidth). Across 32 nodes on 400 Gb/s InfiniBand NDR, healthy inter-node bus bandwidth reaches 42 to 45 GB/s per GPU (roughly 84–90% of the 50 GB/s line rate).

Always cite bus bandwidth when evaluating whether your network is healthy. If someone tells you their 8-GPU all-reduce achieved 217 GB/s algbw, multiply by 1.75 to get 380 GB/s busbw—this proves their NVLink links are running at 85% of peak line rate.

Latency and Sizing for the Pretraining Run

Worked calculations: FSDP layer collectives on NVLink vs InfiniBand

Now let us evaluate the interviewer's question: Can flat FSDP across all 256 GPUs sustain our 40% MFU target?

In Llama 3.1 8B, each transformer layer contains attention weights (W_q, W_k, W_v, W_o), MLP weights (gate, up, down projections in SwiGLU), and RMSNorm parameters:

  • Attention parameters: 4096 \times (4096 + 1024 + 1024 + 4096) = 4,096 \times 10,240 = 41,943,040\text{ parameters}.
  • MLP parameters: 3 \times 4096 \times 14,336 = 176,160,768\text{ parameters}.
  • RMSNorm parameters: 2 \times 4,096 = 8,192\text{ parameters}.
  • Total per layer: 41,943,040 + 176,160,768 + 8,192 = 218,112,000\text{ parameters} \approx 218.1\text{M parameters}.
  • BF16 layer payload: 218,112,000 \times 2\text{ bytes} = 436,224,000\text{ bytes} \approx 436.2\text{ MB}.

In standard FSDP (ZeRO-3), every layer requires three collective transfers during each training step:

  1. Forward pass: All-Gather the 436.2 MB layer weights before forward computation.
  2. Backward pass: All-Gather the 436.2 MB layer weights before backward computation.
  3. Backward pass: Reduce-Scatter the 436.2 MB gradients after computing weight gradients.

Now let us calculate the transfer time for a single 436.2 MB All-Gather in two scenarios: intra-node NVLink versus cross-node InfiniBand NDR.

Scenario 1: Intra-node 8-GPU NVLink domain

Inside an 8-GPU node, healthy achieved bus bandwidth is \text{busbw} \approx 380\text{ GB/s}. For an All-Gather across 8 GPUs, the bus factor is (8 - 1)/8 = 0.875:

\text{algbw} = \frac{\text{busbw}}{\text{Factor}} = \frac{380\text{ GB/s}}{0.875} \approx 434.3\text{ GB/s}

Dividing the 436.2 MB layer payload by algorithm bandwidth yields the transfer time:

t_{\text{All-Gather, NVLink}} = \frac{436.224 \times 10^6\text{ bytes}}{434.3 \times 10^9\text{ bytes/s}} \approx 1.00\text{ ms}

At 40% MFU on an H100 SXM, the forward compute of one transformer layer for our pretraining batch takes approximately 7.5 milliseconds. Because the 1.00 ms All-Gather is prefetched in the background while the previous layer executes, 1.00 ms of communication is completely hidden behind 7.5 ms of compute (Figure 6, Case A). Communication stall time is zero.

Scenario 2: Flat 256-GPU InfiniBand NDR domain

Now consider executing the same layer All-Gather across all 256 GPUs over 400 Gb/s InfiniBand NDR. Achieved bus bandwidth is \text{busbw} \approx 43\text{ GB/s}. For N = 256, the bus factor is 255/256 \approx 0.996:

\text{algbw} = \frac{43\text{ GB/s}}{0.996} \approx 43.17\text{ GB/s}

Calculating the All-Gather transfer time:

t_{\text{All-Gather, InfiniBand}} = \frac{436.224 \times 10^6\text{ bytes}}{43.17 \times 10^9\text{ bytes/s}} \approx 10.11\text{ ms}

Here, the communication time of 10.11 ms exceeds the 7.5 ms forward compute time by 2.6 ms. The GPU finishes its compute and stalls, waiting for weights to arrive over the network. In the backward pass, each layer requires both an All-Gather (10.11 ms) and a Reduce-Scatter (10.11 ms), totaling 20.22 ms of communication against only ~15 ms of backward compute.

Across all 32 layers, communication adds 32 \times 30.33\text{ ms} \approx 970\text{ ms} of transfer time per step. Flat FSDP across 256 GPUs turns a compute-bound run into a severely network-bound run, collapsing MFU from 40% to below 22%.

Timeline comparison of a single layer's 436 MB All-Gather against forward compute time. On NVLink (1.00 ms), communication is completely hidden behind 7.5 ms of compute. On InfiniBand NDR (10.11 ms), communication exceeds compute by 2.6 ms, causing severe GPU idle stalls and destroying MFU.

Network congestion, adaptive routing, and stragglers

In distributed training, all 256 GPUs operate in lockstep. Before an optimizer step can occur, all ranks must complete their collective reductions. This synchronous barrier behavior gives rise to the straggler problem [4, 7]:

If 255 GPUs complete their backward pass in 400 milliseconds, but a single GPU experiences network packet drops or thermal throttling and requires 520 milliseconds, all 255 healthy GPUs sit 100% idle at the collective barrier for 120 milliseconds (Figure 7). A single slow link wastes 255 \times 0.120\text{ s} = 30.6\text{ GPU-seconds} every single step.

Illustration of 255 healthy GPUs stalling at the collective barrier while waiting for one straggler GPU delayed by network packet drops. The collective barrier forces the entire cluster to match the speed of the slowest link.

Common causes of network stragglers in large GPU clusters include:

  • Routing hash collisions: In standard Equal-Cost Multi-Path (ECMP) routing, traffic flows are hashed onto paths based on packet headers. When multiple high-bandwidth collective rings hash onto the same physical spine link, that link saturates while parallel links sit idle. AI clusters resolve this using Adaptive Routing (AR) on InfiniBand switches or RoCEv2 switches, dynamically steering packets away from congested links on a per-packet basis [3, 4].
  • Priority Flow Control (PFC) storms: RoCEv2 networks rely on PFC to provide lossless Ethernet. If a receiver buffer fills, it emits PFC PAUSE frames upstream. In misconfigured topologies, pause frames can cascade backward through the entire fabric, causing a PFC deadlock that halts all traffic.
  • Degraded PCIe or optical links: A faulty optical transceiver may experience high Bit Error Rates (BER), triggering silent packet retransmissions at the link layer. While the link does not drop, its effective bandwidth plummets from 50 GB/s to 5 GB/s, turning that node into a cluster-wide straggler.

Debugging NCCL: environment variables

NCCL's internal state can be inspected and debugged using environment variables. When troubleshooting cluster hangs or degraded throughput, engineers configure these variables to isolate faults [2]:

  • NCCL_DEBUG=INFO: Enables verbose logging from NCCL. When ranks initialize, NCCL prints the detected hardware topology, rank-to-GPU mappings, and the selected collective algorithms (Ring vs Tree).
  • NCCL_DEBUG_SUBSYS=INIT,COLL,ENV,NET: Restricts logging to specific subsystems. NET logs InfiniBand device detection and connection state; COLL logs every collective call and buffer size.
  • NCCL_IB_DISABLE=0: Ensures InfiniBand is enabled. Setting NCCL_IB_DISABLE=1 forces NCCL to fall back to Linux TCP sockets, useful for verifying whether an issue is specific to the RDMA driver.
  • NCCL_NET_GDR_LEVEL=5: Configures the GPUDirect RDMA path level. Level 5 (or SYS/NVL) instructs NCCL to use direct NVLink-to-NIC routing without host memory staging.
  • NCCL_CROSS_NIC=1: Allows GPUs to communicate through NICs associated with other GPUs in the node if the local NIC is congested or down.
  • NCCL_BUFFSIZE=4194304: Sets the internal ring buffer size (default is 4 MB). Increasing to 8 MB can improve throughput for large message sizes on high-latency networks, but increases GPU memory overhead.
  • NCCL_TOPO_DUMP_FILE=topo.xml: Dumps the XML graph of detected GPUs, PCIe switches, NVLinks, and NICs. This XML can be inspected to confirm whether all 18 NVLinks per GPU are active.
Do not blindly copy NCCL tuning scripts from online blogs. Variables like NCCL_BUFFSIZE or NCCL_ALGO force NCCL to bypass its internal cost model. In 95% of cases, poor collective throughput is caused by bad physical cables, failed GPUDirect drivers, or ECMP hash collisions, not NCCL configuration parameters.

Is our network fast enough for our layout?

We can now answer the interviewer's question decisively. Flat FSDP across all 256 GPUs is not fast enough for our cluster. Because our inter-node InfiniBand bandwidth (50 GB/s per GPU) is 9× slower than NVLink, an All-Gather of a 436.2 MB layer takes 10.11 ms, exceeding the 7.5 ms forward compute time. Across 32 layers, communication stalls add over 970 ms per step, degrading MFU from 40% to ~22%.

The correct architecture is Hybrid Sharded Data Parallelism (HSDP) [5] (or 3D Parallelism with intra-node TP):

  • Intra-node domain (size 8): Run FSDP across the 8 GPUs within each node over the 900 GB/s NVLink crossbar. Slicing model and optimizer states across 8 GPUs reduces memory by 8×—from 128.5 GB down to 16.1 GB per GPU—fitting comfortably within each 80 GB H100 with ample headroom for activations. Intra-node All-Gather takes only 1.00 ms, completely hidden behind compute.
  • Inter-node domain (size 32): Replicate the 8-GPU sharded model across the 32 nodes using standard Data Parallelism (DDP). Across nodes, only a single gradient All-Reduce is required at the end of the backward pass. With gradient bucketing (bucket size 64 MB), this All-Reduce overlaps seamlessly with the backward pass over the rail-optimized InfiniBand network.

HSDP confines fine-grained weight all-gathers to the 900 GB/s NVLink fabric, while limiting inter-node InfiniBand traffic to coarse-grained gradient synchronization, easily sustaining our target 40% MFU.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • NVLink Network (NVLink-SHARP): Newer NVIDIA platforms (such as GB200 NVL72) extend NVLink switching beyond single server nodes across entire racks, performing in-network collective reductions directly inside NVSwitch hardware.
  • RoCEv2 vs InfiniBand in hyperscalers: While InfiniBand provides native credit-based flow control, large cloud providers (Meta, Microsoft Azure) frequently deploy RoCEv2 (RDMA over Converged Ethernet) to standardize on commodity Ethernet infrastructure, requiring careful tuning of DCQCN (Data Center Quantized Congestion Notification) and ECN markings.
  • Communication bucketing: PyTorch DDP groups small parameter gradients into 25 MB contiguous memory buffers (bucket_cap_mb) before issuing All-Reduce. Bucketing ensures communication stays in the bandwidth-saturated regime rather than paying per-parameter latency penalties.
  • CUDA stream concurrency: Modern training engines issue collective communication on dedicated non-default CUDA streams (the communication stream) while GEMM kernels execute on the default compute stream, using CUDA events to synchronize without CPU intervention.
  • Packet trimming and spray routing: Advanced data center fabrics use packet spraying (distributing individual packets of a single flow across multiple network links) to prevent hash collisions, utilizing out-of-order reassembly buffers on receiving NICs.
  • DCGM network metrics: Monitoring cluster network health requires scraping InfiniBand port counters such as port_xmit_wait (indicating switch buffer congestion) and symbol_error counters (indicating damaged optical fibers).

Summary

Mind map summarizing cluster networking and collectives: physical interconnects, core NCCL primitives, bandwidth equations, latency sizing, straggler impacts, and hybrid sharding decisions.
  • AI clusters feature a steep bandwidth disparity: 8-GPU H100 nodes provide 900 GB/s bidirectional NVLink per GPU, whereas inter-node 400 Gb/s InfiniBand provides 50 GB/s per GPU—an 18× difference.
  • Rail-optimized fat-tree networks map GPU k on every node to an independent Rail k leaf switch, allowing data parallel traffic to avoid crossing spine switches.
  • The five NCCL primitives are All-Reduce, All-Gather, Reduce-Scatter, All-to-All, and Broadcast. All-Reduce is equivalent to Reduce-Scatter followed by All-Gather, transferring 2(N - 1)/N \times S bytes per GPU.
  • Bus bandwidth normalizes algorithm bandwidth (\text{busbw} = \text{algbw} \times 2(N - 1)/N for All-Reduce) to reflect physical hardware saturation. Healthy H100 SXM nodes reach ~380 GB/s bus bandwidth on NVLink and ~43 GB/s on InfiniBand NDR.
  • For Llama 3.1 8B, a 436 MB layer All-Gather takes 1.00 ms on NVLink (easily hidden behind 7.5 ms compute) but 10.11 ms on InfiniBand (stalling compute and collapsing MFU).
  • Synchronous collective barriers turn tail network latency into cluster-wide idle time: a single degraded link stalls all 256 GPUs.
  • To sustain 40% MFU, use Hybrid Sharded Data Parallelism (HSDP): shard states across 8 GPUs via NVLink, and replicate across nodes via rail-optimized InfiniBand.

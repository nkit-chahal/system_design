Introduction

In standard data-parallel training, every GPU maintains a complete, independent replica of the neural network. As established in Lesson 10, Data Parallelism and All-Reduce, this redundancy creates an impenetrable memory barrier. For standard mixed-precision training with the AdamW optimizer, each parameter demands 16 bytes of static memory [1]. For an 8-billion-parameter model such as Llama 3.1 8B, this baseline footprint reaches 128.5 GB per device, immediately exceeding the physical capacity of an 80 GB NVIDIA H100 GPU before allocating a single activation tensor [1], [4].

To train modern language models without abandoning the operational simplicity of data parallelism, Rajbhandari et al. introduced the Zero Redundancy Optimizer (ZeRO) [1]. Rather than replicating identical parameters, gradients, and optimizer states across every worker, ZeRO partitions these memory states across data-parallel ranks while retaining the same mathematical update as data-parallel SGD. In PyTorch, this paradigm is natively implemented as Fully Sharded Data Parallel (FSDP) [4].

Static memory consumption per GPU for Llama 3.1 8B across sharding stages on an 8-GPU node. Baseline DDP requires 128.5 GB per GPU, exceeding an 80 GB H100. ZeRO Stage 1 shards optimizer states (44.2 GB). ZeRO Stage 2 shards gradients as well (30.1 GB). ZeRO-3 / FSDP shards parameters, gradients, and optimizer states, slashing static memory to 16.1 GB.

State sharding introduces a fundamental systems trade-off: eliminating memory redundancy requires GPUs to dynamically communicate model parameters on the fly during forward and backward passes. In ZeRO Stage 3 and FSDP, workers must execute an all-gather collective before each layer's forward pass, repeat the all-gather before each layer's backward pass, and execute a reduce-scatter collective on gradients. This adds approximately 50% more communication volume (1.5×) compared to baseline data parallelism [1]. Managing this communication through asynchronous prefetching, layer wrapping, and hybrid network sharding is what determines whether distributed training achieves peak compute efficiency.

In this lesson, we examine the three stages of ZeRO, derive the exact 1.5× communication factor, analyze stream prefetching, study PyTorch's modern composable FSDP2 architecture, explore Hybrid Sharded Data Parallelism (HSDP) across our 32-node cluster, and configure production training with PyTorch and DeepSpeed.

Clarifying the Problem

In infrastructure interviews, candidate discussions regarding state sharding typically start from memory sizing and cluster interconnect topology. Here is a typical exchange:

Candidate: What model architecture, parameter count, and precision are we targeting for this cluster run?
Interviewer: We are pretraining a model with the Llama 3.1 8B architecture—8.03 billion parameters across 32 transformer layers. We use BF16 mixed-precision training with AdamW.

Candidate: What hardware topology do we have available?
Interviewer: A cluster of 256 NVIDIA H100 80 GB SXM GPUs arranged across 32 nodes (8 GPUs per node). Within each node, the 8 GPUs communicate via NVLink at 900 GB/s per GPU. Across nodes, each node connects through 8 InfiniBand NDR NICs offering 400 Gb/s (50 GB/s) per GPU.

Candidate: What are the sequence length and global batch targets?
Interviewer: Sequence length is 8,192 tokens. Global batch size is 512 sequences (approximately 4 million tokens).

Candidate: Since plain DDP runs out of memory on 80 GB GPUs, should we deploy full ZeRO-3 / FSDP flat across all 256 GPUs?
Interviewer: That is the core architecture decision. If you run ZeRO-3 flat across 256 GPUs, what happens to your inter-node InfiniBand bandwidth, what is the communication volume compared to DDP, and would a hybrid topology perform better?

The question underneath is: How do we shard optimizer states and weights to eliminate out-of-memory errors while preventing the 1.5× communication penalty from saturating our 50 GB/s inter-node InfiniBand network?

The ZeRO Paradigm: Sharding States Step-by-Step

The 16-byte memory breakdown

As derived in Lesson 3, Training Memory, mixed-precision training with the AdamW optimizer maintains five distinct representations for each parameter p [1]:

  1. BF16 model weight (2 bytes): Evaluated during forward matrix multiplications and backward activation gradient calculations.
  2. BF16 gradient (2 bytes): Computed during backpropagation and accumulated across micro-batches.
  3. FP32 master weight (4 bytes): High-precision weight copy updated by the optimizer step to avoid numerical underflow.
  4. FP32 Adam momentum m (4 bytes): Exponentially decaying moving average of past gradients.
  5. FP32 Adam variance v (4 bytes): Exponentially decaying moving average of squared gradients.

Summing these gives 16 bytes per parameter. Notice that 12 of the 16 bytes (75%) belong entirely to the optimizer states. Model weights and active gradients account for only 4 bytes (25%). The ZeRO family eliminates this redundancy progressively in three stages, denoted P_{os}, P_{os+g}, and P_{os+g+p} [1].

ZeRO Stage 1 (P_{os}): Sharding Optimizer States

In ZeRO Stage 1, the 12 bytes per parameter of FP32 optimizer states (master weights, momentum, and variance) are partitioned equally across the N_d data-parallel workers. Each GPU holds only a 1/N_d slice of the optimizer states. However, all GPUs continue to store complete, replicated copies of the BF16 model parameters (2 bytes) and BF16 gradients (2 bytes) [1].

The static memory footprint per GPU under ZeRO-1 is:

\text{Memory}_{\text{ZeRO-1}} = 2\Psi + 2\Psi + \frac{12\Psi}{N_d} = 4\Psi + \frac{12\Psi}{N_d}\text{ bytes}

where \Psi represents model parameter count. For our 8.03B model (\Psi = 8.03 \times 10^9):

  • On N_d = 8 GPUs: 4(8.03\text{ GB}) + \frac{12(8.03\text{ GB})}{8} = 32.12\text{ GB} + 12.05\text{ GB} = 44.17\text{ GB} (41.13 GiB). This cuts static memory by 66% compared to plain DDP (128.5 GB), immediately fitting within an 80 GB GPU.
  • On N_d = 256 GPUs: 32.12\text{ GB} + \frac{96.36\text{ GB}}{256} = 32.12\text{ GB} + 0.38\text{ GB} = 32.50\text{ GB} (30.26 GiB). As N_d \to \infty, memory asymptotes to 4\Psi (32.12 GB).

Communication under ZeRO-1 matches standard DDP in volume, but the collective is split in two. During the backward pass, workers reduce-scatter the gradients, so each worker receives only the summed gradient slice for its own 1/N_d partition of the optimizer states (1\Psi bytes). Each worker then updates its slice of the master weights, casts the result to BF16, and the workers all-gather the updated parameters (1\Psi bytes). The total of 2\Psi equals a ring all-reduce, which is itself a reduce-scatter followed by an all-gather [1].

ZeRO Stage 2 (P_{os+g}): Sharding Gradients

In ZeRO Stage 2, both optimizer states and gradients are partitioned across the N_d workers. As backpropagation evaluates gradients for each layer, worker GPUs do not maintain a full gradient tensor. Instead, they execute a reduce-scatter collective: gradients are summed across ranks and each rank receives only its assigned 1/N_d gradient partition [1].

The static memory footprint per GPU under ZeRO-2 is:

\text{Memory}_{\text{ZeRO-2}} = 2\Psi + \frac{2\Psi}{N_d} + \frac{12\Psi}{N_d} = 2\Psi + \frac{14\Psi}{N_d}\text{ bytes}
  • On N_d = 8 GPUs: 16.06\text{ GB} + \frac{112.42\text{ GB}}{8} = 16.06\text{ GB} + 14.05\text{ GB} = 30.11\text{ GB} (28.04 GiB).
  • On N_d = 256 GPUs: 16.06\text{ GB} + \frac{112.42\text{ GB}}{256} = 16.06\text{ GB} + 0.44\text{ GB} = 16.50\text{ GB} (15.37 GiB). As N_d \to \infty, memory asymptotes to 2\Psi (16.06 GB, the size of weights alone).

Communication volume in ZeRO-2 is mathematically identical to baseline DDP: reduce-scattering gradients costs 1\Psi, and all-gathering updated weights costs 1\Psi, totaling 2\Psi [1].

ZeRO Stage 3 / FSDP (P_{os+g+p}): Sharding Model Parameters

In ZeRO Stage 3 (and PyTorch FSDP), all 16 bytes per parameter are partitioned across the N_d workers. No GPU maintains a persistent copy of any full tensor: model weights, gradients, master weights, and optimizer moments are all sharded [1], [4].

The static persistent memory footprint per GPU is:

\text{Memory}_{\text{ZeRO-3}} = \frac{2\Psi + 2\Psi + 4\Psi + 4\Psi + 4\Psi}{N_d} = \frac{16\Psi}{N_d}\text{ bytes} Comparison of static memory footprints for Llama 3.1 8B on 8 GPUs versus 256 GPUs across sharding stages. Baseline DDP crashes at 128.5 GB in both setups. ZeRO-1 holds 44.2 GB on 8 GPUs and 32.5 GB on 256 GPUs. ZeRO-2 holds 30.1 GB and 16.5 GB. ZeRO-3 reduces static memory to 16.1 GB on 8 GPUs and just 0.50 GB on 256 GPUs, scaling inversely with worker count.

Communication Dynamics: The 1.5× Factor and Stream Prefetching

The layer-by-layer lifecycle of ZeRO-3 / FSDP

Because model parameters are persistently sharded, a GPU does not hold the weights required to compute a transformer layer. Instead, parameters must be dynamically reconstructed right before computation and discarded immediately afterward [1], [4]:

Step-by-step communication lifecycle for one transformer layer. In forward pass, an all-gather fetches weights (1.0 Psi), forward activations are evaluated, and full weights are discarded. In backward pass, an all-gather re-fetches weights (1.0 Psi) to compute input gradients, followed by a reduce-scatter on gradients (1.0 Psi). Total communication is 3.0 Psi, exactly 1.5x baseline DDP.

1. Forward Pass

Before executing Layer L, all ranks participate in an all-gather collective to reconstruct the complete layer weight tensor from their local shards. The GPU executes the forward matrix multiplications. The instant computation completes, the reconstructed weights are freed from memory, retaining only the persistent local 1/N_d shard [1]. The total data transmitted across all layers during the forward pass is:

\text{Traffic}_{\text{fwd}} = \frac{N_d - 1}{N_d} \Psi \approx 1\Psi\text{ bytes}

2. Backward Pass

During backpropagation, computing input gradients \partial \mathcal{L} / \partial X = (\partial \mathcal{L} / \partial Y) W^\top requires the original layer weights W. Because the forward weights were discarded, the workers must execute a second all-gather to re-acquire W for Layer L [1]. The data transmitted is again:

\text{Traffic}_{\text{bwd, gather}} = \frac{N_d - 1}{N_d} \Psi \approx 1\Psi\text{ bytes}

Next, the GPU evaluates weight gradients \partial \mathcal{L} / \partial W. The workers execute a reduce-scatter collective across the cluster: gradients are summed across all ranks, and each rank receives only its assigned 1/N_d partition [1]. The data transmitted is:

\text{Traffic}_{\text{bwd, scatter}} = \frac{N_d - 1}{N_d} \Psi \approx 1\Psi\text{ bytes}

The exact 1.5× traffic ratio

Summing the three collective operations yields the total communication volume per step in ZeRO-3 / FSDP [1]:

\text{Traffic}_{\text{ZeRO-3}} = 1\Psi\text{ (fwd gather)} + 1\Psi\text{ (bwd gather)} + 1\Psi\text{ (bwd scatter)} = 3 \frac{N_d - 1}{N_d} \Psi \approx 3\Psi\text{ bytes}

Recall from Lesson 10, Data Parallelism and All-Reduce, that standard DDP executes a single gradient all-reduce during the backward pass, transferring 2 \frac{N_d - 1}{N_d} \Psi \approx 2\Psi bytes. Comparing the two:

\frac{\text{Traffic}_{\text{ZeRO-3}}}{\text{Traffic}_{\text{DDP}}} = \frac{3\Psi}{2\Psi} = 1.5\times

ZeRO-3 and FSDP incur exactly 50% more network communication volume than baseline data parallelism. For our Llama 3.1 8B model (\Psi = 16.06\text{ GB}), DDP transfers approximately 32.0 GB per GPU, while ZeRO-3 transfers 48.1 GB per GPU per training step.

Prefetching and stream overlap

If each all-gather operation blocked GPU execution, training throughput would collapse under collective latency. Modern FSDP implementations hide communication through asynchronous prefetching across separate CUDA streams [4]:

FSDP overlaps computation and communication using dual CUDA streams. While the Compute stream evaluates matrix multiplications for Layer L, the NCCL Communication stream concurrently issues an asynchronous all-gather to prefetch parameters for Layer L+1. As a result, computation proceeds without bubbles.
  • Forward Prefetch: While the GPU compute stream is evaluating matrix multiplications for Layer L, the NCCL communication stream concurrently issues a non-blocking all-gather for Layer L+1. When Layer L finishes, the weights for Layer L+1 are already present in memory.
  • Backward Prefetch: While computing backward gradients for Layer L, FSDP simultaneously issues an all-gather for Layer L-1 weights and launches a reduce-scatter for Layer L gradients.

So long as the compute time of a transformer layer exceeds its all-gather transfer time, communication is completely concealed behind matrix multiplications [4].

FSDP in PyTorch: FSDP2 and Composable Fully Shard

From FSDP1 to FSDP2: The DTensor transition

In PyTorch 1.x and early 2.x, FSDP1 operated as a monolithic module wrapper (FullyShardedDataParallel). Internally, FSDP1 flattened all parameters within a layer into a single 1D tensor buffer called a FlatParameter [4]. While effective, flat parameters caused severe friction: they obscured original tensor shapes, hindered module hook registration, created memory fragmentation, and proved fundamentally incompatible with graph capture in torch.compile.

FSDP1 flattened all layer parameters into a monolithic 1D FlatParameter buffer, creating friction with torch.compile and module hooks. Modern FSDP2 (fully_shard) retains original tensor structures and shards each parameter along dimension 0 using native DTensors, enabling seamless composition with PyTorch compilation and mixed-precision policies.

In modern PyTorch (2.4+), FSDP2 replaces the monolithic wrapper with a functional, composable API: torch.distributed.fsdp.fully_shard [5]. Instead of flattening buffers, FSDP2 builds directly on DTensor (Distributed Tensor). Each individual weight matrix (W_q, W_k, W_v, W_{\text{gate}}, W_{\text{up}}) retains its original shape and is sharded along dimension 0 across a logical DeviceMesh [5]. Calling fully_shard(module) modifies the module in-place, attaching pre-forward, post-forward, pre-backward, and post-backward hooks without restructuring the model hierarchy.

FSDP2 Policies and Wrapping

Production FSDP2 deployments configure three core primitives [5]:

  1. Layer Wrapping Policy: Calling fully_shard on the root model would shard the entire network as one giant block, requiring an all-gather of all 16 GB of weights at once. To achieve granular overlap and low peak memory, fully_shard must be applied bottom-up to each transformer block individually, followed by the root model [4], [5]. Peak working memory is capped at the size of a single reconstructed transformer layer (~470 MB for Llama 3.1 8B).
  2. Mixed Precision Policy: Configured via MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32). Parameters and forward activations execute in BF16 for maximum tensor core throughput, while gradient reduction occurs in FP32 to preserve numerical stability during collective summation [5].
  3. CPU Offload Policy: Configured via CPUOffloadPolicy(pin_memory=True). Non-active parameter shards are offloaded to host DRAM, utilizing pinned memory for asynchronous PCIe DMA transfers [5].

Hybrid Sharded Data Parallelism (HSDP)

The multi-node bandwidth mismatch

Now consider our 256-GPU cluster (32 nodes × 8 H100 GPUs). If we deploy flat ZeRO-3 / FSDP across all 256 GPUs, every single transformer layer must execute two all-gathers and one reduce-scatter across the inter-node InfiniBand fabric. Let us examine the bandwidth disparity:

  • Intra-node NVLink: 900 GB/s per GPU (bidirectional). An all-gather of 16 GB of weights within a node completes in approximately 35 ms.
  • Inter-node InfiniBand NDR: 400 Gb/s = 50 GB/s per GPU. Across 32 nodes, transmitting 48.1 GB per GPU (the 1.5× ZeRO-3 traffic) over a 50 GB/s link requires: T_{\text{IB, ZeRO-3}} = \frac{48.1\text{ GB}}{50\text{ GB/s}} \approx 0.962\text{ s} = 962\text{ ms}

NVLink is 18× faster than InfiniBand. Forcing 64 all-gather collective rounds (32 layers × 2 passes) across the inter-node network introduces severe packet serialization, latency sensitivity, and switch contention. If any layer's compute finishes faster than its inter-node all-gather, the GPUs stall.

HSDP: Sharding locally, replicating globally

To resolve this mismatch, modern training architectures employ Hybrid Sharded Data Parallelism (HSDP) [4]. Instead of treating all 256 GPUs as a flat group, HSDP constructs a 2D Device Mesh with two orthogonal dimensions:

HSDP organizes 256 GPUs into a 2D mesh: intra-node shard degree = 8 (over 900 GB/s NVLink) and inter-node replicate degree = 32 (over 400 Gb/s InfiniBand). High-frequency layer all-gathers occur strictly over NVLink, while InfiniBand synchronizes only sharded gradients once per step.
  1. Intra-node Sharding Dimension (dp_shard = 8): Within each 8-GPU node, parameters, gradients, and optimizer states are fully sharded via ZeRO-3 across the 8 GPUs over 900 GB/s NVLink. Static memory per GPU drops to 128.48\text{ GB} / 8 = 16.06\text{ GB}, fitting comfortably within the 80 GB H100 budget. All high-frequency layer-by-layer all-gathers stay strictly confined to intra-node NVLink [4].
  2. Inter-node Replication Dimension (dp_replicate = 32): Across the 32 nodes, the 8-GPU sharded unit is replicated. Inter-node InfiniBand connections execute only a single all-reduce on the local gradient shards (or an inter-node reduce-scatter) once per optimizer step [4].

Under HSDP, zero parameter all-gathers cross the inter-node network. The 1.5× communication penalty is paid exclusively over the 900 GB/s NVLink fabric, where it requires only ~35 ms. The slower 50 GB/s InfiniBand fabric handles only the standard gradient synchronization, preserving peak cluster throughput.

ZeRO-Offload and ZeRO-Infinity

When training extremely large models on clusters with limited GPU counts, even ZeRO-3 may exceed device memory. DeepSpeed introduces memory hierarchy offloading [2], [3]:

ZeRO-Offload shifts FP32 master weights and Adam optimizer states to host CPU DRAM, updating them via CPU Adam over PCIe 5.0. ZeRO-Infinity extends offload to NVMe SSDs with asynchronous prefetching, trading PCIe/NVMe bandwidth for near-infinite parameter capacity.
  • ZeRO-Offload: Offloads FP32 master weights, momentum, and variance states (12 bytes/param) to host CPU DRAM [2]. During backward propagation, gradients are transferred over PCIe 5.0 (64 GB/s) to the host. Host CPU cores evaluate a multi-threaded, AVX-512 optimized CPUAdam optimizer update. Updated weights are cast to BF16 and copied back to GPU HBM before the next step.
  • ZeRO-Infinity: Extends offloading beyond CPU memory to local high-speed NVMe SSDs [3]. By exploiting the high aggregate read bandwidth of multiple PCIe Gen5 NVMe drives and pipelining I/O transfers with computation, ZeRO-Infinity enables training trillion-parameter models on modest hardware clusters [3].

Offloading is valuable for single-node fine-tuning (see Lesson 22, Supervised Fine-Tuning). However, for high-throughput pretraining clusters, host-to-device PCIe bandwidth (64 GB/s) is vastly slower than HBM3 (3.35 TB/s), making offload an unnecessary bottleneck when sufficient GPUs are available [2].

DeepSpeed ZeRO configuration

In DeepSpeed, ZeRO stages and communication optimizations are configured via JSON dictionaries [6]. Key parameters include:

  • stage: 1, 2, or 3.
  • overlap_comm: Enables asynchronous prefetching and gradient communication overlap.
  • contiguous_gradients: Groups gradients into contiguous memory buffers to avoid allocator fragmentation.
  • reduce_bucket_size: Maximum buffer size for gradient reduce operations (e.g., 5 \times 10^8 elements).
  • stage3_prefetch_bucket_size: Buffer capacity for parameter prefetching in ZeRO-3.
  • stage3_param_persistence_threshold: Parameters smaller than this threshold (e.g., LayerNorm weights) remain persistently gathered in GPU memory to avoid collective launch overhead.

Which sharding fits our run?

For our 256-GPU cluster pretraining Llama 3.1 8B, Hybrid Sharded Data Parallelism (HSDP) is the optimal architecture. Sharding across 8 GPUs within each node (\text{shard} = 8) cuts static memory from 128.5 GB to 16.06 GB, providing over 63 GB of headroom for activations and FlashAttention buffers on each H100. Confining all parameter all-gathers to NVLink isolates the 1.5× communication volume to 900 GB/s links, while replicating across the 32 nodes (\text{replicate} = 32) over 400 Gb/s InfiniBand protects inter-node network efficiency. Flat ZeRO-3 across all 256 GPUs would generate unnecessary inter-node traffic, while ZeRO-1 or ZeRO-2 would consume too much static memory per device.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Activation Checkpointing Integration: Why FSDP must be applied outside activation checkpointing blocks, so that recomputed forward layers trigger proper all-gather parameter reconstructions [4].
  • Parameter Persistence Threshold: Small parameters (such as RMSNorm scale vectors and bias terms) generate tiny collective calls. Persisting them in HBM avoids collective launch overhead with negligible memory cost [1].
  • Distributed Checkpoint (DCP): How modern PyTorch saves sharded state dicts concurrently from each rank using torch.distributed.checkpoint, avoiding the massive memory bottleneck of gathering full model checkpoints to rank 0 [5].
  • ZeRO++ Optimizations: DeepSpeed ZeRO++ techniques, including quantization of all-gather parameters to FP8 (block-based weight quantization) to halve all-gather network traffic on slower fabrics [3].
  • Memory Fragmentation: How PyTorch's native caching allocator can suffer from memory fragmentation during frequent layer all-gather allocations, and how setting max_split_size_mb mitigates out-of-memory spikes.
  • Gradient Norm Computation: In ZeRO-3, computing the global gradient norm for gradient clipping requires an all-reduce across local gradient norms before applying parameter updates [1].

Summary

Mind map summarizing the ZeRO stages, memory scaling, communication trade-offs, PyTorch FSDP2 composability, and hybrid sharding.
  • Standard DDP replicates 16 bytes per parameter (128.5 GB for Llama 3.1 8B), exceeding 80 GB GPUs. ZeRO eliminates redundancy by partitioning states across data-parallel ranks.
  • ZeRO-1 shards optimizer states (44.2 GB on 8 GPUs). ZeRO-2 shards optimizer states and gradients (30.1 GB). ZeRO-3 / FSDP shards parameters, gradients, and optimizer states (16.1 GB on 8 GPUs, 0.50 GB on 256 GPUs).
  • ZeRO-3 requires all-gathering weights before forward pass, all-gathering weights again before backward pass, and reduce-scattering gradients. Total communication is 3\Psi, exactly 1.5× baseline DDP.
  • Asynchronous prefetching on dedicated CUDA communication streams hides all-gather collective latency behind the matrix multiplications of adjacent transformer layers.
  • PyTorch FSDP2 replaces monolithic FlatParameter buffers with composable fully_shard, sharding parameters along dimension 0 as native DTensors for seamless integration with torch.compile.
  • Hybrid Sharded Data Parallelism (HSDP) shards parameters across 8 GPUs intra-node over 900 GB/s NVLink and replicates across 32 nodes over 400 Gb/s InfiniBand, confining the 1.5× traffic to NVLink and maximizing cluster efficiency.

Introduction

Distributed deep learning began with a straightforward idea: when a dataset is too vast for a single machine to process in a reasonable time, distribute the data across multiple workers. In data parallelism (DP), every GPU in a cluster holds an identical copy of the model parameters. Each worker ingests a unique slice of the global training batch, computes a forward pass to determine the loss, and evaluates backpropagation to calculate local parameter gradients. Before any parameter can be updated, the workers execute a distributed collective operation called all-reduce to compute the arithmetic average of their gradients across all devices. Once synchronized, every GPU applies an identical optimizer update, guaranteeing that the model replicas remain bit-for-bit identical at the start of the next training step [1].

While conceptually elegant, scaling data parallelism to hundreds or thousands of GPUs reveals severe systems challenges. As cluster size grows, the volume of gradient data transmitted across network links threatens to overwhelm inter-node interconnects. Modern training systems overcome this communication barrier through bandwidth-optimal ring collectives, hierarchical network routing, and aggressive communication-computation overlap, where gradient synchronization for completed layers runs concurrently with backpropagation of earlier layers [1], [2].

A global batch of 512 sequences is partitioned into distinct micro-batches across worker GPUs. Each worker maintains a complete model replica and independently computes local forward and backward passes. A collective all-reduce averages gradients across all workers, enabling identical optimizer parameter updates.

However, pure data parallelism faces an unyielding physical constraint. Because every worker must maintain a complete copy of the model weights, gradients, and optimizer states, data parallelism does not reduce the per-GPU memory footprint by a single byte [5]. For modern large language models, the static memory required by standard mixed-precision optimizers exceeds the physical capacity of modern accelerators before allocating even one activation tensor. Understanding how data parallelism functions, where its network communication scales, and where its memory wall hits is the essential foundation for all advanced distributed training architectures.

In this lesson, we examine the mechanics of data parallelism, derive the exact communication volume of ring and tree all-reduce algorithms, analyze how PyTorch DDP overlaps gradient communication with backward computation, evaluate worked cluster timings for our 256-GPU cluster, examine the mathematical limits of batch size scaling, and discover why plain data parallelism must ultimately yield to state sharding.

The Mechanics of Data Parallelism and All-Reduce

Micro-batch partitioning and synchronization

Let N be the number of data-parallel workers (GPUs) and let B be the global batch size measured in sequences. In standard data parallelism, each GPU receives a disjoint micro-batch of size b = B / N sequences. Worker i evaluates the loss \mathcal{L}_i(W) over its local micro-batch using local model weights W. During the backward pass, automatic differentiation evaluates local parameter gradients:

g_i = \nabla_W \mathcal{L}_i(W)

Because the objective function across the global batch is the arithmetic mean of the local losses, the true global gradient \bar{g} is the average of the local gradient vectors across all N workers [1]:

\bar{g} = \frac{1}{N} \sum_{i=0}^{N-1} g_i

The collective operation that sums tensors across all ranks and delivers the resulting sum to every rank is all-reduce. Once all-reduce completes, each worker scales the sum by 1/N to produce \bar{g} and invokes its local optimizer (such as AdamW) to update W. Because all replicas begin with identical initial weights and apply identical averaged gradients, their updated weights remain synchronized without requiring parameter broadcasts.

The Ring All-Reduce algorithm

A naive implementation of all-reduce might designate a master node, gather all gradients to that node, sum them, and broadcast the result back. For N = 256 workers, the master node's network interface would saturate immediately, creating an intractable bottleneck. Modern distributed systems execute all-reduce using decentralized algorithms, most notably ring all-reduce [2].

In ring all-reduce, the N GPUs are logically arranged in a unidirectional ring: rank i transmits data only to rank (i+1) \bmod N and receives data only from rank (i-1) \bmod N. The gradient buffer of size S bytes is partitioned into N equal chunks of size S / N. The algorithm executes in two distinct phases of N - 1 steps each [2]:

A logical ring of four GPUs where a gradient tensor is split into four equal chunks. In Phase 1 (Reduce-Scatter), workers circulate and accumulate chunks over N - 1 steps until each worker holds one fully reduced chunk. In Phase 2 (All-Gather), workers circulate the reduced chunks over N - 1 steps until all workers possess the complete averaged gradient.

Phase 1: Reduce-Scatter (N - 1 steps)

At each step k \in [0, N-2], each worker i sends chunk (i - k) \bmod N to rank i+1 while simultaneously receiving chunk (i - k - 1) \bmod N from rank i-1. Upon receiving a chunk, the worker performs an element-wise vector sum with its local corresponding chunk. After N - 1 steps, each worker holds the fully accumulated sum for exactly one of the N chunks. The total volume of data sent by each GPU during this phase is:

\text{Data Sent}_{\text{reduce-scatter}} = (N - 1) \times \left(\frac{S}{N}\right) = \frac{N - 1}{N} S\text{ bytes}

Phase 2: All-Gather (N - 1 steps)

In the second phase, the fully reduced chunks are circulated around the ring so that every worker receives the complete gradient tensor. At each step, worker i sends its newly acquired fully reduced chunk to rank i+1 and receives another reduced chunk from rank i-1. After N - 1 steps, all N chunks have visited every GPU. The total data sent by each GPU during all-gather is identical to Phase 1:

\text{Data Sent}_{\text{all-gather}} = (N - 1) \times \left(\frac{S}{N}\right) = \frac{N - 1}{N} S\text{ bytes}

Total traffic and bandwidth optimality

Summing both phases yields the total network traffic transmitted (and received) by each GPU during ring all-reduce [2]:

\text{Total Data Sent per GPU} = 2 \times \frac{N - 1}{N} S\text{ bytes}

This formula demonstrates a profound mathematical property: as the number of GPUs N grows large, the fraction (N - 1) / N \to 1. Consequently:

\lim_{N \to \infty} \text{Total Data Sent per GPU} = 2S\text{ bytes}

The communication volume per GPU is asymptotically independent of the number of GPUs. Doubling the cluster size from 128 to 256 GPUs does not double the data transmitted per worker; each worker always transfers approximately 2S bytes. If the interconnect provides bidirectional bandwidth B, the transfer time is governed by:

T_{\text{ring}} = 2 \frac{N - 1}{N} \frac{S}{B} + 2(N - 1)\alpha

where \alpha represents the network latency per transfer step. For large models where S is measured in gigabytes, the bandwidth term 2S/B completely dominates the latency term 2N\alpha, achieving near 100% link utilization [2].

Collective Topologies in NCCL: Ring versus Tree

The NVIDIA Collective Communications Library (NCCL) implements the communication primitives underpinning PyTorch DDP. While the ring algorithm maximizes bandwidth utilization for large messages, its latency scales linearly with N (2(N-1)\alpha steps). On large clusters with hundreds or thousands of nodes, this linear hop count introduces measurable overhead for small tensors [6].

Comparison of communication topologies in NCCL. Ring all-reduce requires 2(N-1) transfer steps but achieves near 100% bus bandwidth utilization for large tensors. Double Binary Tree requires only 2 log2(N) steps, significantly reducing latency for small payloads. NCCL automatically chooses between Ring and Tree based on message size.

To eliminate this latency bottleneck, NCCL incorporates the Double Binary Tree algorithm [6]. GPUs are arranged into two complementary binary trees where internal nodes in one tree act as leaves in the other. In a tree topology, the reduction flows up to the root in \log_2 N steps, followed by a broadcast down the tree in \log_2 N steps, yielding a total latency of 2 \log_2 N \times \alpha [6]. However, because root and internal nodes must service multiple child edges, link utilization is lower than in a balanced ring.

NCCL selects the optimal algorithm dynamically at runtime using an internal analytical cost model (the auto algorithm mode). For small buffers (typically below 256 KiB to 4 MiB), NCCL deploys Tree all-reduce to minimize latency hops. For large gradient tensors, it routes traffic through Ring all-reduce (or NVLS hardware-accelerated multicast trees within Hopper NVSwitches) to saturate line-rate bandwidth [6].

Overlapping Communication with Computation

Why naive synchronization stalls training

A naive data-parallel implementation would compute the full forward pass, compute the full backward pass across all layers, and then initiate an all-reduce across all model parameters. Under this blocking model, GPU tensor cores sit completely idle throughout the all-reduce phase, waiting for network transfers to conclude. Conversely, the high-speed network interfaces sit completely idle throughout the forward and backward passes. This serialization wastes substantial hardware capacity [1].

PyTorch DDP: Autograd hooks and gradient bucketing

PyTorch DistributedDataParallel (DDP) avoids serialization by overlapping communication directly with the backward pass [1]. This overlap relies on a fundamental architectural reality: backpropagation traverses neural network layers in reverse topological order. Gradients for the final transformer layer (Layer 32) are fully evaluated milliseconds after the backward pass begins, while gradients for Layer 1 will not be computed until the backward pass reaches completion.

PyTorch DDP groups model parameters into buckets in reverse order. As backpropagation evaluates gradients from Layer 32 down to Layer 1, autograd hooks mark parameters ready. When Bucket 0 reaches capacity (bucket_cap_mb, default 25 MB), DDP launches an asynchronous all-reduce on a separate CUDA communication stream while the compute stream concurrently evaluates gradients for Bucket 1.

Instead of dispatching an all-reduce operation for each individual parameter—which would flood the CUDA stream and NCCL with thousands of tiny, high-overhead kernel launches—DDP aggregates parameter gradients into contiguous memory buffers called buckets [1]:

  1. Initialization: When DistributedDataParallel(model) is constructed, DDP inspects the model parameters and packs them into buckets in roughly reverse order of model.parameters(). The maximum size of each bucket is governed by the configuration parameter bucket_cap_mb (defaulting to 25 MiB) [1], [7].
  2. Hook Registration: DDP registers a post-accumulate gradient autograd hook (register_post_accumulate_grad_hook) on every parameter tensor [1].
  3. Bucket Readiness: As loss.backward() executes, whenever a parameter's gradient computation concludes, its autograd hook fires and marks that parameter ready within its assigned bucket.
  4. Asynchronous Launch: The instant the final parameter in a bucket is marked ready, DDP immediately dispatches an asynchronous non-blocking all-reduce (via torch.distributed.all_reduce) for that entire bucket on a dedicated CUDA communication stream [1].
  5. Concurrent Execution: While the network interface transfers and reduces Bucket 0 across the cluster, the GPU compute stream is actively evaluating gradients for Bucket 1. By the time the backward pass reaches the initial model layers, nearly all upper-layer gradient buckets have already completed their network transfers [1].

Gradient accumulation and synchronization control

When training large models, the micro-batch size that fits in memory may be smaller than the desired batch size per GPU. Engineers use gradient accumulation: running multiple local forward and backward passes, accumulating gradients into param.grad, and executing the optimizer update only once every K micro-steps.

Under standard DDP, every call to loss.backward() triggers gradient all-reduce across all buckets. Launching communication on intermediate accumulation steps is entirely redundant, as only the final accumulated gradient needs to be synchronized. PyTorch DDP provides the model.no_sync() context manager to disable gradient synchronization during intermediate micro-batches [1], [7]:

# Accumulate gradients over K micro-batches without network sync optimizer.zero_grad() for step in range(accumulation_steps): is_last_microbatch = (step == accumulation_steps - 1) # Disable all-reduce during intermediate micro-steps if not is_last_microbatch: with model.no_sync(): outputs = model(inputs[step]) loss = criterion(outputs, targets[step]) / accumulation_steps loss.backward() else: # Final micro-step: DDP hooks fire and all-reduce runs outputs = model(inputs[step]) loss = criterion(outputs, targets[step]) / accumulation_steps loss.backward() optimizer.step()

By wrapping the first K-1 backward passes in model.no_sync(), the cluster eliminates K-1 network communication rounds, preserving interconnect bandwidth exclusively for the final synchronization step [1].

Worked Cluster Numbers: Bandwidth, Latency, and Compute Overlap

Sizing gradient communication for Llama 3.1 8B

Let us apply these formulas to our pretraining scenario. The model has N_{\text{params}} = 8.03 \times 10^9 parameters. In BF16 mixed-precision training, each gradient element requires 2 bytes. The uncompressed gradient tensor size is:

S = 8.03 \times 10^9 \times 2\text{ bytes} = 16.06 \times 10^9\text{ bytes} \approx 16.06\text{ GB} \quad (14.96\text{ GiB})

We evaluate all-reduce communication performance across two physical network fabrics:

1. Intra-node NVLink (8 GPUs)

Inside a single 8-GPU H100 SXM node, GPUs connect through NVSwitches providing 900 GB/s bidirectional NVLink bandwidth per GPU (450 GB/s transmit and 450 GB/s receive). For N = 8 ranks:

\text{Traffic Factor} = 2 \times \frac{8 - 1}{8} = 2 \times \frac{7}{8} = 1.75 \text{Data Transferred per GPU} = 1.75 \times 16.06\text{ GB} = 28.105\text{ GB}

At 900 GB/s effective bus bandwidth, the time required to all-reduce the entire 8B gradient tensor across the node is:

T_{\text{NVLink}} = \frac{28.105\text{ GB}}{900\text{ GB/s}} \approx 0.0312\text{ s} = 31.2\text{ ms}

Even accounting for 80% practical bus efficiency (~720 GB/s), the all-reduce completes in under 39 ms.

2. Inter-node InfiniBand (256 GPUs across 32 nodes)

Across the full 256-GPU cluster, each node contains 8 InfiniBand NDR NICs operating at 400 Gb/s, providing 50\text{ GB/s} dedicated bidirectional line rate per GPU. For N = 256 ranks:

\text{Traffic Factor} = 2 \times \frac{256 - 1}{256} = 2 \times \frac{255}{256} \approx 1.9922 \text{Data Transferred per GPU} = 1.9922 \times 16.06\text{ GB} = 31.995\text{ GB} \approx 32.00\text{ GB}

At 50 GB/s line rate, the theoretical minimum all-reduce time across the 256-GPU cluster is:

T_{\text{IB}} = \frac{31.995\text{ GB}}{50\text{ GB/s}} \approx 0.640\text{ s} = 640\text{ ms}

Assuming 90% network efficiency after packet headers and congestion (~45 GB/s), the actual transfer requires approximately 711 ms.

Step compute time versus communication latency

To determine whether the 640 ms InfiniBand all-reduce introduces pipeline stalls, we must compare it against the computation time of one training step. The global batch size is 512 sequences of 8,192 tokens (approximately 4.19 million tokens). Across 256 GPUs, each GPU processes:

\text{Sequences per GPU} = \frac{512}{256} = 2\text{ sequences} = 16,384\text{ tokens per step}

With micro-batch size b = 1, each GPU executes 2 gradient accumulation steps. When using full activation checkpointing (recomputation), training requires approximately 8 \times N_{\text{params}} floating-point operations per token [3] (see Lesson 7, Training FLOPs, Time and MFU). The compute workload per GPU per step is:

\text{FLOPs per step} = 8 \times 8.03 \times 10^9 \times 16,384 \approx 1.053 \times 10^{15}\text{ FLOPs} = 1,053\text{ TFLOPs}

An NVIDIA H100 SXM GPU delivers 989 dense BF16 TFLOPS peak. At our target 40% Model FLOPs Utilization (MFU), the sustained execution throughput is:

\text{Sustained Throughput} = 989\text{ TFLOPS} \times 0.40 = 395.6\text{ TFLOPS}

Dividing workload by throughput yields the total step compute duration:

T_{\text{compute}} = \frac{1,053\text{ TFLOPs}}{395.6\text{ TFLOPS}} \approx 2.662\text{ seconds}

In standard backpropagation with activation recomputation, the forward pass consumes approximately one quarter of the computation (~0.665 s), while the backward pass consumes three quarters (\approx 1.997\text{ s}).

Execution timelines comparing step compute time against all-reduce duration. Within an 8-GPU node over NVLink, all-reduce requires only 31.2 ms (1.2% of step time). Across 256 GPUs over 400 Gb/s InfiniBand, all-reduce takes 640 ms, which fits comfortably inside the 1,997 ms backward pass. With a smaller batch of 1 sequence per GPU, the backward pass shrinks to 998 ms, narrowing the overlap margin.

Here is the critical observation: the 640 ms InfiniBand all-reduce is vastly shorter than the 1,997 ms backward compute pass (640\text{ ms} / 1,997\text{ ms} \approx 32\%). Because DDP streams gradient buckets asynchronously as layers complete, the entire 16 GB gradient transfer finishes long before the backward pass evaluates the final input embeddings. The communication overhead is 100% hidden, allowing the cluster to scale with near-linear compute efficiency.

The vulnerability of shrinking batch size

What happens if the team reduces the global batch size to 256 sequences (1 sequence per GPU, with no gradient accumulation)?

With only 8,192 tokens per GPU, the compute workload halves to 526 TFLOPs, cutting total step compute to 1.33 s and backward pass duration to approximately 0.998 s (998 ms). While the 640 ms all-reduce still fits within 998 ms, the communication margin narrows dramatically: communication now occupies 64% of the backward window. Any transient packet loss, route congestion on the spine switches, or straggler GPU delay will immediately exceed the remaining 358 ms buffer, stalling the compute engines and degrading cluster MFU.

Global Batch Size, Gradient Accumulation, and Optimization Limits

The Critical Batch Size and Gradient Noise Scale

Given that larger batch sizes provide longer backward passes that easily conceal communication latency, why not scale the global batch size to 10 million or 50 million tokens? The constraint lies not in networking, but in optimization mathematics.

In their seminal empirical study, McCandlish et al. established that every neural network training run exhibits a Critical Batch Size, denoted B_{\text{crit}} [4]. The critical batch size is governed by the gradient noise scale \mathcal{B}^*, which measures the ratio of the trace of the gradient covariance matrix to the squared norm of the true gradient vector [4]:

\mathcal{B}^* = \frac{\text{Tr}(\Sigma)}{|G|^2} = \frac{\mathbb{E}[|g_i - G|^2]}{|G|^2}

where G = \mathbb{E}[g_i] is the true gradient and \Sigma is the covariance of individual sample gradients.

Illustrative plots depicting optimization scaling as batch size expands. Below B_crit, training speedup scales linearly with batch size while the total optimization steps required to reach target loss decrease inversely. Above B_crit, gradient noise is eliminated, leading to diminishing returns where processing additional tokens yields minimal optimization progress.

The gradient noise scale defines two distinct operating regimes [4]:

  • Linear Scaling Regime (B \ll B_{\text{crit}}): When the batch size is small, individual gradients are noisy. Increasing the batch size averages out the noise, providing a higher-fidelity gradient estimate. In this regime, doubling the batch size halves the number of optimizer steps required to reach a target validation loss. Step throughput scales with near-perfect linear speedup.
  • Diminishing Returns Regime (B \gg B_{\text{crit}}): Once the batch size surpasses B_{\text{crit}}, gradient variance is effectively eliminated; additional samples yield virtually identical gradient averages. Further increasing batch size does not reduce the required optimization steps, meaning extra compute is wasted on redundant data. Total sample efficiency collapses.

For modern 7B–8B parameter autoregressive language models, empirical measurements show that B_{\text{crit}} starts around 1 million to 2 million tokens in early training and expands to approximately 4M to 8M tokens as the loss stabilizes [4]. Our target pretraining batch size of ~4M tokens (512 sequences of 8,192 tokens) sits precisely at this sweet spot, maximizing cluster parallelism without crossing into the regime of wasteful diminishing returns.

Learning rate scaling rules

When changing the global batch size, the learning rate must be adjusted to maintain stable convergence. Two primary conventions exist:

  1. Linear Scaling Rule: Formulated by Goyal et al. for SGD [3], setting \eta_{\text{new}} = \eta_{\text{base}} \times (B_{\text{new}} / B_{\text{base}}). To prevent early instability when applying large learning rates, training must include a linear warmup schedule, gradually ramping the learning rate from near zero over the first several thousand steps [3].
  2. Square-Root Scaling Rule: For adaptive moment optimizers such as AdamW, the second moment normalizer scales with the root of squared gradients. Many pretraining recipes scale the learning rate with the square root of the batch size ratio: \eta_{\text{new}} = \eta_{\text{base}} \times \sqrt{B_{\text{new}} / B_{\text{base}}}, which maintains better numerical stability across large batch transitions.

The Memory Wall: Why Plain DDP Fails for 8B Models

We have demonstrated that over our 256-GPU InfiniBand network, data-parallel communication takes only 640 ms and hides entirely behind the 1,997 ms backward pass. Why, then, can we not simply deploy standard PyTorch DDP to pretrain Llama 3.1 8B?

The answer is the 16-byte memory wall analyzed in Lesson 3, Training Memory. In pure DDP, every worker GPU maintains a standalone, complete model replica. For mixed-precision training with AdamW, each parameter requires 16 bytes of static memory [5]:

  • BF16 model parameters: 2 bytes (8.03 \times 10^9 \times 2 = 16.06\text{ GB})
  • BF16 gradients: 2 bytes (8.03 \times 10^9 \times 2 = 16.06\text{ GB})
  • FP32 master parameters: 4 bytes (8.03 \times 10^9 \times 4 = 32.12\text{ GB})
  • FP32 Adam momentum (m): 4 bytes (8.03 \times 10^9 \times 4 = 32.12\text{ GB})
  • FP32 Adam variance (v): 4 bytes (8.03 \times 10^9 \times 4 = 32.12\text{ GB})
Under plain DDP, all 16 bytes per parameter are replicated on every GPU. For Llama 3.1 8B, this requires 128.5 GB of static memory per GPU. Because an H100 provides only 79.6 GiB of usable memory, plain DDP crashes with Out-Of-Memory before allocating any activation tensors. This failure necessitates state sharding via ZeRO and FSDP.

Summing these components yields:

\text{Static Memory per GPU} = 16\text{ bytes} \times 8.03 \times 10^9 = 128.48\text{ GB} \quad (119.66\text{ GiB})

An NVIDIA H100 80 GB SXM GPU exposes 79.6 GiB of usable High Bandwidth Memory. Replicating the model states under plain DDP requires 119.66 GiB, exceeding physical memory capacity by 48.5 GB per GPU before allocating a single activation tensor, communication buffer, or CUDA context overhead!

Gradient accumulation reduces activation memory by shrinking the micro-batch size, but gradient accumulation does nothing to shrink static model or optimizer states. Plain PyTorch DDP cannot train Llama 3.1 8B on an 80 GB GPU. To make pretraining physically possible, the redundant 16 bytes per parameter must be partitioned across devices. How much data parallelism for our run?

For our 256-GPU pretraining run targeting Llama 3.1 8B with global batch size 512 sequences, we require a total data-parallel degree of 256 (\text{DP} = 256). However, because plain DDP runs out of memory, we cannot replicate all states. Instead, we must employ sharded data parallelism (Fully Sharded Data Parallelism / ZeRO), which we explore thoroughly in Lesson 11, ZeRO and FSDP. By sharding optimizer states, gradients, and model parameters across GPUs, the static memory per GPU drops from 128.5 GB to under 16 GB, fitting comfortably within our 80 GB H100 budget while preserving the overlap characteristics of all-reduce.

In Practice

The code below demonstrates a minimal, correct PyTorch DistributedDataParallel implementation configured for multi-node execution. The script configures the process group using NCCL, tunes gradient bucketing via bucket_cap_mb, demonstrates gradient accumulation with model.no_sync(), and is launched using torchrun.

Simple model replica model = nn.Sequential( nn.Linear(4096, 4096, bias=False), nn.GELU(), nn.Linear(4096, 4096, bias=False) ).to(device) # Wrap in DDP with custom bucket_cap_mb (default 25 MB) # Tuning bucket_cap_mb balances overlap frequency against collective launch overhead model = DDP( model, device_ids=[local_rank], output_device=local_rank, bucket_cap_mb=25, find_unused_parameters=False ) optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4) criterion = nn.MSELoss() dataset = SyntheticDataset() sampler = DistributedSampler(dataset, shuffle=True) loader = DataLoader(dataset, batch_size=1, sampler=sampler) accumulation_steps = 2 model.train() optimizer.zero_grad() for step, (inputs, targets) in enumerate(loader): inputs = inputs.to(device) targets = targets.to(device) is_accumulation_boundary = ((step + 1) % accumulation_steps == 0) # Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • GPUDirect RDMA: How modern NICs bypass host memory and transfer gradient buffers directly between GPU HBM across PCI switches or NVLink, cutting latency and freeing CPU cores [6].
  • Gradient Compression: Techniques such as FP8 gradient all-reduce, 1-bit Adam, and PowerSGD that compress the 16 GB gradient payload to 8 GB or 2 GB on bandwidth-constrained Ethernet clusters.
  • Straggler Mitigation: How a single throttled GPU or thermal event on one of 256 workers stalls the synchronous ring all-reduce, degrading cluster-wide MFU, and how watchdogs monitor rank completion times.
  • NCCL Channels: How NCCL establishes multiple concurrent rings and trees (typically 8 to 32 channels) mapped to distinct SMs and PCIe lanes to fully saturate bidirectional interconnects [6].
  • Dynamic Batch Sizing: Gradually expanding the global batch size from 1M to 4M tokens across the pretraining curriculum to match the evolving gradient noise scale \mathcal{B}^* [4].
  • Fault Recovery: Why data-parallel checkpoints require coordinated distributed saving (such as PyTorch Distributed Checkpointing), where each rank saves its local data slice without gathering to rank 0.

Summary

Mind map summarizing data parallelism, the ring all-reduce algorithm, NCCL tree and ring topologies, gradient bucketing and overlap, and memory constraints.
  • Data parallelism replicates the full model across all GPUs and partitions the global batch into distinct micro-batches. Local gradients are averaged via collective all-reduce before the optimizer step.
  • Ring all-reduce executes in two phases—Reduce-Scatter and All-Gather—transferring 2(N-1)/N \times S bytes per GPU. Communication volume asymptotically approaches 2S, remaining independent of GPU count.
  • NCCL dynamically switches between Double Binary Tree (low latency, 2 \log_2 N steps) for small payloads and Ring (high bandwidth, 2N steps) for large gradient buffers.
  • PyTorch DDP overlaps communication with computation by grouping parameters into buckets (governed by bucket_cap_mb) and launching asynchronous all-reduces as reverse-topological backpropagation completes each bucket.
  • For Llama 3.1 8B (16.06 GB BF16 gradients), all-reduce takes 31.2 ms over intra-node NVLink and 640 ms across 256 GPUs over 400 Gb/s InfiniBand. This 640 ms is easily hidden within the 1,997 ms backward pass.
  • Plain DDP cannot train Llama 3.1 8B because replicating weights, gradients, and Adam states requires 128.5 GB per GPU, exceeding an 80 GB H100 by 48.5 GB. Sharded data parallelism (ZeRO and FSDP) is mandatory.

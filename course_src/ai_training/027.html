Introduction

Pretraining teaches a model grammar, facts, and statistical representations of the world. However, a raw pretrained base model remains an autocomplete engine: given a question, it frequently responds by generating more questions, continuing an imaginary forum thread, or hallucinating conversational turns. Transforming a base model into a reliable production assistant requires a two-stage post-training pipeline: Supervised Fine-Tuning (SFT) to teach instruction following and formatting, followed by Direct Preference Optimization (DPO) to align responses with human preferences, tone, and safety constraints [1][2].

In this lab, we build an end-to-end post-training pipeline using Low-Rank Adaptation (LoRA) [3]. We take a base instruct model, fine-tune it on conversation data with assistant-only loss masking (computing gradients strictly on assistant responses rather than user prompts), and then optimize the resulting adapter against pairwise preference pairs using DPO. Finally, we evaluate the models with an automated pairwise win-rate judge, merge the adapter parameters directly into the base weights, and serve the resulting artifact behind a high-throughput vLLM engine. Figure 1 illustrates the workflow.

The two-stage post-training pipeline: Step 1 evaluates baseline instruct completions. Step 2 trains a LoRA adapter using SFT with assistant-only loss masking. Step 3 validates SFT formatting. Step 4 optimizes the adapter using DPO against pairwise chosen and rejected responses. Step 5 benchmarks win rates with an automated judge. Step 6 merges the adapter into the base weights for zero-overhead serving in vLLM.

We provide two parallel paths: a small path that trains a 0.5B to 1.5B parameter model (such as Qwen2.5-0.5B-Instruct or Qwen2.5-1.5B-Instruct) on a single consumer GPU or free Colab instance within 16 GB VRAM, and a full path that trains Llama 3.1 8B on an enterprise 8×H100 node matching our course's running post-training scenario.

Step 2: Supervised Fine-Tuning with Assistant-Only Loss

In standard pretraining language modeling, cross-entropy loss is computed uniformly across every token in the sequence. In multi-turn chat fine-tuning, however, calculating loss on prompt tokens is actively harmful: we want the model to learn how to respond like an expert assistant, not memorize the user's questions or system prompts (Lesson 22, Supervised Fine-Tuning). If the loss is computed over user prompt tokens, the model allocates precious gradient capacity to predicting the user's vocabulary and syntax, diluting its conversational alignment.

We use TRL's DataCollatorForCompletionOnlyLM to set all label tokens prior to the assistant's turn to -100 [4]. In PyTorch, torch.nn.CrossEntropyLoss natively ignores positions with target label -100, ensuring that gradients flow strictly from the assistant's tokens. Figure 2 visualizes this masking operation.

The input sequence contains chat delimiters, the user prompt, and the assistant response. DataCollatorForCompletionOnlyLM detects the assistant delimiter and replaces all preceding token labels with -100. PyTorch cross-entropy loss skips -100 entries, computing loss and gradients strictly over assistant tokens.

We configure LoRA via PEFT with rank r = 16 and scaling factor \alpha = 32, targeting all linear projection matrices in the self-attention and MLP blocks (q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj) [3]. In standard LoRA, the modified forward pass decomposes parameter updates into two low-rank matrices:

h = W_0 x + \Delta W x = W_0 x + \frac{\alpha}{r} B A x

where W_0 \in \mathbb{R}^{d_{\text{out}} \times d_{\text{in}}} is the frozen base model weight matrix, B \in \mathbb{R}^{d_{\text{out}} \times r} is initialized to zeros, and A \in \mathbb{R}^{r \times d_{\text{in}}} is initialized from a Gaussian distribution. Targeting all seven projection matrices rather than attention queries and values alone ensures that the MLP layers—which store the bulk of factual and reasoning representations—can adapt to customer-support domain policies.

This adds trainable adapter weights accounting for less than 1% of total model parameters while keeping the base model completely frozen. For Llama 3.1 8B, the trainable parameters total approximately 42 million weights (~84 MB in BF16), compared to 8.03 billion base parameters (16.06 GB).

Step 4: Direct Preference Optimization (DPO)

The LoRA Implicit Reference Model Trick

Direct Preference Optimization (Lesson 25, DPO and Preference Optimization) calculates the implicit reward of completion y given prompt x as:

r(x, y) = \beta \log \frac{\pi_\theta(y \mid x)}{\pi_{\text{ref}}(y \mid x)}

and minimizes the negative log-likelihood of the human preference rankings [2]:

\mathcal{L}_{\text{DPO}}(\theta; \pi_{\text{ref}}) = -\mathbb{E}_{(x, y_w, y_l)} \left[ \log \sigma \left( \beta \log \frac{\pi_\theta(y_w \mid x)}{\pi_{\text{ref}}(y_w \mid x)} - \beta \log \frac{\pi_\theta(y_l \mid x)}{\pi_{\text{ref}}(y_l \mid x)} \right) \right]

To understand how DPO updates the policy parameters, consider the gradient of the loss with respect to \theta derived by Rafailov et al. [2]:

\nabla_\theta \mathcal{L}_{\text{DPO}}(\theta) = -\beta \mathbb{E}_{(x, y_w, y_l)} \left[ \sigma\left(\hat{r}_\theta(x, y_l) - \hat{r}_\theta(x, y_w)\right) \left[ \nabla_\theta \log \pi_\theta(y_w \mid x) - \nabla_\theta \log \pi_\theta(y_l \mid x) \right] \right]

Notice the intuitive mechanics of this gradient update:

  • Direction of update: The gradient increases the likelihood of the chosen response \nabla_\theta \log \pi_\theta(y_w \mid x) while simultaneously decreasing the likelihood of the rejected response \nabla_\theta \log \pi_\theta(y_l \mid x).
  • Dynamic weighting: The step size is scaled by the sigmoid error \sigma(\hat{r}_\theta(x, y_l) - \hat{r}_\theta(x, y_w)). When the current policy incorrectly prefers the rejected response (\hat{r}_\theta(x, y_l) > \hat{r}_\theta(x, y_w)), the error approaches 1.0, generating a massive gradient update. Conversely, when the policy already prefers the chosen completion with high margin, the error decays toward 0.0, preventing unnecessary parameter drift.

In full-parameter DPO, evaluating this objective requires running four forward passes per step: \pi_\theta(y_w), \pi_\theta(y_l), \pi_{\text{ref}}(y_w), and \pi_{\text{ref}}(y_l). This requires maintaining two complete 16-GB model instances in GPU memory (the active policy and the frozen reference model). On single-GPU machines, this frequently triggers Out-Of-Memory (OOM) crashes.

When using PEFT, we exploit an elegant memory optimization: setting ref_model=None in DPOTrainer [4]. Because the policy and reference models share the exact same underlying base weights, TRL loads only one instance of the base model into VRAM. During the policy forward pass, the LoRA adapter is enabled; during the reference forward pass, TRL temporarily disables the adapter using with model.disable_adapter():. As shown in Figure 3, this eliminates all reference model memory duplication!

Step 6: Merge the LoRA Adapter and Serve

While LoRA adapters are compact for training and storage, running separate adapter matrices during production inference introduces runtime overhead: each linear layer must compute both the base GEMM W_0 x and the low-rank projection \frac{\alpha}{r} B A x, adding memory lookups and kernel launches (Inference Lesson 37, Multi-LoRA and Multi-Tenant Serving).

For dedicated single-model serving, we merge the adapter weights permanently into the base model using PEFT's merge_and_unload():

W_{\text{merged}} = W_0 + \frac{\alpha}{r} (B A)

Figure 6 illustrates this matrix fusion. The resulting model is saved as standard Hugging Face safetensors files, indistinguishable from a natively trained base model.

Low-rank matrices B (d x r) and A (r x k) are scaled by alpha/r and added directly into the frozen base weight tensor W_0. Three key patterns emerge from the results:

  • Loss alone does not predict alignment: SFT achieves low cross-entropy loss, but DPO dramatically improves customer satisfaction win rates (from 50% to 64.2%) by penalizing subtle bad habits that SFT loss cannot distinguish.
  • Verbosity calibration: Raw base and naive SFT models tend to generate rambling, defensive responses. DPO sharply trims unneeded boilerplate, bringing average length down to 148 tokens while preserving all essential instructions.
  • Implicit reward margin growth: In DPO, a widening positive gap between chosen and rejected log-probability ratios confirms that the policy is actively re-weighting token probabilities in accordance with preferences.

Common Pitfalls

  • Chat template mismatch: Training SFT on one template (such as ChatML <|im_start|>) and evaluating DPO on a different template (such as Llama 3 <|start_header_id|>). Tokenizer special token mismatches corrupt the model's perception of turn boundaries and cause it to emit raw delimiter tags as output text. Always use tokenizer.apply_chat_template() consistently across all stages, and ensure that special tokens (such as pad_token and eos_token) are synchronized.
  • Computing loss on user prompts: Forgetting DataCollatorForCompletionOnlyLM during SFT. When the model computes cross-entropy over user prompt tokens, it wastes adapter capacity learning to predict the user's syntax rather than mastering assistant responses. Ensure that your response_template matches the exact token string produced by the chat template (including leading newlines such as \n<|im_start|>assistant\n).
  • Reference model OOM crashes: Accidentally passing an explicit ref_model object during PEFT training. Always set ref_model=None when using LoRA in DPOTrainer to allow TRL to reuse the base model with disabled adapters. If an explicit reference model is passed, PEFT cannot intercept the forward pass, and memory consumption immediately doubles.
  • Hyperparameter \beta misconfiguration: If \beta is set too high (such as \beta = 1.0), the KL penalty dominates, preventing the model from learning preferences and keeping the implicit reward margins close to zero. If \beta is set too low (such as \beta = 0.01), the policy rapidly degenerates, overfitting to preference artifacts, generating repetitive gibberish, or repeating the prompt infinitely. Standard practice for instruct models is \beta \in [0.05, 0.2].
  • Learning rate too high in DPO: Using the SFT learning rate (e.g., 2 \times 10^{-4}) during DPO. DPO is a delicate re-weighting optimization; high learning rates destroy the conversational fluency acquired during SFT, leading to loss divergence or reward collapse. Always reduce the learning rate by 5× to 20× (e.g., 5 \times 10^{-6} to 1 \times 10^{-5}).
  • Uncontrolled length bias in preference datasets: Preference datasets often feature chosen responses that are substantially longer than rejected responses simply because annotators associate length with thoroughness. Without regularization, DPO models exploit this bias by generating verbose filler. Regularly monitor average output length, and filter or truncate preference datasets to ensure chosen and rejected lengths remain balanced.

Stretch Goals

If you complete the primary lab exercises ahead of time, consider these advanced extensions:

  1. Conservative DPO (c-DPO): Implement label smoothing in the DPO objective to account for noisy, mislabeled preference pairs where the annotator chose the wrong response [5].
  2. Length-normalized DPO: Modify the DPO loss function to explicitly divide implicit rewards by completion length, verifying whether length normalization prevents the model from exploiting length bias on UltraFeedback.
  3. QLoRA 4-bit quantization: Fine-tune Llama 3.1 8B in 4-bit precision using bitsandbytes (load_in_4bit=True), demonstrating that an 8B model can be fine-tuned and aligned on a single 16 GB consumer GPU.

  • Post-training bridges the gap between raw pretrained foundation models and aligned production assistants via a two-stage pipeline: SFT followed by preference optimization.
  • In SFT, using DataCollatorForCompletionOnlyLM masks prompt tokens with label -100, ensuring cross-entropy loss is computed exclusively on assistant turns.
  • In PEFT LoRA DPO, setting ref_model=None enables TRL to reuse the single frozen base model instance in VRAM by temporarily disabling the LoRA adapter, cutting VRAM by 50%.
  • DPO learning rates must be set significantly lower than SFT rates (typically 5 \times 10^{-6} vs 2 \times 10^{-4}) to prevent catastrophic forgetting of conversational capabilities.
  • Pairwise win-rate evaluation with position-shuffled candidates provides an objective measure of alignment quality that cross-entropy loss cannot capture.
  • Merging LoRA adapters into base weights via merge_and_unload() produces standard standalone model weights, eliminating adapter latency during high-throughput vLLM serving.

Introduction

Fine-tuning a large language model across every parameter requires massive GPU resources. In standard mixed-precision training with the AdamW optimizer, model weights, gradients, master weights, and optimizer momentum and variance tensors consume 16 bytes per parameter (as derived in Lesson 3, Training Memory) [1]. For an 8-billion-parameter model such as Llama 3.1 8B, this static footprint reaches 128.5 GB. Because an NVIDIA H100 SXM GPU provides 80 GB of High Bandwidth Memory, full-parameter fine-tuning cannot fit on a single GPU without multi-GPU sharding techniques such as FSDP (Lesson 11, ZeRO and FSDP) or DeepSpeed ZeRO-3.

Low-Rank Adaptation (LoRA) breaks this memory wall. Instead of updating all parameters across the dense weight matrices of the model, LoRA freezes the original pretrained weights W_0 and injects trainable rank-decomposition matrices into each layer [1]. By constraining the weight update \Delta W to a low intrinsic rank r, LoRA reduces the number of trainable parameters by over 99%. Crucially, because only the low-rank adapter parameters are updated, the optimizer and gradient memory collapses from over 112 GB down to less than 1 GB.

The forward pass architecture of a LoRA-adapted linear layer. The incoming activation vector x is processed simultaneously through the frozen pretrained weight matrix W0 and a parallel low-rank bypass consisting of matrix A and matrix B scaled by alpha/r. Matrix B is initialized to exact zero and matrix A is initialized from a Gaussian distribution, guaranteeing that the adapter perturbation delta W is exactly zero at the beginning of training.

Building on this foundation, QLoRA (Quantized Low-Rank Adaptation) compresses the frozen base weights down to 4-bit precision using an information-theoretically optimal NormalFloat (NF4) data type, double quantization of scaling factors, and paged optimizers [2]. QLoRA reduces the static memory of an 8B model to under 6 GB, enabling high-performance instruction fine-tuning on a single consumer GPU with 24 GB of VRAM.

In this lesson, we analyze the mathematical mechanics of LoRA and QLoRA, calculate the exact parameter and memory budgets for Llama 3.1 8B, examine why LoRA cuts optimizer states but not backward activations, explore recent empirical findings on the "learning versus forgetting" trade-off, examine variants including DoRA and rsLoRA, and evaluate deployment trade-offs between merged weights and multi-tenant adapter serving.

Clarifying the Problem

In post-training engineering discussions, selecting between full fine-tuning, LoRA, and QLoRA revolves around cluster capacity, latency budgets, and downstream task complexity. Here is how an architectural review typically begins:

Candidate: What model and post-training workload are we designing for?
Interviewer: We are fine-tuning Llama 3.1 8B Instruct for an enterprise customer-support platform. Our dataset consists of 50,000 multi-turn customer support conversations averaging 1,000 tokens per conversation.

Candidate: What compute infrastructure do we have available?
Interviewer: We have two hardware profiles to support. In our primary training cluster, we have 8×H100 80 GB nodes. However, smaller partner engineering teams need to replicate and iterate on customer-specific fine-tunes using a single 24 GB workstation GPU (such as an NVIDIA RTX 4090 or L4).

Candidate: Are we targeting task-specific style and format adaptation, or are we injecting massive new domain encyclopedic knowledge?
Interviewer: The model needs to adopt corporate tone, follow strict structured customer-support policies, handle tool call formatting, and avoid hallucinations. It already has strong general English comprehension from pretraining.

Candidate: What is the serving target after fine-tuning?
Interviewer: We will serve over 500 distinct enterprise customer adapters. In production, we cannot maintain 500 separate 16 GB base model replicas in GPU memory.

Candidate: Does adapter fine-tuning compromise final task quality compared to full fine-tuning?
Interviewer: That is what we need you to quantify. How do we configure rank, alpha, and target modules, and what are the trade-offs?

The core engineering question is: How do we configure parameter-efficient fine-tuning to train within single-GPU and single-node memory budgets, while maintaining model quality and enabling efficient multi-tenant serving?

The LoRA Architecture and Parameter Mechanics

Mathematical formulation

Consider a pretrained linear layer with weight matrix W_0 \in \mathbb{R}^{d \times k}. During standard full fine-tuning, the layer output h \in \mathbb{R}^d for an input activation vector x \in \mathbb{R}^k is computed as h = W x = (W_0 + \Delta W) x, where \Delta W \in \mathbb{R}^{d \times k} is an unconstrained full-rank matrix updated directly via gradient descent.

Drawing on the hypothesis by Aghajanyan et al. that parameter updates during downstream adaptation have a low intrinsic dimension [1], LoRA parameterizes the accumulated update \Delta W through a low-rank matrix decomposition:

\Delta W = \frac{\alpha}{r} B A

Here, A \in \mathbb{R}^{r \times k} is a down-projection matrix, B \in \mathbb{R}^{d \times r} is an up-projection matrix, and the rank r \ll \min(d, k) defines the bottleneck dimension. The scalar \alpha is a constant scaling hyperparameter. The modified forward pass computes:

h = W_0 x + \frac{\alpha}{r} B A x

Initialization and scaling dynamics

To ensure that training begins stably from the exact baseline predictions of the pretrained model, the matrices A and B use asymmetric initialization [1]:

  • Matrix B is initialized to exact zeros (B = 0).
  • Matrix A is initialized with random Gaussian noise drawn from \mathcal{N}(0, \sigma^2), where standard implementations use \sigma = 1 / \sqrt{r} or Kaiming uniform initialization.

Because B = 0 at step 0, the product B A = 0, meaning \Delta W = 0. The base model's outputs are unmodified at the onset of training, preventing random initialization shocks.

The constant factor \frac{\alpha}{r} scales the magnitude of the adapter update. When tuning hyperparameters, setting \alpha = 2r (for instance, r = 16, \alpha = 32) is a standard heuristic. Fixing \alpha ensures that if you adjust the rank r during experimentation, you do not need to retune the learning rate from scratch [1].

Which modules to target: attention vs all linear projections

In the original paper by Hu et al. (2021), LoRA was evaluated primarily on the query (W_q) and value (W_v) projection matrices of the attention block to minimize parameter overhead [1]. However, comprehensive ablation studies in QLoRA (Dettmers et al., 2023) demonstrated that adapting all linear projections in both the self-attention and MLP blocks is necessary to match full fine-tuning performance [2].

Comparison of adaptation coverage across a modern transformer block. Adapting only Q and V (Hu et al.) captures 6.82M parameters (0.08% of Llama 3.1 8B). Adapting all seven linear projections (Q, K, V, O, Gate, Up, Down) yields 41.94M parameters (0.52%), providing the expressivity needed to match full-parameter fine-tuning.

In Llama 3.1 8B, each transformer layer contains seven distinct linear projection matrices:

  • Attention projections: W_q \in \mathbb{R}^{4096 \times 4096}, W_k \in \mathbb{R}^{1024 \times 4096}, W_v \in \mathbb{R}^{1024 \times 4096}, and W_o \in \mathbb{R}^{4096 \times 4096} (accounting for Grouped-Query Attention with 8 KV heads).
  • SwiGLU MLP projections: W_{\text{gate}} \in \mathbb{R}^{14336 \times 4096}, W_{\text{up}} \in \mathbb{R}^{14336 \times 4096}, and W_{\text{down}} \in \mathbb{R}^{4096 \times 14336}.

Restricting LoRA to W_q and W_v starves the feed-forward networks—which store substantial factual knowledge and domain mapping capacity—of gradient adaptation. Targeting all seven projections at a modest rank (r = 16) consistently outperforms targeting only attention weights at a high rank (r = 64) while utilizing fewer total parameters [2].

Parameter and Memory Math for Llama 3.1 8B

Trainable parameter count at rank 16

Let us compute the exact number of adapter parameters added to Llama 3.1 8B (L = 32 layers, hidden size d = 4,096, intermediate MLP dimension d_{ff} = 14,336, 8 KV heads with head dim 128 giving KV dimension d_{kv} = 1,024) at rank r = 16. For any linear matrix of shape d_{\text{out}} \times d_{\text{in}}, the adapter parameters are r \times (d_{\text{in}} + d_{\text{out}}):

  • W_q: 16 \times (4,096 + 4,096) = 131,072\text{ parameters}
  • W_k: 16 \times (4,096 + 1,024) = 81,920\text{ parameters}
  • W_v: 16 \times (4,096 + 1,024) = 81,920\text{ parameters}
  • W_o: 16 \times (4,096 + 4,096) = 131,072\text{ parameters}
  • Total attention adapter parameters per layer: 131,072 + 81,920 + 81,920 + 131,072 = 425,984\text{ parameters}.
  • W_{\text{gate}}: 16 \times (4,096 + 14,336) = 294,912\text{ parameters}
  • W_{\text{up}}: 16 \times (4,096 + 14,336) = 294,912\text{ parameters}
  • W_{\text{down}}: 16 \times (14,336 + 4,096) = 294,912\text{ parameters}
  • Total MLP adapter parameters per layer: 3 \times 294,912 = 884,736\text{ parameters}.
  • Total adapter parameters per layer: 425,984 + 884,736 = 1,310,720\text{ parameters}.

Multiplying across all 32 layers gives the exact model-wide trainable count:

\text{Total Trainable Parameters} = 32 \times 1,310,720 = 41,943,040 \approx 41.94\text{ million parameters}

Relative to the 8.03 billion parameters of Llama 3.1 8B, the trainable adapter represents exactly 0.522% of the base model. This matches the exact multi-tenant adapter sizing derived in Inference Lesson 37, Multi-LoRA and Multi-Tenant Serving (42M parameters, 80 MiB in BF16).

Static memory comparison: 128.5 GB vs 16.7 GB

Now consider how this parameter reduction transforms static GPU memory during training:

  • Base model weights: The 8.03B base parameters remain completely frozen in 16-bit BF16: 8.03 \times 10^9 \times 2\text{ bytes} \approx 16.06\text{ GB} (14.96 GiB). Because they are frozen, they require 0 bytes of gradients, 0 bytes of master weights, and 0 bytes of Adam states.
  • Adapter weights: In BF16, 41,943,040 \times 2\text{ bytes} = 83,886,080\text{ bytes} \approx 83.89\text{ MB} (80.0 MiB).
  • Adapter gradients: In BF16, 41,943,040 \times 2\text{ bytes} = 83.89\text{ MB}.
  • Adapter optimizer states (AdamW): FP32 master weights (4 bytes) + FP32 momentum (4 bytes) + FP32 variance (4 bytes) = 12 bytes per parameter. For the adapter: 41,943,040 \times 12\text{ bytes} = 503,316,480\text{ bytes} \approx 503.32\text{ MB}.
  • Total static trainable footprint: 83.89 + 83.89 + 503.32 = 671.1\text{ MB} (640.0 MiB).
Full fine-tuning requires 128.5 GB of static memory (16.1 GB weights + 16.1 GB gradients + 96.3 GB Adam states), exceeding an 80 GB GPU by 48.5 GB. LoRA requires 16.06 GB for frozen base weights and only 0.67 GB for adapter states, leaving roughly 63 GB free on an H100 for activations and micro-batches.

Total static memory for LoRA is 16.06\text{ GB} + 0.67\text{ GB} = 16.73\text{ GB}. The optimizer and gradient footprint collapses by a factor of 168× (from 112.4 GB down to 0.67 GB). On an 80 GB H100, over 63 GB of memory remains entirely available for forward activations, batching, and context scaling.

Why LoRA does NOT cut activation memory or forward compute

A common misconception among systems engineers is that reducing trainable parameters by 99% reduces training FLOPs and activation memory by 99%. It does not.

During the backward pass, backpropagation relies on the chain rule to propagate error gradients from the loss layer down to the earliest layers. For any linear layer y = (W_0 + \Delta W) x, computing the gradient with respect to the input activation x (which forms the upstream error signal for the preceding layer) requires multiplying the incoming output gradient by the full transposed weight matrix:

\frac{\partial \mathcal{L}}{\partial x} = \left(\frac{\partial \mathcal{L}}{\partial y}\right) \left( W_0 + \frac{\alpha}{r} B A \right)^\top

Because \frac{\partial \mathcal{L}}{\partial x} depends directly on W_0, the backward pass must backpropagate through all 32 layers of frozen base weights. Furthermore, computing the adapter gradient requires saving the layer's forward input activations x:

\frac{\partial \mathcal{L}}{\partial A} = \frac{\alpha}{r} B^\top \left( \frac{\partial \mathcal{L}}{\partial y} \right) x^\top

Consequently, all intermediate layer activations—attention scores, LayerNorm statistics, and MLP projections—must either be preserved in memory or recomputed using activation checkpointing (as analyzed in Lesson 3, Training Memory). LoRA provides zero reduction in per-token activation memory.

In terms of compute, the forward pass must evaluate the full matrix multiplication W_0 x in addition to the two low-rank multiplications x A and (x A) B. Rather than saving FLOPs, LoRA actually adds a small arithmetic overhead (~1% to 2% additional FLOPs). LoRA is strictly a memory-reduction technique for optimizer states and gradients, not a compute accelerator.

QLoRA: 4-Bit NormalFloat, Double Quantization, and Paged Optimizers

While LoRA reduces static state from 128.5 GB to 16.7 GB, the 16.06 GB frozen base model still prevents fine-tuning on consumer GPUs with 16 GB or 24 GB of VRAM once backward activations are allocated. QLoRA (Dettmers et al., 2023) eliminates this limitation through three core algorithmic innovations [2]:

QLoRA compresses base model weights into 4-bit NormalFloat (NF4), quantizes quantization constants with Double Quantization to save 0.37 bits/param, and pages adapter optimizer states to CPU RAM via CUDA Unified Memory during peak allocation spikes.

1. 4-bit NormalFloat (NF4) data type

Standard uniform 4-bit integer (INT4) or floating-point (FP4) formats assume a uniform distribution over weight values. However, pretrained neural network weights follow a zero-mean normal distribution \mathcal{N}(0, \sigma^2). Uniform quantization wastes precision by placing equal numbers of quantization bins in the low-probability tails and the high-probability center.

NormalFloat4 (NF4) is an information-theoretically optimal quantile quantization data type for normally distributed tensors [2]. The 16 discrete bin values of NF4 are set to the exact quantiles q_i of a theoretical \mathcal{N}(0, 1) distribution such that each of the 16 intervals contains an identical probability mass 2^{-4} = 1/16 = 0.0625. The weights in each block of size B = 64 are normalized by their absolute maximum value and mapped to the closest quantile. NF4 significantly outperforms standard FP4 and INT4 in preserving linguistic nuance and perplexity [2].

2. Double Quantization (DQ)

To preserve accuracy, QLoRA uses block-wise quantization with a small block size of B_1 = 64. Slicing an 8.03B parameter model into blocks of 64 requires 8.03 \times 10^9 / 64 \approx 125.5\text{ million scaling factors}. Storing each scale as a 32-bit float requires 32 / 64 = 0.5\text{ bits per parameter}, adding 502 MB of overhead.

Double Quantization treats the first-stage quantization constants themselves as weights and quantizes them into 8-bit FP8 (with block size B_2 = 256), tracked by a secondary FP32 scale [2]. The scale memory drops from 0.5 bits per parameter to:

\text{Scale Memory} = \frac{8}{64} + \frac{32}{64 \times 256} = 0.125 + 0.00195 \approx 0.127\text{ bits per parameter}

Double Quantization saves 0.5 - 0.127 = 0.373\text{ bits per parameter}, freeing approximately 374 MB of GPU memory on Llama 3.1 8B with zero observable loss in accuracy [2].

3. Paged optimizers

During long-context training or activation checkpointing, PyTorch allocates temporary workspaces that cause short-lived memory spikes. If a training step peaks near the physical VRAM boundary, the run crashes with an Out-of-Memory (OOM) exception.

QLoRA solves this by allocating the 32-bit AdamW optimizer states using CUDA Unified Memory [2]. When memory pressure spikes during backward activation materialization, the NVIDIA driver automatically pages non-active optimizer page tables to host CPU system RAM across PCIe. Once backward passes finish and the optimizer step begins, the states are paged back to GPU HBM. This eliminates OOM edge crashes without slowing down steady-state execution.

The 65B verification benchmark

In the seminal QLoRA paper, Dettmers et al. verified that QLoRA enabled fine-tuning a 65-billion-parameter LLaMA model on a single 48 GB NVIDIA RTX A6000 GPU in 24 hours [2]. On the Vicuna and OpenAssistant evaluation benchmarks, the 4-bit QLoRA-adapted 65B model matched 99.3% of the performance of ChatGPT (GPT-3.5) and fully matched 16-bit full fine-tuning baselines, proving that 4-bit base weight quantization introduces no fundamental quality degradation when paired with 16-bit low-rank adapters [2].

Quality vs Full Fine-Tuning: "LoRA Learns Less and Forgets Less"

While parameter-efficient fine-tuning saves immense GPU resources, does a low-rank adapter learn as effectively as full fine-tuning?

In the comprehensive empirical study LoRA Learns Less and Forgets Less (Biderman et al., 2024, Databricks Mosaic / Columbia, arXiv:2405.09673), the authors conducted thousands of controlled comparisons across code generation (HumanEval, Python), mathematics (GSM8K), and instruction following [3]. Their findings establish two fundamental engineering trade-offs:

Empirical dynamics from Biderman et al. (2024). Full fine-tuning maximizes target-domain adaptation but causes severe catastrophic forgetting of general knowledge. Standard low-rank LoRA acts as a strong regularizer, retaining pretraining capabilities while adapting style and instruction formatting.

1. LoRA learns less on knowledge-intensive domains

When evaluated on domain adaptation tasks requiring dense factual memorization or complex algorithmic reasoning (such as learning a completely new programming language or solving multi-step mathematical proofs), standard LoRA (r = 8, 16) consistently underperforms full fine-tuning [3]. Spectral analysis of weight update matrices reveals that full fine-tuning modifies weights across an intrinsic rank 10× to 100× higher than standard LoRA configurations. A low-rank constraint simply lacks the parameter degrees of freedom required to store large volumes of novel relational knowledge.

2. LoRA forgets less of the pretraining distribution

Conversely, because LoRA restricts weight perturbations to a low-rank subspace, it acts as a powerful structural regularizer. On out-of-domain general knowledge benchmarks (such as MMLU, ARC, and HellaSwag), LoRA preserves pretraining capabilities far better than full fine-tuning [3]. Full fine-tuning frequently exhibits severe catastrophic forgetting, where aggressively training on customer support dialogues degrades general reasoning and grammar diversity. LoRA mitigates this degradation significantly better than standard regularization techniques like weight decay or dropout [3].

Do not treat LoRA as an exact substitute for full fine-tuning when the goal is massive domain memorization (e.g. ingesting millions of lines of proprietary code or specialized legal corpuses). However, for instruction tuning, conversational alignment, customer support tone adaptation, and tool-use structuring, LoRA's regularizing effect is an active benefit rather than a limitation.

LoRA Variants: DoRA, LoRA+, and rsLoRA

To overcome standard LoRA's capacity ceilings and optimization quirks, several architectural variants have emerged:

DoRA decomposes weight matrices into magnitude and directional components. LoRA+ applies asymmetric learning rates to matrices A and B. rsLoRA stabilizes rank scaling using 1/sqrt(r) to prevent gradient collapse at high ranks.

DoRA (Weight-Decomposed Low-Rank Adaptation)

Proposed by Liu et al. (2024, arXiv:2402.09353), DoRA mathematically decomposes a weight matrix W into its magnitude vector m \in \mathbb{R}^{1 \times k} and its directional matrix V \in \mathbb{R}^{d \times k} [4]:

W = m \odot \frac{V}{\|V\|_c} = m \odot \frac{W_0 + \frac{\alpha}{r} B A}{\|W_0 + \frac{\alpha}{r} B A\|_c}

where \|\cdot\|_c denotes the column-wise vector norm. While standard LoRA proportionally couples changes in weight magnitude and direction, full fine-tuning alters magnitude and direction independently. By using LoRA specifically for directional updates while updating magnitude m directly, DoRA bridges the performance gap with full fine-tuning on reasoning benchmarks. After training, DoRA matrices merge cleanly back into base weights with zero inference latency [4].

LoRA+ (Asymmetric Learning Rates)

Developed by Hayou et al. (ICML 2024, arXiv:2402.12354), LoRA+ proves that in wide neural networks, using the same learning rate for matrix A and matrix B leads to suboptimal feature learning [5]. Because B is initialized to zero, its singular values grow slowly, stalling gradient updates. LoRA+ fixes this by scaling the learning rate of matrix B relative to matrix A:

\eta_B = \lambda \eta_A \quad \text{where } \lambda \in [16, 32]

Setting \lambda = 16 accelerates convergence by up to 2× on downstream tasks with zero additional memory or computational cost [5].

rsLoRA (Rank-Stabilized LoRA)

In standard LoRA, dividing by r causes the effective update scale to shrink as rank increases. Kalajdzievski (2023, arXiv:2312.03732) proved that this causes gradient collapse at high ranks (r \ge 64), preventing practitioners from scaling rank to improve accuracy [6]. rsLoRA modifies the scaling constant from \frac{\alpha}{r} to \frac{\alpha}{\sqrt{r}}:

\Delta W = \frac{\alpha}{\sqrt{r}} B A

This stabilizes gradient norms across arbitrary ranks, enabling practitioners to scale rank up to r = 128 or r = 256 to capture additional domain capacity without training instability [6].

Serving: Merged Adapters vs Unmerged Multi-Tenant Serving

Once post-training finishes, how should adapters be deployed? As shown in Figure 7, the two production paradigms represent opposing trade-offs between latency and hardware multi-tenancy:

Option A merges adapter weights offline, giving maximum inference throughput for single-tenant deployments. Option B keeps base weights shared in GPU memory while dynamically routing batched requests across hundreds of distinct customer adapters using S-LoRA or Punica kernels (Inference Lesson 37).

Option A: Merged adapters for dedicated deployments

For high-volume, single-purpose applications (such as a core customer support assistant), the adapter can be permanently merged into the base weights offline:

W_{\text{merged}} = W_0 + \frac{\alpha}{r} B A

The resulting weights are saved as standard Hugging Face model safetensors. During serving, inference engines (such as vLLM or SGLang) execute standard matrix multiplications with zero latency overhead, zero extra kernel launches, and zero additional GPU memory. However, each fine-tuned variant requires its own dedicated 16 GB base model replica in GPU memory.

Option B: Unmerged adapters for multi-tenant fleets

When an enterprise platform must support 500 distinct customer adapters (our scenario requirement), merging weights would require 500 separate 16 GB models (8 TB of weights), demanding over 100 GPUs. As detailed in Inference Lesson 37, Multi-LoRA and Multi-Tenant Serving, multi-LoRA serving systems (such as S-LoRA and Punica) retain one shared copy of the base model in GPU memory [7].

When a batch arrives containing queries for different customer adapters, specialized batched matrix multiplication kernels (such as Segmented Gather-Matrix-Vector, or SGMV) apply the appropriate adapter A and B matrices on the fly [7]. One 80 GB H100 GPU can concurrently host the 15 GiB base model and cache dozens of 80 MiB customer adapters in VRAM, swapping long-tail customer adapters from host CPU memory in milliseconds [7].

Which fine-tuning strategy fits our deployment?

For our core enterprise customer-support platform, Standard LoRA (BF16, r=16, \alpha=32) targeting all linear modules on our 8×H100 cluster is the optimal engineering choice. It completes in 38 minutes for just $15, eliminates the dequantization latency overhead of QLoRA, and produces lightweight 80 MiB adapter artifacts that directly plug into our multi-tenant S-LoRA serving infrastructure (Inference Lesson 37). For partner engineering teams with only a single 24 GB workstation, QLoRA with NF4 and double quantization is the mandated path: it fits comfortably within 16 GB of working VRAM and produces mathematically compatible adapters with identical serving weight representations.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Tie-weights and LM head adaptation: In models where the input word embeddings and the final output language model head share the same weight tensor (tied embeddings), adapting the LM head with LoRA can break weight sharing or cause memory bloat. For Llama 3.1 8B, the embedding layer and LM head are untied; adapting the LM head adds 16 \times (4096 + 128256) \approx 2.1\text{M parameters} per adapter.
  • Gradient checkpointing interaction with LoRA: Because LoRA base weights are frozen, some naive autodiff frameworks mistakenly skip activation checkpointing for base layers. Enabling model.enable_input_require_grads() or using PEFT's prepare_model_for_kbit_training() attaches backward hooks to ensure input activation checkpoints are retained properly.
  • LoRA dropout and regularization: Setting lora_dropout = 0.05 or 0.1 drops random intermediate coordinates in x A during training. This prevents co-adaptation of low-rank adapter columns and improves generalizability on small instruction datasets.
  • Adapter fusion and weight arithmetic: Multiple LoRA adapters trained on distinct tasks (such as customer support, code syntax, and translation) can be linearly combined into a single adapter via spherical linear interpolation (SLERP) or weighted addition: \Delta W_{\text{fused}} = \sum w_i \Delta W_i.
  • Quantization-aware fine-tuning (QA-LoRA): Standard QLoRA uses NF4, which cannot be directly executed as fast INT4 tensor core GEMMs during inference. QA-LoRA and LoftQ align quantization intervals during fine-tuning so the merged model can be directly exported as an INT4 checkpoint for accelerated inference engines.
  • Rank search and adaptive rank allocation (AdaLoRA): Rather than fixing r=16 uniformly across all layers, AdaLoRA dynamically allocates higher rank to sensitive layers (such as early attention layers and late MLP blocks) while pruning uninformative singular values from middle layers.
  • Multi-GPU scaling with LoRA (DDP vs FSDP): Because LoRA gradients are only 84 MB, standard Distributed Data Parallel (DDP) all-reduce communication takes less than 1 ms over NVLink, rendering complex sharding schemes like FSDP unnecessary for LoRA on an 8-GPU node.

Summary

Mind map summarizing the LoRA and QLoRA lesson: low-rank matrix decomposition, 16-byte memory reduction, QLoRA 4-bit innovations, learning dynamics, variants, and deployment trade-offs.
  • LoRA parameterizes weight updates as \Delta W = \frac{\alpha}{r} B A. Initializing B=0 and A \sim \mathcal{N}(0, 1/r) ensures \Delta W = 0 at initialization, preserving base model outputs.
  • Adapting all seven linear projections (Q, K, V, O, Gate, Up, Down) at r=16 on Llama 3.1 8B adds 41.94M trainable parameters (0.52% of the model), requiring 80.0 MiB in BF16.
  • LoRA collapses optimizer and gradient memory from 112.4 GB to 0.67 GB (a 168× reduction), but does not cut activation memory or forward compute, because the chain rule requires backpropagating through all frozen base weights.
  • QLoRA combines 4-bit NormalFloat (NF4), Double Quantization (saving 0.37 bits/param), and Paged Optimizers to fine-tune Llama 3.1 8B within 14–16 GB of VRAM on a consumer GPU.
  • Biderman et al. (2024) prove that "LoRA learns less and forgets less": it has lower capacity on knowledge-heavy reasoning tasks than full fine-tuning, but provides superior retention of base model general capabilities.
  • Variants enhance capability: DoRA decouples magnitude and direction, LoRA+ scales \eta_B = 16 \eta_A for 2× faster convergence, and rsLoRA scales by \alpha / \sqrt{r} to unlock high ranks.
  • Adapters can be merged offline for single-tenant serving with zero latency penalty, or kept unmerged in multi-LoRA engines (S-LoRA) to serve hundreds of tenant adapters from a single GPU (Inference Lesson 37).

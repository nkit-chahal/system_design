Introduction

When training an 8-billion-parameter language model such as Llama 3.1 8B, Fully Sharded Data Parallel (FSDP) and ZeRO-3 shard the 128.5 GB of model and optimizer states comfortably across eight GPUs in a single server (see Lesson 11, ZeRO and FSDP). But when scaling to 70-billion or 405-billion parameter models, memory requirements explode. A 70B model requires over 1.1 TB of static state in 16-bit mixed precision; a 405B model requires nearly 6.5 TB. Even with Tensor Parallelism (TP) dividing attention and MLP projections across an 8-GPU node (see Lesson 12, Tensor, Sequence and Context Parallelism), an entire 70B or 405B model cannot execute inside a single chassis without sharding or partitioning layers across nodes.

Extending Tensor Parallelism across multiple nodes degrades training throughput catastrophically. TP requires two collective All-Reduce communications inside every single transformer layer—one for the multi-head self-attention projection and one for the feed-forward network. Across 32 or 80 layers, this demands hundreds of collective operations per training step. While intra-node NVLink provides 900 GB/s per GPU with sub-microsecond latency, inter-node InfiniBand networks provide 50 GB/s per GPU with microsecond latencies. Subjecting high-frequency All-Reduce operations to inter-node latency stalls GPU tensor cores and collapses Model FLOPs Utilization (MFU).

Pipeline Parallelism (PP) solves this interconnect dilemma by partitioning the model vertically by layers across sequential stages [1]. Instead of splitting individual weight matrices within each layer, pipeline parallelism assigns consecutive blocks of transformer layers to different GPUs or multi-node GPU groups. Communication occurs only at stage boundaries: stage k transmits its forward output activations to stage k+1, and receives backward activation gradients from stage k+1. Because communication occurs only between adjacent stages at layer boundaries, the communication frequency drops by orders of magnitude compared to tensor parallelism.

A 32-layer transformer partitioned across four pipeline stages (GPU 0 to GPU 3). Stage 0 hosts the token embedding and layers 0 to 7. Intermediate stages 1 and 2 host internal layers. Stage 3 hosts layers 24 to 31, final RMSNorm, the LM head, and the loss function. Forward activations flow left-to-right; backward gradients flow right-to-left.

However, vertical partitioning introduces a fundamental challenge: pipeline bubbles. Because stage k+1 depends on the activations produced by stage k, downstream GPUs sit completely idle waiting for upstream computation to reach them. Without careful scheduling, naive pipeline parallelism leaves accelerators idle for over 70% of the training step. In this lesson, we examine how micro-batch scheduling (GPipe and 1F1B) shrinks the bubble, analyze activation memory accumulation across stages, explore advanced interleaved and zero-bubble schedules, derive the point-to-point network traffic, and evaluate where pipeline parallelism fits in large-scale cluster design.

Clarifying the Problem

In distributed infrastructure interviews, pipeline parallelism questions focus on scheduling trade-offs, bubble fraction arithmetic, memory buffering, and network hierarchy. Here is how a discussion between a candidate and an interviewer typically unfolds:

Candidate: Which model are we distributing, and what is our target hardware cluster?
Interviewer: We are pretraining a 70-billion parameter model (Llama 3.1 70B: 80 layers, hidden dimension 8,192, 64 query heads, 8 KV heads) across 64 nodes of 8 NVIDIA H100 80 GB GPUs (512 GPUs total). Intra-node interconnect is 900 GB/s NVLink; inter-node is 8 × 400 Gb/s InfiniBand NDR (50 GB/s per GPU).

Candidate: What sequence length and batch size are specified for this run?
Interviewer: Sequence length is 8,192 tokens. Global batch size is 4 million tokens, corresponding to 512 sequences per optimizer step.

Candidate: Why not use pure Tensor Parallelism across the entire cluster, or pure FSDP?
Interviewer: TP beyond an 8-GPU node saturates our 400 Gb/s InfiniBand network because it requires two All-Reduce collectives in every layer. Pure FSDP over 512 GPUs oversubscribes the inter-node network with parameter all-gathers. We want to evaluate a hybrid 3D layout using TP inside each node and Pipeline Parallelism across nodes.

Candidate: What pipeline depth are you considering, and what is our tolerance for pipeline bubbles?
Interviewer: We are evaluating pipeline depths of p = 4 and p = 8. We need the pipeline bubble fraction to remain strictly under 15% to maintain an MFU above 40%. How should we schedule the pipeline, how many micro-batches are required, and what happens to GPU memory?

The core question is: How do we split layers across sequential stages, schedule forward and backward micro-batches to minimize idle bubble time, and prevent in-flight activations from triggering out-of-memory errors? To answer it, we begin by analyzing why naive pipelining fails.

The Pipeline Bubble: From Naive Execution to 1F1B

Why naive pipeline execution provides zero speedup

Consider a model divided across p = 4 pipeline stages, where each stage runs on one GPU. If the system processes an entire mini-batch as a single monolithic block, GPU 0 evaluates the forward pass for its layers and sends the intermediate activation tensor to GPU 1. While GPU 1 computes, GPU 0 has no work to perform and sits idle. The computation propagates sequentially through GPU 2 and GPU 3. Once GPU 3 evaluates the loss, it computes its backward pass and transmits activation gradients back to GPU 2. The backward pass propagates in reverse until GPU 0 updates its parameters.

Execution timeline for four pipeline stages with no micro-batching. At any given instant, only one GPU is computing while three GPUs sit idle. The idle pipeline bubble consumes 75% of total execution time.

In this naive arrangement, exactly one stage executes at any point in time while the other p - 1 stages idle. The fraction of idle time—termed the pipeline bubble—is:

\text{Bubble Fraction}_{\text{naive}} = \frac{p - 1}{p}

For p = 4, 75% of GPU cycles are wasted; for p = 8, 87.5% are wasted. Adding GPUs does not accelerate the training step; it merely shards the parameters across devices while leaving total wall-clock execution time identical to single-GPU execution. To achieve parallel speedup, the pipeline must keep multiple stages computing concurrently.

GPipe: Micro-batching and the pipeline flush

The breakthrough introduced by Huang et al. in GPipe is to divide the mini-batch into m smaller micro-batches (m \ge p) [1]. Instead of waiting for an entire batch to finish, GPU 0 executes the forward pass on micro-batch 1 (F_1) and immediately transmits the resulting activations to GPU 1. While GPU 1 executes F_1, GPU 0 immediately starts computing F_2. In this manner, micro-batches stream through the pipeline like an assembly line.

Timeline for p = 4 stages and m = 8 micro-batches under GPipe. All forward micro-batches (F1 to F8) execute before any backward passes begin. Stage 0 must retain activations for all 8 micro-batches until the backward pass returns, creating an O(m) memory bottleneck.

In GPipe, all m forward micro-batches are evaluated across all stages before any backward passes begin. Once the final stage evaluates F_m, it begins the backward pass (B_m), propagating gradients back to stage 0. A global synchronization barrier—a pipeline flush—occurs at the end of every step before the optimizer updates weights across all stages. This preserves exact batch gradient statistics identical to non-pipelined training.

The total duration of the GPipe step can be derived analytically. Let t_F be the forward execution time of one micro-batch on one stage, and t_B be the backward execution time. In neural networks, backward compute takes roughly twice as long as forward compute (t_B \approx 2 t_F) because backpropagation computes both activation gradients and parameter weight gradients (see Lesson 2, Forward and Backward Passes). For simplicity of notation, let t_{\text{step}} = t_F + t_B.

Stage 0 starts F_1 at time 0. The final stage p - 1 begins F_1 at time (p - 1) t_F. The final stage finishes all m forward passes at time (p - 1) t_F + m t_F. It then executes m backward passes, which take m t_B. The backward pass of the final micro-batch then takes (p - 1) t_B to propagate back from stage p - 1 to stage 0. The total step duration is therefore:

T_{\text{total}} = m (t_F + t_B) + (p - 1)(t_F + t_B) = (m + p - 1)(t_F + t_B)

The total useful compute time spent by each GPU across the step is m (t_F + t_B). The total idle time spent by each GPU in the bubble is (p - 1)(t_F + t_B). Dividing idle time by total step time yields the canonical bubble fraction formula:

\text{Bubble Fraction} = \frac{(p - 1)(t_F + t_B)}{(m + p - 1)(t_F + t_B)} = \frac{p - 1}{m + p - 1}

When the number of micro-batches m is substantially larger than the pipeline depth p (m \gg p), the bubble fraction shrinks toward zero. For example, if p = 4 and m = 32, the bubble fraction is 3 / (32 + 3) \approx 8.6\%.

The GPipe memory explosion

While GPipe reduces the idle bubble, it creates an unsustainable activation memory bottleneck. Under backpropagation, computing weight gradients during B_k requires the exact input activations saved during F_k (see Lesson 3, Training Memory). Because GPipe executes all m forward micro-batches before executing a single backward pass, stage 0 must store the intermediate activations for all m micro-batches simultaneously in High Bandwidth Memory (HBM).

As we increase m to reduce the bubble fraction, the activation footprint on stage 0 scales linearly as \mathcal{O}(m). For large transformer models with sequence lengths of 8,192 tokens, buffering activations for 32 or 64 micro-batches requires hundreds of gigabytes per GPU, causing immediate Out-Of-Memory (OOM) crashes. GPipe forces a punishing trade-off: choose a small m and waste 30–50% of compute in pipeline bubbles, or choose a large m and run out of memory.

1F1B (PipeDream-Flush): Capping activations at O(p)

To eliminate GPipe's memory explosion, Narayanan et al. introduced the 1F1B (One-Forward-One-Backward) schedule in PipeDream and PipeDream-Flush [2], [3]. The core insight of 1F1B is simple: as soon as a downstream stage finishes a forward pass on a micro-batch, the pipeline should prioritize running the corresponding backward pass so that intermediate activations can be freed immediately.

Timeline for p = 4 stages and m = 8 micro-batches under 1F1B. Stage k executes p − k forward micro-batches during warmup. In the steady state, each stage alternates one forward pass with one backward pass. Peak activation memory is strictly capped at p micro-batches.

The 1F1B schedule operates in three distinct phases:

  1. Warmup phase: Pipeline stages ramp up sequentially. Stage k (where k \in [0, p-1]) executes exactly p - k forward micro-batches. On stage 0, this means executing p forwards (F_1, F_2, \dots, F_p). At that point, the first micro-batch F_1 has reached the final stage p - 1, which immediately computes backward pass B_1 and sends the activation gradient upstream.
  2. Steady-state phase (1F1B): Each stage alternates strictly between executing one backward pass and one forward pass. On stage 0, computing B_1 consumes and frees the activations stored for F_1. Stage 0 then immediately executes F_{p+1}. Because every forward pass is preceded by a backward pass that frees an older micro-batch, the number of in-flight micro-batches held in memory never exceeds p.
  3. Cooldown phase: Once all m forward micro-batches have been evaluated, the remaining micro-batches drain through backward passes (B_{m-p+1} to B_m) until the pipeline is empty.

Because the startup and drain latencies are identical to GPipe, the 1F1B schedule preserves the exact same bubble fraction:

\text{Bubble Fraction}_{\text{1F1B}} \approx \frac{p - 1}{m + p - 1}

However, peak activation memory on stage 0 drops from \mathcal{O}(m) down to \mathcal{O}(p). Because p is typically fixed between 4 and 16 while m can scale to 64 or 128, 1F1B allows scaling to large micro-batch counts without exceeding GPU memory capacity.

Advanced Schedules: Interleaving and Zero-Bubble

Interleaved / virtual stages in Megatron-LM

When training with a large pipeline depth (such as p = 8 or p = 16), requiring m \ge 8p forces m \ge 64 or m \ge 128. As we will see, large micro-batch counts inflate the global batch size beyond what optimizer convergence allows. To reduce the bubble fraction without requiring massive micro-batch counts, Narayanan et al. developed interleaved pipeline parallelism (also known as virtual stages) in Megatron-LM [4].

Four physical GPUs hosting two virtual stages each (v = 2), creating eight total model chunks. GPU 0 hosts Chunk 0 (layers 0–3) and Chunk 4 (layers 16–19). Activations loop back through the GPUs a second time, cutting the startup and drain bubble durations by roughly 2×.

Instead of assigning a single contiguous block of L / p layers to each GPU, the model is split into p \times v smaller virtual chunks, where v is the virtual stage factor (typically v = 2 or v = 4). Each physical GPU hosts v non-contiguous chunks:

  • GPU 0 hosts Chunk 0 (layers 0–3) and Chunk 4 (layers 16–19).
  • GPU 1 hosts Chunk 1 (layers 4–7) and Chunk 5 (layers 20–23).
  • GPU 2 hosts Chunk 2 (layers 8–11) and Chunk 6 (layers 24–27).
  • GPU 3 hosts Chunk 3 (layers 12–15) and Chunk 7 (layers 28–31).

During the forward pass, micro-batch 1 flows through Chunk 0 (on GPU 0), Chunk 1 (on GPU 1), Chunk 2 (on GPU 2), and Chunk 3 (on GPU 3). It then loops back to GPU 0 to process Chunk 4, continuing through Chunks 5, 6, and 7 on GPUs 1, 2, and 3. Because each individual chunk contains only L / (p \cdot v) layers, the forward and backward computation time per chunk is scaled down by 1/v. Consequently, the time required for a micro-batch to traverse from the first GPU to the last GPU shrinks by roughly v\times.

The resulting bubble fraction for interleaved 1F1B is approximately:

\text{Bubble Fraction}_{\text{interleaved}} \approx \frac{1}{v} \cdot \frac{p - 1}{m + p - 1} \approx \frac{p - 1}{v \cdot m}

For p = 4, m = 8, and v = 2, the bubble drops from 27.3% down to approximately 15.8% without changing the batch size. The penalty is network communication: because activations must pass between GPUs v times rather than once, point-to-point communication volume increases by exactly v\times. Interleaving pays off when network interconnects have sufficient bandwidth headroom to absorb the extra traffic.

Zero-bubble pipeline parallelism

In 2024, Qi et al. introduced Zero-Bubble Pipeline Parallelism (ICLR 2024) [5]. While GPipe and 1F1B treat the backward pass of a micro-batch as an atomic unit B, backpropagation actually consists of two mathematically distinct operations:

  1. Activation gradient pass (B_A): Evaluates \partial \mathcal{L} / \partial X = (\partial \mathcal{L} / \partial Y) W^\top. This computes the gradients with respect to the input activations of the layer. This tensor must be sent upstream to stage k - 1 so that stage k - 1 can continue its backward pass. B_A is on the latency-critical path.
  2. Weight gradient pass (B_W): Evaluates \partial \mathcal{L} / \partial W = (\partial \mathcal{L} / \partial Y)^\top X. This computes the gradients with respect to the layer's local weights. These gradients are accumulated locally in the GPU's gradient buffer for the eventual optimizer step; B_W is never transmitted to another GPU.
In standard 1F1B, monolithic backward computation B combines activation gradients (BA) and weight gradients (BW), forcing upstream stages to idle. Zero-bubble schedules decouple BA and BW. BA executes immediately on the critical path, while BW is postponed and scheduled into idle bubble slots, driving bubble overhead below 5%.

Because B_W is required only at the end of the step when the optimizer updates weights, it does not need to execute immediately after B_A. The zero-bubble scheduler decouples backpropagation into two distinct tasks: it schedules B_A immediately to unblock upstream stages, while postponing B_W to execute inside what would otherwise be idle bubble slots during the pipeline drain.

In standard transformer layers, B_W accounts for roughly half of the total backward compute time (t_B = t_{BA} + t_{BW}, with t_{BA} \approx t_F and t_{BW} \approx t_F). By moving B_W into the idle bubbles of the warmup and drain phases, zero-bubble schedules (such as ZB1P and ZBV) drive the pipeline bubble fraction down to under 5%, unlocking 20–30% higher training throughput compared to standard 1F1B [5]. The trade-off is memory: because computing B_W requires input activations X, intermediate activations must be retained slightly longer until the deferred B_W pass completes, increasing activation memory by 15–25%.

Network Communication: Why PP Crosses Nodes Better Than TP

Deriving point-to-point activation traffic

To understand why pipeline parallelism is the preferred strategy for multi-node model partitioning, we quantify the exact data volume transferred across stage boundaries. Between stage k and stage k + 1, the forward pass transmits the hidden activation tensor emerging from layer L / p - 1. For a micro-batch of size b, sequence length s, and hidden dimension h, the activation tensor has shape [b, s, h].

In 16-bit precision (BF16 or FP16), each element requires 2 bytes. The forward transfer volume per micro-batch is:

\text{P2P Activation Bytes} = b \times s \times h \times 2\text{ bytes}

During the backward pass, stage k + 1 transmits the activation gradient \partial \mathcal{L} / \partial X back to stage k. This gradient tensor has the exact same shape [b, s, h] and precision, requiring the identical number of bytes.

Let us evaluate this transfer volume for our running scenarios with micro-batch size b = 1 and sequence length s = 8,192:

  • Llama 3.1 8B (h = 4,096): 1 \times 8,192 \times 4,096 \times 2\text{ bytes} = 67,108,864\text{ bytes} = 64\text{ MiB} \approx 67.11\text{ MB}
  • Llama 3.1 70B (h = 8,192): 1 \times 8,192 \times 8,192 \times 2\text{ bytes} = 134,217,728\text{ bytes} = 128\text{ MiB} \approx 134.22\text{ MB}

On a modern cluster equipped with 400 Gb/s InfiniBand NDR (providing \approx 50\text{ GB/s} of effective unidirectional bandwidth per GPU), transmitting 67.11 MB takes:

t_{\text{transfer}} = \frac{67.11 \times 10^6\text{ bytes}}{50 \times 10^9\text{ bytes/s}} \approx 1.34 \times 10^{-3}\text{ s} = 1.34\text{ ms}

For Llama 3.1 70B, transmitting 134.22 MB takes approximately 2.68 ms. Evaluating the forward pass of an 8-layer or 10-layer transformer stage on an H100 GPU takes roughly 30 to 50 ms. Because the 1.34–2.68 ms network transfer time is less than one-tenth of the layer compute time, point-to-point communication can be completely overlapped behind computation using asynchronous CUDA streams (torch.cuda.Stream).

PP versus TP network traffic comparison

Figure 7 contrasts the communication patterns of Pipeline Parallelism and Tensor Parallelism.

Tensor Parallelism executes two collective All-Reduces per layer (64 per step), making it disastrous across high-latency inter-node networks. Pipeline Parallelism communicates only once per stage boundary via point-to-point transfers (1.34 ms transfer over InfiniBand), which overlaps easily behind 30–50 ms of stage compute.

In Tensor Parallelism, the GPU must perform an All-Reduce after the multi-head attention projection and another All-Reduce after the MLP projection in every single layer. For a 32-layer model, that represents 64 collective All-Reduce operations per micro-batch. Each collective requires multi-stage network handshakes and ring or tree reductions. Over an inter-node InfiniBand fabric, latency accumulation and synchronization jitter stall the tensor cores at every layer.

In Pipeline Parallelism, communication occurs only at stage boundaries. For p = 4, there are exactly 3 boundary interfaces in the entire model. At each boundary, communication is peer-to-peer between exactly two GPUs, requiring no multi-party barrier synchronizations. This structural difference explains the universal architectural guideline in distributed training: confine Tensor Parallelism to the high-bandwidth NVLink domain inside a node, and use Pipeline Parallelism to cross inter-node network fabrics.

Memory per Stage and Load Balancing

Memory breakdown across pipeline stages

Under 1F1B, the memory footprint on each GPU divides into static states and dynamic activation buffers:

  1. Model and optimizer states: Each stage holds L / p layers. For an N-parameter model in mixed-precision Adam, each stage holds (N / p) \times 16\text{ bytes}. Sharding across p stages reduces static memory by exactly 1/p.
  2. Activation memory: Under 1F1B, stage k holds at most p - k micro-batches of in-flight activations during the steady state. Stage 0 holds p micro-batches, stage 1 holds p - 1, and the final stage p - 1 holds exactly 1 micro-batch.

This creates a pronounced memory asymmetry across the cluster: stage 0 carries the heaviest activation memory burden, while stage p - 1 carries the lightest.

Boundary asymmetry: Token embeddings and the LM head

In addition to activation buffers, the first and last stages host specialized parameter layers that internal stages do not carry:

  • Stage 0 (Input stage): Hosts the token embedding table. For modern tokenizers with large vocabularies (such as Llama 3.1's vocabulary of V = 128,256 tokens and hidden dimension h = 4,096), the embedding tensor alone contains 128,256 \times 4,096 \approx 525\times 10^6 parameters (0.525B). In 16-byte Adam, this single tensor requires 8.4\text{ GB} of GPU memory. Furthermore, stage 0 buffers p in-flight micro-batches.
  • Stage p - 1 (Output stage): Hosts the final RMSNorm, the Language Model (LM) head projection, and the cross-entropy loss computation. The LM head shares the same shape [h, V] as the embedding table, adding another 0.525B parameters (8.4 GB of static memory). In addition, computing cross-entropy loss over a vocabulary of 128,256 requires projecting activations into a massive logit tensor of shape [b, s, V], consuming significant transient memory and compute.
  • Intermediate stages: Host only standard transformer blocks with uniform memory and compute footprints.

If an engineering team partitions layers strictly uniformly (e.g., dividing 32 layers into 8 layers per stage across 4 stages), stages 0 and 3 will execute slower and consume more memory than stages 1 and 2. Because a pipeline runs at the speed of its slowest stage, load imbalance directly inflates the pipeline bubble.

To restore balance, large-scale training frameworks employ non-uniform layer partitioning [4]. Instead of allocating an equal number of layers per stage, stages 0 and p - 1 are assigned fewer transformer layers than intermediate stages. For example, in a 32-layer model distributed across 4 stages, the partition might assign 7 layers to stage 0, 9 layers to stage 1, 9 layers to stage 2, and 7 layers to stage 3 (7 + 9 + 9 + 7 = 32). The reduced layer count on the boundary stages compensates for the embedding table, LM head, and loss computation, equalizing per-stage execution times and memory allocations.

Interaction with Batch Size and Gradient Accumulation

Pipeline parallelism cannot be tuned in isolation; it is coupled directly to the global batch size. In distributed training, the global batch size in sequences (B_{\text{seq}}) is governed by the product of micro-batch size b, micro-batch count m, and the Data Parallel degree (\text{DP}):

B_{\text{seq}} = m \times b \times \text{DP}

Multiplying by sequence length s gives the global batch size in tokens:

B_{\text{tokens}} = m \times b \times \text{DP} \times s

In our pretraining run on 256 H100 GPUs, the global batch size is targeted at 4 million tokens (512 sequences of s = 8,192). If an engineer configures pipeline parallelism with depth p = 8, keeping the bubble fraction under 15% requires m \ge 4p = 32 micro-batches. With micro-batch size b = 1, the batch size required per data-parallel replica is:

B_{\text{per-replica}} = m \times b = 32 \times 1 = 32\text{ sequences} = 262,144\text{ tokens}

If the cluster runs 16 data-parallel replicas (\text{DP} = 16, using 8 \times 16 = 128 GPUs), the global batch size becomes:

B_{\text{global}} = 32 \times 16 = 512\text{ sequences} \approx 4.19 \times 10^6\text{ tokens}

This matches our 4M token target. However, suppose the team attempts to scale to a larger cluster of 1,024 GPUs while maintaining the same 4M token global batch size. With p = 8, the data parallel degree would increase to \text{DP} = 1,024 / 8 = 128. To keep the global batch size at 512 sequences, the micro-batch count m would be forced down to:

m = \frac{B_{\text{global}}}{\text{DP} \times b} = \frac{512}{128 \times 1} = 4\text{ micro-batches}

Plugging p = 8 and m = 4 into our bubble formula reveals a catastrophic result:

\text{Bubble Fraction} = \frac{8 - 1}{4 + 8 - 1} = \frac{7}{11} \approx 63.6\%

More than 63% of the cluster sits completely idle! This dynamic demonstrates a fundamental scaling constraint: pipeline parallelism cannot scale indefinitely on fixed global batch sizes. When the cluster expands, increasing the data parallel degree forces micro-batch count m to shrink, which inflates the pipeline bubble. If you attempt to prevent the bubble by keeping m = 32, the global batch size balloons to 33 million tokens, exceeding the critical batch size and severely degrading optimizer convergence efficiency [6].

Where does pipeline parallelism help?

For our running pretraining scenario with Llama 3.1 8B on 256 H100 GPUs, pipeline parallelism should not be used. The 8B model requires only 128.5 GB of static states. Across eight GPUs in an NVLink node, FSDP shards this to approximately 16 GB per GPU, leaving over 60 GB of memory for activations. Hybrid Sharded Data Parallel (HSDP) across the 32 nodes provides 100% compute efficiency with zero pipeline bubbles. Introducing pipeline parallelism for an 8B model adds unnecessary bubble latency, micro-batch tuning overhead, and load imbalance for zero memory benefit.

In contrast, for 70B and 405B models, pipeline parallelism becomes indispensable. For Llama 3.1 70B, static states require 1,130 GB. Tensor Parallelism is capped at 8 to remain within the NVLink domain of a single node. Sharding the remaining layers across nodes requires either inter-node FSDP or Pipeline Parallelism. Because inter-node FSDP all-gathers saturate multi-node InfiniBand networks, production configurations universally combine \text{TP} = 8 inside each node with \text{PP} = 4 or \text{PP} = 8 across nodes, achieving balanced memory distribution and manageable point-to-point network traffic.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Asynchronous 1F1B (PipeDream): The original PipeDream system avoided the pipeline flush entirely by letting backward passes update weights asynchronously using weight stashing [2]. While this achieved 0% bubble overhead, staleness gradients harmed optimizer convergence on large language models; modern production pipelines universally use synchronous 1F1B with flushes (PipeDream-Flush).
  • Activation recomputation inside stages: Combining pipeline parallelism with activation checkpointing allows each stage to drop intermediate activation tensors, storing only the inputs to each transformer block. This drops activation memory per stage by over 80% at the cost of 33% extra forward compute (see Lesson 3, Training Memory).
  • Handling tied embeddings: In models where the input embedding matrix and the output LM head matrix share the same weights (tied embeddings), stage 0 and stage p - 1 must synchronize embedding weight gradients via an extra point-to-point All-Reduce at each optimizer step. Modern LLMs (including Llama 3) decouple the embedding and LM head weights to eliminate this cross-stage gradient synchronization.
  • Dynamic micro-batch sizing: For models with extreme sequence length variance, fixed micro-batch counts lead to bubbles due to differing token counts per batch. Systems such as Megatron-LM pack tokens into uniform 1D buffers to ensure each micro-batch has identical computational work.
  • PyTorch PiPPy compiler tracing: PyTorch's torch.distributed.pipelining uses FX graph symbolic tracing to automatically detect stage boundaries and slice arbitrary nn.Module graphs into balanced pipeline stages without manual refactoring.
  • DualPipe in DeepSeek-V3: DeepSeek-V3 introduced a bidirectional pipeline schedule called DualPipe that overlaps the forward and backward computation of two independent micro-batch streams, driving bubble fraction down while maintaining exact numerical consistency [9].

Summary

Mind map summarizing the pipeline parallelism lesson: stage partitioning, bubble arithmetic, GPipe vs 1F1B scheduling, zero-bubble execution, and network trade-offs.
  • Pipeline parallelism partitions a model vertically by layers across sequential stages, communicating activations forward and gradients backward only at stage boundaries.
  • Naive execution leaves (p - 1) / p of GPU time idle (75% for 4 stages). Micro-batching streams smaller chunks to overlap computation across stages.
  • The pipeline bubble fraction is analytically (p - 1) / (m + p - 1). Maintaining an idle bubble under 15% requires micro-batch count m \ge 4p to 8p.
  • GPipe executes all forward micro-batches before backward passes, creating an unsustainable \mathcal{O}(m) activation memory bottleneck. 1F1B alternates forwards and backwards in steady state, capping peak activations at \mathcal{O}(p).
  • Interleaved stages (Megatron-LM) cut the bubble duration by 1/v at the cost of v\times higher point-to-point network traffic. Zero-bubble schedules decouple backward passes into latency-critical activation gradients (B_A) and deferred weight gradients (B_W) to fill idle bubbles.
  • Point-to-point activation traffic is shape [b, s, h] (67 MB for 8B, 134 MB for 70B in BF16). On 400 Gb/s InfiniBand, transfers take 1.3–2.7 ms and hide completely behind stage computation, making PP ideal for crossing inter-node fabrics.
  • Pipeline parallelism is unnecessary for 8B models (which fit under pure FSDP/HSDP), but essential for 70B+ models where Tensor Parallelism is confined to an 8-GPU node.

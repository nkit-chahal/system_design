Introduction

In standard transformer training, every parameter in the neural network participates in the computation of every single token. As models scale from 8 billion to 70 billion and 405 billion parameters, the floating-point operations (FLOPs) required per token scale linearly with parameter count. This coupling creates a harsh computational ceiling: training a dense 405B model requires tens of thousands of GPUs running for months, consuming tens of millions of dollars of electricity and compute (see Lesson 7, Training FLOPs, Time and MFU).

Mixture-of-Experts (MoE) breaks this linear coupling by replacing dense feed-forward networks (MLPs) with a set of E independent "experts", coordinated by a lightweight parametric router [1]. For each incoming token, the router evaluates the token's hidden state and dynamically activates only the top-k most relevant experts (typically k = 1 or k = 2 out of E = 8 or E = 16). The remaining E - k experts sit completely idle for that token. This architectural sparsity enables a model to expand its total parameter capacity by 4× to 10× while holding the compute FLOPs per token strictly constant.

In Inference Lesson 35, Mixture-of-Experts Serving, we examined how MoE models are served in production, focusing on KV cache sizing, weight offloading, and batched decode throughput. Training an MoE model, however, introduces fundamentally different systems and algorithmic challenges that do not exist in inference.

Comparison of MoE requirements in inference vs training. Inference executes read-only forward passes where idle experts cost zero compute. Training requires backpropagating through non-differentiable routing decisions, executing four All-to-All collectives per step, storing 16 bytes/param Adam states for all experts, and stabilizing router load balancing.

During training, the system cannot treat idle experts as free. In mixed-precision Adam, every parameter across all E experts requires 16 bytes of memory for weights, gradients, master weights, and optimizer moments, regardless of how rarely that expert is selected (see Lesson 3, Training Memory). Furthermore, the router's gating parameters must learn via backpropagation, creating severe optimization pathologies such as router collapse where a few popular experts monopolize all tokens. Distributing experts across devices via Expert Parallelism (EP) requires four high-volume All-to-All communication collectives on every training step [7], [8]. In this lesson, we examine the mechanics of training MoE models, analyze load-balancing objectives and dropless execution, derive the All-to-All network traffic, explore DeepSeek-V3's auxiliary-loss-free balancing, and determine how to train an MoE version of our running model.

Clarifying the Problem

In machine learning infrastructure interviews, Mixture-of-Experts questions focus on routing differentiability, load balancing losses, All-to-All interconnect scaling, and the asymmetry between compute FLOPs and memory footprint. Here is how a discussion between a candidate and an interviewer typically unfolds:

The active compute per token matches an 8B model (~8.03B active parameters), but total parameter capacity expands to approximately 22.5 billion parameters. Our cluster consists of 256 NVIDIA H100 80 GB GPUs across 32 nodes (NVLink inside each node, 400 Gb/s InfiniBand across nodes).

Candidate: What sequence length and batch size are specified for pretraining?
Interviewer: Sequence length is 8,192 tokens. Global batch size is 4 million tokens (512 sequences of 8,192).

Candidate: How should we distribute the experts across GPUs, and what communication pattern will that create?
Interviewer: We want to use Expert Parallelism (EP). How do the tokens move between GPUs during the forward and backward passes, what is the network traffic volume per step, and can our interconnect support it?

Candidate: What mechanisms should we implement to prevent the router from routing all tokens to the same two experts?
Interviewer: We need to evaluate the classic Switch Transformer auxiliary loss, the ST-MoE router z-loss, dropless token routing via MegaBlocks, and the auxiliary-loss-free dynamic bias strategy introduced by DeepSeek-V3. Which strategy prevents collapse without degrading language modeling accuracy?

The real question underneath is: How do we train a sparse MoE model where compute scales with active parameters but memory scales with total parameters, prevent routing collapse without corrupting the loss gradient, and orchestrate All-to-All communication over physical network fabrics? To answer it, we begin by analyzing the router's gradients and load balancing.

Router Gradients, Collapse, and Load Balancing

How router gradients flow

In a standard top-k MoE layer, let x \in \mathbb{R}^h represent a token's input hidden state, and let E be the total number of experts. The router computes a raw affinity logit H(x) \in \mathbb{R}^E using a linear projection with weight matrix W_g \in \mathbb{R}^{E \times h} [1]:

H(x) = W_g x

The router selects the indices of the k highest logits using the \text{TopK} operator:

\mathcal{T} = \text{TopK}(H(x), k)

The gating weights G(x) \in \mathbb{R}^E assigned to the selected experts are computed by applying a softmax function exclusively over the top-k logits (setting the gating values for all unselected experts to zero):

G_i(x) = \begin{cases} \frac{\exp(H_i(x))}{\sum_{j \in \mathcal{T}} \exp(H_j(x))} & \text{if } i \in \mathcal{T} \\ 0 & \text{otherwise} \end{cases}

The final output of the MoE layer y is the linear combination of the selected expert outputs weighted by their gating coefficients:

y = \sum_{i \in \mathcal{T}} G_i(x) \cdot \text{Expert}_i(x)

A central theoretical subtlety arises during backpropagation: the \text{TopK} selection operator is a discrete step function with zero derivative almost everywhere. The router cannot learn which experts to select via direct gradient descent on the discrete selection decision. Instead, gradients backpropagate through the continuous softmax gating coefficients G_i(x) [1], [2]:

\frac{\partial \mathcal{L}}{\partial W_g} = \sum_{i \in \mathcal{T}} \left(\frac{\partial \mathcal{L}}{\partial y} \cdot \text{Expert}_i(x)\right) \frac{\partial G_i(x)}{\partial H(x)} x^\top

If expert i produces an output that reduces the overall loss, the gradient pushes the router logit H_i(x) upward for similar tokens, making expert i more likely to be selected in future forward passes.

The pathology of router collapse

Because the router learns through this gradient feedback loop, unconstrained top-k routing suffers from severe positive feedback instability, known as router collapse (or representation collapse) [1], [2].

Left: Without load balancing, a positive feedback loop drives tokens onto Experts 0 and 1, leaving Experts 2 and 3 starved and untrained. Right: Switch Transformer auxiliary loss penalizes the product of discrete token dispatch fraction fi and continuous router probability Pi, forcing uniform allocation.

At the start of pretraining, weights are initialized randomly. By chance, expert 0 might receive slightly better initial weights than expert 1 for common grammatical tokens. The router routes more tokens to expert 0. As a consequence, expert 0 receives more gradient updates and improves faster than other experts. The router observes lower loss from expert 0 and increases its routing probabilities further. Within a few thousand training steps, the router collapses onto a small subset of experts (e.g., 2 out of 8), dispatching 95%+ of all tokens to those experts while the remaining experts receive zero tokens.

Router collapse is catastrophic for two reasons:

  1. Hardware underutilization: In distributed training, each expert is hosted on a different GPU. If 95% of tokens route to GPU 0, GPU 0 runs out of memory or compute capacity while the other 7 GPUs sit completely idle, collapsing cluster throughput.
  2. Capacity loss: The parameters in the starved experts are never trained, reducing a 22B-parameter MoE model to the effective representational capacity of an 8B model while still paying the memory overhead of all 22B parameters.

The Switch Transformer auxiliary load-balancing loss

To prevent router collapse, Fedus et al. introduced the canonical auxiliary load-balancing loss in Switch Transformers (JMLR 2022) [2]. The auxiliary loss adds a penalty to the training objective that punishes non-uniform token distributions across experts.

For a batch \mathcal{B} containing T total tokens across all data-parallel ranks, define two vectors across the E experts:

  1. Dispatch fraction vector (f \in \mathbb{R}^E): The actual fraction of tokens assigned to expert i by the discrete \text{TopK} selection: f_i = \frac{1}{k \cdot T} \sum_{x \in \mathcal{B}} \mathbb{1}\{i \in \text{TopK}(H(x), k)\} Because of the indicator function \mathbb{1}, f_i is discrete and non-differentiable.
  2. Probability fraction vector (P \in \mathbb{R}^E): The average router softmax probability assigned to expert i across all tokens in the batch: P_i = \frac{1}{T} \sum_{x \in \mathcal{B}} \text{Softmax}(H(x))_i Because it averages continuous softmax outputs before top-k truncation, P_i is smooth and differentiable.

The Switch Transformer auxiliary loss is the scaled dot product of these two vectors [2]:

\mathcal{L}_{\text{aux}} = \alpha \cdot E \sum_{i=1}^E f_i \cdot P_i

Where \alpha is an auxiliary loss hyperparameter, typically set to \alpha = 0.01 or 0.001. The scaling factor E ensures that under perfect uniform balance (where every f_i = 1/E and every P_i = 1/E), the loss evaluates to a constant:

\mathcal{L}_{\text{aux}}^{\text{uniform}} = \alpha \cdot E \sum_{i=1}^E \left(\frac{1}{E} \cdot \frac{1}{E}\right) = \alpha \cdot E \cdot E \cdot \frac{1}{E^2} = \alpha

If the router begins routing disproportionately to expert i, both f_i and P_i become large, causing their product f_i \cdot P_i to spike quadratically. Because P_i is differentiable, taking the derivative with respect to the router weights \partial \mathcal{L}_{\text{aux}} / \partial W_g provides strong, continuous gradient feedback that pushes probabilities away from overloaded experts and toward underutilized experts, enforcing balanced routing across the cluster.

Router z-loss in ST-MoE

In 16-bit mixed-precision training (BF16 or FP16), router projections introduce a subtle numerical instability. As training progresses, the logits H(x) = W_g x can drift to large absolute magnitudes (e.g., +50 or -80). While softmax is mathematically invariant to constant shifts, in floating-point arithmetic computing \exp(H_i(x)) with large positive logits causes numerical overflow (inf), while large negative logits produce subnormal underflow. This leads to NaN gradients that corrupt router weights.

To eliminate this instability, Zoph et al. introduced the router z-loss in ST-MoE (2022) [3]. The z-loss penalizes large values in the log-normalizer (log-sum-exp) of the router logits:

\mathcal{L}_z = \frac{c_z}{T} \sum_{j=1}^T \left( \log \sum_{i=1}^E \exp(H_{j,i}) \right)^2

Where c_z is a small weighting coefficient (typically c_z = 10^{-4} or 10^{-3}). The z-loss penalizes logits that drift far from zero without altering their relative ranking. ST-MoE demonstrated that adding the router z-loss eliminates loss spikes and allows stable long-duration pretraining without requiring manual gradient clipping or FP32 router casts [3].

Capacity factor, token dropping, and MegaBlocks

Even with an auxiliary load-balancing loss, token assignments fluctuate dynamically across micro-batches. On some batches, an expert might receive 12% of the tokens; on others, 18%. In early MoE implementations (such as Mesh-TensorFlow and Tutel), GPUs required rigid, static tensor dimensions to execute fast cuBLAS GEMM kernels [8].

To enforce static tensor dimensions, systems established a fixed expert capacity (C):

C = \text{Capacity Factor} \times \left(\frac{k \cdot B \cdot s}{E}\right)

Where the Capacity Factor (CF) is a slack hyperparameter (typically 1.0 to 1.5). This rigid capacity created a punishing dilemma:

  • Token dropping: If an expert received more tokens than its capacity C, the excess tokens were dropped—passed around the expert layer via residual connection without MLP processing. Dropping tokens degraded model reasoning and factual recall.
  • Padding waste: If an expert received fewer tokens than C, its input tensor was padded with zeros. A capacity factor of 1.5 wasted up to 33% of GPU memory and compute on dummy padding tokens.
Left: Rigid tensor shapes require a fixed capacity C. Overloaded experts drop excess tokens (degrading quality), while underloaded experts require zero-padding (wasting memory). Right: MegaBlocks (Gale et al., MLSys 2023) uses block-sparse GPU kernels to process variable token counts per expert with zero dropping and zero padding.

To solve this dilemma, Gale et al. developed MegaBlocks (MLSys 2023) [4]. MegaBlocks reformulates MoE computation as a block-sparse matrix multiplication (dMoE). Instead of padding ragged token counts into uniform dense tensors, MegaBlocks implements custom GPU kernels that execute directly on variable-length token assignments. Every expert computes on exactly the number of tokens routed to it. Token dropping is completely eliminated (\text{CF} = \infty), zero compute is wasted on padding, and end-to-end training throughput improves by up to 40%. Modern frontier MoE models (Mixtral 8x7B, DeepSeek-V3) universally operate dropless using block-sparse execution.

DeepSeek-V3's auxiliary-loss-free balancing

While the Switch Transformer auxiliary loss successfully prevents router collapse, it introduces an unavoidable quality penalty: the gradients of the auxiliary loss directly conflict with the gradients of the primary language modeling loss [6]. The auxiliary loss forces the router to dispatch tokens evenly across experts, even when a specific expert is genuinely superior for a given token. This trade-off forces practitioners to tune \alpha delicately: if \alpha is too small, the router collapses; if \alpha is too large, model perplexity degrades significantly.

To eliminate this fundamental trade-off, DeepSeek-AI introduced an auxiliary-loss-free load balancing strategy in the DeepSeek-V3 Technical Report (December 2024) [6]. Instead of adding penalty terms to the loss function, DeepSeek-V3 decouples load balancing entirely from backpropagation by introducing dynamic, expert-specific bias terms.

DeepSeek-V3 decouples routing from loss gradients. Top-K selection uses biased affinity scores (si + bi), while output gating uses clean unbiased scores si. Biases adjust dynamically after each step based on batch load (Δbi = −γ · load_diff), achieving perfect balance without corrupting model loss.

The mechanism operates in three steps:

  1. Biased top-k selection: When selecting which experts to activate, the router adds an expert-specific bias term b_i to each expert's raw affinity score s_i = x^\top e_i: \text{Selection Score}_i = s_i + b_i The top-k experts are selected based on these biased scores. If expert i has a positive bias b_i > 0, it is more likely to win selection; if b_i < 0, it is less likely.
  2. Unbiased gating weights: Crucially, the actual gating weights that scale the expert outputs are computed using the clean, unbiased affinity scores s_i: G_i(x) = \frac{\exp(s_i)}{\sum_{j \in \mathcal{T}} \exp(s_j)} Because b_i is omitted from the output coefficients, the bias terms do not distort the neural network's representations or gradient signals.
  3. Dynamic step-by-step bias updates (zero loss gradients): At the conclusion of each training step, the system measures the actual token count L_i dispatched to expert i across the batch. If expert i is overloaded (L_i > \text{Target}), its bias b_i is decremented by a fixed step size \gamma. If underloaded (L_i < \text{Target}), b_i is incremented: \Delta b_i = -\gamma \cdot \left(\frac{L_i}{\text{Target}} - 1\right)

Because the bias terms b_i are updated via algorithmic feedback rather than autograd backpropagation, not a single auxiliary loss gradient enters the model weights. DeepSeek-V3 demonstrated near-perfect load balance across 256 fine-grained routed experts with zero degradation in pretraining loss [6].

Expert Parallelism (EP) and All-to-All Communication

Sharding experts across devices

When training an MoE model, the E experts within each layer are sharded across E_p GPUs, where E_p is the Expert Parallel (EP) degree. In a typical configuration with E = 8 experts, E_p = 8, placing exactly one expert per GPU inside an 8-GPU node [7], [8].

Because each GPU hosts a different expert, tokens must be physically routed across GPUs based on the router's top-k decisions. This routing is executed via collective All-to-All (A2A) communication.

An MoE layer partitioned across four GPUs (EP = 4). Forward pass executes Local Routing, Forward Dispatch (A2A #1), Local Expert Compute, and Forward Combine (A2A #2). Backpropagation executes Backward Dispatch (A2A #3) and Backward Combine (A2A #4). Every training step requires four All-to-All collectives per MoE layer.

The Four All-to-All collectives per training step

In standard dense training, a layer requires communication only during the backward pass (for data-parallel gradient synchronization) or within the layer (for tensor-parallel All-Reduces). In Expert Parallelism, communication occurs in both forward and backward passes, totaling four All-to-All collectives per MoE layer on every training step:

  1. Forward Dispatch (All-to-All #1): Each GPU routes its local tokens. If token t selects expert e located on GPU j, the hidden state vector of token t (shape [h]) is transmitted from GPU i to GPU j. Every GPU sends and receives slices of tokens to and from all other GPUs in the EP group.
  2. Forward Combine (All-to-All #2): After each GPU executes its local expert MLP on its gathered tokens, the resulting output activation vectors (shape [h]) must be sent back to the tokens' originating GPUs. Originating GPUs receive the outputs, multiply them by their gating coefficients G_i(x), and accumulate them into the residual stream.
  3. Backward Dispatch (All-to-All #3): During backpropagation, the gradients of the loss with respect to the expert outputs (\partial \mathcal{L} / \partial y) are generated on the originating GPUs. These activation gradient vectors must be dispatched back to the GPUs hosting the respective experts so that local expert backward passes can compute weight gradients \partial \mathcal{L} / \partial W_e.
  4. Backward Combine (All-to-All #4): After local expert backward execution, the gradients with respect to the expert inputs (\partial \mathcal{L} / \partial x) are gathered back to the originating GPUs to propagate gradients through the attention block and earlier layers.

Worked traffic arithmetic: Mixtral 8x7B

To quantify the network bandwidth demanded by Expert Parallelism, we evaluate the exact data volume transferred across the four All-to-All collectives. Consider a model with the architecture of Mixtral 8x7B [5]:

  • Layers: L = 32
  • Hidden dimension: h = 4,096
  • Experts per layer: E = 8, top-2 routing (k = 2)
  • Expert Parallel degree: E_p = 8 (1 expert per GPU across 8 GPUs)
  • Micro-batch size: b = 1, sequence length: s = 8,192 tokens
  • Precision: BF16 (2 bytes per element)

For one micro-batch on one GPU, the number of input tokens is b \times s = 8,192\text{ tokens}. Because each token selects k = 2 experts, the GPU must dispatch 2 \times 8,192 = 16,384\text{ token vectors}. Each token vector contains h = 4,096\text{ elements} \times 2\text{ bytes} = 8,192\text{ bytes} (8 KiB).

The total data volume sent by each GPU in a single All-to-All dispatch is:

\text{A2A Volume per Layer} = k \times b \times s \times h \times 2 = 2 \times 1 \times 8,192 \times 4,096 \times 2 = 134,217,728\text{ bytes} = 128\text{ MiB} \approx 134.22\text{ MB}

Across the four All-to-All collectives (Forward Dispatch, Forward Combine, Backward Dispatch, Backward Combine), each GPU transmits and receives:

\text{Per-Layer Step Traffic} = 4 \times 134.22\text{ MB} = 536.87\text{ MB}

Multiplying across all 32 transformer layers yields the total All-to-All communication volume per GPU per micro-batch:

\text{Total EP Comm per Step} = 32 \times 536.87\text{ MB} \approx 17.18 \times 10^9\text{ bytes} \approx 17.18\text{ GB}

Now consider how this 17.18 GB traffic interacts with physical network fabrics:

  • Intra-node NVLink (900 GB/s per GPU): t_{\text{NVLink}} = \frac{17.18\text{ GB}}{900\text{ GB/s}} \approx 0.0191\text{ s} \approx 19.1\text{ ms} Across an entire training step lasting 400–600 ms, 19 ms of communication takes less than 4% of step time and is easily hidden by overlapping All-to-All transfers with attention computation using CUDA streams.
  • Inter-node InfiniBand (50 GB/s per GPU): t_{\text{InfiniBand}} = \frac{17.18\text{ GB}}{50\text{ GB/s}} \approx 0.344\text{ s} = 344\text{ ms} Transmitting 17.18 GB over InfiniBand consumes 344 ms—more than half of the total step time!

This stark arithmetic yields a vital architectural rule: Expert Parallelism should be confined to the ultra-high-bandwidth NVLink domain inside an 8-GPU server node (\text{EP} \le 8). Spanning Expert Parallelism across inter-node InfiniBand fabrics floods network switches with all-to-all traffic and collapses hardware efficiency.

The Fundamental MoE Asymmetry: Active FLOPs vs Total Memory

In dense transformer models, compute and memory scale proportionally: an 8B model requires 8B FLOPs of active compute per token and 128.5 GB of Adam memory; a 70B model requires ~8.7× more compute and ~8.7× more memory. In Mixture-of-Experts models, this proportionality shatters.

Training FLOPs scale with active parameters (6 × N_active × D), but GPU Adam memory scales with total parameters (16 × N_total bytes). Mixtral computes like a 13B model but requires the memory of a 47B model. DeepSeek-V3 computes like a 37B model but requires 10.7 TB of memory.

The mathematical governing laws of MoE pretraining are:

  1. Training Compute FLOPs scale strictly with active parameters (N_{\text{active}}): \text{Training FLOPs} \approx 6 \times N_{\text{active}} \times D Where D is the dataset token count. Because unselected experts do not compute on a given token, they consume zero floating-point operations.
  2. Training GPU Memory scales strictly with total parameters (N_{\text{total}}): \text{Static Adam Memory} = 16 \times N_{\text{total}}\text{ bytes} Every parameter across all E experts must reside in GPU memory alongside its BF16 gradient (2B), FP32 master weight (4B), and FP32 Adam first and second moments (8B). An idle expert takes the exact same memory footprint as a heavily utilized expert.

Combining EP with DP, TP, and PP

Layer-by-layer parallel composition

Because an MoE transformer contains both dense layers (self-attention, RMSNorm, embeddings) and sparse layers (MoE MLPs), the parallelization strategy shifts dynamically within each transformer block.

Dense self-attention layers execute under Data Parallelism (DP). Forward All-to-All Dispatch shifts token states into Expert Parallelism (EP), where each GPU evaluates its local expert. Forward All-to-All Combine returns computed outputs back to DP ranks for residual addition.
  • Attention blocks run under Data Parallelism (DP): In the self-attention block, parameters are shared across data streams. Each GPU in the node evaluates attention on its local micro-batch slice. If the model is large (such as DeepSeek-V3), attention can also be sharded using Tensor Parallelism (\text{TP}) or Multi-Head Latent Attention (MLA).
  • MLP blocks run under Expert Parallelism (EP): As tokens emerge from the post-attention LayerNorm, the router evaluates gating scores. The GPUs execute Forward All-to-All Dispatch, switching the communication domain from DP to EP. Each GPU processes its local expert on the gathered cross-rank tokens. Once expert MLPs evaluate, Forward All-to-All Combine returns outputs back to the original DP ranks to compute the residual addition.

How would we train an MoE version of our model?

To convert our running Llama 3.1 8B pretraining run on 256 H100 GPUs into an MoE model with matching token compute throughput, we adopt the following design:

  1. Architecture sizing:
    • Keep 32 layers, hidden dimension h = 4,096, 32 query heads, 8 KV heads.
    • Replace the dense MLP in each layer with E = 8 experts, with top-2 routing (k = 2).
    • To keep active compute identical to Llama 3.1 8B, each expert is sized with intermediate dimension d_{\text{ffn}} = 7,168 (half the dense 14,336 size). With k = 2 active experts, active parameters per token remain exactly 8.03\text{B}. Total parameter capacity expands to \approx 22.5\text{B} parameters.
  2. Parallel layout on 256 H100 GPUs (32 nodes × 8 GPUs): \text{EP} = 8 \text{ (intra-node over NVLink)}, \quad \text{DP} = 32 \text{ (inter-node over InfiniBand)}, \quad \text{TP} = 1, \quad \text{PP} = 1 Each 8-GPU node hosts all 8 experts for its local data stream (\text{EP} = 8). All-to-All dispatch and combine execute strictly across the 900 GB/s NVLink crossbar within each chassis, completing in under 20 ms. Across the 32 nodes, gradients for shared attention and router parameters synchronize via standard Data Parallel All-Reduce over InfiniBand.
  3. Algorithmic choices:
    • Use MegaBlocks dropless block-sparse execution to eliminate token dropping and padding waste.
    • Use DeepSeek-V3 dynamic bias balancing (s_i + b_i) paired with ST-MoE router z-loss (c_z = 10^{-4}) to maintain perfect expert balance and numerical stability without corrupting the language model loss.

In Practice

Compute router logits logits = self.router(x_flat) # [num_tokens, num_experts] # 2. Router z-loss (ST-MoE: penalize large logits to prevent overflow) logsumexp_logits = torch.logsumexp(logits, dim=-1) z_loss = self.z_loss_coeff * torch.mean(logsumexp_logits ** 2) # 3. Softmax probabilities across all experts (for aux loss and gating) probs = F.softmax(logits, dim=-1) # [num_tokens, num_experts] # 4. Top-2 Expert Selection top2_weights, top2_indices = torch.topk(probs, k=2, dim=-1) # Normalize top-2 weights so they sum to 1 top2_weights = top2_weights / (top2_weights.sum(dim=-1, keepdim=True) + 1e-9) # 5. Switch Transformer Auxiliary Load Balancing Loss # f_i: fraction of tokens routed to expert i mask = F.one_hot(top2_indices, num_classes=self.num_experts).sum(dim=1) # [tokens, experts] dispatch_fraction = mask.float().mean(dim=0) # [num_experts] prob_fraction = probs.mean(dim=0) # [num_experts] aux_loss = self.aux_loss_coeff * self.num_experts * torch.sum(dispatch_fraction * prob_fraction) # 6. Dispatch and combine token computations out = torch.zeros_like(x_flat) for expert_idx, expert in enumerate(self.experts): # Mask tokens routed to this expert (in position 0 or position 1) selected_pos0 = (top2_indices[:, 0] == expert_idx) selected_pos1 = (top2_indices[:, 1] == expert_idx) if selected_pos0.any(): tokens0 = x_flat[selected_pos0] weights0 = top2_weights[selected_pos0, 0:1] out[selected_pos0] += weights0 * expert(tokens0) if selected_pos1.any(): tokens1 = x_flat[selected_pos1] weights1 = top2_weights[selected_pos1, 1:2] out[selected_pos1] += weights1 * expert(tokens1) total_aux_loss = aux_loss + z_loss return out.view(orig_shape), total_aux_loss # Megatron-LM training launch flags for Expert Parallelism (EP) # 8 experts, top-2 routing, EP = 8 inside each 8-GPU node torchrun --nproc_per_node=8 --nnodes=32 pretrain_gpt.py \ --num-layers 32 \ --hidden-size 4096 \ --num-attention-heads 32 \ --seq-length 8192 \ --max-position-embeddings 8192 \ --micro-batch-size 1 \ --global-batch-size 512 \ --tensor-model-parallel-size 1 \ --pipeline-model-parallel-size 1 \ --expert-model-parallel-size 8 \ --num-experts 8 \ --moe-router-topk 2 \ --moe-router-load-balancing-type aux_loss \ --moe-aux-loss-coeff 0.01 \ --moe-z-loss-coeff 1e-4 \ --moe-token-dispatcher-type alltoall \ --bf16

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Shared experts in DeepSeekMoE: In addition to routed experts, DeepSeekMoE isolates 1 or 2 "shared experts" that process every single token unconditionally. The shared experts capture common linguistic syntax and universal representations, leaving the routed experts free to specialize in domain-specific knowledge [6].
  • Hierarchical All-to-All for multi-node EP: When scaling to 64 or 256 experts, EP must cross server nodes. Hierarchical All-to-All breaks the collective into two stages: an intra-node All-to-All over NVLink, followed by an inter-node All-to-All over InfiniBand. This reduces cross-rack network congestion.
  • Fine-grained vs coarse-grained experts: Early MoE models used coarse experts (e.g., 8 large experts with top-1 or top-2). Modern models (such as DeepSeek-V3) favor fine-grained architectures: 256 small experts with top-8 routing. Fine-grained experts allow exponentially more combinatorial routing patterns while maintaining identical active compute.
  • Expert specialization analysis: Contrary to early intuitions, empirical studies show that individual experts do not specialize strictly in semantic domains (e.g., "math" or "history"). Instead, experts specialize in syntactic structure, token frequencies, and morphological patterns across diverse text.
  • MoE checkpoint size during distributed save: Saving an MoE checkpoint with 671 billion parameters in FP32 master weights requires 2.7 terabytes of disk space. Distributed checkpointing frameworks (PyTorch DCP) write each expert shard directly from its host GPU in parallel to distributed storage, avoiding host-memory serialization bottlenecks.
  • Expert parallelism combined with Tensor Parallelism (TP + EP): When individual experts are large, a single expert can be sharded across multiple GPUs using Tensor Parallelism inside each node, while different experts are partitioned across nodes using Expert Parallelism.

Summary

Mind map summarizing the expert parallelism lesson: router gradients, load balancing losses, dropless MegaBlocks execution, DeepSeek-V3 dynamic biases, and All-to-All communication.
  • Mixture-of-Experts (MoE) decouples model capacity from compute cost by activating only top-k experts per token, but introduces memory, routing gradient, and interconnect challenges absent in inference.
  • Router gradients flow through continuous softmax coefficients into router weights W_g. Without constraints, positive feedback causes router collapse onto a few popular experts.
  • The Switch Transformer auxiliary loss (\alpha E \sum f_i P_i) forces uniform token allocation, while the ST-MoE router z-loss penalizes large logits to eliminate numerical overflow in BF16.
  • MegaBlocks dropless MoE eliminates token dropping and padding waste by reformulating MoE as block-sparse matrix multiplications (dMoE).
  • DeepSeek-V3 achieves auxiliary-loss-free load balancing by adding dynamic biases (s_i + b_i) to selection scores while calculating gating weights with unbiased scores, updating biases algorithmically with zero loss gradients.
  • Expert Parallelism requires four All-to-All collectives per MoE layer per step (forward dispatch/combine and backward dispatch/combine). Traffic is high (17.2 GB/step for Mixtral 8x7B) and must remain on intra-node NVLink (\text{EP} \le 8).
  • The fundamental MoE asymmetry: training compute scales strictly with active parameters (6 N_{\text{active}} D FLOPs), while GPU memory scales strictly with total parameters (16 N_{\text{total}} bytes for Adam).
  • To train an MoE version of our 8B model on 256 H100s, configure \text{EP}=8 within each node over NVLink and \text{DP}=32 across nodes over InfiniBand, with 8 experts and top-2 active.

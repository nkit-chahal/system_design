Introduction

When training a deep learning model across multiple GPUs, data parallelism is the foundational scaling paradigm. Historically, Distributed Data Parallel (DDP) has been the standard choice [1]. In DDP, every GPU holds an identical, complete copy of the model weights, gradients, and optimizer states, dividing the global batch across GPUs and synchronizing parameter gradients during backpropagation via an asynchronous ring all-reduce.

However, as models scale into billions of parameters, DDP encounters a fatal architectural limitation: because every GPU must store the full 16 bytes per parameter demanded by mixed-precision AdamW (see Lesson 3, Training Memory), models larger than approximately 5 billion parameters cannot train on an 80 GB GPU under DDP. Fully Sharded Data Parallel (FSDP) [2], [3], and its next-generation native implementation FSDP2 (via fully_shard) [4], solves this limitation by partitioning weights, gradients, and optimizer states across the data-parallel ranks. FSDP dramatically reduces per-GPU static memory at the cost of introducing additional collective communication: all-gathering layer weights on demand during both the forward and backward passes.

Experimental testbed comparing DDP and FSDP2 under identical training workloads. Under DDP (Engine A), model states are fully replicated on each GPU, and only gradients are synchronized via all-reduce during the backward pass. Under FSDP2 (Engine B), model weights, gradients, and optimizer states are sharded across ranks; layers are gathered dynamically during the forward and backward passes. Both scripts are orchestrated with torchrun and instrumented with PyTorch Profiler to capture NCCL communication kernels.

In this lab, we build two complete, production-grade distributed training scripts—one using standard DDP and one using PyTorch's native FSDP2 fully_shard API. We execute both on the exact same model, measure peak GPU memory allocation using torch.cuda.max_memory_allocated(), profile step latency and tokens/second throughput, capture PyTorch Profiler traces to visualize communication and compute overlap, and examine the core engineering pitfalls: wrapping policies, mixed precision configuration, and NCCL tuning.

Step 1: Predict Memory and Communication from First Principles

Before launching benchmarks, we calculate the theoretical memory footprint and network communication volume for both paradigms using the formulas from Lesson 3, Training Memory and Lesson 10, Data Parallelism and All-Reduce.

1. Memory accounting: Replicated vs Sharded states

In standard mixed-precision training with BF16 and AdamW, every parameter requires 16 bytes of static state (2B weight + 2B gradient + 4B FP32 master weight + 8B Adam moments) [6]:

  • Small Path (354.82M parameters): Total static state is 354.82 \times 10^6 \times 16\text{ bytes} \approx 5.68\text{ GB} (5.29 GiB).
    • Under DDP (replicated): Both GPU 0 and GPU 1 store the full 5.68 GB of model and optimizer states.
    • Under FSDP2 (sharded across 2 GPUs): Static state is cut in half to 5.68 / 2 = \mathbf{2.84\text{ GB}} per GPU, saving 2.84 GB of physical VRAM. Active layer ungathered weights add an ephemeral buffer of only 354.82\text{M} / 24 \times 2\text{ bytes} \approx 29.6\text{ MB} during layer compute.
  • Full Path: 1B Model (1.00B parameters) on 8×H100: Total static state is 1.00 \times 10^9 \times 16\text{ bytes} = 16.00\text{ GB}.
    • Under DDP: Every GPU stores 16.00 GB.
    • Under FSDP2: Sharded state drops to 16.00 / 8 = \mathbf{2.00\text{ GB}} per GPU.
  • Full Path: 8B Model (Llama 3.1 8B, 8.03B parameters) on 8×H100: Total static state is 8.03 \times 10^9 \times 16\text{ bytes} = 128.48\text{ GB}.
    • Under DDP: Every GPU must store 128.48 GB of static state. Because an H100 SXM GPU provides only 79.6 GiB (~85.5 GB) of visible memory, DDP crashes with an immediate CUDA Out-Of-Memory error before allocating a single activation tensor!
    • Under FSDP2: Static state is sharded across the 8 GPUs: 128.48 / 8 = \mathbf{16.06\text{ GB}} per GPU. Adding the active layer buffer (0.50 GB), activation checkpoints (~3.3 GB), and GEMM scratch (~5.0 GB), total memory per GPU is approximately 25 GB to 33 GB, fitting comfortably within 80 GB with over 47 GB of headroom!
Memory footprint comparison on 8×H100 GPUs for 1B and 8B models. For the 1B model, both DDP (19.5 GB peak) and FSDP (5.6 GB peak) fit easily within 80 GB. For the 8B model (Llama 3.1 8B), DDP requires 128.5 GB of baseline states and crashes immediately with an Out-Of-Memory failure. FSDP shards model and optimizer states across the 8 GPUs, consuming only 16.1 GB of static state and 28.6 GB total peak memory, leaving 51.4 GB of comfortable headroom.

2. Communication volume and pattern

While FSDP dramatically slashes memory, it changes the network communication profile [7]:

  • DDP Communication:
    • Forward Pass: Zero communication. Each GPU holds the complete set of parameters.
    • Backward Pass: As gradients are computed, DDP groups them into buckets (default 25 MB) and issues an asynchronous ring All-Reduce. Total collective volume sent and received per GPU is 2 \frac{N-1}{N} \times M, where M is the gradient tensor size (equal to model size in BF16).
  • FSDP2 Communication:
    • Forward Pass: Because weights are sharded, before executing Layer i, GPUs must execute an All-Gather collective to reconstruct full BF16 weights for that layer. Once Layer i finishes, the gathered weights are freed (resharded). Total forward communication is \frac{N-1}{N} \times M.
    • Backward Pass: Layer i must all-gather full weights a second time to compute input and parameter gradients: \frac{N-1}{N} \times M. Then, as gradients are computed, GPUs execute a Reduce-Scatter collective to sum gradients and shard them directly to the owning rank: \frac{N-1}{N} \times M.
    • Total FSDP Communication: \text{All-Gather (fwd)} + \text{All-Gather (bwd)} + \text{Reduce-Scatter (bwd)} = 3 \frac{N-1}{N} \times M.

Comparing the two formulas reveals the fundamental trade-off of state sharding: FSDP communicates exactly 1.5× (50% more) data per training step than DDP (3 \frac{N-1}{N} versus 2 \frac{N-1}{N}). Figure 3 visualizes this lifecycle.

In DDP, the forward pass involves zero network communication, and backward gradients are all-reduced concurrently with compute. In FSDP2, layer weights are all-gathered on demand in both forward and backward passes, followed by a reduce-scatter for gradients. FSDP transfers 50% more collective data per step than DDP, relying on fast interconnects (such as 900 GB/s NVLink) to hide communication behind GEMMs.

Step 3: Run FSDP2 Training

Next, we implement our FSDP benchmark using PyTorch's native FSDP2 API (torch.distributed.fsdp.fully_shard) [4]. Unlike legacy FSDP (which required complex auto_wrap_policy classes and wrapped whole submodules into monolithic wrappers), FSDP2 uses a clean, functional API that composes directly with PyTorch modules.

To configure FSDP2 correctly, we perform two critical actions:

  1. Configure MixedPrecisionPolicy: We set param_dtype=torch.bfloat16 to perform forward and backward computations in BF16, and reduce_dtype=torch.float32 to ensure numerical stability during gradient reduction.
  2. Block-Level Wrapping: We iterate over each individual transformer block in model.transformer.h and call fully_shard(block, mp_policy=mp_policy), before calling fully_shard(model, mp_policy=mp_policy) on the root container. This ensures that FSDP shards and un-shards at the layer boundary, freeing each layer's weights immediately after compute!

Interpreting the throughput vs scale crossover

Figure 5 diagrams how throughput (tokens/s per GPU) evolves across model sizes under DDP and FSDP2.

Illustrative throughput comparison across model scales from 350M to 8B parameters. For small models (< 1B), DDP delivers roughly 10% to 15% higher throughput because it incurs zero forward communication. For medium models (1B to 3B), FSDP achieves parity or higher throughput because freed VRAM allows increasing physical batch sizes. Beyond ~5B parameters, DDP crashes into an insurmountable Out-Of-Memory wall, whereas FSDP scales smoothly.

The scaling curve defines three distinct architectural regimes:

  1. Small-Model Regime (< 1B parameters): Model states (5.6 GB for 350M) are small relative to GPU capacity. DDP is the superior choice: zero forward communication and minimal gradient all-reduce volume provide maximum training throughput.
  2. Crossover Regime (1B to 3B parameters): As model states grow to 16–48 GB, DDP forces you to reduce physical micro-batch sizes to avoid OOM errors, lowering tensor core arithmetic intensity. FSDP shards states down to 2–6 GB, permitting 2× to 4× larger micro-batches that offset its 50% communication penalty.
  3. Sharding-Mandatory Regime (> 5B parameters): Mixed-precision states exceed physical GPU capacity (128.5 GB for 8B). DDP cannot execute. FSDP is strictly required to make training physically possible.

Common Pitfalls

When migrating from DDP to FSDP2, four subtle configuration pitfalls frequently trap training engineers:

1. The root-only wrapping pitfall

The single most catastrophic mistake in FSDP is calling fully_shard(model) exclusively on the top-level model container without wrapping individual transformer layers.

Comparison between root-only wrapping and block-level wrapping. Under root-only wrapping, FSDP treats all 32 layers as a single collective unit, forcing an all-gather of the entire 16.1 GB model weights at once and causing an instantaneous OOM spike. Under block-level wrapping, FSDP all-gathers only one block (0.50 GB) at a time, immediately freeing it after compute and preserving 97% of sharding memory gains.

When only the root module is sharded, FSDP does not know where layer boundaries lie. It must all-gather the weights of the entire model before the forward pass can begin! This requires storing both the sharded states (16.1 GB) and the full gathered weights (16.1 GB) simultaneously, causing an immediate OOM spike that completely negates the purpose of FSDP. Always iterate over model.transformer.h and apply fully_shard to each block individually.

2. MixedPrecisionPolicy dtype mismatches

When defining MixedPrecisionPolicy, practitioners frequently set reduce_dtype=torch.bfloat16 assuming it will save network bandwidth. While it halves communication volume, reducing gradients in BF16 can lead to severe numerical underflow and weight divergence on large pretraining runs (see Lesson 5, Mixed Precision Training - BF16 and FP8). The industry standard practice is: param_dtype=torch.bfloat16 for high-throughput tensor core GEMMs, and reduce_dtype=torch.float32 for full-precision accumulation in NCCL.

3. NCCL environment variables and interface binding

Distributed training failures often originate in misconfigured host network interfaces rather than PyTorch code. Always set these environment variables when debugging:

  • NCCL_DEBUG=INFO: Prints detailed collective routing, socket bindings, and network topology detection to stdout.
  • NCCL_IB_DISABLE=0: Ensures NCCL utilizes InfiniBand RoCE / NDR adapters rather than falling back to host TCP sockets.
  • TORCH_NCCL_AVOID_RECORD_STREAMS=1: Prevents PyTorch's caching allocator from accumulating excessive memory references across NCCL streams, mitigating allocator fragmentation.

4. Gradient accumulation without no_sync()

When using gradient accumulation with FSDP, calling loss.backward() on every micro-step triggers a Reduce-Scatter collective on every single micro-batch! This floods the interconnect with redundant network traffic. Wrap micro-steps in model.no_sync():

for micro_step in range(grad_accum):
    # Disable gradient reduction until the final micro-step
    ctx = model.no_sync() if micro_step < grad_accum - 1 else torch.nullcontext()
    with ctx:
        loss = model(x, y) / grad_accum
        loss.backward()

Summary

Mind map summarizing the DDP versus FSDP comparison: memory scaling regimes, communication trade-offs, PyTorch Profiler traces, small path execution, and critical wrapping pitfalls.
  • DDP replicates all states (16 bytes per parameter under mixed-precision AdamW) across every GPU, synchronizing only gradients during backpropagation via asynchronous ring all-reduce.
  • FSDP shards weights, gradients, and optimizer states across ranks, reducing per-GPU static memory by factor N_d (from 128.5 GB down to 16.1 GB per GPU on an 8×H100 node for Llama 3.1 8B).
  • For models larger than ~5B parameters, DDP crashes with an Out-Of-Memory failure on 80 GB GPUs; FSDP is strictly required to make training feasible.
  • FSDP communicates 50% more collective data per step than DDP (3 \frac{N-1}{N} versus 2 \frac{N-1}{N}). Over fast 900 GB/s NVLink, this communication is overlapped with GEMMs; over slow interconnects, it introduces compute stalls.
  • For small models (< 1B parameters), DDP delivers 10% to 15% higher throughput because it incurs zero forward all-gather communication.
  • PyTorch Profiler Chrome traces verify communication overlap: DDP overlaps all-reduce with backward compute, while FSDP2 prefetches Layer i+1 all-gathers during Layer i GEMMs.
  • Block-level wrapping is mandatory in FSDP: wrapping only the root module forces the entire model to all-gather at once, completely negating memory savings.

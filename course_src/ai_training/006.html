Introduction

In Lesson 3, Training Memory, we established the theoretical rules governing GPU memory allocation during large language model training. Static model and optimizer states demand 16 bytes per parameter under standard mixed-precision AdamW, while dynamic activations scale with batch size, sequence length, and layer dimensions [1]. In production infrastructure, however, an unexpected Out-Of-Memory (OOM) error frequently halts training runs. Engineers often respond by guessing: randomly cutting batch sizes, turning on checkpointing without sizing its impact, or switching off mixed-precision features without knowing why memory ran out.

A rigorous training engineer does not guess. Before running a single forward pass, you should be able to predict the memory footprint of your model down to within a few percent of the measured bytes. When discrepancies arise, PyTorch provides internal instrumentation—such as torch.cuda.max_memory_allocated() and the CUDA memory snapshot visualizer—to track every tensor allocation, lifetime, and caching allocator buffer directly against the underlying Python call stack [2], [3].

Workflow of the memory accounting lab. We begin by calculating analytical memory bounds from first principles for static states, activations, logits, and workspaces. Next, we execute an instrumented nanoGPT-style training script on GPU with precision and checkpointing toggles. CUDA memory hooks record allocation milestones and dump snapshot event traces, which are visualized at pytorch.org/memory_viz and validated against a predicted versus measured results table.

In this lab, we build a complete, self-contained generative pretraining script in the minimalist style of nanoGPT [4]. We train a GPT-2-small-sized model (approximately 124 million parameters) [5] on a single GPU, predict every gigabyte before execution, record its exact memory trajectory across the training step, and systematically evaluate the memory reduction levers: BF16 autocast, activation checkpointing, micro-batch sizing, and gradient accumulation. We also provide the parallel accounting for a 1-billion-parameter model on an NVIDIA H100 GPU.

Step 1: Predict the Memory Footprint from First Principles

Before launching training, we calculate the four primary consumers of GPU memory established in Lesson 3, Training Memory: static model states, dynamic forward activations, temporary workspaces and projection buffers, and caching allocator headroom.

1. Static model and optimizer states (16 bytes per parameter)

Under standard mixed-precision training with BF16 and the AdamW optimizer, each parameter requires five tensors [1]:

\text{Static Memory per Parameter} = 2\text{ (BF16 wt)} + 2\text{ (BF16 grad)} + 4\text{ (FP32 master)} + 4\text{ (Adam } m) + 4\text{ (Adam } v) = 16\text{ bytes}

For GPT-2 Small with tied input/output embeddings, the unique trainable parameter count is N = 124,439,808 (approximately 124.44M parameters):

  • BF16 Weights: 124.44 \times 10^6 \times 2\text{ bytes} \approx 248.88\text{ MB} (237.35 MiB).
  • BF16 Gradients: 124.44 \times 10^6 \times 2\text{ bytes} \approx 248.88\text{ MB} (237.35 MiB).
  • FP32 Master Weights: 124.44 \times 10^6 \times 4\text{ bytes} \approx 497.76\text{ MB} (474.70 MiB).
  • FP32 Adam Moments (m and v): 124.44 \times 10^6 \times 8\text{ bytes} \approx 995.52\text{ MB} (949.40 MiB).
  • Total Static States: 124.44 \times 10^6 \times 16\text{ bytes} = 1,991,036,928\text{ bytes} \approx 1,991.04\text{ MB} (1.991 GB or 1,898.80 MiB).

For the full path 1B model (N = 1.00 \times 10^9 parameters), the static baseline scales to exactly 1.00 \times 10^9 \times 16\text{ bytes} = 16.00\text{ GB} (14.90 GiB).

2. Dynamic activation memory

We evaluate intermediate forward activations using Korthikanti et al.'s formulation [1]. With sequence length s = 1,024, micro-batch size b = 8, hidden dimension h = 768, heads a = 12, and L = 12 layers in BF16 (2 bytes per number):

  • Linear terms per layer: 34 s b h = 34 \times 1,024 \times 8 \times 768 = 213,909,504\text{ bytes} \approx 213.91\text{ MB}.
  • Quadratic attention terms per layer (without FlashAttention): 5 a s^2 b = 5 \times 12 \times (1,024)^2 \times 8 = 503,316,480\text{ bytes} \approx 503.32\text{ MB}.
  • Total uncheckpointed standard attention: Across 12 layers, activations require 12 \times (213.91 + 503.32)\text{ MB} = 8,606.71\text{ MB} \approx 8.61\text{ GB}. This would immediately exceed an 8 GB GPU before counting model states!
  • With FlashAttention: The quadratic 5 a s^2 b term is eliminated [7], [8]. Activations collapse to the linear term: 12 \times 213.91\text{ MB} = 2,566.91\text{ MB} \approx 2.57\text{ GB}.
  • With Full Activation Checkpointing: Retaining only the input activation tensor per layer (2 s b h in BF16) requires 12 \times (2 \times 1,024 \times 8 \times 768 \times 2) \approx 301.99\text{ MB} [9]. Adding one layer's peak recomputed activations (213.91\text{ MB}) during backward pass brings total peak activations to just 515.90 MB (an 80% reduction compared to uncheckpointed FlashAttention).

3. Ephemeral logits projection buffer

A critical source of memory spikes often omitted in textbook calculations is the vocabulary projection buffer. At the final layer, hidden states [b, s, h] multiply against the unembedding matrix to produce logits of shape [b, s, V]. For GPT-2 with vocabulary V = 50,257, evaluating cross-entropy in FP32 requires materializing:

\text{Logits Buffer} = 8 \times 1,024 \times 50,257 \times 4\text{ bytes} = 1,646,821,376\text{ bytes} \approx 1,646.82\text{ MB}\text{ (1.65 GB)}

Notice that for GPT-2 Small at batch size 8, the ephemeral logits buffer consumes nearly as much memory as the entire model and optimizer states combined! In the 1B model with Llama-sized vocabulary (V = 128,256, b = 8, s = 2,048), the unchunked logits tensor consumes 8 \times 2,048 \times 128,256 \times 4 \approx 8.41\text{ GB}.

Analytical component sizing for GPT-2 Small (124M parameters, batch size 8, sequence length 1,024) and a 1B model (batch size 8, sequence length 2,048). For GPT-2 Small, static states require 1.99 GB, FlashAttention activations require 2.57 GB, the logits buffer requires 1.65 GB, and scratch workspaces take 0.26 GB, predicting a 6.47 GB peak that fits inside 8 GB VRAM. Activation checkpointing cuts the peak to 4.42 GB.

Step 2: Build the Instrumented Training Script

Now we implement our training script in the minimalist, readable style of Andrej Karpathy's nanoGPT [4]. To ensure reproducibility, we build the model using native PyTorch 2.x modules: nn.Linear, nn.LayerNorm, and F.scaled_dot_product_attention (which automatically routes to FlashAttention-2 on Hopper, Ampere, and Ada architectures). We also wire in PyTorch's native activation checkpointing via torch.utils.checkpoint.checkpoint [5].

Crucially, we instrument the script with CUDA memory milestones to measure exactly when memory is allocated:

  1. Milestone 1 (Model Load): Measures memory immediately after transferring weights to GPU.
  2. Milestone 2 (Optimizer Init): Measures memory after instantiating AdamW.
  3. Milestone 3 (Forward Pass): Measures memory immediately after completing the forward pass, capturing intermediate activations.
  4. Milestone 4 (Backward Pass): Captures peak memory during backpropagation.
  5. Milestone 5 (Step Complete): Measures memory after optimizer.step() and optimizer.zero_grad(set_to_none=True).

Step 3: Profile with PyTorch Memory Snapshot Visualizer

While torch.cuda.max_memory_allocated() tells you the maximum watermark reached, it does not reveal what tensors caused the peak or whether memory fragmentation contributed to the footprint. PyTorch includes a memory snapshot facility that records every allocation, deallocation, and allocator segment transition alongside the Python traceback that invoked it [2], [3].

To capture a memory history, our script executes:

torch.cuda.memory._record_memory_history(
    enabled="all", context="all", stacks="python", max_entries=100000
)

After completing an iteration, we export the recording via torch.cuda.memory._dump_snapshot("memory_snapshot.pickle"). Open your web browser and navigate to pytorch.org/memory_viz. Drag and drop the memory_snapshot.pickle file into the viewer.

Visual reconstruction of a PyTorch memory snapshot timeline across one training step. The dashed line depicts memory reserved by the caching allocator, while the solid shaded polygon shows actively allocated tensors. Baseline weights (237 MiB) climb to 1,900 MiB on Step 0 as Adam moments are instantiated. Activations accumulate during forward pass, reaching a peak of 6.47 GB at the start of backward pass where activations coexist with the logits buffer. Activations are freed layer by layer as gradients accumulate, returning to the static baseline after the optimizer step.

The visualizer timeline reveals three critical architectural insights:

  1. Active vs Reserved Memory: The blue shaded region indicates tensors actively held by PyTorch. The grey area above it represents memory reserved by the CUDA caching allocator. If reserved memory climbs significantly higher than allocated memory, the allocator has experienced fragmentation—unusable gaps between freed blocks.
  2. The Exact Watermark Moment: Hovering over the peak spike at 6.47 GB reveals the line of code responsible: the final LayerNorm and unembedding projection logits = self.lm_head(x), followed by F.cross_entropy. At this instant, every saved activation tensor across all 12 layers is held in HBM waiting for the backward chain rule, while the 1.65 GB logits buffer is simultaneously materialized.
  3. Deallocation Wavefront: As backpropagation traverses backwards from Layer 11 down to Layer 0, the intermediate activations for each layer are released as soon as that layer's weight gradients are computed. Notice how the active memory stairs downward during the backward phase.

Step 4: Run Systematic Ablations

To understand the exact impact of each training configuration, we execute a systematic parameter sweep using run_sweep.py across five controlled axes: precision (FP32 vs BF16), activation checkpointing (ON vs OFF), physical batch size (1 to 16), and gradient accumulation.

Measured and predicted peak memory for GPT-2 Small at an effective batch size of 8. Full FP32 precision requires 10.40 GB and causes an Out-Of-Memory failure on an 8 GB GPU. BF16 autocast brings peak memory to 6.47 GB, fitting within 8 GB VRAM. Activation checkpointing drops the footprint to 4.42 GB. Micro-batching with gradient accumulation (micro-batch 2 with accumulation 4) achieves the same effective batch size at only 3.31 GB, cutting peak memory by 49%.

Interpreting the scaling curves

Figure 4 illustrates how peak memory scales across micro-batch sizes under standard attention, FlashAttention, and activation checkpointing.

Illustrative scaling of peak memory against micro-batch size for GPT-2 Small. The static state baseline (1.99 GB) establishes a non-zero floor. Standard attention scales quadratically with sequence length and steeply with batch size, crossing the 8 GB limit at batch size 6. FlashAttention flattens the slope to linear scaling, allowing batch size 8. Activation checkpointing produces the shallowest slope, remaining under 8 GB even at batch size 32.

Notice the two distinct regimes in the curve:

  • The Static Floor (b \to 0): As batch size approaches zero, memory does not drop to zero. The curve flattens at the static baseline of 1.99 GB (16 bytes per parameter). No matter how small you set your batch size, you can never reduce this floor without sharding model states across GPUs or offloading to CPU RAM (see Lesson 11, ZeRO and FSDP).
  • The Activation Slope: For batch size b \ge 1, memory grows linearly with slope proportional to intermediate activations per sample. Under uncheckpointed FlashAttention, the slope is 34 s h \times L bytes per batch item. Under full activation checkpointing, the slope collapses to 2 s h \times L bytes per batch item, permitting 4× larger batch sizes before hitting the 8 GB ceiling.

The gradient accumulation trade-off

When physical memory limits prevent setting the desired batch size, gradient accumulation bridges the gap without altering the mathematical optimization trajectory [4]. Figure 5 diagrams this trade-off.

Comparison between physical batch size 8 (Case A) and micro-batch size 2 with gradient accumulation factor 4 (Case B). Both configurations update weights using identical mathematical gradients computed over 8 samples. Case A executes a single forward/backward pass, peaking at 6.47 GB. Case B processes four consecutive micro-batches of 2 samples, reducing peak activation and logits memory by 4× and dropping peak memory to 3.31 GB.

Gradient accumulation allows an 8 GB GPU to simulate arbitrarily large batch sizes (e.g., 64, 128, or 256 sequences). However, it introduces a trade-off: processing very small micro-batches (such as b=1) reduces GPU arithmetic intensity, causing tensor cores to operate below maximum compute efficiency due to kernel launch overhead.

Common Pitfalls

When profiling and sizing training memory, watch out for these subtle implementation traps:

  • Lazy optimizer state allocation: The single most common bug when instrumenting training scripts is querying memory immediately after optimizer = torch.optim.AdamW(...). PyTorch optimizers instantiate moment buffers lazily during the first call to optimizer.step(). A script that checks memory during initial setup will underestimate static memory by 75%, leading to an unexpected OOM crash at the end of the first step.
  • Forgetting set_to_none=True in zero_grad(): Calling optimizer.zero_grad() without arguments writes zeros across all gradient tensors, leaving their memory allocated. Passing zero_grad(set_to_none=True) deallocates the gradient storage entirely, allowing the PyTorch caching allocator to reuse those memory blocks for forward activations in the subsequent step.
  • Logits tensor explosion on large vocabularies: Projecting hidden states to vocabulary size V = 128,256 (standard in modern models like Llama 3) creates a massive intermediate tensor (b \times s \times V \times 4\text{ bytes}). If computed unchunked at batch size 8, this single tensor consumes over 8.4 GB. In production pretraining, use chunked cross-entropy or fused kernels (such as Liger Kernel) to compute loss without materializing the full logits tensor in HBM.
  • Autograd graph memory leaks in loss logging: Writing losses.append(loss) inside your training loop retains a reference to the entire backward computational graph in memory across iterations, triggering an inevitable OOM crash after several steps. Always log scalar values using loss.item().
  • Caching allocator fragmentation: Frequent allocations of varying sizes can fragment the PyTorch caching allocator, causing cudaMalloc failures even when total free memory exceeds the requested size. If your memory snapshot reveals wide gaps between allocated and reserved memory, set the environment variable PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True to allow virtual memory address reservation.

  2. Inspect SDPA kernel dispatch: Use torch.nn.attention.sdpa_kernel context managers to force PyTorch's SDPA to alternate between SDPBackend.FLASH_ATTENTION, SDPBackend.EFFICIENT_ATTENTION, and SDPBackend.MATH. Measure how peak activation memory changes when FlashAttention is disabled.
  3. Implement chunked cross-entropy: Modify train_gpt.py to split the sequence dimension of the final linear projection into four chunks, computing F.cross_entropy on each chunk sequentially. Confirm on your memory snapshot that the 1.65 GB logits spike disappears.

Summary

Mind map summarizing the memory accounting lab: analytical sizing rules, PyTorch profiling hooks, mixed-precision impact, checkpointing trade-offs, micro-batch tuning, and hardware realities.
  • GPU training memory divides into four distinct categories: static model and optimizer states (16 bytes per parameter under mixed-precision AdamW), dynamic forward activations, ephemeral projection workspaces (such as the logits buffer), and allocator headroom.
  • For GPT-2 Small (124.44M parameters), static states require 1.99 GB (1,899 MiB). For a 1B-parameter model, static states require 16.00 GB.
  • Uncheckpointed standard attention activations explode quadratically with sequence length (5 a s^2 b). FlashAttention eliminates the quadratic term, cutting activations to linear scaling (34 s b h) and saving over 6.0 GB at batch size 8.
  • Full activation checkpointing retains only layer boundary inputs (2 s b h), cutting activation memory by 80% to 94% in exchange for a 33.3% compute penalty (6ND \to 8ND FLOPs).
  • The cross-entropy logits tensor is an ephemeral peak consumer, demanding b \times s \times V \times 4\text{ bytes} (1.65 GB for GPT-2 Small, 8.41 GB for a 1B model).
  • Gradient accumulation enables simulating large effective batch sizes with smaller physical micro-batches, cutting activation and logits memory linearly without altering optimizer states.
  • PyTorch allocates Adam optimizer moments lazily during the first optimizer.step(). Memory snapshot traces exported to pytorch.org/memory_viz confirm the exact byte breakdown and allocation timestamps.

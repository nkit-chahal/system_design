Introduction

In large-scale AI pretraining, hardware failures are not rare anomalies; they are a daily operational reality. When operating a cluster of 256 NVIDIA H100 GPUs across 32 nodes for days at a time, Mean Time Between Failures (MTBF) drops from months to tens of hours [1]. An uncorrectable SRAM double-bit error, an InfiniBand cable transceiver drop, or a PCIe bus reset will abruptly crash a single GPU. Because distributed training relies on synchronous collective communication across all ranks (Lesson 30, Cluster Networking and Collectives), the crash of a single GPU instantly terminates the entire multi-node job.

Surviving hardware failures requires two coordinated capabilities: resilient state persistence (saving every parameter, optimizer moment, dataloader offset, and random seed) and automated restart orchestration (re-provisioning nodes, establishing network rendezvous, and reloading state). If your checkpointing pipeline omits even one state component—such as the dataloader shuffle index or Adam second moments—resumed training experiences severe loss divergence and poisoned sample distribution [2]. Furthermore, every minute spent detecting failures, waiting for scheduler requeues, and replaying uncheckpointed steps directly erodes training goodput (Lesson 29, Failures, Restarts and Elastic Training).

Architecture of the failure recovery lab. Track A (Small Path) runs a 2-process torchrun job on a local machine to validate state determinism and exact loss matching under fault injection. Track B (Full Path) runs across 16 H100 GPUs (2 nodes) on a Slurm cluster to benchmark real-world scheduler requeue and compute goodput.

In this lab, you will build and test an end-to-end failure recovery harness. You will execute an uninterrupted baseline training run, implement a fully deterministic resumable checkpointing pipeline, simulate a catastrophic mid-run GPU failure by terminating a worker process, restore the run using torchrun, and verify that the resumed loss trajectory continues seamlessly. Finally, you will measure the exact overhead of failure detection, state restoration, and replayed steps to compute your cluster's effective goodput.

Step 1: Baseline Uninterrupted Run

Before testing failure recovery, we must generate a "gold standard" reference trajectory. We train our target model for 500 steps without interruption, saving checkpoints periodically and logging the loss at every step. This provides the exact mathematical baseline against which our resumed run will be verified.

import argparse import os import time import torch import torch.nn as nn import torch.distributed as dist from torch.utils.data import Dataset, DataLoader, Sampler class ResumableSampler(Sampler): """Deterministic sampler that yields identical sequence order and supports offset resumption.""" def __init__(self, size: int, batch_size: int, seed: int = 42): self.size = size self.batch_size = batch_size self.seed = seed self.start_step = 0 g = torch.Generator() g.manual_seed(seed) self.indices = torch.randperm(size, generator=g).tolist() def set_start_step(self, step: int): self.start_step = step def __iter__(self): start_idx = self.start_step * self.batch_size for i in range(start_idx, self.size - self.batch_size + 1, self.batch_size): yield self.indices[i : i + self.batch_size] def state_dict(self): return {"seed": self.seed, "start_step": self.start_step} def load_state_dict(self, state): self.seed = state["seed"] self.start_step = state["start_step"] g = torch.Generator() g.manual_seed(self.seed) self.indices = torch.randperm(self.size, generator=g).tolist() class ToyGPT(nn.Module): def __init__(self, vocab_size=5000, dim=256, layers=4): super().__init__() self.emb = nn.Embedding(vocab_size, dim) self.blocks = nn.ModuleList([nn.Linear(dim, dim, bias=False) for _ in range(layers)]) self.lm_head = nn.Linear(dim, vocab_size, bias=False) def forward(self, x): h = self.emb(x) for layer in self.blocks: h = h + torch.relu(layer(h)) return self.lm_head(h) def run(): dist.init_process_group("nccl" if torch.cuda.is_available() else "gloo") local_rank = int(os.environ.get("LOCAL_RANK", 0)) device = torch.device(f"cuda:{local_rank}" if torch.cuda.is_available() else "cpu") if torch.cuda.is_available(): torch.cuda.set_device(device) # Step 2: Resumable Checkpoint Architecture

To guarantee that a resumed training run continues along the exact numerical trajectory of the uninterrupted run, the checkpoint must encapsulate five distinct state domains (Figure 2) [2]:

The five essential state components required for deterministic recovery: Model Weights, Optimizer States (Adam master weights and moments), Learning Rate Scheduler, Deterministic Dataloader offsets, and Random Number Generator states. Missing any component causes loss divergence.
  1. Model Weights (model.state_dict()): The primary neural network parameters. In distributed FSDP, this is saved via PyTorch Distributed Checkpoint (DCP) sharded across storage (Lesson 28, Checkpointing).
  2. Optimizer State (optimizer.state_dict()): The full AdamW momentum (m_t) and variance (v_t) accumulators, along with high-precision FP32 master weights. If omitted, the optimizer resets momentum to zero, causing learning rates to effectively surge and producing a 20–50% loss jump upon restart.
  3. Scheduler State (scheduler.state_dict()): The active step counter and internal decay variables. If omitted, learning rate warmup restarts from step 0, applying high learning rates at late training stages.
  4. Dataloader State / Sampler Offset: The token index and batch offset. If omitted, the resumed run re-reads training data from epoch 0, re-exposing the model to millions of already-seen tokens while skipping unread portions of the corpus.
  5. RNG States (torch.get_rng_state() and cuda.get_rng_state()): The internal bit-generators governing dropout masks and stochastic augmentations.

Step 3: Simulating a Failure Mid-Run

Now we simulate a sudden hardware crash during active training. We launch a second run configured to save checkpoints every 100 steps. At step 250—exactly halfway between checkpoint 200 and checkpoint 300—we inject a catastrophic failure by sending kill -9 to worker process rank 1.

Step 4: Automatic Restart and Resumption

The job has crashed at step 250. Because step 250 was never checkpointed, all progress between step 201 and step 250 is lost. To recover, our restart runner inspects the checkpoint directory, identifies the latest intact checkpoint (ckpt_step_200.pt), restores all five state domains, advances the dataloader to step 200, and resumes execution through step 500 using the PyTorch Distributed Elastic framework [3].

import os import glob import torch import torch.distributed as dist from train_baseline import ResumableSampler, ToyGPT, nn, DataLoader def find_latest_checkpoint(ckpt_dir: str): ckpts = glob.glob(os.path.join(ckpt_dir, "ckpt_step_*.pt")) if not ckpts: return None # Sort by step number extracted from filename ckpts.sort(key=lambda p: int(p.split("_")[-1].replace(".pt", ""))) return ckpts[-1] def resume(): dist.init_process_group("nccl" if torch.cuda.is_available() else "gloo") local_rank = int(os.environ.get("LOCAL_RANK", 0)) device = torch.device(f"cuda:{local_rank}" if torch.cuda.is_available() else "cpu") if torch.cuda.is_available(): torch.cuda.set_device(device) latest_ckpt = find_latest_checkpoint("./checkpoints_resumed") assert latest_ckpt is not None, "No checkpoint found to resume from!" if local_rank == 0: print(f"[RECOVERY] Found latest intact checkpoint: {latest_ckpt}") checkpoint = torch.load(latest_ckpt, map_location=device) start_step = checkpoint["step"] # 1. Restore Model Weights model = ToyGPT().to(device) model.load_state_dict(checkpoint["model"]) # 2. Restore Optimizer States (Adam m, v and master weights) optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3, betas=(0.9, 0.95), eps=1e-8) optimizer.load_state_dict(checkpoint["optimizer"]) # 3. Restore Learning Rate Scheduler scheduler = torch.optim.lr_scheduler.CosineAnnealingLR(optimizer, T_max=500) scheduler.load_state_dict(checkpoint["scheduler"]) # 4. Restore Deterministic Data Sampler to exact step 200 offset data = torch.randint(0, 5000, (10000, 64)) sampler = ResumableSampler(len(data), batch_size=8, seed=1337) sampler.set_start_step(start_step) loader = DataLoader(data, batch_sampler=sampler) # 5. Restore Random Number Generator States torch.set_rng_state(checkpoint["rng_torch"]) if torch.cuda.is_available() and "rng_cuda" in checkpoint: torch.cuda.set_rng_state(checkpoint["rng_cuda"], device) if local_rank == 0: print(f"[RECOVERY] Resuming training from step {start_step + 1} through step 500...") log_file = f"./resumed_phase2_rank{local_rank}.csv" with open(log_file, "w") as f: f.write("step,loss,lr\n") loader_iter = iter(loader) for step in range(start_step + 1, 501): batch = next(loader_iter).to(device) targets = batch.clone() optimizer.zero_grad() logits = model(batch) loss = nn.functional.cross_entropy(logits.view(-1, 5000), targets.view(-1)) loss.backward() optimizer.step() scheduler.step() if local_rank == 0 and step % 20 == 0: print(f"Resumed Step {step:3d} | Loss: {loss.item():.5f} | LR: {scheduler.get_last_lr()[0]:.6f}") with open(log_file, "a") as f: f.write(f"{step},{loss.item():.6f},{scheduler.get_last_lr()[0]:.6f}\n") dist.destroy_process_group() if __name__ == "__main__": resume() # Launch recovery run starting from step 201 through step 500 torchrun --nproc_per_node=2 resume_training.py # Expected console output: # [RECOVERY] Found latest intact checkpoint: ./checkpoints_resumed/ckpt_step_200.pt # [RECOVERY] Resuming training from step 201 through step 500... # Resumed Step 220 | Loss: 6.41922 | LR: 0.000789 # Resumed Step 260 | Loss: 6.10421 | LR: 0.000712 # ... # Resumed Step 500 | Loss: 4.81230 | LR: 0.000000

Bitwise determinism versus floating-point tolerance

Engineers often ask: Should the resumed loss match the uninterrupted baseline bitwise (exact binary equality), or within a numerical tolerance?

If training runs on CPU or with torch.use_deterministic_algorithms(True) enabled on GPU, modern PyTorch produces exact bitwise matching across all steps (\max |\Delta| = 0.0). However, in high-performance GPU pretraining, several CUDA operations—most notably atomic additions (atomicAdd) executed during backward-pass gradient reductions in FlashAttention and LayerNorm—are inherently non-deterministic in floating-point summation order [4].

Because floating-point addition is non-associative ((a + b) + c \ne a + (b + c)), differing thread schedule orders introduce tiny roundoff variations at the 7th decimal digit in FP32 (\sim 10^{-7}) and 3rd decimal digit in BF16. Over hundreds of steps, chaotic sensitivity can cause trajectories to drift slightly. A healthy resumed run matches within 10^{-4} tolerance across the first 50 steps, whereas a broken run (missing optimizer states or shuffled data) diverges by > 0.5 on the very first resumed step.

Common Pitfalls

  • Missing optimizer state: Saving only model.state_dict(). Upon restart, AdamW initializes momentum and variance accumulators (m_t, v_t) to zero. The denominator \sqrt{v_t} + \epsilon collapses to \epsilon, causing coordinate updates to surge by 10× to 100× and spiking loss by +0.5 to +1.0.
  • Non-resumable dataloader shuffle: Instantiating a new DataLoader without saving the random seed and sample offset. The resumed run re-reads samples from the start of the dataset or shuffles with a different seed, breaking reproducibility and biasing token distributions.
  • Corrupted partial checkpoints: If a process crashes or power drops while torch.save() is writing to disk, the destination file is left truncated. When the recovery script calls torch.load(), it crashes with an EOFError. Solution: Always write checkpoints to an atomic temporary path (ckpt_step_200.pt.tmp) and use an atomic POSIX rename (os.replace()) only after write and flush() complete.
  • Uncoordinated distributed saves: In multi-GPU runs without FSDP DCP, having all 16 ranks write identical full checkpoints simultaneously to shared storage causes storage metadata locks and write storms. Only rank 0 should write non-sharded checkpoints, or all ranks must write non-overlapping DCP shards.
  • Stale NCCL communication sockets: When a crashed rank is killed, leftover zombie processes on other nodes can keep TCP communication sockets in TIME_WAIT state. New torchrun instances attempting to bind to port 29500 fail with Address already in use. Ensure torchrun or Slurm job prolog scripts kill all lingering Python processes before restarting.

Stretch Goals

If you complete the baseline recovery lab ahead of schedule, pursue these production engineering enhancements:

  1. Asynchronous non-blocking checkpointing: Integrate PyTorch Distributed Checkpoint (DCP) with asynchronous staging (Lesson 28). Copy model state from GPU HBM to host pinned CPU memory in 200 ms on a separate CUDA stream, then spawn a background Python thread to stream the checkpoint to disk while GPU compute resumes immediately.
  2. Dynamic rank reassignment (Elastic training): Configure torchrun --nnodes=1:2 to dynamically adjust world size upon node failure. If node 1 suffers a permanent hardware failure, let torchrun re-rendezvous on the remaining 8 GPUs on node 0, scale the global batch size, and continue training without waiting for hardware replacement.
  3. Automated health-check prolog: Write a bash wrapper script that executes a 10-second NCCL All-Reduce test (all_reduce_perf, Lesson 30) across all allocated nodes before resuming training, automatically cordoning broken nodes before loading the checkpoint.

Summary

Mind map summarizing the lab: two execution tracks, the five mandatory checkpoint states, recovery timeline accounting, numerical verification criteria, and common operational pitfalls.
  • Hardware failures are normal operating conditions at scale; training pipelines must support automated crash detection and deterministic state recovery.
  • A valid resumable checkpoint requires five distinct components: Model Weights, Optimizer States (Adam master weights and moments), LR Scheduler state, Dataloader offset, and RNG states.
  • Omitting optimizer state resets momentum to zero, causing learning rate surges and loss spikes upon restart. Omitting dataloader state causes token duplication or data leakage.
  • Total failure recovery time equals failure detection timeout + scheduler requeue and node boot + checkpoint read time + replaying uncheckpointed steps.
  • Resumed runs match the uninterrupted baseline within 10^{-4} tolerance (or exact bitwise equality under CUDA deterministic mode). Non-deterministic atomic additions in backward passes account for minor floating-point divergence.
  • Goodput evaluates the proportion of billed cluster time spent doing useful forward/backward compute versus checkpoint I/O, restart latency, and replayed work.

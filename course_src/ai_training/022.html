Introduction

Pretraining transforms randomly initialized transformer weights into a powerful statistical predictor of web tokens. However, a base pretrained foundation model is not an assistant; it is a document continuator. If a user presents a base model with the prompt "Explain how DNS resolution works", the model is as likely to generate "in 10 easy steps. Chapter 2: TCP/IP" or append forum comments as it is to answer the question. It lacks conversational turn-taking, role boundaries, instruction adherence, and safe tone [1].

Supervised Fine-Tuning (SFT) bridges this behavioral gap. By training the model on curated demonstrations of multi-turn dialogues, system instructions, and task completions, SFT teaches the model to adopt an assistant persona, adhere to strict formatting schemas (such as JSON tool-calling), and follow complex user constraints [2]. Crucially, SFT is not an unsupervised pretraining continuation: it uses assistant-only loss masking so that gradient updates penalize only incorrect completions, never the user prompts.

A base pretrained model acts as an unconstrained document completer, continuing prompts with arbitrary web text. Supervised Fine-Tuning conditions the model to recognize conversational roles and deliver structured, compliant responses.

In this lesson, we break down what SFT changes in a base model and its fundamental limits, examine conversational data formatting and assistant-only loss masking, analyze batch packing versus padding, review verified recipes such as the Allen Institute's Tülu 3 [3], compute the exact memory and compute accounting for full fine-tuning across an 8×H100 GPU node, diagnose catastrophic forgetting, evaluate the architectural choice between full fine-tuning and LoRA, and implement an end-to-end SFT training pipeline using Hugging Face TRL and Accelerate FSDP.

Clarifying the Problem

In post-training systems design interviews, SFT questions typically center on hardware sizing, conversational data representation, and the trade-off between full parameter updates and parameter-efficient adapters. Here is how a discussion between a candidate and an interviewer typically unfolds:

Candidate: What base model architecture and precision are we fine-tuning?
Interviewer: We are fine-tuning a base model with the Llama 3.1 8B architecture—8.03 billion parameters across 32 layers, hidden dimension 4,096, sequence length up to 8,192—in BF16 precision.

Candidate: What is the specific business application and dataset scale?
Interviewer: A customer-support assistant product. Our training set consists of 50,000 multi-turn customer support conversations averaging 1,000 tokens each, totaling approximately 50 million tokens.

Candidate: What compute infrastructure is available for this run?
Interviewer: A single 8×H100 SXM node containing 8 NVIDIA H100 80 GB GPUs connected via 900 GB/s NVLink. We want to know whether we should execute full fine-tuning across the node using FSDP, or use LoRA on a single GPU.

Candidate: What are the primary performance and latency requirements for deployment?
Interviewer: Maximum instruction compliancy, strict JSON output formatting for ticket routing, and zero degradation in core conversational English. Serving latency must be minimal.

Candidate: What training budget and turnaround time are targeted?
Interviewer: We need the fine-tuning run to complete rapidly—ideally under an hour—so our engineering team can iterate on data mixtures daily.

The question underneath is: How do we format conversational dialogues with assistant-only loss masking, account for memory across an 8×H100 node using FSDP, size the compute budget using 6ND arithmetic, and ensure the model assimilates domain guidelines without catastrophically forgetting general reasoning? To answer it, we begin by examining what SFT alters within the transformer parameters.

What SFT Does to a Base Model—and What It Cannot Do

A central question in post-training engineering is whether SFT imparts new foundational knowledge or merely aligns the interface to existing pretraining representations. In their influential study LIMA: Less Is More for Alignment, Zhou et al. formulated the Superficial Alignment Hypothesis [4]:

Almost all foundational knowledge and world capabilities are acquired during pretraining. Alignment (SFT and preference tuning) is a simple process of learning the style, format, and interaction protocol that surfaces those latent capabilities.

The four stages of foundation model development. Pretraining acquires 99% of linguistic and factual knowledge across trillions of tokens. SFT aligns conversational style and format. Preference optimization (DPO) resolves ambiguity, and verifiable RL (GRPO) refines multi-step reasoning.

LIMA demonstrated that fine-tuning a 65B base model on just 1,000 meticulously curated prompt-response pairs produced an assistant that competed effectively with models trained on 50,000 uncurated conversations. However, while the Superficial Alignment Hypothesis holds for general conversational style, production teams must heavily hedge its claims:

  • Domain Vocabulary and APIs: SFT can teach a model to reliably map proprietary business intents to specific internal API schemas, parse unique domain IDs, and adopt a consistent corporate tone.
  • Limits of Knowledge Injection: SFT cannot teach a model entirely new foundational disciplines (such as learning Swedish or organic chemistry from scratch). Attempting to inject vast factual knowledge through small SFT datasets causes severe hallucinations and memorization without generalization.
  • The Imitation Bottleneck: SFT trains via maximum likelihood estimation (teacher forcing). The model imitates surface patterns in the demonstration data. It cannot learn from its own mistakes during generation, nor does it receive negative feedback when an answer is factually incorrect. Resolving ambiguity, sycophancy, and refusal behavior requires subsequent preference optimization (Lesson 24, Reward Models and RLHF, and Lesson 25, DPO and Preference Optimization).

Conversational Data Formatting and Loss Masking

Chat Templates and Special Tokens

Pretrained transformers process a flat sequence of integer token IDs. To structure a multi-turn dialogue into a format the model can parse unambiguously, training pipelines apply a chat template that introduces reserved control tokens (Lesson 19, Tokenizers).

In Llama 3.1, the conversational protocol uses four primary special tokens [2]:

  • <|begin_of_text|>: Marks the absolute start of the sequence.
  • <|start_header_id|>{role}<|end_header_id|>: Declares the message sender, where role is system, user, or assistant.
  • <|eot_id|> (End of Turn): Demarcates the conclusion of a message, prompting the model to switch roles.

Assistant-Only Loss Masking

In standard causal language modeling, the cross-entropy loss is computed across every token in the sequence:

\mathcal{L}_{\text{pretrain}}(\theta) = -\frac{1}{T} \sum_{t=1}^T \log P_\theta(x_t \mid x_{

In SFT, calculating loss on the entire sequence is destructive. A user prompt represents an incoming query that the assistant must observe, not generate. If the loss is computed over user prompt tokens, the model spends gradient capacity learning to predict the user's phrasing, grammatical quirks, and query distribution. This causes prompt memorization, impairs out-of-distribution instruction generalization, and dilutes gradient updates [5].

Input tokens and role demarcations. Tokens in the system prompt and user query are assigned a label value of -100, which PyTorch's CrossEntropyLoss ignores natively. Only the assistant response tokens evaluate loss and update parameter gradients.

The standard solution is assistant-only loss masking (completion-only loss). During data collation, every token belonging to the system prompt or user turn is assigned a label value of -100. In PyTorch, torch.nn.CrossEntropyLoss(ignore_index=-100) natively skips positions where the label equals -100:

\mathcal{L}_{\text{SFT}}(\theta) = -\frac{1}{|\mathcal{T}_{\text{assistant}}|} \sum_{t \in \mathcal{T}_{\text{assistant}}} \log P_\theta(x_t \mid x_{

Only tokens generated by the assistant contribute to the loss numerator and backpropagation denominator. The model is trained purely to condition on the prompt and predict the completion.

Sequence Packing versus Padding

Conversational dialogues exhibit high length variance: some user exchanges require 150 tokens, while complex technical troubleshooting spans 3,500 tokens. Batching these dialogues presents an efficiency challenge.

Top: Standard padding pads sequences to a fixed context length, wasting up to 45% of compute on pad tokens. Bottom: Sequence packing concatenates multiple dialogues into a continuous 4,096-token sequence with cumulative sequence length masks, achieving 100% compute utilization.
  • Padding (Padded Batching): Dialogues within a batch are padded with [PAD] tokens to match the longest sequence in that micro-batch (or a fixed max length like 4,096). While straightforward to implement, padding wastes 30% to 60% of GPU compute on pad tokens that do not contribute to gradients.
  • Packing (Sequence Concatenation): Multiple independent conversations are concatenated end-to-end into a single contiguous sequence of length L = 4,096 or 8,192. Packing eliminates compute waste completely. However, packing introduces a critical requirement: cross-contamination masking. Tokens in Conversation B must never attend to tokens in Conversation A. Training frameworks supply cumulative sequence lengths (cu_seqlens) to FlashAttention-2 varlen kernels to enforce strict block-diagonal causal masking across packed conversation boundaries [6].

Hyperparameters and Training Dynamics

Fine-tuning an 8B model requires radically different hyperparameters from pretraining. During pretraining, the learning rate typically starts at 3 \times 10^{-4} and decays slowly. In SFT, applying a learning rate that high instantly shatters the delicate, pre-converged self-attention representations, resulting in catastrophic collapse.

Modern verified recipes—such as the Allen Institute's Tülu 3 recipe on Llama 3.1 8B [3] and the Stanford Alpaca / Tülu 2 recipes [5]—establish precise bounds:

  • Learning Rate: Typically between 5 \times 10^{-6} and 2 \times 10^{-5} for an 8B model. Tülu 3 determined that an optimal learning rate of 5 \times 10^{-6} achieved peak benchmark scores on Llama 3.1 8B, while 70B models required an even more conservative 2 \times 10^{-6}.
  • Learning Rate Schedule: Linear warmup over the first 3% of training steps (warmup ratio 0.03), followed by linear decay to zero.
  • Effective Batch Size: 64 to 128 sequences (approximately 128k to 512k tokens per optimizer step). This is achieved by combining per-device micro-batch size with gradient accumulation.
  • Epochs and Overfitting: SFT converges rapidly. Optimal performance is universally achieved in 1 to 2 epochs. Training beyond 3 epochs leads to severe memorization: the training loss continues to decrease, but output diversity collapses, responses become repetitive and verbose, and out-of-domain reasoning degrades sharply.
  • Weight Decay: Set to 0.0 or a minimal 0.01 to prevent ungrounded weight drift away from the pretraining minimum.

Memory and Compute Accounting: Full Fine-Tuning vs LoRA

We now size the exact compute and memory budget for our post-training scenario: fine-tuning Llama 3.1 8B (N = 8.03 \times 10^9 parameters) on 50,000 customer-support conversations averaging 1,000 tokens (D = 50 \times 10^6\text{ tokens}) across our 8×H100 SXM node.

Memory allocation comparison. Left: One GPU of an 8-GPU node running full fine-tuning with FSDP consumes 20.1 GB peak memory, leaving > 70% headroom on an 80 GB H100. Right: LoRA (r=16) on a single GPU consumes 17.9 GB peak memory, fitting comfortably on a single 24 GB or 80 GB GPU.

Analytical Compute Accounting (6ND)

For standard mixed-precision training, the theoretical floating-point operations per token is 6N (2N forward pass, 4N backward pass; see Lesson 7, Training FLOPs, Time and MFU). For a 2-epoch fine-tuning run on 50M unique tokens, the total tokens processed is D_{\text{total}} = 2 \times 50 \times 10^6 = 100 \times 10^6 = 10^8\text{ tokens}:

\text{Training FLOPs} = 6 \times N \times D_{\text{total}} = 6 \times 8.03 \times 10^9 \times 10^8 = 4.818 \times 10^{18}\text{ FLOPs}

Our compute hardware consists of one node with 8 NVIDIA H100 SXM GPUs. Each H100 provides 989 dense BF16 TFLOPS (TeraFLOPS). Assuming a standard 40% Model FLOPs Utilization (MFU):

\text{Cluster Effective FLOPS} = 8 \times 989 \times 10^{12} \times 0.40 = 3.1648 \times 10^{15}\text{ FLOPS}

Dividing total required FLOPs by effective cluster throughput yields the wall-clock training time:

\text{Training Time} = \frac{4.818 \times 10^{18}\text{ FLOPs}}{3.1648 \times 10^{15}\text{ FLOPS}} \approx 1,522.4\text{ seconds} \approx 25.37\text{ minutes}

Converting this to GPU-hours and financial cost at our standard assumption of $3.00 per H100-hour:

\text{GPU-Hours} = 8\text{ GPUs} \times \left(\frac{1,522.4}{3,600}\right) \approx 3.38\text{ GPU-hours} \text{Total Training Cost} = 3.38 \times \$3.00 \approx \$10.15

Notice the extraordinary contrast: while pretraining Llama 3.1 8B on 1 trillion tokens required 33,800 GPU-hours and $101,000 over 5.5 days, full fine-tuning on 50,000 customer-support conversations executes in 25 minutes and costs approximately $10! Compute is not the bottleneck in SFT; data curation is.

Memory Accounting: FSDP over 8 GPUs vs LoRA

In Lesson 3 (Training Memory), we established that standard mixed-precision training with Adam requires 16 bytes per parameter (2B weights + 2B gradients + 4B FP32 master weights + 8B Adam moments). For our 8.03B model, the total static model and optimizer state is:

\text{Total Static State} = 8.03 \times 10^9 \times 16\text{ bytes} \approx 128.48\text{ GB} \approx 128.5\text{ GB}

Full Fine-Tuning with FSDP (8 GPUs)

When running PyTorch Fully Sharded Data Parallel (FSDP) with FULL_SHARD across the 8 GPUs of our H100 node (Lesson 11, ZeRO and FSDP):

  • Sharded Model and Optimizer States: The 128.5 GB is divided equally across the 8 GPUs via high-speed NVLink (900 GB/s per GPU): \text{States per GPU} = \frac{128.48\text{ GB}}{8} \approx 16.06\text{ GB}
  • Activation Memory: With FlashAttention-2, sequence length 2,048, and per-device micro-batch size 2, intermediate activations require approximately 1.5 GB per GPU.
  • Communication and Workspace Buffers: All-Gather forward and Reduce-Scatter backward buffers add approximately 2.5 GB.
  • Total Peak Footprint per GPU: 16.06 + 1.5 + 2.5 \approx 20.06\text{ GB} (roughly 18.7 GiB).

An NVIDIA H100 SXM GPU provides 79.6 GiB (85.5 GB) of visible memory. Consuming 20.1 GB leaves over 70% of GPU memory free. Full fine-tuning on an 8-GPU node operates with massive safety margins against Out-Of-Memory (OOM) errors.

LoRA on a Single GPU (Lesson 23)

If a team lacks an 8-GPU node and trains on a single GPU using LoRA (Low-Rank Adaptation; see Lesson 23, LoRA and QLoRA):

  • Base Model Weights: Frozen in BF16: 8.03 \times 10^9 \times 2\text{ bytes} \approx 16.06\text{ GB}. Zero gradients and zero Adam optimizer states are allocated for base parameters.
  • Adapter Parameters and States: Applying rank r = 16 adapters to all linear attention and MLP projections updates approximately 20 million parameters (0.25% of the model). Adapter weights (40 MB in FP32/BF16) plus their Adam states (12 bytes/param) consume less than 0.3 GB.
  • Total Peak Footprint: 16.06 + 0.3 + 1.5\text{ (activations)} \approx 17.86\text{ GB}.

LoRA fits comfortably on a single 24 GB GPU (such as an NVIDIA RTX 4090 or L4), enabling post-training without multi-GPU cluster infrastructure.

Catastrophic Forgetting and Evaluation

When a language model undergoes supervised fine-tuning on a narrow task distribution (such as customer support dialogues), its parameter weights drift away from the pretraining manifold [8]. While the model rapidly acquires the desired conversational style, it risks catastrophic forgetting: losing the multi-step mathematical reasoning, algorithmic logic, or broad world knowledge learned during pretraining.

Evaluation trajectories during customer-support fine-tuning. Task compliancy surges to 94% within 1.5 epochs. General knowledge (MMLU) remains stable. Complex multi-step reasoning (GSM8K) degrades sharply after epoch 2 unless protected by pretraining data replay.

Why Forgetting Occurs

Neural networks suffer from retroactive interference. In transformers, higher self-attention layers and MLP projections specialize in logical induction and variable tracking (Lesson 2, Forward and Backward Passes). When fine-tuned exclusively on customer greeting templates and refund policies, gradient steps overwrite those induction attention heads with conversational boilerplate.

Detecting and Mitigating Forgetting

Production engineering teams employ four defense mechanisms:

  1. Continuous Benchmark Auditing: Throughout fine-tuning, evaluate checkpoints against both domain-specific validation sets (support ticket accuracy, JSON validity) and foundational general capability benchmarks: MMLU for factual knowledge, GSM8K for multi-step reasoning, and HumanEval for code syntax (Lesson 34, Evaluation During Training). A drop of more than 2%–3% on GSM8K signals excessive parameter drift.
  2. Pretraining Data Replay: Mix a small percentage (e.g., 5% to 10%) of raw pretraining data (general web text, code, and math) directly into the SFT conversational mixture. Replay gradients anchor attention heads to pretraining representations without impairing conversational alignment.
  3. Low Learning Rate and Early Stopping: Keep the learning rate at or below 5 \times 10^{-6} for 8B models and halt training at epoch 2. Overfitting past epoch 2 accelerates capability erosion.
  4. KL Divergence Penalty: In advanced post-training pipelines, add an explicit Kullback-Leibler (KL) regularization term penalizing policy drift from the frozen base model reference policy \pi_{\text{ref}}, a mechanism formalized in DPO (Lesson 25).

Which approach fits our customer-support product?

For our dedicated customer-support product on an 8×H100 node, we choose full fine-tuning with FSDP over 8 GPUs, using the Tülu 3 hyperparameter recipe (LR 5 \times 10^{-6}, batch size 128, 2 epochs) and 5% pretraining replay. Because our team has dedicated access to the 8×H100 node, full fine-tuning completes in just 25 minutes at a negligible compute cost of ~$10. Full fine-tuning avoids adapter serving overhead, eliminates rank capacity constraints on structured JSON tool-calling, and bakes support guidelines directly into the base weights. For rapid customer-specific experimentation or multi-tenant branching, LoRA is maintained as a complementary tool, but the core product model is fully fine-tuned.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Direct Preference Optimization (DPO) Hand-off: SFT models act as the reference policy \pi_{\text{ref}} for DPO. A weak or overfitted SFT model severely impairs downstream preference learning because DPO penalizes drift relative to the SFT policy (Lesson 25, DPO and Preference Optimization).
  • Length Bias in Supervised Demonstrations: SFT models are notorious for learning length heuristics: if demonstration answers are verbose, the model learns that generating more tokens yields lower training loss, resulting in verbose, sycophantic customer responses.
  • Tool-Calling and JSON Schema Adherence: Modern SFT recipes enforce structured syntax by formatting tool calls within reserved XML or JSON blocks (e.g., <tool_call>{"name": "check_balance", "args": {"user_id": 104}}</tool_call>) and penalizing invalid JSON during post-training evals.
  • Distillation from Frontier Teacher Models: When human demonstration dialogues are scarce, teams distill responses from larger models (such as GPT-4o or Claude 3.5 Sonnet). While highly effective for conversational fluency, distilled models often mimic teacher refusal behaviors and struggle on niche domain edge cases unless supplemented with real internal logs.
  • Safety and Refusal Alignment: SFT introduces deliberate refusal demonstrations ("I cannot help you bypass authentication protocols..."). Training on excessive refusal examples can cause the model to become over-cautious, refusing benign queries that share keywords with malicious prompts.
  • Weight Averaging Across SFT Checkpoints: Averaging checkpoints from epochs 1.5, 1.8, and 2.0 smooths out optimization variance, consistently yielding 0.5%–1.0% higher benchmark scores than the final step alone.

Summary

Mind map summarizing Supervised Fine-Tuning: base model alignment, assistant-only loss masking, Tülu 3 hyperparameters, 8×H100 FSDP compute and memory accounting, and forgetting mitigation.
  • Supervised Fine-Tuning (SFT) transforms raw base continuators into compliant, role-bounded assistants by training on conversational dialogues using assistant-only loss masking (setting prompt labels to -100).
  • Per the Superficial Alignment Hypothesis (LIMA), pretraining acquires world knowledge while SFT learns interaction style, format, and schemas; however, SFT cannot inject deep foundational skills without hallucination.
  • Verified recipes (Tülu 3) specify an optimal learning rate of 5 \times 10^{-6}, linear warmup and decay, batch size 128, and strict stopping at 1 to 2 epochs to prevent memorization and diversity collapse.
  • For our 50,000-conversation run on Llama 3.1 8B, 6ND compute arithmetic demonstrates that full fine-tuning executes in just 25.4 minutes across an 8×H100 node at a compute cost of ~$10.15.
  • Under FSDP across 8 GPUs, the 128.5 GB model and Adam states shard to 16.06 GB per GPU (peak footprint ~20.1 GB), leaving > 70% headroom on an 80 GB H100.
  • To mitigate catastrophic forgetting of multi-step math and coding capabilities, production pipelines cap epochs at 2, maintain low learning rates, and blend 5%–10% pretraining data replay into the fine-tuning stream.

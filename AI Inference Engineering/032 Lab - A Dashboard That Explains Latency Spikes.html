Lab - A Dashboard That Explains Latency Spikes

Introduction

When p99 latency jumps, the first question is always "why?", and the answer is usually already in the metrics. The serving engine knows how long requests waited and how full its KV cache is; the GPU knows whether it was throttled; the request counters know whether traffic or prompt length changed. What is usually missing is a dashboard that puts those signals side by side in an order that leads from the symptom to the cause, and alerts that fire on the causes before users feel the symptom.

In this lab we build that dashboard. vLLM exposes engine metrics on /metrics, NVIDIA's dcgm-exporter exposes GPU metrics, Prometheus scrapes both and evaluates alert rules, and Grafana draws the dashboard from provisioned files. Figure 1 shows the setup.

In this lab, we start the monitoring stack, learn what each metric measures and how to read latency histograms, build a dashboard with five rows (user-facing latency, load, saturation, GPU, and errors), write alerts on leading indicators, map symptom combinations to causes with a decision tree, rehearse the common failure modes, and walk through an incident end to end. Stage 6's lessons explain the metrics in depth: Lesson 28, p50, p95 and p99 Latency; Lesson 29, Queue Depth; Lesson 30, GPU Metrics; and Lesson 31, Per-Request Token Accounting.

Step 1: Start the Monitoring Stack

Start vLLM on the host as in earlier labs (vllm serve meta-llama/Llama-3.1-8B-Instruct --gpu-memory-utilization 0.90, setting 0.90 explicitly because recent releases default to 0.92). Then create the files below in one directory and run docker compose up -d. The first tab runs the three services. Prometheus reaches vLLM on the host through host.docker.internal, as in vLLM's own Prometheus and Grafana example [1]. dcgm-exporter needs the GPU and the SYS_ADMIN capability for the profiling fields [2].

Two settings matter more than they look. dcgm-exporter collects every 30 seconds by default, too coarse for a spike that lasts a minute, so we set DCGM_EXPORTER_INTERVAL to 5,000 ms [3]. And the default collector list leaves out the fields we need most, such as DCGM_FI_PROF_SM_ACTIVE and the throttling counters, so the third tab supplies our own list [4]. These are the names dcgm-exporter exposes and the ones you query in Prometheus; newer DCGM releases document some fields under new canonical names, but the exporter's names are what appear on /metrics.

Step 2: Know What Each Metric Measures

Where the time goes

vLLM times each phase of a request with its own histogram [5]. Figure 2 places them on one request's timeline. TTFT covers waiting in vLLM's queue plus prefill; time per output token covers decode; end-to-end covers everything vLLM sees. None of them includes time spent in a gateway in front of vLLM or on the network, so a user can feel latency that vLLM never reports. If you run Lab 27's gateway, its metrics fill that gap.

Table 2 lists the metrics the dashboard uses. Counters gain a _total suffix on /metrics, and histograms appear as _bucket, _sum, and _count series.

DCGM_FI_DEV_GPU_UTIL is worth one warning: it reports the share of time any kernel was running, so a GPU can read 100% while doing little work. DCGM_FI_PROF_SM_ACTIVE and DCGM_FI_PROF_DRAM_ACTIVE say how much of the chip is busy, which is what matters for a memory-bound decode (Lesson 30, GPU Metrics).

Reading latency histograms

Prometheus stores a histogram as cumulative bucket counters, one per upper bound le. histogram_quantile() finds the bucket that contains the requested rank and interpolates linearly inside it [6], so a percentile is an estimate whose precision depends on the bucket edges, as Figure 3 shows.

  • Aggregate buckets, never percentiles. Sum the bucket rates across replicas with sum by (le), then take the quantile. An average of per-replica p95s has no meaning.
  • Use bucket edges for SLOs. vLLM's default TTFT buckets include an edge at 0.5 s and its inter-token buckets one at 0.025 s, exactly the course's targets. The share of requests within target, the bucket rate at le="0.5" divided by the count rate, is therefore exact rather than interpolated.
  • Know the coarse spots. The queue-time and end-to-end histograms share buckets that start at 0.3 s, so their p50 at light load is not precise.

Step 3: Build the Dashboard

The dashboard reads top to bottom as a diagnosis, the order of the four golden signals and the USE method [7][8]: what users feel, what arrived, what filled up, what the GPUs did, and what failed. Figure 4 shows the layout.

Grafana loads data sources and dashboards from files at start-up [9]. The first two tabs are the provisioning files; place them under grafana/provisioning/datasources/ and grafana/provisioning/dashboards/. The data source has a fixed uid so that the dashboard can refer to it. The third tab generates the dashboard JSON in Grafana's classic JSON model, which Grafana 13 still loads through file provisioning; writing it from a short script keeps 20 panels consistent and easy to review. The last tab shows one panel of the generated file. Every query uses $__rate_interval, which Grafana sizes to the scrape interval.

def q(metric: str, p: float) -> str:

def pcts(metric: str) -> list:

Step 4: Alert on Leading Indicators

An alert on p95 TTFT tells you users are already suffering. The causes of a latency spike usually show up earlier: the queue starts growing, the KV cache fills, the prefix hit rate drops, a GPU gets throttled. Alerts on those leading indicators buy time to act, by adding replicas, shedding, or rolling back, before the symptom alert fires. Figure 5 shows the idea on an illustrative slow climb.

The rule file has two groups [10]. The leading group uses deriv() on a subquery to require that the queue is still growing, predict_linear() to catch a cache that will fill within 10 minutes, a comparison with the same time yesterday (offset 1d) to catch a prefix-cache regression, and the DCGM violation counters for throttling [11]. The symptom group pages on the SLO itself and on XID errors, which usually mean a GPU needs to be drained and replaced (Lesson 40, Reliability and Rollouts). Each for period keeps a brief blip from paging anyone.

rules.yml
groups:
  - name: llm-leading-indicators       # fire before users feel it
    rules:
      - alert: QueueBuilding
        expr: sum(vllm:num_requests_waiting) > 5 and deriv(sum(vllm:num_requests_waiting)[5m:30s]) > 0
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "{{ $value }} requests waiting and the queue is still growing"
      - alert: KVCacheFillingUp
        expr: max(vllm:kv_cache_usage_perc) > 0.9 or max(predict_linear(vllm:kv_cache_usage_perc[10m], 600)) > 1
        for: 3m
        labels:
          severity: warning
        annotations:
          summary: "KV cache above 90% or on course to fill within 10 minutes"
      - alert: Preempting
        expr: sum(rate(vllm:num_preemptions_total[5m])) > 0
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "vLLM is preempting requests: the KV cache is overcommitted"
      - alert: PrefixCacheHitRateDropped
        expr: |
          sum(rate(vllm:prefix_cache_hits_total[10m])) / sum(rate(vllm:prefix_cache_queries_total[10m]))
            < 0.5 * (sum(rate(vllm:prefix_cache_hits_total[10m] offset 1d))
                     / sum(rate(vllm:prefix_cache_queries_total[10m] offset 1d)))
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "Prefix cache hit rate is less than half of yesterday's"
      - alert: GPUThrottling
        expr: max by (gpu) (rate(DCGM_FI_DEV_POWER_VIOLATION[5m]) + rate(DCGM_FI_DEV_THERMAL_VIOLATION[5m])) > 0
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "GPU {{ $labels.gpu }} is being slowed by power or thermal limits"
  - name: llm-slo                      # fire when users already feel it
    rules:
      - alert: TTFTSLOBreach
        expr: histogram_quantile(0.95, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m]))) > 0.5
        for: 5m
        labels:
          severity: page
        annotations:
          summary: "p95 TTFT is {{ $value }} s (target 0.5 s)"
      - alert: TPOTSLOBreach
        expr: histogram_quantile(0.95, sum by (le) (rate(vllm:request_time_per_output_token_seconds_bucket[5m]))) > 0.025
        for: 5m
        labels:
          severity: page
        annotations:
          summary: "p95 TPOT is {{ $value }} s (target 0.025 s)"
      - alert: GPUXidError
        expr: max by (gpu) (DCGM_FI_DEV_XID_ERRORS) > 0
        labels:
          severity: page
        annotations:
          summary: "GPU {{ $labels.gpu }} reported XID {{ $value }}"

Check the file with promtool check rules rules.yml; it should report 8 rules. Firing alerts appear on Prometheus's Alerts page; add Alertmanager to route them to people.

Step 5: From Symptom to Cause

When the SLO alert fires, walk the dashboard with the questions in Figure 6. Each question looks at one or two panels, and the first "yes" usually names the cause. The order matters: traffic and prompt changes are the most common causes and the easiest to confirm, so they come first.

CauseWhat the dashboard shows
Traffic surgeFinished requests and tokens/s up together; waiting rises; prompt length flat
Long promptsPrompt tokens/s and prompt length p95 up at a flat request rate; TTFT up more than TPOT

Slow or throttled GPUOne instance slower; its SM clock lower, its violation counters rising, or its temperature high

Step 6: Rehearse the Failure Modes

A dashboard is only trustworthy once you have watched it explain failures you caused on purpose. Run a steady baseline with a shared prefix, then inject one cause at a time and check that the decision tree finds it. The baseline matches the running example: a 1,600-token shared prefix plus 400 random tokens, 500 output tokens, at 4 requests per second, about 80% of the course's figure of 5 requests per second per H100, which assumes no cache hits [12].

What you should see: the surge raises the request rate and the waiting queue together; the prefix-cache miss leaves the request rate and prompt length unchanged while the hit rate falls from about 80% to near zero; long prompts raise prompt tokens per second and TTFT more than TPOT; and the power cap lowers the SM clock and starts the power-violation counter. If one of these does not show up where Table 3 says it should, fix the dashboard before you need it.

Reading the Results: A Worked Incident

Here is how the dashboard explains a real kind of incident. The timeline in Figure 7 is illustrative, but its numbers follow from the running example.

A fleet of six H100 replicas serves the daily peak of about 33 requests per second, 5.5 per replica. The team sized it with prefix caching in mind: with 1,600 of each 2,000-token prompt served from cache, Lesson 21's capacity model gives about 9.6 requests per second per replica at the 25 ms target, so 5.5 looked comfortable. At 14:02 a deploy adds a request timestamp to the start of the system prompt.

  1. 14:05, QueueBuilding fires. The on-call engineer opens the dashboard. Latency row: TTFT p95 is climbing while TPOT has risen only a little, so the pressure is in prefill.
  2. Question 1, traffic surge? No: finished requests per second are flat at about 33.
  3. Question 2, long prompts? No: prompt length p50 and p95 are unchanged at about 2,000 tokens.
  4. Question 3, prefix-cache miss? Yes: the hit rate fell from about 80% to under 5% at 14:02, the minute of the deploy. Every request now prefills 2,000 tokens instead of 400, five times the prefill work: 33 × 2,000 ≈ 67,000 tokens per second instead of 13,000. Without cache hits, the model's limit per replica drops to about 5.7 requests per second, and each replica is receiving 5.5, so the fleet is at 96% of its new limit and the queue grows.
  5. 14:09, the TTFT alert pages. The cause is already known. The diff shows the timestamp at the start of the prompt, which makes every prompt unique from its first token, so no prefix is ever shared (Lesson 24, Prefix Caching).
  6. 14:16, rollback; 14:20, recovered. The hit rate returns within a minute, the queue drains, and TTFT falls back to 0.3 s.

The follow-ups matter more than the fix: put variable content at the end of prompts, keep the PrefixCacheHitRateDropped alert, and either size the fleet to survive a total loss of cache hits or treat the hit rate as a capacity input that is watched like one.

Common Pitfalls

  • Averaging percentiles. avg(histogram_quantile(...)) across replicas is wrong; aggregate buckets with sum by (le) first.
  • Rate windows shorter than two scrapes. rate() needs at least two samples in the window. $__rate_interval handles this in Grafana; in alert rules, use windows of a minute or more with a 5-second scrape.
  • Trusting DCGM_FI_DEV_GPU_UTIL. A memory-bound decode can show 100% utilization while its SMs are mostly idle. Read SM and DRAM activity instead.
  • A coarse exporter interval. At dcgm-exporter's default 30 seconds, a 20-second throttle event can vanish between samples.
  • Missing the gateway's view. vLLM's TTFT starts when vLLM receives the request. Time queued in a gateway, a load balancer, or the client is invisible unless you export it too.
  • Too many alerts. Leading-indicator alerts should notify, not page. Page only on the SLO and on hardware errors, or people learn to ignore the pager.
  • High-cardinality labels. Per-request or per-user labels on server metrics can overwhelm Prometheus. Keep tenant-level accounting in the gateway or in logs (Lesson 31).

Stretch Goals

  • Add a $instance template variable so that every panel can switch between the fleet and one replica.
  • Add recording rules for the p95 TTFT and the within-target share, and build a multi-window burn-rate alert on the SLO.
  • Export per-tenant prompt and output token counters from Lab 27's gateway and add the noisy-tenant panel.
  • Annotate deploys on the dashboard, so that a step change lines up with the change that caused it.
  • Repeat Step 6 with Lab 27's spike test and check that the dashboard explains every phase of the timeline.

Summary

  • Prometheus scrapes vLLM's vllm:* metrics and dcgm-exporter's DCGM_FI_* metrics every 5 seconds; set the exporter's collection interval to match and enable the profiling fields.
  • TTFT is queue time plus prefill, TPOT is decode, and none of vLLM's histograms include time spent in front of vLLM.
  • Aggregate histogram buckets across replicas before taking a quantile; with bucket edges at 0.5 s and 25 ms, the share of requests within target is exact.
  • Lay out the dashboard as a diagnosis: latency, load, saturation, GPU, errors.
  • Alert early on growing queues, a filling KV cache, a falling prefix hit rate, and throttling; page on the SLO.
  • Walk the decision tree: surge, long prompts, prefix-cache miss, cache thrash, slow GPU, cold replicas, noisy tenant.

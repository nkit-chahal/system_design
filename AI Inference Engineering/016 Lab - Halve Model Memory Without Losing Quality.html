Lab - Halve Model Memory Without Losing Quality

Introduction

Lesson 13, Quantization - FP8, INT8 and 4-bit, showed that storing weights in fewer bits shrinks a model and often speeds up decode. The goal of this lab is the practical version of that promise: cut the model's weight memory by at least 50% and prove that quality held. Both halves matter. Memory is easy to measure and easy to get right. Quality is easy to measure badly, and a quantized model that quietly answers 3% of questions differently can pass a careless check.

So we define what "quality held" means before touching the model, measure a BF16 baseline, quantize, serve the quantized model, and repeat exactly the same measurements. Figure 1 shows the loop.

In this lab, we build an evaluation set from a public benchmark and our own prompts, quantize Llama 3.1 8B Instruct to FP8 and to 4-bit with llm-compressor, measure memory from the engine's log, and decide with a rule written down in advance. Along the way we find that the 50% target is harder than the bit widths suggest: FP8 weights alone cannot reach it on this model.

FP8 needs care on older GPUs. vLLM runs FP8 matrix multiplications on GPUs with compute capability 8.9 or higher (Ada Lovelace, Hopper, Blackwell); on Turing and Ampere it still loads FP8 checkpoints, but as weight-only W8A16 through Marlin kernels, which saves the memory without the faster math [11]. 4-bit W4A16 checkpoints run on compute capability 8.0 and newer [12]. Step 1: Define "Quality Held" Before You Start

An evaluation chosen after seeing the results is not an evaluation. We fix three things first: the public benchmark, our own task set, and the decision rule. Figure 2 shows how they fit together.

The public benchmark. We use GSM8K, 1,319 grade-school math problems whose answer is a single number [6], run 5-shot through lm-evaluation-harness [9]. It is generative, and one wrong step changes the final answer, so damage shows up as wrong answers rather than as subtle shifts in probability. MMLU, 14,042 multiple-choice questions across 57 subjects [7], is a common second benchmark; it scores by log-likelihood, so it is easiest to run with lm-eval's in-process vLLM backend while the server is stopped. Benchmark numbers are sensitive to prompt format, few-shot count, and answer extraction [8], so the only comparison that means anything is between two runs with identical settings, never against a number from a paper.

Your own task set. A public benchmark does not know what your product does. Collect 100 to 200 real prompts from your traffic, each with an answer that a script can check: an exact string, a number, a required phrase, a regular expression, or the keys a JSON reply must contain. The first tab below shows the format; the second scores the set against any OpenAI-compatible server.

"""own_eval.py: score your own task prompts against an OpenAI-compatible server.

Each line of the task file is a JSON object such as
  {"id": "refund-017", "prompt": "...", "check": {"type": "number", "value": 42}}
Check types: exact, contains, regex, number (last number in the answer), json_keys.
Writes one JSON line per item ({"doc_id", "filter", "score", "output"}) for compare.py.
"""
import argparse
import asyncio
import json
import re

import httpx


def last_number(text):
    nums = re.findall(r"-?\d+(?:,\d{3})*(?:\.\d+)?", text)
    return float(nums[-1].replace(",", "")) if nums else None


def parse_json(text):
    text = re.sub(r"^```(?:json)?\s*|\s*```$", "", text.strip())
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        return None


def score(output, check):
    kind, value = check["type"], check["value"]
    if kind == "exact":
        return float(" ".join(output.split()).lower() == " ".join(str(value).split()).lower())
    if kind == "contains":
        return float(str(value).lower() in output.lower())
    if kind == "regex":
        return float(re.search(value, output, flags=re.S) is not None)
    if kind == "number":
        got = last_number(output)
        return float(got is not None and abs(got - float(value)) < 1e-6)
    if kind == "json_keys":
        obj = parse_json(output)
        return float(isinstance(obj, dict) and all(k in obj for k in value))
    raise ValueError(f"unknown check type {kind!r}")


async def run_item(client, sem, args, item):
    payload = {"model": args.model, "temperature": 0.0, "max_tokens": args.max_tokens,
               "messages": [{"role": "user", "content": item["prompt"]}]}
    async with sem:
        for attempt in range(3):
            try:
                r = await client.post("/chat/completions", json=payload)
                r.raise_for_status()
                output = r.json()["choices"][0]["message"]["content"] or ""
                break
            except httpx.HTTPError:
                if attempt == 2:
                    raise
                await asyncio.sleep(2)
    return {"doc_id": item["id"], "filter": "own", "score": score(output, item["check"]),
            "output": output}


async def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--base-url", default="http://localhost:8000/v1")
    ap.add_argument("--model", required=True)
    ap.add_argument("--tasks", required=True, help="JSONL file of task prompts")
    ap.add_argument("--out", required=True)
    ap.add_argument("--max-tokens", type=int, default=512)
    ap.add_argument("--concurrency", type=int, default=16)
    args = ap.parse_args()

    items = [json.loads(line) for line in open(args.tasks, encoding="utf-8") if line.strip()]
    sem = asyncio.Semaphore(args.concurrency)
    async with httpx.AsyncClient(base_url=args.base_url, timeout=300) as client:
        rows = await asyncio.gather(*(run_item(client, sem, args, it) for it in items))
    with open(args.out, "w", encoding="utf-8") as f:
        for row in rows:
            f.write(json.dumps(row) + "\n")
    acc = sum(r["score"] for r in rows) / len(rows)
    print(f"{len(rows)} items, accuracy {100 * acc:.1f}%")


if __name__ == "__main__":
    asyncio.run(main())

The threshold and the decision rule. We accept a quantized model if its score drops by no more than 1.0 point absolute on every evaluation. A single number is not enough on its own, because every score is a sample. At about 80% accuracy on 1,319 problems, the standard error of one score is √(0.8 × 0.2 ÷ 1,319) ≈ 1.1 points, so two independent runs could differ by a point by chance. Since both models answer the same items, we compare them paired, item by item, which is far tighter. On a 150-item task set one item is worth 0.67 points, so a 1-point threshold is a margin of 1.5 items; such a set catches large regressions but cannot prove a sub-point one. The full rule, in Step 5, therefore has a third outcome besides pass and fail: inconclusive, meaning "collect more items".

Step 3: Quantize

We build two variants with llm-compressor [10], the quantization library maintained alongside vLLM. FP8 dynamic stores each Linear layer's weights in FP8 (E4M3) with one scale per output channel, and quantizes activations to FP8 on the fly with one scale per token, so it needs no calibration data [3][11]. W4A16 stores weights in 4 bits in groups of 128, with one 16-bit scale per group, and keeps activations in 16 bits; it uses GPTQ, which quantizes one layer at a time and corrects the rounding error using 512 calibration samples [1][12]. Both recipes leave lm_head, the output projection, in BF16. Run the scripts in a second environment.

"""quantize_fp8.py: FP8 weights (per channel) and dynamic FP8 activations (per token).

Run in the llm-compressor environment. Needs no calibration data.
"""
from transformers import AutoModelForCausalLM, AutoTokenizer

from llmcompressor import oneshot
from llmcompressor.modifiers.quantization import QuantizationModifier

MODEL_ID = "meta-llama/Llama-3.1-8B-Instruct"
SAVE_DIR = "Llama-3.1-8B-Instruct-FP8-Dynamic"

model = AutoModelForCausalLM.from_pretrained(MODEL_ID, dtype="auto")
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)

# Every Linear layer except the output head. The embedding table is not a Linear
# layer, so it also stays in BF16.
recipe = QuantizationModifier(targets="Linear", scheme="FP8_DYNAMIC", ignore=["lm_head"])
oneshot(model=model, recipe=recipe)

model.save_pretrained(SAVE_DIR)
tokenizer.save_pretrained(SAVE_DIR)

What you should see. Model loading took drops to about 8.5 GiB for FP8 and about 5.3 GiB for W4A16. nvidia-smi, however, shows almost the same 72 GiB as before. This is the most common confusion in this lab, and Figure 3 explains it: vLLM sizes its KV cache to fill whatever its memory budget leaves after weights and runtime overhead, so every gigabyte saved on weights becomes cache. The saving appears as more cache tokens and more concurrent requests, not as free GPU memory. To see weight memory, read the engine's log line, or the size of the checkpoint files; to see free memory, you would have to lower --gpu-memory-utilization.

Holding the runtime overhead at the 4.6 GiB of Lesson 3, the cache grows from about 52.1 GiB to 58.6 GiB with FP8 and 61.7 GiB with W4A16. At 8,192 tokens per GiB, that is about 426,000, 480,000, and 505,000 tokens: roughly 12% and 18% more concurrent chat requests on the same GPU.

Step 5: Compare and Decide

The comparison script reads two per-item files, the baseline's and a candidate's, and reports both scores, the paired change with a bootstrap 95% confidence interval, the answers that flipped, and the decision. It works on lm-eval's samples files and on own_eval.py output alike.

compare.py
Run it
"""compare.py: paired comparison of a baseline and a quantized run on the same items.

Inputs are lm-eval samples files (samples_<task>_<time>.jsonl, from --log_samples) or
own_eval.py output. Prints both accuracies, the paired difference with a bootstrap 95%
confidence interval, the answers that flipped, and a decision against --threshold.
"""
import argparse
import json
import random


def load(path, metric, filt):
    scores = {}
    for line in open(path, encoding="utf-8"):
        if not line.strip():
            continue
        rec = json.loads(line)
        if filt and rec.get("filter") != filt:
            continue
        scores[str(rec["doc_id"])] = float(rec[metric])
    return scores


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("baseline")
    ap.add_argument("candidate")
    ap.add_argument("--metric", default="exact_match", help="'score' for own_eval.py files")
    ap.add_argument("--filter", default="flexible-extract", help="'own' for own_eval.py files")
    ap.add_argument("--threshold", type=float, default=1.0, help="largest acceptable drop, points")
    ap.add_argument("--boot", type=int, default=10000)
    args = ap.parse_args()

    base = load(args.baseline, args.metric, args.filter)
    cand = load(args.candidate, args.metric, args.filter)
    ids = sorted(set(base) & set(cand))
    if len(ids) != len(base) or len(ids) != len(cand):
        raise SystemExit(f"item sets differ: {len(base)} vs {len(cand)}, {len(ids)} shared")
    n = len(ids)
    diffs = [cand[i] - base[i] for i in ids]
    delta = 100 * sum(diffs) / n
    lost = sum(1 for i in ids if base[i] > cand[i])
    gained = sum(1 for i in ids if cand[i] > base[i])

    rng = random.Random(0)
    boots = sorted(100 * sum(rng.choice(diffs) for _ in range(n)) / n for _ in range(args.boot))
    lo, hi = boots[int(0.025 * args.boot)], boots[int(0.975 * args.boot) - 1]

    print(f"items: {n}")
    print(f"baseline:  {100 * sum(base[i] for i in ids) / n:.2f}%")
    print(f"candidate: {100 * sum(cand[i] for i in ids) / n:.2f}%")
    print(f"change:    {delta:+.2f} points, 95% CI [{lo:+.2f}, {hi:+.2f}]")
    print(f"flips:     {lost} items lost, {gained} gained ({100 * (lost + gained) / n:.1f}% changed)")
    if -delta <= args.threshold:
        print("decision:  ACCEPT, drop within threshold")
    elif hi < 0:
        print("decision:  REJECT, the drop is larger than the threshold and not noise")
    else:
        print("decision:  INCONCLUSIVE, drop above threshold but within noise; add items")


if __name__ == "__main__":
    main()

Reading the Results

Why FP8 is not half and 4-bit is not a quarter

If every weight shrank with its bit width, FP8 would take 8.03 GB, exactly half of 16.06 GB, and 4-bit would take 4.02 GB, a quarter. The published checkpoints are 9.08 GB and 5.74 GB. Figure 6 shows where the difference comes from.

Two things do not shrink. The first and larger is the vocabulary. Llama 3.1 has 128,256 tokens, so its embedding table and its output head each hold 128,256 × 4,096 ≈ 525 million parameters: together 1.05 billion, 13% of the model. The embedding table is a lookup, not a Linear layer, and both recipes deliberately leave lm_head in BF16, so these 2.10 GB stay the same size in every variant. The second is metadata. FP8 per-channel scales are tiny, one per output row, about 3 MB in all. 4-bit groups of 128 need one 16-bit scale per 128 weights, plus a 4-bit zero point in asymmetric formats such as AWQ: 6.98 billion ÷ 128 ≈ 54.5 million groups, about 0.14 GB. Table 3 puts the pieces together.

The consequence for our goal is direct: FP8 weights alone cannot cut this model's weight memory by 50%. Even quantizing the output head as well would only reach about 8.56 GB, 47%. The same arithmetic applies to FP8 plus an FP8 KV cache measured on total serving memory: at 170 chat requests of 2,500 tokens, BF16 needs 16.06 GB of weights plus 55.7 GB of cache, 71.8 GB, while FP8 for both needs 9.08 + 27.9 = 36.9 GB, a 48.5% cut. Because the 2.10 GB of 16-bit embeddings never shrink, an all-FP8 deployment approaches 50% but never passes it. So for this model, "50% or more" means 4-bit weights. If your team's goal is really "as much memory as possible with no measurable quality loss", define the metric that way and FP8 may be the better answer; the point is to say which metric you mean.

Small models show the same effect more strongly. Qwen2.5-1.5B's embedding table is 233 million of its 1.54 billion parameters, 15%. Its official GPTQ-Int4 build is 1.15 GB, 63% smaller than the 3.09 GB BF16 model, but the official AWQ build is 1.61 GB, only 48% smaller, because it stores a separate 16-bit copy of the output head instead of sharing the embedding table. Two "4-bit" checkpoints of the same model land on opposite sides of the target, which is why we measure instead of assuming.

Did quality hold?

Figure 7 sketches the typical shape of the result. The horizontal position of each variant is fixed by the arithmetic above; the vertical position is what your evaluations decide, and it is drawn here only for illustration.

A study of more than 500,000 evaluations across the Llama 3.1 family found FP8 weight-and-activation quantization effectively lossless and 4-bit weight-only quantization rivaling 8-bit [4], but "on average across benchmarks" is not "on your task set", which is why the lab exists. Look beyond the accuracy change, too. Two models can have the same accuracy while answering many questions differently. Dutta et al. call these changed answers flips, show that compressed models with near-identical accuracy can behave noticeably differently, and propose reporting flips alongside accuracy [5]. Read the lost items from own.jsonl by hand: they tell you what quantization damaged, for example long arithmetic, rare names, or strict output formats.

Which variant fits our deployment?

If W4A16 passes on both GSM8K and the task set, ship it: weights drop from 16.06 GB to 5.74 GB, 64%, and the same GPU holds about 18% more cache for concurrent requests. Then re-check speed with the client from Lesson 6, Lab - Measure TTFT and Throughput, because the formats trade places with load: the same study found W4A16 the most cost-efficient at low concurrency and W8A8 ahead under continuous batching [4] (Lesson 13). If W4A16 fails but FP8 passes, FP8 is the safe fallback: it misses the 50% target at 43%, says so honestly in the write-up, and can be paired with an FP8 KV cache for capacity. If both fail, the next section applies.

When the result fails, and what to try next

  • Use a different method. If simple round-to-nearest 4-bit fails, calibration-based methods such as GPTQ [1] or AWQ [2] usually recover much of the loss. If 4-bit fails outright, step back to an 8-bit format: FP8 on Hopper, or INT8 weights and activations on GPUs without FP8.
  • Keep sensitive layers in higher precision. Add entries to the recipe's ignore list; llm-compressor accepts regular expressions with a re: prefix, such as "re:.*mlp.down_proj". Common candidates are the first and last decoder blocks and the MLP down-projections, but measure which ones matter rather than guessing. Each kept layer costs memory, so recompute the reduction.
  • Calibrate on your own data. GPTQ and AWQ fit their corrections to the calibration set. If your traffic is code, legal text, or another language, replace the general chat data with a few hundred of your own prompts.
  • Treat the KV cache as a separate change. An FP8 KV cache (--kv-cache-dtype fp8) halves the cache per token, from 128 KiB to 64 KiB [13], but it is a different risk, mostly on long contexts. Evaluate it as its own step so that a regression can be traced to one change.
  • Grow the evaluation if the result was inconclusive. More items narrow the interval; a second public benchmark such as MMLU adds coverage.
  • Reconsider the model. A smaller model trained for the task can beat a heavily quantized larger one (Lesson 14, Distillation).

Common Pitfalls

  • Reading nvidia-smi as weight memory. vLLM fills its budget with KV cache, so used memory hardly changes. Use the Model loading took line or the checkpoint size.
  • Changing two things at once. Different few-shot counts, a chat template on one run, a different max_length, or a different answer filter can move GSM8K by more than quantization does. Keep the evaluation command byte-for-byte identical.
  • Comparing with published numbers. A paper's GSM8K score for the same model used a different harness version and prompt. The only valid baseline is your own BF16 run.
  • Using --limit for the final decision. lm-eval's --limit is for testing commands; a 250-problem subset has an interval more than twice as wide as the full set.
  • Sampling with temperature. Non-zero temperature adds run-to-run noise to both models. Both scripts use temperature 0.
  • One environment for everything. llm-compressor and vLLM pin different library versions; install them separately.
  • Assuming "4-bit" means "a quarter". Embeddings, the output head, and scales stay large. Check the files.

Stretch Goals

  • Add an FP8 KV cache to the winning variant, rerun both evaluations, and report total serving memory for 170 concurrent chat requests as a second metric.
  • Measure speed: run the concurrency sweep from Lesson 6, Lab - Measure TTFT and Throughput, for BF16, FP8, and W4A16 and plot per-user tokens/s at each concurrency.
  • Run MMLU with lm-eval's in-process vllm backend for all three variants and add it to the decision rule.
  • Quantize with a calibration set drawn from your own prompts and compare against the general-purpose calibration data.
  • Use the same arithmetic to work out whether Llama 3.1 70B in W4A16 fits on one H100 with room for cache, then check it against Lesson 17, VRAM Budgeting.

Summary

  • Define "quality held" first: GSM8K's 1,319 problems through lm-eval, 100 to 200 of your own auto-scored prompts, and a drop of at most 1 point on each.
  • Compare paired, item by item, with a 95% confidence interval and a count of flipped answers; an inconclusive result means "add items", not "pass".
  • Llama 3.1 8B checkpoints are 16.06 GB in BF16, 9.08 GB in FP8 dynamic (43% smaller), and 5.74 GB in W4A16 (64% smaller).
  • FP8 is not half and 4-bit is not a quarter because the 2.10 GB of 16-bit embeddings and LM head never shrink; FP8 alone cannot reach a 50% cut on this model.
  • vLLM turns saved weight memory into KV cache: about 426K, 480K, and 505K tokens on one H100, while nvidia-smi barely changes.
  • If a variant fails, change the method, keep sensitive layers in BF16, calibrate on your own data, and evaluate an FP8 KV cache as a separate step.

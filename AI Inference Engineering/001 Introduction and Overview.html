Introduction and Overview

Introduction

Training a large language model is a project. Serving it is a business. A model is trained once, but every chat message, code completion, and agent step afterwards is an inference request that must be answered quickly, reliably, and cheaply, often thousands of times per second. For most companies that deploy LLMs, inference is where the GPUs, the latency complaints, and the cloud bill end up.

Inference engineering is the discipline of running models in production: choosing how a model is served, on which hardware, with which optimizations, and how to keep it healthy under real traffic. It sits between machine learning and systems engineering. You need to understand how a transformer generates tokens, how GPU memory and bandwidth limit it, and how classic distributed-systems ideas such as queues, load balancing, autoscaling, and observability apply when every request holds gigabytes of state on a GPU.

Figure 1 follows a single request through a typical serving stack. Every box in it is a lesson in this course. In this first lesson, we set up the vocabulary, the numbers that bound every design, a framework for answering inference design questions, and a map of the course.

Clarifying the Problem

Most inference design discussions, in interviews and at work, start from a vague request such as "we want to serve an open model for our product". Here is a typical exchange that turns it into something we can design for:

Candidate: What is the product, and who waits for the output?
Interviewer: A chat assistant inside our app. Users read the answer as it streams.

Candidate: Which model, and do we need to fine-tune it?
Interviewer: Llama 3.1 8B Instruct for now, as released. We may try a 70B model later.

Candidate: What do requests look like?
Interviewer: About 2,000 prompt tokens, most of them a shared system prompt and chat history, and about 500 output tokens.

Candidate: How much traffic?
Interviewer: Around 1,000 requests per minute on average. Product launches can bring short spikes of ten times that.

Candidate: What latency do users need?
Interviewer: The first words should appear within about half a second, and the text should stream at least as fast as people read.

Candidate: What hardware and budget do we have?
Interviewer: NVIDIA H100 GPUs in the cloud. The budget is whatever it takes to meet the targets, but we want to know the cost per million tokens.

This scenario is the running example of the course. Each lesson returns to it and answers one part of the underlying question: how do we serve this model to these users, within these latency targets, at the lowest cost, and how do we know it is working?

The Vocabulary of Inference

Two phases: prefill and decode

An LLM answers in two phases. In prefill, it reads the whole prompt in one parallel pass and computes the first output token. In decode, it generates the rest of the answer one token at a time, each step feeding the previous token back in. The two phases stress the hardware in opposite ways: prefill is limited by arithmetic, decode by memory bandwidth. Lesson 2, Prefill vs Decode, explains why, and almost every optimization in this course targets one phase or the other.

To avoid redoing work at every decode step, the model stores the attention keys and values of all previous tokens in the KV cache. The cache grows with every token and lives in GPU memory, so it, rather than the model weights, usually decides how many users one GPU can serve (Lesson 3, KV Cache).

The latency of a streamed answer

Because answers stream, "latency" is not one number. Figure 2 breaks a single response into its parts.

end-to-end latency=TTFT+TPOT×(output tokens−1)

For our 500-token answers, end-to-end latency is dominated by decoding: even a fast first token of 0.3 s is followed by about 12.5 s of streaming at 25 ms per token. Users judge responsiveness by the first number and reading comfort by the second, so we track them separately.

The Numbers That Bound Every Design

A few pieces of arithmetic explain most of inference performance. You should be able to do them on a whiteboard for any model and GPU. For Llama 3.1 8B in BF16 on one H100, they are:

  • Weights: 8.03 billion parameters [4] × 2 bytes ≈ 16 GB. Every decode step must read all of them from memory.
  • Decode speed limit: the H100 reads memory at 3.35 TB/s [5], so one decode step takes at least 16 GB ÷ 3.35 TB/s ≈ 4.8 ms. A single stream can never exceed about 200 tokens per second, no matter how much compute the GPU has.
  • Prefill cost: a forward pass costs about 2 FLOPs per parameter per token, so a 2,000-token prompt needs 2 × 8.03 × 10⁹ × 2,000 ≈ 32 TFLOPs. At 50% of the H100's 989 dense BF16 TFLOPS, that is about 65 ms.
  • KV cache: 128 KiB per token, about 312 MiB for a 2,500-token conversation. About 52 GiB of free memory holds roughly 426,000 tokens, so about 170 such conversations fit at once (Lesson 3).

These numbers already tell a story. Prefill is cheap per request but scales with prompt length. Decode is bounded by memory reads [3], so the way to use a GPU well is to batch many users into each decode step: the weights are read once per step for everyone. Batching is limited by the KV cache, and a fuller batch makes each step slower for every user. Most of Stages 1 to 4 elaborate this trade-off between per-user speed and total throughput.

Interview tip

Before proposing any design, write down the weights size, the KV cache bytes per token, the GPU's memory bandwidth and its compute. Ten seconds of arithmetic tells you whether a model fits, how fast a single stream can be, and roughly how many users one GPU can carry.

A Framework for Inference Design Questions

Like the ML system design framework in the Generative AI chapters, inference questions have a reliable structure. Figure 3 shows the seven steps we follow in every lab and in most real projects.

1. Clarify requirements

Pin down the model and its quality bar, the latency targets as percentiles [9] (for example p95 TTFT under 500 ms), traffic volume and its peaks, and the budget. "Low latency" is not a requirement; "p95 TTFT under 500 ms at 1,000 requests per minute" is.

2. Model the workload

Describe the traffic in tokens, not just requests: the distribution of prompt and output lengths, how much of each prompt is shared between requests, and how bursty arrivals are. A workload of short prompts and long answers is decode-heavy; retrieval-augmented generation with long documents is prefill-heavy. The design differs.

3. Choose the model and its precision

The smallest model that meets the quality bar is usually the biggest cost lever. Quantization (Lesson 13), distillation (Lesson 14), and speculative decoding (Lesson 15) make a given model cheaper and faster, provided an evaluation shows the quality held.

4. Choose the engine and its configuration

vLLM [6], SGLang [7], and TensorRT-LLM [8] all implement continuous batching [2] and paged KV caches [1]. Their differences, and the handful of settings that control capacity and latency, are the subject of Stage 2.

5. Size the hardware

Budget GPU memory (Lesson 17), decide whether one GPU is enough or the model must be split (Lesson 18), estimate per-GPU capacity at the latency target, and convert it into a GPU count and a cost per million tokens (Lessons 19–21).

6. Design for production

Traffic is not constant. Autoscaling, cold starts, prefix caching, request routing, and rate limiting (Stage 5) decide whether the system survives a spike and how much idle capacity we pay for.

7. Observe and iterate

Measure latency percentiles, queue depth, GPU behavior, and tokens per request (Stage 6). Real traffic always differs from the plan, and the measurements feed back into the workload model.

How to use the labs

Every lab offers two paths. The small path runs on a laptop or a consumer GPU with a model of 0.5B to 3B parameters; it is enough to see every effect the course describes, just at smaller numbers. The full path uses a cloud H100 with Llama 3.1 8B, matching the running example. vLLM and SGLang run on Linux; on Windows, use WSL2, or use Ollama for the first lab. Labs show expected results either as arithmetic you can check or as clearly labelled illustrations; your own measurements are the real results.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Why serving cost is driven by output tokens more than input tokens, and how API pricing reflects it (Lesson 20).
  • Disaggregated serving, which runs prefill and decode on separate GPU pools so each can be tuned for its bottleneck (Lesson 34).
  • Mixture-of-experts models, which activate only part of their weights per token and change the memory and parallelism math (Lesson 35).
  • Reasoning models that generate thousands of hidden tokens per answer, which shifts the workload heavily toward decode.
  • Agentic workloads, where many short calls share long prefixes, making prefix caching and cache-aware routing central (Lessons 24 and 25).
  • Serving on non-NVIDIA accelerators (AMD GPUs, Google TPUs, AWS Inferentia), and how engine support differs.

Summary

  • Inference is the ongoing cost of every deployed model; inference engineering decides its latency, reliability, and price.
  • Generation has two phases: compute-bound prefill and memory-bound decode, with the KV cache holding each request's state in GPU memory.
  • A streamed answer has a time to first token and a time per output token; end-to-end latency is TTFT + TPOT × (tokens − 1).
  • Four numbers bound every design: weight bytes, KV cache bytes per token, memory bandwidth, and compute. For Llama 3.1 8B on an H100: 16 GB, 128 KiB, 3.35 TB/s, 989 TFLOPS.
  • Answer design questions in seven steps: requirements, workload, model, engine, hardware, production, observability.
  • The course follows six roadmap stages, each ending in a lab on the same running example, plus a seventh stage of advanced serving topics.

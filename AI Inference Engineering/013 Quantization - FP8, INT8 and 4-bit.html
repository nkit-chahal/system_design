Quantization - FP8, INT8 and 4-bit

Introduction

A model's weights are usually stored in BF16, two bytes per number. Llama 3.1 8B therefore occupies about 16 GB, and Llama 3.1 70B about 141 GB, more than a single 80 GB H100 can hold. Every decode step reads all of those bytes from GPU memory, so the size of the weights sets both how many GPUs a model needs and how fast it can generate.

Quantization stores numbers in fewer bits, typically 8 or 4, together with a small number of scale factors that map the narrow format back to real values. Halving the bits halves the bytes that each decode step must read and frees memory for the KV cache. If the activations are quantized too, the matrix multiplications themselves can run on faster low-precision tensor cores. Figure 1 shows the core idea on four weights.

The catch is that rounding loses information. Whether that matters depends on the format, the scales, which tensors are quantized, and how carefully we measure quality. And a format only speeds things up if the GPU has kernels for it.

In this lesson, we look at the number formats used for LLM inference, decide what to quantize and at what granularity, compare the main methods (GPTQ, AWQ, SmoothQuant, and FP8 dynamic quantization), work out the memory and speed for Llama 3.1 8B and 70B, explain why weight-only quantization speeds up decode but not prefill, and build an evaluation that catches regressions an average score would hide.

Clarifying the Problem

Quantization questions usually come from a cost or capacity problem. Here is a typical exchange:

Candidate: Which model and hardware are we serving today?
Interviewer: Llama 3.1 8B Instruct in BF16 on H100 80 GB GPUs. Product also wants Llama 3.1 70B for a premium tier.

Candidate: What does the traffic look like?
Interviewer: Chat requests with about 2,000 prompt tokens and 500 output tokens, 1,000 requests per minute on average and up to about 33 per second at the daily peak. Each H100 handles about 5 requests per second, around 53 streams at once, within our latency targets.

Candidate: What are we trying to improve: memory, latency, or cost?
Interviewer: Cost per token, and we would like the 70B on fewer GPUs. The targets of p95 time to first token under 500 ms and p95 time per output token under 25 ms must still hold.

Candidate: Is there other hardware in the fleet?
Interviewer: A pool of NVIDIA L4 cards with 24 GB each that we would like to use for a cheaper tier.

Candidate: How do we decide that quality is acceptable?
Interviewer: We have 2,000 graded prompts from real customers, plus the public benchmarks we already track. No meaningful regression on either.

The question underneath is: which number format, applied to which tensors, with which method, gives us the memory and speed we need on each GPU type, without a quality loss our evaluation can detect? We start with the formats themselves.

Number Formats

Floating point and integer layouts

A floating-point number has a sign bit, exponent bits that set its magnitude, and mantissa bits that set its precision. More exponent bits mean a wider range; more mantissa bits mean finer steps. An integer format has no exponent: its values are evenly spaced, and a separate scale factor decides what range they cover. Figure 2 shows the layouts that matter for inference.

  • BF16 keeps FP32's 8-bit exponent, so it never overflows in practice, but only 7 mantissa bits. It is the standard serving precision and the baseline every quantized model is compared against.
  • FP8 comes in two encodings [1]. E4M3 trades range for precision: its largest value is 448, and it gives up infinities to gain range. E5M2 follows IEEE conventions and reaches 57,344 with coarser steps. Inference uses E4M3 for weights and activations; E5M2 is mainly a training format for gradients, though vLLM also accepts it for the KV cache.
  • INT8 has 256 evenly spaced levels and INT4 has 16. Uniform spacing wastes levels on the tails of a bell-shaped weight distribution, which is why 4-bit integer schemes need fine-grained scales.
  • FP4 E2M1 has only eight magnitudes: 0, 0.5, 1, 1.5, 2, 3, 4, and 6. It is usable only together with a scale for every small block of values.

Scales: mapping real values onto a format

A narrow format cannot hold a weight like 0.0037 directly. Instead we store a code q and a scale s shared by a group of values. With symmetric quantization, the scale maps the largest magnitude in the group onto the largest code:

s=max|x|qmax,q=round(x/s),x^=s·q

Here qmax is 127 for INT8, 7 for INT4, and 448 for FP8 E4M3. In Figure 1, s=0.98/127≈0.00772, and the largest rounding error is about 0.0035. Asymmetric quantization adds a zero point so that the codes cover the range from the minimum to the maximum instead of a range centered on zero; it helps when a group's values are skewed to one side.

The scale is the weak point. One large value in a group stretches the scale for everyone. If the group in Figure 1 also contained a weight of 8.0, the scale would grow to 8.0/127≈0.063, and the weight −0.07 would round to the single code −1, an error of about 10%. Most of quantization engineering is about choosing groups so that no single outlier sets the scale for many ordinary values.

Block-scaled 4-bit floats: NVFP4 and MXFP4

The newest 4-bit formats build the scale into the format. MXFP4, from the Open Compute Project's microscaling (MX) specification, stores E2M1 values with one shared power-of-two scale (an 8-bit E8M0 exponent) for every block of 32 values [2]. NVFP4, introduced with NVIDIA's Blackwell GPUs, uses smaller blocks of 16 values, each with an FP8 E4M3 scale that is not limited to powers of two, plus one FP32 scale per tensor [3]. NVIDIA reports about 4.5 bits per value for NVFP4, roughly 3.5 times smaller than FP16 and 1.8 times smaller than FP8, and an accuracy loss of 1% or less for DeepSeek-R1-0528 compared with FP8 on key language modeling tasks [3]. OpenAI's gpt-oss models ship with their mixture-of-experts weights already in MXFP4.

The hardware column is what decides speed. The A100 (Ampere) has INT8 tensor cores at 624 dense TOPS, twice its BF16 rate, but no FP8. Ada GPUs such as the L4, and Hopper GPUs such as the H100, add FP8: the H100 runs FP8 and INT8 at about 1,979 dense TFLOPS or TOPS, twice its BF16 rate. Blackwell adds FP4: an HGX B200 board lists 72 PFLOPS of dense FP4 across its 8 GPUs, double its FP8 rate [5]. vLLM still loads FP8 checkpoints on Ampere, but runs them as weight-only FP8 with BF16 math through its Marlin kernels [6], and it runs NVFP4 checkpoints as weight-only on GPUs older than Blackwell.

What Gets Quantized

A transformer layer holds three kinds of tensors that could be stored in fewer bits: the weights of its linear layers, the activations that flow into them, and the KV cache. Schemes are named by the bits of each: W4A16 means 4-bit weights with 16-bit activations, and W8A8 means 8-bit weights and 8-bit activations.

Weight-only quantization

In a weight-only scheme such as W4A16 or W8A16, only the weights are stored in low precision. The kernel loads the packed 4-bit weights and their group scales from memory, converts them to BF16 inside the GPU's registers, and runs an ordinary BF16 matrix multiplication. The model reads four times fewer weight bytes, but the arithmetic runs at BF16 speed. Activations never leave 16 bits, so weight-only schemes are the gentler option for accuracy.

Weights and activations

In a W8A8 scheme, both inputs of the matrix multiplication are 8-bit, so the multiplication itself runs on FP8 or INT8 tensor cores at twice the BF16 rate. The activations must be quantized on the fly, because they depend on the input. The output is rescaled by the product of the weight scale and the activation scale and returned in BF16. Figure 3 compares the two data paths.

Activations are harder to quantize than weights. In large LLMs, a handful of hidden dimensions carry activations about 100 times larger than typical values, and the same few channels stay large for every token [7][8]. A per-tensor activation scale sized for the outliers would round most ordinary activations to zero. This is the problem that SmoothQuant, described below, was built to solve, and one reason FP8, with its exponent bits, tolerates activations better than INT8.

The KV cache

The third candidate is the KV cache, which we covered in Lesson 3, KV Cache: an FP8 cache halves memory per token, from 128 KiB to 64 KiB for Llama 3.1 8B, with a single engine flag. It is independent of weight quantization, and the two are usually combined.

Granularity: how many values share a scale

The smaller the group that shares a scale, the less damage one outlier can do, but the more scales we must store and apply. Figure 4 shows the four common choices.

  • Per tensor: one scale for a whole matrix. Cheapest, and the most sensitive to outliers.
  • Per channel: one scale per output row of the weight matrix, 4,096 scales for a 4,096 × 4,096 projection. The standard choice for 8-bit weights.
  • Per group: one scale per group of consecutive input weights, usually 128. This is the default for 4-bit integer weights. An FP16 scale per 128 weights adds 16/128=0.125 bits per weight, so INT4 with group size 128 costs about 4.125 bits per weight. NVFP4 and MXFP4 are per-group schemes with groups of 16 and 32.
  • Per token, dynamic: for activations, one scale per token row, computed from that token's largest value at run time. It adapts to each input, so it needs no calibration data, at the cost of a small reduction before each matrix multiplication.

Scales can also be static, computed once from calibration data and stored in the checkpoint. Static activation scales save the run-time reduction but fail when production inputs look different from the calibration set. The FP8 "dynamic" scheme that most teams start with uses static per-channel weight scales and dynamic per-token activation scales.

Quantization Methods

All the methods below are post-training quantization (PTQ): they take a finished BF16 model and convert it in minutes to hours on one or a few GPUs, without retraining. They differ in how they choose codes and scales.

Round-to-nearest and FP8 dynamic

The simplest method computes the scales from the weights and rounds every weight to the nearest code, which is exactly what Figure 1 does. For 8-bit formats with per-channel scales, round-to-nearest is usually good enough. FP8 dynamic quantization (per-channel FP8 weights, per-token FP8 activations) needs no calibration data at all, and vLLM can apply a per-tensor FP8 variant while it loads a BF16 checkpoint [9]. Round-to-nearest breaks down at 4 bits, where rounding errors in thousands of weights add up in each output.

GPTQ

GPTQ quantizes a layer's weights one column at a time and, after rounding each column, adjusts the not-yet-quantized columns to cancel the error it just introduced, using second-order information estimated from calibration activations [10]. The authors quantized 175-billion-parameter models to 3 or 4 bits in about four GPU hours with negligible accuracy loss. GPTQ needs a few hundred calibration samples, and its usual output is W4A16 with group size 128.

AWQ

Activation-aware Weight Quantization (AWQ) starts from the observation that not all weights matter equally: protecting about 1% of salient weight channels greatly reduces quantization error, and those channels are best identified by the size of the activations that multiply them, not by the weights themselves [11]. Rather than keeping those channels in high precision, AWQ scales them up before quantization, an equivalent transformation that gives them finer effective steps. It needs no backpropagation and only a small calibration set, which makes it robust across domains. Like GPTQ, it typically produces W4A16 checkpoints.

SmoothQuant

SmoothQuant targets W8A8 INT8, where activation outliers are the problem [8]. Its insight is that weights are easy to quantize and activations are not, so it moves the difficulty from one to the other with an exact rewrite of each matrix multiplication:

Y=XW=(Xdiag(s)−1)(diag(s)W),sj=(max|Xj|)α(max|Wj|)1−α

Dividing each activation channel j by sj shrinks the outlier channels; multiplying the matching row of weights by sj keeps the product unchanged. The migration strength α balances the two; the paper found 0.5 a good balance for most models. The scales can usually be folded into the preceding layer's parameters offline, so the rewrite adds no work at inference. Figure 5 shows the effect on illustrative values.

Rotation methods such as QuaRot multiply weights and activations by orthogonal matrices that spread outliers across channels, making 4-bit activations feasible [12]. Quantization-aware training goes further by fine-tuning with quantization in the loop.

Memory and Speed

Memory math for Llama 3.1 8B and 70B

The first-order estimate is parameters × bits ÷ 8. Real checkpoints are a little larger, because standard recipes leave the token embeddings and the output layer (the LM head) in BF16: they are sensitive to rounding and together hold about 1.05 billion of the 8B model's 8.03 billion parameters. Only the linear layers inside the transformer blocks, 6.98 billion parameters for the 8B and 68.45 billion for the 70B, are quantized. The weights of one 8B checkpoint in FP8 are therefore:

6.98×109×1 byte+1.05×109×2 bytes≈9.08 GB

which matches the published FP8 checkpoints exactly. Figure 6 and Table 3 show every precision for both models, and what each leaves for the KV cache on an H100 under the Lesson 3 budget (about 71.6 GiB usable with --gpu-memory-utilization 0.90 set explicitly, since recent vLLM defaults to 0.92, minus about 4.6 GiB per GPU of activations and CUDA graphs).

Two lessons come out of the table. For the 8B on an H100, weight quantization adds only about 13% more cache room (52 to 58.6 GiB), because the weights were never the main consumer of memory; the FP8 KV cache from Lesson 3 does more for capacity. The real gains for the 8B are speed and cost per token. For the 70B, quantization decides the GPU count: BF16 needs four H100s per replica in practice, FP8 needs two, and W4A16 fits on one. Notice also that cutting memory by half is not automatic: the FP8 8B checkpoint is 57% of the BF16 size because the embeddings and LM head stay in 16 bits. Why weight-only quantization speeds up decode but not prefill

Whether a matrix multiplication is limited by memory or by compute depends on its arithmetic intensity: floating-point operations per byte read. A linear layer with a K×N weight matrix, applied to M tokens at once, does 2MKN operations and must read bwKN bytes of weights, where bw is bytes per weight. While M is much smaller than the matrix, the weights dominate the traffic, and the intensity is:

I≈2MKNbwKN=2Mbw FLOP per byte

An H100 can perform about 989 TFLOPS of BF16 math while reading 3.35 TB/s, so it becomes compute-bound above roughly 989/3.35≈295 FLOP per byte. Plugging in each scheme gives the batch size, in tokens per step, at which it stops being memory-bound:

  • BF16 (bw=2): I=M, so the crossover is at about 295 tokens per step.
  • W4A16 (bw=0.5, BF16 math): I=4M, so the crossover drops to about 74 tokens. Beyond that, the layer runs at BF16 compute speed, no faster than the unquantized model.
  • W8A8 FP8 (bw=1, FP8 math at 1,979 TFLOPS): I=2M against a ridge of about 591, so the crossover is again about 295 tokens, but every step on both sides of it takes half as long as BF16.

Figure 7 puts numbers on it for the 8B model, assuming every weight is stored at the format's width and ignoring attention. A decode step for a handful of streams is pure weight reading: about 4.79 ms in BF16, 2.40 ms in FP8, and 1.20 ms in 4-bit. Prefill of one 2,000-token prompt is a single step with M=2,000, deep in the compute-bound region: about 32.5 ms in BF16, 16.2 ms in FP8, and still about 32.5 ms in W4A16, because the math runs in BF16 (the conversion even adds a little). This is what Lesson 2, Prefill vs Decode, predicts: memory savings help the memory-bound phase, and only lower-precision math helps the compute-bound one.

Measured kernels agree. The Marlin W4A16 kernels reach close to the full 4× speedup up to batch sizes of 16 to 32, with a shrinking gain up to 64 to 128 [13]. A large study of the Llama 3.1 family concluded that W4A16 is the most cost-efficient choice for synchronous, latency-bound deployments, while W8A8 wins under continuous batching with many concurrent requests [14].

Interview tip

Say "weight-only quantization buys bandwidth, W8A8 buys compute." Then name the crossover: on an H100, 4-bit weights stop helping above roughly 74 tokens per step, while FP8 keeps its 2× all the way into prefill.

Which format fits our deployment?

Llama 3.1 8B on the H100s: we choose FP8 W8A8 with dynamic per-token activation scales. Hopper computes in FP8 natively (Lesson 33, GPU Architecture and Attention Kernels, explains the tensor cores behind this), so it speeds up both decode and prefill. At our traffic, each H100 serves about 5 requests per second: about 53 decode streams plus 10,000 prompt tokens per second of prefill (5 × 2,000). With steps of about 21 ms, a typical step mixes roughly 210 prefill tokens with the 53 decode tokens, well beyond the 74 tokens where W4A16 stops helping, so faster math is what lowers cost. It needs no calibration data, and the study above found FP8 W8A8 effectively lossless across Llama 3.1 sizes [14]. Memory is not what limits the 8B at these targets, but the extra room (cache for about 192 chats, or 384 with the FP8 KV cache) absorbs long prompts. We still run the evaluation below before shipping.

Llama 3.1 70B for the premium tier: FP8 on two H100s per replica. It holds about 66 GiB of KV cache, roughly 87 concurrent chats, which matches the per-GPU capacity of a four-GPU BF16 replica with half the GPUs per replica. Smaller replicas are easier to autoscale (Lesson 22, Autoscaling), and two-way tensor parallelism halves the all-reduce traffic of four-way (Lesson 18, Tensor Parallelism). W4A16 on a single H100 is tempting, but it leaves only about 30 GiB of cache and gives up FP8's prefill speedup, so we keep it as a fallback for low-traffic hours.

Llama 3.1 8B on the L4 pool: W4A16 with GPTQ or AWQ. An L4 reads only 300 GB/s, so decode is starved for bandwidth: one step must read 16.06 GB in BF16 (at least 53.5 ms, under 19 tokens per second per stream), 9.08 GB in FP8 (at least 30.3 ms), or 5.74 GB in W4A16 (at least 19.1 ms, about 52 tokens per second). BF16 weights would also fill two thirds of the 24 GB card before any cache. The cheap tier runs small batches, exactly where 4-bit weights pay off most. The L4 does support FP8 math, so if the 4-bit model fails our evaluation, FP8 W8A8 is the fallback.

Evaluating Quality

Why perplexity is not enough

Perplexity measures how well a model predicts held-out text, and it is the quickest sanity check after quantizing: a broken checkpoint shows up immediately. But it averages over every token, most of which are easy, and it says nothing about generated output: long reasoning chains, exact formats such as JSON, tool calls, or instructions buried in a long prompt. A model can lose a fraction of a point of perplexity and still fail a specific task badly.

Even task accuracy can hide damage. Dutta et al. found that compressed models with nearly the same benchmark accuracy as the baseline still change many individual answers, from correct to wrong and from wrong to correct in equal proportion [15]. They call these changes flips and propose tracking them, along with the KL divergence between the two models' token distributions. Figure 8 shows why this matters to users.

An evaluation that catches regressions

  1. Same harness, same settings. Run the BF16 baseline and the quantized model through the same harness, chat template, and greedy decoding. Differences in prompting easily exceed quantization effects. EleutherAI's lm-evaluation-harness runs public tasks directly against vLLM [16].
  2. Public task benchmarks that match the product: math reasoning such as GSM8K, instruction following such as IFEval, knowledge (MMLU-style), code, and long-context retrieval if users send long documents.
  3. Your own eval set. The 2,000 graded customer prompts are the real test. Compare accuracy, count flips, and break results down by slice: long prompts, non-English, structured output.
  4. Know the noise. At 80% accuracy on 2,000 items, the standard error is 0.8×0.2/2000≈0.9 points, so differences under about 2 points are within noise. Flips are a paired measure and much more sensitive.
  5. Gate on speed too. Benchmark latency and throughput at production concurrency, as in Lesson 12, Lab - Benchmark Two Engines at 50 Concurrent Users. A quantized model that is not faster on your hardware is all risk and no reward.

from transformers import AutoModelForCausalLM, AutoTokenizer
from llmcompressor import oneshot
from llmcompressor.modifiers.gptq import GPTQModifier
from llmcompressor.modifiers.quantization import QuantizationModifier

MODEL_ID = "meta-llama/Llama-3.1-8B-Instruct"
SCHEME = "FP8_DYNAMIC"   # or "W4A16" for 4-bit weights (L4, low-batch serving)

model = AutoModelForCausalLM.from_pretrained(MODEL_ID, dtype="auto")
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)

if SCHEME == "FP8_DYNAMIC":
    # FP8 weights with per-channel scales; FP8 activations with per-token
    # scales computed at run time. No calibration data needed.
    recipe = QuantizationModifier(targets="Linear", scheme="FP8_DYNAMIC", ignore=["lm_head"])
    oneshot(model=model, recipe=recipe)
else:
    # GPTQ with group size 128 needs a few hundred calibration samples.
    recipe = GPTQModifier(targets="Linear", scheme="W4A16", ignore=["lm_head"])
    oneshot(model=model, dataset="perfectblend", splits="train[:512]", recipe=recipe,
            max_seq_length=2048, num_calibration_samples=512)

save_dir = MODEL_ID.split("/")[-1] + "-" + SCHEME
model.save_pretrained(save_dir, save_compressed=True)
tokenizer.save_pretrained(save_dir)
print("saved", save_dir)
# Serve the quantized checkpoint; vLLM reads the scheme from its config.
vllm serve ./Llama-3.1-8B-Instruct-FP8_DYNAMIC --port 8001 \
  --gpu-memory-utilization 0.90 --kv-cache-dtype fp8

import json
from openai import OpenAI

# Baseline and quantized model running side by side as two vLLM servers.
ENDPOINTS = {"bf16": "http://localhost:8000/v1", "fp8": "http://localhost:8001/v1"}

def is_correct(output: str, expected: str) -> bool:
    return expected.strip().lower() in output.lower()   # replace with your grader

def run(url: str, items: list[dict]) -> list[bool]:
    client = OpenAI(base_url=url, api_key="EMPTY")
    model = client.models.list().data[0].id
    results = []
    for item in items:
        reply = client.chat.completions.create(
            model=model, temperature=0.0, max_tokens=512,
            messages=[{"role": "user", "content": item["prompt"]}])
        results.append(is_correct(reply.choices[0].message.content, item["expected"]))
    return results

# One JSON object per line: {"prompt": "...", "expected": "..."}
with open("eval_set.jsonl") as f:
    items = [json.loads(line) for line in f]

base, quant = (run(url, items) for url in ENDPOINTS.values())
n = len(items)
lost = sum(b and not q for b, q in zip(base, quant))
gained = sum(q and not b for b, q in zip(base, quant))
print(f"accuracy: bf16 {sum(base) / n:.1%}, fp8 {sum(quant) / n:.1%}")
print(f"flips: {lost + gained} of {n} ({(lost + gained) / n:.1%}); "
      f"{lost} correct->wrong, {gained} wrong->correct")

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Rotation-based methods such as QuaRot [12] and SpinQuant [18], which remove outliers so that weights, activations, and the KV cache can all run at 4 bits.
  • Why the LM head and embeddings are usually left in BF16, and what it costs: about 2.1 GB of the 8B model's 9.08 GB FP8 checkpoint.
  • Mixture-of-experts models, where most weights sit in experts that each token rarely touches, so 4-bit expert weights (as in gpt-oss's MXFP4) save the most memory for the least accuracy risk. Lesson 35, Mixture-of-Experts Serving, covers how such models are served.
  • LLM.int8(), which keeps outlier channels in 16 bits and the rest in INT8 [7]: accurate, but the SmoothQuant authors measured it running slower than the FP16 baseline in most cases because of the mixed-precision overhead [8].
  • Quantization-aware training, and the newer practice of releasing models trained or post-trained directly in low precision, which removes most of the post-training accuracy gap.
  • TensorRT-LLM and NVIDIA's Model Optimizer as an alternative quantization toolchain, covered in Lesson 11, TensorRT-LLM.

Summary

  • Quantization stores weights, activations, or the KV cache in 8 or 4 bits plus scale factors. FP8 E4M3 (max 448) is the inference FP8; INT4 and the block-scaled NVFP4 and MXFP4 cover 4 bits.
  • Smaller scale groups (per channel, per group of 128, per token) limit the damage from outliers; an FP16 scale per 128 weights adds 0.125 bits per weight.
  • Published Llama 3.1 checkpoints: 8B is 16.06 GB in BF16, 9.08 GB in FP8, and 5.74 GB in W4A16; 70B is 141.1 GB, 72.66 GB, and 39.79 GB, which means four, two, or one H100 per replica.
  • Weight-only quantization buys bandwidth: on an H100, W4A16 helps decode up to roughly 74 tokens per step. W8A8 buys compute: FP8 halves the time of both decode and prefill on Hopper.
  • Ampere has INT8 but no FP8 math; Ada and Hopper add FP8; Blackwell adds FP4.
  • For our fleet: FP8 W8A8 for the 8B on H100, FP8 on two H100s for the 70B, and W4A16 for the 8B on bandwidth-starved L4s.
  • Judge quality with task benchmarks and your own eval set under identical settings, and count flips: equal accuracy can still hide changed answers.

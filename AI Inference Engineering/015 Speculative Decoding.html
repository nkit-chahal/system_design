Speculative Decoding

Introduction

During decode, a model produces one token per sequence per forward pass, and every pass must read all of the model's weights from GPU memory. For Llama 3.1 8B on an H100, that read takes about 4.8 ms, while the arithmetic for a single token takes about 0.016 ms. At small batch sizes the GPU's compute units sit idle for more than 99% of each step, and the stream is limited to roughly 200 tokens per second no matter how fast the tensor cores are.

Speculative decoding puts that idle compute to work. A cheap draft guesses the next few tokens, and the expensive target model checks all of the guesses in a single forward pass, which costs about the same as generating one token. Every accepted guess is a token gained for free. A carefully designed acceptance rule guarantees that the output follows exactly the same distribution as the target model alone, so quality does not change. Figure 1 shows one round.

In this lesson, we show why decode leaves compute idle, walk through the draft-then-verify algorithm and the rejection-sampling rule that makes it lossless, derive how many tokens each target pass yields and what speedup to expect for a given draft cost, compare the ways to get a draft (separate models, n-gram lookup, Medusa, EAGLE, and multi-token prediction), explain when speculation helps and when it slows a server down, and configure it in vLLM and SGLang.

Clarifying the Problem

Speculative decoding questions usually come from a per-user latency complaint. Here is a typical exchange:

Candidate: Which model and GPU are we serving?
Interviewer: Llama 3.1 8B Instruct in BF16 on one H100 per replica, behind a coding assistant.

Candidate: What is the complaint?
Interviewer: We meet our targets of p95 time to first token under 500 ms and p95 time per output token under 25 ms, but users still wait: a 2,000-token code edit at 25 ms per token takes 50 seconds to stream.

Candidate: How loaded is each replica?
Interviewer: Usually 4 to 16 concurrent requests per replica. At the daily peak, about 50, close to the 53 streams an H100 holds within the latency targets.

Candidate: Can the outputs change at all?
Interviewer: No. The quality team signed off on this model's behavior. Code edits use temperature 0, chat uses 0.7.

Candidate: Can we spend extra GPU memory or train something small?
Interviewer: A few GB of memory is fine. We would rather use published components than train our own.

The question underneath is: how much faster can each stream get without changing the output distribution, and at what load does speculation stop paying for itself? We start with where the idle compute comes from.

Why Decode Leaves Compute Idle

A forward pass over M new tokens must read every weight once, whatever M is, and does about 2×params floating-point operations per token. For Llama 3.1 8B on an H100:

  • Memory: 16.06 GB of weights ÷ 3.35 TB/s ≈ 4.79 ms per step.
  • Compute for one token: 2×8.03×109 ≈ 16 GFLOPs ÷ 989 TFLOPS ≈ 0.016 ms.
  • Compute for five tokens: about 0.081 ms, still hidden under the 4.79 ms weight read.

As Lesson 13 showed, an H100 running BF16 stays memory-bound until a step processes about 295 tokens. Below that, adding tokens to a forward pass is almost free. Prefill already exploits this: it processes the whole prompt in one pass (Lesson 2, Prefill vs Decode). Decode cannot, because each token depends on the one before it. But if we had good guesses for the next few tokens, we could check them all in one pass. Figure 2 shows the imbalance.

Draft, Then Verify

The algorithm

Speculative decoding was introduced independently by Leviathan, Kalman, and Matias [1] and by Chen et al. [2]. One round works like this:

  1. Draft. A cheap draft proposes k tokens, one after another, recording its probability q for each.
  2. Verify. The target runs one forward pass over the context plus the k draft tokens. Because attention is causal, this single pass yields the target's probability p at each of the k draft positions, plus one more position after the last draft token.
  3. Accept or reject each draft token from left to right with the rule below. At the first rejection, sample a replacement token from a corrected distribution and discard the remaining drafts.
  4. Bonus token. If all k drafts are accepted, sample one more token from the target's distribution at the extra position.

Every round emits between 1 and k+1 tokens, never fewer than normal decoding. The KV cache entries for rejected tokens are simply discarded, and the next round starts from the last emitted token.

Why the output distribution does not change

The acceptance rule is a form of rejection sampling. For a draft token x, proposed by the draft with probability q(x) and given probability p(x) by the target:

P(accept x)=min(1,p(x)q(x)),on rejection, sample from max(0,p−q)∑ymax(0,p(y)−q(y))

If the target likes a token at least as much as the draft does, it is always kept. If the draft was overconfident, the token is kept only in proportion. Rejections are then resampled from the tokens the draft under-proposed. The two paths add up exactly: the probability of emitting x is min(p(x),q(x))+max(0,p(x)−q(x))=p(x). Figure 3 checks this on a four-token example.

In the example, a draft token is accepted with probability ∑xmin(p(x),q(x))=0.4+0.2+0.1+0.1=0.8. This quantity, one minus the total variation distance between the two distributions, is the acceptance rate α for that position: the closer the draft is to the target, the more drafts survive. With greedy decoding the rule reduces to a simple check: keep the draft token if it is the target's top token. vLLM describes its implementation as lossless up to the precision limits of hardware numerics, though log probabilities can differ slightly with batch composition [3].

How many tokens per target pass

If each draft token is accepted independently with probability α, the expected number of tokens emitted per target pass, counting the corrected or bonus token, is [1]:

E(α,k)=1+α+α2+…+αk=1−αk+11−α

The first token is free because the verify pass always produces one; each further token requires every earlier draft to have survived. Table 1 evaluates the formula, and Figure 4 plots it.

Two lessons follow. Returns diminish quickly: at α=0.6, drafting more than three or four tokens adds almost nothing, because the chance that all of them survive collapses. And the acceptance rate matters more than k: going from 0.7 to 0.9 raises the ceiling from 3.3 to 10 tokens per pass. Real acceptance is not independent from token to token, and it varies with the text (boilerplate code is easy, a creative answer is not), so treat the formula as a model and measure α on your own traffic.

Speedup versus draft cost

Drafting is not free. Let c be the time of one draft step divided by the time of one target step. A round costs k draft steps plus one verify pass, which takes about one target step while decode is memory-bound. The speedup over plain decoding is then [1]:

S(α,k,c)=1−αk+1(1−α)(kc+1)

Worked example. Use Llama 3.2 1B Instruct as the draft for Llama 3.1 8B. It has about 1.24 billion parameters and shares the target's 128,256-token vocabulary. Its weights are about 2.47 GB, so a draft step takes at least 2.47 GB ÷ 3.35 TB/s ≈ 0.74 ms against 4.79 ms for the target, giving c≈0.15. With α=0.8 and k=4:

  • Tokens per round: E=3.36.
  • Time per round: 4.79+4×0.74≈7.74 ms.
  • Stream speed: 3.36/7.74 ms≈434 tokens per second, against 1/4.79 ms≈209 without speculation: about 2.1×.

A cheaper draft changes the picture. An EAGLE-3 draft head for Llama 3.1 8B is a single transformer layer with a 32,000-token draft vocabulary, about 0.85 GB on disk [4], so c is closer to 0.05. Figure 5 plots the speedup against k for these cases.

The best k grows with the acceptance rate and shrinks with the draft cost: about 8 for a very cheap, accurate draft, 5 for the 1B draft at α=0.8, and only 2 when acceptance falls to 0.6. Too large a k spends draft time on tokens that will almost certainly be rejected. This is why engines expose k as a setting and why it should be tuned on measured acceptance, not guessed.

Interview tip

Write down E = (1 − α^(k+1)) / (1 − α) and S = E / (kc + 1), then plug in numbers: "with α = 0.8, four drafts, and a draft at 15% of the target's step time, we get 3.36 tokens per pass and about a 2.1× faster stream."

Where the Draft Comes From

The draft only has to be cheap and agree with the target often. Several designs meet that goal in different ways; Figure 6 sketches them.

A separate draft model

The original approach uses a smaller model from the same family, which shares the tokenizer: Llama 3.2 1B for Llama 3.1 8B or 70B, or Qwen3-0.6B for a larger Qwen3. It needs no training if a suitable model exists, but it adds its own weights and its own KV cache, and its cost ratio c is typically 0.1 to 0.2. A draft distilled on the target's outputs agrees with it more often, as Lesson 14, Distillation, describes.

N-gram and prompt lookup

Many outputs copy spans of their input: code edits repeat most of the file, summaries quote the document, and retrieval answers cite passages. Prompt lookup decoding exploits this with no model at all: it matches the last few generated tokens against the prompt and proposes the tokens that followed the match [5]. The draft costs almost nothing, so c≈0. The vLLM team measured up to 2.8× faster generation with n-gram speculation on a summarization dataset at low load [6]. When nothing matches, no tokens are proposed and decoding proceeds normally.

Medusa heads

Medusa adds several extra decoding heads to the target model, each predicting the token one, two, or more positions ahead from the target's last hidden state, and verifies a tree of candidate continuations at once with a tree-shaped attention mask [7]. Training only the heads on a frozen model gave over 2.2× speedups without changing outputs; training heads and backbone together reached 2.3 to 3.6×, at the cost of a special training recipe.

The EAGLE family

EAGLE drafts at the feature level: a lightweight head reads the target's second-to-top-layer features together with the token sequence and predicts the next features autoregressively, reporting 2.7 to 3.5× lower latency on LLaMA2-Chat 70B [8]. EAGLE-2 builds a draft tree whose shape adapts to the draft's confidence, reaching 3.05 to 4.26× [9]. EAGLE-3 drops feature prediction in favor of direct token prediction, fuses features from several target layers, and is trained with a technique its authors call training-time test; it reports speedups up to 6.5×, about 1.4× better than EAGLE-2, and a 1.38× throughput gain at batch size 64 in SGLang [10]. EAGLE-3 heads for popular models are published on Hugging Face, so no training is needed for Llama 3.1 8B.

Multi-token prediction

Some models are trained from the start to predict more than one token. DeepSeek-V3 adds a multi-token prediction (MTP) module that predicts one extra token beyond the next; at inference the module can be discarded or repurposed as a built-in draft. DeepSeek reports that the second token is accepted 85% to 90% of the time, which gives about 1.8 times the tokens per second [11]. vLLM and SGLang can use such MTP modules directly. DeepSeek-V3 is a mixture-of-experts model, whose serving is covered in Lesson 35, Mixture-of-Experts Serving.

When It Helps and When It Hurts

Where speculation pays off

  • Low batch sizes and latency-sensitive streams, where the GPU is memory-bound and most compute is idle. This is the regime the vLLM documentation targets: reducing inter-token latency at medium to low load [3].
  • Predictable outputs: code, edits that copy input, boilerplate, and structured formats such as JSON, where many tokens are forced (Lesson 38, Structured Output and Tool Calling). Acceptance rates are higher, and n-gram drafts become effective.
  • Greedy or low-temperature sampling. At high temperature, the target's distribution is flatter and harder to guess, so acceptance drops.
  • Long contexts. Each decode step also reads the whole KV cache, which keeps the GPU memory-bound even at larger batch sizes. MagicDec showed speedups of up to 2.51× for Llama 3.1 8B at batch sizes from 32 to 256 on moderate-to-long sequences, using a draft with a sparse KV cache [12]. Lesson 36, Long-Context Serving, covers this regime.

Where it hurts

The verify pass processes k+1 tokens for every sequence in the batch. At batch size B, that is B(k+1) tokens per step. Once that number passes the GPU's ridge point, about 295 tokens for BF16 on an H100, verification becomes compute-bound: the extra tokens now cost real time, and every rejected draft is wasted arithmetic that a plain batch could have spent on other users' tokens. The draft's own steps and memory also compete with the target's KV cache.

Figure 7 shows this in the same roofline model, for α=0.8, k=4, and the 1B draft. With short 200-token contexts, the modeled speedup holds near 2× up to about 64 concurrent sequences, falls to 1.36× at 128, and turns into a slowdown above roughly 200, where each verify pass carries more than 1,000 tokens. With 2,500-token contexts, reading the cache keeps decode memory-bound and the modeled gain stays near 1.8× up to 128 sequences, about as many as fit once the draft's weights and cache take their share of memory.

Real engines cross over sooner than this ideal model, because kernels do not reach peak compute and drafting has fixed per-step overheads. The vLLM team measured 1.4× and 1.8× slowdowns at high request rates for Llama 3 70B on four H100s, on the same workloads that sped up at low load [6]. Better methods move the crossover out but do not remove it, so the practical answer is to adapt: recent vLLM releases can lower k as the batch grows, down to zero at high concurrency, through the num_speculative_tokens_per_batch_size setting; check its documentation for the model runner it requires [13].

Which method fits our deployment?

For the coding assistant on H100s, with 4 to 16 concurrent streams most of the time, we choose EAGLE-3 with a published Llama 3.1 8B head and three speculative tokens. The head is cheap (about 0.85 GB, one layer), needs no training, works for both code and chat, and is supported by vLLM and SGLang. We start at k=3 because acceptance at temperature 0.7 will be lower than on greedy code edits, then tune k from the measured acceptance length. N-gram lookup is the strongest choice for pure edit traffic, where outputs copy the input, and costs nothing; if edits become a large, separate workload, we can run an n-gram pool for them behind the router (Lesson 25, Request Routing). At the daily peak of about 50 streams, each verify pass carries about 200 tokens with k=3 (50 × 4), still under the ridge point in our model, but prefill chunks share those steps and push them toward it. So we confirm with a load test at peak concurrency (Lesson 12, Lab - Benchmark Two Engines at 50 Concurrent Users) that speculation still helps, and let k fall with batch size if it does not. Throughout, we watch the acceptance counters and inter-token latency, and turn speculation down if acceptance drops after a model or traffic change.

The first tab serves Llama 3.1 8B with an EAGLE-3 head in vLLM, configured through the JSON --speculative-config flag [3], and shows the n-gram and draft-model alternatives. # Other values of --speculative-algorithm include EAGLE, STANDALONE
# (a separate draft model) and NGRAM.
import urllib.request

def expected_tokens(alpha: float, k: int) -> float:
    """Tokens per target pass, including the corrected or bonus token."""
    return (1 - alpha ** (k + 1)) / (1 - alpha)

def speedup(alpha: float, k: int, c: float) -> float:
    """c = draft step time / target step time; verification costs about one target step."""
    return expected_tokens(alpha, k) / (k * c + 1)

for k in (1, 2, 3, 4, 5, 8):
    print(f"k={k}: E={expected_tokens(0.8, k):.2f}, speedup with c=0.15: {speedup(0.8, k, 0.15):.2f}")

# Measured acceptance from a running vLLM server (counters are cumulative).
def counter(text: str, name: str) -> float:
    total = 0.0
    for line in text.splitlines():
        if line.startswith(name + "{") or line.startswith(name + " "):
            total += float(line.rsplit(" ", 1)[1])
    return total

metrics = urllib.request.urlopen("http://localhost:8000/metrics").read().decode()
drafts = counter(metrics, "vllm:spec_decode_num_drafts_total")
drafted = counter(metrics, "vllm:spec_decode_num_draft_tokens_total")
accepted = counter(metrics, "vllm:spec_decode_num_accepted_tokens_total")
if drafts:
    k = round(drafted / drafts)
    mean_len = 1 + accepted / drafts   # measured tokens per target pass
    lo, hi = 0.0, 0.999                # solve expected_tokens(alpha, k) = mean_len
    for _ in range(60):
        mid = (lo + hi) / 2
        lo, hi = (mid, hi) if expected_tokens(mid, k) < mean_len else (lo, mid)
    print(f"k={k}, mean acceptance length {mean_len:.2f}, implied alpha {lo:.2f}")

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Tree verification, as in SpecInfer, which checks a tree of candidate continuations in one pass with a tree attention mask, trading more verified tokens for a higher chance of a long accepted path [15].
  • Lookahead decoding, which generates and verifies n-grams from the target model itself with no draft model at all [16].
  • Why speculation helps tensor-parallel and multi-GPU deployments: the large model's step is slow and communication-heavy, so saving target steps saves the most time.
  • Lossy variants that relax the acceptance rule to accept more tokens, and why they need the same quality evaluation as quantization (Lesson 13, Quantization - FP8, INT8 and 4-bit).
  • How speculative decoding interacts with continuous batching (Lesson 7, Continuous Batching): sequences in one batch accept different numbers of tokens, so the scheduler must handle ragged progress.
  • Monitoring: per-request acceptance metrics show which traffic benefits, so speculation can be enabled per route or per tenant.

Summary

  • Decode is memory-bound: for Llama 3.1 8B on an H100, reading the weights takes 4.79 ms while one token's arithmetic takes 0.016 ms, so verifying several tokens per pass is almost free.
  • A cheap draft proposes k tokens; the target verifies them in one pass. Rejection sampling with acceptance min(1,p/q) and a corrected resample keeps the output distribution exactly the target's.
  • Expected tokens per target pass are (1−αk+1)/(1−α): 3.36 at α=0.8,k=4. The speedup divides that by kc+1: about 2.1× with a 1B draft.
  • Drafts come from small models, n-gram lookup of the prompt, Medusa heads, EAGLE-3 heads, or built-in multi-token prediction modules.
  • It helps most at low batch sizes, low temperature, predictable outputs, and long contexts; it hurts once B(k+1) tokens per step make verification compute-bound.
  • For our coding assistant: EAGLE-3 with three draft tokens, tuned from vLLM's acceptance metrics, with k reduced at peak load.

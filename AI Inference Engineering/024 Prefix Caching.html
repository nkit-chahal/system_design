Prefix Caching

Introduction

Most prompts that reach an LLM server are not new. A chat assistant sends the same long system prompt with every message, an agent resends its whole history at every step, and a document question-answering app sends the same document with each question. Prefill recomputes the keys and values of all those repeated tokens every time, although the result is identical.

Prefix caching keeps the KV cache of prompts after their requests finish and reuses it when a later request starts with the same tokens. Lesson 3, KV Cache, introduced the idea; this lesson explains how engines implement it, what it saves, and why a fleet often gets far less benefit than it should. Figure 1 shows the core effect on our running example.

In this lesson, we look at where shared prefixes come from, how vLLM and SGLang find and evict cached prefixes, how much prefill time and GPU compute a given hit rate saves, how to design prompts and conversations that hit, and how to measure the hit rate in production.

Clarifying the Problem

Prefix caching questions usually start from a latency or cost complaint about long prompts. Here is a typical exchange between a candidate and an interviewer:

Candidate: What do the prompts look like?
Interviewer: Each request has a 1,500-token system prompt with instructions, tool definitions, and few-shot examples, then about 500 tokens of user message and recent history. Answers are about 500 tokens.

Candidate: Is the system prompt the same for everyone?
Interviewer: We serve 12 enterprise customers, and each has its own system prompt, identical for all of that customer's users. The first line of every system prompt currently contains the current time and the user's name.

Candidate: How is it deployed?
Interviewer: Llama 3.1 8B on vLLM, five H100 replicas behind a round-robin load balancer, about 1,000 requests per minute on average. The autoscaler keeps each replica at about 75% of its capacity (Lesson 22, Autoscaling).

Candidate: What are the targets?
Interviewer: p95 time to first token of at most 500 ms. We would also like to spend less GPU time on prefill.

Candidate: Are there isolation requirements between customers?
Interviewer: Yes. No customer may learn anything about another customer's prompts.

The question underneath is: how much prefill can we skip, what stops us from skipping it today, and how do we know it is working?

Where Shared Prefixes Come From

Reuse is exact because of causal attention: the keys and values of a token depend only on that token and the tokens before it (Lesson 3). Two requests that begin with the same token sequence therefore have identical KV cache for that sequence, and the first request's cache can serve the second. Only a shared prefix counts; identical text in the middle of two prompts, after different beginnings, has different keys and values. Figure 2 shows the common sources.

  • System prompts and tool definitions: identical for every user of an application or tenant, and often 1,000 tokens or more.
  • Few-shot examples: the same instructions and examples before every input in a classification or extraction job.
  • Documents: a manual, contract, or report that many questions refer to.
  • Multi-turn chat: each turn's prompt is the previous turn's prompt plus the answer and a new message.
  • Agent loops: each step resends the system prompt, the tools, and every earlier call and result, so the new part of the prompt is often only a few percent of it.

How vLLM Caches Prefixes

Hashing full blocks

vLLM stores the KV cache in fixed-size blocks, 16 tokens by default (Lesson 8, PagedAttention). Its automatic prefix caching gives every full block a hash computed from three things: the hash of the previous block, the tokens in this block, and extra keys such as a LoRA adapter ID, multimodal input hashes, and a cache salt [1]. Because each hash includes its parent's, a block's hash identifies the entire prefix up to and including that block. A table maps hashes to physical blocks. Only full blocks are cached [1]. Figure 3 walks through request B from Figure 1.

When a request arrives, the scheduler hashes its prompt block by block and looks the hashes up in order, stopping at the first miss. The 1,500-token system prompt fills 93 full blocks (1,488 tokens); block 93 holds the last 12 system tokens and the first 4 user tokens, so it differs between users. Every request of the same tenant therefore reuses exactly 1,488 tokens, and engines with finer granularity can reuse a few more.

Sharing, reference counts, and eviction

A hit does not copy anything. The new request's block table simply points at the cached physical blocks, and each block's reference count records how many running requests use it [1]. Concurrent requests of one tenant share the system prompt's 93 blocks: at 53 running requests per replica (Lesson 22, Autoscaling), that is 186 MiB instead of 53 × 186 MiB ≈ 9.6 GiB of KV cache.

When a request finishes, its blocks are not erased. Blocks whose reference count drops to zero keep their hash and join a free block queue, ordered from least to most recently used. Allocating a block for new tokens takes the head of the queue and drops its old hash, which is the eviction. A hit on a block that is waiting in the queue removes it from the queue and puts it back in use [1]. A finished request's blocks join the tail in reverse order, so the end of a prefix is evicted before its beginning, which keeps the most shareable part cached longest. Figure 4 shows the three events.

Prefix caching is on by default in current vLLM releases and can be turned off with --disable-prefix-caching [2]. Two more details matter in practice. The default hash, sha256, can be switched to the faster xxhash, which the vLLM documentation warns increases collision risk in multi-tenant setups [1][2]. And the cache_salt field of a request is injected into the first block's hash, so only requests with the same salt can share blocks [1]. Without salts, a tenant could time its own requests and infer from a fast first token that another tenant recently sent a given prefix, so each of our 12 customers gets its own long, secret salt (Lesson 37, Multi-LoRA and Multi-Tenant Serving).

How SGLang's RadixAttention Works

SGLang's RadixAttention keeps the cache of prompts and generated tokens in a radix tree, a compressed prefix tree whose edges carry token sequences of any length, mapping token sequences to their KV cache [3]. The KV tensors live in a paged layout whose page size is one token by default, so matches are token-exact rather than block-aligned [3][4]. Figure 5 shows a tree for two tenants.

  • Matching and insertion: a new request walks the tree along its tokens. Where it diverges in the middle of an edge, the node splits, so the shared part becomes its own node, as with tenant B's edited prompt.
  • Reference counts: each node counts the running requests that use it, and only nodes with a count of zero can be evicted [3].
  • Eviction: least recently used leaves go first, so shared ancestors survive until they become leaves themselves [3]. Current versions also offer other policies through --radix-eviction-policy [4].
  • One memory pool: cached tokens and running requests share the same pool, with no fixed cache size; when running requests need room, cached tokens are evicted [3].
  • Cache-aware scheduling: the paper orders waiting requests by matched prefix length, longest first, which it shows is equivalent to a depth-first walk of the tree and maximizes reuse in a batch [3]. In current SGLang this is --schedule-policy lpm; the default is first come, first served [4], because reordering can starve requests with short matches.

For a workload of shared system prompts, both designs reach nearly the same hit rate. The radix tree shines when prefixes branch deeply and unpredictably, as in agent programs that fork many calls from a common context, which is what SGLang was built for [3].

What Prefix Caching Saves

Prefill compute and time to first token

Prefill costs about 2 FLOPs per parameter per token. For our 2,000-token prompt on Llama 3.1 8B:

2×8.03×109×2,000≈32 TFLOP⇒≈65 ms at half of 989 TFLOPS

With the 1,488-token prefix cached, only 512 tokens are computed: about 8.2 TFLOP, or 16.6 ms. If a fraction h of requests find their prefix cached, the expected work per request is

tokens computed=2,000−1,488h

and the token hit rate, the share of prompt tokens served from the cache, is 1,488h÷2,000=0.744h. At h=90%, each request computes about 661 tokens in about 21.5 ms, and the token hit rate is 67%. Figure 6 plots the relationship. These figures ignore attention's own FLOPs, which add only a few percent at 2,000 tokens.

The fleet-wide effect is larger than the per-request one suggests. At 1,000 requests per minute, prefill without caching processes 33,333 prompt tokens per second, about 535 TFLOP/s, which is 1.08 H100s of compute at 50% efficiency, or about a fifth of each of our five replicas. At h=90% it falls to about 177 TFLOP/s, or 0.36 of an H100. The freed compute also shortens the decode steps that share a batch with prefill chunks, so time per output token improves a little too.

Interview tip

Separate the two hit rates: the share of requests that hit and the share of prompt tokens served from cache. Our prompt shape caps the token hit rate at 74.4% no matter how well caching works, because the last 512 tokens of every prompt are new.

Memory, and what caching does not save

Sharing also saves memory, as computed above, which leaves more room for other tenants' prefixes and for conversation histories. Prefix caching does not speed up decode: each new token still attends over the whole prompt, cached or not, so the vLLM documentation notes that it reduces only the time to process the query, not the time to generate new tokens [5]. A workload of short prompts and long answers gains little. Attention kernels that read a shared prefix once for a whole batch, such as Hydragen's [6], target that remaining cost (Lesson 33, GPU Architecture and Attention Kernels).

Designing for Cache Hits

Static first, dynamic last

The interviewer's prompts put the current time and the user's name on the first line. That one line makes block 0 different for every request, and because every later hash includes its parent, nothing after it can match: the hit rate is zero. Figure 7 shows the fix: put everything static first and everything that varies last.

  • Order prompt sections from most stable to least stable: instructions, tool definitions, few-shot examples, then per-user and per-request content.
  • Make serialization deterministic. Tools listed in a different order, or JSON keys in a different order, produce different tokens.
  • Watch the chat template. Llama 3.1's template writes a "Today Date:" line into the system header from a date_string variable; filled with today's date, it costs one miss per tenant per day, which is harmless, but a template or application that adds a timestamp to the second defeats the cache entirely.
  • Version long prompts deliberately. Every edit invalidates the cache from the first changed token onward, so batch edits rather than tweaking a line a day.

Multi-turn chat and agent loops

Each chat turn resends the conversation so far. vLLM caches blocks of generated tokens as well as prompt tokens, so the answer to turn 1 is already cached when turn 2 arrives. Figure 8 shows the effect: turn 2 computes only the new message, about 120 tokens of 2,620.

The template must reproduce earlier turns exactly. Templates that rewrite history, for example by dropping a reasoning model's hidden reasoning from earlier answers, change the tokens and end the match at the first changed token. Agent loops behave like long multi-turn chats and benefit even more, provided tool results earlier in the context are never reordered or rewritten.

Two conditions decide whether these hits happen in a fleet. The first is routing. With round-robin across five replicas, the next turn reaches the replica that holds the history only 20% of the time. System prompts are cached on every replica anyway, but conversation history is not. Session affinity or prefix-aware routing, which sends a request to the replica most likely to hold its prefix, fixes this; Lesson 25, Request Routing, covers it.

The second is retention. Each of our five replicas receives about 200 requests per minute, and each request allocates about 1,012 new tokens of blocks (its 512 uncached prompt tokens and 500 output tokens), about 202K tokens per minute. Of the roughly 426K tokens of KV cache from Lesson 3, about 53K are held by running requests and the 12 tenants' system prompts, leaving about 373K tokens of evictable cache. At that churn, a finished conversation's blocks survive about 373 ÷ 202 ≈ 1.8 minutes before being evicted. A user who takes longer than that to reply loses the history's cache even on the right replica.

Beyond GPU Memory: Multi-Tier Caches

Retention can be extended by keeping evicted blocks in cheaper memory and copying them back on a hit. vLLM offers KV offloading with --kv-offloading-size (the buffer in GiB) and a native or lmcache backend [2], and LMCache stores KV caches in CPU memory, local disk, or remote storage and shares them across engine instances [7]. SGLang's hierarchical cache adds a host memory pool, sized with --hicache-ratio or --hicache-size, and optional storage backends [4]. A 200 GiB CPU tier holds about 1.6 million more tokens, which in our example stretches retention from about 1.8 minutes to about 10. Table 2 shows when loading beats recomputing.

CPU memory wins comfortably at any length. A local SSD barely beats recomputation for a short prefix but wins for long documents, where recomputation also pays attention's quadratic cost. Lesson 36, Long-Context Serving, covers these tiers in depth; Mooncake shows the idea taken to a whole cluster built around a shared KV cache [8].

Prompt caching in hosted APIs

Hosted model APIs expose the same mechanism as a pricing feature. Cached input tokens are billed at a discount, because the provider skips their prefill, and some providers charge extra to write a prefix into the cache, require a minimum prefix length, or keep entries for only minutes. Some cache automatically; others ask the caller to mark where the cacheable prefix ends. The design rules are the ones above: static content first, deterministic serialization, and requests close enough in time that the entry is still alive. Usage fields in the response report how many input tokens were cached.

Observing the Hit Rate

vLLM exports two counters, vllm:prefix_cache_queries and vllm:prefix_cache_hits, both counted in tokens; Prometheus exposes them with a _total suffix [9]. Their ratio over a window is the token hit rate. Older releases exported a precomputed vllm:gpu_prefix_cache_hit_rate gauge instead. Hits from an offload tier appear in vllm:prompt_tokens_cached_by_source, broken down by tier [9]. With --enable-prompt-tokens-details, each response's usage.prompt_tokens_details.cached_tokens reports the cached tokens of that request [2], which feeds per-request accounting (Lesson 31, Per-Request Token Accounting). With --kv-cache-metrics, vLLM samples block residency histograms such as vllm:kv_block_idle_before_evict_seconds, which measures the retention computed above directly [9].

SGLang exports a sglang:cache_hit_rate gauge [10], counters of cached and prompt tokens, and with --enable-cache-report it returns cached tokens in each response's usage [4].

Always compare the measured rate with the ceiling the prompt shape allows, 74.4% for our single-turn requests, and slice it by replica and by tenant. A replica far below the others usually has a routing problem; a tenant far below the others usually has a dynamic line at the top of its prompt.

Which setup fits our deployment?

We keep vLLM, whose automatic prefix caching is already on, and fix the prompts first: the time and user name move into the user turn, tools are serialized in a fixed order, and system prompt edits are batched. That alone takes the hit rate from zero toward the 74.4% ceiling for first turns and cuts average prefill from about 65 ms to about 21.5 ms at a 90% request hit rate. Each tenant gets its own secret cache_salt, and we keep the default sha256 hash. To make conversation history hit, we route each conversation back to the replica that served it (Lesson 25) and add a 200 GiB CPU tier per replica, which stretches retention from about 1.8 minutes to about 10. We track the token hit rate per tenant and per replica against the ceiling. SGLang would serve this workload equally well; we would reach for it if the product became an agent platform with deeply branching programs.

In Practice

The first tab starts vLLM with prefix caching, per-request cache reporting, and a CPU tier, and SGLang with its equivalents. The second sends two requests that share a tenant's system prompt and prints each one's TTFT and cached tokens. The third holds PromQL queries for the hit rate and for cache retention.

Cache hit check
PromQL
# vLLM: prefix caching is on by default in current releases; the flags make it explicit,
# report cached tokens per request, and add a 200 GiB CPU tier for evicted blocks.
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --served-model-name llama-8b-chat \
  --enable-prefix-caching \
  --enable-prompt-tokens-details \
  --kv-offloading-size 200 \
  --kv-offloading-backend native

# SGLang: RadixAttention is on unless --disable-radix-cache is passed.
python -m sglang.launch_server --model-path meta-llama/Llama-3.1-8B-Instruct \
  --schedule-policy lpm \
  --enable-metrics --enable-cache-report \
  --enable-hierarchical-cache --hicache-ratio 2
import os
import time

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
SYSTEM = open("system_prompt_tenant_a.txt").read()   # ~1,500 tokens, nothing dynamic
SALT = os.environ["TENANT_A_CACHE_SALT"]             # long random secret per tenant


def ask(question: str) -> None:
    start = time.perf_counter()
    stream = client.chat.completions.create(
        model="llama-8b-chat",
        messages=[{"role": "system", "content": SYSTEM},
                  {"role": "user", "content": question}],
        max_tokens=64,
        stream=True,
        stream_options={"include_usage": True},
        extra_body={"cache_salt": SALT},
    )
    ttft, cached, prompt = None, 0, 0
    for chunk in stream:
        if ttft is None and chunk.choices and chunk.choices[0].delta.content:
            ttft = time.perf_counter() - start
        if chunk.usage:
            prompt = chunk.usage.prompt_tokens
            details = chunk.usage.prompt_tokens_details
            cached = details.cached_tokens if details else 0
    print(f"TTFT {1000 * (ttft or 0):6.1f} ms, cached {cached} of {prompt} prompt tokens")


ask("How do I reset my password?")   # fills the cache with the system prompt
ask("What is your refund policy?")   # same prefix: expect about 1,488 cached tokens
# vLLM: share of prompt tokens served from the prefix cache, last 5 minutes
sum(rate(vllm:prefix_cache_hits_total[5m]))
  / sum(rate(vllm:prefix_cache_queries_total[5m]))

# vLLM: the same per replica; one low replica usually means a routing problem
sum by (instance) (rate(vllm:prefix_cache_hits_total[5m]))
  / sum by (instance) (rate(vllm:prefix_cache_queries_total[5m]))

# vLLM with --kv-cache-metrics: median idle time of a block before eviction
histogram_quantile(0.5, sum by (le) (rate(vllm:kv_block_idle_before_evict_seconds_bucket[10m])))

# SGLang: cached tokens over prompt tokens
sum(rate(sglang:cached_tokens_total[5m])) / sum(rate(sglang:prompt_tokens_total[5m]))

Run the client twice against a fresh server: the first call should report 0 cached tokens and the second about 1,488, with a visibly shorter TTFT. If the second call also reports 0, look for a dynamic line near the top of the prompt or a missing salt match.

Other Talking Points

If there is extra time at the end of the interview, here are some additional talking points:

  • Reusing cached chunks that are not prefixes, such as retrieved documents placed in a different order, by blending their caches and recomputing a few tokens, as in CacheBlend [11].
  • Prompt Cache's modular approach, which precomputes attention states for reusable prompt modules defined in a schema [12].
  • Multi-turn serving that keeps conversation caches in a host memory and SSD hierarchy, as in CachedAttention [13].
  • Prefix-aware scheduling across a cluster, which balances cache locality against load, as in Preble [14] (Lesson 25, Request Routing).
  • Transferring prefix caches between prefill and decode workers in disaggregated serving (Lesson 34, Disaggregated Prefill and Decode).
  • Why LoRA adapters cannot share cached blocks with the base model or with each other: the adapter ID is part of the block hash, because the adapter changes the keys and values.
  • Small numerical differences between cached and recomputed KV caches, which can make outputs differ slightly between a hit and a miss even with greedy decoding.

Summary

  • Requests that start with the same tokens have identical KV cache for those tokens; system prompts, few-shot examples, documents, chat history, and agent loops all create such prefixes.
  • vLLM hashes full 16-token blocks with their parent's hash, shares blocks through reference counts, and evicts free blocks least recently used first; SGLang keeps a radix tree with token-level matching and evicts leaves first.
  • With a 1,500-token system prompt, 1,488 of 2,000 prompt tokens are reusable: prefill drops from about 65 ms to 16.6 ms on a hit, and to about 21.5 ms on average at a 90% request hit rate.
  • Fleet prefill at 1,000 requests per minute falls from about 1.08 H100s of compute to 0.36; decode time is unchanged.
  • Put static content first and dynamic content last; one timestamp at the top of the prompt makes the hit rate zero.
  • Chat history hits only if the next turn reaches the same replica and the blocks survive about 1.8 minutes of churn; routing and a CPU tier fix both.
  • Measure the token hit rate with vllm:prefix_cache_hits over vllm:prefix_cache_queries, per tenant and per replica, against the ceiling the prompt shape allows.
